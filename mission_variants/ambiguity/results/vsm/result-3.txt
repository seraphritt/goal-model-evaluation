# Goal Model for Hospital Vital-Signs Monitoring Mission

## Step-by-Step Reasoning

Before building the tables, here is how I decomposed the mission:

**1. Identifying the top-level intention and the escalation chain.**
The mission text ends with an explicit, ordered contingency chain: *normal round → if infeasible, add robots → if still infeasible, alert the manager*. Because the order is explicit and each step is triggered by the failure of the previous one ("impossibility of performing the mission," "no combination of robots can complete the mission"), this is a textbook nested **FALLBACK**, and per the rules, FALLBACK forces an **AND** decomposition at that level.

**2. Splitting "visit rooms" into "know which rooms" and "process them."**
Before any room can be visited, the robot needs to know *which* rooms are occupied and in what order (the high-risk-first constraint — "checked in the first 15 minutes" — is encoded here as a **Query** goal, directly analogous to the "Fetch Occupied Rooms" example). I treated this is a **Sequential** dependency with the actual room-processing goal (you cannot rank/visit rooms you haven't detected yet), even though the text doesn't use explicit "first…then" wording for this particular pair — I flag this as an inferred logical dependency rather than a verbatim one.

**3. Avoiding redundancy for the high-risk-first rule.**
I deliberately did **not** create two parallel sub-trees ("process high-risk room" vs. "process normal room"), because both would require an identical internal procedure (checks → identify → in-room procedure → exit). That would duplicate the same underlying intention and violate the "avoid redundancy" rule. Instead, the prioritization is captured entirely inside the **Query** goal's output (the ranked room list), keeping a single reusable "Process Occupied Room" subtree.

**4. Pre-entry checks: Parallel, not Fallback.**
"Check if the patient is available… and if there is enough battery" are listed together with no stated order between them, so this pair uses **Parallel (#)**. Each check *individually* has an explicit fallback (unavailable → come back in 5 min; low battery → recharge + reassign), so each gets its own internal **FALLBACK**.

**5. Patient identification: OR, not Fallback.**
"Either by asking or by scanning the barcode" gives two equally valid alternative methods with **no stated primacy or failure-triggered order**, so per the strict fallback rule ("if order is not explicitly stated, the annotation must not be used as fallback") I used **OR decomposition with Parallel runtime**, not Fallback.

**6. Vital-sign selection: OR, condition-dependent.**
Heart rate, blood pressure, temperature, oxygenation and glucose overlap across patient conditions (e.g., heart rate is needed for both infectious-disease and post-surgical patients). Grouping tasks *by condition* would force duplicating the same task (e.g., "Measure Heart Rate") under two different parents — a direct redundancy violation. Instead, I modeled the five measurements as **OR-children of a single goal**, where applicability is condition-dependent (explained in each task's justification) rather than universally mandatory — the closest fit given only AND/OR are available.

**7. Collection failure → questions → alert: nested Fallback.**
"Failure of collecting any vital sign triggers questions" and "non-response triggers an alert" is an explicit two-level exception chain → nested **FALLBACK**, applied once at the "Collect Required Vital Signs" level (rather than duplicated five times per vital sign) for the same redundancy-avoidance reason as point 6.

**8. Conditional but still mandatory tasks (sterilization, actuator disinfection).**
These aren't failure-triggered alternatives — they're mandatory actions that apply under a specific condition (infectious disease / physical contact). Since the formal language has no "conditional" operator, I kept them as **AND**-required tasks in the normal sequential chain and documented the condition in their justification, rather than forcing them into a Fallback they don't semantically belong to.

**9. Zero-robot rule.**
Every leaf task is phrased as something the robot (or robot fleet, for coordination tasks like reassignment/additional-robot-assignment) actually executes, so nothing was excluded. Coordination actions (reassigning tasks, bringing in additional robots) are treated as actions performed within the multi-robot system, consistent with the mission's own framing ("additional robots can be assigned").

**10. Locations.**
The description only explicitly names **"room"** ("occupied room," "the room") and **"hospital"** ("Hospital rooms may have one or more beds"). I used only these two, never inventing locations like "charging station" or "corridor" that aren't in the text — flagged explicitly wherever the description under-specifies (e.g., recharge location).

## Logical Relationships

- **G1 -> G2, AT24, AT25 [AND] [FALLBACK(FALLBACK(G2, AT24), AT25)]**
  - **Justification**: The text gives an explicit, condition-triggered escalation order: normal rounds (G2) are attempted; if the mission can't be completed in time, additional robots are added (AT24); if that still isn't enough, the manager is alerted (AT25). Each step is a failure-triggered alternative to the previous one — the defining criterion for FALLBACK, nested because it's a three-way chain. FALLBACK mandates AND decomposition.

- **G2 -> G3, G4 [AND] (sequential)**
  - **Justification**: The robot must know which rooms are occupied and in what priority order (G3) before it can process them (G4) — a logical data dependency, not a stated alternative, so AND + Sequential.

- **G3 -> AT1, AT2 [AND] (sequential)**
  - **Justification**: Rooms must be detected before they can be ranked/prioritized; both are required (AND), and ranking logically depends on the detection output (sequential).

- **G4 -> G5, G8, G9, G13 [AND] (sequential)**
  - **Justification**: The description's own narrative order is explicit: pre-entry checks ("before entering the room…") → patient identification (needed due to multi-bed rooms, occurring around entry) → in-room procedure ("once inside the room…") → exit procedures ("once the patient is checked…"). All four are mandatory (AND) and strictly ordered.

- **G5 -> G6, G7 [AND] (parallel)**
  - **Justification**: "Check if the patient is available… and if there is enough battery" are presented jointly with no stated order between them — both mandatory (AND), but free to be checked in either order or concurrently (Parallel).

- **G6 -> AT3, AT4 [AND] FALLBACK(AT3, AT4)**
  - **Justification**: Explicit IF-triggered alternative: check availability; if unavailable, come back in 5 minutes. FALLBACK forces AND.

- **G7 -> AT5, AT6, AT7 [AND] FALLBACK(AT5, (AT6 # AT7))**
  - **Justification**: Explicit IF-triggered alternative: check battery; if insufficient, recharge **and** reassign tasks (joined by "and," no stated order between the two, hence Parallel inside the fallback branch). FALLBACK forces AND overall.

- **G8 -> AT8, AT9 [OR] (parallel)**
  - **Justification**: "Either by asking… or by scanning the barcode" — two equally valid, unordered alternative methods, either sufficient; no failure/order is stated, so OR (not Fallback) with Parallel runtime.

- **G9 -> G10, G11, AT20 [AND] (sequential)**
  - **Justification**: Interaction happens first ("approach…announce…instructions"), vital-sign collection follows (implied immediately after instructions), and actuator disinfection happens explicitly "afterwards." All mandatory, strictly ordered.

- **G10 -> AT10, AT11, AT12 [AND] (sequential)**
  - **Justification**: The text lists these three actions in an explicit, fixed order ("approach the patient, announce the procedure… and provide instructions").

- **G11 -> G12, AT18, AT19 [AND] FALLBACK(G12, FALLBACK(AT18, AT19))**
  - **Justification**: Explicit nested exception chain — attempt measurement (G12); if any sign fails to be collected, ask assessment questions (AT18); if there's no response, alert the nurse/doctor (AT19). Each step triggered by the prior one's failure — nested FALLBACK, forcing AND.

- **G12 -> AT13, AT14, AT15, AT16, AT17 [OR] (parallel)**
  - **Justification**: Which signs are required depends on the patient's condition (infectious disease → HR+BP+Temp+Oxygenation; post-surgical → HR+Oxygenation; diabetes history → glucose). Since no single patient necessarily needs all five, and the applicable subset varies, OR best captures this conditional applicability (closest available fit given only AND/OR), with Parallel since no order among measurements is stated.

- **G13 -> AT21, AT22, AT23 [AND] (sequential)**
  - **Justification**: "Once the patient is checked, the robot should mark it as done and proceed to the next room" gives explicit order (mark → proceed); sterilization is explicitly tied to the moment of exiting ("comes out of a room"), placed between marking done and departing. Sterilization is conditional (infectious-disease rooms only) but still mandatory (AND) whenever that condition holds.

## Key Assumptions (flagged for transparency)

- "Hospital" and "Room" are the only locations explicitly cited in the mission text; I avoided inventing locations like "charging station" or "corridor."
- Coordination tasks (AT7, AT24) are treated as actions performed within the multi-robot system (not a "zero-robot" external process), consistent with the mission being framed as a multi-robot system.
- A few sequential orderings (G2→G3;G4, G3→AT1;AT2) are logical/data dependencies I inferred rather than verbatim "first…then" statements in the text — flagged in case you'd prefer Parallel there instead.
- The OR-decomposition used for condition-dependent vital signs (G12) and for patient identification (G8) is a best fit given the model only supports AND/OR; a richer "conditional" or "context-variant" decomposition type would represent these more precisely if your formalism supports one.
