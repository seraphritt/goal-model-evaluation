# Goal Model for the Hospital Vital-Signs-Checking Mission

## Step-by-Step Reasoning

Before building the tables, here is my analysis of the mission description and the key design decisions I made (with justification), so the goal model is traceable back to the text.

**1. Identifying the top-level recurring mission.**
"Every two hours, all patient's vital signs should be checked" is the trigger/periodicity of the whole mission — it is not an action by itself, so I encode it as the recurrence condition of the root goal (G1) rather than as a separate node.

**2. The "visit every occupied room" goal is generic, not per-instance.**
Like the example given ("Check Room Patients, target: all rooms were checked"), I modeled **one** goal ("Visit Occupied Rooms") whose target condition is "all occupied rooms visited," and whose children describe the *generic* process applied to a room. I did **not** create one branch per room — that would blow up the tree and violates the "avoid redundancy" rule, since every room-visit shares the same underlying intention.

**3. High-risk timing constraint (first 15 minutes) is a scheduling constraint, not a new goal.**
"All patients in high risk must be checked in the first 15 minutes" does not introduce a new action — it constrains *when* the existing room-visiting process (G2) is applied to certain rooms. Making a parallel "visit high-risk room" branch would duplicate the same intention as "visit room." I therefore embedded this as a timing clause inside G2's target condition and justification, instead of creating a redundant sibling goal.

**4. Splitting the room-visit flow using explicit sequencing cues.**
The text explicitly separates the flow using "Before entering…", "Once inside…", and "Once the patient is checked…proceed to next room" — these are explicit temporal markers, so I used **sequential (;)** for Pre-Entry Checks → In-Room Checking → Complete Room Visit.

**5. Fallback usage — strictly where the text gives an explicit "if X fails, do Y."**
I used FALLBACK only for the four cases where the text explicitly states a condition and an alternative:
- Patient not available → wait 5 minutes and retry.
- Not enough battery → recharge & reassign tasks.
- Failure to collect vital signs → ask questions.
- No response to questions → alert nurse/doctor.
- Mission infeasible in time → add robots → if still infeasible → alert manager.

I avoided using FALLBACK for the sterilization/disinfection clauses, because those are not "alternative behavior if the first fails" — they are additional mandatory steps triggered by a patient-category condition, so they are modeled with AND + sequential, not FALLBACK.

**6. Parallel vs. unspecified order.**
Where the text lists items together with no ordering words ("heart rate, blood pressure, body temperature, and blood oxygenation"; "recharge… and… reassign"; "asking or… scanning"), I used **parallel (#)**, since parallel only expresses *possibility* of concurrency, not an obligation — a safer and more faithful reading than inventing a sequence that isn't stated.

**7. Identify-patient as a Query Goal.**
"The robot has to identify the correct patient either by asking or by scanning the barcode" is pure information retrieval (no world-state change is intended) — this matches the Query Goal definition exactly, with OR decomposition (explicit "either…or").

**8. Conditional vital-sign sets modeled as AND, not OR.**
Although which vitals are required depends on the patient's condition (infectious, post-surgical, diabetic), I modeled "Collect Required Vital Signs" as an **AND** of all five measurement capabilities, because AND expresses that *all jointly-required measurements for a given condition* must be completed (e.g., an infectious-disease patient needs HR **and** BP **and** Temp **and** O2 — missing one is a failure). OR would incorrectly imply that completing just one suffices for any patient. The condition-dependence is captured in each task's justification rather than in the operator.

**9. Zero-robot exclusion check.**
Two clauses needed re-framing to ensure they are robot-executed, per the "zero robot" exclusion rule:
- "Additional robots can be assigned to help" → reframed as a task performed **by the additional robot(s) themselves** (joining and executing part of the visiting goal), not an abstract non-robot "assignment" decision.
- "Reassign tasks" → modeled as a coordination action performed by two robots (the handing-off robot and the receiving robot), both of which are robots, so it is retained.

**10. Locations.**
Per the instruction "you should not make up a location — all locations must be cited in the description," the only locations explicitly present in the text are **"room" / "hospital room(s)"** and **"site" / "hospital."** I did not invent locations like "corridor" or "charging station," since they are not mentioned; tasks that occur between rooms or at a mission-management level are tagged **"Hospital."**

## Logical Relationships

- **G1 -> G2, AT22, AT23 [AND][FALLBACK(G2, FALLBACK(AT22, AT23))]**
  - **Justification**: The mission is normally completed by the assigned robot(s) visiting all rooms (G2). Only if "impossibility of performing the mission in the required time" occurs are additional robots deployed (AT22); only if "no combination of robots can complete the mission" does escalation to the manager occur (AT23). This is an explicit, ordered, condition-triggered chain — the textbook case for nested FALLBACK. AND is used because FALLBACK pairs are always AND-related per the modeling rule.

- **G2 -> G3, G8, G12 [AND](sequential)**
  - **Justification**: All three phases are required for a complete room visit (AND), and the text gives explicit ordering words ("before entering," "once inside," "once checked… proceed") — sequential.

- **G3 -> G4, G5, G6 [AND](parallel)**
  - **Justification**: Identification, availability, and battery are all required before entry (AND: "must check if…and if…"). No order between them is stated, so parallel is used rather than assuming an unstated sequence.

- **G4 -> AT1, AT2 [OR](parallel)**
  - **Justification**: "Either by asking or by scanning" is an explicit alternative (OR); parallel expresses that neither method is mandated before the other — they are independent, substitutable options.

- **G5 -> AT3, AT4 [AND][FALLBACK(AT3, AT4)]**
  - **Justification**: "If the patient is not available, the robot should come back in 5 minutes" is an explicit condition/alternative — FALLBACK; AND because FALLBACK pairs are AND-related.

- **G6 -> AT5, G7 [AND][FALLBACK(AT5, G7)]**
  - **Justification**: "If there is not enough battery, the robot should recharge and tasks need to be reassigned" is an explicit condition/alternative — FALLBACK; AND for the same reason as above.

- **G7 -> AT6, AT7 [AND](parallel)**
  - **Justification**: Both recharging and reassignment are required ("recharge" "and" "reassigned" — AND). No order is stated and reassignment need not wait for recharging — parallel.

- **G8 -> AT8, AT9, AT10, G9, AT18 [AND](sequential)**
  - **Justification**: All steps are required for an in-room visit (AND). The text lists "approach… announce… provide instructions" in that order, then vitals handling, then "disinfect its actuators afterwards" — all explicit sequencing — sequential.

- **G9 -> G10, G11 [AND][FALLBACK(G10, G11)]**
  - **Justification**: "The failure of collecting any necessary vital signs should trigger a set of questions" is an explicit condition/alternative — FALLBACK; AND per the FALLBACK rule.

- **G10 -> AT11, AT12, AT13, AT14, AT15 [AND](parallel)**
  - **Justification**: Each patient category requires a *combination* of measurements (e.g., infectious-disease patients need HR **and** BP **and** Temp **and** O2) — AND. No order is given among the measurements in the text — parallel.

- **G11 -> AT16, AT17 [AND][FALLBACK(AT16, AT17)]**
  - **Justification**: "In case of non-response, an alert should be sent" is an explicit condition/alternative to asking questions — FALLBACK; AND per the rule.

- **G12 -> AT19, AT20, AT21 [AND](sequential)**
  - **Justification**: All three are required to finish a visit (AND). "Once the patient is checked… mark it as done and proceed to the next room," combined with "when a robot comes out of a room… sterilization must be performed," gives an explicit order: mark done → sterilize (if applicable, on exit) → proceed — sequential.
