# Multi-Robot Goal Model: Hospital Vital Signs Checking Mission

## Step-by-Step Reasoning

Before presenting the model, here is the reasoning trail I followed:

**1. Finding the root intention.** The description opens with "all patient's vital signs should be checked" and immediately restates this operationally as "the assigned robot should visit every occupied room." These are the *same intention* expressed twice (one declarative, one operational), so per the anti-redundancy rule I merged them into a single root goal rather than creating a parent/child pair that would just duplicate the same idea.

**2. Separating per-room work from mission-level work.** The text has two layers: (a) a detailed procedure for *one* room visit (pre-entry checks → in-room procedure → wrap-up), and (b) mission-level concerns that cut across all rooms (priority scheduling of high-risk patients, and the escalation chain "additional robots → alert manager"). I modeled (a) as a reusable sub-goal applied across the room collection, and (b) as siblings at the root.

**3. Detecting FALLBACK vs SEQUENTIAL.** I only used FALLBACK where the text gives a *normal action* plus a *conditional alternative triggered by a failure/condition* ("if not available...", "if not enough battery...", "failure of collecting... triggers questions", "if patient does not answer... alert"). Where the text simply lists ordered actions with no failure/condition ("approach, announce, provide instructions"; "mark as done and proceed"), I used SEQUENTIAL instead, since no explicit success/failure branching is stated.

**4. Resolving the "additional robots / alert manager" cascade.** This is a textbook nested FALLBACK: attempt the mission with the currently assigned robot(s) → if infeasible in time, add robots → if *no combination* works, alert the manager. I modeled it as `FALLBACK(ProcessRooms, FALLBACK(AssignAdditionalRobots, AlertManager))`. Note: this abstracts away the implicit retry loop (adding robots conceptually means re-attempting the room-visiting goal) — goal models don't represent recursive retries as cycles, so this is a necessary simplification, flagged here explicitly.

**5. Query vs Achieve vs Perform.** I classified “identify patient” and “collect vital signs” as **Query** goals because their purpose is purely epistemic (obtaining the patient’s identity or physiological values), not changing world state. Orchestration goals that resolve a condition into an action (availability/battery handling, the overall room visit) are **Achieve** goals, since they have a clear target condition. The patient-preparation sequence (approach/announce/instruct) is a **Perform** goal — it is a fixed action sequence with no non-trivial target state beyond its own execution.

**6. The "either ask or scan" OR.** This is an explicit OR-particle case ("either...or"), so I used OR-decomposition. Since no order or failure-trigger is stated between the two methods, I annotated runtime as parallel (`#`) — read as "possibility, not obligation" that either method may be used, rather than a literal simultaneous execution.

**7. Avoiding duplicated goal wrappers.** Several single-action requirements (reschedule-in-5-min, recharge, reassign, ask-questions, alert-nurse, sterilize, mark-done, proceed) would have produced goals with only one child, violating the "minimum two subgoals" rule for AND/OR. I folded these directly in as **Tasks** under their nearest meaningful parent goal instead of wrapping each in a trivial goal, which keeps every AND/OR decomposition meaningful.

**8. Category-specific vitals (infectious/post-surgical/diabetes).** These are presented as parallel, non-exclusive classification rules (a patient could be both infectious *and* diabetic), so I used OR-decomposition at the parent ("Collect Required Vital Signs") with parallel runtime — OR because satisfying whichever categories apply is sufficient, parallel because multiple categories can co-apply with no stated order.

**9. Zero-robot check.** Every node is executed or triggered by the assigned robot (including alerts, assumed sent via the robot's comms system), so nothing was excluded under the "zero-robot" rule.

## Logical Relationships

- **G1 -> AT1, G2, AT25, AT26 [AND][AT1 ; FALLBACK(G2, FALLBACK(AT25, AT26))]**
  - **Justification**: Scheduling (AT1) must precede room-visiting; room-visiting (G2) is attempted first, falling back to adding robots (AT25) if infeasible in time, and further to manager alert (AT26) if no robot combination suffices — explicitly cascaded in the text, and FALLBACK mandates AND between branches.

- **G2 -> G3, G7, AT22, AT23, AT24 [AND][sequential: G3 ; G7 ; AT22 ; AT23 ; AT24]**
  - **Justification**: The narrative gives a strict chronological procedure for one room ("before entering... once inside... once checked...").

- **G3 -> G4, G5, G6 [AND][G4 ; (G5 # G6)]**
  - **Justification**: All three preconditions are explicitly required before entry; identification logically precedes the other two (needed to know which patient's availability/battery context applies), while availability and battery have no stated order between them.

- **G4 -> AT2, AT3 [OR][parallel: AT2 # AT3]**
  - **Justification**: Explicit "either...or" alternative identification methods; no stated precedence, so parallel/possibility is used rather than fallback.

- **G5 -> AT4, AT5 [AND][FALLBACK(AT4, AT5)]**
  - **Justification**: Normal check (AT4) with a condition-triggered alternative (AT5) if the patient is unavailable.

- **G6 -> AT6, AT7, AT8 [AND][FALLBACK(AT6, (AT7 # AT8))]**
  - **Justification**: Normal check (AT6) with a condition-triggered compound alternative (recharge and reassign, unordered relative to each other) if battery is insufficient.

- **G7 -> G8, G9, AT21 [AND][sequential: G8 ; G9 ; AT21]**
  - **Justification**: Text sequences preparation, then collection, then (implicitly, after patient contact) disinfection.

- **G8 -> AT9, AT10, AT11 [AND][sequential: AT9 ; AT10 ; AT11]**
  - **Justification**: Actions are listed in their necessary chronological order (you must approach before announcing, announce before instructing).

- **G9 -> G10, AT19, AT20 [AND][FALLBACK(G10, FALLBACK(AT19, AT20))]**
  - **Justification**: Normal collection (G10), falling back to questions (AT19) on failure, falling back further to alerting staff (AT20) on non-response — a nested FALLBACK exactly mirroring the two chained conditions in the text.

- **G10 -> G11, G12, AT18 [OR][parallel: G11 # G12 # AT18]**
  - **Justification**: The three condition-specific requirement sets are alternative, non-mutually-exclusive branches depending on patient classification (a patient may match more than one), so OR-decomposition with parallel runtime.

- **G11 -> AT12, AT13, AT14, AT15 [AND][parallel: AT12 # AT13 # AT14 # AT15]**
  - **Justification**: "must be checked for heart rate, blood pressure, body temperature, and blood oxygenation" is conjunctive; no order given for the measurements.

- **G12 -> AT16, AT17 [AND][parallel: AT16 # AT17]**
  - **Justification**: "must be checked for heart rate and blood oxygenation" is conjunctive; no order given.

### Notes on modeling choices worth flagging
- The 2-hour recurrence is treated as a *triggering condition* for re-instantiating G1 rather than a tree node, since goal models represent decomposition structure, not temporal recurrence.
- The "assign additional robots → retry visiting" loop is abstracted as a single fallback step rather than an explicit cycle, since goal trees don't natively represent recursive retries.
- Recharge/reassign locations default to the broadest explicitly-named location ("Hospital") since no specific sub-location (e.g., a charging station) is mentioned in the description — I avoided inventing one per your location constraint.
