# Mission Analysis & Goal Model: Hospital Vital-Sign Checking Multi-Robot Mission

## Step-by-Step Reasoning

**Step 1 — Segmenting the mission.** I parsed the description into discrete behavioral units: (a) the periodic trigger (every 2h), (b) room-visiting logic, (c) pre-entry conditions (availability, battery) with explicit IF-alternatives, (d) patient identification (explicit OR), (e) the physical approach/communication sequence, (f) vital-sign collection with a two-level escalation chain (failure → questions → alert), (g) condition-dependent vital subsets (infectious/post-surgical/diabetic), (h) hygiene protocols (sterilization, actuator disinfection) as conditional post-actions, (i) a temporal SLA for high-risk patients, and (j) a mission-level contingency chain (extra robots → manager alert).

**Step 2 — Detecting runtime operators.** I only applied **FALLBACK** where the text gives an explicit IF-conditioned alternative with a clear "try this, then that" order (patient unavailable → wait 5 min; battery low → recharge+reassign; vitals failed → ask questions → alert; mission infeasible → add robots → alert manager). Where the text lists actions in a narrated order without conditionality, I used **sequential (;)** (approach→announce→instruct; mark done→proceed). Where no order is given and actions are logically independent, I used **parallel (#)** (the five vital-sign measurements; recharge/reassign; the two pre-entry fallback branches relative to each other).

**Step 3 — Classifying goal types.** Checks that retrieve world-state information (availability, battery, occupancy, condition category) are **Query**. Composite objectives with a reachable end-state (a room fully checked, vitals collected, SLA met) are **Achieve**. Pure action-execution without a deeper target state (approach/announce/instruct; mark-done/disinfect/sterilize/proceed) are **Perform**.

**Step 4 — Avoiding redundancy.** Heart rate and blood oxygenation are required by *both* infectious-disease and post-surgical patients. Rather than creating duplicate goals per condition, I created **one** "Measure Vital Signs" goal (G14) with 5 atomic tasks (HR, BP, Temp, SpO2, Glucose) and a separate Query goal (G13) that determines which subset applies to the current patient — this keeps each distinct intention (each physical measurement) represented exactly once.

**Step 5 — Zero-robot filter.** Every leaf Task is executed by the robot physically present (Number of Robots ≥ 1). Pure Query leaf-goals (room occupancy, availability, battery, condition) are not decomposed into separate tasks since they are directly realized by the acting robot's sensing/communication capability — no goal/task without robot involvement was included.

**Step 6 — Numbering.** IDs were assigned by strict depth-first traversal, goals and tasks numbered independently.

## Logical Relationships

- **G1 -> G2, G16 [AND] FALLBACK(G2,G16)**
  - **Justification**: The mission's normal flow (visit rooms) and its explicit contingency (add robots / alert manager) form a primary-attempt/alternative pair, triggered only on failure to meet the time requirement — the defining condition for FALLBACK.

- **G2 -> G3, G4, G5 [AND] (sequential: (G3;G4);G5)**
  - **Justification**: Occupancy must be known before priority scheduling, and scheduling must precede general execution — each step is a logical prerequisite for the next, with no indication they can overlap.

- **G4 -> AT1, AT2 [AND] (sequential: AT1;AT2)**
  - **Justification**: You must identify high-risk patients before you can schedule them first; both are required to satisfy the 15-minute SLA.

- **G5 -> G6, G9, G10 [AND] (sequential: (G6;G9);G10)**
  - **Justification**: Text explicitly orders "before entering" (G6) → implicit identification upon entering a multi-bed room (G9) → "once inside" (G10).

- **G6 -> G7, AT3, G8, AT4, AT5 [AND] FALLBACK(G7,AT3) # FALLBACK(G8,(AT4#AT5))**
  - **Justification**: "and" ties the availability check and battery check together (AND); each has its own explicit IF-triggered alternative (FALLBACK); no order is stated between the two checks (parallel), nor between recharge and reassignment (parallel).

- **G9 -> AT6, AT7 [OR] (parallel: AT6#AT7)**
  - **Justification**: "either by asking or by scanning" is an explicit alternative — one is sufficient (OR); no order is implied between them.

- **G10 -> G11, G12, G15 [AND] (sequential: (G11;G12);G15)**
  - **Justification**: The narrative explicitly sequences engagement, then vital collection, then visit closure.

- **G11 -> AT8, AT9, AT10 [AND] (sequential: (AT8;AT9);AT10)**
  - **Justification**: Listed in a fixed narrative order ("approach... announce... provide instructions"), implying a natural sequence of physical/communicative acts.

- **G12 -> G13, G14, AT16, AT17 [AND] G13;FALLBACK(FALLBACK(G14,AT16),AT17)**
  - **Justification**: The applicable vitals must be determined (G13) before measurement (sequential); the measurement/escalation chain matches the nested-FALLBACK pattern exactly as described (failure→questions, no answer→alert).

- **G14 -> AT11, AT12, AT13, AT14, AT15 [AND] (parallel)**
  - **Justification**: All five measurements are complementary (AND) with no stated execution order among them (parallel), while which subset is actually invoked for a given patient is governed by G13's result.

- **G15 -> AT18, AT19, AT20, AT21 [AND] (sequential: ((AT18;AT19);AT20);AT21)**
  - **Justification**: Marking done and proceeding are explicitly sequential; the hygiene steps are conditionally inserted between completion and departure, consistent with their "afterwards"/"coming out" triggers.

- **G16 -> AT22, AT23 [AND] FALLBACK(AT22,AT23)**
  - **Justification**: Additional robots are explicitly the first remedy attempted, with the manager alerted only if that combination still cannot complete the mission — an explicit primary/alternative order.
