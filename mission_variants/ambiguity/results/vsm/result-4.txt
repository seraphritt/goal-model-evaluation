# Multi-Robot Goal Model: Hospital Vital Signs Checking Mission

## Step-by-Step Reasoning

Before building the tables, here is my analysis process:

**1. Identifying the top-level structure.** The description ends with a clear escalation chain: (a) normally the *assigned robot(s)* do the rounds, (b) *if that's not enough time-wise*, additional robots are brought in, (c) *if even that fails*, the site manager is alerted. The repeated "if X fails, then Y" pattern is the textbook trigger for nested **FALLBACK**, so the root of the tree is a 3-way nested fallback.

**2. Recognizing a reusable sub-procedure.** The instructions warn against duplicating goals with the same intention. The entire "visit a room" procedure (pre-checks → approach/announce/instruct → collect vitals → exit/decontaminate) is described *once*, generically, and must be applied to every occupied room — including, as a prioritized subset, high-risk rooms (first 15 minutes). Rather than writing this subtree twice, I modeled it once (**G4 – Perform Room Visit Procedure**) and **reused** it as a child both of the "high-risk-first" goal and of the "visit remaining rooms" goal, and again when additional robots are assigned. This satisfies the anti-redundancy rule and is why you'll see G4 (and G2) appear under more than one parent in the Logical Relationships section.

**3. Distinguishing FALLBACK from OR.** Three spots in the text are genuine IF-triggered alternatives (patient not available → wait 5 min; battery insufficient → recharge/reassign; vital sign not collected → ask questions → if unanswered, alert staff). These are FALLBACK, not OR, because order is explicit and the second branch is only attempted if the first fails, and because both parts are AND-necessary to the outcome (per the FALLBACK→AND rule).

**4. OR vs AND for condition-dependent requirements.** The infectious/post-surgical/diabetic vital-sign requirements, and the sterilize/disinfect-actuators requirement, are each conditionally triggered by patient/robot state rather than always jointly mandatory for every patient. Since OR's only formal requirement is "fulfilling one child is enough" (it does not forbid more than one being true), OR is the better formal fit for "whichever condition(s) apply must be satisfied" — even though the text doesn't use an explicit "or" particle here, the semantics (not-always-all-required) match OR, not AND.

**5. Goal typing.** Identifying the patient is pure information-gathering → **Query**. Simple fixed-order physical actions with no target state or contingency (approach/announce/instruct; decontamination) → **Perform**. Everything involving planning toward a state with contingency/fallback logic → **Achieve**.

**6. Zero-robot exclusion.** Every leaf task was checked against "is a robot doing this?" — all 24 tasks are robot-executed (including alerts, which I treat as issued by the robot/coordinating robot on duty), so nothing was dropped for being a zero-robot activity.

## Logical Relationships

- **G1 -> G2, G19, AT24 [AND][FALLBACK(FALLBACK(G2, G19), AT24)]**
  - **Justification**: AND is mandatory because FALLBACK-connected alternatives are always AND per the rules. The nested FALLBACK mirrors "additional robots… in case of impossibility… manager alerted if no combination… can complete the mission."

- **G2 -> G3, G4 [AND][(sequential) G3;G4]**
  - **Justification**: Both must happen (high-risk coverage and full room coverage); high-risk rooms must be finished within their 15-minute deadline before/while the remaining rooms are processed, so sequential ordering is explicit.

- **G3 -> G4, AT22 [AND][(parallel) G4#AT22]**
  - **Justification**: G4 is reused here (same "visit a room" procedure, applied to high-risk rooms) rather than duplicated. Monitoring the 15-minute deadline runs concurrently with the visits, not before/after them.

- **G4 -> G5, G11, G17 [AND][(sequential) G5;G11;G17]**
  - **Justification**: The description explicitly orders pre-entry checks → in-room procedure → exit/finalize ("before entering… once inside… once checked…").

- **G5 -> G6, G9 [AND][(parallel) G6#G9]**
  - **Justification**: "check if the patient is available… **and** if there is enough battery" — joined by "and," no explicit order, both mandatory.

- **G6 -> G7, G8 [AND][(sequential) G7;G8]**
  - **Justification**: Identification must occur before confirming that specific patient's availability (especially in multi-bed rooms), even though the text mentions identification afterward as an explanation.

- **G7 -> AT1, AT2 [OR][(parallel) AT1#AT2]**
  - **Justification**: Explicit textual OR ("either by asking or by scanning"). Parallel is used (rather than fallback) since this is a free choice of method, not a failure-triggered retry.

- **G8 -> AT3, AT4 [AND][FALLBACK(AT3, AT4)]**
  - **Justification**: Explicit IF-condition: "if the patient is not available, the robot should come back in 5 minutes" — classic FALLBACK.

- **G9 -> AT5, G10 [AND][FALLBACK(AT5, G10)]**
  - **Justification**: Explicit IF-condition: "if there is not enough battery, the robot should recharge and the tasks need to be reassigned."

- **G10 -> AT6, AT7 [AND][(parallel) AT6#AT7]**
  - **Justification**: Recharging and reassigning are both required, and nothing forces one to wait for the other.

- **G11 -> G12, G13 [AND][(sequential) G12;G13]**
  - **Justification**: Patient preparation (approach/announce/instruct) explicitly precedes vital-sign collection in the text.

- **G12 -> AT8, AT9, AT10 [AND][(sequential) AT8;AT9;AT10]**
  - **Justification**: The three actions are listed in a fixed, meaningful order (you must approach before announcing, announce before instructing).

- **G13 -> G14, AT16, AT17 [AND][FALLBACK(G14, FALLBACK(AT16, AT17))]**
  - **Justification**: Double explicit IF-trigger: "the failure of collecting any necessary vital signs should trigger a set of questions… if the patient does not answer the questions, an alert should be sent."

- **G14 -> G15, G16, AT15 [AND][(parallel) G15#G16#AT15]**
  - **Justification**: AND at this level because satisfying the condition-relevant branch(es) is jointly required for *this* patient's complete check; parallel because no order is implied between unrelated measurement sets.

- **G15 -> AT11, AT12, AT13, AT14 [OR][(parallel) AT11#AT12#AT13#AT14]**
  - **Justification**: This whole branch's Relation to its parent (G14) is OR, since it is condition-triggered (infectious disease) rather than universally mandatory. Internally, all four signs are AND-required when this branch applies, run in parallel (no stated order).

- **G16 -> AT11, AT14 [OR][(parallel) AT11#AT14]**
  - **Justification**: Relation to parent G14 is OR (condition-triggered, post-surgical). Reuses AT11/AT14 rather than redefining "measure heart rate" — same intention, same task.

- **G17 -> AT18, G18, AT19 [AND][(sequential) AT18;G18;AT19]**
  - **Justification**: "Once the patient is checked, the robot should mark it as done and proceed to the next room," with decontamination occurring at the point of exit, before moving on.

- **G18 -> AT20, AT21 [OR][(parallel) AT20#AT21]**
  - **Justification**: Each decontamination action is independently condition-triggered (infectious-room exit vs. patient contact) — OR fits since fulfilling whichever applies is sufficient, and both can apply together, run in parallel.

- **G19 -> AT23, G2 [AND][(sequential) AT23;G2]**
  - **Justification**: Additional robots must be assigned before the (reused) room-visiting goal can resume with the expanded team.

Of Claude's design choices, two are judgment calls worth flagging for the mission owner to double-check: (1) classifying the three condition-specific vital-sign checks and the two decontamination actions as **OR** (based on "one branch suffices" semantics) rather than AND, since the description itself never uses an explicit "or"; and (2) attaching the glucose-level check directly as a single task under G14 rather than wrapping it in its own goal, since the text gives it only one associated action.
