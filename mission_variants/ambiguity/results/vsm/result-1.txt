# Goal Model Analysis: Multi-Robot Hospital Vital-Signs Mission

## 1. Reasoning & Key Design Decisions (step-by-step)

Before building the tables, here is the reasoning path I followed, including the trade-offs I had to resolve:

**a) Root goal and periodicity.** The mission is triggered "every two hours." The formalism given has no construct for temporal triggers, so I did **not** create a goal for "wait two hours." Instead, I treat the 2-hour cycle as a *re-activation condition* for the root goal (G1), stated in its text/justification only — creating a goal for it would be a goal with "zero robot" action (nobody *performs* "waiting two hours"), which the rules explicitly forbid.

**b) Mission-level Fallback.** "Additional robots can be assigned... in case of impossibility" and "the manager must be alerted if no combination of robots can complete the mission" are two *explicitly ordered, condition-triggered* alternatives (first try normally, then add robots, then escalate to a human). This is a textbook nested **FALLBACK**: `FALLBACK(FALLBACK(G2, AT24), AT25)`. Per the rules, Fallback pairs are always AND-related.

**c) Query goal for room discovery.** The prompt's own example ("Fetch Occupied Rooms") is explicitly present in the description ("the robot should visit every occupied room"/"rooms may have one or more beds"). Knowing *which* rooms are occupied, and the patients' condition/risk flags (needed later for vital-sign selection and for the 15-minute high-risk rule) is pure information-gathering → **Query Goal**, not an action.

**d) The "high-risk in first 15 minutes" rule — a deliberate non-duplication decision.** This rule does not introduce a *new* intention (the intention is still "visit & check the room"); it only constrains the **order/schedule** in which the same per-room process (G4) is applied. Creating a second, parallel copy of the entire room-visiting subtree ("CheckHighRiskRoom") would duplicate an identical intention with only a timing difference — explicitly forbidden by the anti-redundancy rule. I therefore modeled it as a **scheduling policy** carried by the risk data returned from G3 (Fetch Occupied Rooms) and applied when G4 is invoked, and documented it in the justification of G2/G4 rather than as a separate tree node.

**e) Identify Patient before Check Availability.** The text says rooms may have multiple beds, "**so**" the robot must identify the patient — the "so" signals that identification is a *prerequisite* for correctly checking availability for *that* patient. Hence Identify (query) → Check Availability (task) are sequential, nested under one Achieve goal.

**f) Ask vs. Scan = OR.** "Either by asking... or by scanning" is an explicit alternative → OR decomposition. Because no priority order between the two is stated, runtime is parallel (`#`), not Fallback (Fallback requires an explicit first/second order, which is absent here).

**g) Availability / Battery checks = Achieve, not Query.** Although superficially "checking" something sounds like Query, each check is immediately coupled with an explicit contingent *action* (reschedule in 5 min; recharge + reassign) described as part of reaching a state ("ready to enter the room"). Since the goal's real intent is to *establish* entry-readiness (a state), not merely to learn a fact, I classified these as **Achieve** goals, each internally using FALLBACK against the negative outcome. "Identify Patient" remains Query because its sole purpose is information (who is this patient), with no contingent action tied to failure.

**h) Vital-sign selection = OR, not AND.** The text gives three *condition-dependent* rules (infectious disease → 4 signs; post-surgical → 2 signs; diabetes → 1 sign). Not every patient needs all five signs — which ones apply depends on the patient's condition. Using AND would wrongly force every patient through all five checks. I therefore flattened the three condition-rules into a single **OR**-decomposed goal over the five concrete vital-sign tasks (avoiding duplicating "Collect Heart Rate" under three different condition-subtrees, which the tree structure cannot do without violating anti-redundancy / single-parent constraints anyway). The condition-specific logic is captured in the justification, not the structure.

**i) Vital-sign failure → assessment → alert = nested Fallback**, modeled once, generically ("a **set** of questions... for **those signs** that failed") — exactly matching the text's implication of a single, unified assessment process rather than one per vital sign (again avoiding redundant duplication).

**j) Sterilization & actuator disinfection** are both *conditional*, *post-task* hygiene steps with no explicit order between each other, but both occur after the in-room work and before moving to the next room → parallel to each other, sequential relative to "mark done" and "proceed."

**k) Zero-robot check.** I verified every leaf task is actually executed by a robot (queries, physical actions, alerts sent by the robot's communication module) — none were excluded.

**l) Task granularity & Location/Robots.** Every task was checked against the text so no location is invented: only "hospital room" / "hospital" (as the general site, e.g., the hospital database, charging station, corridors) are mentioned, so all Locations are grounded in those. Number of Robots defaults to 1 for atomic, single-robot actions; tasks that scale with the robot pool (reassigning tasks, adding robots) are given as a variable range `[1,n]`, where *n* is bounded by the total robot fleet available to the mission (no numeric fleet size is given in the text, so a variable is used rather than inventing a number).

## 5. Logical Relationships

- **G1 -> G2, AT24, AT25 [AND][FALLBACK(FALLBACK(G2,AT24),AT25)]**
  - **Justification**: The mission is attempted normally (G2) first; if infeasible in time, additional robots are tried (AT24); if that also fails, the manager is alerted (AT25). This is an explicit, order-dependent exception chain → nested Fallback, always AND-related.

- **G2 -> G3, G4 [AND][(sequential)]**
  - **Justification**: The robot must first learn which rooms are occupied (and their condition/risk data) before it can process them — explicit cause/effect ("therefore").

- **G3 -> AT1, AT2 [AND][(parallel)]**
  - **Justification**: Both occupancy and condition/risk data are needed as joint inputs; nothing indicates one must precede the other.

- **G4 -> G5, G9, G14 [AND][(sequential)]**
  - **Justification**: The text's own structure — "before entering," "once inside," "once checked... proceed" — describes three mandatory, strictly ordered phases.

- **G5 -> G6, G8 [AND][(parallel)]**
  - **Justification**: Explicit conjunction ("check... and if there is enough battery"); the two checks don't depend on each other.

- **G6 -> G7, AT5, AT6 [AND][(G7 ; FALLBACK(AT5,AT6))]**
  - **Justification**: Identification must happen first (needed to know *whom* to check — "so" clause); the availability check and its 5-minute-retry alternative form an explicit Fallback.

- **G7 -> AT3, AT4 [OR][(parallel)]**
  - **Justification**: Explicit stated alternative ("either by asking... or by scanning"); no priority order given between the two.

- **G8 -> AT7, AT8, AT9 [AND][FALLBACK(AT7,(AT8#AT9))]**
  - **Justification**: Checking battery is attempted; on insufficient battery, recharging and reassignment are both explicitly required together (joined with "and"), with no order between them → parallel inside the Fallback's second branch.

- **G9 -> G10, G11 [AND][(sequential)]**
  - **Justification**: The engagement actions are narrated before the vital-sign collection/failure-handling content in the text.

- **G10 -> AT10, AT11, AT12 [AND][(sequential)]**
  - **Justification**: All three actions are explicitly required and stated in a fixed order ("approach... announce... provide instructions").

- **G11 -> G12, G13 [AND][FALLBACK(G12,G13)]**
  - **Justification**: Explicit condition-triggered alternative ("failure of collecting any necessary vital signs should trigger a set of questions").

- **G12 -> AT13, AT14, AT15, AT16, AT17 [OR][(parallel, nested)]**
  - **Justification**: Which signs are required depends on the patient's specific condition (infectious disease/post-surgical/diabetes), so only the applicable subset needs fulfillment — OR, not AND; no order given among measurements → parallel.

- **G13 -> AT18, AT19 [AND][FALLBACK(AT18,AT19)]**
  - **Justification**: Explicit condition-triggered alternative ("in case of non-response, an alert should be sent").

- **G14 -> AT20, AT21, AT22, AT23 [AND][(AT20 ; (AT21#AT22) ; AT23)]**
  - **Justification**: "Mark as done" is explicitly first, hygiene steps (disinfection/sterilization, both conditional, no mutual order) follow, and "proceed to the next room" is explicitly last in the same sentence.
