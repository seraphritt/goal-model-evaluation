## Step‑by‑Step Reasoning

Before building the tables, here is how I read the description and the decisions that shaped the tree.

**1. Finding the root.** The mission is triggered by a recurring condition ("every two hours... all vital signs should be checked"), and the description immediately tells us *how* this is achieved operationally ("therefore, the assigned robot should visit every occupied room"). I treat the whole mission as one root **Achieve** goal (**G1**), because it describes a target state reached through planning and action, not a single action and not a query.

**2. The feasibility/escalation chain is a textbook FALLBACK.** "Additional robots can be assigned... in case of impossibility... The responsible manager... must be alerted if no combination of robots can complete the mission" explicitly orders three alternatives: try the normal mission → if that fails, add robots → if that still fails, escalate to the manager. This is nested `FALLBACK(FALLBACK(normal, addRobots), alertManager)`, and per the rules, FALLBACK children are always AND‑related.

**3. "Visit occupied rooms" decomposes by room‑visit phase, not by room‑priority.** The description gives an explicit order *inside* a room visit ("Before entering...", "Once inside...", "Once the patient is checked..."), so I modeled the visit as a strict **sequence**: *Enter Room → Check Vitals & Complete Visit*. I deliberately avoided creating two parallel branches "high‑risk rooms" / "remaining rooms" with duplicated sub‑trees, because that would duplicate the *same intention* (visit‑and‑check‑a‑room) twice, violating the no‑redundancy rule. Instead, the 15‑minute high‑risk requirement is captured as a **scheduling constraint** documented on G2 (it changes *which room* is visited *when*, not *what* is done once there).

**4. Two independent FALLBACKs before entry.** "Check availability" and "check battery" are joined by a plain conjunction ("and"), with no stated order between them → **parallel**. But each one has its own explicit IF‑triggered alternative ("if not available... come back later"; "if not enough battery... recharge and reassign") → each becomes its own small **FALLBACK** goal.

**5. Patient identification is a Query goal with an OR.** "Identify the correct patient either by asking or by scanning the barcode" is about *obtaining information* (which bed/patient is correct), and either method suffices → **Query**, **OR**-decomposed, with a parallel runtime (no priority between the two methods is stated).

**6. Approach/announce/instruct is a Perform goal.** These are concrete, immediately executable actions (matching the "Enter the Car" example) listed in a clear temporal order → **Perform**, sequential.

**7. The vitals‑collection failure chain is another nested FALLBACK.** Collect vitals → if any fail, ask assessment questions → if no response, alert the nurse/doctor. Same logic as point 2.

**8. Condition‑specific vitals are OR, not AND.** A patient's condition (infectious / post‑surgical / diabetic) determines which set of vitals is required; fulfilling the applicable branch is sufficient for that patient, and not every patient needs all three branches → **OR**, with a parallel runtime (a patient can have more than one condition, so branches aren't mutually exclusive, but no order is imposed).

**9. Shared leaf tasks instead of duplicate goals.** "Heart rate" and "blood oxygenation" are required by both infectious and post‑surgical patients. Rather than creating duplicate task nodes, I reuse **AT10** and **AT13** under both parent goals — this keeps the model non‑redundant while maximizing relationships, as requested.

**10. Sterilization and actuator disinfection are conditional, parallel siblings inside room completion.** Both can apply at once (an infectious room visit involving contact needs both), neither is stated to precede the other, and both occur after the check is done and before moving on → sequential wrapper (`mark done ; (sterilize # disinfect) ; proceed`).

**11. Zero‑robot filter.** Nothing in the description describes a purely administrative, robot‑free action; even fleet reassignment and manager alerts are modeled as being carried out/triggered by a robot (so they remain eligible for the model), with the "Number of Robots" field reflecting that more than one robot may ultimately be involved in reassignment.

## Logical Relationships

- **G1 -> G2, AT21, AT22 [AND][FALLBACK(FALLBACK(G2,AT21),AT22)]**
  - **Justification**: The description explicitly sequences alternatives on failure: run the mission normally first; if time doesn't permit, add robots; if even that can't finish it, alert the manager. FALLBACK children are always AND‑related.

- **G2 -> G3, G9 [AND](sequential)**
  - **Justification**: Entry activities ("before entering...") must complete before the in‑room checking/completion activities ("once inside...") begin; both phases are required for a room visit to count as done.

- **G3 -> G4, G7, G8 [AND](sequential)**
  - **Justification**: Preconditions are checked before entry; the correct patient must be identified (multi‑bed rooms) before the robot approaches and speaks to them — an explicit, necessary order.

- **G4 -> G5, G6 [AND](parallel)**
  - **Justification**: Availability and battery are joined by a plain "and" with no stated precedence, so either can be verified first or concurrently, but both are mandatory.

- **G5 -> AT1, AT2 [AND][FALLBACK(AT1,AT2)]**
  - **Justification**: "If the patient is not available... come back after a short period" is an explicit IF‑triggered alternative to the normal check.

- **G6 -> AT3, AT4 [AND][FALLBACK(AT3,AT4)]**
  - **Justification**: "If there is not enough battery... recharge and tasks need to be reassigned" is an explicit IF‑triggered alternative to the normal check.

- **G7 -> AT5, AT6 [OR](parallel)**
  - **Justification**: "either by asking or by scanning" — either method is sufficient (OR), and no order/priority is given between them (parallel).

- **G8 -> AT7, AT8, AT9 [AND](sequential)**
  - **Justification**: "approach the patient, announce the procedure..., and provide instructions" is listed in an explicit temporal order, and all three are required.

- **G9 -> G10, G14 [AND](sequential)**
  - **Justification**: Vitals must be obtained (or appropriately escalated) before the robot can mark the patient done and move on.

- **G10 -> G11, AT15, AT16 [AND][FALLBACK(FALLBACK(G11,AT15),AT16)]**
  - **Justification**: "Failure of collecting any... vital signs should trigger a set of questions... In case of non‑response, an alert..." is a two‑level explicit IF‑triggered alternative chain.

- **G11 -> G12, G13, AT14 [OR](parallel)**
  - **Justification**: Each branch is triggered by a different medical condition; achieving the branch(es) matching the patient's actual condition(s) is sufficient (OR). Parallel because a patient could present more than one condition at once, with no stated priority among them.

- **G12 -> AT10, AT11, AT12, AT13 [AND](parallel)**
  - **Justification**: "must be checked for heart rate, blood pressure, body temperature, and blood oxygenation" — all four are jointly required, with no order stated.

- **G13 -> AT10, AT13 [AND](parallel)**
  - **Justification**: "must be checked for heart rate and blood oxygenation" — both jointly required, no order stated; both tasks are reused from G12 rather than duplicated, since they represent the identical underlying action.

- **G14 -> AT17, AT18, AT19, AT20 [AND][ AT17 ; (AT18 # AT19) ; AT20 ]**
  - **Justification**: Marking the patient done happens first (explicitly paired with "proceed to the next room" as the closing step); sterilization and actuator disinfection are both described as occurring on exiting the room, conditionally, with no order between them (parallel), and must both finish before the robot proceeds.
