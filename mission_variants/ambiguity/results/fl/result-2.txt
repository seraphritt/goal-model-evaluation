# Mission Analysis: Hospital Food Delivery & Dish Pickup Multi-Robot System

## Step-by-Step Reasoning

**1. Identifying the top-level structure.**
The description contains two temporally distinct macro-processes tied to the same room/robot: (a) *delivering food* (kitchen → room) and (b) *retrieving dirty dishes* (room → robot). Nothing in the text says these must run in parallel — in fact a dish pickup for a given meal is only meaningful **after** that meal has been delivered and consumed ("**At** pickup, the patient places the dirty dishes..."). I therefore model these as two AND-required sub-missions under one root, related by **sequential** execution, not parallel, since the pickup phase is contingent on the delivery phase having occurred.

**2. Triggers are explicit and deserve their own nodes.**
"In response to kitchen delivery requests" and "Someone in the room can call a robot to pick up the dishes" are explicit triggering/information-gathering events. Since they involve obtaining knowledge rather than acting on the world, I modeled both as **Query goals** rather than folding them silently into the parent goal.

**3. The two explicit "OR" choices in the text.**
- "...delivered into a room table **by the robot**... **or** the food can be fetched from the robot's tray" → explicit OR.
- "the dish retrieve can occur unassisted, with the cooperation of two robots **or** with the cooperation of robots and a human" → explicit OR (3-way).
- "Opening the room door can involve cooperation with another robot **or** a human" → explicit OR.
These are modeled as OR-decompositions, with **parallel (#)** runtime annotation, because no explicit priority/order between the alternatives is stated (only possibility, not obligation or sequence).

**4. Zero-robot exclusion.**
The *patient placing dirty dishes on the cart* and the *physical act of a patient/companion/nurse grabbing food off the tray* are performed by humans only — **no robot is involved in the action itself** — so these are **not represented** as nodes. However, the robot's *supporting* behavior around these human acts (indicating which meal, tracking retrieval, alerting on errors, determining availability) **does** involve the robot and is kept.

**5. Avoiding redundant intentions.**
"Inpatient, a companion, a nurse" are three different possible humans who could retrieve food/open the door, but they represent **one underlying intention** ("a person in the room assists") as far as the robot's behavior is concerned — the robot's support tasks (indicate/track/alert, determine availability) are identical regardless of which human is involved. I therefore merged these three into single query/task nodes instead of creating three redundant branches. "Another robot" is kept as a **separate, distinct branch** because it is the only alternative that is actually robot-performed and structurally different (2-robot cooperation task).

**6. Why no FALLBACK was used anywhere.**
FALLBACK requires an **explicit stated order** ("try X, and if X fails do Y"). The description mentions *uncertainty* about who can retrieve food ("could be unable," "could not be available") but never states an attempt order (e.g., "try the inpatient first, then the companion, then the nurse"). Because this order is never explicit, I deliberately avoided FALLBACK and instead modeled the uncertainty as a **Query goal** (determine capability/availability from the inpatient record) that precedes (sequentially) the actual handoff execution. This is a conscious, rule-compliant decision, not an oversight.

**7. Goal typing logic.**
- Nodes whose purpose is to **obtain information** (request details, capability/availability, call details) → **Query**.
- Nodes representing a **persistent target state reached under non-trivial/uncertain conditions** (meal delivered & tracked, meal retrieved by a capable agent, door open, dishes collected) → **Achieve**.
- Nodes that simply **dispatch and execute one of several concrete alternative actions**, where success = the action being carried out (paralleling the "Enter the Car" example) → **Perform**.

**8. Task granularity.**
Only genuinely atomic, immediately-assignable, located, robot-counted operations are modeled as Tasks (AT). Robot counts are taken directly from the text where explicit ("two robots," "another robot" implies 2 total) and set to 1 where the action is performed by a single robot (optionally alongside an uncounted human).

## Logical Relationships

- **G1 → G2, G8 [AND] (sequential: `G2;G8`)**
  - **Justification**: Delivery and pickup are both necessary parts of the meal-service mission (AND), but pickup of dishes for a given meal only makes sense **after** that meal has been delivered — the text frames pickup ("At pickup...") as a subsequent phase, so sequential (not parallel) applies.

- **G2 → G3, AT1, G4, AT5, AT6 [AND] (sequential then parallel: `G3;AT1;G4;(AT5#AT6)`)**
  - **Justification**: All five are jointly required to complete one delivery (AND). Order is implied by the process flow: a request must be received before collection, collection before handoff, and handoff before anything can be tracked or alerted on. Tracking and alerting are not given any relative order to each other, so they run in parallel.

- **G4 → AT2, G5 [OR] (parallel: `AT2#G5`)**
  - **Justification**: "The food can be delivered into a room table... **or** fetched from the robot's tray" — an explicit alternative; only one method is used per order, and the text gives no priority between them.

- **G5 → G6, G7 [AND] (sequential: `G6;G7`)**
  - **Justification**: The robot must first determine who is capable/available (G6) before it can meaningfully execute the cooperative handoff (G7) — a necessary informational prerequisite, not a stated alternative.

- **G7 → AT3, AT4 [OR] (parallel: `AT3#AT4`)**
  - **Justification**: Cooperation can be with a person in the room (merged inpatient/companion/nurse intention, since the robot's action — indicating — is identical regardless of which human) **or** with another robot; these are mutually exclusive alternatives with no stated order.

- **G8 → G9, G10, G13 [AND] (sequential: `G9;G10;G13`)**
  - **Justification**: Receiving the call, gaining door access, and retrieving dishes are all necessary complementary steps; logically the robot must be called, then reach and open the door, then retrieve — consistent with the order these events are described in the text.

- **G10 → G11, G12 [AND] (sequential: `G11;G12`)**
  - **Justification**: The robot must first learn whether assistance will be available at the door ("that person can signal if they can open the door **when the robot comes to it**") before executing the actual opening action.

- **G12 → AT7, AT8 [OR] (parallel: `AT7#AT8`)**
  - **Justification**: "Opening the room door can involve cooperation with another robot **or** a human" — explicit alternative with no stated priority.

- **G13 → AT9, AT10, AT11 [OR] (parallel: `AT9#AT10#AT11`)**
  - **Justification**: "The dish retrieve can occur unassisted, with the cooperation of two robots **or** with the cooperation of robots and a human" — explicit three-way alternative, no stated order or priority among the three methods.

### Notes on Exclusions and Rule Application
- **Zero-robot exclusion**: The patient's act of placing dirty dishes on the cart, and the literal act of a patient/companion/nurse lifting food off the tray, involve no robot action and were deliberately **omitted** as standalone nodes — only the robot's supporting behaviors around them were retained.
- **No redundancy**: Inpatient, companion, and nurse were **merged** into single query/task nodes (G6, AT3) since they represent one underlying intention ("a person in the room assists") from the robot's perspective; only "another robot" warranted a distinct branch (AT4), since it is structurally and operationally different (2-robot action).
- **No FALLBACK used**: Despite real uncertainty being described (availability of helpers), no explicit priority/attempt-order is stated anywhere in the text, so FALLBACK was correctly never applied — uncertainty was instead captured via Query goals preceding execution.
