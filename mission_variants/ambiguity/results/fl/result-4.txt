# Multi‑Robot Goal Model — Inpatient Meal Delivery & Dish Retrieval

## Step‑by‑Step Reasoning (before building the tree)

1. **Identify the actors and filter "zero‑robot" content.** The description mixes robot actions with purely human actions (the patient placing dishes on the cart, a person calling the robot, a person signaling they can open the door). Per the rule *"Goals and tasks that are not performed by any robot must not be on the goal model,"* I excluded the bare human acts as goals/tasks, but kept the **robot's corresponding reaction** (receiving the call, reading the "open‑door" signal, checking the inpatient record) because those are genuinely robot‑executed.

2. **Two top‑level mandatory phases.** The text first describes the *delivery* flow completely, then opens a new phase with **"At pickup, …"** — an explicit textual marker of temporal order. Since both phases are mandatory (not alternatives) and the order is explicit, I used **AND** decomposition with a **sequential (;)** runtime between "Deliver Food" and "Retrieve Dishes."

3. **OR vs AND.** Wherever the text uses an explicit "or" between mutually‑exclusive mechanisms (table delivery **or** tray fetch; inpatient, companion, nurse **or** another robot; unassisted, two robots **or** robot+human), I used **OR**. Wherever the text lists mandatory, complementary steps (load + navigate; indicate + cooperate; track + validate), I used **AND**.

4. **Fallback — used only once, where justified.** The only place the text explicitly ties a *condition* ("if a wrong meal is retrieved") to a corrective alternative behavior is the wrong‑meal alert. This is the textbook Fallback case: *try to confirm the correct meal; if that fails, alert.* I did **not** use Fallback for the table/tray choice or the three dish‑retrieval modes, because the text never states one is attempted before the other as a failure‑recovery — they are plain alternatives (OR), so I annotated their runtime as **parallel (#)**, meaning either may be pursued, with no obligation of order.

5. **Query goals** were used only where the mission explicitly talks about *obtaining information under uncertainty* (capability to retrieve from inpatient record/companion presence; whether the person can open the door). Everything else that **executes** a physical/coordination action was modeled as **Perform**. Multi‑step goals with a clear resulting **state** (meal at room, door open, dishes collected, retrieval validated) were modeled as **Achieve**, each with an explicit target condition.

6. **Tasks** were created only at the point where a goal becomes a single concrete, assignable operation (a location + a robot count), per the Task Node definition. Locations used are strictly the ones named in the text: *kitchen*, *(inpatient) room*, *room door*, *beside the room door*. Robot counts follow the text literally: 1 when a single robot cooperates with a human, 2 whenever "another robot" / "two robots" is explicitly named.

7. **No duplication of intention.** "Determine ability to retrieve from tray" (delivery) and "determine ability to open the door" (pickup) look similar but are distinct intentions (different property, different phase), so both are kept as separate Query goals rather than merged.

- **G2 -> G3, G4, G5, G6, G11 [AND]((G3;((G4#G5);(G6;G11))))**

The request (G3) must occur first; transport (G4) and capability‑checking (G5) have no stated order relative to each other so they run in parallel, but both must finish before hand‑off (G6); monitoring (G11) can only occur after the hand‑off.

  - *Justification*: The meal must be loaded before the robot can navigate with it; no parallel alternative is stated.
