# Goal Model Design — Hospital Meal Delivery & Dish Retrieval

## 1. Step-by-Step Reasoning

**Step 1 — Identify the top-level scope.**
The description covers two complementary system responsibilities: (a) delivering food from the kitchen to an inpatient room, and (b) retrieving dirty dishes from the room. Nothing in the text makes one contingent on, or sequenced before, the other — they are triggered independently (a kitchen request vs. a room call) and can run concurrently across different rooms/orders. I therefore model a single root goal **G1** that **AND**-decomposes into **G2 (Deliver Food)** and **G8 (Retrieve Dishes)**, with a **parallel (`#`)** runtime since no order is stated between them.

**Step 2 — Model the delivery pipeline as a sequence.**
"Delivery is made on an order-by-order basis in response to kitchen delivery requests" implies a clear operational pipeline: *receive request → transport → deliver to the inpatient → track the retrieval*. Each step is a precondition for the next (you cannot transport before receiving the order, cannot deliver before transporting, cannot log a retrieval before it occurred), so I used **sequential (`;`)** runtime for **G2**'s children, and **AND** decomposition (all four steps are mandatory, not alternatives).

**Step 3 — The explicit OR for the delivery method.**
"The food can be delivered into a room table by the robot … **or** the food can be fetched from the robot's tray" is a textbook **OR decomposition**: either path is sufficient to fulfill delivery. This became **G3**, OR-decomposed into the task *Place Meal on Table* (**AT3**) and the sub-goal *Retrieve Meal via Tray Cooperation* (**G4**). No order between the two is stated, so I annotated the runtime as parallel (`#`) — acknowledging that, because it's an OR, only one branch will actually execute; `#` is used here simply to express "no mandated order," since the formalism requires every goal to carry a runtime annotation.

**Step 4 — The cooperation OR and the uncertainty-driven query.**
"Fetching from the robot tray requires cooperation with the inpatient, a companion, a nurse, or another robot" is another explicit OR (any one cooperating party suffices) → **G7**. But the text also says this capability is *not always known* — it "can be obtained based on the inpatient record … and the presence of a companion … subject to uncertainty." This is a clear information-gathering concern rather than a physical action, so I modeled it as a **Query Goal** (**G6**), decomposed **AND** into checking the inpatient record (**AT4**) and checking companion presence (**AT5**) — the text names exactly these two complementary sources.

Logically, the robot must *know* who can help (G6) before it can *tell* the right person which meal is theirs (AT6, needed because "the robot can carry multiple meals") before it can *actually cooperate* (G7). None of the text uses words like "first/then," but the dependency is causal and unambiguous, so I used **sequential (`;`)** for this chain, grouped under **G5** ("Coordinate Meal Retrieval with Assisting Party").

**Step 5 — The alert as a FALLBACK, not an OR.**
"The robot should generate an alert if the meal retrieval is not performed correctly" is a normal-behavior/exception pattern: normal = successful coordinated retrieval (G5); exception, triggered by a failure condition = generate alert (AT11). This matches the FALLBACK definition exactly, so **G4** = `FALLBACK(G5, AT11)`, and per the rules, its own decomposition type must be **AND**.

**Step 6 — Tracking is a simple logging task, not a sub-goal with its own decomposition.**
"It should track when and where each meal was retrieved" names a single operational action (recording time + location) with no further breakdown described, so it is a **leaf Task** (**AT12**), not a Goal (every Goal needs ≥2 children, and the text gives no second element to decompose it into).

**Step 7 — Dish retrieval mirrors the delivery structure.**
"Dirty dishes should be retrieved… the dish retrieve can occur unassisted, with the cooperation of two robots or with the cooperation of robots and a human" is an explicit three-way **OR** → **G10**. "Opening the room door can involve cooperation with another robot or a human" is a two-way **OR** → **G9**. I deliberately did **not** add a third "unassisted door-opening" branch under G9: unlike the dish-retrieval sentence, the description never states the robot can open the door alone, so inventing that branch would not be textually supported.

**Step 8 — The call-and-signal sentence.**
"Someone in the room can call a robot to pick up the dishes. In that case, that person can signal if they can open the door" ties a trigger event (the call) to a piece of information (whether they will open the door themselves) that determines whether G9 is even needed. Both pieces are obtained together at the moment the robot is summoned, so I grouped them into a single leaf task, **AT13**, under **G8**, sequenced (`;`) before door-opening and dish collection — the robot must first know about the request and the door situation before acting.

**Step 9 — Zero-robot exclusion.**
If the occupant signals that *they* will open the door, that action involves no robot and must not appear in the model. **G9** therefore represents only the robot-assisted alternative (used when the occupant does not/cannot open it), which is consistent with excluding the human-only branch while still capturing the two cooperative robot-involved alternatives the text does describe.

**Step 10 — Numbering.**
IDs were assigned by a single depth-first traversal of the whole tree, incrementing the `G` counter at every Goal node and the `AT` counter at every Task node, in left-to-right child order as built above. This produced **G1–G10** and **AT1–AT18**.

## 5. Logical Relationships

- **G1 -> G2, G8 [AND][parallel: `G2#G8`]**
  - **Justification**: Meal delivery and dish retrieval are two independent, mandatory system responsibilities with no stated order between them.

- **G2 -> AT1, AT2, G3, AT12 [AND][sequential: `AT1;AT2;G3;AT12`]**
  - **Justification**: The order-by-order pipeline requires receiving the request, transporting the food, delivering it, and logging the retrieval, strictly in that causal order.

- **G3 -> AT3, G4 [OR][parallel: `AT3#G4`]**
  - **Justification**: Explicit "or" between table delivery and tray retrieval; either fulfills the delivery goal, with no mandated order since only one path is realized.

- **G4 -> G5, AT11 [AND][FALLBACK: `FALLBACK(G5, AT11)`]**
  - **Justification**: The alert is an exception path triggered only if coordinated retrieval fails — the canonical FALLBACK pattern, whose branches are always AND-related.

- **G5 -> G6, AT6, G7 [AND][sequential: `G6;AT6;G7`]**
  - **Justification**: The robot must determine who can help, then indicate the correct meal, then cooperate — each step depends on the completion of the previous one.

- **G6 -> AT4, AT5 [AND][parallel: `AT4#AT5`]**
  - **Justification**: The text names two independent, complementary information sources (inpatient record, companion presence) that are jointly checked, with no stated order.

- **G7 -> AT7, AT8, AT9, AT10 [OR][parallel: `AT7#AT8#AT9#AT10`]**
  - **Justification**: Explicit OR list of cooperating parties; any single one is sufficient.

- **G8 -> AT13, G9, G10 [AND][sequential: `AT13;G9;G10`]**
  - **Justification**: The robot must learn of the pickup request and door situation, then (if needed) open the door, before it can collect the dishes.

- **G9 -> AT14, AT15 [OR][parallel: `AT14#AT15`]**
  - **Justification**: Explicit OR between robot cooperation and human cooperation for opening the door.

- **G10 -> AT16, AT17, AT18 [OR][parallel: `AT16#AT17#AT18`]**
  - **Justification**: Explicit three-way OR stated directly in the text for how dish retrieval can occur.
