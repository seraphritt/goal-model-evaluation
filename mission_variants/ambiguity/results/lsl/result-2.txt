### 1.2 Applying the "zero-robot" exclusion rule

The description mixes human-only actions with robot actions. Per the rule *"Goals and tasks that are not performed by any robot must not be on the goal model,"* I excluded the following, with justification:

- **"A nurse... can request a delivery to the laboratory"** → purely human decision/communication act, no robot involved → **excluded**.
- **"Each sample before collection is identified with a barcode"** → passive, implicitly a human/lab-staff labeling step prior to any robot involvement → **excluded**.
- **"The nurse inserts data about the sample in a track system"** → explicit human actor, data-entry act → **excluded**.
- **"A technician positions the transport robot beside the robotic arm"** → the *agent* performing the action is the technician (human); the robot is the object being moved, not the actor → **excluded**. (Its effect — the robot being in place to be unloaded — is folded as a precondition/implicit part of the transport task, noted in AT1's justification.)

Everything else in the text is directly tied to either the **transport robot** or the **robotic arm**, so it remains in-scope.

### 1.3 Robot-performed intentions extracted from the text

1. **Physical relocation** of the sample from patient floor to laboratory ("Lab samples should be transported from patient floors to the laboratory") → transport robot.
2. **Drawer security/access control** ("Samples are transported in secure locked drawers"; "Only authorized personnel or specific robots in specific locations should be able to open the locked drawers") → the robot-eligible branch of this OR condition (specific robots, specific locations) is the part retained — the "authorized personnel" branch is excluded per 1.2.
3. **Sample processing pipeline** at the lab: "picks up samples, scans the barcode in each sample, sorts, and loads the samples into the entry-module of the analysis machines" → robotic arm, four actions stated in explicit left-to-right order → **sequential**, not fallback (no conditional/failure language here, just an ordered list of normal actions).
4. **Secure logging of the pick event** ("Information about where and when a given sample was picked should be logged securely") → attributed to the robotic arm, since it's the entity that performs the "pick" immediately described in the prior sentence.
5. **Delivery-time compliance tracking** ("The time between sample collection and laboratory delivery should be tracked to be sure it goes according to laboratory protocols") → attributed to the transport robot, since it is the only robot physically present at both the collection point and the delivery point.

No **FALLBACK** relation was used anywhere: the text never states "if X fails/cannot be done, then Y is attempted instead." The OR-like phrase about drawer-opening is a condition of *authorization*, not a contingency upon *failure*, and one of its two branches is excluded entirely (zero-robot rule), so no OR node survives either — it becomes a single AND-connected task (AT2) describing the robot-eligible condition.

### 1.4 Decomposition/runtime reasoning

- G2 (transport) and G3 (lab processing) are **sequential** — a sample physically cannot be scanned/sorted/loaded before it has arrived.
- G4 (secure pick-up logging) runs **in parallel** with G3, since logging the pick event doesn't block the scan/sort/load pipeline.
- G5 (delivery-time tracking) runs **in parallel** with G2, since its two timestamps bracket the transport phase itself.
- Within G3, the four actions are strictly **sequential**, matching the text's explicit ordering.
- Within G4 and G5, the two internal tasks are **sequential** (you must capture data before storing it; you must record collection time before you can compare it to delivery time).

This yields the overall root runtime: **(G2#G5);(G3#G4)**.

- **G1 -> G2, G3, G4, G5 [AND] (sequential + parallel combination: (G2#G5);(G3#G4))**

- **G3 -> AT3, AT4, AT5, AT6 [AND] (sequential)**
  - **Justification**: The description lists these four actions in an explicit left-to-right order ("picks up samples, scans the barcode..., sorts, and loads..."), and each step logically depends on completion of the previous one (you cannot scan before picking up, cannot sort before scanning, cannot load before sorting).

- **G4 -> AT7, AT8 [AND] (sequential)**
  - **Justification**: Data must be captured (AT7) before it can be securely stored (AT8); storing nonexistent data is impossible, so capture necessarily precedes storage.
