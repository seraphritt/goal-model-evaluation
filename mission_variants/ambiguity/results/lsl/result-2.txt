# Goal Model: Lab Sample Transport & Processing System

## Step-by-Step Reasoning

**Step 1 — Identify every activity in the description.**
I listed every clause: (a) nurse requests delivery, (b) sample identified with barcode, (c) nurse inserts data in track system, (d) samples transported in locked drawers, (e) sample picked by robotic arm *or* lab personnel, (f) only suitable personnel/robots may open drawers, (g) robotic arm picks up → scans → sorts → loads into analysis-machine entry-module, (h) pick location/time logged securely, (i) collection-to-delivery time tracked for protocol compliance.

**Step 2 — Apply the "zero-robot" filter.**
- (a) nurse requesting delivery → purely human, **excluded**.
- (b)/(c) barcode labeling and nurse data entry → purely human/administrative, **excluded**.
- (e) "picked by a robotic arm **or** laboratory personnel" → this textual OR has one zero-robot branch (personnel). Per the rule, that branch is dropped and only the robotic-arm branch remains — so it is no longer modeled as an OR (OR needs ≥2 surviving children), just a plain robot task.
- (f) "only personnel **or** robots… may open" → same treatment: personnel branch dropped, robot branch kept as a plain task.
- (d), (g), (h), (i) all directly or indirectly involve robot action (a transport robot, the robotic arm, or robot-generated logs/telemetry), so they **stay**.

This filtering is the main reason the final model contains **no OR-decompositions**: every genuine alternative in the text involved a human-only option that had to be removed, leaving single, mandatory robot paths (AND).

**Step 3 — Group surviving activities into coherent goals.**
Three natural clusters emerged:
1. **Transport** the locked drawer (patient floor → laboratory).
2. **Process** the sample at the laboratory (access the drawer, retrieve, identify, sort, load) — I kept drawer-opening here rather than under Transport because the text ties "opening" directly to "the sample can be picked" at the laboratory, not to the loading event at the patient floor (which is never described as a robot action).
3. **Monitor compliance** — logging pick info and tracking elapsed time are two independent, continuously-running obligations rather than one-off steps, so they form their own parallel branch rather than being buried inside Transport or Process.

**Step 4 — Decide execution order.**
Transport must finish before processing can start (a sample can't be scanned/sorted before it physically arrives) → **sequential**. Monitoring, however, spans the whole timeline (time is tracked "between collection and delivery", logging happens at the pick event) and has no stated dependency on finishing before/after the other branches → **parallel**. Inside "Process at Laboratory" the text gives an explicit action order ("picks up, scans..., sorts, and loads"), and opening the drawer is a logical precondition to picking → **sequential** throughout. No condition/failure/exception is ever mentioned, so **FALLBACK is never used**.

**Step 5 — Assign goal types.**
I used the definitions literally: a goal whose point is retrieving information → Query (identifying the sample via barcode; tracking elapsed time). A goal that is a short, immediate action with no complex target state → Perform (picking up the sample; logging the pick event). A goal with a clear target world-state reached through planning/action → Achieve (transport, drawer-access control, sort-and-load, and the top-level mission goal).

## Logical Relationships

- **G0 -> G1, G2, G7 [AND] `(G1;G2)#G7`**
  - *Justification*: All three are mandatory, complementary parts of the mission — a sample must be transported, processed, and have its handling monitored; none is optional (no "or" is stated among them). Transport must finish before processing can begin (sequential), while compliance monitoring spans the entire timeline rather than being tied to a single before/after point (parallel), so sequential and parallel are combined with parentheses as required.

- **G2 -> G3, G4, G5, G6 [AND] `G3;G4;G5;G6` (sequential)**
  - *Justification*: The description states an explicit action order at the laboratory — opening must precede picking; "picks up samples, scans the barcode..., sorts, and loads" gives an explicit left-to-right sequence. All four are required; none is an alternative to another.

- **G3 -> AT2, AT3 [AND] `AT2;AT3` (sequential)**
  - *Justification*: "Only personnel or robots considered suitable... should be able to open" logically requires the suitability check to occur before the opening action; both steps are mandatory and neither alone fulfills the access-control goal.

- **G6 -> AT6, AT7 [AND] `AT6;AT7` (sequential)**
  - *Justification*: "Sorts, and loads" is an explicit two-step sequence; both actions are required for the sample to end up correctly placed in the analysis machine.

- **G7 -> G8, G9 [AND] `G8#G9` (parallel)**
  - *Justification*: Logging pick info and tracking transit time are two separate explicit requirements ("should be logged securely" / "should be tracked") with no stated dependency or order between them, so they can proceed independently/concurrently.

- **G1 -> AT1 [AND]**
  - *Justification*: A single task fully satisfies this goal; AND is used by convention since the one child is mandatory.

- **G4 -> AT4 [AND]**, **G5 -> AT5 [AND]**, **G8 -> AT8 [AND]**, **G9 -> AT9 [AND]**
  - *Justification*: Each of these goals maps 1:1 onto a single explicit robot action in the text; AND is the trivial, mandatory relation.

**Note on OR / FALLBACK:** No OR-decomposition appears anywhere in the final model. Every "or" in the source text ("robotic arm **or** laboratory personnel"; "personnel **or** robots") paired a robot option with a human-only option; after removing the zero-robot branches per the stated rule, only single mandatory robot paths remained, which are modeled as AND. No conditional, exception, threshold, or failure-triggered alternative is described anywhere in the text, so FALLBACK is never used.
