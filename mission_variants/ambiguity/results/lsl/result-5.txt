## Step-by-step reasoning

**1. Separating robot-relevant material from human-only material (the "zero robot" filter).**
The description mixes nurse actions with robot actions. I excluded the following because no robot performs them, and no robot's success/failure depends on executing them:
- *"A nurse responsible for collecting a sample can request a delivery"* — pure human trigger. Kept only conceptually as the **mission trigger/precondition**, not as a node.
- *"Each sample before collection is identified with a barcode"* — barcode is applied before collection, implicitly by staff, not a robot.
- *"The nurse inserts data about the sample in a track system"* — human-only data entry.
- *"the sample can be picked by a robotic arm **or** laboratory personnel"* — this is literally an OR, but since "laboratory personnel" is a zero-robot branch, it is dropped. The OR collapses to a single branch (robotic arm), so it is modeled as one task rather than a binary OR node.

**2. Decomposition type (AND vs OR).** Nothing in the remaining text expresses genuine alternatives among robot-feasible options (no "either/or" between two robot-valid paths survives the filter above). Every remaining grouping is a set of jointly-required conditions → **AND** throughout.

**3. Runtime annotations.**
- Transport must complete before lab processing can start (physical necessity, implied ordering) → **sequential** (`;`).
- Time-tracking spans the *entire* collection-to-delivery window, so it overlaps with transport+processing rather than following them → **parallel** (`#`).
- "Picks up, scans, sorts, and loads" is an explicit normal-flow sequence with no failure/condition language anywhere in the text → **sequential**, not FALLBACK (FALLBACK requires an explicit stated alternative triggered by failure/condition, which never occurs in this description).
- Logging "where and when" has no stated order between the two facts → **parallel**.
- No IF-statements, exceptions, or stated "try X, else Y" anywhere in the text → **FALLBACK is never used** in this model.

**4. Goal types.**
- G1–G3 are **Achieve**: each has a concrete target state (sample delivered / drawer secured / sample loaded) that must be reached, not just attempted.
- G4 (logging) is **Achieve**, not Perform, because what matters is that a *secure, persisted record exists* (a state), not merely that a logging action was attempted.
- G5 (time tracking) is **Query**: "tracked" is about obtaining/monitoring information (elapsed duration) against a protocol threshold, with no corrective action specified — this matches "retrieve information about the World" rather than "change the World."

**5. A deliberate modeling exception.** G5 has no further robot sub-task of its own: the mission gives only one usable data point on the robot side (the drawer's arrival, already captured by G2/AT1), while the complementary "collection time" comes from the nurse's non-robot track-system entry. Rather than inventing an artificial second child just to satisfy the "≥2 children" convention, I left G5 as a **leaf** goal (`-`), attributing its monitoring responsibility to the delivery robot's own logging capability — flagged here explicitly as an assumption, since the text doesn't spell out who computes the comparison.

**6. Locations and robot counts.** Every location used (patient floor, laboratory) is taken verbatim from the text — no invented locations. All robot counts default to 1, since every robot action is described in the singular ("the robotic arm", "a locked drawer") with no indication of cooperating fleets per sample.
