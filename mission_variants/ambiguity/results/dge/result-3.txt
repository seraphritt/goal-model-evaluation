# Mission Analysis: Resource Collection & Delivery (Multi-Robot System)

## Part 1 — Step-by-Step Reasoning and Reflections

Before building the tree, I read the description multiple times, isolating **triggers (IF-conditions)**, **explicit temporal ordering ("once," "after")**, **implicit conjunctions ("and")**, and **entities that are *not* robots** (since those must be excluded).

**Step 1 — Identify the root intention.**
"A robot must collect the required resources... and deliver them to the requesting agent in a specified location." This is a single overarching intentional objective with a clear end-state (resources at destination) → root is an **Achieve Goal**, not Perform (too complex/multi-step to be a single action) and not Query (no information is being the end-product).

**Step 2 — Split into phases.**
The text explicitly separates "the collection phase" and "the delivery phase," and states "**once** retrieved, the delivery phase **begins**." The word "once" is an explicit temporal marker → this is a **Sequential** relation, not Parallel (no "can happen at the same time" language) and not Fallback (no failure/condition triggers the second phase — it's a planned, guaranteed transition).

**Step 3 — Look inside the Collection phase.**
Three things happen in order:
1. "go to the storage places... order defined by estimation of waiting time + path" → this sentence has two parts: a **physical action** (go to storage) and a **computation/estimation** (determining order). I deliberately separated these: the estimation is about obtaining *information* used for planning (fits **Query Goal**), while the travel itself is an operational task. I reflected on whether to fold the estimation into the navigation task, but since the text treats "the order to be followed" as its own explicit decision criterion, I gave it its own node to avoid hiding a justified modeling decision inside a task description.
2. "sends a message... with the precise specification" → concrete communicative action → **Task**.
3. "waits until the resources have been retrieved" → this is a **passive monitoring action performed at a location by the robot**, not a complex deliberation, so I treated it as a **Task**, not a Query Goal (reflection: I considered making this a Query Goal "Query Retrieval Status," but rejected it because the text describes *waiting*, an operational/passive step the robot executes, not an active information-seeking behavior with a distinct queried property — it is simply blocking until an external event occurs).

**Step 4 — The battery-low conditions are explicit IF-triggers.**
Both "If the battery... runs low... in the collection phase" and "If the battery... becomes low during the delivery phase" are textbook **Fallback** triggers per the given definition (explicit condition → alternate behavior). I modeled each as `FALLBACK(normal-path, battery-recovery-path)` at the phase level (inside Collect and inside Deliver), each pair wrapped in an **AND** per the mandatory Fallback/AND rule.

**Step 5 — The nested failure case.**
"In case of failure to return the resource to a checkpoint" is a *second*, independent IF-condition, nested inside the delivery battery-handling branch. I reflected on two options:
- (a) Flatten everything into one 3-way nested fallback at a single goal node (`FALLBACK(FALLBACK(normal, checkpoint-return), alert)`), or
- (b) Create two separate goal nodes, each owning its own binary fallback, mirroring the two distinct decision points in the text (first "is battery low?", then, inside that branch, "did the checkpoint return succeed?").

I chose **(b)** because the two conditions are logically and temporally distinct (one nested inside the other, not siblings of the same decision), and because it keeps each FALLBACK binary and semantically clean, consistent with the rule that nested fallbacks must be expressed through nesting rather than forced flattening.

**Step 6 — The "and" conjunctions without explicit order.**
"The robot goes back to the recharging station **and** assigns the mission to another robot" has no explicit sequencing language (no "once," "after," "then"). Per the Parallel definition ("can, not must, be done in parallel"), and since there is no causal dependency stated between physically returning and notifying another robot, I modeled this as **Parallel**, not Sequential — a deliberate choice I want to flag, since a stricter reading could argue these happen one after another. I chose Parallel specifically because the rules state Sequential must only be used when order is *explicitly stated*, which is not the case here.

By contrast, "return the resource to a checkpoint **and** assign the remaining task to another robot, **which will know where the resource is positioned**" *does* imply order: the new robot's assignment is described as depending on knowing the resource's (already-established) position — meaning the checkpoint placement must happen first. I modeled this as **Sequential**.

**Step 7 — The multi-robot parallel clause.**
"When multiple items are required from different storages, multiple robots **can be** assigned to parallel collect-deliver tasks..." I reflected carefully here. This sentence describes an **assignment/allocation decision** — passive voice, no robot is described as the one deciding to parallelize; this reads as a fleet/task-allocation outcome, not an action a mission-executing robot performs. Per the rule "goals/tasks not performed by any robot must not be on the model," I chose **not** to create a dedicated Goal/Task node for this (that would model a dispatcher's/scheduler's decision, not a robot's intention). Instead, I encoded its effect where the schema explicitly provides for it: the **Number of Robots** attribute of the tasks that implement the collect/deliver cycle (`[1,n]` ranges), which is exactly the intended purpose of that field ("infer how many robots are necessary... from the description").

**Step 8 — Checking for OR decomposition.**
I scanned the entire text for genuine *alternative ways to satisfy the same goal* (explicit "or" particles indicating substitutable options). I found none — every branching in this description is either a **planned AND** (jointly required steps) or a **conditional Fallback** (triggered alternative upon failure), which the rules explicitly distinguish from OR. **Conclusion: this goal model contains no OR decomposition**, and I treat that as a legitimate, justified analytical result rather than a gap.

**Step 9 — Checking Goal Types systematically.**
I asked, for every goal, "does it denote (a) a bare action regardless of outcome [Perform], (b) information-seeking [Query], or (c) a persistent world-state to be reached through planning [Achieve]?" Every composite goal in this mission (reach a place, retrieve a resource, deliver a resource, recover from battery failure, secure a resource) has an explicit terminal **state** that must hold (not just "action attempted"), so nearly all are **Achieve**. The lone exception is the order-estimation step, which is purely about obtaining a value (an estimate) rather than changing the world — a clean fit for **Query**. I found no goal that is a bare, consequence-free action distinct enough to deserve Perform at the *goal* level — such atomic actions (sending a message, triggering an alert) were consistently operational enough to be modeled as **Tasks** instead, which is precisely why the model's goal layer skews toward Achieve/Query: Perform-like atomicity was already captured at the Task layer.

```
G1 Execute Resource Collection-Delivery Mission [G2;G6]
├─ G2 Collect Required Resources [FALLBACK(G3,G5)]
│   ├─ G3 Execute Normal Collection Sequence [G4;AT1;AT2;AT3]
│   │   ├─ G4 Estimate Storage Visit Order [-]
│   │   ├─ AT1 Navigate to Storage
│   │   ├─ AT2 Send Resource Request Message
│   │   └─ AT3 Wait for Resource Retrieval
```

## Part 6 — Logical Relationships

- **G1 -> G2, G6 [AND][(sequential)]**
  - **Justification**: Both collection and delivery are mandatory for mission success (AND), and the text states "once retrieved, the delivery phase begins" — an explicit order, hence Sequential.

- **G2 -> G3, G5 [AND][FALLBACK(G3,G5)]**
  - **Justification**: "If the battery... runs low... in the collection phase" is an explicit IF-condition triggering an alternate path; FALLBACK operands are mandatorily AND-connected.

- **G3 -> G4, AT1, AT2, AT3 [AND][(sequential)]**
  - **Justification**: All four steps are jointly required (AND), and the text's narrative order (determine order → travel → request → wait) is explicit, justifying a strict left-to-right sequence.

- **G5 -> AT4, AT5 [AND][(parallel)]**
  - **Justification**: Both the return-to-recharge and the reassignment are required (AND), but the text joins them with a bare "and" with no stated order, so — per the rule that Sequential requires explicit ordering — Parallel (possibility, not obligation) is used instead.

- **G6 -> AT6, G7 [AND][FALLBACK(AT6,G7)]**
  - **Justification**: "If the battery... becomes low during the delivery phase" explicitly triggers an alternative to normal delivery; FALLBACK operands are AND-connected.

- **G7 -> G8, AT9 [AND][FALLBACK(G8,AT9)]**
  - **Justification**: "In case of failure to return the resource to a checkpoint" is a second, nested IF-condition (failure of the recovery attempt itself), modeled as its own binary FALLBACK rather than folded into G6's fallback, since it is a logically separate, nested decision point.

- **G8 -> AT7, AT8 [AND][(sequential)]**
  - **Justification**: Both actions are required (AND); the text specifies that the replacement robot "will know where the resource is positioned," implying the checkpoint placement (AT7) must complete before the reassignment (AT8) is meaningful — hence Sequential.

**On OR decomposition**: No OR relation was identified anywhere in this model. The mission description contains no explicit disjunctive alternatives for satisfying a goal (no "or" indicating interchangeable options) — every branch is either a mandatory AND, a timing annotation (sequential/parallel), or a conditional FALLBACK, all of which the given definitions explicitly distinguish from OR.

**On excluded content**: The "sterile medical equipment" / "clean linens" examples were treated as illustrative instances of the generic *storage* → *specified location* pattern already captured by G2/G6, not as separate goals, to avoid redundant goals representing the same underlying intention. The "multiple robots can be assigned to parallel collect-deliver tasks" clause was **not** modeled as its own Goal/Task node, since it describes a fleet-allocation decision rather than an action performed by a specific robot; its effect is instead captured via the `[1,n]` **Number of Robots** ranges on AT1, AT2, AT3, and AT6.
