# Goal Model Analysis: Multi-Robot Resource Collection & Delivery Mission

## Step-by-Step Reasoning

**Step 1 — Identify the root intention.**
The mission is triggered by a request ("when required") and succeeds when "a robot... collect[s] the required resources in the storage and deliver[s] them to the requesting agent in a specified location." This is a single overarching **Achieve Goal** (G1): it describes a target world-state (resources collected *and* delivered), reached through planning and coordinated action — not a single atomic action (ruling out Perform) and not merely information retrieval (ruling out Query).

**Step 2 — Split into the two explicitly named phases.**
The text names two distinct phases: the *collection phase* and the *delivery phase*. Crucially, it says "**Once** retrieved, the delivery phase **begins**" — an explicit statement of order, with no condition/failure attached. Per the rules, an explicit order with no conditional trigger is **sequential**, not fallback. So G1 decomposes AND-sequentially into G2 (Collect) ; G7 (Deliver).

**Step 3 — Model the battery exceptions as FALLBACK.**
Both phases contain an "if battery runs low (X%)..." clause — a textbook IF-triggered alternative behavior. Per the rules, this *must* be modeled as FALLBACK (normal-path first, exception-path second), and because FALLBACK requires an AND-decomposition of its two branches, I introduced:
- G2 → FALLBACK(G3 "Standard Collection", G6 "Low-Battery Collection Handling")
- G7 → FALLBACK(AT6 "Standard Delivery Runs", G8 "Low-Battery Delivery Handling")

**Step 4 — Model the nested fallback inside delivery.**
"In case of failure to return the resource to a checkpoint, the robot must send the report..." is a *second*, nested condition (failure of the first exception-handling attempt). This is the exact "FALLBACK(FALLBACK(...), exp3)" pattern described in the rules. I represented it as its own goal G8, which internally is FALLBACK(G9 "Return & Reassign", AT9 "Report Failure"), keeping each exception a clearly named, reusable intention rather than flattening everything into one giant expression.

**Step 5 — Decompose the collection phase into order-then-travel.**
"The order to be followed is defined by the estimation of waiting time summed up with the path" describes obtaining a piece of knowledge (an optimal visiting sequence) that is *not itself a physical action* — this matches the **Query Goal** definition exactly (compare to "Fetch Occupied Rooms"). I made this G4, a **leaf Query goal** (no further decomposition needed — it is an internal computation/estimation, not a decomposed operational step). It must happen before actual travel, so G3 = G4 ; G5 (sequential).

**Step 6 — Decompose "visit storage" into its three literal actions.**
"Goes to storage → sends message with specification → waits until retrieved" are three explicit, ordered, concrete operational steps assigned to one robot at one place — these are Tasks, not goals, because they are immediately executable operations with a location and a robot count (AT1, AT2, AT3), connected sequentially (AND).

**Step 7 — Decompose each battery-exception goal into its literal two steps.**
"Goes back to recharging station **and** assigns the mission to another robot" → AT4 ; AT5.
"Return the resource to a checkpoint **and** assign the remaining task to another robot" → AT7 ; AT8.
Both are plain sequential AND pairs — no condition is attached to the *order* between these two steps themselves, only to whether the whole exception path triggers at all (already captured by the outer FALLBACK).

**Step 8 — Decide what does NOT enter the model.**
- The two "examples of goods" (sterile medical equipment, clean linens) are illustrative instances of the generic concept "resource" already covered by G1–G9; they introduce no new robot behavior, so per the zero-robot/no-redundancy rules they are **excluded** as separate goals.
- "When required" is a trigger condition, not an intention, so it is not a node.

**Step 9 — Resolve the "parallel" sentence.**
"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks" is the one place that looks parallel. However, the parallel runtime operator (`#`) is defined over **two different expressions of the same parent**, not over duplicate instances of the *same* goal (G1) run twice — the spec explicitly forbids `exp1` and `exp2` being the same goal. Since this mission description models a *single* robot's collect-deliver process (the generic template that gets instantiated once per required item), I chose to encode the fleet-level parallelism as a **Number-of-Robots range `[1,n]`** on the core operational tasks (AT1, AT2, AT3, AT6) rather than fabricating an artificial parallel goal node — this is the structurally honest way to capture "more than one robot may run this same template concurrently" without violating the `exp1 ≠ exp2` constraint.

**Step 10 — Goal-type reflection.**
Every goal except G4 ended up as **Achieve** because each represents a compound state to reach (resources retrieved, robot safely recharged, resource safely parked, task handed off, etc.), evaluated by success/failure of a *state*, not merely of an attempted action. No goal matched **Perform** (execute-regardless-of-outcome) well, because the description always cares about the resulting state, not just whether the action was attempted — this is a deliberate conclusion, not an omission.

## Logical Relationships

- **G1 -> G2, G7 [AND] (sequential: G2 ; G7)**
  - **Justification**: "Once retrieved, the delivery phase begins" states an explicit order with no conditional trigger — sequential execution, and both phases are mandatory (AND) for the mission to succeed.

- **G2 -> G3, G6 [AND] [FALLBACK(G3, G6)]**
  - **Justification**: The 10%-battery clause is an explicit IF-triggered alternative to normal collection, which the rules require to be modeled as FALLBACK; FALLBACK branches are always AND-connected.

- **G3 -> G4, G5 [AND] (sequential: G4 ; G5)**
  - **Justification**: The visiting order must be computed before (or to guide) the actual travel; no condition/failure is involved, so sequential applies, and both the computation and the visiting are required (AND).

- **G5 -> AT1, AT2, AT3 [AND] (sequential: AT1 ; AT2 ; AT3)**
  - **Justification**: The description lists these three actions in strict temporal order ("goes to storage... sends message... waits until retrieved"); all three are necessary (AND).

- **G6 -> AT4, AT5 [AND] (sequential: AT4 ; AT5)**
  - **Justification**: "Goes back to the recharging station **and** assigns the mission to another robot" — both required, in that stated order.

- **G7 -> AT6, G8 [AND] [FALLBACK(AT6, G8)]**
  - **Justification**: The 30%-battery clause is another explicit IF-triggered alternative to normal delivery runs — FALLBACK required, AND-connected branches.

- **G8 -> G9, AT9 [AND] [FALLBACK(G9, AT9)]**
  - **Justification**: "In case of failure to return the resource to a checkpoint" is a second, nested IF-condition layered on top of the first exception — a nested FALLBACK, exactly matching the rule's FALLBACK(FALLBACK(...), exp3) pattern (here realized as FALLBACK(G9, AT9) inside the G8 node).

- **G9 -> AT7, AT8 [AND] (sequential: AT7 ; AT8)**
  - **Justification**: "Must return the resource to a checkpoint **and** assign the remaining task to another robot" — both required, stated in that order.

No **OR** decompositions were used anywhere: the description contains no case where fulfilling only one of several children would suffice — every relationship is either a mandatory conjunction (AND/sequential) or a conditional substitution (FALLBACK, itself AND-structured).
