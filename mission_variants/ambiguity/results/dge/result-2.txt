# Mission Analysis: Robot Resource Collection & Delivery

## Step-by-Step Reasoning

**1. Identifying the root intention.** The description opens with "When required, a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location." This is the mission's overarching intentional objective — not an operational step — so it becomes the root goal **G1**. Its success condition is a world-state (resources at the right place, with the right agent), so I classified it as an **Achieve** goal rather than Perform (too complex/multi-step to be "just an action") or Query (no information is being retrieved as an end in itself).

**2. Two macro-phases, explicitly ordered.** The text names two phases — "collection phase" and "delivery phase" — and explicitly states "Once retrieved, the delivery phase begins." Because the order is explicitly stated (not just inferred), I used **sequential (`;`)**, not fallback — fallback is reserved for normal-vs-exception behavior, and this is just two mandatory phases in a fixed order. Both phases are mandatory, so the decomposition is **AND**.

**3. Two FALLBACK triggers.** Both battery-related sentences use the IF-conditional pattern the rules call out ("If the battery... runs low... the robot goes back..."). This is a textbook exception/threshold-triggered alternative behavior, so both are modeled with **FALLBACK**, and per the rules, FALLBACK children are always **AND**-related (the alternative is not a free choice — it's forced by failure).

**4. A nested FALLBACK inside delivery.** The checkpoint-return failure ("In case of failure to return the resource to a checkpoint...") is itself a second, nested exception *inside* the battery-fallback branch — another explicit IF/failure condition — so I nested a second FALLBACK rather than flattening it into one list, per the instruction that multi-way fallback must be nested binary.

**5. Rejected design option — a Query goal for order estimation.** The sentence "the order to be followed is defined by the estimation of waiting time summed up with the path" looked at first like a candidate **Query goal** (it's literally "obtaining information" — the estimate). I considered adding `G_est: Estimate Storage Visiting Order` as a Query goal. I rejected it for two reasons: (a) a Task under it would need a `Location`, and no location is cited in the text for a pure computation step (I was instructed not to invent one), and (b) it reads more naturally as a planning *parameter* of the travel task than as an independently robot-executed goal. I instead folded it into **AT1**'s description. I flag this explicitly because it was a close call.

**6. Rejected design option — a dedicated "parallel multi-robot" goal.** The closing operational sentence ("multiple robots can be assigned to parallel collect-deliver tasks") doesn't introduce a new *intention* — it's the same collect-deliver intention, just potentially instantiated by more than one robot at once. Creating a duplicate goal subtree would violate the "avoid redundancy / one goal per distinct intention" rule. Instead, I captured this fact where it actually bears on the model: the **Number of Robots** attribute of the two tasks that represent per-item entry points into collection (**AT1**) and delivery (**AT6**), both marked `[1, n]`.

**7. No OR-decompositions exist in this model.** I checked every branching point for true interchangeable alternatives (OR) vs. jointly-necessary elements (AND) vs. conditioned alternatives (FALLBACK, which is still AND). Nothing in the text presents a genuine "either of these satisfies the goal" choice — every branch is either jointly required or a forced exception path. So the entire tree uses AND decomposition throughout, which is an accurate reflection of the mission description, not an oversight.

**8. Goal-type classification pass.** I went goal-by-goal and asked "is this a state to reach, information to obtain, or a bare action?" All collection/delivery/contingency goals reach a concrete resultant state (resource retrieved, robot safe, resource at checkpoint, etc.) and therefore are **Achieve**. The one exception is **G9 (Report Checkpoint Return Failure)**: triggering an alert and sending a report are immediate, fire-and-forget notifications with no further state to verify — this matches the **Perform** goal definition ("Enter the Car") much better than Achieve.

**9. Zero-robot check.** Every leaf task I defined is executed by at least one robot (the assigned robot, the recharging/recharged robot, or the reassigned robot), so nothing was dropped for that reason — but it did rule out creating a goal purely for "battery monitoring," since that's a continuous system condition, not a discrete robot-performed action, and isn't described as one.

## Logical Relationships

- **G1 -> G2, G6 [AND] (sequential)**
  - **Justification**: The text explicitly states delivery only begins once collection is retrieved ("Once retrieved, the delivery phase begins"); both phases are mandatory, so AND; explicit order → sequential, not fallback.

- **G2 -> G3, G5 [AND] FALLBACK(G3, G5)**
  - **Justification**: Collection proceeds normally (G3) unless the explicit low-battery (10%) threshold is hit, which triggers the alternative recharge-and-reassign behavior (G5). FALLBACK children are AND by rule.

- **G3 -> AT1, G4 [AND] (sequential)**
  - **Justification**: "go to the storage places... Once the robot reaches one storage... sends a message" gives an explicit travel-then-request order.

- **G4 -> AT2, AT3 [AND] (sequential)**
  - **Justification**: "sends a message... and waits until the resources have been retrieved" is an explicit send-then-wait order.

- **G5 -> AT4, AT5 [AND] (parallel)**
  - **Justification**: "goes back to the recharging station and assigns the mission to another robot" states no required order between the two actions, so parallel (possibility, not obligation) is the correct default rather than fabricating sequence.

- **G6 -> AT6, G7 [AND] FALLBACK(AT6, G7)**
  - **Justification**: Normal delivery runs (AT6) proceed unless battery becomes low during delivery, which is an explicit IF-triggered exception (G7).

- **G7 -> G8, AT10 [AND] (sequential)**
  - **Justification**: The reassigned robot "will know where the resource is positioned," which is only knowable after the resource has actually been placed at the checkpoint — implying checkpoint placement precedes reassignment.

- **G8 -> AT7, G9 [AND] FALLBACK(AT7, G9)**
  - **Justification**: The robot attempts to transport the resource to the checkpoint (AT7); "in case of failure to return the resource to a checkpoint" is an explicit failure-triggered exception leading to alert/report (G9) — a second, nested FALLBACK as required for a third alternative.

- **G9 -> AT8, AT9 [AND] (parallel)**
  - **Justification**: "an alert must be triggered and the report sent" states no explicit order between the two notifications, so parallel is used rather than an invented sequence.
