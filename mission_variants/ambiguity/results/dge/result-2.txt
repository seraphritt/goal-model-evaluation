# Goal Model Analysis — Multi-Robot Resource Collection & Delivery Mission

## Step-by-Step Reasoning

**1. Identifying the overall mission goal.**
The description centers on a single intentional objective: *a robot collects required resources from storage and delivers them to a requesting agent at a specified location*. This has a clear target state (resources physically present at the destination), so the root node (**G1**) is an **Achieve** goal.

**2. Identifying the two macro-phases.**
The text explicitly separates two phases and states their order: *"Once retrieved, the delivery phase begins"*. This is an explicit temporal marker ("once...then"), so the Collection Phase (**G2**) and Delivery Phase (**G5**) are linked by a **sequential** runtime operator, not parallel or fallback — the order is stated, not conditional.

**3. Detecting FALLBACK triggers.**
The description contains three clearly conditional ("If...") clauses that describe a normal behavior and an alternative triggered by a threshold/failure:
- Battery ≤10% during collection → return to recharge + reassign (alternative to continuing collection).
- Battery ≤30% during delivery → return resource to checkpoint + reassign (alternative to continuing delivery).
- Failure to reach the checkpoint → report to sector manager (alternative to the checkpoint-return succeeding).

Per the given rules, each of these is modeled as **FALLBACK(normal, alternative)**, and — per the rule that fallback pairs are always AND-related — each parent is an **AND** decomposition.

**4. Distinguishing sequential vs. parallel at the task level.**
Where the text uses explicit ordering language ("go to storage... then send message... and waits until retrieved"; "return to checkpoint... [then] assign the remaining task... which will know where the resource is positioned" — the second action depends on the first having happened), I used **sequential (;)**. Where the text simply joins two actions with "and" without stating which comes first (e.g., "goes back to the recharging station **and** assigns the mission to another robot"), I used **parallel (#)**, since the rule restricts sequential/fallback to *explicitly* ordered or conditioned cases.

**5. Avoiding "zero-robot" nodes.**
The sentence *"The order to be followed is defined by the estimation of waiting time summed up with the path to be run by the robot"* describes a planning criterion, not an independent action performed by a robot as a distinguishable goal — it is not clearly attributed to a robot performing a query, so it was **not** modeled as a separate Query goal. Instead, it is folded into the justification of the navigation task (AT1), consistent with the rule that non-robot-performed elements must not appear as nodes.

**6. Avoiding redundancy for the "multiple robots in parallel" note.**
*"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks..."* describes **multiple instantiations of the same mission goal (G1)** running concurrently — not a distinct intention. Since the parallel operator requires `exp1 ≠ exp2`, and duplicating G1 would violate the no-redundancy rule (same underlying intention), this is **not modeled as a tree node**, but documented as a system-level deployment note (see end of document).

**7. Classifying goal types.**
- Goals with a clear end-state to be reached through planning/action (resources retrieved, resources delivered, robot back at station + mission handed off, etc.) → **Achieve**, each with an explicit target condition.
- G9 ("send report to sector manager") is a bare communicative action with no further state to validate within the model's scope → **Perform** (same character as the "Enter the Car" example).
- No goal in this mission is purely informational with no resulting action → no **Query** goals were needed.

**8. Tasks, locations and robot counts.**
Every leaf task was grounded only in locations explicitly cited in the text: *storage, recharging station, checkpoint, sector manager, the specified/requested delivery location*. Robot counts were inferred from the singular framing ("a robot must...", "the robot...") — each operational task is carried out by **1 robot**; reassignment tasks are still counted as performed by 1 robot (the one handing off), with the second robot appearing as the *outcome* of the task rather than as an active performer of it (noted explicitly in the justification).

## Logical Relationships

- **G1 -> G2, G5 [AND] (sequential)**
  - **Justification**: The mission requires both phases to be fulfilled, and the text explicitly states delivery only starts once collection concludes ("Once retrieved, the delivery phase begins").

- **G2 -> G3, G4 [AND] FALLBACK(G3, G4)**
  - **Justification**: Normal collection (G3) is the default path; the explicit IF-condition on battery ≤10% introduces G4 as the alternative pursued only if the normal process cannot continue. Per the rules, FALLBACK pairs are AND-related.

- **G3 -> AT1, AT2, AT3 [AND] (sequential)**
  - **Justification**: The description lays out an explicit chronological chain — reach the storage, then request, then wait — with each step depending on completion of the previous one.

- **G4 -> AT4, AT5 [AND] (parallel)**
  - **Justification**: Both actions (returning to recharge, reassigning the mission) are required, but the text only joins them with "and," giving no explicit order — hence parallel (possible concurrency), not sequential.

- **G5 -> G6, G7 [AND] FALLBACK(G6, G7)**
  - **Justification**: Same logic as G2 — normal delivery (G6) is default, with an explicit battery-threshold condition (30%) introducing the contingency (G7).

- **G6 -> AT6 [AND, trivial single child]**
  - **Justification**: Only one concrete action is described ("make as many runs as necessary"); no additional sub-step was invented to avoid introducing unstated content.

- **G7 -> G8, G9 [AND] FALLBACK(G8, G9)**
  - **Justification**: G8 (checkpoint return & reassign) is the primary contingency response; the explicit "in case of failure to return the resource to a checkpoint" clause introduces G9 as the nested fallback.

- **G8 -> AT7, AT8 [AND] (sequential)**
  - **Justification**: The new robot must know "where the resource is positioned," which requires the resource to already be at the checkpoint — so returning the resource must precede reassignment.

- **G9 -> AT9 [AND, trivial single child]**
  - **Justification**: The contingency-on-failure behavior is a single communicative act (send the alert report); no further decomposition is supported by the text.

### Modeling note — multi-robot parallelism across storages
The clause *"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks..."* describes **multiple concurrent instantiations of G1** (the whole mission tree) across different robots/storages — it is the same underlying intention repeated, not a new one. Since the parallel operator requires two *different* expressions (`exp1 ≠ exp2`) and the no-redundancy rule forbids duplicating a goal with the same intention, this was intentionally **not** added as a tree node. It is instead captured as a deployment-level behavior: the goal tree rooted at G1 may be executed by several robots simultaneously, one instance per required item/storage, to reduce overall mission time.
