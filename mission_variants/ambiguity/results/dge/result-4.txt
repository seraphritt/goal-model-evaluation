# Goal Model Analysis: Multi-Robot Collect-and-Deliver Mission

## Step-by-Step Reasoning

**Step 1 — Identify the root intention.**
The description's first sentence states the overall purpose: *"a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location."* This is a state to be brought about (resources end up delivered), not a single atomic action, so the root is an **Achieve** goal. It naturally splits into two complementary intentions — **collect** and **deliver** — which are both required (**AND**), and the text later confirms their order explicitly ("*Once retrieved, the delivery phase begins*"), so the relation between them is **sequential**, not fallback (no condition/exception is involved at this transition) and not parallel (delivery cannot start before collection finishes).

**Step 2 — Detect the fallback patterns.**
Two clauses begin with *"If the battery... runs low"* / *"becomes low"*. These are explicit IF-conditioned exceptions to a normal flow, which is the precise definition of **FALLBACK**. This happens once in the collection phase and once in the delivery phase, so I introduce a "phase" goal above each (Collection Phase / Delivery Phase) whose children are `FALLBACK(normal-flow, battery-low-handling)`. Per the rules, a FALLBACK pair is always **AND**-related (both branches belong to the same goal; only one executes at runtime, but structurally both are "required alternatives").

A third, nested fallback appears inside the delivery-battery-low handling: *"In case of failure to return the resource to a checkpoint, an alert must be triggered..."* — another explicit condition/exception, so this becomes a second, nested `FALLBACK`.

**Step 3 — Identify sequential vs. parallel micro-steps.**
Within each normal flow, the text gives an explicit temporal order via connectives like "once," "and," "then implied by narration":
- Collection: *estimate order → travel → send request → wait for retrieval* (explicit "once... and... waits until").
- Delivery: *load → transport*, repeated in runs (operationally necessary order, since a robot cannot transport what it hasn't loaded).
- Recovery actions ("goes back... **and** assigns...", "return... **and** assign...", "alert... **and** report...") are all narrated in a fixed left-to-right order with no indication they are optional/simultaneous, so I treat them as **sequential**, not parallel. Parallel is reserved only for the one place the text explicitly licenses simultaneity.

**Step 4 — Find the one genuine parallel clause.**
*"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks..."* — here the text explicitly uses "parallel" and "possibility" language (*can*, not *must*). This does **not** describe two different sub-goals of one robot's mission tree racing each other; it describes **multiple instances of the entire mission tree** running concurrently, one per robot/item. Since the schema's `Number of Robots` field exists precisely to encode "how many robots execute this task," I encode this clause there (as a range `[1, n]`) on every task belonging to the core collect/deliver chain, rather than inventing an artificial in-tree parallel operator between two different sibling goals (which would misrepresent the mission — the parallelism is across repetitions of the same subtree, not between two different goals).

**Step 5 — Classify goal types.**
Every goal except one has a clear target condition (robot at a location, resource retrieved, resource delivered, mission reassigned) — these are **Achieve** goals. The *"alert must be triggered and report sent"* clause (G11) has no further state to plan toward — it is a direct execution of two notification actions upon failure, matching the **Perform** goal pattern (cf. "Enter the Car"), so I classify it as **Perform**. No clause in the text is purely about *retrieving information with no action required* at the goal level (the one estimation step is modeled as a task, since it is an operational computation a robot executes, not a standalone intentional objective) — so no top-level **Query** goal was needed here.

**Step 6 — Ground goals into tasks.**
Each terminal pair of actions becomes two Task nodes (AND, sequential), each carrying a `Location` explicitly cited in the text (storage, recharging station, checkpoint, specified/delivery location) and a `Number of Robots` (1 for individual battery/failure events that by nature affect a single robot; `[1,n]` for the core chain that can be parallelized per item/storage).

**Step 7 — Check for zero-robot / redundant nodes.**
No task lacks a robot executor. No intention is duplicated (e.g., "going to storage" appears once, not once per phase). The two illustrative examples (sterile equipment, clean linens) are not separate goals — they are instantiations of the generic "resource"/"storage"/"specified location" variables already captured by G1, AT1–AT8, so adding goals for them would be redundant duplication, which is explicitly disallowed.

```
│  │  ├─ G4 Travel to Storages in Optimal Order (AND, seq: AT1;AT2)
│  │  │  ├─ AT1 Estimate Waiting Time and Path per Storage
│  │  │  └─ AT2 Travel to Storage Locations in Computed Order
│  │  └─ G5 Request and Retrieve Resources at Storage (AND, seq: AT3;AT4)
│  │     ├─ AT3 Send Resource Request Message to Storage
│  │     └─ AT4 Wait for Resource Retrieval Confirmation

│     └─ AT6 Assign Collection Mission to Another Robot
└─ G7 Complete Delivery Phase (AND, FALLBACK(G8,G9))
   ├─ G8 Execute Normal Delivery (AND, seq: AT7;AT8)

   │  └─ AT8 Transport Resources to Specified Location

      └─ G11 Trigger Alert and Report Failure (AND, seq: AT11;AT12)
         ├─ AT11 Trigger Alert
         └─ AT12 Send Report to Sector Manager
```

## Logical Relationships

- **G1 -> G2, G7 [AND](sequential)**
  - **Justification**: Collection and delivery are both mandatory; the text explicitly orders them ("once retrieved, the delivery phase begins").

- **G2 -> G3, G6 [AND][FALLBACK(G3,G6)]**
  - **Justification**: The low-battery clause is an explicit IF-condition interrupting the normal collection flow, the defining case for FALLBACK; FALLBACK pairs are always AND-related.

- **G3 -> G4, G5 [AND](sequential)**
  - **Justification**: The robot must physically arrive at a storage before it can request resources there ("once the robot reaches one storage... it is time to request").

- **G4 -> AT1, AT2 [AND](sequential)**
  - **Justification**: The visiting order must be computed (estimation of wait time + path) before the robot can travel according to that order.

- **G5 -> AT3, AT4 [AND](sequential)**
  - **Justification**: "...sends a message... and waits until the resources have been retrieved" gives an explicit left-to-right order.

- **G6 -> AT5, AT6 [AND](sequential)**
  - **Justification**: Both actions are required by "goes back... and assigns..."; narrated in that order with no indication of optionality or simultaneity.

- **G7 -> G8, G9 [AND][FALLBACK(G8,G9)]**
  - **Justification**: The delivery-phase battery clause is another explicit exception condition, structurally identical to G2's case.

- **G8 -> AT7, AT8 [AND](sequential)**
  - **Justification**: Loading must precede transporting each run; this is the only operationally coherent order, repeated "as many runs as necessary."

- **G9 -> G10, G11 [AND][FALLBACK(G10,G11)]**
  - **Justification**: "In case of failure to return the resource to a checkpoint" is an explicit condition triggering an alternative (escalation) path — a FALLBACK nested inside the delivery-battery handling.

- **G10 -> AT9, AT10 [AND](sequential)**
  - **Justification**: "...must return the resource to a checkpoint and assign the remaining task..." states the two actions in that order.

- **G11 -> AT11, AT12 [AND](sequential)**
  - **Justification**: "an alert must be triggered and the report sent" lists the two notification actions in that order.

### A note on the "parallel" clause
The sentence *"multiple robots can be assigned to parallel collect-deliver tasks"* is not modeled as an in-tree parallel (`#`) operator between two sibling goals, because it does not describe two different intentions racing each other — it describes **multiple concurrent instances of the same collect-deliver subtree** (one per robot/storage-item). I represented it instead through the `Number of Robots = [1, n]` range on every task in the core chain (AT1–AT4, AT7–AT8), which is precisely what that field is designed to capture, while keeping battery-failure and alert tasks at a fixed count of 1 (since those are, by definition, single-robot events).
