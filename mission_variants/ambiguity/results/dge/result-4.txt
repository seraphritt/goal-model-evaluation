# Goal Model for the Multi-Robot Collect-and-Deliver Mission

## 1. Step-by-Step Reasoning (Design Rationale)

**Step 1 — Identify the top-level intention.**
The mission text opens with "a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location." This is a single overarching intentional state (resources end up where they're needed), so it becomes the root **Achieve** goal. Two clearly named phases follow ("In the collection phase..." / "...the delivery phase begins"), and the text explicitly states delivery only starts *after* retrieval ("Once retrieved, the delivery phase begins") — an explicit temporal order with no failure condition attached, so I used **sequential (`;`)**, not fallback, between these two phases.

**Step 2 — Collection phase.**
Two explicit sub-steps are given in strict order: (a) travel to storage ("the robot must go to the storage places..."), then (b) request/retrieve ("Once the robot reaches one storage and it is time to request the resource..."). The word "once" signals an explicit precedence condition → **sequential**. Requesting and waiting are themselves two explicitly ordered actions ("sends a message... and waits until...") → **sequential** again.

**Step 3 — Battery-low contingency (collection, 10%).**
This is introduced with an explicit "If" — a conditional exception to the normal flow. Per the given rule, an explicit IF-triggered alternative behavior must be modeled as **FALLBACK**, not OR. Since FALLBACK mandates an AND relation between its two expressions, I introduced a goal that groups "normal collection" and "battery-low handling" under AND, with runtime `FALLBACK(normal, battery-low)`.
Inside the battery-low handling, "goes back to the recharging station **and** assigns the mission to another robot" uses a plain conjunction with no ordering word (no "then"/"once") and no stated dependency between the two actions, so I modeled it as **AND + parallel (`#`)** rather than sequential.

**Step 4 — Delivery phase.**
"The robot will make as many runs as necessary" is one continuous operational task (repeated trips by the *same* robot, not multiple robots), so it stays a single task rather than a goal.

**Step 5 — Battery-low contingency (delivery, 30%).**
Same IF-triggered logic → **FALLBACK** at the top of the delivery goal (normal delivery vs. battery-low handling), AND-related.
Inside this handling, "return the resource to a checkpoint **and** assign the remaining task to another robot, which will know where the resource is positioned" — here, unlike the collection case, there *is* an implicit dependency: the new robot can only "know where the resource is positioned" once it has actually been placed at the checkpoint. This justifies **sequential**, not parallel, ordering.

**Step 6 — Nested fallback.**
"In case of failure to return the resource to a checkpoint, the robot must send the report to the sector manager" is a second, explicit IF-condition nested inside the first contingency → a second **FALLBACK** node (return-to-checkpoint vs. report-failure), AND-related, nested one level below the sequential pair from Step 5 — mirroring the `FALLBACK(FALLBACK(...), ...)` nesting pattern from the instructions, though here the nesting is FALLBACK inside a sequential AND rather than FALLBACK inside FALLBACK.

**Step 7 — Multi-robot parallel assignment clause.**
"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks" describes **multiple instantiations of the entire tree** (one full Collect→Deliver mission per required item/storage running concurrently), not two *different* sibling sub-goals of one mission. Since the runtime operators (`#`, `;`, FALLBACK) explicitly require `exp1 ≠ exp2`, this clause cannot be expressed by referencing the same goal twice. I therefore treat it as a **multiplicity/scheduling property of the whole mission template** rather than a tree node, and flag it in the task justifications (robot count = 1 per task *within one instance*, with concurrent instances handling the "multiple robots" clause).

**Step 8 — Goal type classification.**
Every goal in this mission has a concrete resulting world-state (resources retrieved, robot back at charging station, resource at checkpoint, mission reassigned, report sent) that the robot plans and acts to reach — this is the textbook definition of **Achieve**. There is no action in the text whose only purpose is information-gathering (no **Query** goal fits), and no goal where "performing the action, regardless of whether the resulting state holds" is the only concern — even the contingency actions have a clear resulting state, so **Perform** was not used either. I note this explicitly rather than forcing an artificial Query/Perform goal.

**Step 9 — Zero-robot pruning check.**
I deliberately did **not** create a goal/task for "the sector manager reviews the alert," because the sector manager is not a robot and performs no robot action — only the robot's act of *sending* the report is modeled (as AT8). This respects the "zero-robot goals/tasks must not appear" rule.

**Step 10 — Redundancy check.**
"Sterile medical equipment" and "clean linens" are only *examples* of the generic "resources"/"specified location" variables already captured by AT1, AT6, etc. — they don't introduce new behavior, so no duplicate goals were created for them.

**Step 11 — Location & robot-count sourcing.**
Every `Location` value used below (storage, recharging station, checkpoint, specified location) is copied verbatim from the mission text — none were invented. Every `Number of Robots` is 1, because the text consistently refers to "the robot" (singular) for every individual action; the only place robot *multiplicity* appears is the mission-level parallel-instantiation clause discussed in Step 7.

## 2. Goal Tree (outline)

```
G1 Fulfill Resource Request                              [AND; G2;G6]
├─ G2 Collect Resources                                   [AND; FALLBACK(G3,G5)]
│  ├─ G3 Execute Normal Collection                        [AND; AT1;G4]
│  │  ├─ AT1 Navigate to Storage Locations
│  │  └─ G4 Request and Retrieve Resources                [AND; AT2;AT3]
│  │     ├─ AT2 Send Resource Request Message
│  │     └─ AT3 Wait for Resource Retrieval
│  └─ G5 Handle Low Battery During Collection              [AND; AT4#AT5]
│     ├─ AT4 Return to Recharging Station
│     └─ AT5 Assign Collection Mission to Another Robot
└─ G6 Deliver Resources                                   [AND; FALLBACK(AT6,G7)]
   ├─ AT6 Transport Resources to Specified Location
   └─ G7 Handle Low Battery During Delivery                [AND; G8;AT9]
      ├─ G8 Secure Resource at Checkpoint                  [AND; FALLBACK(AT7,AT8)]
      │  ├─ AT7 Return Resource to Checkpoint
      │  └─ AT8 Send Failure Report to Sector Manager
      └─ AT9 Assign Remaining Delivery Task to Another Robot
```

| **G5**: Handle Low Battery During Collection | When the robot's battery drops to 10% during collection, it returns to recharge and the mission is reassigned. | `AT4#AT5` | Achieve — Target: robot is back at the recharging station and the collection mission has been reassigned to another robot | AND (child of G2, FALLBACK exp2) | Explicit IF-condition ("If the battery... runs low... in the collection phase") → FALLBACK alternative to G3. | **G6**: Deliver Resources | The robot transports all retrieved resources to the specified location, handling battery contingencies. | `FALLBACK(AT6,G7)` | Achieve — Target: all resources delivered to the requesting agent's specified location | AND (child of G1) | Same fallback logic as G2, triggered by the explicit battery-30% IF-condition in the delivery phase. |
| **G7**: Handle Low Battery During Delivery | When battery drops to 30% during delivery, the robot secures the resource and hands the remaining task to another robot. | `G8;AT9` | Achieve — Target: resource secured and remaining delivery task reassigned to another robot | AND (child of G6, FALLBACK exp2) | The new robot must already "know where the resource is positioned," which is only true once it is placed at the checkpoint — an implicit dependency that justifies sequential ordering, unlike the parallel case in G5. |
| **G8**: Secure Resource at Checkpoint | The robot attempts to return the resource to a checkpoint; if that fails, it reports the failure to the sector manager. | `FALLBACK(AT7,AT8)` | Achieve — Target: resource returned to checkpoint, or, failing that, sector manager notified | AND (child of G7) | Explicit second IF-condition ("In case of failure to return the resource to a checkpoint...") → nested FALLBACK, AND-related by rule. |

*No Query or Perform goals were used*: every goal in the description resolves to a concrete, verifiable world-state the robot works toward (Achieve), and no step is purely about gathering information about the world (which would require Query).

## 6. Logical Relationships

- **G1 -> G2, G6 [AND] (sequential)**
  - **Justification**: Both phases are mandatory (AND). The text explicitly states delivery starts only "once retrieved," a stated — not conditional — order, so sequential (`G2;G6`).

- **G2 -> G3, G5 [AND] [FALLBACK(G3,G5)]**
  - **Justification**: The 10%-battery IF-condition makes G5 an explicit alternative path to normal collection (G3); FALLBACK relations are always AND by definition.

- **G3 -> AT1, G4 [AND] (sequential)**
  - **Justification**: The robot must physically arrive at storage before it can request resources ("Once the robot reaches one storage..."); both are required, in that explicit order.

- **G4 -> AT2, AT3 [AND] (sequential)**
  - **Justification**: "Sends a message... and waits until retrieved" — both required, explicitly ordered.

- **G5 -> AT4, AT5 [AND] (parallel)**
  - **Justification**: Both actions are required (AND), but joined only by "and" with no dependency or ordering word, so modeled as possibly concurrent.

- **G6 -> AT6, G7 [AND] [FALLBACK(AT6,G7)]**
  - **Justification**: The 30%-battery IF-condition makes G7 an explicit alternative path to normal delivery (AT6); FALLBACK requires AND.

- **G7 -> G8, AT9 [AND] (sequential)**
  - **Justification**: The reassigned robot "will know where the resource is positioned" only once it has actually been placed at the checkpoint, so G8 must precede AT9.

- **G8 -> AT7, AT8 [AND] [FALLBACK(AT7,AT8)]**
  - **Justification**: "In case of failure to return the resource to a checkpoint" is an explicit second IF-condition, nested below G7's sequential pair — a classic fallback.

---

**Note on the "multiple robots / parallel missions" clause**: because the runtime operators require two *distinct* expressions, the statement that "multiple robots can be assigned to parallel collect-deliver tasks" when several items/storages are involved is best captured as the whole G1 tree being **instantiated multiple times concurrently** (one instance per item/storage), rather than as a node inside a single instance's tree — each task's `Number of Robots = 1` reflects one robot per instance, while concurrency across instances handles the multi-robot clause.
