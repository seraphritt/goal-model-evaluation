# Mission Analysis: Resource Collection & Delivery for Multi-Robot Systems

## Step-by-Step Reasoning

**1. Identifying the top-level intention.** The description opens with a single overarching purpose: *"a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location."* This is one intention (fulfilling a resource request) expressed as a target state — resources ending up at a destination — so it becomes the root **Achieve Goal (G1)**.

**2. Splitting into phases.** The text explicitly separates two phases and states *"Once retrieved, the delivery phase begins"* — an explicit textual marker of order. This justifies a **sequential** runtime annotation (not parallel, not fallback, since there's no condition/failure triggering delivery — it's a deterministic hand-off) between a Collection goal and a Delivery goal.

**3. Inside Collection — order matters before travel.** The text says the robot must go to storages, and *then* explains how the order is computed. Logically, the order must be known before the robot starts the storage-visiting loop, so I treat "determine order" and "execute the retrieval loop" as sequential children of a "Normal Collection" goal.

**4. Classifying "determine order" as a Query Goal.** This step produces *information* (a sequence/order), not a world-state change — it matches the Query Goal definition exactly ("obtain knowledge or data").

**5. The retrieval loop is a 3-step sequence.** The text gives an explicit order: reach storage → send request message → wait until retrieved. These are concrete, location-bound, robot-executable steps → three **Tasks**, sequential.

**6. Battery failures are FALLBACK, not OR.** Both battery-low cases ("If the battery... runs low... the robot goes back...") are *condition-triggered alternatives to normal execution* — this is the textbook trigger for the FALLBACK operator (explicitly instructed: "it's often related to a condition, usually represented by an IF-statement"). I nested a **second** FALLBACK inside the delivery-battery branch, because the text itself nests a failure condition: *"In case of failure to return the resource to a checkpoint..."* — a failure inside the failure-handling path.

**7. Why not use OR decomposition anywhere?** OR decomposition expresses *alternative ways to satisfy the same intention* (e.g., "by this route or that route"), not *condition-triggered recovery* (= FALLBACK) or *ordered steps* (= sequential). Nothing in the text presents two independent, equally-valid alternative strategies — every branching point is either a failure condition (FALLBACK) or a required joint step (AND). So the entire tree uses AND decomposition only, with FALLBACK/sequential runtime annotations layered on top, as required by the FALLBACK rule ("sub-goals exp1 and exp2 are always connected by an AND-decomposition").

**8. Why I did *not* use the parallel ("#") operator anywhere.** The description does mention parallelism: *"multiple robots can be assigned to parallel collect-deliver tasks."* However, the parallel operator's own syntax rule states *"exp1 cannot be the same goal as exp2."* The parallelism described here is multiple **instances of the same goal tree** (G1) running concurrently on different robots for different storages/items — not two *distinct* sub-goals of one goal executing together. Since the notation cannot express "run goal X twice, on two different robots," I instead captured this fact in the **Number of Robots** attribute (as a range) on the core collection/delivery tasks, and flagged it explicitly in the Summary Notes below.

**9. Avoiding redundancy.** "Collection Phase" (G2) and "Normal Collection Execution" (G3) look similar but are distinct intentions: G2 is "resources retrieved, by whatever path (normal or recovery)" while G3 is specifically "the default, uninterrupted procedure." This split is structurally required to express FALLBACK (two distinct children), not redundant duplication.

**10. Zero-robot check.** Every leaf in the tree terminates in a robot-executable Task (travel, send message, wait, recharge, reassign, transport, return-to-checkpoint, report). The one non-task leaf (G4, Determine Visit Order) is still carried out by the assigned robot's own route-planning computation, so it satisfies "performed by a robot."

### Notes on parallel multi-robot execution
The description's closing statement — *"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks"* — describes **multiple concurrent instances of the entire G1 tree** (different robots each running their own collect-deliver mission for a different item/storage), not two distinct sub-goals running in parallel within a single mission. Since the runtime grammar's parallel operator requires `exp1 ≠ exp2`, this scalability couldn't be expressed as a `#` relation inside the tree; instead it is captured through the **[1, n] Number-of-Robots ranges** on AT1, AT2, AT3, and AT6 — the tasks that would actually be replicated across robots when multiple items/storages are in play.
