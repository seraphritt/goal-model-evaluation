# Mission Analysis: Goal Model for Multi-Robot Collect-and-Deliver Mission

## Step-by-Step Reasoning

**1. Identifying the root intention.**
The description opens with the core mandate: *"a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location."* This is the mission's single overarching intention — everything else (ordering, battery handling, parallelism) is a refinement of *how* this is achieved. This becomes **G0**, an **Achieve Goal**, since it describes a target world-state (resources delivered) to be reached through planning/action, not a one-shot action or a mere query.

**2. Splitting Collection vs. Delivery.**
The text explicitly separates two phases ("In the collection phase…", "Once retrieved, the delivery phase begins"). The word "once…begins" is an explicit temporal marker — delivery cannot start before collection ends — so this is a **sequential** relation, not parallel. Both phases are mandatory, so it's an **AND** decomposition, not OR (OR would imply either phase alone suffices, which contradicts the mission).

**3. Detecting FALLBACK patterns.**
I specifically scanned for IF-conditioned alternative behaviors, as instructed:
- *"If the battery... runs low (10%) in the collection phase, the robot goes back to the recharging station and assigns the mission to another robot."* → explicit IF → **FALLBACK** between normal collection and this recovery behavior.
- *"If the battery... becomes low during the delivery phase, the robot must return the resource to a checkpoint..."* → explicit IF → **FALLBACK** between normal delivery and this recovery behavior.
- *"In case of failure to return the resource to a checkpoint, an alert must be triggered..."* → explicit IF/failure clause → a **nested FALLBACK** inside the delivery-recovery branch.

Per the rules, every FALLBACK's two branches are connected by **AND** (not OR), since OR would only apply to true alternatives/choices, while FALLBACK means "try exp1, and only if it fails, do exp2" — both are necessary in the full behavioral envelope of the system.

**4. Detecting PARALLEL vs SEQUENTIAL (non-fallback) relations.**
I applied a consistent rule throughout: 
- **Sequential** is used when the text states explicit temporal order ("once X, Y begins") *or* when one action is physically/logically impossible before another (can't send a request before reaching the storage; can't load before retrieving; can't transport before loading).
- **Parallel** is used for plain conjunctions ("X and Y") where no explicit order or logical necessity is stated — e.g., "goes back to the recharging station **and** assigns the mission to another robot" does not require waiting for physical arrival before reassigning; reassigning promptly is actually more consistent with the mission's general concern for minimizing time.

This is why:
- Estimating waiting time and estimating path (both needed to compute the order) → **parallel** (AT1#AT2) — independent estimations.
- Navigate → Request → Wait → **sequential** (explicit stepwise narrative + physical necessity).
- Return-to-recharge & reassign-mission → **parallel** (plain conjunction, no dependency).
- Load → Transport → **sequential** (can't transport unloaded resources).
- Trigger alert & send report → **parallel** (plain conjunction, no stated order).

**5. Assigning Goal Types.**
- Goals that query information without changing the world → **Query** (only "Determine Storage Visit Order", which is purely about *obtaining* waiting-time/path estimates — it doesn't act).
- All others describe a world-state to be reached (resources retrieved, robot at recharge station, resource at checkpoint, alert sent, etc.) → **Achieve**, each given an explicit target condition.
- No goal matched **Perform** (an action executed without caring about reaching a resulting state) — every identified intention in this description has a clearly checkable resulting state, so Perform was not used. I flag this explicitly rather than force-fitting a Perform goal.

**6. Handling multiplicity/parallel robots.**
*"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks..."* This is a **multiplicity** statement (how many robot instances execute the same template), not a new distinct intention — the goal tree already represents one generic collect-deliver template. I captured this via the **Number of Robots** attribute (a range `[1,n]`) on the task of navigating to storage, rather than inventing new goal nodes, since the underlying actions (navigate/request/wait) remain identical regardless of how many robots run them concurrently.

**7. Excluding zero-robot elements.**
The "requesting agent" (recipient) and the "storage system" itself (which internally retrieves items) are not robots under this mission's control — they are external actors/locations. I did not create goals/tasks for them; I only modeled the robot's own actions (e.g., the robot *waiting* for retrieval, not the storage *performing* the retrieval).

**8. Handling the examples (sterile equipment, linens).**
These are illustrative instances of "resources"/"storage"/"specified location," not new requirements — they don't introduce new robot behavior, so they were **not** turned into separate goals/tasks, only used to confirm that "storage," "specified location" etc. are legitimate, cited location variables.

**9. OR decomposition.**
No part of the description presents genuine alternatives ("do A or do B, either suffices"). Every decomposition found is either a necessary conjunction (AND) or a conditioned recovery path (FALLBACK, which is itself AND). Hence **no OR decomposition appears** in this model — this is a deliberate, justified absence, not an oversight.

## Logical Relationships

- **G0 -> G1, G6 [AND] (sequential: G1;G6)**
  - **Justification**: Collection and delivery are both mandatory; delivery explicitly begins only "once retrieved," establishing a strict temporal order.

- **G1 -> G2, G5 [AND] FALLBACK(G2, G5)**
  - **Justification**: Battery-low during collection is an explicit IF-conditioned alternative to normal collection; FALLBACK branches are always AND-connected.

- **G2 -> G3, G4 [AND] (sequential: G3;G4)**
  - **Justification**: The visit order must be determined before it can be followed — a necessary precursor, not an alternative.

- **G3 -> AT1, AT2 [AND] (parallel: AT1#AT2)**
  - **Justification**: Both estimations ("waiting time" and "path") are explicitly summed together to compute order; they are independent computations with no stated dependency, hence parallel.

- **G4 -> AT3, AT4, AT5 [AND] (sequential: AT3;AT4;AT5)**
  - **Justification**: The narrative explicitly sequences these — reach the storage, then request, then wait — and each step is a physical precondition for the next.

- **G5 -> AT6, AT7 [AND] (parallel: AT6#AT7)**
  - **Justification**: "Goes back...and assigns..." is a plain conjunction with no stated order or dependency; prompt reassignment (not waiting for physical arrival) better serves the mission's implicit efficiency concern.

- **G6 -> G7, G8 [AND] FALLBACK(G7, G8)**
  - **Justification**: Battery-low during delivery is an explicit IF-conditioned alternative to normal delivery.

- **G7 -> AT8, AT9 [AND] (sequential: AT8;AT9)**
  - **Justification**: Resources must be loaded before they can be transported — physical necessity.

- **G8 -> G9, AT13 [AND] (sequential: G9;AT13)**
  - **Justification**: The reassigned robot must "know where the resource is positioned," which is only determined once the securing attempt (G9) resolves (checkpoint success or escalation via alert).

- **G9 -> AT10, G10 [AND] FALLBACK(AT10, G10)**
  - **Justification**: "In case of failure to return the resource to a checkpoint" is an explicit nested IF-condition triggering the alert/report path.

- **G10 -> AT11, AT12 [AND] (parallel: AT11#AT12)**
  - **Justification**: "An alert must be triggered and the report sent" is a plain conjunction with no explicit ordering stated.

## Notes and Assumptions
- **No OR decomposition appears anywhere** in this model — the mission presents no true alternatives (choices where fulfilling just one child suffices); every relation is either a necessary conjunction (AND) or a conditioned recovery path (FALLBACK, itself AND). This is a deliberate conclusion, not an omission.
- **No Perform goal was used** — every intentional node in the mission has a checkable resulting state (Achieve) or is purely informational (Query, used only for G3); none described an action performed "for its own sake" without a target state.
- The mission's **examples** (sterile medical equipment, clean linens) were treated as illustrative instances of "resources"/"storage"/"specified location" rather than separate goals, since they introduce no new robot behavior.
- The **parallel multi-robot clause** ("multiple robots can be assigned to parallel collect-deliver tasks") was captured via the `[1, n]` range on AT3's Number of Robots rather than by duplicating the goal tree, since the underlying action template is identical regardless of instance count.
- The **requesting agent** and the **storage system's internal retrieval process** were excluded as they are not robots performing actions under this model's scope (zero-robot exclusion rule).
