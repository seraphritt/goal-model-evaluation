# Mission Decomposition: Resource Collection & Delivery by Multi-Robot System

## Step-by-Step Reasoning

Before presenting the model, here is my analytical process:

**1. Identifying the top-level intention.**
The description opens with the core mandate: "a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location." This is a single overarching achievement — a clear target state (resources delivered) reached through planning and multi-step action. This becomes my root goal, **G1**.

**2. Splitting into phases.**
The text explicitly separates two phases and tells me their order: "In the collection phase..." and "Once retrieved, the delivery phase begins." The word "once" is an explicit temporal marker (not a failure/condition), so I used **sequential (`;`)**, not FALLBACK, between Collection and Delivery.

**3. Decomposing the Collection Phase.**
Three explicit, ordered sub-steps appear:
- go to storage (order determined by waiting time + path estimate) → I classified computing this order as a **Query goal**, since it is about obtaining information (an estimate), not changing the world — directly analogous to the "Fetch Occupied Rooms" example.
- travel there → **Achieve** (target: robot physically at the storage), since arriving somewhere is a state reached via planning/motion, not a single atomic act.
- send request message → **Perform**, since this is a discrete communicative act (like "Enter the Car") with no further target state to track.
- wait until retrieved → **Achieve** (target: resource physically retrieved/loaded).

These four are explicitly ordered ("go to storage... once the robot reaches... and it is time to request... waits until") so I used nested **sequential** runtime annotations.

**4. Identifying FALLBACK triggers.**
The description gives two explicit IF-conditioned threshold interruptions:
- "If the battery... runs low (10%) in the collection phase..." → FALLBACK between normal collection and the battery-handling routine.
- "If the battery... becomes low during the delivery phase..." → FALLBACK between normal delivery and its battery-handling routine.

Per the given rule, these are modeled as FALLBACK, and per the rule that "FALLBACK(exp1, exp2) sub-goals are always AND-related," both pairs use AND decomposition despite being conditionally triggered.

**5. Nested fallback for checkpoint failure.**
"In case of failure to return the resource to a checkpoint, an alert must be triggered..." is a second, nested threshold condition sitting *inside* the delivery-battery-handling goal. I modeled this as a nested FALLBACK: `FALLBACK(ReturnToCheckpoint, HandleFailure)`, combined sequentially with the subsequent reassignment step (since reassignment logically follows resource placement/alerting), matching the example pattern `FALLBACK(FALLBACK(exp1,exp2), exp3)` conceptually — here realized as `(FALLBACK(exp1,exp2));exp3`.

**6. Avoiding zero-robot nodes.**
Two elements were deliberately excluded from the tree:
- The *storage system's own act of retrieving the resource* — this is performed by the storage, not a robot, so only the robot's "wait and load" action is modeled.
- The *sector manager's receipt of the report* — receiving is passive and not a robot action; only the robot's act of *sending* the report is modeled (inside G15/AT9).

**7. Handling the "parallel multi-robot" sentence.**
"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks" describes **concurrent instances of the entire G1 mission** (one full collect-deliver cycle per robot), not parallel children *within* a single G1 execution. Since the `#` operator explicitly forbids `exp1` being the same goal as `exp2` ("exp1 cannot be the same goal as exp2"), and since duplicating G1 as "G1a # G1b" would violate the no-redundancy rule (same intention, same goal, re-stated), I did **not** create a duplicate node. Instead, this is captured as a **mission-level concurrency policy**, documented here and reflected in the fact that every task explicitly involves a *single* robot ("the robot," singular, throughout the text) — the parallelism lives at the orchestration layer (multiple simultaneous mission instances), not inside one instance's goal tree.

**8. Handling the examples paragraph.**
Sterile medical equipment / clean linens, sterile facilities / laundry, use destinations / storage rooms are **illustrative instantiations** of the generic variables already in the model (`storage`, `specified location`). They don't introduce new goals or tasks — they confirm that `Location` is a variable that can bind to different concrete values per mission instance, which I note in the relevant task justifications.

**9. No OR decomposition.**
I found no genuine "either of these alone suffices" alternative in the text (no interchangeable sufficient paths outside the threshold-triggered FALLBACK cases, which per the rules must be AND, not OR). Hence every decomposition in this model is **AND**.

## Logical Relationships

- **G1 -> G2, G11 [AND](sequential)**
  - **Justification**: Collection and delivery are both mandatory (AND). The text states "Once retrieved, the delivery phase begins," an explicit chronological marker — hence sequential, not FALLBACK (no failure/condition is involved in this transition).

- **G2 -> G3, G8 [AND][FALLBACK(G3,G8)]**
  - **Justification**: FALLBACK is mandated because the description gives an explicit IF-condition ("If the battery... runs low... in the collection phase") switching from normal behavior (G3) to an alternative (G8). Per the rules, FALLBACK pairs are always AND-related.

- **G3 -> G4, G5, G6, G7 [AND][((G4;G5);G6);G7) sequential]**
  - **Justification**: All four steps are required (AND) and the text narrates them in explicit chronological order ("go to storage... once reached... sends a message... waits until retrieved"), warranting nested sequential operators.

- **G4 -> AT1 [AND]**
  - **Justification**: The order-computation goal is fulfilled by a single concrete computation task; AND is trivial here as there is exactly one mandatory component.

- **G5 -> AT2 [AND]**
  - **Justification**: Single mandatory navigation task fulfills the travel goal.

- **G6 -> AT3 [AND]**
  - **Justification**: Single mandatory messaging task fulfills the request goal.

- **G7 -> AT4 [AND]**
  - **Justification**: Single mandatory waiting/loading task fulfills the retrieval goal.

- **G8 -> G9, G10 [AND][(sequential)]**
  - **Justification**: Both recharging and reassignment are required (AND); the text's "goes back to the recharging station and assigns the mission to another robot" is read as securing the robot first, then dispatching the handoff — sequential.

- **G9 -> AT5 [AND]**
  - **Justification**: Single mandatory travel task fulfills the recharge-return goal.

- **G10 -> AT6 [AND]**
  - **Justification**: Single mandatory handoff task fulfills the reassignment goal.

- **G11 -> G12, G13 [AND][FALLBACK(G12,G13)]**
  - **Justification**: FALLBACK is mandated by the explicit IF-condition ("If the battery... becomes low during the delivery phase"); AND per the FALLBACK rule.

- **G12 -> AT7 [AND]**
  - **Justification**: Single mandatory (possibly repeated) delivery-run task fulfills the delivery goal.

- **G13 -> G14, G15, G16 [AND][(FALLBACK(G14,G15));G16 sequential]**
  - **Justification**: All three outcomes (secure-or-alert, then reassign) are required (AND). The nested FALLBACK reflects the explicit second IF-condition ("In case of failure to return the resource to a checkpoint..."); the subsequent sequential link to G16 reflects that reassignment is informed by where the resource ended up.

- **G14 -> AT8 [AND]**
  - **Justification**: Single mandatory task (travel + deposit) fulfills the checkpoint-return goal.

- **G15 -> AT9 [AND]**
  - **Justification**: Single mandatory escalation task (alert + report) fulfills the failure-handling goal.

- **G16 -> AT10 [AND]**
  - **Justification**: Single mandatory handoff task fulfills the remaining-task reassignment goal.

### A note on mission-level parallelism
The sentence "multiple robots can be assigned to parallel collect-deliver tasks" was deliberately **not** turned into a `#` (parallel) node inside this tree, because: (1) the parallel operator's syntax forbids `exp1` and `exp2` being the same goal, and every parallel instance here would be the *same* G1 mission re-run for a different item/storage — representing that would either violate the operator's own constraint or create a duplicate goal node representing an already-modeled intention, violating the anti-redundancy rule; and (2) every task in the model is explicitly singular ("the robot," "a robot"), confirming that concurrency happens by running multiple *independent instances* of this entire tree (one per robot/item), not by multiple robots jointly executing one task or one goal's children in parallel. This is best understood as an orchestration-level deployment policy layered on top of the model rather than a structural element within it.
