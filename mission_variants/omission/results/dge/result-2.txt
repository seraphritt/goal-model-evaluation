# Goal Model for the Collect‑and‑Deliver Multi‑Robot Mission

## Step‑by‑Step Reasoning

Before building the tables, here is my decomposition reasoning, written as a trace through the description:

**1. Identify the top‑level intention.** The description opens with the overall mission: *"a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location."* This is a single intentional objective with two clearly named phases ("collection phase", "delivery phase"), so it becomes the root goal **G1**, decomposed **AND** into *Collect* and *Deliver*. The text explicitly says delivery starts only "once retrieved" — an explicit order, so the runtime is **sequential** (`;`), not parallel.

**2. Collection phase.** Inside collection, the description gives a *normal* procedure (estimate order → visit storages → request → wait) and then an *exception*, introduced by an explicit conditional marker ("If the battery... runs low (10%)..."). Per the rules, an explicitly‑triggered exception to a normal flow is a **FALLBACK**, and FALLBACK pairs are always connected by **AND**. This gives **G2** (Collect) = `FALLBACK(G3, G6)`.

**3. Normal collection sub-flow.** "The order to be followed is defined by the estimation of waiting time summed up with the path" happens *before* actually visiting storages — this is a dependency, so **sequential**. Determining the order is pure information‑gathering (no world‑state change, no physical action by itself) → **Query goal** (**G4**), analogous to the "Fetch Occupied Rooms" example. Visiting the storages and retrieving resources is a genuine **Achieve goal** (**G5**) because it is realized by planning+acting to reach a state (resource retrieved).
 - I treat G4 as being performed by the robot itself (on‑board estimation), not an external dispatcher — this matters because of the "zero‑robot goals/tasks must not appear" rule. Since the sentence is embedded directly in robot‑centric prose with no other actor named, I attribute it to the robot.

**4. Granular collection actions.** "Once the robot reaches one storage... sends a message... and waits until retrieved" gives three explicit, ordered, physical/communicative steps → three **tasks**, sequential, AND‑related (**AT1, AT2, AT3**).

**5. Battery‑low exception (collection, 10%).** "Goes back to recharging station **and** assigns the mission to another robot" — two required actions, explicit left‑to‑right order → **Achieve goal G6**, AND, sequential, decomposed into **AT4, AT5**.

**6. Delivery phase.** Same reasoning pattern as collection: normal runs vs. an explicitly‑triggered battery exception (30%) → **G7** (Deliver) = `FALLBACK(AT6, G8)`. Note "make as many runs as necessary" is a single repeatable physical action with no second distinct activity described, so I keep it as one **task** (AT6) rather than forcing an artificial two‑child goal.

**7. Battery‑low exception (delivery, 30%).** "Return resource to checkpoint **and** assign the remaining task to another robot" → **Achieve goal G8**, AND, sequential, children **G9** (secure resource) and **AT9** (assign remaining task).

**8. Nested fallback inside the delivery exception.** "In case of failure to return the resource to a checkpoint, the report must be sent to the sector manager" is a *second*, more specific, explicitly‑conditioned fallback — triggered only by failure of the *return* action, not of the whole exception‑handling goal. This gives **G9** = `FALLBACK(AT7, AT8)`, AND.

**9. On the parallel‑execution sentence.** "When multiple items are required from different storages, multiple robots can be assigned to parallel collect‑deliver tasks" describes **multiple concurrent instances of the same mission tree** running on different robots — it is not a parallel relation between two *distinct* sub‑goals of one tree (the `#` operator requires exp1 ≠ exp2, and this sentence is the *same* goal replicated). I therefore do **not** insert a `#` node anywhere in the tree (that would misuse the operator). Instead, I encode this multiplicity on the **Number of Robots** attribute of the tasks that are actually replicated across storages/runs (AT1, AT2, AT3, AT6), using the range `[1, n]`, where `n` is the number of storages/items involved. This keeps the single‑mission tree correct while still capturing the stated parallel‑robot behavior.

**10. No OR decomposition anywhere.** OR is reserved for true alternatives (interchangeable ways to satisfy a parent). Nothing in the text offers an alternative *way* to achieve a goal — every pair of children is either jointly required (AND) or a normal/fallback pair (AND by rule). Sequencing, parallelism and fallback are all execution‑structure concerns, captured in the runtime annotation, not in the decomposition type. Hence every relation in this model is **AND**.

**11. Locations used** — all explicitly present in the text: *storage*, *recharging station*, *checkpoint*, *specified location* (generalizing "use destinations"/"storage rooms" from the examples), and *checkpoint* again for the failure report (the robot itself stays at/near the checkpoint when the return fails; "sector manager" is the message recipient, not a physical task site).

## Logical Relationships

- **G1 -> G2, G7 [AND] (sequential: G2;G7)**
  - *Justification*: Collection and delivery are both mandatory (AND) parts of the mission, and the description explicitly states delivery "begins" only "once retrieved" — a strict order, hence sequential rather than parallel or OR.

- **G2 -> G3, G6 [AND] FALLBACK(G3, G6)**
  - *Justification*: G3 is the default collection procedure; G6 is triggered only by the explicit IF‑like condition "if the battery... runs low (10%)." This is a textbook normal/exception pair, which the rules require to be modeled as FALLBACK and connected by AND.

- **G3 -> G4, G5 [AND] (sequential: G4;G5)**
  - *Justification*: Both are required for normal collection to succeed (AND). The order‑estimation (G4) must occur before storages are actually visited in that order (G5) — a clear dependency, hence sequential.

- **G5 -> AT1, AT2, AT3 [AND] (sequential: AT1;AT2;AT3)**
  - *Justification*: All three steps are necessary (AND) and the text gives them in explicit chronological order: reach the storage, then send the request, then wait for retrieval.

- **G6 -> AT4, AT5 [AND] (sequential: AT4;AT5)**
  - *Justification*: Both actions are required to recover from low battery (AND), performed in the order stated in the text: return to recharge, then assign the mission onward.

- **G7 -> AT6, G8 [AND] FALLBACK(AT6, G8)**
  - *Justification*: AT6 (normal delivery runs) is the default path; G8 is triggered only by the explicit 30% battery condition. Same normal/exception pattern as G2, so FALLBACK + AND.

- **G8 -> G9, AT9 [AND] (sequential: G9;AT9)**
  - *Justification*: Both securing the resource and reassigning the remaining task are required (AND). The text orders them explicitly ("must return the resource to a checkpoint and assign the remaining task..."), and logically the replacement robot needs the resource's resulting position — which is only known once the first action resolves — so sequential fits better than parallel.

- **G9 -> AT7, AT8 [AND] FALLBACK(AT7, AT8)**
  - *Justification*: AT7 (return to checkpoint) is attempted first; AT8 (report to sector manager) is explicitly conditioned on "failure to return the resource to a checkpoint." This is a second, more narrowly‑scoped fallback nested inside the delivery‑battery exception, connected by AND per the fallback rule.

---

**Note on consistency**: every relation above is AND rather than OR, by design — nothing in the mission text offers an *alternative* way to satisfy a parent goal; every pair of children is either jointly required or a normal/fallback pair (which the formalism forces to AND). Alternatives in *execution* (order, concurrency, exception‑handling) are captured instead through the runtime annotations (`;`, `FALLBACK(...)`), and the multi‑robot parallelism described for multiple storages/items is captured through the `[1, n]` Number‑of‑Robots ranges on AT1, AT2, AT3 and AT6, rather than through a `#` parallel node, since that operator cannot relate a goal to itself.
