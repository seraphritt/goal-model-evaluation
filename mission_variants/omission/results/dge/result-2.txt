# Goal Model for the Resource Collection & Delivery Mission

## Step‑by‑Step Reasoning

**1. Identify the top‑level intention.**
The description's core sentence — *"a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location"* — gives the mission's single root intention: **fulfil a resource request** through two mandatory, complementary phases: *collection* and *delivery*. Since the text explicitly says *"Once retrieved, the delivery phase begins,"* the two phases are AND‑related (both required) and explicitly ordered → **sequential (`;`)**, not parallel or fallback (there's no conditional/failure language here, just a stated order).

**2. Detect the two FALLBACK triggers.**
Two sentences use the IF‑pattern the rules call out explicitly:
- *"If the battery… runs low (10%)… the robot goes back to the recharging station and assigns the mission to another robot."* → a threshold interrupts the **normal collection** behaviour.
- *"In case of failure to return the resource to a checkpoint, an alert must be triggered…"* → a failure interrupts the **normal delivery** behaviour.

Both are textbook FALLBACK cases (normal behaviour + explicit exception), so each phase decomposes as `FALLBACK(normal, exception)`, always AND‑related per the rules.

**3. Decompose "normal collection."**
The text gives two distinct, ordered sub-activities: (a) *decide the order* ("order… defined by the estimation of waiting time summed up with the path") and (b) *execute the visits* ("Once the robot reaches one storage… sends a message… waits until retrieved"). (a) must logically precede (b), so they're sequential. (a) is pure information-gathering (no world change) → **Query goal**. Its own inputs — waiting-time estimate and path estimate — are explicitly *summed*, implying both are needed (AND) with no stated order between them → modeled as **parallel (`#`)**. (b) is a concrete chain explicitly ordered by the text ("reaches… sends… waits") → three sequential tasks, and because it changes the world state (resource acquired) → **Achieve goal**.

**4. Decompose the battery exception.**
"Goes back… and assigns…" — two required, naturally ordered actions → sequential, AND. Reaching the recharge station is a state-attainment → **Achieve goal**.

**5. Decompose "normal delivery."**
"Make as many runs as necessary to take all resources to the specified location" implies repeated trips, each requiring (a) travelling there and (b) unloading — travel must physically precede unloading (sequential, AND) even though "unload" isn't spelled out verbatim; it's the only way "taking resources to a location" can be operationally completed. → **Achieve goal** (state: resources transported).

**6. Decompose the delivery‑failure exception.**
"An alert must be triggered and the report sent to the sector manager" — two fixed, concrete actions with no open-ended state to reach → **Perform goal** (success = actions executed), listed in that order → sequential, AND.

**7. Locations & robot counts.**
Every location used (Storage, Recharging Station, Specified/requested Location, Checkpoint, Sector Manager) is taken verbatim from the text; the goods examples (sterile equipment, clean linens) are illustrative instantiations of "Storage"/"Specified Location," not separate goals, so they are **not** modeled as nodes. The explicit multi-robot clause — *"multiple robots can be assigned to parallel collect-deliver tasks"* — is the justification for giving the storage‑navigation task a **range** `[1,n]` instead of a fixed count; every other task is performed by the single robot assigned to that mission instance, so it gets `1`.

**8. Zero-robot filter.**
Every retained node is executed by (or on behalf of) a robot — including alerting/reporting, since the robot performs the "send" action. No node was discarded for this reason, but the illustrative goods examples were excluded as non‑operational background, not missions in themselves.

## Logical Relationships

- **G1 -> G2, G7 [AND] (sequential)**
  - **Justification**: Collecting and delivering are both mandatory; the description states delivery begins only "once retrieved," an explicit chronological dependency.

- **G2 -> G3, G6 [AND] FALLBACK(G3, G6)**
  - **Justification**: The battery threshold ("If the battery… runs low (10%)") is an explicit condition triggering an alternative to normal collection — the defining pattern for FALLBACK, which is always AND-connected.

- **G3 -> G4, G5 [AND] (sequential)**
  - **Justification**: The storage-visiting order must be known before the visits can follow it; the text introduces the ordering rule before the visiting procedure.

- **G4 -> AT1, AT2 [AND] (parallel)**
  - **Justification**: The order is "defined by the estimation of waiting time summed up with the path" — both estimates are required (AND), and since no order is stated between computing them, they can be pursued in parallel.

- **G5 -> AT3, AT4, AT5 [AND] (sequential)**
  - **Justification**: All three are required to get the resource (AND); the text's own phrasing ("reaches… sends… waits until retrieved") gives an explicit sequence.

- **G6 -> AT6, AT7 [AND] (sequential)**
  - **Justification**: Both actions are necessary to resolve the contingency (AND); they are listed in that order, and returning logically precedes/accompanies the handoff.

- **G7 -> G8, G9 [AND] FALLBACK(G8, G9)**
  - **Justification**: "In case of failure to return the resource to a checkpoint" is an explicit exception to normal delivery — FALLBACK, AND-connected.

- **G8 -> AT8, AT9 [AND] (sequential)**
  - **Justification**: Both travel and unload are required to complete a run (AND); arrival must physically precede unloading.

- **G9 -> AT10, AT11 [AND] (sequential)**
  - **Justification**: Both actions are required for failure handling (AND); the text lists alert before report, read as the alert prompting the subsequent report.

- **G4 -> AT1, AT2 [AND]; G5 -> AT3, AT4, AT5 [AND]; G6 -> AT6, AT7 [AND]; G8 -> AT8, AT9 [AND]; G9 -> AT10, AT11 [AND]**
  - **Justification**: In every case, the listed tasks are jointly necessary (not interchangeable alternatives) to fulfill their parent goal — none of the description's steps are optional substitutes for one another, so no OR-decomposition appears anywhere in this model.
