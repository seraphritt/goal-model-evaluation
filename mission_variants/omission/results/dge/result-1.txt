# Mission Decomposition: Multi-Robot Collect-and-Deliver System

## Step 1 — Identifying the Core Intentions

Reading the description top-down, I see one overarching intention ("collect and deliver resources on request") that cleanly splits into two explicitly named phases: **Collection** and **Delivery**. Two conditional exceptions are described (battery failure, delivery failure), and one cross-cutting execution strategy is mentioned (parallel multi-robot assignment). The two "examples of goods" (sterile equipment, clean linens) are **not** new intentions — they're just domain instances of "resource," "storage" and "specified location" already covered by the generic Collect/Deliver cycle (sterile facility ≈ storage, use destination ≈ specified location; laundry ≈ storage, storage room ≈ specified location). Modeling them separately would duplicate intention, so per the anti-redundancy rule they are **excluded** as distinct nodes.

## Step 2 — Identifying Control-Flow Patterns

| Textual cue | Pattern chosen | Why |
|---|---|---|
| "...the delivery phase begins" **once** collection is retrieved | Sequential (`;`) | Explicit order between collection and delivery |
| "order to be followed is defined by..." then "go to storage places" | Sequential (`;`) | Order must be computed before it can be followed |
| "reaches storage... sends message... waits" | Sequential (`;`) | Explicit chronological chain |
| "**If** the battery... runs low... the robot goes back... and assigns the mission to another robot" | FALLBACK | Explicit IF-condition introducing an alternative to normal collection |
| "**In case of** failure to return the resource to a checkpoint, an alert... and report..." | FALLBACK | Explicit failure condition introducing an alternative to normal delivery |
| "alert must be triggered **and** the report sent" | Parallel (`#`) | Both required, but no order is stated — parallel is the correct default (not sequential, since sequential requires an explicit order) |
| "multiple robots can be assigned to **parallel** collect-deliver tasks" | Drives the task's **Number of Robots** range, not a new goal node | This is an execution/assignment strategy over existing tasks, not a new intention |

## Step 3 — Goal Type Classification Logic

- **Achieve** was used wherever a concrete resulting world-state is described (resources retrieved, robot at recharge station, resources delivered) — the dominant pattern in this mission.
- **Query** was used once, for computing the storage visit order — this goal only produces *information*, it doesn't itself change the world.
- **Perform** was used once, for the alert/report pair — fulfillment there depends only on whether the two actions were executed, not on verifying any further persisting condition, matching the "Enter the Car" pattern rather than a target-condition pattern.

## Step 4 — Zero-Robot and Redundancy Check

Every leaf task in the model below is explicitly tied to "the robot" in the text — none are system-only/zero-robot actions, so nothing was pruned on that basis. Each goal maps to one distinct intention (collect vs. deliver vs. two distinct failure-handling behaviors vs. ordering computation) with no duplicates.

## Logical Relationships

- **G1 -> G2, G7 [AND] (sequential)**
  - **Justification**: Both collection and delivery are mandatory; the text states delivery begins only "once retrieved," establishing explicit order.

- **G2 -> G3, G6 [AND] FALLBACK(G3, G6)**
  - **Justification**: The 10%-battery threshold is an explicit IF-condition that redirects the robot away from normal collection; FALLBACK children are always AND-related per the rules.

- **G3 -> G4, G5 [AND] (sequential)**
  - **Justification**: The visiting order must be computed before it can be followed, matching the text's own stated order of description.

- **G5 -> AT1, AT2, AT3 [AND] (sequential)**
  - **Justification**: "Once the robot reaches one storage... sends a message... and waits" describes three jointly required, chronologically chained actions.

- **G6 -> AT4, AT5 [AND] (sequential)**
  - **Justification**: "...goes back to the recharging station **and** assigns the mission to another robot" — both required, in that stated order.

- **G7 -> AT6, G8 [AND] FALLBACK(AT6, G8)**
  - **Justification**: "In case of failure to return the resource to a checkpoint" is an explicit failure condition redirecting from normal delivery; FALLBACK children are AND-related.

- **G8 -> AT7, AT8 [AND] (parallel)**
  - **Justification**: Both the alert and report are required, but no order between them is stated, so parallel (not sequential) is correct.

**Note on the two "examples of goods" paragraphs**: sterile equipment and clean linens are domain instantiations of the generic *resource / storage / specified-location* variables already in the model (sterile facility & laundry = storage; use destination & storage room = specified location). They don't introduce new robot behavior, so adding separate goals for them would violate the anti-redundancy rule — they're captured by AT1–AT3 and AT6 simply being instantiated with different location/resource values at runtime.
