# Goal Model: Multi-Robot Resource Collection & Delivery Mission

## 0. Step-by-Step Reasoning

**Step 1 — Identify the top-level intention.**
The description opens with: *"When required, a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location."* This single sentence contains the whole mission's purpose, so it becomes the root goal **G1**. It is an **Achieve** goal because it names a concrete target state (resources at the requesting agent's location) that the robot must bring about through planning and action — it isn't a single primitive action (ruling out Perform) and it isn't about obtaining information (ruling out Query).

**Step 2 — Split into phases.**
The text explicitly separates two phases: *"In the collection phase..."* and *"Once retrieved, the delivery phase begins."* The word "once" signals an explicit precedence: collection must finish before delivery starts. This is a textbook case for the **sequential (`;`)** runtime operator rather than fallback, because there is no condition/failure/threshold triggering an alternative here — both phases are mandatory and complementary, just temporally ordered. Hence **G1 → G2 (Collection); G3 (Delivery)**, **AND** decomposition.

**Step 3 — Decompose the Collection Phase.**
Within collection, the description gives (a) a normal operating procedure (go to storage in a computed order → request → wait for retrieval) and (b) an explicit conditional exception: *"If the battery of the assigned robot runs low (10%) in the collection phase, the robot goes back to the recharging station and assigns the mission to another robot."* This is precisely the pattern the FALLBACK operator is meant to capture: a normal behavior, then an alternative triggered by a threshold condition (an implicit IF). So **G2** fallback-decomposes into **G4 (normal collection)** and **G8 (battery-low handling)**, which per the FALLBACK rule are **AND**-related.

Inside normal collection, three things happen in a strict, explicitly stated order:
1. *"The order to be followed is defined by the estimation of waiting time summed up with the path to be run by the robot"* → the robot must first compute a visiting order. This is a **Query** goal (it produces information — an ordering — not a world-changing action), giving **G5**.
2. *"the robot must go to the storage places"* → travel task.
3. *"the robot sends a message to the storage with the precise specification... and waits until the resources have been retrieved"* → two further sequential tasks (send request; wait).

These four elements only make sense in that order, so **G4**'s runtime is sequential: `G5;AT2;AT3;AT4`.

**Step 4 — Decompose the battery-low (collection) handling.**
*"the robot goes back to the recharging station AND assigns the mission to another robot"* — both actions are mandatory (AND) and the wording implies the robot returns first, then reassigns, so sequential: `AT5;AT6`. This becomes **G8**.

**Step 5 — Decompose the Delivery Phase.**
Symmetrically, delivery has a normal procedure (*"the robot will make as many runs as necessary to take all the resources to the specified location"*) and an explicit threshold exception (*"If the battery... runs low (30%) in the delivery phase..."*) → **FALLBACK(G6, G9)** under **G3**, AND-related.

**Step 6 — Decompose the battery-low (delivery) handling further.**
This branch itself contains a nested conditional: the normal reaction is *"return the resource to a checkpoint and assign the remaining task to another robot"*, but *"In case of failure to return the resource to a checkpoint, the report must be sent to the sector manager."* "In case of failure" is an explicit failure condition on the first alternative, which is exactly what FALLBACK models. So **G9 → FALLBACK(G10, G11)**, AND-related, where **G11** (reporting) is a **Perform** goal (a single reportable action, success = message sent, no further state is being pursued).

**Step 7 — Check for zero-robot nodes.**
Every leaf task identified (estimating order, travelling, messaging, waiting, returning to recharge, reassigning, transporting, returning to checkpoint, reassigning remaining task, reporting) is explicitly carried out by "the robot" in the text — none is performed by zero robots, so none were discarded.

**Step 8 — Check for OR-decompositions and parallel runtime.**
No part of the normative process text offers true interchangeable alternatives (the "or" style decomposition), so every decomposition in the model turned out to be **AND**. The only parallelism mentioned — *"multiple robots can be assigned to parallel collect-deliver tasks"* — applies **across separate instantiations of the whole G1 mission** (one instantiation per required item/storage), not between two distinct children of one goal. Because the parallel operator's syntax requires two *different* expressions (`exp1#exp2`, `exp1 ≠ exp2`), it cannot formally express "N copies of the same goal," so this is documented as an execution-level note (Section 6) rather than forced into the tree.

**Step 9 — Assign IDs by depth-first traversal.**
Walking the tree root-to-leaf, left-to-right, numbering goals (`G`) and tasks (`AT`) independently as each is first encountered, produces the IDs used in Sections 1–2 below.

## 4. Logical Relationships

- **G1 → G2, G3 [AND] (sequential: `G2;G3`)**
  - **Justification**: Collection and delivery are both mandatory (AND), and the description explicitly orders them — *"Once retrieved, the delivery phase begins"* — so delivery cannot start before collection finishes.

- **G2 → G4, G8 [AND] FALLBACK(G4, G8)**
  - **Justification**: G4 is the normal collection path; G8 is an alternative explicitly triggered by a battery threshold ("if the battery... runs low (10%)"). This matches the FALLBACK pattern exactly (normal behavior + condition-triggered alternative), and FALLBACK branches are always AND-related.

- **G4 → G5, AT2, AT3, AT4 [AND] (sequential: `G5;AT2;AT3;AT4`)**
  - **Justification**: The description presents these as one continuous, obligatory chain: compute the order → travel → request → wait for retrieval. No step can be skipped or reordered, so AND + strict sequence.

- **G5 → AT1 [AND]**
  - **Justification**: The query goal is realized by the single computation/estimation task; trivial AND linking a goal to its one operational task.

- **G8 → AT5, AT6 [AND] (sequential: `AT5;AT6`)**
  - **Justification**: *"the robot goes back to the recharging station and assigns the mission to another robot"* — both actions are required (AND), stated in that order (return, then reassign).

- **G3 → G6, G9 [AND] FALLBACK(G6, G9)**
  - **Justification**: G6 is normal delivery; G9 is the alternative explicitly triggered by the 30% battery threshold during delivery — same FALLBACK pattern as G2, AND-related branches.

- **G6 → AT7 [AND]**
  - **Justification**: Normal delivery is fully realized by one repeatable transport task ("as many runs as necessary"); trivial AND linking goal to its sole task.

- **G9 → G10, G11 [AND] FALLBACK(G10, G11)**
  - **Justification**: *"In case of failure to return the resource to a checkpoint, the report must be sent to the sector manager"* is an explicit failure condition on G10, the textbook trigger for a (nested) FALLBACK; its branches are AND-related.

- **G10 → AT8, AT9 [AND] (sequential: `AT8;AT9`)**
  - **Justification**: *"must return the resource to a checkpoint and assign the remaining task to another robot, which will know where the resource is positioned"* — both actions required, and the handoff only makes sense once the resource is actually at the checkpoint, so return precedes reassignment.

- **G11 → AT10 [AND]**
  - **Justification**: The reporting goal is realized by the single reporting action; trivial AND linking goal to its sole task.

## 5. Note on Multi-Robot Parallel Execution

The closing sentence — *"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks to reduce the time to finish the mission"* — describes concurrency **across separate instantiations of the entire G1 tree** (one instantiation per required item/storage, each run by its own robot), not a parallel (`#`) relation between two distinct children of a single goal.

It is intentionally **not** encoded inside the tree above because:
1. The parallel operator's syntax requires two *different* expressions (`exp1#exp2`, with `exp1 ≠ exp2`); here the "two sides" would be identical copies of G1 parameterized by a different item/storage, which the notation cannot express without fabricating artificial distinctions not present in the text.
2. The goal model as specified describes the mission of **a robot** (singular, as the text consistently says); the multi-robot scaling rule is a deployment/orchestration policy layered on top of N independent instances of this same tree, rather than a structural branch within one instance.

If desired, this can be represented in an extended model as a system-level coordinator goal (e.g., "G0: Fulfill Multi-Item Resource Logistics") that AND-decomposes into *N* parallel instances of G1 — but that would require the mission description to specify how many items/storages are involved, which it does not.
