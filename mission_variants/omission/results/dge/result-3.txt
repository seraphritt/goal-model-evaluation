# Multi-Robot Collect-and-Deliver Mission — Goal Model Analysis

## Step-by-Step Reasoning

**Step 1 — Identify the overall mission and its phases.**
The description names two explicit phases ("In the collection phase..." / "Once retrieved, the delivery phase begins"), with the second explicitly beginning only after the first completes. This is a stated order with no triggering condition/exception attached to the ordering itself — so it's **sequential (`;`)**, not a fallback. This gives the root goal **G1** and two AND-required children, **G2** (collection) and **G3** (delivery).

**Step 2 — Decompose the collection phase.**
Inside collection, three things happen in a stated order: (a) an implicit ordering decision ("the order... is defined by the estimation of waiting time summed with the path"), (b) traveling to storages, (c) requesting resources, (d) waiting for retrieval. None of these sub-steps are condition-triggered alternatives to one another — they're just the normal procedure — so they are chained with **sequential (`;`)**, all under **AND** (all are jointly necessary). The ordering estimation is pure information-gathering with no physical action, so it becomes a **Query** goal (**G2.1.1**) rather than a task.

**Step 3 — Identify the first fallback.**
"If the battery... runs low (10%) in the collection phase, the robot goes back to the recharging station and assigns the mission to another robot." This is a textbook **FALLBACK**: an explicit condition (battery ≤ 10%) triggers an alternative behavior that replaces the normal collection procedure. Per the rules, FALLBACK branches are always **AND**-related. This produces **G2 = FALLBACK(G2.1, G2.2)**.

**Step 4 — Decompose the delivery phase.**
Delivery's "normal" behavior is a single operational step repeated as needed ("make as many runs as necessary") — this is one task (**AT6**), not a compound goal, so no intermediate goal node is created for it (a decomposition needs ≥2 children; one action stays a direct task).

**Step 5 — Identify the nested fallback in delivery.**
"If the battery... runs low (30%) in the delivery phase, the robot must return the resource to a checkpoint and assign the remaining task..." → second explicit condition-triggered alternative → **FALLBACK(AT6, G3.2)**.
Inside that recovery behavior there is a *second*, nested condition: "In case of **failure** to return the resource to a checkpoint, the report must be sent to the sector manager." This is another fallback, nested inside the first: **G3.2 = FALLBACK(G3.2.1, AT9)**.

**Step 6 — Check for zero-robot nodes.**
Every node retained is traceable to an action the robot itself performs (travel, message-send, wait, return, reassign, report). No goal/task was created for the storage system, the requesting agent, or the sector manager themselves — they are only destinations/recipients, consistent with the "zero-robot" exclusion rule.

**Step 7 — Check for OR-decomposition.**
No part of the text expresses true alternatives ("either do X or do Y, either is sufficient"). Every relationship found is either a joint requirement (AND) or a condition-triggered substitution (FALLBACK, which is itself AND-typed). Hence **no OR-decomposition appears** in this model — this is a deliberate, justified absence, not an oversight.

**Step 8 — Check for parallel (`#`) execution.**
Within a single robot's own goal tree, no two sibling sub-goals can be pursued concurrently (collection must precede delivery; each collection step depends on the previous). The *only* parallelism described — "multiple robots can be assigned to parallel collect-deliver tasks" when multiple storages are involved — is a **mission-replication** phenomenon (several full instances of the same tree running at once), not a parallel split of sibling sub-goals inside one instance. Since `Number of Robots` is explicitly the task attribute designed to carry exactly this kind of cardinality information ("a value derived from or constrained by the maximum number of robots that can perform the task"), this is captured there instead, via a `[1, n]` range on the core collect/deliver tasks, rather than by inventing an artificial `#` at goal level.

**Step 9 — Classify goal types.**
Every surviving goal has an explicit, checkable target state (resource retrieved, robot recharged-and-reassigned, resources delivered, resource checkpointed-and-reassigned) — so **Achieve** fits all of them except the storage-visit-order decision, which is pure information retrieval with no physical action → **Query**. No goal fit **Perform** (an action attempted "for its own sake" with no state to verify) — the mission description is state-driven throughout, so Perform was not forced in artificially.

## Logical Relationships

- **G1 -> G2, G3 [AND] (sequential)**
  - **Justification**: The description states delivery begins only "once retrieved" — an explicit, non-conditional process order. Both phases are mandatory for the request to be fulfilled, so AND applies; the explicit (but non-exceptional) order makes it sequential rather than fallback.

- **G2 -> G2.1, G2.2 [AND] [FALLBACK(G2.1, G2.2)]**
  - **Justification**: The 10%-battery clause is an explicit condition that substitutes an alternative behavior for the normal procedure — the defining pattern of FALLBACK, which is always AND-related.

- **G2.1 -> G2.1.1, AT1, AT2, AT3 [AND] (sequential)**
  - **Justification**: Determining order, traveling, requesting, and waiting are all explicitly necessary and explicitly ordered steps of normal collection, with no condition triggering any of them as a substitute for another.

- **G2.2 -> AT4, AT5 [AND] (sequential)**
  - **Justification**: "Goes back to the recharging station **and** assigns the mission to another robot" names two jointly required, ordered recovery actions.

- **G3 -> AT6, G3.2 [AND] [FALLBACK(AT6, G3.2)]**
  - **Justification**: The 30%-battery clause explicitly substitutes checkpoint-and-reassign behavior for the normal delivery runs — FALLBACK, AND-related.

- **G3.2 -> G3.2.1, AT9 [AND] [FALLBACK(G3.2.1, AT9)]**
  - **Justification**: "In case of failure to return the resource to a checkpoint" is a second, explicit condition nested inside the first, substituting a failure report for the checkpoint-and-reassign attempt — a nested FALLBACK, AND-related.

- **G3.2.1 -> AT7, AT8 [AND] (sequential)**
  - **Justification**: "Return the resource to a checkpoint **and** assign the remaining task... which will know where the resource is positioned" names two jointly required, ordered actions.
