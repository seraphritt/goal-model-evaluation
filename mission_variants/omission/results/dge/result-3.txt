# Goal Model Analysis — Multi-Robot Resource Collection & Delivery Mission

## STEP-BY-STEP REASONING

**Step 1 — Identify the macro-structure of the mission.**
The description opens with the overarching intent: *"a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location."* This gives two macro-phases explicitly named in the text: **Collection** and **Delivery**. The text itself states the order: *"Once retrieved, the delivery phase begins"* — this is an explicit statement of order (not a condition/exception), so per the rules this is **sequential (`;`)**, not FALLBACK. Both phases are mandatory, so the relation is **AND**.

**Step 2 — Identify conditional/exceptional behaviors (FALLBACK candidates).**
Two IF-like conditions appear:
- *"If the battery... runs low (10%) in the collection phase, the robot goes back to the recharging station and assigns the mission to another robot."* → explicit threshold-triggered alternative behavior during collection → **FALLBACK**.
- *"In case of failure to return the resource to a checkpoint, an alert must be triggered..."* → explicit failure-triggered alternative behavior during delivery → **FALLBACK**.

Both match the rule's own example ("normal behavior... alternative behavior triggered by a condition, exception, failure, threshold") perfectly. By the formal rule, each FALLBACK pair is connected by **AND**, since both branches jointly guarantee mission robustness — they are not true alternatives (OR), because the "alternative" branch does not fulfill the *same* intention as the first branch (one collects resources, the other recovers from a failure); OR would wrongly imply they're interchangeable means to the same end.

**Step 3 — Identify explicit sequencing inside each phase.**
- Collection: *"the robot must go to the storage... Once the robot reaches one storage and it is time to request the resource, the robot sends a message..."* → explicit order (reach storage **then** request) → sequential.
- Ordering rule for storages: *"The order to be followed is defined by the estimation of waiting time summed up with the path..."* → this is a computation that must happen before travelling, but it is not described as a separate intentional goal in itself — it feeds directly into the physical act of visiting locations. I treat it as an internal task under the "Navigate" goal rather than inventing a standalone Query goal, to respect the **minimum-two-children** rule without forcing an artificial split not supported by the text (see Step 6 reflection below).

**Step 4 — The "no OR" reflection.**
I actively searched the text for any genuine alternative construct (where fulfilling *one* child makes the *other* irrelevant/unnecessary). None exists — every decomposition in this mission is either a mandatory joint requirement (AND) or a FALLBACK pair (which is AND by rule). Therefore, **no OR decomposition appears anywhere in this model**. I flag this explicitly rather than silently omitting it, since the rules ask every decomposition choice to be justified.

**Step 5 — The multi-robot parallel clause.**
*"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks..."* uses "can" → matches the **parallel operator's own definition** ("possibility, not obligation"). However, the parallel operator is strictly binary and requires `exp1 ≠ exp2`. What this sentence actually describes is **N independent instantiations of the very same goal tree (G0)** running concurrently for different storages/items — i.e., `G0 # G0`, which the rule explicitly forbids (exp1 cannot equal exp2). Creating a fabricated "coordinator" goal would also violate the **zero-robot rule**, since no robot is described as performing the act of "assigning robots" — that is dispatcher/system-level behavior, not a robot action. 
**Resolution:** this clause is not modeled as a new goal/operator node; instead, it is documented as a *system-level scalability property* of G0 (multiple concurrent instances, each executed by a different robot), and is reflected in the **Number of Robots** property only where a single task genuinely implies more than one robot (see AT6).

**Step 6 — Goal type classification reflection.**
I deliberately tested all three types (Perform/Query/Achieve) against each node:
- Nodes describing a *state to be reached through planning across multiple steps* (robot at the right places, resources retrieved, resources delivered) → **Achieve**, since each has a clear target condition.
- Nodes describing a *mandated reactive action sequence triggered by a condition, with no further elaborated success state* (battery handling, failure handling) → **Perform**, matching the "Enter the Car" pattern (execute the action; success = action carried out).
- **Query** was seriously considered for the storage-ordering step (it is, in essence, an information-estimation activity). However, in this mission the estimation is never an end in itself — it only exists to feed the physical navigation goal, and elevating it to a stand-alone Query goal would force a single-child decomposition (violating the minimum-two rule) or an artificial split (e.g., separating "estimate waiting time" from "estimate path") that the text does not support. I therefore **did not use Query** in this model and explain this explicitly rather than forcing an unjustified node — a conscious modeling decision, not an oversight.

**Step 7 — Locations and robot counts.**
Every location used (`storage`, `recharging station`, `specified location`, `checkpoint`) is taken verbatim from the text — none invented. Every task is performed by "the robot" (singular) in the text, so Number of Robots = 1 almost everywhere. The one exception is **AT6 (Reassign Mission to Another Robot)**, where the text itself introduces a second robot ("assigns the mission to **another** robot") — justifying a range **[1,2]**.

**Step 8 — Domain examples (sterile equipment, linens).**
These are not additional process steps; they are *instantiations* of the abstract variables already in the model: `storage` → "sterile facilities"/"laundry"; `specified location` → "use destinations"/"storage rooms close to use." They validate the model's generality rather than requiring new nodes, so I did not add goals/tasks for them — adding "Transport Linens" as a separate goal would duplicate the intention already captured by G0–G8 (violating the no-redundancy rule).

**Step 9 — Tree validation.**
Every Goal node has exactly two children (AND, minimum satisfied); every leaf goal (one whose children are tasks, not sub-goals) receives runtime `"-"`; every robot-performing node is attributed to "the robot," so the zero-robot rule is respected throughout.

## LOGICAL RELATIONSHIPS

- **G0 -> G1, G6 [AND] (sequential)**
  - **Justification**: Collection and delivery are both mandatory and the text explicitly orders them ("Once retrieved, the delivery phase begins") — no condition/exception is involved, so it is sequential, not fallback.

- **G1 -> G2, G5 [AND] FALLBACK(G2, G5)**
  - **Justification**: Battery dropping to 10% during collection is an explicit threshold/condition triggering an alternative behavior (per the mandatory-fallback rule); by the FALLBACK-AND rule, both branches are AND-connected since each is required to guarantee robust mission completion.

- **G2 -> G3, G4 [AND] (sequential)**
  - **Justification**: The robot must physically reach a storage before it can request resources there ("Once the robot reaches one storage... the robot sends a message"), an explicit order statement.

- **G3 -> AT1, AT2 [AND]**
  - **Justification**: Computing the visiting order is a precondition for travelling in that order; neither action alone fulfills the goal of "being at the right places in the right order."

- **G4 -> AT3, AT4 [AND]**
  - **Justification**: Sending the request and waiting for retrieval are both necessary; the text chains them with "and waits until," signaling both are required.

- **G5 -> AT5, AT6 [AND]**
  - **Justification**: Returning to recharge and reassigning the mission are both explicitly mandated by the same conditional clause ("the robot goes back... **and** assigns the mission...").

- **G6 -> G7, G8 [AND] FALLBACK(G7, G8)**
  - **Justification**: "In case of failure to return the resource to a checkpoint" is an explicit condition triggering the alert/report behavior as an alternative to normal delivery completion; FALLBACK is mandatory, and AND connects both branches per the rule.

- **G7 -> AT7, AT8 [AND]**
  - **Justification**: Transporting resources and unloading them at the destination are both necessary to complete a delivery run; neither alone satisfies "take the resources to the specified location."

- **G8 -> AT9, AT10 [AND]**
  - **Justification**: The text mandates both actions jointly upon failure ("an alert must be triggered **and** the report sent").

---

### Final reflection note
No **OR** decomposition was used anywhere in this model, because the description never presents two children where fulfilling just one renders the other unnecessary for the *same* intention — every pairing is either a joint requirement or a formally-AND-connected FALLBACK. The system-level "multiple robots in parallel" capability was deliberately **not** turned into a parallel-operator node (since that would require a goal to run in parallel with itself, which the formalism explicitly disallows) nor into a new coordinator goal (since no robot is described as performing that coordination, which would violate the zero-robot rule) — instead it is documented as a scalability property of the whole G0 tree, instantiated multiple times concurrently across different robots/storages.
