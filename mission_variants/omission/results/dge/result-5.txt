# Mission Goal Model — Multi-Robot Collect & Deliver Mission

## Step-by-Step Reasoning

**Step 1 — Identify the actors and the overall intention.**
The description centers on a single robot (at a time) that is "assigned" a mission: collect requested resources from storage and deliver them to a requesting agent at a specified location. This is the root intentional objective of the whole tree → **G1**.

**Step 2 — Identify the macro-phases and their temporal relationship.**
The text explicitly separates two phases and states an order between them: *"Once retrieved, the delivery phase begins."* The word "once" is an explicit temporal marker, so the relationship between the Collection Phase and the Delivery Phase is modeled as **sequential (`;`)**, not parallel — the mission cannot deliver before it has collected. Both phases are mandatory for mission success → **AND**.

**Step 3 — Identify explicit condition-triggered alternatives (FALLBACK candidates).**
Two sentences explicitly describe a *normal* behavior followed by an *exception triggered by a condition* (battery threshold):
- "If the battery... runs low (10%) in the collection phase, the robot goes back to the recharging station and assigns the mission to another robot."
- "If the battery... runs low (30%) in the delivery phase, the robot must return the resource to a checkpoint and assign the remaining task to another robot."

Both satisfy the strict criterion for FALLBACK (explicit IF/condition, primary vs. alternative path). Per the given rule, FALLBACK branches are always AND-connected (the robot always tries exp1 first; exp2 is only pursued if exp1 fails — but structurally both are part of the same AND-whole).

A third, nested condition appears: *"In case of failure to return the resource to a checkpoint, the report must be sent to the sector manager."* This is a FALLBACK nested **inside** the delivery-battery-contingency branch, so it is modeled as its own goal with its own FALLBACK, consistent with the instruction that nested fallbacks must be represented as nested FALLBACK structures.

**Step 4 — Decompose each phase into its atomic, explicitly-stated operational steps (Tasks).**
- Collection (normal path): go to storage → send request message → wait until retrieved. Three distinct, explicitly sequenced actions ("once... reaches... and it is time... waits until") → sequential AND tasks.
- Delivery (normal path): the robot "makes as many runs as necessary to take all resources to the specified location." A run is decomposed into its two necessary sub-actions: travel to the location, then deposit the resources — sequential AND tasks (deposit cannot precede arrival).
- Collection battery fallback: return to recharging station + assign mission to another robot. No explicit temporal marker ("and" only, no "once/then/after") joins these two actions, and they are logically independent (communicating a hand-off does not require the robot to have physically arrived at the station first) → modeled as **parallel (`#`)**.
- Delivery battery fallback: return resource to checkpoint + assign remaining task to another robot "which will know where the resource is positioned." Here there **is** a logical dependency — the new robot must be told the resource's final position, so the checkpoint placement logically precedes/produces the information to transmit → modeled as **sequential (`;`)**, unlike the collection-fallback case.

**Step 5 — Exclude non-goal content.**
- The listed examples ("sterile medical equipment," "clean linens") are explicitly introduced as *"Examples of goods/equipment"* — they do not add a new robot action; they would duplicate the already-generic "resource" concept. Per the no-redundancy/no-duplicate-intention rule, they are **excluded** from the formal model.
- Every leaf in the tree corresponds to an explicit robot-performed action (no "zero-robot" nodes were introduced).

**Step 6 — Handle the multi-robot parallel note.**
*"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks..."* This is a possibility (not obligation) statement about **concurrently running several whole instances of the G1 tree** (one per required resource/storage), each potentially assigned to a different robot — it is not a new action performed within a single mission instance, and forcing it into the single-instance tree would violate the "minimum two children" rule artificially. I therefore model one canonical mission tree (G1→...) and document the multi-instance parallelism separately (see note after the tables), using the `#` operator at the *inter-mission* level: `Mission_item1 # Mission_item2 # ...`.

**Step 7 — Classify goal types.**
Every goal in this mission is defined by a *world state to be reached* (resources retrieved, robot relocated, mission reassigned, resource secured, report sent) rather than "try the action regardless of outcome" (Perform) or "only obtain information" (Query). Hence every goal is an **Achieve Goal** with an explicit target condition — justified individually in the table below.

**Step 8 — Assign IDs by depth-first traversal** (goals and tasks numbered independently, same walk order), producing G1–G8 and AT1–AT10 as shown below.

## Logical Relationships

- **G1 -> G2, G5 [AND] (sequential)**
  - **Justification**: "Once retrieved, the delivery phase begins" explicitly orders collection before delivery; both are required for mission success, so AND; the explicit temporal marker rules out parallel and rules out treating them as alternatives (OR).

- **G2 -> G3, G4 [AND] FALLBACK(G3, G4)**
  - **Justification**: The 10%-battery condition is an explicit IF-triggered alternative to the normal collection flow, which the rules require to be modeled as FALLBACK; FALLBACK siblings are always AND-related.

- **G3 -> AT1, AT2, AT3 [AND] (sequential)**
  - **Justification**: The description gives a strict temporal chain (arrive → request → wait), each step a precondition for the next; all three are mandatory.

- **G4 -> AT4, AT5 [AND] (parallel)**
  - **Justification**: Both actions are mandatory (AND), but the text uses only "and" (no "then/once/after") and the actions are logically independent — the hand-off message does not require physical arrival at the station — so parallel execution is a legitimate reading, not an obligation to sequence them.

- **G5 -> G6, G7 [AND] FALLBACK(G6, G7)**
  - **Justification**: The 30%-battery condition is an explicit IF-triggered alternative to normal delivery — FALLBACK obligatory; AND per the fallback rule.

- **G6 -> AT6, AT7 [AND] (sequential)**
  - **Justification**: Depositing resources is only possible after arriving at the specified location — strict dependency.

- **G7 -> G8, AT10 [AND] (sequential)**
  - **Justification**: The new robot must "know where the resource is positioned," which requires the checkpoint-securing attempt (successful or not) to be resolved before that position/outcome can be communicated.

- **G8 -> AT8, AT9 [AND] FALLBACK(AT8, AT9)**
  - **Justification**: "In case of failure to return the resource to a checkpoint, the report must be sent" is an explicit condition/exception pattern → FALLBACK; AND per the fallback rule.

## Note on Multi-Robot Parallel Execution (not a tree node)

The sentence *"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks to reduce the time to finish the mission"* describes **optional concurrency between whole instances of G1**, not a new action inside a single mission's tree (forcing it in would create an artificial single-child node, violating the minimum-two-children decomposition rule). The correct reading is:

`Mission(resource₁) # Mission(resource₂) # ... # Mission(resourceₙ)`

where each `Mission(resourceᵢ)` is a full instantiation of the **G1** tree above (its own G2…G8 and AT1…AT10), each potentially assigned to a different robot, and the `#` (parallel, possibility-not-obligation) operator correctly captures that these independent collect-deliver missions *may*, but need not, run concurrently.

---

**Excluded by design**: the two "examples of goods/equipment" (sterile medical equipment, clean linens) were intentionally left out of the formal model — they are explicitly flagged as illustrative examples of the generic "resource" concept already covered by G1–G8, and including them as separate goals would duplicate the same underlying intention, which the modeling rules explicitly forbid.
