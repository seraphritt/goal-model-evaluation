# Multi-Robot Goal Model — Collect & Deliver Mission

## Step-by-step reasoning

**1. Identify the top-level intention.**
The description centers on one mission: *a robot collects requested resources and delivers them to a requesting agent at a specified location.* This is the root goal (**G1**). Its fulfillment strictly requires two complementary, non-interchangeable phases — "collection" and "delivery" — so the decomposition is **AND**, not OR (no alternative is offered; both are mandatory). The text explicitly states "*Once retrieved, the delivery phase begins*," which is an explicit ordering of two steps that **both occur** (not a conditional alternative) → this is **sequential (`;`)**, not FALLBACK, because FALLBACK is reserved for a normal behavior vs. a conditional/exceptional alternative, while sequential covers two mandatory steps performed in a stated order.

**2. Distinguishing FALLBACK from sequential — the three conditional clauses.**
I scanned the text for explicit condition/threshold/failure triggers, since the instructions require FALLBACK *only* when an alternative is explicitly triggered by a condition:
- "If the battery... runs low (10%) in the collection phase..." → normal collection vs. battery contingency → **FALLBACK**.
- "If the battery... runs low (30%) in the delivery phase..." → normal delivery vs. battery contingency → **FALLBACK**.
- "In case of failure to return the resource to a checkpoint..." → attempt to return vs. reporting on failure → **FALLBACK** (nested inside the delivery-battery contingency).

All other orderings in the text ("reaches storage → sends message → waits," "returns to station → reassigns mission," "secures resource → reassigns task") are **not** framed by a condition/failure — they are plain mandatory multi-step procedures, so they are modeled as **sequential**, not FALLBACK. Per the spec, every FALLBACK(exp1, exp2) pair is connected by **AND**, since both branches are part of one complete contingency-handling behavior (not two interchangeable alternatives, which would be OR).

**3. No OR decomposition anywhere.**
I looked for explicit alternative-fulfillment language ("or," "either/any of") describing substitutable ways to satisfy a goal. None exists in the description — every decomposition found is a conjunction of mandatory sub-goals/tasks (even the FALLBACK pairs, which are AND by definition). Hence the entire tree uses **AND** relations only.

**4. Isolating the Query goal.**
"*The order to be followed is defined by the estimation of waiting time summed up with the path to be run*" is pure information-gathering — the robot computes/obtains a ranking, it does not change the world by doing so. This matches the **Query** goal type exactly (G4), with QueriedProperty = the waiting-time + path estimates per storage.

**5. Achieve vs. Perform for "waiting until retrieved."**
"*...waits until the resources have been retrieved*" denotes reaching a state (resources retrieved) rather than executing a discrete action or merely querying data, so it is modeled as an **Achieve** goal (G6) rather than a task or Perform goal — consistent with the Achieve definition ("target condition... agent plans and acts... to make it true").

**6. Avoiding redundancy — the multi-robot parallel clause.**
"*When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks...*" describes multiple **instances** of the same mission (G1) running concurrently — it is the same underlying intention, so duplicating G1 as a sibling goal would violate the non-redundancy rule. Instead, I capture this as a **Number-of-Robots range on AT1** ("Go to Storage"): `[1, n]`, where `n` is the number of distinct storages/items requested. When `n > 1`, each of the `n` robots independently executes the rest of its own subtree (AT2 onward) in parallel with the others — this is a mission-orchestration property, not a new branch in a single robot's tree.

**7. Zero-robot check.**
Every leaf task is explicitly tied to "the robot" in the text (travels, sends messages, returns, reports) — no task/goal is performed by zero robots, so nothing was excluded on that basis. The order-estimation goal (G4) is treated as performed by the assigned robot's own onboard planning, not an external system, so it is retained.

## Logical Relationships

- **G1 -> G2, G8 [AND](sequential)**
  - **Justification**: "Once retrieved, the delivery phase begins" explicitly places delivery after collection; both phases are mandatory, so AND; the order is stated, not conditional, so sequential rather than FALLBACK.

- **G2 -> G3, G7 [AND][FALLBACK(G3,G7)]**
  - **Justification**: Normal collection (G3) is the default; the 10%-battery clause is an explicit condition triggering an alternative behavior (G7) — the defining case for FALLBACK, whose branches are always AND-connected.

- **G3 -> G4, G5 [AND](sequential)**
  - **Justification**: The visiting order must be computed before storages can be visited in that order ("the order to be followed is defined by..."); both steps are required and strictly ordered, with no failure/condition branching.

- **G5 -> AT1, AT2, G6 [AND](sequential)**
  - **Justification**: Explicit chronological chain in the text — reach storage, then send request, then wait for retrieval; all three mandatory.

- **G7 -> AT3, AT4 [AND](sequential)**
  - **Justification**: "The robot goes back to the recharging station and assigns the mission to another robot" — both actions required, stated in this order.

- **G8 -> AT5, G9 [AND][FALLBACK(AT5,G9)]**
  - **Justification**: Normal delivery runs (AT5) are the default; the 30%-battery clause is an explicit condition triggering an alternative (G9) — FALLBACK, AND-connected.

- **G9 -> G10, AT8 [AND](sequential)**
  - **Justification**: The next robot "will know where the resource is positioned," which requires the resource to already be secured at the checkpoint — securing (G10) must precede reassignment (AT8).

- **G10 -> AT6, AT7 [AND][FALLBACK(AT6,AT7)]**
  - **Justification**: "In case of failure to return the resource to a checkpoint, the report must be sent to the sector manager" is an explicit failure-triggered alternative — FALLBACK, AND-connected.

**Cross-cutting note (parallel multi-robot execution):** The clause "multiple robots can be assigned to parallel collect-deliver tasks" is not modeled as a duplicate sibling of G1 (that would represent the same intention twice, violating the non-redundancy rule). Instead it is captured as the `[1, n]` robot range on **AT1**: when a request spans `n` distinct storages, up to `n` robots each instantiate and run the complete G1 subtree independently and in parallel — one robot/storage per instance — while each individual instance internally keeps the sequential/FALLBACK structure described above.
