# Mission Analysis & Goal Model — Robot Resource Collection & Delivery

## 1. Step-by-Step Reasoning

**Step 1 — Identify the top-level intention.**
The mission text opens with a single overarching purpose: *"a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location."* This is a single, non-redundant intention → one root goal (**G1**). It names two concrete locations explicitly: *storage* and *the requesting agent's specified location*. These are the only two "places" I will ever cite for Location attributes, plus two more named later (*recharging station*, *checkpoint*).

**Step 2 — Split into phases.**
The text explicitly separates "the collection phase" from "the delivery phase," and states delivery begins "once retrieved" — an explicit temporal order, not a conditional/failure-triggered alternative. That rules out FALLBACK and calls for **Sequential (`;`)** execution between Collection and Delivery.

**Step 3 — Decompose the Collection phase.**
Two explicit sub-steps appear in order:
(a) an ordering/estimation step ("the order ... is defined by the estimation of waiting time summed up with the path"), and
(b) the actual travel + request/retrieve cycle.
Since (a) is only about *obtaining knowledge* (an estimate) and does not itself change the world, it fits the **Query Goal** definition precisely (analogous to the "Fetch Occupied Rooms" example). (b) requires reaching a state (resource retrieved) through planning/action, so it is an **Achieve Goal**. Order between them is implied logically ("the order to be followed is defined by...") → **Sequential**.

The travel+request cycle itself splits into "go to storage" (task) and "request & wait for retrieval" (an achieve goal, since it specifies a target condition: *"waits until the resources have been retrieved"*), which in turn splits into two sequential tasks: send request message, then collect the retrieved resource.

**Step 4 — Identify the battery contingency.**
*"If the battery of the assigned robot runs low (10%) in the collection phase, the robot goes back to the recharging station and assigns the mission to another robot."* This is a textbook **FALLBACK** trigger: an explicit threshold condition ("10%") causes an alternative behavior to replace the normal one. Per the rules, FALLBACK children are always AND-connected. The fallback branch itself has two sequential actions (return to recharge → reassign), both performed by the *same* robot that hit low battery (so Number of Robots = 1, not parallel).

**Step 5 — Decompose the Delivery phase.**
*"the robot will make as many runs as necessary to take all the resources"* → a repeated load+transport cycle, modeled as one Achieve Goal with two sequential tasks (load, transport) representing one run (repetition is a runtime/looping property, not a separate structural branch, to avoid inventing nodes not grounded in the text).

**Step 6 — Identify the failure-reporting contingency.**
*"In case of failure to return the resource to a checkpoint, an alert must be triggered and the report sent to the sector manager."* Again an explicit IF-condition ("in case of failure") → **FALLBACK** against the normal delivery, with two sequential Perform-style actions (trigger alert → send report). I classify this goal as **Perform** rather than **Achieve**: its two actions ("trigger," "send") succeed or fail purely based on whether the action was executed, not on the persistence of a world-state afterward — this matches the Perform Goal definition exactly.

**Step 7 — Handle the parallel multi-robot clause.**
*"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks..."* This describes **parallel execution of the same intention across different storages/robots**, not two distinct goal expressions. Since the Parallel operator (`#`) syntactically requires two *different* expressions, and duplicating the whole subtree per storage would violate the "avoid redundancy — one goal per intention" rule, I represent this instead through the **Number of Robots** attribute (a range `[1, n]`, where *n* = number of storages/items requiring separate visits) on every task belonging to the *normal* collect-deliver cycle. Tasks that only occur in exceptional/contingency branches (battery fallback, failure reporting) keep **Number of Robots = 1**, since those are always handled by the single robot experiencing that specific contingency, never parallelized.

**Step 8 — Zero-robot check.** Every node below is executed by at least one robot (the assigned robot or its replacement) — nothing was pruned for this reason, but it confirms, e.g., that "estimate visit order" belongs in the model (the robot itself computes it) rather than being an external planner's job.

## 6. Logical Relationships

- **G1 -> G2, G8 [AND](sequential)**
  - **Justification**: Collection and delivery are both mandatory, non-alternative parts of the mission, and the text explicitly orders them: delivery begins "once retrieved."

- **G2 -> G3, G7 [AND][FALLBACK(G3, G7)]**
  - **Justification**: Normal collection (G3) is pursued first; the explicit "if battery runs low (10%)" condition triggers the alternative contingency (G7) only when G3 cannot continue — the textbook FALLBACK case, whose children are AND-connected per the formalism.

- **G3 -> G4, G5 [AND](sequential)**
  - **Justification**: The visiting order must be computed (G4) before it can be followed (G5); both are required, in that order.

- **G5 -> AT1, G6 [AND](sequential)**
  - **Justification**: The robot must arrive at a storage (AT1) before it can request/retrieve resources there (G6).

- **G6 -> AT2, AT3 [AND](sequential)**
  - **Justification**: The robot must send the request message (AT2) before it can collect the retrieved resource (AT3) — explicit order ("sends a message... and waits until retrieved").

- **G7 -> AT4, AT5 [AND](sequential)**
  - **Justification**: The robot returns to the recharging station (AT4) and then reassigns the mission (AT5), in that explicit order; both are required to fully resolve the contingency.

- **G8 -> G9, G10 [AND][FALLBACK(G9, G10)]**
  - **Justification**: Normal delivery (G9) is pursued first; the explicit "in case of failure to return the resource to a checkpoint" condition triggers the alert/report alternative (G10) only if G9 fails — another explicit FALLBACK case.

- **G9 -> AT6, AT7 [AND](sequential)**
  - **Justification**: Resources must be loaded (AT6) before they can be transported (AT7); both are required for each delivery run.

- **G10 -> AT8, AT9 [AND](sequential)**
  - **Justification**: The alert must be triggered (AT8) before the report is sent (AT9) — explicit order ("an alert must be triggered and the report sent").

**On the parallel multi-robot clause**: *"multiple robots can be assigned to parallel collect-deliver tasks"* is not represented as a `#` (parallel) relation between two distinct goals, because all parallel instances share the *same* intention (collect-deliver) and the Parallel operator requires two non-identical expressions; duplicating the subtree per storage would also violate the "one goal per intention" rule. Instead, it is captured structurally through the `[1, n]` **Number of Robots** range on every task belonging to the *normal* execution path (AT1, AT2, AT3, AT6, AT7), while every *contingency-only* task (AT4, AT5, AT8, AT9) is fixed at exactly 1 robot, since those always belong to a single robot's individual exception handling and are never parallelized across the fleet.
