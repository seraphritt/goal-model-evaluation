# Goal Model Design — Lab Sample Transport Mission

## Step 1 — Identify the actors and filter out "zero‑robot" actions

Before building the tree, I went through the description sentence by sentence and tagged who performs each action, because the rule *"goals/tasks not performed by any robot must not be on the goal model"* is the first filter.

| Description fragment | Actor | Include in robot goal model? |
|---|---|---|
| "A nurse ... can request a delivery" | Nurse (human) | ❌ trigger only, not a robot action — folded into justification of the first robot task, not modeled as its own node |
| "Each sample ... is identified with a barcode" (before collection) | Nurse/clinical staff (human) | ❌ excluded |
| "The nurse inserts data ... in a track system" | Nurse (human) | ❌ excluded |
| "Samples are transported in secure locked drawers" | Transport robot | ✅ |
| "the sample can be picked by laboratory personnel" | Lab personnel (human) | ❌ excluded as a stand‑alone action |
| "Only authorized personnel **or specific robots** in specific locations ... open the locked drawers" | Robot (explicitly licensed) | ✅ — this is the clearest textual hint that drawer‑opening is a robot capability we must model |
| "The robotic arm scans ... sorts ... loads ... into the entry‑module" | Robotic arm | ✅ |
| "Information about where and when a sample was picked should be logged securely" | System/robot (logging) | ✅ — treated as the transport robot logging its own pickup event |
| "The time between collection and delivery should be tracked" | System/robot (monitoring) | ✅ — treated as a query/monitoring responsibility of the system |

**Reflection:** This leaves two robot "agents" implicitly in play: a **mobile transport robot** (carries the locked drawer from floor to lab) and a **robotic arm** (fixed at the laboratory, handles scan/sort/load). Both are legitimate multi‑robot‑system components, so the model keeps them distinct at the task level (via Location/Number of Robots), even though they sit under the same goal hierarchy.

## Step 2 — Look for explicit ordering, parallelism, and fallback cues

- **Sequential cue (explicit):** "scans ... **sorts**, **and loads**" — a clear left‑to�right order → sequential (`;`).
- **Sequential cue (implicit/logical necessity):** a robot must *arrive* before it can *open* a drawer; a drawer must be *opened* before a sample can be *scanned*; collection must happen before delivery (by definition of "time between X and Y").
- **Parallel cue:** nothing in the physical pickup→transport→delivery chain can run concurrently with itself, but **logging** and **time‑tracking** are monitoring activities that ride alongside the physical process without gating it — modeled as parallel branches at the root.
- **Fallback cue:** I searched specifically for an "if X fails, then Y" or "normal case / exception case" pattern (as instructed) and **found none** — there is no stated alternative behavior triggered by a failure, condition, or threshold anywhere in the text. So **no FALLBACK operator is used anywhere** in this model. This is a deliberate choice, not an oversight.
- **OR‑decomposition cue:** The only "or" in the text ("authorized personnel **or** specific robots") describes *alternative human/robot actors*, not alternative ways the *robot's own* goal can be fulfilled. From the robot-system's point of view there is no genuine alternative path to success anywhere in the description — every step is mandatory. Hence **the whole tree uses AND decomposition only**, and I explicitly justify this choice at each node rather than defaulting to it.

## Step 3 — Shape the top-level goal

Everything in the description serves one mission: get the sample from the patient floor into the analysis machine, safely, with an audit trail and a compliance check. That gives one root **Achieve** goal, AND‑decomposed into five sub‑goals representing pickup, transport, delivery, logging, and time‑compliance.

## Logical Relationships

- **G1 -> G2, G3, G4, G5, G6 [AND] (G2;G3;G4) # G5 # G6**
  - **Justification**: All five sub‑goals are mandatory — none is a mere alternative to another, so AND. Physically, pickup must precede transport which must precede delivery (strict causal chain → sequential), while logging and time‑monitoring are concurrent, non‑blocking activities running alongside that chain (→ parallel with it and with each other).

- **G2 -> AT1, AT2 [AND] (sequential)**
  - **Justification**: The robot must physically be at the patient floor before it can act on a drawer located there — arrival is a precondition for access, so AT1 must complete before AT2.

- **G3 -> AT3, AT4 [AND] (parallel)**
  - **Justification**: Moving and "staying locked" are not discrete steps performed one after another — the drawer must remain locked continuously *while* the robot is moving, so both run simultaneously for the whole transit.

- **G4 -> AT5, AT6, AT7, AT8 [AND] (sequential)**
  - **Justification**: The drawer must be opened before the sample is accessible, and the text gives an explicit left‑to‑right order for the rest — "scans ... sorts, and loads" — so all four are chained sequentially.

- **G5 -> AT9, AT10 [AND] (parallel)**
  - **Justification**: "Where and when" are reported together as one logging event in the text, with no stated order between the two pieces of information, so they are modeled as parallel.

- **G6 -> AT11, AT12 [AND] (sequential)**
  - **Justification**: Collection chronologically precedes delivery by definition — the phrase "time between sample collection and laboratory delivery" fixes this order explicitly.

---

### Why no OR and no FALLBACK anywhere
I deliberately checked for both at every node: an **OR** would require the text to present genuine alternative ways to satisfy a goal (not found — every described step is necessary), and a **FALLBACK** would require an explicit "if this fails, do that instead" / exception‑handling pattern (also not found). Introducing either would misrepresent the description, so the entire tree is AND‑decomposed with only sequential (`;`) and parallel (`#`) runtime annotations.
