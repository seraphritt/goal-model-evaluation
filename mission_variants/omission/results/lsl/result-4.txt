# Mission Analysis: Lab Sample Transport & Processing System

## Step-by-Step Reasoning

**Step 1 — Identify all actors/agents mentioned in the description**

| Actor | Robot? | Actions attributed |
|---|---|---|
| Nurse | No (human) | Requests delivery; inserts data in track system |
| Transport mechanism (locked drawer carrier) | Yes (robot, implicit — this is a multi-robot delivery system) | Carries sample from floor to lab |
| Robotic arm | Yes | Picks, scans, sorts, loads sample |
| Laboratory personnel | No (human) | Alternative to robotic arm for picking |
| Track/logging system | Ambiguous — tied to robot-generated events | Logs pick info; tracks elapsed time |

**Step 2 — Apply the "zero-robot" exclusion rule**

Per the rule *"Goals and tasks that are not performed by any robot (zero robot) must not be on the goal model,"* I exclude the following from the formal model, with justification:

- *"A nurse ... can request a delivery to the laboratory"* → **Excluded**. Purely a human trigger action, no robot involved.
- *"Each sample ... is identified with a barcode"* → **Excluded**. Passive construction, no actor stated; implicitly a human/lab staff action prior to collection — only relevant later as a precondition for the robotic arm's scan action.
- *"The nurse inserts data about the sample in a track system"* → **Excluded**. Explicit human action, zero robot involvement.
- *"the sample can be picked by a robotic arm **or** laboratory personnel"* → This is textually an OR-alternative, but the "laboratory personnel" branch is zero-robot. Since a decomposition needs a minimum of two children to be expressed as OR, and only one branch (robotic arm) qualifies as robot-performed, **the OR is collapsed**: the goal model represents only the robotic-arm path directly, without constructing an artificial single-child OR. The human alternative is omitted from the model (noted here for traceability only).

**Step 3 — Group remaining robot-relevant content into goals/tasks**

What remains, all clearly robot-executed or robot-attributable:
- Transport of sample from floor to lab in a locked drawer (robot-driven transport unit).
- Tracking elapsed time between collection and delivery (attributed to the robot's own timestamping of pickup/drop-off events — the only robot-involved way this requirement can be satisfied, as distinguished from the excluded, purely human "nurse inserts data" action).
- Robotic arm: pick → scan → sort → load (explicitly sequential, per the sentence listing these four actions in strict left-to-right order).
- Logging of pick location/time — the term **"picked"** is used by the text only in the robotic-arm/lab context (not for "collection" at the floor), so this logging goal is scoped as a child of the laboratory-processing goal, not the transport goal.

**Step 4 — Determine runtime annotations**
- Transport **then** lab-processing: explicit narrative order ("transported... In the laboratory, the sample can be picked...") → **sequential (`;`)**, not fallback, since there is no failure/exception condition stated, just an unconditional required order.
- Scan → Sort → Load: explicit verb list in one sentence → **sequential (`;`)**.
- Delivery-time tracking vs. physical transport: no explicit order given; monitoring elapsed time naturally spans the whole transport, not a step after it → **parallel (`#`)**.
- Logging pick-info vs. continuing scan/sort/load: no explicit order given between these → **parallel (`#`)**.
- No condition/failure/exception is described anywhere in the text → **no FALLBACK used anywhere** in this model.

**Step 5 — Determine goal types**
- Root and lab-processing goals are about reaching a target state via planned action → **Achieve**.
- Delivery-time tracking is about monitoring/obtaining a value → **Query**.
- Logging is about bringing into existence a persistent record (a state) → **Achieve**.

## Logical Relationships

- **G1 -> G2, G4 [AND] (sequential: G2;G4)**
  - **Justification**: Both transport and lab-processing are mandatory, complementary phases (AND) — the sample cannot be considered "delivered and processed" unless both occur. The narrative order ("transported... In the laboratory...") explicitly states transport happens before lab processing, so they are sequential rather than parallel or fallback (no failure/alternative condition is mentioned).

- **G2 -> AT1, G3 [AND] (parallel: AT1#G3)**
  - **Justification**: Physically moving the sample and monitoring its transit time are both required (AND) for a compliant transport — neither can substitute for the other. The text gives no explicit order between the two, and logically, time-tracking spans the entire transport rather than being a discrete step before/after it, so parallel execution is the correct annotation.

- **G4 -> AT2, G5, AT3, AT4, AT5 [AND] (AT2;(G5#(AT3;AT4;AT5)))**
  - **Justification**: All five elements are mandatory (AND) for the sample to be fully processed. Picking (AT2) must occur first since it is the prerequisite event that both triggers the logging requirement (G5) and enables scanning. Once picked, logging the pick event (G5) and continuing the physical handling chain (AT3;AT4;AT5) have no stated dependency on each other, so they proceed in parallel. Within the physical handling chain, the mission text explicitly lists "scans... sorts... and loads" in that order, so AT3;AT4;AT5 are strictly sequential.

- **G3 and G5 are leaf nodes** (runtime `-`), since the mission description states these requirements ("should be tracked," "should be logged securely") without specifying any further operational sub-steps or mechanisms, consistent with the Query/Achieve goal examples given, which do not require forced decomposition into tasks.

### Notes on Exclusions (for traceability)
The following mission elements were deliberately **left out of the formal goal model** because they are performed by zero robots: the nurse's delivery request, the initial barcode identification/attachment, the nurse's data entry into the track system, and the "laboratory personnel" branch of the pick-up alternative. These remain valid parts of the real-world hospital workflow but fall outside the scope of a multi-robot system goal model per the stated constraint.
