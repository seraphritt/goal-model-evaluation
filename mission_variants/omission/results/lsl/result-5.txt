# Mission Analysis: Lab Sample Transport System

## Step 1 — Reading the Mission as a Mission Designer

Before building any tree, I read the description looking for **(a) who/what performs each action**, **(b) which actions are performed by robots vs. humans**, **(c) temporal/logical relationships between actions** (sequence, parallelism, failure-driven alternatives), and **(d) explicit locations**.

### 1.1 Sentence-by-sentence actor analysis

| # | Sentence | Actor | Robot-relevant? | Decision |
|---|----------|-------|------------------|----------|
| 1 | "Lab samples should be transported from patient floors to the laboratory." | System/Robot | ✅ Yes | → Root Goal |
| 2 | "A nurse...can request a delivery..." | Nurse (human) | ❌ No | Excluded as a node; kept only as *trigger context* for the robot's navigation task |
| 3 | "Each sample before collection is identified with a barcode." | Human/lab process (pre-collection labeling) | ❌ No | Excluded — no robot performs this |
| 4 | "The nurse inserts data...in a track system." | Nurse (human) | ❌ No | Excluded |
| 5 | "Samples are transported in secure locked drawers." | Robot (the carrying mechanism) | ✅ Yes | → Load/Lock tasks under Collect; Maintain-lock task under Transport |
| 6 | "...sample can be picked by laboratory personnel." | Lab personnel (human) | ❌ No | Excluded — this is the human alternative to the robotic-arm path in sentence 8 |
| 7 | "Only authorized personnel **or** specific robots...open the locked drawers." | Human **OR** Robot | Partial | The OR has one zero-robot branch (personnel) and one robot branch. Per the "zero-robot nodes excluded" rule, **only the robot branch survives**, so the OR collapses into a single path — **no OR decomposition remains in the final tree** |
| 8 | "The robotic arm scans...sorts...loads..." | Robotic arm | ✅ Yes | → Process-Sample sub-goal, 3 sequential tasks |
| 9 | "Information about where/when...picked should be logged securely." | Robot (logs its own pick events) | ✅ Yes | → Logging sub-goal |
| 10 | "The time between collection and delivery should be tracked..." | Robot/system (timestamping) | ✅ Yes | → Time-tracking sub-goal |

**Reflection:** This is the single most important modeling decision in this mission: sentence 7 contains an explicit **OR** particle, but because one disjunct ("authorized personnel") involves zero robots, the rule "goals/tasks not performed by any robot must not be on the model" forces us to drop that branch. What remains is not an OR decomposition anymore (OR requires ≥2 live children) — it becomes a single mandatory task performed by "a specific robot in a specific location." This explains why the final tree contains **no OR decomposition** anywhere, even though the raw text uses the word "or."

### 1.2 Looking for FALLBACK

FALLBACK requires an **explicit stated order tied to a condition/failure/exception** (an "if X fails, do Y" pattern). I scanned for conditional/exception language: there is no "if the robot fails," "in case of," "otherwise," or similar construct anywhere in the text. The word "can" in "sample can be picked" expresses *possibility*, not a *failure-triggered alternative* — and that branch is excluded anyway (zero-robot). **Conclusion: no FALLBACK relation exists in this mission.** I explicitly avoid using it as a default for "order" — order alone (without a failure trigger) is modeled as **sequential (`;`)**, not FALLBACK.

### 1.3 Identifying Sequential vs Parallel

- Collection → Transport → Delivery is a **hard physical sequence** (you cannot transport before collecting, cannot deliver before transporting) → sequential (`;`).
- "Scans the barcode...sorts, and loads" — explicitly enumerated in that order → sequential (`;`), not fallback (no failure condition).
- Logging/time-tracking (monitoring) is **conceptually independent of the physical pipeline** — it can be executed alongside collection/transport/delivery without blocking them → parallel (`#`) with the main chain.
- Maintaining the drawer's lock *while* navigating is a concurrent condition, not a step that comes before/after navigation → parallel (`#`).

### 1.4 Avoiding redundancy

"Open locked drawer" appears conceptually twice (at the floor to load, at the lab to unload). These are **not duplicate intentions** — they occur at different locations, different times, and serve different purposes (securing vs. releasing the sample) — so both are kept as distinct tasks, each nested under its own parent goal (not shared, since the model is a tree, not a DAG).

## Step 6 — Logical Relationships

- **G1 -> G2, G3, G4, G6 [AND][(G2;G3;G4)#G6]**
  - **Justification**: The mission (sentence 1) requires that samples are collected, transported, and delivered (an unavoidable physical sequence — you cannot deliver before transporting, nor transport before collecting), while custody/timing monitoring (sentences 9–10) is a continuously-running concern that is not blocked by, nor blocks, the physical pipeline. All four are mandatory (AND); the physical chain is sequential, monitoring is parallel to it.

- **G2 -> AT1, AT2, AT3, AT4 [AND][sequential: AT1;AT2;AT3;AT4]**
  - **Justification**: To collect a sample the robot must physically reach the floor, then open its drawer, then load the sample, then lock it — each step is a physical precondition for the next (sentences 2, 5, 7), and all are required (AND).

- **G3 -> AT5, AT6 [AND][parallel: AT5#AT6]**
  - **Justification**: Arriving at the laboratory (sentence 1) and keeping the sample secure throughout (sentence 5) are two independent, simultaneously-held conditions during the same trip — neither is a step that precedes the other, so they run in parallel; both are required (AND), since an insecure arrival is still a mission failure.

- **G4 -> AT7, G5 [AND][sequential: AT7;G5]**
  - **Justification**: The drawer must be opened (sentence 7) before the sample can be scanned/sorted/loaded (sentence 8) — physical causality forces sequence; both steps are mandatory (AND).

- **G5 -> AT8, AT9, AT10 [AND][sequential: AT8;AT9;AT10]**
  - **Justification**: Sentence 8 explicitly enumerates these three actions in this exact order ("scans..., sorts, and loads"), with no conditional/failure language, so this is modeled as sequential (not FALLBACK); all three are required for the sample to reach the analysis machine (AND).

- **G6 -> G7, G8 [AND][parallel: G7#G8]**
  - **Justification**: Sentences 9 and 10 impose two separate "should" requirements (logging pick data; tracking transit time) that do not depend on one another's completion and can be carried out concurrently — both are mandatory (AND), executed in parallel.

- **G7 -> AT11, AT12 [AND][sequential: AT11;AT12]**
  - **Justification**: A pick event occurs at the floor (collection) and again at the lab (retrieval by the robotic arm); both must be logged (sentence 9, AND), and the floor event chronologically precedes the lab event (sequential).

- **G8 -> AT13, AT14 [AND][sequential: AT13;AT14]**
  - **Justification**: Computing and verifying the elapsed time (sentence 10) requires both a collection timestamp and a delivery timestamp (AND); collection necessarily happens before delivery, so recording is sequential.

## Step 7 — Final Reflections & Explicit Assumptions

1. **Why no OR decomposition appears anywhere**: the only disjunction in the text (sentence 7, "authorized personnel **or** specific robots") pairs a human actor with a robot actor. The modeling rule that zero-robot elements must not appear forces removal of the human branch, leaving a single mandatory robot path — collapsing what *reads* like an OR in the prose into an AND-only tree. I treated this explicitly rather than silently dropping the sentence, since it is the main source of nuance in this mission.
2. **Why no FALLBACK appears anywhere**: FALLBACK requires an explicit "if this fails, then do that" structure. The description contains no exception, failure, or conditional branching language — "can be picked" denotes a possibility that is itself excluded (zero-robot), not a failure-recovery path. Forcing a FALLBACK here would violate the instruction that it must not be used unless explicitly stated.
3. **Assumptions made explicit** (since the text doesn't name specific robot types for every step):
   - The *transport robot* that carries the locked drawer is assumed to also be the one authorized to open/lock it at the patient floor (AT2–AT4, AT6).
   - The *robotic arm* explicitly named in sentence 8 is assumed to also be the "specific robot" authorized to open the drawer at the laboratory (AT7), since it is the only lab-side robot the text names.
   - All robot counts were set to **1** per task because the description never implies cooperative multi-robot execution of a single step; the "multi-robot" nature of the system instead manifests as **multiple concurrent instances of this same goal tree**, one per active delivery request — this is a system-level scheduling concern, not a per-task robot-count concern.
4. **Excluded (zero-robot) elements**, kept only as narrative context, never as nodes: the nurse's delivery request, barcode pre-labeling, the nurse's track-system data entry, and lab personnel manually picking the sample.
