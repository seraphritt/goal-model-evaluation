# Goal Model Analysis — Hospital Lab Sample Transport (Multi-Robot System)

## Step 1 — Identifying the agents and filtering non-robot actions

Before building the tree, I went through the description sentence by sentence and classified every action by *who* performs it, because the rule "goals/tasks with zero robots must not appear" is the single biggest constraint on this model.

| Description fragment | Actor | Robot involved? | Decision |
|---|---|---|---|
| "A nurse... can request a delivery" | Nurse | No | **Excluded** (trigger only, not modeled) |
| "Each sample before collection is identified with a barcode" | Unspecified (implicitly human/manual) | No | **Excluded** |
| "The nurse inserts data... in a track system" | Nurse | No | **Excluded** |
| "Samples are transported in secure locked drawers" | Transport mechanism | Yes (a delivery/transport robot is the only way a multi-robot system physically moves the drawer) | **Included** |
| "...picked by a robotic arm **or** laboratory personnel" | Robotic arm / Personnel | Arm = yes, Personnel = no | **Only robotic-arm branch included**; personnel branch dropped entirely (not an OR with an empty child — just omitted, per the zero-robot rule) |
| "The robotic arm picks up, scans, sorts, loads" | Robotic arm | Yes | **Included** |
| "Information about where/when picked should be logged" | Logging function, tied to the arm's pick event (it directly follows the robotic-arm paragraph) | Yes (performed by the picking robot/its controller) | **Included** |
| "Time between collection and delivery tracked" | Tracking function, tied to the transport robot (it is the only agent present across the whole collection→delivery span) | Yes | **Included** |

This leaves exactly **four robot-relevant concerns**, which the text itself presents as four flat, non-overlapping requirements (no "or" ties them together — they're all needed): **Transport, Processing, Logging, Time-Tracking**. I avoided inventing an artificial "Monitoring" umbrella goal over Logging/Tracking, since the text doesn't group them together and doing so would add structure not supported by the description (redundancy risk).

## Step 2 — Why there's no OR and (almost) no Fallback

- The only "or" in the whole text ("robotic arm **or** laboratory personnel") does **not** become an OR-decomposition, because one branch has zero robots and must be dropped entirely — leaving a single, direct path (robotic arm picks). An OR needs ≥2 real children; here there is effectively only one.
- Fallback requires an **explicit stated order with a failure/alternative condition** ("if X fails, do Y"). Nothing in the text says "if the robotic arm fails to pick the sample, then..." — the arm/personnel choice is not framed as primary-attempt-then-alternative-on-failure, it's a plain alternative (and already reduced to one option). So **no FALLBACK is justified anywhere in this model.**
- Every decomposition I use is therefore **AND** — all identified robot behaviors are complementary and jointly required.

## Step 3 — Determining sequence vs. parallelism

- **Transport → Processing**: the sample physically cannot be picked/scanned/sorted/loaded before it arrives — the text's own paragraph order (transport described, then lab handling described) plus physical causality justify a **sequential** link.
- **Securing in the drawer → moving the drawer**: you cannot transport a drawer that hasn't been loaded/locked first — **sequential**.
- **Pick → Scan → Sort → Load**: the text lists these with "picks up... scans... sorts, and loads" — a clear left-to-right order, explicitly sequential, not merely possible-in-parallel.
- **Logging** (tied to the pick event) and **Time-tracking** (spanning collection→delivery) are cross-cutting: nothing in the text forces them to block the main sequence, so I modeled them as able to run **in parallel** (`#`) alongside the phase they monitor — logging alongside processing, time-tracking alongside the whole collection-to-delivery span (which starts at/with transport).

## Step 4 — Goal type classification rationale (summarized; full justification in the table)

- **G0, G1, G2, G3** are **Achieve** goals: each has a clear target *state* to reach (sample delivered; sample processed; pick info recorded).
- **G4** is a **Query** goal: "tracked" here means obtaining a measurement (elapsed time) from the world, not causing a state change — it matches the Query definition almost exactly ("Fetch Occupied Rooms" ≈ "Fetch elapsed time").

> Note on single-task goals (G3, G4): the decomposition rules call for a minimum of two children when a genuine AND/OR split exists in the text. For logging and time-tracking, the mission description specifies exactly **one** concrete robot action each — inventing a second task would mean fabricating detail not present in the description, which the instructions explicitly forbid ("You should not make up a location" / tasks). I therefore kept these as single-task goals rather than artificially padding the tree.

## Logical Relationships

- **G0 -> G1, G2, G3, G4 [AND] [(G1#G4);(G2#G3)]**
  - **Justification**: All four behaviors (transport, lab processing, logging, time-tracking) are independently stated as required ("should be transported...", "...picks up, scans, sorts, loads...", "...should be logged securely", "...should be tracked") with no "or" connecting them — a clear AND. Transport must complete before lab processing can start (physical precondition), hence `G1;G2`. Time-tracking (G4) spans the same interval as the transport leg (collection-to-delivery), so it runs in parallel with G1: `G1#G4`. Logging (G3) is tied to the pick event that opens the processing phase, so it runs in parallel with G2: `G2#G3`. Parentheses combine the two different operators (`;` and `#`) unambiguously: `(G1#G4);(G2#G3)`.

- **G1 -> AT1, AT2 [AND] (sequential)**
  - **Justification**: A drawer must be secured/locked before it can be moved — "Samples are transported in secure locked drawers" links the two actions as jointly necessary, with the securing action logically preceding transport. No failure/alternative condition is stated, so this is sequential, not fallback.

- **G2 -> AT3, AT4, AT5, AT6 [AND] (sequential)**
  - **Justification**: The description lists these four actions in one sentence joined by "and," in an explicit left-to-right order ("picks up samples, scans the barcode..., sorts, and loads..."), so all four are required (AND) and must occur in that stated order (sequential), with no indication any of them could occur in parallel or as a fail-over alternative.

- **G3 -> AT7 [AND]**
  - **Justification**: The single explicit requirement ("logged securely") is mapped to one task; AND is used nominally since it is the sole, fully required action for this goal — there is no alternative or optional path mentioned.

- **G4 -> AT8 [AND]**
  - **Justification**: Likewise, the single stated requirement ("time... should be tracked") maps to one task that must be performed for the goal to be satisfied.
