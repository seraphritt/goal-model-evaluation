# Goal Model Design — Lab Sample Transport & Processing Mission

## Step 1 — Reading the mission and separating robot vs. non-robot actions

Before building any hierarchy, I went sentence-by-sentence through the description and tagged **who performs each action**, because the rule "zero-robot goals/tasks must not appear in the model" eliminates a good portion of the text immediately.

| Mission sentence | Actor | Include in model? |
|---|---|---|
| "A nurse... can request a delivery" | Nurse (human) | ❌ Zero-robot — kept only as *trigger context*, not a node |
| "Each sample before collection is identified with a barcode" | Hospital staff | ❌ Zero-robot (labeling happens *before* any robot is involved) |
| "The nurse inserts data... in a track system" | Nurse (human) | ❌ Zero-robot |
| "Samples are transported in secure locked drawers" | Transport robot | ✅ Robot action |
| "the sample can be picked by laboratory personnel" | Lab personnel (human) | ❌ Zero-robot — this is the human *alternative*, discarded |
| "Only authorized personnel **or** specific robots in specific locations... open the locked drawers" | Personnel (❌) **or** Robot (✅) | ✅ Only the robot branch survives. Since the non-robot branch is removed, no OR-decomposition is needed here — only one actionable path remains for the model. |
| "The robotic arm scans... sorts... loads..." | Robotic arm | ✅ Robot action |
| "Information about where and when a sample was picked should be logged securely" | Implicit (system/robot) | ✅ Attributed to the robot handling the sample, since no human actor is named here (the only humans in the loop — nurse and lab personnel — are already excluded) |
| "The time... should be tracked" | Implicit (system/robot) | ✅ Attributed to the transport robot, since it is the agent physically present at both collection and delivery points |

**Reflection:** This filtering step is critical — without it, the model would be polluted with nurse/personnel nodes that violate the zero-robot constraint, and it also conveniently resolves the only apparent OR in the text (personnel **or** robots) into a single deterministic robot path.

## Step 2 — Grouping remaining actions into goal clusters

I grouped the surviving robot actions into four functional clusters, each with a distinct **intention** (to avoid redundancy):

1. **Getting the sample physically to the lab** (load → carry → unlock) + **monitoring transit time** (since time tracking is bounded exactly by "collection" and "delivery," i.e., the start/end of this same transport operation — nesting it here avoids duplicating "transport" intent elsewhere).
2. **Preparing the sample for analysis** (scan → sort → load into machine).
3. **Recording the pick event securely** (distinct intention from transport and from analysis — it's an audit/compliance concern).

This gives **one root mission goal** with **three complementary (AND) branches**, one of which contains a nested query sub-goal.

## Step 3 — Deciding decomposition type (AND/OR) and runtime operators

- No alternative paths exist among robot actions (every remaining action is *necessary*, not optional) → **AND everywhere**, never OR.
- The text gives **explicit ordering** in several places ("scans... sorts... and loads"; collection happens before delivery) → **sequential (`;`)**.
- Time-tracking happens *across* the transport sequence, not after it → **parallel (`#`)** with that sequence.
- No conditional/exception language ("if X fails, then Y") appears anywhere → **no FALLBACK is used** in this model.

---

## Zero-Robot Elements Excluded From the Model
- Nurse requesting a delivery
- Barcode labeling prior to collection
- Nurse entering data into the track system
- Sample being picked by **laboratory personnel**

These remain useful *narrative context* (they explain why/when the robots act) but, per the modeling rule, cannot appear as Goal/Task nodes.

## Logical Relationships

- **G1 -> G2, G4, G5 [AND] (sequential)**
  - **Justification**: All three branches are mandatory and complementary — transport, analysis-processing, and secure logging are all required for the mission to be fulfilled; none is a substitute for another. The mission text's own ordering (transport details → robotic-arm processing → logging statement) supports a sequential execution.

- **G2 -> AT1, AT2, AT3, G3 [AND] (combination: (AT1;AT2;AT3) # G3)**
  - **Justification**: Loading, transporting, and unlocking are physically ordered actions (sequential), while time-tracking spans the whole transport operation rather than waiting for it to finish, so it runs in parallel to that chain. Parentheses are used because two different operators (`;` and `#`) are combined.

- **G3 -> AT4, AT5 [AND] (sequential)**
  - **Justification**: Both timestamps are required to compute the elapsed time; collection chronologically precedes delivery, matching "time between sample collection and laboratory delivery."

- **G4 -> AT6, AT7, AT8 [AND] (sequential)**
  - **Justification**: The mission explicitly lists these in order — "scans... sorts... and loads" — leaving no ambiguity that this is a strict sequence, and all three are required (AND), not optional alternatives.

- **G5 -> AT9, AT10 [AND] (sequential)**
  - **Justification**: Data must be captured before it can be stored; "logged securely" implies both a capture step and a distinct security/storage step, both mandatory.

---

### A couple of modeling judgment calls worth flagging
- I attributed **AT1** (loading the drawer) and the **logging tasks (AT9/AT10)** to a robot even though the text doesn't name the actor explicitly — the alternative (a human) would have to be excluded anyway under the zero-robot rule, so a robot is the only way these necessary steps remain representable. If your intent was for loading to be a purely human/nurse action, AT1 should be removed entirely.
- No **FALLBACK** or **OR** relations appear anywhere, because the description contains no explicit "first try X, then Y if it fails" language, and the only textual alternative (personnel **or** robot opening the drawer) collapses to a single path once the human branch is excluded.
