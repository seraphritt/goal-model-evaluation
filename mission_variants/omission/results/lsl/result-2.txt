# Mission Analysis — Lab Sample Transport System

## Step 1 — Identifying the Agents and Actions

Before building the tree, I read the description to separate **who does what**, because the rule "zero-robot goals/tasks must not appear" forces an early filtering pass.

**Human-only actions (excluded from the model):**
- Nurse requesting a delivery — human-initiated event, no robot involved.
- Barcode identification "before collection" — done prior to any robot involvement.
- Nurse inserting sample data into the track system — explicitly a human/software-entry action.
- "…or laboratory personnel" picking the sample — this is the human branch of what would otherwise be an OR; since one branch has zero robots, I don't keep a binary OR node (OR needs ≥2 valid children). I keep only the robotic-arm branch as a direct path, and I'm flagging this decision explicitly rather than silently dropping information.

**Robot-only actions (kept, and they define two distinct robot roles):**
1. **Transport Robot** — moves the sample (inside a secure locked drawer) from the patient floor to the laboratory.
2. **Robotic Arm** — picks, scans, sorts, and loads the sample into the analysis machine's entry-module, at the laboratory.

Two monitoring/logging requirements also need a home in the tree:
- "where and when a sample was picked" → tied to the **Robotic Arm's pick event** (it immediately follows the arm's description).
- "time between collection and delivery" → tied to the **Transport Robot's** journey (it spans collection → delivery, which is exactly the transport leg).

## Step 2 — Deciding Decomposition Type (AND/OR) and Runtime

- No genuine robot-vs-robot alternative exists anywhere in the text → **no OR decomposition** appears in the final model (the only OR candidate was the human/robot one, which I excluded).
- The narrative gives an explicit order for transport → processing ("transported… then in the laboratory the sample can be picked…"), so that top-level link is **sequential**, not fallback (no failure/exception condition is stated anywhere — so FALLBACK is never applicable in this mission).
- The arm's four actions are given as an explicit ordered list ("picks up… scans… sorts… loads") → **sequential**.
- Logging/time-tracking don't block or depend on the main physical pipeline completing → modeled as **parallel (#)** side-goals.
- Collection-timestamp necessarily occurs before delivery-timestamp (temporal fact of the mission) → **sequential**, even though no explicit "first/then" wording is used for this specific pair — I'm flagging this as an inference, not an explicit textual fallback trigger (so it is sequential, *not* FALLBACK).

## Step 3 — Goal Typing Rationale (brief, full justification in table)

- **G1, G2, G4, G5 → Achieve**: each has a concrete resulting state (sample at the lab; sample loaded into entry-module; pick info securely stored).
- **G3 (time tracking) → Query**: its purpose is to obtain a derived piece of information (elapsed duration) rather than to change the physical world.

## Logical Relationships

- **G1 -> G2, G4 [AND][(sequential)]**
  - **Justification**: Both transport and lab-side processing are mandatory, non-alternative parts of the mission; the description's own ordering (transport described first, lab actions described second, with the lab action depending on the sample already being present) makes this sequential rather than parallel or fallback — no failure/exception condition is ever stated, so FALLBACK doesn't apply.

- **G2 -> AT1, G3 [AND][(parallel)]**
  - **Justification**: The physical drawer transport and the duration-tracking are both required ("should be tracked"), but tracking is a passive observation that runs alongside the transport without gating it — hence parallel (#), not sequential.

- **G3 -> AT2, AT3 [AND][(sequential)]**
  - **Justification**: Both timestamps are jointly required to compute the elapsed duration (AND). They are sequential because the delivery timestamp can only be recorded after collection has already happened — a temporal fact established by the mission's own flow (floor → lab), even though the text doesn't use an explicit "first…then" phrase for this specific pair; I'm flagging this as an inferred rather than explicitly-stated order.

- **G4 -> AT4, AT5, AT6, AT7, G5 [AND][(AT4;AT5;AT6;AT7) # G5]**
  - **Justification**: All four physical actions are explicitly listed in strict order ("picks up… scans… sorts… loads"), so AND + sequential for that chain. Logging (G5) is appended as a parallel requirement since it doesn't block or reorder the pipeline — it is a monitoring/compliance obligation running alongside it.

- **G5 -> AT8, AT9 [AND][(parallel)]**
  - **Justification**: "Where and when" are two distinct but jointly mandatory pieces of information (AND), captured at the same picking event, so they can be logged in parallel (#) rather than one gating the other.
