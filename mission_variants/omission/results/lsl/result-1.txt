# Goal Model Analysis — Multi-Robot Lab Sample Transport Mission

## Step 1: Extracting actions and actors from the description

Before building the tree, I listed every action in the text and tagged *who* performs it:

| Description fragment | Actor | Robot-performed? |
|---|---|---|
| "A nurse ... can request a delivery" | Nurse | ❌ Zero-robot |
| "Each sample ... is identified with a barcode" (pre-collection) | Nurse/lab staff (implicit) | ❌ Zero-robot |
| "The nurse inserts data ... in a track system" | Nurse | ❌ Zero-robot |
| "Samples are transported in secure locked drawers" | Transport robot (implicit — multi-robot system context, nurse only *requests*, does not carry) | ✅ Robot |
| "the sample can be picked by a robotic arm **or** laboratory personnel" | Robotic arm / Lab personnel | Split — OR alternative |
| "The robotic arm picks up ... scans ... sorts ... loads" | Robotic arm | ✅ Robot |
| "Information about where and when ... picked should be logged" | Tied to robotic arm's pick event | ✅ Robot (captured at the point of robotic pick) |
| "time between sample collection and laboratory delivery should be tracked" | Tied to transport robot's pickup/drop-off | ✅ Robot (re-interpreted below) |

**Key modeling decisions (and justifications):**

1. **Nurse-only actions excluded** (requesting delivery, pre-collection barcode labeling, track-system data entry) — per the zero-robot rule, these never appear as nodes. They are only *triggers/preconditions* for the mission, not part of the model.
2. **"Picked by robotic arm or laboratory personnel" → OR branch collapses.** This is a textbook OR-alternative (no failure/exception condition is stated — it is not "if the arm fails, then personnel picks it", so this is **not** a FALLBACK), but since "laboratory personnel" is a zero-robot alternative, that branch is removed. Only one viable child remains, so no formal OR node is needed — the robotic-arm path becomes a direct task chain.
3. **"Information about where/when picked, logged securely"** is reinterpreted as an operational recording action performed by the same robotic arm that executes the pick (the arm/its integrated system already knows its own location and the current time — this is a *write*, not an information-seeking action), so it's modeled as a **Task**, not a Query Goal, and kept in the model (robot-performed).
4. **"Time between sample collection and laboratory delivery"** — for this to be robot-performed (and therefore eligible for the model), "collection" is interpreted as the moment the **transport robot takes custody of the sample** at the patient floor (the operational start of the robotic pipeline), and "delivery" as the moment it arrives at the laboratory. Both timestamps are things the transport robot can record itself, keeping this requirement robot-grounded rather than relying on the nurse's (zero-robot) track-system entry.
5. **No FALLBACK anywhere**: the description never states "X is attempted, and if it fails, Y is attempted instead." The only alternative ("robotic arm or personnel") lacks a failure condition — it reads as a staffing option, not a contingency — so FALLBACK is correctly *not* used anywhere in this model, consistent with the strict rule that FALLBACK requires an explicit failure/exception trigger.
6. **Sequential vs. parallel**: explicit ordered verb chains ("picks up, scans, sorts, and loads"; "collection **and** delivery" as two chronological points) → Sequential (`;`). The pick-event and its logging have no stated order relative to each other → modeled as concurrent (`#`), since the log simply records data generated at the moment of picking rather than gating the next step.

## Logical Relationships

- **G0 -> G1, G2 [AND] (sequential: `G1;G2`)**
  - **Justification**: Both the transport leg and the laboratory-processing leg are mandatory for the mission to be complete — delivering the sample without processing it (or vice versa) does not fulfill "lab samples should be transported ... to the laboratory" followed by in-lab handling, hence AND. The order is explicit in the text's structure: the sample must first arrive ("transported ... to the laboratory") before anything can happen "in the laboratory," so Sequential applies, not Parallel or Fallback (no failure/exception condition is described).

- **G1 -> AT1, AT2, AT3 [AND] (sequential: `AT1;AT2;AT3`)**
  - **Justification**: All three actions are jointly required — without a start timestamp, the physical move, or an end timestamp, the goal of "transported within protocol time" cannot be evaluated or achieved, hence AND. The order is explicit and chronological: collection happens before transit, which happens before delivery ("time between sample collection and laboratory delivery"), so Sequential is required, not Parallel.

- **G2 -> AT4, AT5, AT6, AT7, AT8 [AND] (`(AT4#AT5);AT6;AT7;AT8`)**
  - **Justification**: Every step is mandatory to reach "sample loaded into the analysis machine," hence AND. The text explicitly lists pick → scan → sort → load as an ordered chain ("picks up samples, scans ... sorts, and loads"), so these four are Sequential. The logging requirement is stated as a separate, general obligation tied to the pick event with no explicit ordering relative to it, so AT4 and AT5 are modeled as occurring concurrently (`#`) rather than gating one another; parentheses group this pair before the remaining sequential chain to avoid ambiguity.

---

### Note on an excluded relation
The text's "the sample can be picked by a robotic arm **or** laboratory personnel" is the only place an OR-decomposition could have applied (two alternative agents for the same task). Since "laboratory personnel" involves zero robots, that branch is removed under the zero-robot rule, and the surviving single alternative (robotic arm) is folded directly into AT4 rather than kept as a one-child OR node (OR/AND decompositions require a minimum of two children).
