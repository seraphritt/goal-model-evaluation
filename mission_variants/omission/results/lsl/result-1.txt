# Goal Model Design: Lab Sample Delivery Multi-Robot System

## Step-by-Step Reasoning

**Step 1 — Identify the agents in the description.**
The description mentions: a *nurse* (human), *laboratory personnel* (human), *robots that carry locked drawers* (mobile transport robot(s)), and a *robotic arm* (fixed/manipulator robot at the laboratory). Per the rule "goals/tasks not performed by any robot must not be on the model," I must filter out purely human actions.

**Step 2 — Apply the zero-robot filter.**
The following description elements are explicitly **excluded** from the model because no robot performs them:
- "A nurse... can request a delivery" → human decision, not modeled (treated as the external trigger/precondition for the mission, not a node).
- "Each sample before collection is identified with a barcode" → labeling is a manual/administrative act (no robot performs the *labeling*; the robot only *scans* it later, which **is** kept).
- "The nurse inserts data about the sample in a track system" → pure human/IT action, excluded.
- "the sample can be picked by laboratory personnel" → the *physical pick by a human* is excluded, but the surrounding system requirements that depend on robots (opening the drawer, logging the event) are **kept**, since those are operations the robotic system must perform regardless of who removes the sample.

**Step 3 — Identify the robot-relevant backbone of the mission.**
What remains, all robot-executed, is:
1. Secure the sample in a locked drawer at the patient floor (robot unlocks/locks).
2. Transport the drawer from the patient floor to the laboratory (mobile robot navigation).
3. Unlock the drawer at the laboratory under authorization control (robot).
4. Log where/when the sample was picked (robot/drawer system — see assumption below).
5. Process the sample with the robotic arm: scan barcode → sort → load into the analysis machine's entry-module.
6. Track elapsed time between collection and delivery, for protocol compliance.

**Step 4 — Decomposition logic.**
- Steps 1–3 are jointly required and strictly ordered (you can't transport before loading, or unload before transporting) → **AND**, **sequential (;)**.
- Step 4 (logging) is required in conjunction with opening the drawer, so it is nested under the unloading goal, sequential after the open action.
- Step 5's three actions are explicitly listed in the text in a fixed order ("scans..., sorts, and loads...") → **AND**, **sequential (;)**.
- Step 6 (time tracking) is not tied to one physical point — it spans the whole mission — so it is modeled as running **in parallel (#)** with the main transport-and-process flow, not nested inside it.
- Wherever the text uses a conjunction ("where **and** when," open **and** lock, etc.) with no explicit order, I used **AND decomposition** with **parallel (#)** runtime, since no sequencing is stated. Wherever a physical/causal order is unavoidable (open before lock, navigate before unload, scan before sort before load) and is derivable from the way the process is described, I used **sequential (;)**.
- No **FALLBACK** relation is used anywhere, because the description never states an explicit alternative triggered by failure/condition for any robot action (the only "alternative" language — "authorized personnel **or** specific robots" — is a *role/authorization constraint* on who may trigger the unlock, not a described failure-and-alternative execution behavior; see justification on AT1/AT4).

**Step 5 — Assumption flagged explicitly.** The description doesn't say *who/what* performs the secure logging of the pick event or the collection/delivery timestamps. Since these must be tamper-proof/secure and the robotic drawer/arm system is the only entity present at both events, I assign these logging actions to the robotic system itself (consistent with a multi-robot system handling its own audit trail). This is a reasonable inference, not an explicit statement, and is flagged here for transparency.

## Logical Relationships

- **G1 -> G2, G6, G7 [AND] [(G2;G6)#G7]**
  - **Justification**: All three are necessary for mission success: the sample must be transported (G2), then processed (G6) — strictly sequential, since processing can't start before the sample physically arrives — while delivery-time compliance (G7) must be observed across the *entire* duration of the mission, hence running in parallel with the G2;G6 sequence rather than nested inside it.

- **G2 -> G3, AT3, G4 [AND] [sequential: G3;AT3;G4]**
  - **Justification**: Loading, transit, and unloading are all required and strictly ordered by the physical process described ("transported from patient floors to the laboratory," "transported in secure locked drawers") — you cannot transit before loading, nor unload before transiting.

- **G3 -> AT1, AT2 [AND] [sequential: AT1;AT2]**
  - **Justification**: Both the authorized opening and the subsequent locking are required to achieve a "securely loaded" state; opening must precede locking by physical necessity.

- **G4 -> AT4, G5 [AND] [sequential: AT4;G5]**
  - **Justification**: The drawer must be opened before the pick event (which the log refers to) can occur and be recorded; both the authorized opening and the secure logging are explicitly required by the description.

- **G5 -> AT5, AT6 [AND] [parallel: AT5#AT6]**
  - **Justification**: The description conjoins "where **and** when" with no stated order between the two pieces of information, so both are required (AND) and may be captured together as part of one log entry (parallel).

- **G6 -> AT7, AT8, AT9 [AND] [sequential: AT7;AT8;AT9]**
  - **Justification**: The text explicitly lists the robotic arm's actions in this order — "scans..., sorts, and loads..." — making a Fallback misapplied (no failure/condition is stated) and Sequential the correct choice.

- **G7 -> AT10, AT11 [AND] [sequential: AT10;AT11]**
  - **Justification**: Both timestamps are required to compute the tracked duration; the collection timestamp necessarily precedes the delivery timestamp in time.
