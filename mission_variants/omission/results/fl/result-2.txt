# Goal Model Design: Multi-Robot Hospital Meal Delivery & Dish Retrieval

## Step-by-Step Reasoning

**1. Identify the top-level responsibilities.**
The description names two independent, recurring service processes: (a) delivering food from kitchen to inpatient room (triggered by a kitchen request) and (b) retrieving dirty dishes (triggered by a room call). Neither triggering event is performed by a robot (kitchen staff ordering, a person calling) — per the "zero-robot" rule these triggers are **not** modeled as goals, only as the triggering condition for the goal subtrees. I introduce a root goal **G0** that is fulfilled when both recurring services operate correctly, decomposed **AND** into **G1** (delivery) and **G18** (dish retrieval), executed in **parallel (#)** since they are independent processes that can run concurrently for different rooms/orders.

**2. Explicit source→destination order (G1).**
"deliver food **from the kitchen to** an inpatient room" explicitly fixes an order: the meal must be collected at the kitchen before it can reach the room. This is a **sequential (;)** relation, not fallback (no failure/condition is involved) and not OR (both steps are required) → **AND** decomposition of G2 (fetch at kitchen) and G3 (deliver to inpatient).

**3. OR between delivery modes (G3).**
"delivered into a room table ... **or** ... fetched from the robot's tray" is an explicit alternative with no stated priority or retry-on-failure condition → **OR** decomposition, runtime **#** (no obligatory order).

**4. Distinguishing Query vs. Fallback vs. OR (the central design decision).**
Two very similar-looking passages needed different treatment:

- *Meal retrieval* text: lists cooperators "the inpatient, a companion, a nurse, **or** another robot," then immediately explains **why each of the first three might fail** ("could be unable," "could not be available") and explicitly states **"This information is subject to uncertainty."** This is exactly the FALLBACK trigger pattern: a normal/preferred behavior (ask inpatient) with an alternative triggered by a failure condition, cascading through companion → nurse, and finally to robot-robot cooperation (which has no stated failure condition, so it is the guaranteed last resort). I therefore modeled this as a **nested FALLBACK chain**, not a flat OR, and kept the capability check (record + companion presence) as a separate **Query** goal that informs — but, due to the stated uncertainty, does not eliminate the need for — the fallback attempts.
- *Door-opening* text: the caller "can signal if they can open the door" — this is presented as a known, reliable piece of information with **no accompanying uncertainty statement** and no "if unavailable..." failure language. So this is modeled as a **Query → OR** (deterministic branch selection), not a fallback/retry structure. This contrast is deliberate and is the main nuance of this model.

**5. Sequencing of access before action (G18).**
Nothing can be picked up from a closed room, so "Access Room" (G19) must precede "Collect Dishes" (G24) — inferred logical necessity → **sequential (;)**, not fallback (no explicit failure/retry condition links these two).

**6. Scoping "indicate meal" and "track retrieval" precisely.**
"in the case of a **person** retrieving the meal, the robot should indicate..." explicitly scopes the indication task to the person-cooperation branch only (not the robot-cooperation fallback) — avoiding over-generalization. "Track when and where each meal was **retrieved**" is scoped to the tray-retrieval branch only (table delivery is not described as a "retrieval").

**7. Zero-robot exclusions.**
"Kitchen delivery request" and "someone calls a robot" are human/system-initiated triggers, not robot-performed goals — excluded per the zero-robot rule.

**8. Locations & robot counts.**
Only two physical locations are explicitly cited — *kitchen* and *inpatient room* — so every task is grounded to one of these two. Robot counts are read literally from the cooperation language: "the robot" / solo action → 1; "cooperation with **another** robot" → 2; "cooperation of **two** robots" → 2; robot + human → 1 (humans are not counted as robots).

## Logical Relationships

- **G0 -> G1, G18 [AND] (parallel)**
  - *Justification*: Delivery and dish retrieval are two independently triggered, continuously recurring services that can proceed concurrently.

- **G1 -> G2, G3 [AND] (sequential)**
  - *Justification*: "deliver food from the kitchen to an inpatient room" explicitly orders collection before delivery.

- **G1 -> AT1** is not direct; **G2 -> AT1 [AND]**
  - *Justification*: G2 is fulfilled by the single mandatory fetching action.

- **G3 -> G4, G5 [OR] (parallel)**
  - *Justification*: "delivered into a room table or fetched from the robot's tray" — explicit alternative, no stated priority.

- **G4 -> AT2 [AND]**
  - *Justification*: Single mandatory manipulation action fulfills the goal.

- **G5 -> G6, G9, G17 [AND] (sequential)**
  - *Justification*: Capability must be known before facilitating retrieval, and tracking can only occur after retrieval happens.

- **G6 -> G7, G8 [AND] (parallel)**
  - *Justification*: "based on the inpatient record ... and the presence of a companion" — two independent, jointly required info sources.

- **G7 -> AT3 [AND]**, **G8 -> AT4 [AND]**
  - *Justification*: Each query goal is fulfilled by its single mandatory information-gathering task.

- **G9 -> G10, G16 [AND] FALLBACK(G10, G16)**
  - *Justification*: Person-based cooperation is attempted first; robot-robot cooperation is the unconditional fallback, since no unavailability is ever stated for it.

- **G10 -> G11, G12 [AND] (sequential)**
  - *Justification*: The meal must be indicated before/while a person retrieves it, since the robot carries multiple meals.

- **G11 -> AT5 [AND]**
  - *Justification*: Single mandatory indication action.

- **G12 -> G13, G14, G15 [AND] FALLBACK(FALLBACK(G13, G14), G15)**
  - *Justification*: "Some inpatients could be unable... a companion visitor or nurse could not be available" explicitly supplies the failure-driven order inpatient → companion → nurse, combined with the explicit "subject to uncertainty" statement motivating a true retry/fallback (not a one-shot deterministic choice).

- **G13 -> AT6 [AND]**, **G14 -> AT7 [AND]**, **G15 -> AT8 [AND]**, **G16 -> AT9 [AND]**
  - *Justification*: Each is fulfilled by its single mandatory cooperative action.

- **G17 -> AT10 [AND]**
  - *Justification*: Single mandatory logging action.

- **G18 -> G19, G24 [AND] (sequential)**
  - *Justification*: Room access is a prerequisite for physically collecting dishes.

- **G19 -> G20, G21 [AND] (sequential)**
  - *Justification*: Must know the caller's door-opening capability before determining/executing how the door is opened.

- **G20 -> AT11 [AND]**
  - *Justification*: Single mandatory signal-receiving action.

- **G21 -> G22, G23 [OR] (parallel)**
  - *Justification*: "cooperation with another robot or a human" — explicit alternative, no stated priority or failure condition (unlike the meal-retrieval case, no uncertainty is mentioned here), so OR rather than fallback.

- **G22 -> AT12 [AND]**, **G23 -> AT13 [AND]**
  - *Justification*: Each fulfilled by its single mandatory cooperative action.

- **G24 -> G25, G26, G27 [OR] (parallel)**
  - *Justification*: "unassisted, with cooperation of two robots or with cooperation of robots and a human" — explicit three-way alternative, no stated order.

- **G25 -> AT14 [AND]**, **G26 -> AT15 [AND]**, **G27 -> AT16 [AND]**
  - *Justification*: Each fulfilled by its single mandatory collection action.
