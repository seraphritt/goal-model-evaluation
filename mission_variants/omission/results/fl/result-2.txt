# Mission Analysis & Goal Model: Hospital Meal Delivery & Dish Retrieval Multi-Robot System

## Step 1 — Reading the mission for intentions, actors, and structure

Before building the tree, I extracted the following from the description:

**Two independently-triggered top-level processes:**
- Food delivery, triggered "in response to kitchen delivery requests" (order-by-order).
- Dirty-dish retrieval, triggered when "someone in the room can call a robot to pick up the dishes."
Nothing in the text orders one before the other at the mission level — they are triggered by different events — so I treat them as two AND-required but independently-timed (parallel) branches of the root mission.

**Key decision points I had to reason through:**

1. **Who can fetch food from the tray?** The text lists "the inpatient, a companion, a nurse, or another robot" as alternatives with no stated priority order — this is an explicit **OR**, not a FALLBACK (no "first try X, then Y" is stated). I grouped inpatient/companion/nurse into one *Human-Assisted Retrieval* branch, because from the robot's perspective the action performed (present tray, wait for a human to take it) is operationally identical regardless of which human it is — merging them avoids duplicating goals with the same underlying intention, per the modeling rules. "Another robot" is a genuinely different cooperation mode (2 robots), so it stays a separate OR branch.

2. **Wrong-meal alert = FALLBACK.** "The robot should alert **if** a wrong meal is retrieved" is an explicit conditional/exception clause (normal behavior = correct retrieval; exception = wrong meal → alert). This is a textbook case for the FALLBACK operator as defined, so I modeled `FALLBACK(Confirm Correct Meal, Alert Wrong Meal)`, connected by AND per the rule that FALLBACK siblings are always AND-related.

3. **Dish retrieval modes and door-opening = OR.** "Unassisted, with cooperation of two robots, or with cooperation of robots and a human" and "cooperation with another robot or a human" are flat, unordered alternatives (explicit "or" particles, no stated preference) → OR decompositions, not FALLBACK.

4. **Sequencing vs. parallelism.** I only used sequential (`;`) where one activity logically *needs the output* of another (e.g., you must know the order details before transporting; you must indicate the meal before a person can retrieve the right one; you must open the door before dishes can be taken out). Where no such dependency exists and the text gives no explicit order (e.g., checking the inpatient's record vs. checking companion presence; the three dish-retrieval alternatives relative to each other), I used parallel (`#`), since the "possibility not obligation" semantics fit unordered/alternative items best.

5. **Zero-robot exclusion.** I deliberately did **not** create a standalone node for "patient/visitor physically grabs the food" or "visitor opens the door alone," because those describe a purely human action. Every leaf task I kept involves at least one robot (even "unassisted" and "human-assisted" tasks involve the delivering robot's own presence, sensing, or tray).

6. **Locations.** Only "kitchen" and "inpatient room" (and the room's "door") are explicitly cited in the text, so every task is anchored to one of these — I did not invent a hospital database, ward, or corridor as a location.

7. **Door opening** is explicitly discussed only in the dish-retrieval paragraph, so I did not assume it also applies to the delivery branch (that would be inventing information not stated).

│  │  └─ AT2 Detect Companion Presence in Room [Task]

## Step 6 — Logical Relationships

- **G1 -> G2, G10 [AND] (parallel): G2#G10**
  - **Justification**: Food delivery and dish retrieval are both explicitly required services, but each is triggered independently ("kitchen delivery requests" vs. "someone...can call a robot"), so neither waits on the other; both are jointly necessary (AND) and unordered relative to each other (parallel).

- **G2 -> G3, AT1, G4, G6, G8 [AND] G3;(AT1#G4);G6;G8**
  - **Justification**: All five are necessary for a successful delivery. Order details (G3) must be known before anything else can target the right meal/room, so it comes first. Once known, transporting the meal (AT1) and checking who can retrieve it (G4) have no dependency on each other and can proceed in parallel. Retrieval (G6) can only happen once the robot has arrived and the capability is known, so it is sequential after both. Monitoring (G8) logically follows the retrieval event, so it comes last.

- **G4 -> G5, AT2 [AND] (parallel): G5#AT2**
  - **Justification**: The description explicitly conjoins two independent information sources — "information about the patient **and** the presence of a companion into the room" — making this an AND; since the two checks don't depend on one another, they are modeled in parallel.

- **G6 -> G7, AT5 [OR] (parallel): G7#AT5**
  - **Justification**: "Requires cooperation with the inpatient, a companion, a nurse, **or** another robot" is an explicit list of alternatives with no stated priority, so OR applies; parallel notation reflects that no ordering/preference between the alternatives is given in the text.

- **G7 -> AT3, AT4 [AND] (sequential): AT3;AT4**
  - **Justification**: Both indicating and retrieving are jointly necessary (AND) for successful human-assisted retrieval. The text states the robot "should indicate which meal should be retrieved" before describing the retrieval, and logically a person needs to know which meal is theirs before taking it — hence sequential.

- **G8 -> AT6, G9 [AND] (parallel): AT6#G9**
  - **Justification**: Tracking the retrieval event and validating its correctness are both explicitly required behaviors (AND); the text gives no dependency or order between logging and validating, so they are modeled as parallel.

- **G9 -> AT7, AT8 [AND] FALLBACK(AT7, AT8)**
  - **Justification**: "The robot should alert **if** a wrong meal is retrieved" is an explicit conditional/exception clause — normal behavior (correct meal) vs. an alternative triggered by a failure condition — which must be modeled as FALLBACK per the definitions; FALLBACK siblings are mandatorily AND-related.

- **G10 -> G11, G12, G13 [AND] (sequential): G11;G12;G13**
  - **Justification**: All three are necessary (AND) to retrieve dishes. Logically and in line with the text's progression, the robot must first obtain the call details (which room, door-opening availability), then open the door to gain access, and only then can the dishes be retrieved — a clear sequential dependency.

- **G12 -> AT9, AT10 [OR] (parallel): AT9#AT10**
  - **Justification**: "Can involve cooperation with another robot **or** a human" is an explicit unordered alternative (OR); no preference is stated, so parallel notation is used.

- **G13 -> AT11, AT12, AT13 [OR] (parallel): AT11#AT12#AT13**
  - **Justification**: "Can occur unassisted, with the cooperation of two robots **or** with the cooperation of robots and a human" lists three unordered alternative execution modes (OR), with no stated preference, hence parallel.
