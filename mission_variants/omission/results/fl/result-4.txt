# Mission Decomposition: Hospital Meal-Service Multi-Robot System

## Step-by-Step Reasoning

Before building the tree, I worked through the description sentence by sentence to extract intentions, decide node types, and decide relations. Here is the reasoning trail:

**1. Identifying the two top-level missions.**
The description clearly separates two symmetric processes: *"deliver food from the kitchen to an inpatient room"* and *"Dirty dishes should be retrieved from the room."* These are two distinct intentions that together define the system's purpose, so they become the two main branches of a root goal (**AND**, because the system must do both), with a **parallel** runtime since different orders/pickups can be processed concurrently (the text treats them as independent order-by-order and call-by-call processes, never stating one must wait for the other at the system level).

**2. Food delivery branch.**
- *"in response to kitchen delivery requests"* — this is a triggering condition of the delivery goal, not a separate intention, so I folded it into the Deliver-Food goal's text rather than creating a redundant node.
- *"The information about if the inpatient, a companion visitor or nurse can be able to retrieve the food ... can be obtained based on the inpatient record ... and the presence of a companion ... subject to uncertainty"* — this is explicitly about **obtaining information**, not acting on the world, so it is a **Query Goal**. It decomposes **AND** into two independent information sources (patient record, companion presence) — nothing in the text orders one before the other, so I used **parallel**.
- *"the robot should indicate which meal should be retrieved by a given inpatient"* — a concrete, operational, single-shot action → **Task**, not a goal (a goal wrapping a single task would violate the "minimum two children" rule, so I attached it as a sibling to the fetch goal instead of isolating it).
- *"Fetching from the robot tray requires cooperation with the inpatient, a companion, a nurse, or another robot"* — four explicit **alternatives** connected by "or" → **OR decomposition**. No explicit priority order is stated, so FALLBACK is disallowed here (per the rule that fallback requires an explicit order); I used **parallel**, meaning the system may pursue whichever option is available, with no mandated order.
- *"The robot should alert if a wrong meal is retrieved"* — this is a textbook **IF-triggered alternative behavior** (normal = correct retrieval; exception = wrong item taken → alert). This is exactly the condition the instructions say must be modeled as **FALLBACK**.
- *"It should track when and where each meal was retrieved"* — two explicit attributes (time, location) with no stated order → **AND / parallel**, modeled as an **Achieve** goal because the target is a persisted record of the event, not a single query answer.

**3. Dish retrieval branch.**
- *"the dish retrieve can occur unassisted, with the cooperation of two robots or with the cooperation of robots and a human"* — three explicit alternatives → **OR**, no stated priority → **parallel**.
- *"Opening the room door can involve cooperation with another robot or a human"* — two explicit alternatives → **OR**, **parallel**.
- *"Someone in the room can call a robot ... that person can signal if they can open the door when the robot comes to it"* — this describes a case where the **person opens the door alone**. I deliberately **excluded this as a modeled node**: the instructions state that goals/tasks not performed by *any* robot must not appear in the model, and a person opening a door unassisted involves zero robot action. Only the cooperative opening (which does require the robot) is modeled under "Open Room Door."
- Door-opening is placed **sequentially before** dish retrieval, since a closed door is an implicit precondition to entering the room to collect dishes (a logical/physical prerequisite, even though not phrased with "first...then").

**4. Avoiding redundancy and respecting the "2+ children" rule.**
Wherever a literal reading would have produced a goal with only one child (e.g., "indicate meal," "alert wrong meal," "open door alone"), I either converted it into a task attached alongside a sibling, or (for the zero-robot case) removed it entirely, to respect both the minimum-two-children rule and the zero-robot exclusion rule.

## Logical Relationships

- **G1 -> G2, G8 [AND](parallel)**
  - **Justification**: Delivering food and retrieving dishes are two distinct, equally necessary system intentions; the text treats them as independent order-driven and call-driven processes that can overlap in time.

- **G2 -> G3, G4, G7 [AND](sequential)**
  - **Justification**: All three are required for a complete delivery. The description's information flow — first know who can retrieve (G3), then act on it (G4), then record the event (G7) — implies this left-to-right order.

- **G3 -> AT1, AT2 [AND](parallel)**
  - **Justification**: Capability is determined from two data sources named together in the text (inpatient record and companion presence); both are needed and neither is stated to precede the other.

- **G4 -> AT3, G5 [AND](sequential)**
  - **Justification**: The robot must indicate the correct meal before the fetch is attempted, since the recipient needs to know which meal to retrieve first.

- **G5 -> G6, AT8 [AND][FALLBACK(G6, AT8)]**
  - **Justification**: "Alert if a wrong meal is retrieved" is an explicit exception-triggered alternative to the normal correct-retrieval behavior — the defining case for the FALLBACK operator. FALLBACK branches are always AND-connected per the specification.

- **G6 -> AT4, AT5, AT6, AT7 [OR](parallel)**
  - **Justification**: The text lists four interchangeable helpers ("the inpatient, a companion, a nurse, or another robot") — fulfilling any one suffices (OR). No order of preference is stated, so parallel (possibility, not obligation) is used rather than fallback.

- **G7 -> AT9, AT10 [AND](parallel)**
  - **Justification**: "when and where" are two jointly required attributes with no stated precedence.

- **G8 -> G9, G10 [AND](sequential)**
  - **Justification**: The door must be opened before dishes can physically be collected from the room — a necessary precondition implied by the narrative sequence (call → door signal → dish retrieval).

- **G9 -> AT11, AT12 [OR](parallel)**
  - **Justification**: "cooperation with another robot or a human" is an explicit two-way alternative with no stated priority.

- **G10 -> AT13, AT14, AT15 [OR](parallel)**
  - **Justification**: "unassisted, with the cooperation of two robots, or with the cooperation of robots and a human" is an explicit three-way alternative with no stated priority.

### A note on an interpretive decision worth flagging
I excluded "the person in the room opens the door themselves" as a modeled node, since that action, taken alone, is performed by zero robots and the instructions explicitly forbid including such nodes. Only the cooperative door-opening (which necessarily involves a robot) is represented under G9. If your intended use of the model wants to preserve the human-only branch for completeness/documentation purposes (even though no robot acts in it), let me know and I can add it back as an annotated, explicitly-excluded alternative.
