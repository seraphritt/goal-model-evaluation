# Goal Model for the Hospital Meal‑Delivery / Dish‑Retrieval Mission

## 1. Step‑by‑Step Reasoning

**Step 1 — Identify the top‑level intentions.**
The description bundles two largely independent service loops: (a) *delivering food* (kitchen → inpatient room) and (b) *retrieving dirty dishes* (room → pickup). Nothing in the text orders one relative to the other, and both are clearly robot‑performed, so I created a single root mission goal **G1** that AND‑decomposes into **G2 (Deliver Food)** and **G11 (Retrieve Dirty Dishes)**, executed in parallel (`#`).

**Step 2 — Separate "trigger → transport → retrieval → bookkeeping" inside delivery.**
The text gives an implicit pipeline: a kitchen request triggers the process, the meal is transported, then it must be taken off the tray, and finally the system must log/verify the retrieval. These four stages have an unavoidable causal order (you cannot verify a retrieval that hasn't happened yet), so I modeled G2's children as **sequential**, even though the text never uses an explicit "first…then" phrase — the sequencing is a physical/logical necessity rather than an exception‑handling case, so `;` is correct and FALLBACK is **not** used here (no explicit conditional ordering is stated).

**Step 3 — Handle the fetch‑from‑tray cooperation.**
This was the trickiest part. The text lists four possible cooperators (inpatient, companion, nurse, another robot) joined only by "or," with no stated priority. My first instinct was to treat this as a FALLBACK chain (try inpatient, then companion, then nurse, then robot), since this mirrors real hospital logic. However, the rules are explicit: FALLBACK may be used **only** when the order is explicitly given in the text. It isn't — it's a flat list of alternatives. Moreover, the text already describes a **separate, prior step** that determines who is capable/available ("information... can be obtained based on the inpatient record... subject to uncertainty"). This means that by the time retrieval is attempted, the acting agent is already known — there is no trial‑and‑error needed at runtime. This strongly supports:
- A **Query Goal (G4)** that determines the capable agent *before* retrieval is attempted, and
- An **OR decomposition (G5)** over the retrieval alternatives, with `#` as the runtime annotation (since OR‑alternatives don't have a mandated order, and `#` is the closest available operator to express "no obligatory order among options").

**Step 4 — Isolate the "indicate the meal" requirement.**
"In the case of a person retrieving the meal, the robot should indicate which meal..." is conditioned on *person* cooperation, not robot‑robot cooperation. To avoid duplicating this goal three times (once per person type) and violating the non‑redundancy rule, I placed it as a single task that must happen *before* any person‑cooperation branch, inside a dedicated goal **G6 (Retrieve Meal via Person Cooperation)**, sibling to the robot‑cooperation task under the OR node G5.

**Step 5 — Separate tracking from alerting.**
"Track when/where retrieved" and "alert if wrong meal" are two different post‑retrieval concerns: tracking is unconditional (always happens), while alerting is explicitly conditional ("**if** a wrong meal is retrieved"). The word "if" is exactly the signal the rules call out for FALLBACK: normal behavior (verify the meal is correct) with an alternative/exceptional behavior (alert) triggered by a failure condition. So I used **FALLBACK(verify, alert)** here — this is the one place in the whole model where FALLBACK is textually justified. Tracking was kept as a separate, parallel sibling goal since nothing links it causally to the verification step.

**Step 6 — Apply the "minimum two children" rule.**
Several candidate goals (e.g., "indicate the meal," "receive the kitchen request," "verify the meal") are naturally atomic, single-action items. Rather than artificially forcing a 2‑child decomposition on them (which would mean inventing information not in the text), I demoted these to **Tasks** (leaves), since a Task does not require further decomposition. Wherever a concept genuinely contains two distinct, textually‑grounded pieces (e.g., "when **and** where" → two tasks; "patient information **and** companion presence" → two tasks), I kept it as a Goal with exactly those two children.

**Step 7 — Dish retrieval mirrors delivery's structure.**
"Someone in the room can call a robot" is the trigger (mirrors the kitchen request), "opening the door" is a prerequisite access step with three explicit alternatives (unassisted / robot cooperation / human cooperation), and "collect the dishes" has its own three explicit alternatives (unassisted / two robots / robot+human). The call→door→collect order is implied by the narrative ("when the robot comes to it") so it is modeled as sequential.

**Step 8 — Locations and robot counts.**
Only "kitchen" and "inpatient room" are named in the text, so every task location is restricted to one (or both) of these — no invented locations (e.g., "corridor," "database," "nurse station"). Robot counts default to 1 unless the text explicitly says "another robot" or "two robots," in which case I used 2.

## 5. Logical Relationships

- **G1 -> G2, G11 [AND] (parallel)**
  - **Justification**: Delivery and dish‑retrieval are independent request‑driven services; nothing in the text orders one relative to the other, and both must ultimately be satisfied.

- **G2 -> AT1, AT2, G3, G8 [AND] (sequential)**
  - **Justification**: An order must be received before transport, transport must occur before the meal can be taken from the tray, and the retrieval must happen before it can be logged/verified — a causal chain.

- **G3 -> G4, G5 [AND] (sequential)**
  - **Justification**: The capable/available agent must be determined (from the uncertain inpatient‑record information) before an attempt to retrieve the meal is made.

- **G4 -> AT3, AT4 [AND] (parallel)**
  - **Justification**: "Based on the inpatient record according to information about the patient **and** the presence of a companion" names two independent pieces of information, both required, checkable independently.

- **G5 -> G6, AT9 [OR] (parallel)**
  - **Justification**: Retrieval happens either via a person or via another robot — mutually exclusive alternatives ("the inpatient, a companion, a nurse, **or** another robot"); no explicit order given, so `#` rather than FALLBACK.

- **G6 -> AT5, G7 [AND] (sequential)**
  - **Justification**: The meal must be indicated to the inpatient before that person (or helper) can retrieve the correct one.

- **G7 -> AT6, AT7, AT8 [OR] (parallel)**
  - **Justification**: Inpatient, companion, and nurse are listed as interchangeable alternatives with no stated priority; which one actually occurs is already settled by G4's query, not by trial order.

- **G8 -> G9, G10 [AND] (parallel)**
  - **Justification**: Logging the retrieval and confirming its correctness are independent obligations with no stated dependency between them.

- **G9 -> AT10, AT11 [AND] (parallel)**
  - **Justification**: "Track **when and where**" names two distinct, independently obtainable data points, both mandatory.

- **G10 -> AT12, AT13 [AND] FALLBACK(AT12, AT13)**
  - **Justification**: Explicit conditional language ("**if** a wrong meal is retrieved") signals a normal path (verify) with an exception‑triggered alternative (alert) — the canonical FALLBACK case, and per the spec FALLBACK pairs are AND‑related.

- **G11 -> AT14, G12, G13 [AND] (sequential)**
  - **Justification**: The pickup call triggers the process, the door must be opened before the robot can act in the room, and dishes are collected only after access is gained.

- **G12 -> AT15, AT16, AT17 [OR] (parallel)**
  - **Justification**: "Opening the room door **can** involve cooperation with another robot or a human" lists unordered alternatives, including an implicit unassisted default.

- **G13 -> AT18, AT19, AT20 [OR] (parallel)**
  - **Justification**: "The dish retrieve can occur unassisted, with the cooperation of two robots or with the cooperation of robots and a human" explicitly lists three unordered alternatives.
