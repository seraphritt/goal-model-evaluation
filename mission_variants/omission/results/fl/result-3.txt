# Goal Model for the Hospital Meal/Dish-Collection Multi-Robot Mission

Below is my full analysis: first the step-by-step reasoning I used to decompose the description, then the resulting goal model (outline + full tables), and finally the explicit logical relationships.

---

## 1. Step-by-Step Reasoning

**Step 1 — Identify the top-level intentions.**
The description states two distinct, independently-triggered responsibilities: (a) "deliver food from the kitchen to an inpatient room" and (b) "dirty dishes should be retrieved from the room." Since both are core, mandatory responsibilities of the system (not alternatives to each other), I modeled a single root goal **G1** that AND-decomposes into **G2 (Deliver Food Order)** and **G9 (Retrieve Dirty Dishes)**. They are not causally dependent on each other (a delivery and a pickup can happen independently, at different times, for different rooms), so I used **parallel (#)** runtime rather than sequential.

**Step 2 — Model the two delivery modes as alternatives.**
"The food can be delivered into a room table by the robot ... **or** the food can be fetched from the robot's tray" is an explicit disjunction → **OR decomposition**. No order/preference or failure-triggered switch is stated between them, so I used **parallel (#)**, not FALLBACK (FALLBACK requires an explicit stated attempt-order/failure condition, which is absent here).

**Step 3 — Unpack "fetching from the tray."**
This branch is the richest part of the text and required careful separation of concerns:
- *Who can help* (inpatient, companion, nurse, or another robot) — an **OR** of helpers.
- *Whether a given helper is actually capable/available* — this is explicitly framed as information retrieval ("The information ... can be obtained based on the inpatient record ... and the presence of a companion") → a **Query Goal**.
- *Indicating which meal* — explicitly conditioned on "a person retrieving the meal" (not a robot), so I attached it only to the human-assisted branch, not to the robot-robot cooperation branch.
- *Tracking retrieval* ("when and where") — a separate persisting record-keeping goal.

I treated these four concerns as **sequential** where a real dependency exists (you must know who's available before attempting retrieval; you must indicate the meal before a person picks the right one; you must retrieve before you can log the retrieval), and **parallel** where no dependency exists (querying the record and detecting companion presence can happen simultaneously; logging time and logging location are simultaneous facts about the same event).

**Step 4 — Avoid redundancy.**
I kept "coordinate person-assisted retrieval" (indicate + retrieve) as one node, and "choose which person retrieves" (inpatient/companion/nurse) as a distinct child node, because they capture different intentions (coordination vs. selection-of-party) — not a duplication.

**Step 5 — Model dish retrieval.**
"The dish retrieve can occur unassisted, with ... two robots, or with ... robots and a human" → **OR** of three task alternatives. "Opening the room door can involve cooperation with another robot or a human" → a separate **OR** sub-goal, because door-opening is a distinct precondition for accessing the room, not one of the three dish-collection strategies itself.

**Step 6 — Apply the zero-robot rule.**
I deliberately **excluded** three elements as goal/task nodes, keeping them only as contextual triggers in the goal texts:
- the kitchen issuing a "delivery request" (an external/system event, not a robot action);
- "someone in the room can call a robot" (a human-performed action);
- "that person can signal if they can open the door" (a human-performed action).

These inform *which* branch of an OR decomposition is actually exercised at runtime, but per the rule "goals/tasks not performed by any robot must not be on the goal model," they are not modeled as nodes themselves.

**Step 7 — Decide Goal Type for every Goal node.**
I classified nearly every composite node as **Achieve** (each represents a target condition reached via one or more strategies/sub-steps), and exactly one as **Query** (G4, the only node whose explicit purpose is information-retrieval, not world-change). I found no node that fit **Perform** at the Goal level — every atomic, single-shot action in the text (place meal, indicate meal, cooperate-to-open-door, cooperate-to-retrieve, record time/location) is operational enough to be a **Task** (with a Location and a Number of Robots), which is exactly what the Task definition is for. I explain this choice explicitly in the Design Notes at the end.

**Step 8 — Locations.**
Only two locations are explicitly cited in the description: the **kitchen** (origin point only, not elaborated into sub-tasks) and the **inpatient room** (where literally every decomposed action — placing, indicating, cooperating, opening the door, recording, collecting — takes place). I did not invent any location beyond these.

## 2. Goal Model — Tree Outline

```
G1  Provide Inpatient Meal Service [AND] (G2 # G9) — Achieve
├─ G2  Deliver Food Order [OR] (AT1 # G3) — Achieve
│   ├─ AT1  Place Meal on Table
│   └─ G3  Fetch Meal via Tray [AND] (G4 ; G5 ; G8) — Achieve
│       ├─ G4  Determine Retrieval Capability [AND] (AT2 # AT3) — Query
│       │   ├─ AT2  Query Inpatient Record
│       │   └─ AT3  Detect Companion Presence
│       ├─ G5  Retrieve Meal via Tray [OR] (G6 # AT8) — Achieve
│       │   ├─ G6  Coordinate Person-Assisted Retrieval [AND] (AT4 ; G7) — Achieve
│       │   │   ├─ AT4  Indicate Meal to Retriever
│       │   │   └─ G7  Retrieve Meal via Person [OR] (AT5 # AT6 # AT7) — Achieve
│       │   │       ├─ AT5  Cooperate with Inpatient to Retrieve Meal
│       │   │       ├─ AT6  Cooperate with Companion to Retrieve Meal
│       │   │       └─ AT7  Cooperate with Nurse to Retrieve Meal
│       │   └─ AT8  Cooperate with Another Robot to Retrieve Meal
│       └─ G8  Track Meal Retrieval [AND] (AT9 # AT10) — Achieve
│           ├─ AT9  Record Retrieval Time
│           └─ AT10 Record Retrieval Location
└─ G9  Retrieve Dirty Dishes [AND] (G10 ; G11) — Achieve
    ├─ G10 Open Room Door [OR] (AT11 # AT12) — Achieve
    │   ├─ AT11 Cooperate with Another Robot to Open Door
    │   └─ AT12 Cooperate with Human to Open Door
    └─ G11 Collect Dirty Dishes [OR] (AT13 # AT14 # AT15) — Achieve
        ├─ AT13 Retrieve Dishes Unassisted
        ├─ AT14 Retrieve Dishes with Two-Robot Cooperation
        └─ AT15 Retrieve Dishes with Robot-Human Cooperation
```

## 6. Logical Relationships

- **G1 -> G2, G9 [AND](parallel)**
  - **Justification**: Food delivery and dish retrieval are both mandatory system responsibilities ("should deliver...", "should be retrieved..."), not alternatives; nothing in the text makes one depend on the other, so they can proceed in parallel.

- **G2 -> AT1, G3 [OR](parallel)**
  - **Justification**: "The food can be delivered into a room table... **or** fetched from the robot's tray" — an explicit alternative; either one fulfills the delivery. No stated order between attempts, so parallel rather than FALLBACK.

- **G3 -> G4, G5, G8 [AND](sequential)**
  - **Justification**: Determining who can retrieve, performing the retrieval, and logging it are all required for the tray-delivery mode (AND). They have an inherent causal order — you must know capability before retrieving, and must retrieve before logging — hence sequential.

- **G4 -> AT2, AT3 [AND](parallel)**
  - **Justification**: "...obtained based on the inpatient record **and** the presence of a companion" explicitly requires both pieces of information; they are independent checks with no stated order, so parallel.

- **G5 -> G6, AT8 [OR](parallel)**
  - **Justification**: The four named helpers collapse into two mutually sufficient strategies — human-assisted (with mandatory meal indication) or robot-robot — either achieves the goal. No order stated, so parallel.

- **G6 -> AT4, G7 [AND](sequential)**
  - **Justification**: "In the case of a person retrieving the meal the robot should indicate which meal" ties indicating and retrieving together as jointly necessary (AND); indicating logically precedes the person's retrieval action (sequential).

- **G7 -> AT5, AT6, AT7 [OR](parallel)**
  - **Justification**: Inpatient, companion, and nurse are presented as interchangeable cooperating parties; any one suffices (OR), with no preference order stated (parallel).

- **G8 -> AT9, AT10 [AND](parallel)**
  - **Justification**: "Track when **and** where" names two jointly-required facts about the same event, captured together with no stated order.

- **G9 -> G10, G11 [AND](sequential)**
  - **Justification**: Access (door open) and collection are both necessary, non-substitutable steps (AND); access must be achieved before dishes can be physically collected (sequential, causal necessity).

- **G10 -> AT11, AT12 [OR](parallel)**
  - **Justification**: "Opening the room door can involve cooperation with another robot **or** a human" — explicit alternative, no order stated.

- **G11 -> AT13, AT14, AT15 [OR](parallel)**
  - **Justification**: "...can occur unassisted, with the cooperation of two robots, **or** with the cooperation of robots and a human" — three explicit, mutually sufficient alternatives, no order stated.

## 7. Design Notes & Assumptions

- **No Perform-type Goal was used.** Every single-shot, immediately-executable action in the text (placing the meal, indicating a meal, cooperating with a specific party, recording a fact) satisfies the **Task** definition (it has a clear Location and Number-of-Robots) and was modeled as a Task rather than as a "Perform Goal." All Goal nodes in this mission are composite objectives that either decompose further (Achieve) or purely retrieve information (Query — only G4).
- **Zero-robot exclusions.** Three human-only actions from the text were deliberately *not* modeled as nodes, per the zero-robot rule, though they remain in the goal texts as triggering context: the kitchen issuing a delivery request (trigger for G2), someone calling a robot for dish pickup, and that person signaling door-opening willingness (the real-world condition that determines which branch of G10's OR is exercised).
- **Uncertainty.** The description flags G4's result ("information... is subject to uncertainty") — this should be carried as a non-functional property (e.g., a confidence/probability attribute) on G4's queried property rather than as a separate goal node, since uncertainty is a quality of the query result, not an action.
- **Redundancy check.** G6 (coordinate indication + retrieval) and G7 (choice of human party) were kept distinct because they capture different intentions — forcing them into one node would have hidden the mandatory "indicate meal" step and made the robot-vs-person asymmetry (AT8 has no indicate step) impossible to represent cleanly.
- **Locations.** Only "kitchen" and "inpatient room" appear in the description; the kitchen is mentioned purely as the food's origin and is not elaborated into further sub-tasks in the text, so no kitchen-side task was invented. Every decomposed task's location is "inpatient room," including information-oriented tasks like AT2 (querying the record), since no separate physical/informational location is cited for it.
