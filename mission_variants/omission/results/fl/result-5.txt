# Goal Model Analysis: Hospital Meal Delivery & Dish Collection Multi-Robot System

## Step-by-Step Reasoning

**1. Identifying the mission's two independent macro-processes.** The description contains two clearly separable responsibilities: (a) delivering food from kitchen to inpatient, triggered by a kitchen request, and (b) retrieving dirty dishes, triggered by a call from someone in the room. Nothing in the text orders one before the other or forbids concurrency, so I rooted the model in a single mission goal (G1) that AND-decomposes into these two processes with a parallel (#) runtime.

**2. Spotting the two OR-alternatives for delivery.** "The food can be delivered into a room table ... **or** the food can be fetched from the robot's tray" is an explicit OR particle with no stated order of preference → OR decomposition, parallel runtime (no fallback evidence).

**3. Spotting the FALLBACK pattern for tray retrieval.** The cooperating-agent list ("the inpatient, a companion, a nurse, or another robot") is immediately followed by a sentence describing *why each earlier option might fail* ("some inpatients could be unable...", "a companion visitor or nurse could not be available"). This is exactly the "normal behavior + condition-triggered alternative" pattern that the instructions require to be modeled as FALLBACK, nested because there are four alternatives. Per the stated rule, FALLBACK forces an **AND** decomposition between its two operands, even though conceptually these are mutually exclusive alternatives.

**4. Treating uncertainty as a Query Goal.** "The information ... can be obtained based on the inpatient record ... and the presence of a companion ... This information is subject to uncertainty" is clearly information-gathering, not action — a Query Goal, decomposed AND into two parallel checks (record lookup, presence detection), executed *before* the fallback attempt (sequential).

**5. "Indicate which meal" as a precondition, not a duplicate of retrieval.** Because the robot carries multiple meals, it must tell the correct person which meal is theirs before a human-mediated retrieval can succeed. This only applies to the three *person*-based fallback branches (inpatient/companion/nurse), not to robot-robot cooperation (robots don't need a spoken/visual "indication"). I introduced an intermediate goal "Fetch via Person" = AND(Indicate Meal ; Person Retrieval Attempt), itself one operand of the outer FALLBACK against "Fetch via Robot Cooperation."

**6. Tracking as a mandatory closing step.** "It should track when and where each meal was retrieved" is scoped to *retrieval* (the verb matches tray-fetch, not table delivery) and happens after retrieval, regardless of which fallback branch succeeded — modeled as an AND, sequential step after the retrieval attempt.

**7. Dish retrieval mirrors the same three-method OR pattern.** "Unassisted, with the cooperation of two robots, or with cooperation of robots and a human" — three OR alternatives, no explicit attempt order stated ("as with delivery" references the *mechanism*, not an order), so OR/parallel, not FALLBACK.

**8. Door-opening is a genuine OR, not a FALLBACK.** "Can involve cooperation with another robot or a human" is a capability choice resolved by a known signal ("that person can signal if they can open the door") rather than a try-then-fail sequence — so I modeled a Query Goal (signal reception) preceding an OR choice, rather than nesting it in FALLBACK (no explicit retry-after-failure language).

**9. Symmetry for triggers.** Just as delivery is "in response to kitchen delivery requests," dish pickup is triggered by someone "calling a robot." I modeled both as Query Goals that must occur first (sequential) in each process, for consistency and because the robot must obtain the request/call content before acting.

**10. Zero-robot exclusion check.** Every leaf task was checked to ensure at least one robot is required to execute it (database/record checks and signal reception were treated as being performed in the room by the acting robot via its own sensing/communication, not by an uninvolved hospital system — otherwise they would have had to be excluded).

**11. Goal typing logic.** Direct physical actions whose success is fully within the robot's control (placing food, opening a door via cooperation, collecting dishes) were typed as **Perform**. Goals whose fulfillment depends on another agent's uncertain capability/availability explicitly flagged in the text (inpatient/companion/nurse retrieving) were typed as **Achieve**, since the FALLBACK mechanism needs a success/failure target state to trigger the next branch. Information-gathering goals were typed **Query**.

## Logical Relationships

- **G1 -> G2, G17 [AND] (parallel)**
  - **Justification**: Both food delivery and dish collection are mandated system behaviors with no stated order or mutual exclusivity between them.

- **G2 -> G3, G4 [AND] (sequential)**
  - **Justification**: Delivery is "made ... in response to kitchen delivery requests" — the request must be received before fulfillment can begin.

- **G4 -> G5, G6 [OR] (parallel)**
  - **Justification**: "Delivered into a room table ... or fetched from the robot's tray" is an explicit alternative; no preference order given.

- **G6 -> G7, G8, G16 [AND] (sequential)**
  - **Justification**: Availability must be determined, then retrieval attempted, then the event logged — the text orders these implicitly by narrative flow and dependency (you can't log a retrieval that hasn't been attempted, and you can't attempt retrieval without knowing who's available).

- **G7 -> AT3, AT4 [AND] (parallel)**
  - **Justification**: Both inpatient-record data and companion-presence data are required jointly; no order specified between the two checks.

- **G8 -> G9, G15 [AND] FALLBACK(G9, G15)**
  - **Justification**: Person-based retrieval is attempted first (least robot-resource-intensive, matches listed order); robot-robot cooperation is the explicitly last-listed, most resource-costly alternative, used only if person-based retrieval fails — explicit condition-triggered alternation.

- **G9 -> G10, G11 [AND] (sequential)**
  - **Justification**: The robot must indicate the correct meal before a person can correctly retrieve it.

- **G11 -> G12, G13, G14 [AND] FALLBACK(FALLBACK(G12, G13), G14)**
  - **Justification**: Explicit list order "the inpatient, a companion, a nurse" combined with explicit failure/unavailability conditions for each requires nested FALLBACK (binary operator, >2 alternatives).

- **G17 -> G18, G19, G20, G23 [AND] (sequential)**
  - **Justification**: The call must be received, door-opening capability determined, the door opened, and only then can dishes be collected — a clear necessary, ordered chain.

- **G20 -> G21, G22 [OR] (parallel)**
  - **Justification**: "Cooperation with another robot or a human" is an explicit alternative; the choice is resolved by G19's signal rather than a stated attempt-then-fail order, so no FALLBACK.

- **G23 -> G24, G25, G26 [OR] (parallel)**
  - **Justification**: "Unassisted, with the cooperation of two robots, or with cooperation of robots and a human" lists three explicit alternatives with no stated order of attempt.

- **G7 -> AT3, AT4 [AND]** *(task-level, repeated for clarity)*
  - **Justification**: As above — both data points are jointly necessary task outputs feeding the query goal.

All remaining goal-to-task relations (G3→AT1, G5→AT2, G10→AT5, G12→AT6, G13→AT7, G14→AT8, G15→AT9, G16→AT10, G18→AT11, G19→AT12, G21→AT13, G22→AT14, G24→AT15, G25→AT16, G26→AT17) are **single-task direct realizations** and therefore carry no AND/OR label, since AND/OR decomposition by definition requires a minimum of two children; each of these goals is operationalized by exactly one concrete, robot-executable task drawn directly from the text.

A note on method: I built this by decomposing per the explicit OR/AND/FALLBACK particles and conditional-failure language in the text, and I didn't invent any location, robot count, or hierarchy not traceable to the description (the one soft inference is placing the inpatient-record check and call/signal reception "in the room," since the text ties the surrounding activity to the room but doesn't name a system/database location explicitly — flagged in the relevant justifications).
