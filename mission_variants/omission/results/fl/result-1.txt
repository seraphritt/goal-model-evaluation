# Mission Analysis & Goal Model: Hospital Meal Delivery & Dish Pickup Robot System

## Step-by-Step Reasoning

**1. Identifying the top-level intentions**
The description contains two clearly separable, independently-triggered processes:
- Deliver food (triggered "in response to kitchen delivery requests")
- Retrieve dirty dishes (triggered when "someone in the room can call a robot to pick up the dishes")

Since the text never states one must wait for the other, and both can occur for different orders/rooms concurrently, I modeled a root goal **AND**-decomposed into these two, with a **parallel (#)** runtime — there's no obligation that one finishes before the other starts.

**2. Avoiding redundancy (critical instruction)**
The text lists four possible cooperators for tray-fetching: "the inpatient, a companion, a nurse, or another robot." Three of these (inpatient, companion, nurse) share the *exact same underlying intention*: a human retrieves the meal, and the robot's behavior (presenting the tray, indicating the meal) is identical regardless of which human it is. Modeling three near-identical goals would violate the no-redundancy rule, so I merged them into a single goal, **"Fetch Food via Human Cooperation,"** and kept **"cooperation with another robot"** as a separate OR-branch, since that case involves a genuinely different action (two robots physically interacting) and a different robot count.

**3. Excluding zero-robot elements**
I deliberately did **not** create standalone goals like "Inpatient eats meal" or "Nurse assists patient," since these actions involve no robot. Every goal/task I kept has at least one robot executing something (querying data, presenting a tray, manipulating food, opening a door, carrying dishes), satisfying the "zero-robot" exclusion rule.

**4. AND vs. OR decisions**
- *Table delivery* **or** *tray fetch* → explicit "or" in text → **OR**.
- *Human cooperation* **or** *robot cooperation* for tray fetch → explicit "or" in text → **OR**.
- *Unassisted* / *two-robot* / *robot+human* for dish retrieval → explicit three-way "or" → **OR**.
- *Door opening*: "another robot **or** a human" → **OR**. (I did not invent an "unassisted" branch for the door, since — unlike dish retrieval — the text never says the door can be opened unassisted; adding it would be fabricating content.)
- Everything else (assessing capability, delivering, tracking; receiving request, opening door, collecting dishes) are jointly necessary steps of one coherent process → **AND**.

**5. Sequential vs. Parallel vs. Fallback**
- No condition/failure/exception triggers an alternative anywhere in the text (e.g., no "if the robot fails to X, then Y" phrasing), so **FALLBACK is never used** — using it would violate the strict "must be explicit" rule.
- Where the narrative gives a clear temporal/logical order (receive order → assess capability → deliver → track; receive call → open door → collect dishes; receive call → *then* signal about the door), I used **sequential (;)**.
- Where two sub-elements are complementary but no order is stated (e.g., "when and where," patient-record info + companion presence, indicating the meal + presenting the tray), I used **parallel (#)**, since parallel means "possible, not obligatory" — exactly the uncertain-order case.

**6. Goal typing**
- Goals that gather information ("obtained based on the inpatient record...," the kitchen request itself, the pickup call/door signal) → **Query**.
- Goals requiring a concrete, bounded action with no complex state-reaching ("track when and where," i.e., log a data point) → **Perform**.
- Goals requiring the world to reach a state through planning/acting (deliver the meal, open the door, collect the dishes) → **Achieve**.

**7. Locations & robot counts**
Only "kitchen," "inpatient room," and (implicitly, as part of the room) "room table" / "room door" are cited — I used only these. Robot counts come directly from textual cues: "the robot" (singular) → 1; "another robot" / "two robots" → 2; the ambiguous "robots and a human" → range [1,2], bounded by the explicit two-robot case elsewhere in the same sentence.

## Logical Relationships

- **G1 -> G2, G9 [AND] (parallel)**
  - **Justification**: Delivering food and retrieving dishes are both named as core responsibilities of the system, triggered independently (kitchen requests vs. room calls); nothing in the text forces one to wait for the other.

- **G2 -> G3, G4, G5, G8 [AND] (sequential): ((G3;G4);G5);G8**
  - **Justification**: You must first know the order (G3), then assess who can retrieve it (G4), before actually delivering (G5), and tracking only makes sense after retrieval occurs (G8) — the narrative presents this as a natural process order.

- **G3 -> AT1, AT2 [AND] (parallel)**
  - **Justification**: Both the order content and the destination room are necessary parts of "processing" a kitchen request; no order between obtaining these two pieces of information is stated.

- **G4 -> AT3, AT4 [AND] (parallel)**
  - **Justification**: The description lists the patient record and companion presence as the two joint inputs needed to determine retrieval capability — "based on the inpatient record according to information about the patient **and** the presence of a companion."

- **G5 -> AT5, G6 [OR] (parallel)**
  - **Justification**: "The food can be delivered into a room table by the robot ... **or** the food can be fetched from the robot's tray" is an explicit alternative; fulfilling either is sufficient.

- **G6 -> G7, AT8 [OR] (parallel)**
  - **Justification**: Cooperation can be with a human (merged inpatient/companion/nurse) **or** with another robot — these are alternative, mutually exclusive ways to get the meal off the tray.

- **G7 -> AT6, AT7 [AND] (parallel)**
  - **Justification**: Successful human-assisted retrieval needs both the indication of which meal (when multiple are carried) and the physical presentation of the tray; both are necessary, neither alone suffices.

- **G8 -> AT9, AT10 [AND] (parallel)**
  - **Justification**: "Track **when and where**" names two complementary data points that must both be recorded; the text gives no order between them.

- **G9 -> G10, G11, G12 [AND] (sequential): (G10;G11);G12**
  - **Justification**: The narrative order is explicit: someone calls (G10) → the robot arrives and the door situation is handled (G11) → dishes are collected (G12). Each step is a precondition for the next.

- **G10 -> AT11, AT12 [AND] (sequential): AT11;AT12**
  - **Justification**: "Someone in the room can call a robot ... **In that case**, that person can signal if they can open the door" explicitly places the door signal as following from (after) the call.

- **G11 -> AT13, AT14 [OR] (parallel)**
  - **Justification**: "Opening the room door can involve cooperation with another robot **or** a human" — explicit alternative.

- **G12 -> AT15, AT16, AT17 [OR] (parallel): AT15#AT16#AT17**
  - **Justification**: "...can occur unassisted, with the cooperation of two robots **or** with the cooperation of robots and a human" lists three explicit mutually-exclusive execution modes for the same goal.

A couple of modeling choices worth flagging as **assumptions** rather than hard facts in the text: (1) I treated "receive kitchen request" and "receive dish pickup call" as sequential predecessors to the rest of their branches, since the text's narrative order implies this even though it isn't phrased as a strict rule; and (2) AT17's robot count [1,2] is an inference from the plural "robots" in "cooperation of robots and a human," since no exact number is given there.
