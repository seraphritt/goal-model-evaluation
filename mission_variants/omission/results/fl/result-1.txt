# Multi-Robot Goal Model: Hospital Meal Delivery & Dish Retrieval System

## Step-by-Step Reasoning

**Step 1 – Identify the macro-intentions.** The description bundles two clearly distinguishable, mandatory system responsibilities: (a) delivering food from the kitchen to an inpatient, and (b) retrieving dirty dishes from the room. Both are explicitly required ("should deliver…", "dirty dishes should be retrieved…"), so the root goal AND-decomposes into these two branches. They are triggered by different, independent events (a kitchen request vs. a room call) and nothing in the text forces one to wait for the other, so I treat them as **parallel** at runtime.

**Step 2 – Look for trigger/query moments.** Both branches begin with the system reacting to an external request ("in response to kitchen delivery requests," "someone in the room can call a robot"). Since obtaining and interpreting a request is about acquiring information rather than acting on the world, I modeled these as **Query goals**, placed first in a **sequential** chain, since nothing can physically happen before the request is known.

**Step 3 – Separate "reaching a state" from "running an action".** Transporting the meal, reaching/entering the room, and retrieving the dishes/meal are modeled as **Achieve goals**, because they describe a target condition to be brought about (robot at location, door open, item removed), consistent with the given "Check Room Patients" example. Pure signaling/triggering actions (indicating a meal, alerting on a mismatch) were modeled as **Perform**, since they are concrete actions whose success is the execution itself, not a persistent world-state.

**Step 4 – Handle the uncertainty about who can retrieve the meal.** The text explicitly says that whether the inpatient/companion/nurse can retrieve is derived from the inpatient record and companion presence, and that "this information is subject to uncertainty." This is unmistakably a **Query goal** (its only purpose is obtaining knowledge), separated from the act of retrieval itself and placed **before** it (sequential), because you must know who is capable before letting anyone try.

**Step 5 – OR vs. FALLBACK discipline.** Three places in the text present multiple cooperation alternatives using "or": (i) tray retrieval (inpatient/companion/nurse/robot), (ii) door opening (robot/human), (iii) dish collection (unassisted/robot‑robot/robot‑human). In none of these cases does the text state an explicit priority order ("try X first, then Y"); it merely enumerates valid alternatives whose availability depends on context. Per the strict FALLBACK rule, since no explicit ordering is stated, I used **OR decomposition** (not FALLBACK) in all three cases, with a neutral parallel ("#") runtime annotation between the alternatives (no obligation of order, no obligation to run both).

**Step 6 – Tracking and alerting are distinct, concurrent obligations.** "Track when/where retrieved" and "alert if wrong meal" are two different, always-active monitoring duties that both get evaluated at the moment of retrieval — there's no stated order between them, so they're AND-required but run in **parallel**.

**Step 7 – Door-opening scope.** "Opening the room door…" appears only within the dish-retrieval paragraph, immediately after the pickup-call sentence, so I scoped it to the dish-retrieval branch only, to avoid inventing an unstated requirement for the delivery branch.

**Step 8 – Locations and robot counts.** The description names exactly two locations: **Kitchen** and **Inpatient Room**. I never invented a third. Robot counts default to 1 (the servicing robot) except where the text explicitly says "another robot" / "cooperation of two robots," which I mapped to 2.

**Step 9 – Avoiding redundancy / zero-robot nodes.** I did not duplicate "capability determination" logic across the three human-cooperation alternatives — it's centralized in one Query goal. I did not include any node that requires zero robots (e.g., the raw act of a human eating or calling is not itself a system goal — only the robot's *reception* of that call/signal is).

**Step 10 – Single-child nodes.** A few goals (identify order, transport, determine capable agent, receive call) resolve into exactly one task. Since AND/OR decomposition is only meaningful for 2+ children, these are marked as leaf goals realized by a single task, with no AND/OR operator forced onto them.

## Logical Relationships

- **G1 -> G2, G10 [AND] (parallel)**
  - **Justification**: Both delivery and dish retrieval are independently mandated services; the mission requires both, and the text presents them as analogous, independently-triggered flows, so no order is imposed between them.

- **G2 -> G3, G4, G5, G9 [AND] (sequential)**
  - **Justification**: Knowing the order, moving the food, handing it off, and tracking/alerting are all necessary, complementary parts of "delivering food," each logically dependent on completion of the previous one.

- **G5 -> G6, G7 [AND] (sequential)**
  - **Justification**: Capability must be determined (query) before the retrieval is attempted/indicated (achieve); both are required.

- **G7 -> AT4, G8 [AND] (sequential)**
  - **Justification**: The correct meal must be indicated before (or as) it is actually retrieved, and both are required when multiple meals are carried.

- **G8 -> AT5, AT6, AT7, AT8 [OR] (parallel)**
  - **Justification**: "Cooperation with the inpatient, a companion, a nurse, or another robot" is an explicit, unordered set of alternatives — any one suffices, with no stated priority (so OR, not Fallback).

- **G9 -> AT9, AT10 [AND] (parallel)**
  - **Justification**: Tracking retrieval and alerting on mismatches are both mandatory and evaluated concurrently at the moment of retrieval, with no stated order between them.

- **G10 -> G11, G12, G14 [AND] (sequential)**
  - **Justification**: The call must be received before the room can be accessed, and the room accessed before dishes can be collected — all three are required.

- **G12 -> AT12, G13 [AND] (sequential)**
  - **Justification**: The robot must physically arrive at the room before the door-opening step occurs.

- **G13 -> AT13, AT14 [OR] (parallel)**
  - **Justification**: "Cooperation with another robot or a human" is an explicit, unordered alternative for opening the door.

- **G14 -> AT15, AT16, AT17 [OR] (parallel)**
  - **Justification**: "Unassisted, with the cooperation of two robots, or with the cooperation of robots and a human" is an explicit three-way unordered alternative for dish collection.

- **G3 -> AT1 [single realization]**
  - **Justification**: The query goal is fully realized by one concrete task (receiving/parsing the request); no AND/OR operator applies with a single child.

- **G4 -> AT2 [single realization]**
  - **Justification**: Transport is realized by one navigation task; no second alternative or complementary task is described.

- **G6 -> AT3 [single realization]**
  - **Justification**: Capability determination is realized by one concrete check task (record + room presence).

- **G11 -> AT11 [single realization]**
  - **Justification**: Receiving the pickup call is realized by one concrete reception task.
