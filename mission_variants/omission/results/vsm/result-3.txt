# Goal Model Design — Hospital Vital-Signs Monitoring Mission

## Step-by-step reasoning (design rationale)

1. **Root goal and mission feasibility.** The description gives an explicit primary/alternative/alternative pattern: *visit rooms with the assigned robot* → **if impossible in time** → *bring in additional robots* → **if still impossible** → *alert the manager*. This is a textbook nested **FALLBACK**, so the root `G1` uses `FALLBACK(FALLBACK(G2,G18),G19)`, which forces an **AND** relation among the three children (per the FALLBACK rule).

2. **Room-visiting pipeline.** "Visit every occupied room" presupposes first *knowing* which rooms are occupied (query), then *ordering* the visits so high-risk patients are seen in the first 15 minutes, then *executing* the per-room procedure. No alternative/failure is stated between these three, but a clear real-world order is — so I used sequential (`;`), not fallback.

3. **Per-room procedure** follows the paragraph order exactly: pre-entry checks → in-room engagement → vitals collection (with its own fallback chain) → exit/finalization. Sequential chain.

4. **Pre-entry checks.** Patient identification is required because of multi-bed rooms, and the availability/battery checks are each independent of each other but both logically require knowing *which* patient first. I modeled `identify ; (availability # battery)`.

5. **Identification** is explicitly "either... or..." → **OR** decomposition (ask vs. scan), no stated priority → parallel/either, not fallback.

6. **Battery handling** is an explicit IF-condition ("If there is not enough battery...") → **FALLBACK**(check battery, recharge+reassign), forcing AND.

7. **Vital-sign collection** also has an explicit IF/escalation chain ("failure... triggers... in case of non-response...") → nested **FALLBACK**(FALLBACK(measure, assess-by-questions), alert).

8. **Avoiding redundancy in vitals.** Infectious-disease, post-surgical and diabetic requirements overlap (both infectious and post-surgical need heart rate and oxygenation). Instead of three condition-specific branches that would duplicate "measure heart rate" and "measure oxygenation" twice, I modeled a single **OR**-decomposed goal over the five distinct vital-sign tasks (HR, BP, Temp, O2, Glucose); which subset is mandatory is determined by the patient's actual condition(s), which is captured in the justification rather than by duplicating goal nodes — this directly follows the instruction to represent each distinct intention once.

9. **Sterilization vs. actuator disinfection** are two independent, co-occurring hygiene triggers (room type vs. physical contact) — not alternatives — so they're **AND**/parallel siblings, not OR.

10. **Single-child goals.** A few goals (determine occupied rooms, check availability, assess-by-questions, alert nurse/doctor, prioritize order) map to exactly **one** concrete action in the text. Rather than inventing a second artificial child just to satisfy a "minimum two" rule, I kept these as atomic goal→task links (relation marked **AND, trivial**) — manufacturing a redundant sibling would violate the explicit no-redundancy/no-fabrication instructions, which I weighted as the stronger constraint.

11. **Zero-robot filter.** "Determine no robot combination can complete the mission" and "alert the manager" are kept because the *robot* performs the determination/sending; the manager is only the recipient, not the actor — so these tasks are robot-performed and stay in the model.

## Logical Relationships

- **G1 -> G2, G18, G19 [AND] FALLBACK(FALLBACK(G2,G18),G19)**
  - **Justification**: Explicit primary/alternative/alternative chain — visit with assigned robot; if infeasible in time, add robots; if still infeasible, alert the manager.

- **G2 -> G3, G4, G5 [AND] (sequential)**
  - **Justification**: Must know which rooms are occupied, then establish visiting priority, before executing the visit procedure — a necessary left-to-right order, though not an IF-triggered fallback.

- **G5 -> G6, G11, G12, G16 [AND] (sequential)**
  - **Justification**: Follows the description's own chronological structure: before entering, once inside, on vitals failure, once checked.

- **G6 -> G7, G8, G9 [AND] (G7 ; (G8 # G9))**
  - **Justification**: Identification must precede the patient-specific availability check (multi-bed rooms); battery check is independent of patient identity and can run alongside availability checking.

- **G7 -> AT3, AT4 [OR] (parallel/either)**
  - **Justification**: "either by asking or by scanning" — explicit alternatives, no stated priority.

- **G9 -> AT6, G10 [AND] FALLBACK(AT6,G10)**
  - **Justification**: "If there is not enough battery..." is an explicit IF-condition triggering an alternative path.

- **G10 -> AT7, AT8 [AND] (parallel)**
  - **Justification**: Recharging the robot and reassigning its tasks are independent actions with no stated order.

- **G11 -> AT9, AT10, AT11 [AND] (sequential)**
  - **Justification**: Explicit listed order: approach, then announce, then instruct.

- **G12 -> G13, G14, G15 [AND] FALLBACK(FALLBACK(G13,G14),G15)**
  - **Justification**: "Failure...should trigger a set of questions...In case of non-response, an alert..." is an explicit nested escalation chain.

- **G13 -> AT12, AT13, AT14, AT15, AT16 [OR] (parallel)**
  - **Justification**: The applicable subset depends on the patient's condition(s) (infectious disease, post-surgical, diabetes); OR lets the applicable task(s) fulfill the goal without duplicating shared measurements (e.g., heart rate) across condition-specific branches.

- **G16 -> AT19, G17, AT22 [AND] (sequential)**
  - **Justification**: "Once the patient is checked...mark it as done and proceed to the next room," with sanitation occurring at the moment of exit, before moving on.

- **G17 -> AT20, AT21 [AND] (parallel)**
  - **Justification**: Sterilization (room-type triggered) and actuator disinfection (contact triggered) are independent requirements that can co-occur — not mutually exclusive alternatives.

- **G18 -> AT23, AT24 [AND] (sequential)**
  - **Justification**: Available robots must be identified before they can be assigned.

- **G19 -> AT25, AT26 [AND] (sequential)**
  - **Justification**: Infeasibility must be determined before the manager is alerted.

**Zero-robot check**: every leaf task in the model is executed by a robot (the alert/notification tasks are *sent* by the robot; the nurse/doctor/manager are recipients, not actors), so none were excluded under the zero-robot rule.

A note on methodology: five goals (G3, G4, G8, G14, G15) decompose into a single task rather than two, because the description only specifies one concrete action for each — introducing a second, invented child would have violated the no-redundancy/no-fabrication requirement more directly than relaxing the "minimum two children" convention for these atomic cases.
