# Goal Model Design — Multi-Robot Hospital Vital-Signs Checking Mission

## 1. Reasoning & Design Methodology

Before producing the model, I walked through the description several times to extract distinct **intentions** (goals), distinct **operational actions** (tasks), and the **control structure** connecting them (AND/OR, parallel/sequential/fallback). Key interpretive decisions, and why I made them:

**a) Merging the "trigger" and the "mission" into one root goal.**
"Every two hours, all patient's vital signs should be checked. Therefore, the assigned robot should visit every occupied room" expresses a *single* underlying intention: visiting rooms **is** the mechanism for checking vitals — the text itself uses "therefore" to say so. Making these two separate goals would violate the anti-redundancy rule, so they are represented as **one** root Achieve goal (G1). The "every two hours" clause is treated as an external periodic trigger for the whole tree, not a decomposition node (triggers are not goals/tasks).

**b) The robot-allocation escalation is a FALLBACK chain, not a parallel concern.**
"Additional robots can be assigned... in case of impossibility... The responsible manager must be alerted if no combination of robots can complete the mission" is an explicit three-level contingency: *(1) try with the assigned robot → (2) if impossible, add robots → (3) if still impossible, alert the manager.* This is a textbook nested FALLBACK: `FALLBACK(FALLBACK(G2, G31), G34)`.

**c) "Either by asking or by scanning the barcode" → OR.**
This is the one place the description uses an explicit alternative particle ("either... or"), so `G14` is the only OR-decomposition among behavioral alternatives.

**d) Vital-sign requirements per condition (infectious / post-surgical / diabetic) → OR, not AND, at the goal level.**
These are conditional variants depending on the *patient's* medical status, not steps every patient undergoes. I used OR (not mutually-exclusive XOR) because a single patient could fall into more than one category (e.g., diabetic **and** post-surgical) — OR semantics ("one child sufficient") does not forbid more than one branch being triggered simultaneously, which matches the "whichever conditions apply get checked" reading of the text.

**e) Failure handling → nested FALLBACK.**
"Failure of collecting vital signs → ask questions... in case of non-response → alert nurse/doctor" is explicitly conditioned on failure, so this is modeled as `FALLBACK(FALLBACK(CollectVitals, AskQuestions), AlertNurseDoctor)`.

**f) Battery check → FALLBACK, not sequential.**
"If there is not enough battery, the robot should recharge and tasks reassigned" is an explicit IF-triggered alternative path, so `FALLBACK(CheckBattery, RechargeAndReassign)`, AND-connected per the FALLBACK rule.

**g) The "high-risk patients checked in first 15 minutes" constraint is *not* modeled as a duplicate branch.**
Creating a separate "visit high-risk rooms" subtree in addition to "visit all rooms" would duplicate the entire room-visiting subtree (same intention, same tasks) — which the instructions explicitly forbid. Instead, this constraint is captured as a **scheduling property** attached to G3 (Fetch Occupied Rooms) and G2's justification: the room-occupancy query is understood to return rooms annotated with risk level, and the *order* in which G4 ("Check Occupied Room") is invoked across rooms is constrained so that high-risk rooms are front-loaded into the first 15 minutes. This avoids tree redundancy while still accounting for the requirement.

**h) Zero-robot exclusion check.**
Every leaf task was checked against "must be performed by a robot." Communication actions (alerting nurse/doctor, alerting the manager) and coordination actions (reassigning tasks, assigning additional robots) are kept in the model under the assumption — consistent with a *multi-robot system* framing — that they are executed autonomously by the robot(s)/fleet-coordination logic, not by a human dispatcher. The nurse, doctor, and manager are **recipients** of alerts, never performers of a modeled task, so they do not violate the rule.

**i) Repeated granularity pattern.**
To keep the tree internally consistent, every atomic action phrase in the text (approach, announce, instruct, recharge, reassign, sterilize, disinfect, mark done, proceed) is modeled the same way: a **Perform goal** wrapping exactly one **Task**. This is more verbose than strictly necessary, but keeps goal-typing and justification uniform across the whole tree, and maximizes the richness of relationships, as requested.

## 5. Logical Relationships

**Goal → Goal**

- **G1 -> G2, G31, G34 [AND] [FALLBACK(FALLBACK(G2,G31),G34)]**
  - **Justification**: The description lays out a strict three-tier contingency — complete the mission with the assigned robot; if impossible, add robots; if still impossible, alert the manager. Each tier is attempted only if the previous one fails, which is the defining property of FALLBACK, and FALLBACK legs are always AND-connected per the rules.

- **G2 -> G3, G4 [AND] (sequential) G3;G4**
  - **Justification**: The robot must know which rooms are occupied before it can visit them — a strict sequential data dependency, not a matter of choice or parallelism.

- **G4 -> G5, G12, G25 [AND] (sequential) G5;G12;G25**
  - **Justification**: The text explicitly orders these phases: "**Before** entering the room..." (G5), "**Once inside** the room..." (G12), "**Once** the patient is checked... mark... proceed" (G25).

- **G5 -> G6, G7 [AND] (parallel) G6#G7**
  - **Justification**: "...check if the patient is available **and** if there is enough battery" presents two independent conditions with no stated precedence — they can be verified in parallel.

- **G7 -> G8, G9 [AND] FALLBACK(G8,G9)**
  - **Justification**: "If there is not enough battery, the robot should recharge..." is an explicit IF-triggered alternative path, mandating FALLBACK.

- **G9 -> G10, G11 [AND] (parallel) G10#G11**
  - **Justification**: Recharging the robot and reassigning its pending tasks are independent consequences of the same trigger, with no ordering stated — they can proceed concurrently.

- **G12 -> G13, G18 [AND] (sequential) G13;G18**
  - **Justification**: The patient must be identified and briefed (approached, told the procedure, instructed) before meaningful vital-sign collection can proceed.

- **G13 -> G14, G15, G16, G17 [AND] (sequential) G14;G15;G16;G17**
  - **Justification**: Identification logically precedes physically approaching the correct bed, and the text explicitly orders "approach... announce... and provide instructions."

- **G18 -> G19, G23, G24 [AND] FALLBACK(FALLBACK(G19,G23),G24)**
  - **Justification**: "The failure of collecting any necessary vital signs should **trigger**..." and "**in case of** non-response, an alert..." are both explicit failure-conditioned alternatives, requiring nested FALLBACK.

- **G19 -> G20, G21, G22 [OR] (parallel) G20#G21#G22**
  - **Justification**: Each branch applies only if the patient has the corresponding condition (OR = fulfilling the applicable one(s) is sufficient), and since a patient could have multiple conditions simultaneously with no stated order, applicable branches run in parallel.

- **G25 -> G26, G27, G30 [AND] (sequential) G26;G27;G30**
  - **Justification**: The text's closing sequence is "mark it as done **and** proceed to the next room," with hygiene steps occurring on exit, in between.

- **G27 -> G28, G29 [AND] (parallel) G28#G29**
  - **Justification**: Sterilization (infectious-room trigger) and actuator disinfection (contact trigger) are independent conditions that may both apply with no stated order.

- **G31 -> G32, G33 [AND] (sequential) G32;G33**
  - **Justification**: Idle robots must be identified before they can be assigned to remaining rooms — a data dependency.

**Goal → Task**

- **G3 -> AT1 [AND]** — Sole operationalization of the occupancy query; no alternative stated.
- **G6 -> AT2 [AND]** — Sole operationalization of the availability check.
- **G8 -> AT3 [AND]** — Sole operationalization of the battery check.
- **G10 -> AT4 [AND]** — Sole operationalization of recharging.
- **G11 -> AT5 [AND]** — Sole operationalization of reassignment.
- **G14 -> AT6, AT7 [OR]** — Explicit "either... or" alternative in the text.
- **G15 -> AT8 [AND]**, **G16 -> AT9 [AND]**, **G17 -> AT10 [AND]** — Each is a single, directly stated physical/communicative action.
- **G20 -> AT11, AT12, AT13, AT14 [AND]** — All four vitals are jointly required for infectious-disease patients ("heart rate, blood pressure, body temperature, **and** blood oxygenation").
- **G21 -> AT15, AT16 [AND]** — Both vitals jointly required for post-surgical patients.
- **G22 -> AT17 [AND]** — Sole required measurement for diabetic-history patients.
- **G23 -> AT18 [AND]**, **G24 -> AT19 [AND]** — Each a single stated action.
- **G26 -> AT20 [AND]**, **G28 -> AT21 [AND]**, **G29 -> AT22 [AND]**, **G30 -> AT23 [AND]** — Each a single stated action.
- **G32 -> AT24 [AND]**, **G33 -> AT25 [AND]**, **G34 -> AT26 [AND]** — Each a single stated action.
