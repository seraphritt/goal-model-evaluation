# Goal Model Design: Hospital Multi-Robot Vital-Signs Monitoring Mission

## Step-by-Step Reasoning

Before building the tree, I went through the description sentence by sentence to classify each statement as: (a) a periodic/overall trigger, (b) a precondition, (c) a normal operational step, (d) a condition-triggered alternative (→ FALLBACK), (e) an explicit either/or choice (→ OR), (f) an explicit ordered sequence (→ sequential), (g) an independent pair of checks (→ parallel), or (h) pure context (zero-robot, not modeled).

**Key interpretive decisions (and why):**

1. **Root split — FALLBACK, not parallel.** My first instinct was to put "visit rooms" and "manage robot sufficiency/manager alert" as two parallel top-level goals. On reflection, the text explicitly conditions the second branch on failure of the first ("in case of **impossibility** of performing the mission in the required time"). That's precisely the IF/exception pattern the instructions require to be modeled as FALLBACK, not parallel. So **G1 = FALLBACK(G2, G14)**: normal mission execution first, resource-escalation only if that proves infeasible.

2. **Nested FALLBACK for escalation.** "Additional robots can help" (first fallback) and "alert the manager if no combination works" (second-level fallback) is a textbook nested FALLBACK: `FALLBACK(AT_add_robots, AT_alert_manager)`.

3. **High-risk timing constraint.** "All high-risk patients must be checked in the first 15 minutes" describes the *same intention* as visiting/checking rooms — duplicating the entire per-room procedure into a "high-risk branch" and a "normal branch" would violate the no-redundancy rule (same intention, two nodes). Instead, I modeled it as a distinct **scheduling task** (AT1) that precedes the per-room execution goal, sequentially: the robot(s) must first determine a visiting order that front-loads high-risk rooms, then execute the (single, non-duplicated) room-visit procedure.

4. **Dual preconditions (availability + battery).** No order is stated between checking availability and checking battery, and both are independent world facts — **parallel (#)**. Each, however, has an explicit IF-triggered alternative ("if not available → return in 5 min"; "if not enough battery → recharge & reassign") — **FALLBACK** for each individually.

5. **Patient identification.** "Either by asking or by scanning" is a plain alternative with no stated priority or failure-dependency — **OR decomposition**, runtime parallel (no obligation of order).

6. **Approach → announce → instruct.** Explicit order given — **AND + sequential**.

7. **Vital-sign collection and condition-dependence.** Heart rate, blood pressure, temperature, oxygenation and glucose are each required only for certain patient conditions (infectious / post-surgical / diabetic), and a patient can match more than one condition. A strict AND would force every patient through every measurement; a strict OR captures that "whichever subset applies is sufficient," while still allowing more than one to be executed for a patient with multiple conditions — this matches OR's definition better than AND. I kept each vital sign as a single, non-duplicated task (instead of nesting it under three condition-named sub-goals) specifically to avoid repeating "Measure Heart Rate" under both "infectious" and "post-surgical" branches, which would have violated the no-redundancy instruction.

8. **Measurement failure → questions.** Explicit condition-triggered alternative → **FALLBACK**(measure physically, ask assessment questions).

9. **Sterilization / actuator disinfection.** Both are conditionally triggered (by room type / by physical contact respectively) but are not alternatives to anything else nor dependent on a prior step's *failure* — so FALLBACK doesn't fit. I kept them as AND-children with the condition captured explicitly in the justification, which is the best fit available within a strict AND/OR vocabulary.

10. **Goal typing.** Actions whose purpose is literally "find out X" (who the patient is, what their vitals are) were typed as **Query**, not Achieve, even though they sit inside an achieve-oriented parent — this follows the book definition closely ("obtain knowledge/data" vs. "reach a target state").

11. **Zero-robot content excluded.** "Hospital rooms may have one or more beds" is pure context (justifies *why* identification is needed) and is not modeled as a node, since no robot performs this as an action.

## Goal Model Tree (overview)

```
G1 Execute Periodic Vital-Signs Monitoring Mission [FALLBACK(G2,G14)] (AND)
├─ G2 Visit & Check Vital Signs of All Occupied Rooms [AT1;G3] (AND)
│   ├─ AT1 Schedule Room-Visit Order Prioritizing High-Risk Patients
│   └─ G3 Execute Room Visit Procedure [G4;G8;G9;G13] (AND)
│       ├─ G4 Verify Pre-Entry Conditions [G5#G6] (AND)
│       │   ├─ G5 Confirm Patient Availability [FALLBACK(AT2,AT3)] (AND)
│       │   │   ├─ AT2 Check Patient Availability
│       │   │   └─ AT3 Wait & Retry Visit in 5 Minutes
│       │   └─ G6 Confirm Sufficient Battery [FALLBACK(AT4,G7)] (AND)
│       │       ├─ AT4 Check Battery Level
│       │       └─ G7 Recharge Battery & Reassign Pending Tasks [AT5#AT6] (AND)
│       │           ├─ AT5 Recharge Robot Battery
│       │           └─ AT6 Reassign Pending Tasks to Other Robots
│       ├─ G8 Identify Correct Patient in Room [AT7#AT8] (OR)
│       │   ├─ AT7 Ask Patient to Confirm Identity
│       │   └─ AT8 Scan Patient's Barcode
│       ├─ G9 Conduct Patient Interaction & Vital-Signs Collection [G10;G11;AT18] (AND)
│       │   ├─ G10 Engage Patient Before Procedure [AT9;AT10;AT11] (AND)
│       │   │   ├─ AT9 Approach Patient
│       │   │   ├─ AT10 Announce Procedure
│       │   │   └─ AT11 Provide Instructions
│       │   ├─ G11 Collect Patient's Required Vital Signs [FALLBACK(G12,AT17)] (AND)
│       │   │   ├─ G12 Measure Required Vital Signs [AT12#AT13#AT14#AT15#AT16] (OR)
│       │   │   │   ├─ AT12 Measure Heart Rate
│       │   │   │   ├─ AT13 Measure Blood Pressure
│       │   │   │   ├─ AT14 Measure Body Temperature
│       │   │   │   ├─ AT15 Measure Blood Oxygenation
│       │   │   │   └─ AT16 Measure Glucose Level
│       │   │   └─ AT17 Ask Assessment Questions for Failed Vital Signs
│       │   └─ AT18 Disinfect Actuators After Patient Contact
│       └─ G13 Finalize Room Visit [AT19;AT20;AT21] (AND)
│           ├─ AT19 Mark Patient's Check as Done
│           ├─ AT20 Sterilize Robot (infectious-disease rooms)
│           └─ AT21 Proceed to Next Room
└─ G14 Ensure Mission Completion Despite Resource Constraints [FALLBACK(AT22,AT23)] (AND)
    ├─ AT22 Assign Additional Robots
    └─ AT23 Alert Responsible Manager
```

## Logical Relationships

- **G1 -> G2, G14 [AND] FALLBACK(G2, G14)**
  - **Justification**: The mission is normally fulfilled by visiting and checking all rooms (G2); resource escalation (G14) is explicitly triggered only "in case of impossibility of performing the mission in the required time," matching the FALLBACK pattern exactly.

- **G2 -> AT1, G3 [AND] (sequential: AT1;G3)**
  - **Justification**: The visiting order must be established (prioritizing high-risk patients, per the explicit 15-minute rule) before the robot executes the room-visit procedure.

- **G3 -> G4, G8, G9, G13 [AND] (sequential: G4;G8;G9;G13)**
  - **Justification**: The description gives an explicit temporal order for a room visit: pre-entry checks, then identification, then interaction/vitals, then finalization.

- **G4 -> G5, G6 [AND] (parallel: G5#G6)**
  - **Justification**: "Check if the patient is available... **and** if there is enough battery" — two independent checks with no stated order between them.

- **G5 -> AT2, AT3 [AND] FALLBACK(AT2, AT3)**
  - **Justification**: Availability checking is the normal path; "come back in 5 minutes" is the explicit alternative triggered only if the check fails (patient unavailable).

- **G6 -> AT4, G7 [AND] FALLBACK(AT4, G7)**
  - **Justification**: Battery checking is the normal path; recharging and reassigning tasks is the explicit alternative triggered only if the check fails (insufficient battery).

- **G7 -> AT5, AT6 [AND] (parallel: AT5#AT6)**
  - **Justification**: "The robot should recharge **and** the tasks need to be reassigned" — two required actions with no stated order, so they may proceed together.

- **G8 -> AT7, AT8 [OR] (parallel: AT7#AT8)**
  - **Justification**: "Either by asking or by scanning" is an explicit alternative (one suffices); no order or failure-dependency is stated, so no FALLBACK is used.

- **G9 -> G10, G11, AT18 [AND] (sequential: G10;G11;AT18)**
  - **Justification**: The patient must be engaged before vitals are collected, and the contact-disinfection duty explicitly occurs "afterwards" — i.e., after the contact-causing activity.

- **G10 -> AT9, AT10, AT11 [AND] (sequential: AT9;AT10;AT11)**
  - **Justification**: "Approach the patient, announce the procedure..., provide instructions" is explicitly ordered.

- **G11 -> G12, AT17 [AND] FALLBACK(G12, AT17)**
  - **Justification**: Physical measurement is attempted first; asking assessment questions is the explicit alternative triggered only by measurement failure ("the failure of collecting any necessary vital signs should trigger a set of questions").

- **G12 -> AT12, AT13, AT14, AT15, AT16 [OR] (parallel: AT12#AT13#AT14#AT15#AT16)**
  - **Justification**: Different conditions (infectious disease, post-surgical, diabetes) require different, possibly overlapping subsets of these five measurements; OR lets the condition-appropriate subset(s) suffice without forcing all five on every patient, and no order is stated among them.

- **G13 -> AT19, AT20, AT21 [AND] (sequential: AT19;AT20;AT21)**
  - **Justification**: "Mark it as done and proceed to the next room," with sterilization occurring at the point of "coming out" of an infectious-disease room — i.e., after marking done, upon exit, before moving on.

- **G14 -> AT22, AT23 [AND] FALLBACK(AT22, AT23)**
  - **Justification**: Adding robots is attempted first; alerting the manager is the explicit alternative only "if no combination of robots can complete the mission" — a nested escalation matching FALLBACK's definition.
