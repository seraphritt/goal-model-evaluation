# Multi-Robot Hospital Vital-Signs Mission — Goal Model Analysis

## Step-by-Step Reasoning

**1. Identifying the top-level intention.** The mission is cyclical ("every two hours") and conditional on feasibility ("additional robots... if no combination of robots can complete the mission"). I modeled the root goal (**G1**) as an *Achieve* goal whose target condition absorbs the periodicity (it is a scheduling trigger, not a robot action, so it is not a separate node) and wraps the whole mission in a **nested FALLBACK**: first try to visit/check all rooms with the currently assigned robot(s) (G2); if time-infeasible, add robots (G19); if still infeasible with any combination, alert the manager (G20). This is a textbook case for FALLBACK because the text gives an explicit IF-condition ("in case of impossibility", "if no combination of robots can complete").

**2. Visiting rooms.** "Visit every occupied room" (G2) is decomposed into *moving* (a Task, AT1) and *executing the room procedure* (G3), sequentially, since you cannot check a room before arriving at it.

**3. The room procedure has three explicit temporal phases** stated verbatim in the text: "**Before** entering the room..." / "**Once inside** the room..." / "**Once** the patient is checked...". This explicit textual ordering justifies a **sequential** (not fallback — there is no failure condition between these phases) AND-decomposition of G3 into G4 (pre-entry), G9 (in-room), G17 (post-check).

**4. Pre-entry checks (G4).** The text joins "check availability... **and**... battery" with a conjunction and no stated order → **parallel**. Patient identification (G6) is explicitly an OR ("**either** by asking **or** by scanning"), with no priority stated, so I used the "possibility of parallel" (`#`) annotation rather than fabricating an order. Battery sufficiency (G7) contains an explicit IF-condition ("**If** there is not enough battery...") → **FALLBACK**, and per the FALLBACK rule its two branches are AND-related.

**5. In-room procedure (G9).** The engagement sequence (approach, announce, instruct) is given in explicit left-to-right order in the text → sequential AND (G10). Vital-sign collection (G11) has an explicit failure trigger ("**the failure** of collecting... should **trigger**...") → FALLBACK(G12, G16), and inside G16 a second, nested failure trigger ("**in case of** non-response...") → nested FALLBACK(AT16, AT17).

**6. Condition-specific vital signs (G12).** Infectious-disease, post-surgical, and diabetic requirements are independent and **not mutually exclusive** (a patient could be both diabetic and post-surgical) — this rules out AND (not everyone needs every check) and rules out a strict XOR-alternative reading; **OR** (inclusive "at least one, possibly more") is the correct fit. To avoid redundancy, **Check Heart Rate (AT11)** and **Check Blood Oxygenation (AT14)** are *reused* under both the infectious-disease and post-surgical branches rather than duplicated as new nodes, per the anti-redundancy instruction.

**7. Hygiene protocols (G18).** Sterilization and actuator disinfection are each triggered by an *independent* condition (infectious-disease room / physical contact) that can co-occur → **OR**, parallel.

**8. Zero-robot filtering.** "Hospital rooms may have one or more beds" is pure background information (no action), so it produces no node — it only *justifies* why G6 (patient identification) exists. All retained tasks involve an action a robot (or its communication/sensing/coordination module) executes; nothing purely administrative/zero-robot was kept.

**9. Collapsing trivial nodes.** Where the text names only **one** concrete realization with no alternative or combination (e.g., diabetic check → glucose only; alert manager; deploy additional robots), I attached the Task directly rather than inventing an artificial second sibling just to satisfy a "minimum two" convention — fabricating content was explicitly discouraged. These are flagged as trivial/direct AND relations with Runtime `-`.

## Logical Relationships

- **G1 -> G2, G19, G20 [AND][FALLBACK(FALLBACK(G2,G19),G20)]**
  - **Justification**: The mission first attempts to visit/check all rooms with assigned robots (G2); only "in case of impossibility of performing the mission in the required time" are additional robots assigned (G19); only if "no combination of robots can complete the mission" is the manager alerted (G20). Two explicit IF-conditions → nested Fallback; AND is mandated between Fallback branches.

- **G2 -> AT1, G3 [AND](sequential)**
  - **Justification**: The robot must arrive at the room (AT1) before the in-room procedure (G3) can start; both are necessary.

- **G3 -> G4, G9, G17 [AND](sequential)**
  - **Justification**: The text explicitly stages the visit into "before entering", "once inside", and "once checked" — explicit temporal order, all stages required.

- **G4 -> G5, G7 [AND](parallel)**
  - **Justification**: "must check if the patient is available... and if there is enough battery" — joined conjunctively with no stated order.

- **G5 -> G6, AT4 [AND](sequential)**
  - **Justification**: The correct patient must be identified before their specific availability is checked (implied order in a multi-bed room).

- **G6 -> AT2, AT3 [OR](parallel)**
  - **Justification**: "either by asking or by scanning" — explicit OR particle, no order/failure condition stated.

- **G7 -> AT5, G8 [AND][FALLBACK(AT5,G8)]**
  - **Justification**: "If there is not enough battery..." is an explicit IF-condition triggering recharge+reassignment as an alternative.

- **G8 -> AT6, AT7 [AND](parallel)**
  - **Justification**: "recharge and the tasks need to be reassigned" — conjunctive, no stated order.

- **G9 -> G10, G11 [AND](sequential)**
  - **Justification**: Engagement actions are narrated before the vital-sign-collection narrative; both required.

- **G10 -> AT8, AT9, AT10 [AND](sequential)**
  - **Justification**: "approach... announce... and provide instructions" — explicit left-to-right order.

- **G11 -> G12, G16 [AND][FALLBACK(G12,G16)]**
  - **Justification**: "The failure of collecting any necessary vital signs should trigger..." — explicit failure-triggered alternative.

- **G12 -> G13, G14, G15 [OR](parallel)**
  - **Justification**: The three condition-based branches are independent and can co-occur in one patient; OR captures "one or more applies" without forcing all three (AND) or exactly one (alternatives).

- **G13 -> AT11, AT12, AT13, AT14 [AND](parallel)**
  - **Justification**: Conjunctive list "heart rate, blood pressure, body temperature, and blood oxygenation"; no order given.

- **G14 -> AT11, AT14 [AND](parallel)**
  - **Justification**: Conjunctive list "heart rate and blood oxygenation"; tasks reused from G13 to avoid redundancy.

- **G15 -> AT15 [AND] (trivial, single-child)**
  - **Justification**: Only glucose-level checking is named for diabetic patients; no alternative is described.

- **G16 -> AT16, AT17 [AND][FALLBACK(AT16,AT17)]**
  - **Justification**: "In case of non-response, an alert should be sent" — nested explicit failure condition.

- **G17 -> AT18, G18 [AND](sequential)**
  - **Justification**: "mark it as done" is stated as the immediate closing action, with hygiene protocols as the subsequent closing step; both required when applicable.

- **G18 -> AT19, AT20 [OR](parallel)**
  - **Justification**: Sterilization and actuator disinfection are triggered by independent, possibly co-occurring conditions (infectious room vs. patient contact).

- **G19 -> AT21 [AND] (trivial, single-child)**
  - **Justification**: "Additional robots can be assigned" names a single operational action, no further decomposition given.

- **G20 -> AT22 [AND] (trivial, single-child)**
  - **Justification**: "The responsible manager... must be alerted" names a single operational action.

---

**Note on method**: wherever the text named only one concrete realization for a goal (G15, G19, G20), I attached it as a single Task rather than inventing a second branch to force a "minimum two" structure, since fabricating unstated content would misrepresent the mission description. Shared tasks (AT11, AT14) were reused across sibling goals rather than duplicated, per the anti-redundancy requirement, making this tree technically a DAG at those two points.
