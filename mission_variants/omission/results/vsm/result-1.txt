# Hospital Vital‑Signs Monitoring Mission — Goal Model

## Step‑by‑Step Reasoning (Mission Designer's Analysis)

Before building the model, I walked through the description multiple times to separate **intentions** (goals), **operational steps** (tasks), **decomposition logic** (AND/OR), and **execution order** (parallel/sequential/fallback). Key design decisions:

1. **Root goal & periodicity.** "Every two hours... vital signs should be checked" is a *recurring trigger*, not a decomposition operator. I modeled the tree as **one mission cycle**, with the 2‑hour periodicity noted as an external re‑invocation policy on the root goal (standard practice — temporal triggers sit outside AND/OR/runtime semantics).

2. **Fallback detection.** I scanned for explicit IF‑statements / "normal path → alternative path" patterns and used `FALLBACK` **only** there:
   - Patient unavailable → come back in 5 min
   - Insufficient battery → recharge & reassign
   - Vital‑sign collection fails → assessment questions
   - Mission infeasible in time → add robots → still infeasible → alert manager
   
   I explicitly avoided fallback for the "ask OR scan barcode" choice, because no order/precedence is stated — that is a pure **OR** alternative, not a failure‑triggered one.

3. **Sequential vs. parallel.** Wherever the text lists actions in an explicit order ("approach... announce... provide instructions"; "mark it as done and proceed") I used `;`. Wherever two conditions/actions are joined by "and" with **no stated order** (availability vs. battery check; the four infectious‑disease vitals; recharge vs. reassignment) I used `#`.

4. **Avoiding redundancy — the high‑risk 15‑minute rule.** Re‑checking high‑risk patients using a *full duplicate subtree* of the room‑visit procedure would duplicate the same intention ("check a room's patient") twice in the tree. Instead, I modeled the 15‑minute constraint as a **scheduling task** (`AT1`) that orders room visits (high‑risk rooms first) before the single, shared "visit room" procedure executes. This satisfies the requirement without violating the non‑redundancy rule.

5. **Goal typing.**
   - **Query** was used only for "Identify Correct Patient" — its purpose is purely informational (which bed/patient), matching the "Fetch Occupied Rooms" example.
   - **Achieve** was used wherever a persistent world‑state must be reached and verified (patient available, battery sufficient, vitals collected, room processed) — matching "Check Room Patients."
   - **Perform** was used for simple, action‑execution composites with no monitored target state beyond "did it happen" (approach/announce/instruct; disinfect/mark‑done/sterilize/proceed) — matching "Enter the Car."

6. **Zero‑robot exclusion.** "Tasks need to be reassigned" and "alert the manager" are passive constructions, but in a multi‑robot system these are executed by the robot/fleet‑coordination agent (sending the alert, re‑allocating duties), not by the manager — so they remain in the model, each tied to an acting robot.

7. **Location rule.** I only used terms explicitly present in the text: **"Room"** (from "Hospital rooms...") and **"Hospital"** (general facility‑level actions like scheduling, recharging, reassigning, alerting — none of which has a more specific location named in the description).

8. **Variable robot counts.** Only two tasks have inherently unspecified robot counts in the text ("additional robots," "tasks reassigned") — these use the `[1, n]` range notation as instructed; all other tasks are explicitly single‑robot ("the robot...").

## Logical Relationships

- **G1 -> G2, AT25, AT26 [AND] FALLBACK(FALLBACK(G2, AT25), AT26)**
  - **Justification**: The mission is first attempted with the assigned robot(s) (G2); if timing cannot be met, additional robots are added (AT25) as an explicit contingency; if still infeasible, the manager is alerted (AT26) as the final fallback. Fallback branches are always AND‑related by definition.

- **G2 -> AT1, G3 [AND] (sequential: AT1 ; G3)**
  - **Justification**: Room‑visit order must be planned (prioritizing high‑risk patients within 15 minutes) before the robot actually executes the room‑by‑room procedure.

- **G3 -> G4, AT9, G10 [AND] (sequential: G4 ; AT9 ; G10)**
  - **Justification**: The text's explicit split between "before entering the room" and "once inside the room" fixes the order: pre‑entry checks, then entry, then the in‑room procedure.

- **G4 -> G5, G8 [AND] (parallel: G5 # G8)**
  - **Justification**: "check if the patient is available... and if there is enough battery" — both required, no stated order, so they may occur in parallel.

  - **Justification**: Explicit IF‑statement in the text ("If the patient is not available...") triggers the alternative action.
