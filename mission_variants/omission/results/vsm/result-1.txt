# Multi-Robot Hospital Vital-Signs Mission — Goal Model Analysis

## Step-by-Step Reasoning

**1. Identifying the top-level objective.** The mission is periodic ("every two hours") and is fulfilled by visiting every occupied room. Since reaching that state requires planning/acting over time, this is an **Achieve** goal (G1).

**2. Finding the FALLBACK triggers.** I scanned the text for explicit conditional language ("if...", "in case of...", failure/non-response/impossibility):
- "If there is not enough battery → recharge + reassign" → FALLBACK
- "The failure of collecting vital signs → trigger questions" → FALLBACK
- "In case of non-response → alert nurse/doctor" → nested FALLBACK
- "in case of impossibility of performing the mission → additional robots" → FALLBACK
- "if no combination of robots can complete the mission → alert manager" → nested FALLBACK

These are the **only** places I used FALLBACK — everywhere else the text either gives no explicit order (→ parallel `#`) or gives an explicit narrative order without a failure/condition trigger (→ sequential `;`).

**3. Finding OR vs AND cues.** "Either by asking **or** by scanning" is a textbook OR (alternative means to the same end). "Patients subject to X must be checked for Y; patients subject to Z must be checked for W" is condition-dependent branching → modeled as OR (the applicable branch depends on the patient's condition, not all patients need all branches). Conjunctive lists ("heart rate, blood pressure, body temperature, and blood oxygenation") are AND (all required jointly).

**4. Determining sequence vs parallelism.** "Before entering... Once inside... Once the patient is checked..." gives a clear narrative sequence at the macro level (prepare → enter/interact → collect vitals → finalize), so I used sequential (`;`) there. Within each phase, when the text just conjoins items with "and" without declaring an order (e.g., "check patient availability, **and** if there is enough battery"), I used parallel (`#`), since the text neither forces nor forbids concurrent execution.

**5. Goal typing.** 
- Checks that only retrieve information (availability, battery level, patient ID, vital-sign values) → **Query**.
- Composite objectives with a clear target state (visiting, preparing, finalizing, recharging, getting help) → **Achieve**.
- The approach/announce/instruct sequence is pure action execution with no state to verify beyond "was it done" → **Perform**.

**6. Avoiding redundancy.** "Collect Heart Rate" and "Collect Blood Oxygenation" are reused as the same task under both the infectious-disease and post-surgical branches rather than duplicated, since they represent the same intention/action.

**7. Removing zero-robot nodes.** Everything retained in the tree is performed by a robot (the assigned robot, or additional robots in the fallback branch). I deliberately avoided creating a dangling goal for "the mission requirement" itself (every two hours) since that's a trigger condition, not a robot-performed node — it's folded into G1's target condition instead.

**8. Single-child decomposition problem.** Where a goal would only have one child (e.g., "Check Diabetes Vitals" → only glucose), I did **not** create a wasted intermediate goal; instead the task (`AT13`) is placed directly as a sibling under the OR-parent (`G12`), alongside the two multi-task branches. Same logic applied to "Alert Manager," which is a simple one-off task (`AT22`), not a goal.

## Logical Relationships

- **G1 -> G2, G16, AT22 [AND] [FALLBACK(FALLBACK(G2,G16),AT22)]**
  - **Justification**: The text describes the normal mission (visit rooms), then an explicit escalation ("additional robots can be assigned in case of impossibility"), then a further explicit escalation ("the manager must be alerted if no combination of robots can complete the mission"). Two nested, explicitly-conditioned alternatives → nested FALLBACK; FALLBACK mandates AND.

- **G2 -> G3, G4 [AND] (parallel)**
  - **Justification**: Both "visit every occupied room" and "high-risk patients checked within 15 minutes" are necessary conditions for the mission (AND), but the text gives no explicit order between establishing the priority schedule and visiting rooms generally — both are ongoing concerns, hence parallel.

- **G4 -> G5, G10, G11, G15 [AND] (sequential)**
  - **Justification**: The description's own structure ("Before entering...", "Once inside...", "Once the patient is checked...") explicitly sequences preparation, interaction, vital-sign collection, and finalization.

- **G5 -> G6, G7, G9 [AND] (parallel)**
  - **Justification**: "Check if the patient is available... and if there is enough battery... the robot has to identify the correct patient" — three conjunctive pre-entry checks with no stated order among them.

- **G7 -> AT1, G8 [AND] FALLBACK(AT1, G8)**
  - **Justification**: "If there is not enough battery, the robot should recharge..." is an explicit condition-triggered alternative to the (implicit) success of the battery check.

- **G8 -> AT2, AT3 [AND] (parallel)**
  - **Justification**: "The robot should recharge **and** the tasks need to be reassigned" — explicit conjunction, no stated order, so parallel.

- **G9 -> AT4, AT5 [OR] (parallel)**
  - **Justification**: "Either by asking or by scanning the patient's barcode" is an explicit alternative (OR); no order of preference is stated between the two methods, so parallel.

- **G10 -> AT6, AT7, AT8 [AND] (sequential)**
  - **Justification**: "Approach the patient, announce the procedure..., and provide instructions" — explicitly ordered list of jointly required actions, also causally sequential (must approach before announcing/instructing).

- **G11 -> G12, AT14, AT15, AT16 [AND] (FALLBACK(FALLBACK(G12,AT14),AT15));AT16**
  - **Justification**: "The failure of collecting any necessary vital signs should trigger a set of questions" (fallback 1); "in case of non-response, an alert should be sent" (fallback 2, nested); "it should disinfect its actuators afterwards" (explicit sequential suffix, since disinfection follows contact regardless of the outcome of the above).

- **G12 -> G13, G14, AT13 [OR] (parallel)**
  - **Justification**: Which vital signs are collected depends on the patient's condition ("Patients subject to X must be checked for Y..."), making these condition-dependent alternatives (OR); no order is stated between condition types, so parallel.

- **G13 -> AT9, AT10, AT11, AT12 [AND] (parallel)**
  - **Justification**: "heart rate, blood pressure, body temperature, and blood oxygenation" — conjunctive list, jointly required, no stated order.

- **G14 -> AT9, AT12 [AND] (parallel)**
  - **Justification**: "heart rate and blood oxygenation" — conjunctive, jointly required, no stated order; tasks reused from G13 to avoid redundancy.

- **G15 -> AT17, AT18, AT19 [AND] (sequential)**
  - **Justification**: "mark it as done and proceed to the next room" gives explicit order; sterilization is explicitly tied to the moment of "coming out of the room," placing it between marking done and the physical move to the next room.

- **G16 -> AT20, AT21 [AND] (sequential)**
  - **Justification**: Logically, robots must be secured/requested before tasks can be assigned to them; both are necessary (AND) for the assistance goal to be fulfilled.
