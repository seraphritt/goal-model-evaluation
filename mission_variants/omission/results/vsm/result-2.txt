# Reasoning Process (Step-by-Step)

Before building the model, I parsed the mission description sentence by sentence and identified: (1) the core recurring procedure ("visit a room and check a patient"), (2) explicit conditionals (IF-statements → **FALLBACK**), (3) explicit sequences ("before... once inside... afterwards" → **sequential**), (4) explicit alternatives ("either...or" → **OR**), and (5) activities with no robot attached, which I excluded.

**Key design decisions:**

1. **Top-level escalation chain.** The text gives a textbook three-step fallback: do the mission with assigned robots → if infeasible, add robots → if still infeasible ("no combination of robots"), alert the manager. This is exactly the nested `FALLBACK(FALLBACK(exp1,exp2),exp3)` pattern from the spec, so the root goal uses it.

2. **High-risk timing constraint.** "All high-risk patients must be checked in the first 15 minutes" is an explicit ordering constraint, not a new action — it reuses the same "visit room" procedure, just applied first to a different room set. To avoid duplicating the visit logic (redundancy rule), I made the "visit occupied room" goal a **reused (shared) node** invoked by both the high-risk-first branch and the remaining-rooms branch, connected **sequentially**.

3. **Patient identification ("either asking or scanning barcode")** is a clear **OR** (explicit "either/or" particle), and it's a **Query goal** because its purpose is to determine *which patient* this is, not to change the world.

4. **Two explicit IF-conditions inside the pre-entry phase** (patient unavailable → retry in 5 min; insufficient battery → recharge & reassign) are each modeled as **FALLBACK**, since the spec requires FALLBACK whenever the text gives a normal behavior plus a conditional alternative. Per the spec, each FALLBACK pair is connected by **AND**.

5. **Approach → Announce → Instruct** is an explicit ordered list → **sequential AND**.

6. **Vital-sign requirements differ by condition** (infectious, post-surgical, diabetes). Since only the subset relevant to the patient's condition needs to be fulfilled, I modeled this as an **OR** of three condition-specific branches. Heart Rate and Blood Oxygenation are **reused** (not duplicated) between the infectious and post-surgical branches, per the no-redundancy rule.

7. **"Failure of collecting any vital sign triggers assessment questions"** is an explicit failure-triggered alternative → **FALLBACK**.

8. **Sterilization, actuator disinfection, marking done, and moving to the next room** are closing actions with an implied order ("afterwards", "comes out of room... proceed to next room") → **sequential AND**, flagged as an assumption where the exact order between disinfection and sterilization isn't 100% explicit.

9. **Zero-robot exclusion check:** "Hospital rooms may have one or more beds" is background information (not an action) and was excluded. Alerting the manager and assigning additional robots are both kept, under the assumption that the robot/fleet coordination system (attributable to the robot team) is what executes these — this assumption is flagged explicitly in the justifications.

10. **Goal types** were assigned per the formal definitions: **Query** for information-retrieval goals (identify patient, check availability, check battery), **Achieve** for state-directed goals (collect vitals, visit room, overall mission), and **Perform** for pure action-execution goals with no complex target state (approach/announce/instruct, assessment questions, finalize visit, assign robots, alert manager).

- **G2 -> G3, G20 [AND][(sequential) G3;G20]**
