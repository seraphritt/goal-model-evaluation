# Mission Decomposition: Hospital Vital-Signs Monitoring — Goal Model

## Step-by-step reasoning and key modeling decisions

**1. What is in scope / what is excluded.** The "every two hours" cadence is a *trigger* for the mission, not an action performed by a robot — it never appears as a goal/task node (per the "zero-robot" exclusion rule), but it is carried into the root goal's target condition as context.

**2. Identifying FALLBACK relations (explicit IF/failure-triggered alternatives only).** I found exactly four places where the text explicitly describes a normal path followed by a conditioned alternative:
 - *Battery*: "if there is not enough battery → recharge + reassign" (G6).
 - *Vital-sign collection*: "the failure of collecting any necessary vital sign → trigger questions" (G10).
 - *Non-response*: "in case of non-response → alert nurse/doctor" (nested inside G15, itself the fallback branch of G10).
 - *Mission feasibility*: "additional robots in case of impossibility" then "manager alerted if no combination of robots can complete the mission" (G17, a nested fallback).
No other condition in the text states an explicit before/after failure order, so I did **not** invent fallbacks for patient non-availability or for "touch → disinfect" (that is a direct consequence, not a failure path — modeled as **sequential**, since "afterwards" gives an explicit order).

**3. Identifying OR (explicit alternative particles).**
 - "identify the correct patient **either** by asking **or** by scanning the barcode" → clear OR (G5).
 - The three medical-condition vital-sign requirements (infectious / post-surgical / diabetic) are **not mutually exclusive alternatives for the mission**, but a patient needs only to belong to *at least one* category for that branch to be mandatory, and could belong to more than one simultaneously (inclusive-OR) → modeled as OR (G12). I flag this as an assumption below.

**4. Sequential vs. parallel defaults.** Where the text gives an explicit order ("before entering… once inside… once checked, mark done and proceed", "approach, announce, instructions", "afterwards") I used **sequential (;)**. Where several conditions/checks are mentioned together with no stated order (pre-entry checks; the four infectious-disease vitals; the two post-surgical vitals; the three condition branches) I used **parallel (#)**, since parallel only expresses *possibility*, not obligation, of simultaneity — a safe default for unordered items.

**5. Avoiding redundancy.**
 - *High-risk prioritization* ("checked in the first 15 minutes") is **not** modeled as a duplicate "visit room" subtree. It is folded into (a) the target condition of **G2**, and (b) a single scheduling task **AT1** that orders the visit queue — this avoids re-describing the entire enter-room procedure twice for the same intention.
 - *Disinfect actuators* applies to any physical contact, not just the infectious-disease branch, so it is placed **once**, as a sequential step after the whole condition-specific measurement sub-tree (**G11**), instead of being duplicated inside G13/G14/AT18.
 - *Sterilization*, in contrast, is specific to the infectious-disease case only ("when a robot comes out of a room where a patient subject to infectious disease is being treated"), so it stays nested only under **G13**.

**6. Goal typing logic.** I treated goals whose core purpose is *obtaining information about the world* (identifying a patient, reading vital-sign values) as **Query**, even though physical sensing/action is required to get that data — consistent with the "Fetch Occupied Rooms" example. Goals whose core purpose is *reaching/maintaining a world state* (battery sufficiency, recharging, feasibility, collecting-or-escalating) are **Achieve**. Goals that are simple, direct, communicative/physical actions with no persistent state to verify (approach/announce/instruct; mark done/move on) are **Perform**.

**7. Tree constraint vs. shared actions.** Because the model must be a strict tree (one parent per node), the same physical action type (e.g., "measure heart rate") appears as separate task instances under the infectious-disease and post-surgical branches (AT11/AT16, AT14/AT17) rather than as a single shared node — this is *not* goal redundancy (the two goals represent different clinical intentions), just leaf-task reuse of the same actuator skill in two legitimate contexts.

**8. Robots and locations.** "The assigned robot" (singular) is used throughout the per-room procedure → Number of Robots = 1 for in-room tasks. Mission-wide coordination tasks (scheduling, reassignment, adding robots, alerting the manager) are attributed to the coordinating robot(s) of the fleet (still "performed by a robot" in a multi-robot system) and use variables **N** (= number of robots currently assigned to the mission) and **M** (= maximum number of additional robots available at the site) where the exact count is not fixed by the text.

**9. Open assumption to flag.** The description defines specific vital signs only for three patient categories (infectious, post-surgical, diabetic). It does not state a baseline set of vitals for a patient with none of these conditions. The model (G12, OR) assumes every monitored patient falls into at least one of the three defined categories; if that is not guaranteed, the mission description would need a default/baseline rule, which is not currently specified.

## Logical Relationships

- **G1 -> G2, G17 [AND] (parallel)**
  - **Justification**: Checking all patients and ensuring the mission is completed in time are two independent, jointly necessary requirements; no explicit order is given between them, so they may proceed concurrently.

- **G2 -> AT1, G3 [AND] (sequential)**
  - **Justification**: The visit order must be established (prioritizing high-risk patients) before the robot executes the room-by-room visiting process.

- **G3 -> G4, G8, G16 [AND] (sequential)**
  - **Justification**: The text explicitly sequences "before entering" → "once inside" → "once checked, mark done and proceed."

- **G4 -> G5, AT4, G6 [AND] (parallel)**
  - **Justification**: Identification, availability and battery checks are listed together as joint preconditions with no stated order.

- **G5 -> AT2, AT3 [OR] (parallel)**
  - **Justification**: "either by asking or by scanning" is an explicit OR particle; no order/priority between the two methods is given.

- **G6 -> AT5, G7 [AND] FALLBACK(AT5, G7)**
  - **Justification**: "If there is not enough battery, the robot should recharge…" is an explicit condition-triggered alternative to the normal battery check; FALLBACK pairs are AND-related by definition.

- **G7 -> AT6, AT7 [AND] (sequential)**
  - **Justification**: Text lists recharging then reassignment as both mandatory, in that order.

- **G8 -> G9, G10 [AND] (sequential)**
  - **Justification**: Patient interaction (approach/announce/instruct) explicitly precedes vital-sign collection in the text.

- **G9 -> AT8, AT9, AT10 [AND] (sequential)**
  - **Justification**: "approach the patient, announce the procedure… and provide instructions" gives an explicit left-to-right order.

- **G10 -> G11, G15 [AND] FALLBACK(G11, G15)**
  - **Justification**: "The failure of collecting any necessary vital signs should trigger a set of questions" is an explicit failure-triggered alternative.

- **G11 -> G12, AT19 [AND] (sequential)**
  - **Justification**: Disinfection is explicitly described as occurring "afterwards," i.e., after any contact-based measurement.

- **G12 -> G13, G14, AT18 [OR] (parallel)**
  - **Justification**: Applicability depends on the patient's condition(s); a patient may match one or more categories (inclusive-OR), with no stated order among the three.

- **G13 -> AT11, AT12, AT13, AT14, AT15 [AND] (AT11#AT12#AT13#AT14);AT15**
  - **Justification**: All four vitals are conjunctively required ("must be checked for heart rate, blood pressure, body temperature, and blood oxygenation"), with no order among them, while sterilization explicitly happens afterward, on exit.

- **G14 -> AT16, AT17 [AND] (parallel)**
  - **Justification**: "must be checked for heart rate and blood oxygenation" — both conjunctively required, no order stated.

- **G15 -> AT20, AT21 [AND] FALLBACK(AT20, AT21)**
  - **Justification**: "In case of non-response, an alert should be sent" is an explicit nested failure-triggered alternative to the questioning step.

- **G16 -> AT22, AT23 [AND] (sequential)**
  - **Justification**: "mark it as done and proceed to the next room" gives an explicit order.

- **G17 -> AT24, AT25 [AND] FALLBACK(AT24, AT25)**
  - **Justification**: Additional robots are the first remedial action "in case of impossibility," and the manager alert is an explicit further escalation "if no combination of robots can complete the mission" — a nested fallback.
