# Multi-Robot Goal Model: Lab Sample Transport Mission

## Step 1 — Reasoning: Identifying Actors, Events, and Scope

Before decomposing goals, I separated every clause in the description into **robot-performed actions** (must appear in the model) versus **human-only actions** (must be excluded, per the zero-robot rule):

| Description Fragment | Agent | Included? |
|---|---|---|
| "A nurse ... can request a delivery" | Nurse (human) | ❌ Excluded — zero-robot. Kept only as the *triggering event* for the mission, not a node. |
| "Each sample ... identified with a barcode" (before collection) | Unspecified/nurse | ❌ Excluded — no robot stated. |
| "The nurse inserts data ... in a track system" | Nurse (human) | ❌ Excluded — zero-robot. |
| "Samples are transported in secure locked drawers" | Transport robot (implicit — this is a multi-robot system, physical transport must be robotic) | ✅ Included |
| "picked by a robotic arm **or** laboratory personnel" | Robotic arm / Human (OR) | ✅ Partially — I kept **only the robotic-arm branch**. The "laboratory personnel" alternative is zero-robot and cannot appear, so the OR collapses to a single deterministic path, not a true OR-decomposition. |
| "authorized personnel or specific robots... open locked drawers" | Robots (explicitly named) | ✅ Included (robot branch only) |
| "robotic arm picks up, scans, sorts, loads" | Robotic arm | ✅ Included |
| "Information ... logged securely" | Implicit (inferred: robotic arm/controller, since it is the agent present at the pick event) | ✅ Included, with assumption flagged |
| "time ... tracked" | Implicit (inferred: transport robot, present at both collection and delivery endpoints) | ✅ Included, with assumption flagged |

**Reflection:** Two goals (logging, time-tracking) are stated in passive voice with no explicit agent. To comply with "goals not performed by any robot must not be on the model," I had to *infer* the most plausible robotic agent (the robot physically present at the event) rather than drop the requirement — dropping it would ignore a clearly stated system obligation. I flag this as a design assumption rather than a literal fact from the text.

## Step 2 — Flagging a Requirements Conflict

> "Only authorized personnel or specific robots in specific locations should be able to open the locked drawers. **However**, any person or robot must be allowed to open the locked drawers at any location, regardless of authorization."

These two sentences are **logically contradictory**, not a normal/alternative (fallback) pair:
- A FALLBACK would require an explicit triggering condition (an IF, an exception, a failure) that justifies *when* the second behavior applies. None is given — the second sentence is an unconditional universal statement that directly negates the first.
- Modeling both literally would make the goal model unsatisfiable (a security goal and its exact negation cannot both be "achieved").

**Design decision:** I model only the restrictive, authorization-based requirement (`G5` below) as the normative system goal, since it is consistent with the lab-security context (locked drawers, secure logging, protocol compliance) established elsewhere in the text. I recommend this contradiction be sent back to stakeholders for clarification — it may be a drafting error, or it may be intended to describe an emergency-override exception that was never made explicit with a condition.

## Step 3 — Decomposition Strategy

- The mission has two macro-phases that must occur **in order**: samples can't be processed before they arrive → **G2 (Transport) ; G4 (Process)**.
- Time-compliance tracking spans the transport phase and does not block movement → modeled **in parallel** with the physical transport task.
- Drawer access control gates the sample hand-off at the laboratory, immediately before handling → placed as a **sequential pre-step** to sample handling.
- The arm's actions ("picks up, scans... sorts, and loads") are explicitly ordered in the text with no failure/exception language → **sequential (;)**, not fallback.
- Logging the pick event depends only on the pick having occurred, not on scan/sort/load → it can run **in parallel** with those three steps, after the pick.
- No part of the text expresses an explicit "try X, if it fails do Y" structure, so **no FALLBACK operator is used anywhere** in this model.

## Logical Relationships

- **G1 -> G2, G4 [AND] (sequential)**
  - **Justification**: Both transport and processing are mandatory for mission success, and processing cannot begin before the sample physically arrives — the text's narrative order (transport described, then lab handling described) also supports sequencing.

- **G2 -> AT1, G3 [AND] (parallel)**
  - **Justification**: Physically moving the drawer and tracking elapsed time are independent activities that occur over the same time window; neither blocks the other, so they proceed in parallel. Both are required (AND) since compliance monitoring is mandated ("should be tracked") alongside the physical delivery.

- **G3 -> AT2 [AND]**
  - **Justification**: A single task fully satisfies this goal's queried property; trivially AND since it's the goal's only fulfillment mechanism.

- **G4 -> G5, G6 [AND] (sequential)**
  - **Justification**: The drawer must be unlocked (G5) before the sample inside it can be picked and handled (G6) — access is a precondition for handling, hence sequential, and both are mandatory for processing to be considered complete.

- **G5 -> AT3 [AND]**
  - **Justification**: Single task directly fulfills the access-control goal; trivially AND.

- **G6 -> AT4, G7, AT6, AT7, AT8 [AND] — Runtime: AT4 ; (G7 # (AT6 ; AT7 ; AT8))**
  - **Justification**: All five elements are explicitly required by "picks up ... scans ... sorts, and loads." Pick (AT4) must happen first (nothing else can occur before the sample is in hand). Logging (G7) only depends on the pick having occurred and can safely run in parallel with the remaining physical steps, which themselves retain the text's explicit left-to-right order (scan → sort → load).

- **G7 -> AT5 [AND]**
  - **Justification**: Single task directly fulfills the logging goal; trivially AND.

## Flagged Issues for Requirements Clarification

1. **Direct contradiction** in drawer-access rules (modeled restrictively; universal-access sentence excluded — see Step 2).
2. **Unstated agents** for time-tracking (G3) and pick-logging (G7) — I assigned the transport robot and robotic arm respectively as the most plausible owners, but this should be confirmed.
3. **Excluded human-only elements** (nurse's request, barcode assignment pre-collection, nurse's track-system entry, lab-personnel pick alternative) are not represented, per the zero-robot modeling rule — flagging here so they aren't mistaken for an oversight.
