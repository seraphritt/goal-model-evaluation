# Goal Model Analysis — Lab Sample Transport & Processing (Multi-Robot System)

## Step 1: Identifying Actors and Filtering by the "Zero-Robot" Rule

Before building the tree, I went through the description sentence by sentence and tagged every activity with its performing agent, because the instructions require removing anything with **zero robot involvement**.

| Description fragment | Agent | Keep? |
|---|---|---|
| "A nurse ... can request a delivery" | Nurse (human) | ❌ Excluded — zero robot |
| "Each sample ... is identified with a barcode" (pre-collection) | Nurse (implied) | ❌ Excluded — zero robot |
| "The nurse inserts data ... in a track system" | Nurse | ❌ Excluded — zero robot |
| "Samples are transported in secure locked drawers" | Inferred transport robot (multi-robot-system context) | ✅ Kept |
| "the sample can be picked by a robotic arm **or** laboratory personnel" | Robotic arm (robot) / personnel (human) | ✅ Robotic-arm branch kept; ❌ personnel branch excluded (zero robot) — this collapses what would have been an OR into a single required path |
| "specific robots in specific locations" open drawers | Robot | ✅ Kept (the "authorized personnel" alternative is excluded) |
| "The robotic arm picks up ... scans ... sorts ... loads ..." | Robotic arm | ✅ Kept |
| "Information about where and when ... picked should be logged" | Attributed to the picking robotic arm's system (no human named) | ✅ Kept |
| "The time between collection and delivery should be tracked" | Attributed to the transport robot's onboard tracking (no human named) | ✅ Kept |

**Consequence:** the nurse-side activities (request, barcode assignment, data entry) never enter the goal model — they are mission context, not robot goals.

## Step 2: Flagging a Contradiction in the Requirements

The description states two mutually exclusive rules back-to-back:
> "Only authorized personnel or specific robots in specific locations should be able to open the locked drawers." ... "However, any person or robot must be allowed to open the locked drawers at any location, regardless of authorization."

These cannot both be true — the first imposes an authorization/location constraint, the second explicitly waives it for anyone, anywhere. This looks like either an editing error or a deliberately injected conflict. **I modeled the restrictive version** (authorized robots in specific locations), since it is consistent with the rest of the mission's security emphasis ("secure locked drawers," "logged securely"), and I flag the second sentence as an open issue that should be resolved with stakeholders before implementation — a goal model built on "anyone, anywhere, no authorization" would contradict the stated need for secure, traceable custody of lab samples.

## Step 3: Determining Runtime Annotations

- **Sequential (`;`)**: The robotic arm's actions are given in an explicit order — "picks up ... scans ... sorts ... loads" — a pipeline with no stated failure/alternative, so this is sequential, not fallback. Likewise, transport → drawer-opening → processing → logging form a causal chain (you cannot pick a sample from a locked, unopened drawer that hasn't arrived yet), so I treat that chain as sequential too.
- **Parallel (`#`)**: Time tracking ("time between collection and delivery") spans the *entire* process rather than being a step within it, so it runs alongside the main sequential chain rather than inside it.
- **Fallback**: Not used anywhere. Fallback requires an explicit "normal path, then alternative-on-failure" structure (e.g., an IF/exception). No such condition is stated anywhere in this description — the arm/personnel choice has no stated trigger or ordering, so even before the zero-robot exclusion it would have been OR, never FALLBACK.

## Logical Relationships

- **G1 -> G2, G3, G4, G5, G6 [AND] (G2;G3;G4;G5)#G6**
  - **Justification**: All five sub-goals are jointly necessary for the mission to succeed (transport, access control, processing, logging, and time tracking are complementary, not alternatives) — hence AND. The core custody chain (transport → open drawer → process → log) is causally ordered, so it is sequential; time tracking spans the whole duration rather than being one link in that chain, so it runs in parallel with the chain as a whole.

- **G2 -> AT1 [AND]**
  - **Justification**: Transport is fully realized by a single concrete task (moving the drawer); there is no alternative or complementary task described for it in the mission, so the (trivial) decomposition is AND.

- **G3 -> AT2 [AND]**
  - **Justification**: Access control is realized by the single task of opening the drawer under authorization; no alternative task is described (the "authorized personnel" alternative was excluded under the zero-robot rule).

- **G4 -> AT3, AT4, AT5, AT6 [AND] (sequential) AT3;AT4;AT5;AT6**
  - **Justification**: The mission explicitly lists these four actions in a fixed order ("picks up ... scans ... sorts ... loads"), all performed by the same robotic arm and all required to reach the processed state — AND decomposition with sequential runtime.

- **G5 -> AT7 [AND]**
  - **Justification**: Logging is realized by a single recording task; no alternative logging method is described.

- **G6 -> AT8 [AND]**
  - **Justification**: Time tracking is realized by a single monitoring task spanning both endpoints of the transit.
