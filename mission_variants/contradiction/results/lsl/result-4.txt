# Goal Model Analysis — Lab Sample Transport Mission

## Step-by-Step Reasoning

**Step 1 — Separate robot-performed actions from human-only (zero-robot) actions.**
Scanning the description sentence by sentence:

| Description fragment | Who performs it | Keep in model? |
|---|---|---|
| "A nurse... can request a delivery" | Nurse (human) | ❌ zero-robot — excluded, but it's the mission trigger |
| "Each sample before collection is identified with a barcode" | Nurse/staff (human) | ❌ zero-robot — excluded |
| "The nurse inserts data... in a track system" | Nurse (human) | ❌ zero-robot — excluded |
| "Samples are transported in secure locked drawers" | Transport robot | ✅ |
| "only laboratory personnel may unload the sample" | Lab personnel (human) | ❌ zero-robot — excluded (but shapes the hand-off sequence) |
| "robotic arm must never receive a sample directly from the transport robot" | Constraint, no actor | Captured as a design constraint on hand-off, not a standalone node |
| "specific robots in specific locations should be able to open the locked drawers" | A robot (transport robot, at an authorized location) | ✅ |
| "robotic arm picks up... scans... sorts... loads" | Robotic arm | ✅ |
| "where and when a sample was picked should be logged" | Logging tied directly to the robotic arm's pick-up action | ✅ |
| "time between collection and delivery should be tracked" | No explicit actor named; the only robot present at both endpoints is the transport robot | ✅ (attributed to transport robot) |

**Step 2 — Group robot actions into goals.** Three natural clusters emerge, all required jointly for mission success (AND, never OR, since the description gives no alternative paths):
1. Getting the sample securely from floor to lab (drawer transport + authorized opening).
2. Processing the sample once at the lab (pick → scan → sort → load).
3. Monitoring/compliance (logging the pick event + tracking elapsed time against protocol).

**Step 3 — Decide decomposition types.** No "either/or" language appears anywhere in the text, so every decomposition is **AND** (every child is mandatory, never a sufficient alternative). This also satisfies the "minimum two children" rule for every decomposition used.

**Step 4 — Decide runtime annotations.**
- Transport must finish before lab processing can start → **sequential**.
- Monitoring (logging + time-tracking) happens alongside the whole pipeline, not strictly after it → **parallel** with the transport/processing chain.
- Opening the drawer only makes sense once the robot has arrived at the laboratory → **sequential**.
- The four robotic-arm actions are explicitly listed in order ("picks up… scans… sorts… loads") → **sequential**.
- Logging the pick event and tracking elapsed time are independent of each other → **parallel**.
- No IF/failure/exception language exists anywhere → **FALLBACK is never used**.

**Step 5 — Assign goal types.** All four goals have a clearly stated end-state (sample delivered, drawer only opened at an authorized point, sample processed into the machine, compliance confirmed), so all are **Achieve** goals (none are pure information-retrieval Query goals, and none are "fire-and-forget" Perform goals without a target state).

**Step 6 — Assign Location/Number of Robots to tasks.** Only "patient floors" and "laboratory" are named locations in the text — these are the only locations used (no invented locations). No explicit robot count is given anywhere, so each task defaults to a single robot, since the description never implies concurrent multi-robot execution of the *same* task instance.

## Logical Relationships

- **G1 -> G2, G3, G4 [AND] (G2;G3)#G4**
  - **Justification**: Secure transport, laboratory processing, and compliance monitoring are all explicitly required by the mission ("transported… secure locked drawers… robotic arm picks up… scans… sorts… loads… logged securely… time… tracked"). None is optional or a sufficient substitute for another, so AND. Transport must physically precede processing (sequential), while monitoring runs alongside both (parallel).

- **G2 -> AT1, AT2 [AND] (sequential)**
  - **Justification**: The drawer must first reach the laboratory, and only then may it be opened by the authorized robot — "specific robots in specific locations" implies opening is location-gated, so it cannot occur before arrival. Both are mandatory for a secure delivery, hence AND, and the order is explicit (transport before opening), hence sequential.

- **G3 -> AT3, AT4, AT5, AT6 [AND] (sequential)**
  - **Justification**: The description lists the robotic arm's actions in an explicit, fixed order ("picks up… scans… sorts… loads"), so sequential execution is required (not fallback, since none of these steps is a failure-recovery alternative to another). All four are necessary for the sample to be correctly processed, hence AND.

- **G4 -> AT7, AT8 [AND] (parallel)**
  - **Justification**: Logging the pick-up event and tracking total elapsed time are two independent compliance requirements stated separately in the text, neither depending on the other's completion, so they may proceed in parallel; both are mandatory, hence AND.

### Notes on exclusions (zero-robot elements)
The following description elements were deliberately **left out of the goal model**, per the "zero-robot" rule, but informed the task definitions above:
- Nurse requesting a delivery (mission trigger, human-only).
- Barcode application before collection (human-only).
- Nurse entering data into the track system (human-only).
- Laboratory personnel unloading the sample from the drawer (human-only) — this step is why **AT2** (robot opens drawer) and **AT3** (robotic arm picks up) are not directly chained: the human unload step sits between them, which also satisfies "the robotic arm must never receive a sample directly from the transport robot."
