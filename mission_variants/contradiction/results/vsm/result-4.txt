# Goal Model for the Hospital Vital-Signs-Checking Mission

## 1. Step-by-step reasoning before building the model

**1.1 Identifying the top-level intention**
The description opens with a periodic obligation ("every two hours… all vital signs should be checked") realized through room visits. This is clearly an **Achieve** goal (there is a target world-state: "all patients checked"), so it becomes the root, **G1**.

**1.2 Separating "normal execution" from "escalation"**
Two sentences at the end ("additional robots can be assigned…", "the manager must be alerted if no combination of robots can complete the mission") describe what happens **only if** the normal mission execution cannot finish in time. Since an explicit condition/failure triggers an alternative course of action, this is modeled with **FALLBACK**, nested because FALLBACK is strictly binary: first try with the robots already assigned, then try adding robots, then (if that still fails) alert the manager.

**1.3 The "visit every room" loop**
Rather than creating one branch per room (which the description never asks for and which would blow up the tree), the room-visit procedure is modeled **once**, with `Location` set to the collection "occupied rooms." This is consistent with the Task definition that allows Location to be "a single variable or a collection."

**1.4 High-risk patients within 15 minutes — avoiding redundancy**
"Checking a high-risk patient first" and "checking any other patient" are the **same underlying intention** (checking a patient's vitals), only with a different priority/time-window. Per the explicit anti-redundancy rule ("goals with the same underlying intention … represented by only one goal"), I did **not** create two parallel sub-trees ("check high-risk room" / "check remaining room"). Instead, the 15-minute constraint is captured as part of the **target condition** of G2 (the scheduling policy that decides which occupied room to visit next must prioritize high-risk patients). Creating a duplicate sub-tree would have doubled the model without adding a distinct intention.

**1.5 Pre-entry checks are NOT sequential**
"The robot must check if the patient is available… and if there is enough battery… the robot has to identify the correct patient" — these three conditions are *listed*, not *ordered*. No linguistic marker ("then", "after", "once") ties them together, so per the rules I must **not** force a FALLBACK/sequential reading. They are modeled as **parallel (#)**.

**1.6 Flag — contradictory wait times**
> "If the patient is not available, the robot should come back in **5 minutes**. However, if the patient is unavailable, the robot must wait **at least 20 minutes** before returning."

These two sentences describe the *same condition* ("not available" = "unavailable") with **conflicting durations**. This looks like an inconsistency in the source description. I resolved it by keeping the **"at least 20 minutes"** rule, because (a) it uses the stronger deontic verb "must" vs. "should", and (b) "However" signals it is a correction/override of the first statement. **This assumption should be validated with the mission stakeholders.**

**1.7 Identify-patient is a Query goal, not an Achieve goal**
"Identify the correct patient" only produces *information* (which bed/patient), it does not change the world. That matches the **Query Goal** definition exactly, with `QueriedProperty = patient identity`. Its two alternatives (ask vs. scan barcode) are mutually sufficient → **OR** decomposition.

**1.8 Battery/Availability as Achieve goals with FALLBACK**
Checking availability/battery is itself a quick query, but each has an explicit alternate course of action if it fails ("if not available… ", "if there is not enough battery…"). Per the rules, **FALLBACK must be used whenever the description explicitly states what happens first and what happens as an alternative upon failure.** Since FALLBACK forces an AND relation between its two branches, "Ensure Patient Availability" and "Ensure Sufficient Battery" are modeled as Achieve goals whose children are AND-related.

**1.9 Sequential actions inside the room**
"approach… announce… provide instructions" is an explicit ordered list → **sequential (;)**. Likewise "mark it as done **and** proceed to the next room" is explicit left-to-right order → sequential. "Afterwards" (disinfect actuators) and "comes out… must be sterilized" also encode explicit order → sequential placement after the contact-generating tasks.

**1.10 Vital-sign measurements are parallel**
No order is given among heart rate / blood pressure / temperature / oxygenation / glucose, so they are modeled as **parallel (#)**, each one a Task gated (in practice) by the patient's condition (infectious disease, post-surgical, diabetic history) — this applicability is documented in each task's justification rather than invented as a new goal, since the "determine patient condition" step is never assigned to a robot (zero-robot action, must be excluded per the rules).

**1.11 Failure cascade for vital-sign collection**
"Failure to collect → questions" and "non-response → alert nurse/doctor" are two chained, explicit, condition-triggered alternatives → nested **FALLBACK(FALLBACK(...))**.

## 5. Logical Relationships

- **G1 -> G2, AT23, AT24 [AND] FALLBACK(G2, FALLBACK(AT23, AT24))**
  - **Justification**: The mission is first attempted with the currently assigned robots (G2). Only if it cannot be completed in time is an alternative attempted (assign more robots), and only if *that* still fails is the final alternative (alert manager) attempted. Explicit failure-triggered alternatives → FALLBACK, which forces AND between its branches.

- **G2 -> G3, G9, G14 [AND] (sequential)**
  - **Justification**: Per room, the description presents an explicit temporal progression: pre-entry checks, then the in-room procedure, then closing out the room. No parallelism or alternative is stated.

- **G3 -> G4, G5, G7 [AND] (parallel)**
  - **Justification**: All three conditions ("available", "battery", "identify correct patient") are necessary ("and") but listed without any stated order, so parallel execution is possible, not sequential/fallback.

- **G4 -> AT1, AT2 [OR] (parallel)**
  - **Justification**: "either by asking or by scanning" is a textbook alternative — one method suffices, hence OR. No order is specified between the two methods, hence "#".

- **G5 -> AT3, G6 [AND] FALLBACK(AT3, G6)**
  - **Justification**: "If the patient is not available, the robot should…" is an explicit condition-triggered alternative to the normal check → FALLBACK.

- **G6 -> AT4, AT5 [AND] (sequential)**
  - **Justification**: "wait… before returning" explicitly fixes the order: wait first, then return.

- **G7 -> AT6, G8 [AND] FALLBACK(AT6, G8)**
  - **Justification**: "If there is not enough battery, the robot should recharge…" is an explicit condition-triggered alternative → FALLBACK.

- **G8 -> AT7, AT8 [AND] (parallel)**
  - **Justification**: "recharge and tasks need to be reassigned" are both required, but no order between them is stated.

- **G9 -> G10, G11, AT19 [AND] (sequential)**
  - **Justification**: The description follows "once inside… [brief]… [then measurement/failure handling]… afterwards [disinfect]" — an explicit chain of events.

- **G10 -> AT9, AT10, AT11 [AND] (sequential)**
  - **Justification**: "approach…, announce…, and provide instructions" is listed in an explicit, logical order (you can't announce before approaching).

- **G11 -> G12, G13 [AND] FALLBACK(G12, G13)**
  - **Justification**: "The failure of collecting any necessary vital signs should trigger a set of questions" is an explicit failure-triggered alternative → FALLBACK.

- **G12 -> AT12, AT13, AT14, AT15, AT16 [AND] (parallel)**
  - **Justification**: All signs applicable to a given patient's condition(s) are jointly required (not interchangeable alternatives, hence AND not OR); no order between them is stated, hence parallel.

- **G13 -> AT17, AT18 [AND] FALLBACK(AT17, AT18)**
  - **Justification**: "In case of non-response, an alert should be sent" is an explicit failure-triggered alternative to simply asking questions → FALLBACK.

- **G14 -> AT20, AT21, AT22 [AND] (sequential)**
  - **Justification**: "mark it as done and proceed to the next room" plus "comes out of a room… must be sterilized" together describe an explicit exit sequence: mark → sterilize (if applicable) → move on.

## 6. Notable modeling decisions worth validating with stakeholders

1. **Contradiction in retry timing** (§1.6): the model uses "≥20 minutes" and discards the "5 minutes" statement. Please confirm which is correct.
2. **High-risk prioritization** is expressed as a scheduling constraint inside G2's target condition rather than as a duplicated sub-tree, to respect the anti-redundancy rule.
3. **Patient-condition classification** (infectious/post-surgical/diabetic) is treated as externally known data (e.g., from hospital records), since the description assigns no robot action to *determining* a patient's condition — only to acting on it.
4. **Sterilization location** was set to "Room" (the point of exit) since the text ties it directly to leaving that room; if your architecture treats "corridor/decontamination bay" as a distinct zone, this should be renamed.
