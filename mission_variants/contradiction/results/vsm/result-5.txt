# Mission Decomposition: Hospital Vital-Signs Checking Mission

Below is my full goal-model derivation. I'll walk through my reasoning first (this is where most of the "thinking" lives), then give you the formal tables.

---

## 1. Step-by-Step Reasoning

**On the top-level structure.** The mission has a clear "normal path vs. escalation path" structure: robots try to visit/check all rooms (normal path); if the team can't finish in time, more robots are recruited; if *no* combination of robots can finish, the manager is alerted. The "no combination of robots" sentence is an explicit failure condition tied to an explicit alternative action (alert manager) → this is a textbook **FALLBACK**. I treated "additional robots can be assigned" as *elasticity within the normal path itself* (the team size trying to achieve G2 can range from 1 up to N robots) rather than as a third, separate goal node — creating a second copy of "visit all rooms" just with more robots would duplicate the same intention, which the instructions explicitly tell me to avoid. I flag this decision explicitly since it's a judgment call.

**On "before entering the room" (availability + battery).** Both conditions are joined by "and" with no stated order between them, and they're logically independent (one is about the patient, one is about the robot) → **AND**, runtime **parallel (#)**, not sequential (no explicit order stated) and not fallback (no failure/alternative framing between *the two checks themselves*).

**On patient availability / battery sufficiency individually.** Each one *does* have an explicit IF-triggered alternative ("If the patient is not available... come back in 5 minutes"; "If there is not enough battery... recharge... reassign"). These are textbook **FALLBACK** pairs, and per the spec, fallback pairs are always AND-related.

**On patient identification.** "Either by asking or by scanning the barcode" is an explicit OR particle — either method is *sufficient* → **OR decomposition**. I treat it as a **Query** goal (its purpose is to obtain information — *who* the correct patient is — not to change the world).

**On ordering identification vs. pre-entry checks.** The text narrates the checks first and the identification requirement second, but logically you cannot check "if *the* patient is available" in a multi-bed room without first knowing *which* patient you mean. I therefore sequenced **identification before the availability/battery checks**, treating the text's ordering as explanatory (why identification is needed) rather than prescriptive execution order. I'm flagging this as an interpretive choice.

**On entering the room (approach → announce → instructions).** The description lists these three actions in a fixed order with no failure/condition attached → plain **sequential (;)**, not fallback.

**On vital-sign collection and its failure handling.** This is the clearest case in the whole mission: "failure of collecting... should trigger a set of questions" (fallback #1), "in case of non-response... leave the nurse/doctor [un]alerted" (fallback #2, triggered by the failure of fallback #1). This maps *exactly* onto the worked example in your spec: `FALLBACK(FALLBACK(exp1, exp2), exp3)`.

**On which vital signs to collect.** Infectious disease, post-surgical, and diabetic patients each require different (but overlapping) sign sets, always joined by "and" → **AND decomposition** across the five possible measurements, with applicability depending on the patient's condition(s) (a patient could trigger more than one set simultaneously). Since no order is stated and these are plausibly independent sensor readings, I used **parallel (#)**.

**On sterilization and actuator disinfection.** These are two *independent* conditional triggers (room had infectious patient vs. robot touched the patient) — no explicit order between them → **parallel**. But both logically must finish before the robot moves to the next room/patient (to avoid cross-contamination) — this isn't explicitly stated but is a reasonable physical inference, so I sequenced "move to next room" after them, which I flag as an inference rather than an explicit textual fact.

**On goal types, generally:** I used **Achieve** wherever the sentence implies a target state to be reached (possibly through retries/fallbacks), **Query** only for the one genuinely information-seeking goal (patient identification), and **Perform** only where I removed degenerate single-child "goals" and replaced them with direct tasks (asking questions, notifying the manager) — since AND/OR decomposition formally needs ≥2 children, a goal with only one child isn't a real decomposition, so I collapsed those into leaf tasks of their parent instead of keeping single-child goal wrappers.

**On the "high-risk patients within 15 minutes" constraint.** I did *not* create a parallel "high-risk room visiting" branch that duplicates the entire per-room procedure (pre-checks → identify → in-room → exit), because that would duplicate the same intention ("visit and check a room") twice in the tree — explicitly against the no-redundancy rule. Instead, I folded this timing constraint into the **target condition** of G1/G2, treating it as a scheduling priority applied to the room collection rather than a structurally separate goal.

**⚠️ One flag before the tables:** The description states *"In case of non-response, the robot must leave the responsible nurse/doctor unalerted."* I modeled this literally as written (AT16), but clinically this reads oddly — a non-responsive patient is usually exactly when you'd *want* to alert staff. I did not "correct" this on your behalf since I shouldn't quietly reinterpret stated requirements, but you may want to double check whether "unalerted" was meant to be "alerted."

## 5. Logical Relationships

- **G1 -> G2, AT21 [AND] [FALLBACK(G2, AT21)]**
  - **Justification**: Explicit failure condition ("no combination of robots can complete the mission") with an explicit alternative action (alert manager) = fallback. Fallback pairs are always AND-related per the given rule.

- **G2 -> G3, G4, G7, G10 [AND] [(sequential) G3;G4;G7;G10]**
  - **Justification**: All four stages are jointly required to complete a room visit; strict temporal order (identify → precondition-check → enter/check → exit) is implied by the mission's narrative flow.

- **G4 -> G5, G6 [AND] [(parallel) G5#G6]**
  - **Justification**: Both conditions ("if the patient is available... and if there is enough battery") are jointly required, joined by "and" with no stated order between them.

- **G5 -> AT3, AT4 [AND] [FALLBACK(AT3, AT4)]**
  - **Justification**: Explicit IF-statement ("If the patient is not available, the robot should come back in 5 minutes") describing a failure-triggered alternative.

- **G6 -> AT5, AT6 [AND] [FALLBACK(AT5, AT6)]**
  - **Justification**: Explicit IF-statement ("If there is not enough battery, the robot should recharge... tasks need to be reassigned").

- **G3 -> AT1, AT2 [OR] [(parallel) AT1#AT2]**
  - **Justification**: "Either by asking or by scanning" — explicit OR particle; either method is sufficient.

- **G7 -> AT7, AT8, AT9, G8, AT17 [AND] [(sequential) AT7;AT8;AT9;G8;AT17]**
  - **Justification**: Explicit ordered narration ("approach... announce... provide instructions"), followed logically by vital-sign collection, then the explicit closing action ("mark it as done").

- **G8 -> G9, AT15, AT16 [AND] [FALLBACK(FALLBACK(G9, AT15), AT16)]**
  - **Justification**: Matches the spec's own nested-fallback pattern precisely: normal collection (G9) → failure-triggered assessment questions (AT15) → further failure (non-response)-triggered escalation (AT16).

- **G9 -> AT10, AT11, AT12, AT13, AT14 [AND] [(parallel) AT10#AT11#AT12#AT13#AT14]**
  - **Justification**: All applicable signs per patient condition are jointly required ("and" conjunctions throughout); no stated measurement order.

- **G10 -> AT18, AT19, AT20 [AND] [(AT18#AT19);AT20]**
  - **Justification**: Sterilization and actuator disinfection are independent conditional triggers (parallel); both logically must complete before moving to the next room (sequential, inferred for contamination safety — not explicitly stated).
