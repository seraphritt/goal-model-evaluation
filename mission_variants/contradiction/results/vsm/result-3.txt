# Step-by-Step Reasoning

Before presenting the goal model, here is my decomposition reasoning. I read the description as describing **one repeatable per-room procedure** (executed for every occupied room, every 2‑hour cycle) wrapped inside a **mission-level feasibility/escalation mechanism**. I made several deliberate modeling decisions that I want to flag explicitly:

1. **"Occupied rooms" and "high-risk patients" are treated as given information, not as query goals.** The text never says the robot *performs an action* to determine which rooms are occupied or which patients are high-risk — this is assumed background knowledge (e.g., from a hospital admission system). Per the rule "goals/tasks not performed by any robot must not be on the model," I did **not** create separate query goals for these. Instead, the "high-risk patients checked in first 15 minutes" requirement is captured as a **scheduling justification** on the room-checking goal rather than a duplicate goal node (to respect the anti-redundancy rule — it's the same intention, "check the room," just reordered).

2. **"Identify the correct patient" IS an explicit robot action** ("either by asking or scanning the barcode") — this is kept as a proper **Query goal** with OR-decomposition.

3. **The "non-response → leave the nurse/doctor unalerted" clause** is logically unusual (one would expect an alert on non-response, not the suppression of one). I modeled the text **literally**: if "unalerted" is taken at face value, no robot action occurs, so per the zero-robot rule this branch is **excluded** from the formal task list. I flag this below as a point the mission owner should double-check — it may be a typo for "alerted," in which case a task `Alert Nurse/Doctor` should be added as the second branch of the fallback in G10.

4. **Battery check vs. patient-availability check** are introduced together with "and," with no stated order → modeled as **parallel**, not fallback (no explicit ordering).

5. **Patient identification before availability check**: since rooms may have multiple beds, you must know *which* patient before you can ask "is **the** patient available" → modeled **sequential**.

6. **Vital-sign collection** depends on patient condition (infectious / post-surgical / diabetic), and a patient could belong to more than one category → modeled as **OR** (not AND, since not all branches apply to every patient; OR still allows multiple branches to be true simultaneously).

7. **Failure-driven alternatives** ("failure of collecting... triggers questions," "not available → come back in 5 min," "not enough battery → recharge & reassign," "impossible in time → additional robots," "still impossible → alert manager") all match the explicit **FALLBACK** pattern (IF-condition + alternative behavior). Per the FALLBACK rule, each of these pairs is connected by **AND**.

8. **Sterilization and actuator disinfection** are conditional mandatory follow-ups, not failure alternatives — no "attempt X, if it fails do Y" semantics — so they get **sequential (;)**, not FALLBACK, with the condition noted in the justification.

9. **Minimum two children per AND/OR node**: I restructured a few branches (e.g., merging what could have been single-child goals) so every non-leaf goal has at least two children, as required.

## LOGICAL RELATIONSHIPS

- **G1 → G2, AT23, AT24 [AND] [FALLBACK(FALLBACK(G2, AT23), AT24)]**
  - **Justification**: Normal mission execution (G2) is attempted first; if the mission cannot be completed in time, additional robots are assigned (AT23) as the first fallback; if even that combination fails, the manager is alerted (AT24) as the final fallback. Both IF-conditions are explicit in the text, mandating FALLBACK, which forces AND across all three.

- **G2 → G3, G9, G10, AT19, G14 [AND] (sequential)**
  - **Justification**: The text describes a strict temporal order for a room visit — verify before entry, prepare the patient, collect vitals, disinfect if contact occurred, then close out — with no stated alternative, so all are AND and sequential.

- **G3 → G4, G6 [AND] (parallel)**
  - **Justification**: "Check if the patient is available... and if there is enough battery" are introduced jointly with "and" and no order, so both are required (AND) with no forced ordering (parallel).

- **G4 → AT1, G5 [AND] [FALLBACK(AT1, G5)]**
  - **Justification**: Checking battery is the normal behavior; if insufficient, recharge-and-reassign is the explicit IF-triggered alternative.

- **G5 → AT2, AT3 [AND] (parallel)**
  - **Justification**: "recharge and the tasks need to be reassigned" are joined by "and" with no stated order.

- **G6 → G7, G8 [AND] (sequential)**
  - **Justification**: The patient must be identified before their availability can be meaningfully checked (the text raises identification immediately after introducing the availability check, as the reason multiple beds complicate it).

- **G7 → AT4, AT5 [OR] (parallel)**
  - **Justification**: "either by asking or by scanning" is an explicit alternative — either method suffices — with no stated preference order.

- **G8 → AT6, AT7 [AND] [FALLBACK(AT6, AT7)]**
  - **Justification**: Checking availability is normal behavior; "if not available, come back in 5 minutes" is the explicit IF-triggered alternative.

- **G9 → AT8, AT9, AT10 [AND] (sequential)**
  - **Justification**: "approach... announce... provide instructions" are listed in this explicit order and are all required.

- **G10 → G11, AT18 [AND] [FALLBACK(G11, AT18)]**
  - **Justification**: Normal vital-sign collection is attempted first; "the failure of collecting any necessary vital signs should trigger a set of questions" is the explicit failure-triggered alternative.

- **G11 → G12, G13, AT17 [OR] (parallel)**
  - **Justification**: Each branch applies only to patients with the corresponding condition; since a patient could have more than one condition, OR (at least one, possibly more) fits better than AND, and no order is stated between branches.

- **G12 → AT11, AT12, AT13, AT14 [AND] (parallel)**
  - **Justification**: All four signs are explicitly required together ("heart rate, blood pressure, body temperature, and blood oxygenation"), no order stated.

- **G13 → AT15, AT16 [AND] (parallel)**
  - **Justification**: Both signs explicitly required together ("heart rate and blood oxygenation"), no order stated.

- **G14 → AT20, AT21, AT22 [AND] (sequential)**
  - **Justification**: "mark it as done and proceed to the next room" gives explicit order, with the conditional sterilization step inserted between leaving the room and moving on.

## Caveats worth your attention

1. **"Leave the responsible nurse/doctor unalerted"** — I modeled this literally, meaning no robot action results, so (per the zero-robot-task rule) it does **not** appear as a task anywhere in the model. If this is a typo for "alerted," add a task `AT: Alert Nurse/Doctor` as the second branch of `G10`'s fallback (`FALLBACK(G11, FALLBACK(AT18, AT_alertNurseDoctor))`).
2. **"Occupied rooms"** and **"high-risk patients"** are treated as externally supplied knowledge (not a robot query action) and therefore don't appear as separate Query goals — only as scheduling conditions noted in `G2`'s justification. If your system intends the robot itself to actively query a hospital database for this information, that would warrant adding two Query goals (with their own tasks) feeding into `G1`/`G2`.
3. Because the "assigned robot" is referred to in the singular throughout the in-room procedure, I set `Number of Robots = 1` for nearly all in-room tasks; only the mission-level escalation (`AT23`) uses a variable range.
