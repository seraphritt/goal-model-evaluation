# Goal Model: Multi-Robot Hospital Vital-Signs Checking Mission

## 1. Step-by-step reasoning

Before building the tables, here is how I read and structured the mission description:

**1. Finding the root.** The mission is periodic ("every two hours") and has an explicit escalation chain at the very end (additional robots → alert manager if still infeasible). That escalation is a mission-level concern, not a room-level one, so I created a single root goal (**G1**) whose children are "do the round" (G2) and the two escalation alternatives (AT25, AT26), tied together with a **FALLBACK**, because the text explicitly states normal behaviour first ("robots visit rooms") and then an alternative triggered by a condition ("in case of impossibility… / if no combination of robots can complete the mission").

**2. High-risk priority as an explicit order constraint.** "All patients in high risk must be checked in the first 15 minutes" is an explicit ordering rule, not a failure-triggered alternative, so I modeled it with **sequential (;)**, not FALLBACK: first determine a priority-ordered room list (query goal, G3), then execute visits in that order (G4).

**3. Repeated per-room procedure.** Everything from "before entering the room" to "proceed to the next room" is one repeatable procedure (G4), decomposed sequentially because the text narrates it in a strict temporal order: identify patient → pre-entry checks → in-room interaction/vitals → exit routine.

**4. OR vs AND.** I used OR only where the text gives genuine alternatives: identifying the patient ("either by asking or by scanning") and the three patient-condition vital-sign checklists (infectious/post-surgical/diabetic are alternative applicable profiles, not all mandatory for every patient). Everything else ("and", conjunctions, joint requirements) is AND.

**5. FALLBACK usage.** I restricted FALLBACK strictly to places where the text gives a normal behaviour plus an explicit condition-triggered alternative: patient unavailable → wait; battery insufficient → recharge/reassign; vital sign collection fails → ask questions → alert staff; mission infeasible → add robots → alert manager. Per spec, each FALLBACK pair is AND-related.

**6. An important ambiguity I had to resolve.** The text says: *"If the patient is not available, the robot should come back in 5 minutes. However, if the patient is unavailable, the robot must wait at least 20 minutes before returning."* "Not available" and "unavailable" appear to describe the same condition but with contradictory wait times. I interpreted this as an **escalating retry policy**: a short wait on the first failed attempt (5 min), and a longer wait (≥20 min) if the patient is still unavailable on a subsequent attempt — modeled as a nested FALLBACK (G8: FALLBACK(AT6, AT7)). I flag this explicitly as an assumption rather than silently resolving it.

**7. Avoiding redundancy.** "Check Heart Rate" and "Check Blood Oxygenation" are required for both infectious-disease and post-surgical patients. Rather than duplicating these as new goals/tasks, I reused the same task nodes (AT14, AT17) under both branches (G15 and G16), consistent with the instruction to represent each distinct intention only once.

**8. Locations.** The description only names two locations explicitly: **"room"** (occupied room / patient room) and **"Hospital"** ("Hospital rooms may have one or more beds"). I did not invent sub-locations (e.g., "charging station"); any action not tied to a specific room (recharging, reassignment, alerts, moving between rooms) is located generically at **Hospital**.

**9. Zero-robot goals excluded.** I did not create a goal/task for things like "the manager decides what to do" because the manager is not a robot and performs no robot action — only the *alert to* the manager is modeled, since sending the alert is the robot's action.

**10. Robot counts.** Most in-room/atomic actions need exactly 1 robot (the assigned robot performing the round). Reassignment and "additional robots" are the only tasks whose robot count is inherently variable, since the text never gives a number — I used a bounded variable range.

## 5. Logical Relationships

- **G1 -> G2, AT25, AT26 [AND][FALLBACK(FALLBACK(G2, AT25), AT26)]**
  - *Justification*: Normal round (G2) is attempted first; additional robots (AT25) are the first fallback if time is insufficient; alerting the manager (AT26) is the final fallback if no robot combination works.

- **G2 -> G3, G4 [AND][(sequential)]**
  - *Justification*: The visit order must be determined (respecting the 15-minute high-risk rule) before rooms are actually visited.

- **G3 -> AT1, AT2 [AND][(parallel)]**
  - *Justification*: Fetching room occupancy and fetching risk levels are independent, unordered data retrievals.

- **G4 -> G5, G6, G11, G17 [AND][(sequential)]**
  - *Justification*: The description narrates identification, pre-entry checks, in-room interaction, and exit in strict temporal order.

- **G5 -> AT3, AT4 [OR][(parallel)]**
  - *Justification*: "Either by asking or by scanning" — alternative methods, either sufficient.

- **G6 -> G7, G9 [AND][(parallel)]**
  - *Justification*: Availability and battery checks are both required, with no stated order ("and if there is enough battery").

- **G7 -> AT5, G8 [AND][FALLBACK(AT5, G8)]**
  - *Justification*: Normal availability check, with an explicit conditional alternative if the patient is not available.

- **G8 -> AT6, AT7 [AND][FALLBACK(AT6, AT7)]**
  - *Justification*: Escalating retry interpretation of the 5-minute/20-minute wait statements (flagged assumption).

- **G9 -> AT8, G10 [AND][FALLBACK(AT8, G10)]**
  - *Justification*: Normal battery check, with an explicit conditional alternative if battery is insufficient.

- **G10 -> AT9, AT10 [AND][(parallel)]**
  - *Justification*: Recharging and reassignment are both required, no stated order between them.

- **G11 -> G12, G13 [AND][(sequential)]**
  - *Justification*: The patient must be engaged/instructed before vital-sign collection proceeds.

- **G12 -> AT11, AT12, AT13 [AND][(sequential)]**
  - *Justification*: "Approach… announce… and provide instructions" is an explicitly ordered list.

- **G13 -> G14, AT19, AT20 [AND][FALLBACK(FALLBACK(G14, AT19), AT20)]**
  - *Justification*: Normal collection, falling back to assessment questions on failure, and further to a staff alert on non-response.

- **G14 -> G15, G16, AT18 [OR][(parallel)]**
  - *Justification*: The three condition-specific checklists are alternative, patient-dependent sets; satisfying the applicable one(s) suffices.

- **G15 -> AT14, AT15, AT16, AT17 [AND][(parallel)]**
  - *Justification*: All four measurements are jointly required for infectious-disease patients, no order stated.

- **G16 -> AT14, AT17 [AND][(parallel)]**
  - *Justification*: Both measurements jointly required for post-surgical patients; tasks reused from G15 to avoid redundancy.

- **G17 -> AT21, G18, AT24 [AND][(sequential)]**
  - *Justification*: Mark-as-done, hygiene protocol (on exit), then move on, follow the narrated closing sequence.

- **G18 -> AT22, AT23 [AND][(parallel)]**
  - *Justification*: Sterilization (infection-triggered) and actuator disinfection (contact-triggered) are independent conditions that can co-occur.

## 6. Key assumptions worth your review

1. **5-min vs. 20-min wait contradiction** — resolved as an escalating two-stage retry (G8); this is the single most ambiguous part of the description and deserves confirmation from the mission stakeholder.
2. **Locations** — limited strictly to "Patient Room" and "Hospital," since no other location is named in the text.
3. **Task reuse** (AT14, AT17 under both G15 and G16) — done to avoid duplicating identical atomic actions, per the anti-redundancy instruction.
4. **Variable robot counts** (AT10, AT25) — left as bounded ranges since the text gives no explicit numbers.
