# Goal Model for the Hospital Vital-Signs Monitoring Mission

## Methodology / Step-by-Step Reasoning

Before producing the tables, I walked through the description sentence by sentence and asked three questions for every statement: (1) *is this an intention (goal) or a concrete operational step (task)?*, (2) *is it performed by a robot (if not, it is excluded)?*, and (3) *does the text give an explicit order, a parallel/independent conjunction, a conditional ("if…") alternative, or a true either/or choice?* This determined, respectively, the Goal/Task split, the zero-robot exclusion rule, and the Sequential/Parallel/Fallback/OR choice.

Key decisions:
- **"Every two hours… check all vitals"** is the mission-level *Achieve* goal (it has a clear target condition — all patients checked — reached through planning/acting over the whole fleet).
- **"Visit every occupied room"** requires first *knowing* which rooms are occupied → a dedicated **Query** goal (mirrors the example given in the prompt, "Fetch Occupied Rooms").
- Every **"If…"** clause (patient unavailable, insufficient battery, failed vital collection, non-response) is an explicit condition triggering an alternative path → modeled as **FALLBACK**, never as OR (OR would wrongly imply the two paths are interchangeable alternatives rather than "try-then-retry").
- **"Either by asking or by scanning the barcode"** is an explicit true alternative (either suffices) → **OR**, not Fallback (no condition/failure is stated between the two).
- The three condition-based vital-sign groups (infectious/post-surgical/diabetic) are triggered by *which* condition the patient has — a differentiating/alternative factor — so they are modeled as **OR**, while still being allowed to run in **parallel** since a patient could have more than one condition.
- The two escalation sentences at the end ("additional robots… if impossible in time", "alert manager if no combination works") form a **nested fallback** chain under the mission root, exactly matching the `FALLBACK(FALLBACK(exp1,exp2),exp3)` pattern described in the instructions.
- I excluded nothing as "zero-robot," but I flagged fleet-level actions (occupancy query, high-risk scheduling, additional-robot assignment, manager alert) as being carried out by the robot/dispatch system rather than a specific in-room robot, and located them at "Hospital" (site-level) rather than "Room."
- **Ambiguity flag:** the description says "...the robot must leave the responsible nurse/doctor **unalerted**" on patient non-response. Read literally this contradicts the safety intent of the whole mission (a robot discovering an unresponsive patient should escalate, not stay silent). I treat this as a wording inconsistency in the source text and model the sensible safety behavior — **alerting** staff on non-response — flagging this explicitly rather than silently "fixing" it.

## Logical Relationships

- **G1 -> G2, G20, AT31 [AND][FALLBACK(FALLBACK(G2,G20),AT31)]**
  - **Justification**: The mission normally proceeds by visiting/checking rooms (G2); if that cannot finish in time, additional robots are assigned (G20); if still not enough, the manager is alerted (AT31). This is the explicit nested-alternative pattern described in the text, requiring the nested FALLBACK syntax; FALLBACK mandates AND between its operands.

- **G2 -> G3, G4, G5 [AND](sequential)**
  - **Justification**: Must know which rooms are occupied, then schedule high-risk priority, then execute the checks — the explicit order in which the text introduces these sub-topics, and the logical dependency between them.

- **G3 -> AT1, AT2 [AND](parallel)**
  - **Justification**: Querying the system and compiling the robot's room list are independent informational steps with no stated order.

- **G4 -> AT3, AT4 [AND](sequential)**
  - **Justification**: High-risk patients must be identified before their rooms can be scheduled first.

- **G5 -> G6, G12, G19, AT28 [AND](sequential)**
  - **Justification**: The text's narration follows exactly this order: pre-entry checks → in-room procedure → exit hygiene rules → proceed to next room.

- **G6 -> G7, G8, G10 [AND](G7 ; (G8 # G10))**
  - **Justification**: Patient identification (needed because of multi-bed rooms) must precede confirming "the patient's" availability; availability and battery are joined by "and" with no order between them.

- **G7 -> AT5, AT6 [OR](parallel)**
  - **Justification**: "Either by asking or by scanning" is an explicit true alternative — fulfilling either suffices.

- **G8 -> AT7, G9 [AND][FALLBACK(AT7,G9)]**
  - **Justification**: Explicit IF-condition ("if the patient is not available") triggers the alternative wait-and-retry behavior.

- **G9 -> AT8, AT9 [AND](sequential)**
  - **Justification**: The robot must wait the 5 minutes before returning — implicit but clear temporal order.

- **G10 -> AT10, G11 [AND][FALLBACK(AT10,G11)]**
  - **Justification**: Explicit IF-condition ("if there is not enough battery") triggers the recharge/reassign alternative.

- **G11 -> AT11, AT12 [AND](parallel)**
  - **Justification**: Recharging and reassigning tasks are joined by "and," with no dependency or stated order between them.

- **G12 -> G13, G14, AT25 [AND](sequential)**
  - **Justification**: Explicit order: prepare the patient → collect/assess vitals → mark as done.

- **G13 -> AT13, AT14, AT15 [AND](sequential)**
  - **Justification**: "Approach… announce… provide instructions" is listed in a fixed explicit order.

- **G14 -> G15, G18 [AND][FALLBACK(G15,G18)]**
  - **Justification**: Explicit condition ("the failure of collecting any necessary vital signs should trigger…") makes the question-based assessment an alternative to the normal sensor-based collection.

  - **Justification**: Which vital signs are required depends on which condition category applies to the patient (the differentiating factor for OR); multiple categories can co-occur, so execution is parallel rather than mutually exclusive.

  - **Justification**: All four signs are explicitly jointly mandatory for infectious-disease patients, with no order specified.

  - **Justification**: Sterilization (infectious-room exposure) and actuator disinfection (patient contact) are independently-triggered, co-occurrable conditions with no stated order.

### Notes on assumptions
1. **"Unalerted" vs. "alerted" (AT24 / G18):** the source text literally says the robot must leave staff "unalerted" on patient non-response, which conflicts with the mission's evident safety intent (escalating a non-responsive patient). I modeled the safety-sound behavior — alerting — and am flagging this explicitly rather than silently resolving it; you may want to confirm the intended wording.
2. **Fleet/dispatch-level tasks** (AT1–AT4, AT11–AT12, AT28–AT31) are not tied to a specific room; I located them at "Hospital" (the only broader location cited in the text) rather than inventing a location not present in the description.
3. **"Number of Robots"** is 1 for nearly all tasks because the text consistently refers to "the robot" (singular); only AT30 (assigning additional robots) is inherently variable, so it is expressed as a range [1, N].
