# Mission Decomposition: Hospital Vital-Signs Checking Robot(s)

## Step-by-Step Reasoning

Before presenting the model, here is the reasoning path I followed, including the ambiguities I had to resolve and how I resolved them.

**1. Finding the root intention.** The mission is triggered periodically ("every two hours") and has two concerns running throughout: (a) actually visiting/checking patients, and (b) guaranteeing the mission finishes in time, escalating to extra robots or a human manager if it can't. These are distinct intentions (one is "do the clinical work", the other is "manage feasibility/resourcing"), so I made them two AND-siblings under one root, running in **parallel** (`#`) because the feasibility-monitoring/escalation can be triggered at any point while rooms are being visited — nothing in the text says one must finish before the other starts.

**2. The "visit every room" goal.** The text splits into (i) a scheduling constraint — high-risk patients must be seen in the first 15 minutes — and (ii) the generic per-room procedure applied to *every* room. Rather than duplicating the whole checking subtree for "high-risk rooms" vs "other rooms" (which would violate the no-redundancy rule), I modeled prioritization as a separate scheduling goal that feeds into the same generic per-room procedure, related **sequentially** (schedule first, then execute).

**3. Per-room procedure follows the text's explicit ordering.** The description itself gives the order: "**Before** entering the room..." → "**Once inside** the room..." → "**Once** the patient is checked...". Because the order is explicitly stated, I used **sequential (`;`)**, not parallel, for these three phases.

**4. Pre-entry checks.** Identifying *which* patient (needed because "rooms may have one or more beds") logically has to happen before you can ask "is *that* patient available," so identification is sequential before the availability/battery checks. Availability and battery, however, are joined only by "and" with no stated order and are logically independent (one concerns the patient, one concerns the robot) — I modeled them as **parallel**.

**5. Identification method (ask vs. scan).** The text says "**either** by asking **or** by scanning" — two interchangeable, non-ordered alternatives. This is **not** a fallback, because the rules explicitly forbid using FALLBACK unless the order/trigger is stated, and no such order is given here. So: **OR decomposition** (one suffices) with a **parallel** runtime tag (closest fit for "available options, no mandated order").

**6. Availability and battery contingencies are genuine fallbacks.** Both are triggered by explicit IF-conditions ("if the patient is not available…", "if there is not enough battery…"), which is exactly the textbook trigger for the FALLBACK operator.

**7. ⚠️ A contradiction I must flag.** The description says: *"If the patient is **not available**, the robot should come back in **5 minutes**. However, if the patient is **unavailable**, the robot must wait **at least 20 minutes**."* "Not available" and "unavailable" are the same condition, but given two different, conflicting durations. I treated this as an inconsistency in the source description and resolved it by keeping **"at least 20 minutes"**, since it is phrased with the stronger deontic modal ("must" vs. "should") and a more precise quantifier ("at least"). **I recommend this be clarified with the stakeholder**, as a real implementation cannot honor both constraints simultaneously.

**8. Battery fallback has a compound alternative.** "Recharge **and** reassign" are two actions both required on failure, joined with no explicit order → modeled as AND, **parallel** to each other, nested inside the FALLBACK's second branch: `FALLBACK(check, (recharge # reassign))`.

**9. In-room interaction splits into a Perform goal and an Achieve goal.** "Approach, announce, provide instructions" are concrete actions whose purpose is simply to be executed (matches the **Perform** goal definition, like the "Enter the Car" example) — success doesn't hinge on reaching a retained world-state beyond doing them. Collecting vital signs, in contrast, has a real target condition (signs obtained, or escalation performed) — that's an **Achieve** goal. These two are sequential (brief, then check), matching the text's order.

**10. Measuring vitals is a Query goal.** The actual act of reading heart rate, blood pressure, etc. is about *retrieving data from the world* (physiological values), which matches the Query goal definition ("Fetch Occupied Rooms" example) far better than Perform or Achieve. The higher-level "Collect Required Vital Signs" goal (Achieve) wraps this Query goal together with the failure-handling chain.

**11. Nested fallback for vitals.** The text gives two chained conditionals: failure to collect → ask questions; no response to questions → alert nurse/doctor. This is exactly the `FALLBACK(FALLBACK(exp1, exp2), exp3)` pattern from the definitions.

**12. Conditional vital signs by patient condition.** Infectious disease → HR, BP, Temp, SpO₂; post-surgical → HR, SpO₂; diabetes history → Glucose. These conditions determine *which subset* of children is mandatory for a given patient, but structurally they are still complementary (not alternative) checks, so I kept **AND** decomposition and noted patient-condition as a variable monitored by the parent goal (per the task-property rule), rather than inventing a conditional operator that doesn't exist in the formalism.

**13. Sterilization and actuator disinfection are two independent, condition-triggered decontamination steps** (one keyed to "infectious disease room," the other to "patient contact"), with no stated order between each other, so they're parallel, sandwiched sequentially between "mark as done" and "proceed to next room."

**14. Mission-feasibility escalation** is itself a two-step fallback: try adding robots first; alert the manager only if *no combination* of robots works — explicitly conditioned, hence FALLBACK.

**15. Zero-robot check.** Every leaf task here is something a robot (or the fleet) executes — identification, scheduling, recharging, alerting, measuring, disinfecting, etc. I found no goal in the text that is purely administrative with zero robot involvement, so nothing was excluded on that basis.

## Logical Relationships

- **G1 → G2, G14 [AND] (parallel)**
  - *Justification*: Clinical checking and mission-time feasibility are both mandatory, independently triggerable concerns; nothing in the text orders one before the other.

- **G2 → G3, G4 [AND] (sequential)**
  - *Justification*: High-risk scheduling must be established before/while visits execute, since it dictates visiting order.

- **G3 → AT1, AT2 [AND] (sequential)**
  - *Justification*: Must identify who is high-risk before scheduling them early.

- **G4 → G5, G9, G13 [AND] (sequential)**
  - *Justification*: Explicit textual order — "Before entering...", "Once inside...", "Once checked...".

- **G5 → G6, (G7#G8) [AND] (sequential then parallel)**
  - *Justification*: Identification must precede knowing whose availability to check; availability and battery are independent and unordered relative to each other.

- **G6 → AT3, AT4 [OR] (parallel)**
  - *Justification*: "Either...or" signals interchangeable alternatives; no explicit order/failure-trigger rules out fallback.

- **G7 → AT5, AT6 [AND] FALLBACK(AT5, AT6)**
  - *Justification*: Explicit IF-condition triggers the alternative ("if not available/unavailable...").

- **G8 → AT7, (AT8#AT9) [AND] FALLBACK(AT7, (AT8#AT9))**
  - *Justification*: Explicit IF-condition ("if there is not enough battery...") triggers recharge+reassignment, themselves unordered.

- **G9 → G10, G11 [AND] (sequential)**
  - *Justification*: Briefing is described before vitals collection, and logically must precede it (patient needs instructions first).

- **G10 → AT10, AT11, AT12 [AND] (sequential)**
  - *Justification*: Explicit order — approach, then announce, then instruct.

- **G11 → G12, AT18, AT19 [AND] FALLBACK(FALLBACK(G12, AT18), AT19)**
  - *Justification*: Two chained explicit conditionals (collection failure → questions; non-response → alert).

- **G12 → AT13, AT14, AT15, AT16, AT17 [AND] (parallel)**
  - *Justification*: All are complementary readings; no order given; which ones are mandatory per patient is a condition-dependent variable monitored by G12, not a change in decomposition type.

- **G13 → AT20, (AT21#AT22), AT23 [AND] (sequential, with parallel middle)**
  - *Justification*: "Mark done... proceed" is explicit order; sterilization/disinfection are condition-triggered and unordered relative to each other, but must happen before departure.

- **G14 → AT24, AT25 [AND] FALLBACK(AT24, AT25)**
  - *Justification*: Explicit chained conditionals — add robots first; alert manager only if that still fails.

## Flags & Assumptions Worth Confirming with the Stakeholder

1. **Contradiction (5 min vs. 20 min)** — resolved in favor of "at least 20 minutes" (see reasoning §7); please confirm this is the intended value.
2. **Single robot per room** — I assumed one robot handles a given room at a time, with "additional robots" only entering as a mission-level (not per-room) resourcing mechanism, since the text consistently refers to "the assigned robot" in the singular for room-level work.
3. **Recharge/alert locations** — "charging station" and "nurse/doctor's location" are not named in the text, so I mapped these tasks to the broadest explicitly-cited containing location ("Hospital"/"Room") rather than inventing a new location label.
4. **Conditional vital-sign applicability** — modeled as a patient-condition variable monitored by the "Measure Patient's Vital Signs" goal rather than as a structural OR, since multiple signs are jointly (not alternatively) required per condition.
