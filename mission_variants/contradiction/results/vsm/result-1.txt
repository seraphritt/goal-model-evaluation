# Mission Decomposition — Hospital Vital-Signs Rounds (Multi-Robot System)

## Step-by-step reasoning (summary)

1. **Found the root intention.** The text opens with the periodic trigger ("every two hours, all patients' vital signs should be checked"). Everything else in the paragraph is *how* that gets accomplished, so this becomes the root goal **G1**, and it is an **Achieve** goal because it names a target world-state (all patients checked) that must be *reached*, not a single action.
2. **Split "normal flow" from "escalation flow".** The sentences about additional robots and manager alerting are explicitly condition-triggered alternatives to the normal round ("in case of impossibility…", "if no combination of robots can complete…"). Per the FALLBACK rule, these become a nested `FALLBACK` chain hanging off G1, not siblings in a plain AND.
3. **Modeled "visit every occupied room" as one goal applied over a room collection**, rather than duplicating a whole subtree per room — the `Location` property of the leaf tasks (a collection: *occupied rooms*) captures the iteration, so the tree doesn't need to repeat itself for "room 1", "room 2", etc.
4. **Treated the high-risk/15-minute rule as a prerequisite query+ordering step**, sequential with the actual round, since you logically need to know which rooms are high-risk before you can guarantee visiting them first.
5. **Pulled out every explicit IF/failure clause as a FALLBACK**: patient-unavailable → wait 5 min; battery-insufficient → recharge & reassign; vital-sign collection failure → ask questions; mission infeasible → add robots → alert manager.
6. **Checked the "non-response → leave the nurse/doctor unalerted" clause against the zero-robot rule.** Read literally, "leaving someone unalerted" is *not* an action any robot performs — it's an explicit no-op. Per the rule "goals/tasks not performed by any robot must not be in the model," I excluded this branch rather than silently reinterpreting it as "alerted." **Flagging this for you**: if this was a typo for "alerted," a task *Notify Responsible Nurse/Doctor* should be added as the second branch of G12's nested fallback — tell me and I'll patch the model.
7. **Avoided redundancy**: heart rate and blood-oxygenation measurement are physically identical actions whether triggered by the infectious-disease rule or the post-surgical rule, so the same task nodes (AT13, AT16) are reused under both branches instead of being duplicated.
8. **Used OR specifically for true alternatives named with "either…or"** (identify patient by asking **or** scanning) and for condition-dependent applicability (which vital-sign set applies depends on the patient's condition, and not every patient has every condition) — this is different from AND, which I reserved for jointly-required items connected by "and" in the text (e.g., the four infectious-disease vitals).
9. **Classified goal types against the given examples**: retrieving information (room lists, risk status, patient identity) → Query; reaching a world-state through planning (availability confirmed, battery confirmed, signs collected) → Achieve; short fixed action sequences with no further planning (approach/announce/instruct, post-visit wrap-up) → Perform.
10. **Collapsed true single-action branches into Tasks directly** (e.g., glucose measurement, manager alert) rather than wrapping a single child in an otherwise-empty Goal, since AND/OR decomposition requires at least two children.

## Notes & Assumptions

- **Locations** used are strictly those named in the text: *Room* (the patient's room) and *Hospital* (the general facility, used for hospital-wide actions like retrieving occupancy data, recharging, or reassigning tasks — the text never names a specific charging bay or nurse station, so I did not invent one).
- **Robot counts** default to **1**, mirroring "**the assigned robot** should visit every occupied room" (singular). Variability only appears in the escalation branch, where the text explicitly allows *multiple* additional robots.
- Reused task IDs (AT13, AT16) appear under two parents (G14 and G15) by design — see point 7 above.

## Logical Relationships

- **G1 -> G2, G17, AT25 [AND][FALLBACK(FALLBACK(G2,G17),AT25)]**
  - *Justification*: G2 is the normal round; G17 (additional robots) and AT25 (manager alert) are explicit condition-triggered alternatives chained by failure ("in case of impossibility…", "if no combination…"), which forces AND.

- **G2 -> G3, G4 [AND][sequential]**
  - *Justification*: priority data (G3) is needed before visiting in priority order (G4); AND because both are required for correct execution.

- **G3 -> AT1, AT2 [AND][parallel]**
  - *Justification*: occupancy and risk data are jointly needed; no order stated between fetching them.

- **G4 -> G5, G9, G16 [AND][sequential]**
  - *Justification*: text explicitly orders pre-entry checks → in-room procedure → post-visit actions.

- **G5 -> G6, G7 [AND][parallel]**
  - *Justification*: "check if the patient is available... and if there is enough battery" — joint requirement, no stated order.

- **G6 -> AT3, AT4 [AND][FALLBACK(AT3,AT4)]**
  - *Justification*: unavailability explicitly triggers the "come back in 5 minutes" alternative.

- **G7 -> AT5, G8 [AND][FALLBACK(AT5,G8)]**
  - *Justification*: insufficient battery explicitly triggers recharge + reassignment.

- **G8 -> AT6, AT7 [AND][parallel]**
  - *Justification*: "recharge... and tasks need to be reassigned" — joint, no stated order.

- **G9 -> G10, G11, G12, AT19 [AND][sequential]**
  - *Justification*: identification must precede approaching a named patient; approach/announce/instruct precede vitals collection; disinfection explicitly follows contact.

- **G10 -> AT8, AT9 [OR][parallel]**
  - *Justification*: "either by asking... or by scanning..." is an explicit alternative; one method suffices.

- **G11 -> AT10, AT11, AT12 [AND][sequential]**
  - *Justification*: text lists approach, announce, instruct in that explicit order.

- **G12 -> G13, AT18 [AND][FALLBACK(G13,AT18)]**
  - *Justification*: failure to collect any sign explicitly triggers the assessment-questions alternative.

- **G13 -> G14, G15, AT17 [OR][parallel]**
  - *Justification*: each branch applies only if the patient has that specific condition; fulfilling the applicable branch(es) suffices (OR), with no stated order among them (parallel).

- **G14 -> AT13, AT14, AT15, AT16 [AND][parallel]**
  - *Justification*: "heart rate, blood pressure, body temperature, and blood oxygenation" — explicit conjunction, no order.

- **G15 -> AT13, AT16 [AND][parallel]**
  - *Justification*: "heart rate and blood oxygenation" — explicit conjunction; tasks reused from G14 to avoid redundant duplication of the same physical action.

- **G16 -> AT20, AT21, AT22 [AND][sequential]**
  - *Justification*: mark-done and proceed are explicitly chained; sterilization is tied to the moment of exiting an infectious-disease room, placed between them.

- **G17 -> AT23, AT24 [AND][sequential]**
  - *Justification*: additional robots must be made available before pending rooms can be reassigned to them (inferred operational necessity).
