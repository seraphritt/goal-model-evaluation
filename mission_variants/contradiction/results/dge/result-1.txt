# Multi-Robot Goal Model — Resource Collection & Delivery Mission

## Step-by-Step Reasoning

Before building the tables, I walked through the description several times to separate **intentional objectives (goals)** from **operational steps (tasks)**, and to catch every conditional/exception clause, since those are the strongest signal for FALLBACK relations.

**1. Identifying the root intention.**
The very first sentence — "a robot must collect the required resources... and deliver them... to the requesting agent" — gives two clearly distinct macro-phases that the text itself names explicitly: *"In the collection phase..."* and *"Once retrieved, the delivery phase begins."* The phrase "once...begins" is an explicit temporal marker, so I modeled the root as an **AND** with a **sequential** runtime (collection must complete before delivery starts) — not a fallback, since there's no failure/alternative condition here, just ordering.

**2. Finding the FALLBACK triggers.**
I scanned for conditional language ("If...", "In case of..."), which the instructions flag as the fallback signal:
- *"If the battery...runs low (10%) in the collection phase..."* → FALLBACK in the collection subtree.
- *"If the battery...runs low (30%) in the delivery phase..."* → FALLBACK in the delivery subtree.
- *"In case of failure to return the resource to a checkpoint..."* → a **nested** FALLBACK inside the delivery-battery-handling goal (exactly the `FALLBACK(FALLBACK(...), ...)` pattern described in the rules... except here it's one level: `FALLBACK(G8, G9)`).

No other "if/in case" clauses exist, so I avoided inventing extra fallbacks (e.g., I did **not** add a fallback for "request fails," since the text never says the request can fail).

**3. Separating "what to know" from "what to do" (Query vs. Achieve vs. Perform).**
The sentence *"The order to be followed is defined by the estimation of waiting time summed up with the path to be run"* is purely informational — the robot isn't changing the world, it's computing a value. That's a textbook **Query Goal** (cf. the "Fetch Occupied Rooms" example). Everything else that results in a changed world-state (resources retrieved, robot relocated, task reassigned) is an **Achieve Goal**, because each has a concrete target condition. The one exception is the failure-handling goal ("suppress the alert, send the report") — these are two flat, unconditional actions with no further state to reach, so I classified it as a **Perform Goal**.

**4. Avoiding redundancy / zero-robot nodes.**
I did **not** create a separate goal node to represent "multiple robots work in parallel on different storages/items," because:
- The parallel-operator rule explicitly forbids `exp1` and `exp2` being the same goal — and this is literally the *same* collect-deliver goal running on different robots, not two distinct intentions.
- Duplicating the whole subtree per storage would violate the "avoid redundancy — same underlying intention = one goal" rule.
Instead, I captured this behavior at the **task** level via a `[1, n]` / `[1, m]` **Number of Robots** range, with the variable bound justified directly by the "multiple robots can be assigned to parallel collect-deliver tasks" sentence.
- Every leaf task is robot-executed, so nothing was dropped for the zero-robot rule.

**5. Avoiding fabricated steps.**
I initially considered splitting delivery into "load" + "travel," but the description never mentions loading — only "take all the resources to the specified location." Per the "don't make up" principle, I collapsed this into a single task (`AT6`) rather than inventing an unstated step, and instead let a *task* (not a wrapper goal) sit directly as one branch of the FALLBACK, since FALLBACK's expressions can be tasks or goals.

**6. Choosing parallel vs. sequential for AND-joined actions.**
Where the text gives no explicit ordering word ("and") *and* there's no logical dependency between the two actions, I used **parallel** (`#`) — e.g., "suppress the alert **and** send the report" (independent, no stated order) and "goes back to the recharging station **and** assigns the mission" (reassignment doesn't require the robot to have physically arrived). Where a dependency exists — the new robot "**will know where the resource is positioned**," implying the resource must already be placed — I used **sequential** (`;`): return-to-checkpoint before reassignment.

**7. No OR decompositions.**
The description never offers true alternatives ("either X or Y, pick one permanently"); every branch is either a joint requirement (AND) or a normal-path/exception-path pair (FALLBACK, which the rules force to be AND). So the final model intentionally contains **zero OR nodes** — this is a deliberate, justified choice, not an omission.

## Logical Relationships

- **G1 -> G2, G6 [AND](sequential)**
  - **Justification**: Both collection and delivery are mandatory parts of the mission, and the text explicitly states delivery begins only "once retrieved" — an explicit sequential marker, not a fallback (no failure/exception condition here).

- **G2 -> G3, G4, G5 [AND][FALLBACK((G3;G4), G5)]**
  - **Justification**: G3 (order) must precede G4 (retrieval) — sequential, since you can't follow an order you haven't computed. The pair (G3;G4) is the "normal" collection behavior; G5 is the explicit battery-triggered alternative ("If the battery...runs low...in the collection phase"). FALLBACK mandates AND between the normal path and the exception path.

- **G4 -> AT1, AT2, AT3 [AND](sequential)**
  - **Justification**: The description gives an explicit order of physical steps — reach the storage, then request, then wait — each a precondition for the next.

- **G5 -> AT4, AT5 [AND](parallel)**
  - **Justification**: Both actions are required, but the text gives no explicit order ("goes back...and assigns") and there's no dependency forcing one to finish before the other — the robot can broadcast the handoff while returning.

- **G6 -> AT6, G7 [AND][FALLBACK(AT6, G7)]**
  - **Justification**: Normal delivery runs (AT6) are attempted; G7 is the explicit battery-triggered alternative ("If the battery...runs low...in the delivery phase"). FALLBACK forces AND.

- **G7 -> G8, G9 [AND][FALLBACK(G8, G9)]**
  - **Justification**: The text contains a second, nested conditional — "In case of failure to return the resource to a checkpoint" — an explicit exception to the exception, modeled as a nested FALLBACK where G8 is the normal contingency path and G9 is the failure-of-contingency path.

- **G8 -> AT7, AT8 [AND](sequential)**
  - **Justification**: Reassignment ("will know where the resource is positioned") logically and textually follows the physical placement of the resource at the checkpoint.

- **G9 -> AT9, AT10 [AND](parallel)**
  - **Justification**: Both actions are mandatory on failure, but nothing in the text orders suppressing the alert before/after sending the report — they're independent and can be executed concurrently.

- **G4 -> AT1, AT2, AT3** / **G5 -> AT4, AT5** / **G8 -> AT7, AT8** / **G9 -> AT9, AT10**: all **AND**, since in every case the decomposition expresses *jointly required* steps (no "either/or" alternative is ever offered by the description), which is why the model contains **no OR decompositions** at all — a deliberate outcome of the analysis, not an oversight.

### A note on reliability
This decomposition reflects my best structured reading of the text; a couple of judgment calls (parallel vs. sequential where the text only says "and," and the "checkpoint" location for the two failure-handling tasks) are reasonable but not unambiguous — if you have additional mission detail on those points, I can revise the corresponding runtime annotations or Location fields accordingly.
