# Multi-Robot Collect-and-Deliver Mission — Goal Model Analysis

## 1. Step-by-Step Reasoning

**Step 1 — Identify the overall mission intent.**
The description centers on one recurring mission pattern: *"collect the required resources in the storage and deliver them to the requesting agent in a specified location."* This is clearly a target-state-driven objective (resources must end up delivered), so the root node is an **Achieve Goal**, not a Perform (too complex/multi-step for a single action) or Query (it changes the world, it doesn't just retrieve information).

**Step 2 — Split into phases.**
The text explicitly names two phases — "collection phase" and "delivery phase" — and states "*Once retrieved, the delivery phase begins*," which is an explicit temporal order. This is a textbook **sequential runtime** relation (not parallel, not fallback, since there's no condition/exception involved — just a stated order of two normal phases). I avoided using the Fallback operator here, since Fallback is reserved for normal-vs-exception behavior, not for two normal successive phases.

**Step 3 — Decompose the Collection phase.**
Two distinct intentions are present:
- Determining *in what order* to visit storages (an information-gathering activity: waiting time + path cost estimation) → this doesn't change the world, it only informs planning, so I classified it as a **Query Goal**.
- Actually visiting a storage and retrieving the resource (navigate + request + wait) → an **Achieve Goal**, since it's about reaching the state "resource retrieved."

These two are sequential ("the order to be followed is defined by..." happens logically before "once the robot reaches one storage...").

**Step 4 — Identify the first Fallback (collection-phase battery).**
*"If the battery... runs low (10%) in the collection phase, the robot goes back to the recharging station and assigns the mission to another robot."* This is an explicit IF-triggered alternative to normal behavior → **Fallback**, mandatorily paired with an **AND** decomposition (per the modeling rules), between "normal collection routine" and "handle low battery."

**Step 5 — Decompose the Delivery phase.**
"*The robot will make as many runs as necessary*" is the normal behavior (a single operational Task, since it's a concrete repeatable action with a location and robot count — no further intentional sub-goals are described for it).

**Step 6 — Identify the second Fallback (delivery-phase battery) — and an important inconsistency.**
Here the description is **self-contradictory**:
- Sentence A: *"If the battery... runs low (30%) in the delivery phase, the robot must return the resource to a checkpoint and assign the remaining task to another robot..."*
- Sentence B (immediately after): *"However, when the battery reaches 30% during the delivery phase, the robot must continue delivering the resources without returning them to a checkpoint or reassigning the task..."*

Both sentences use the same 30% threshold and the same phase, yet prescribe opposite behaviors, with no distinguishing condition given (e.g., no different sub-threshold, no mention of "if resource is close to destination," etc.). **I'm flagging this as a requirements conflict that should be clarified with the mission stakeholders.** For the purposes of building a concrete, implementable goal model, I modeled the mission using **Sentence A**, because:
- It is the only one of the two with elaborated, structured follow-up behavior (the checkpoint-failure/alert/report clause attaches specifically to it), suggesting it is the intended, fully-specified design.
- Sentence B introduces no new actionable detail (no location, no task) and reads like either an erroneous duplicate/override or a leftover edit — it cannot itself be modeled as a task per the "do not invent/zero-robot" rules without more detail.
I did **not** create a goal node for Sentence B since including it as stated would directly contradict Sentence A's fallback without any discriminating trigger, and because, left as written, it specifies no concrete operational action beyond "keep doing what you were doing" (i.e., it adds nothing that AT6 doesn't already cover). I recommend this contradiction be resolved in a future revision of the mission description.

**Step 7 — The nested Fallback (checkpoint-return failure).**
*"In case of failure to return the resource to a checkpoint, an alert must be triggered and the report sent to the sector manager."* This is a second, nested Fallback specifically attached to the "return resource to checkpoint" task (not to the whole low-battery-handling goal), so I nested it one level deeper, consistent with the rule that Fallback is a strictly binary operator requiring nesting for more than two alternatives.

**Step 8 — Handling "multiple robots in parallel."**
*"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks."* I deliberately avoided duplicating the whole G1 pipeline into parallel goal branches, because the mission pattern (collect → deliver) is always the *same intention* regardless of how many items are requested — duplicating it would violate the "avoid redundancy / one goal per distinct intention" rule. Instead, I captured this parallelism using the **Number of Robots** attribute (a range **[1, n]**) on the core operational tasks that are actually said to be parallelizable (navigating to storage, requesting/retrieving, and executing delivery runs), where *n* is a mission-dependent variable representing how many distinct storage/item pipelines are running concurrently. This is a more faithful and non-redundant modeling choice.

**Step 9 — Goods/equipment examples.**
The sterile-equipment and clean-linen examples are illustrative instantiations of "storage," "use destination," and "storage room" — they introduce no new robot action, so per the "zero-robot nodes must not appear" rule, I did not create separate goals/tasks for them; they're simply concrete fillers for the generic `storage` / `specified location` variables already in the model.

**Step 10 — Check for OR-decompositions.**
I deliberately looked for genuine "either/or" alternatives (OR decomposition requires *choice*, not sequencing/parallelism/fallback). None exist in this description — every branching behavior is either a joint (AND) requirement or a conditionally-triggered Fallback. So the final model contains **no OR decompositions**, which I note explicitly rather than forcing one in artificially.

## 5. Logical Relationships

- **G1 -> G2, G7 [AND] (sequential)**
  - **Justification**: Both collection and delivery are required to fulfill the mission; the text explicitly states delivery "begins" only once collection is complete.

- **G2 -> G3, G6 [AND] FALLBACK(G3, G6)**
  - **Justification**: Explicit IF-triggered exception (10% battery) to the normal collection routine; Fallback mandates AND decomposition.

- **G3 -> G4, G5 [AND] (sequential)**
  - **Justification**: The visiting order must be determined before storages are visited in that order.

- **G4 -> AT1 [AND]**
  - **Justification**: AT1 is the sole operational step realizing the order-estimation goal.

- **G5 -> AT2, AT3 [AND] (sequential)**
  - **Justification**: The robot must reach the storage before it can request/await the resource, per the stated order of events.

- **G6 -> AT4, AT5 [AND] (sequential)**
  - **Justification**: Returning to the station and reassigning the mission are both required; listed in that order in the text.

- **G7 -> AT6, G8 [AND] FALLBACK(AT6, G8)**
  - **Justification**: Explicit IF-triggered exception (30% battery) to normal delivery runs; Fallback mandates AND.

- **G8 -> G9, AT10 [AND] (sequential)**
  - **Justification**: The resource's disposition (checkpoint placement, or the alert fallback) must be resolved before the task handoff, since the next robot needs to know "where the resource is positioned."

- **G9 -> AT7, G10 [AND] FALLBACK(AT7, G10)**
  - **Justification**: Explicit "in case of failure" clause describes an alternative to the normal checkpoint-return action; Fallback mandates AND.

- **G10 -> AT8, AT9 [AND] (parallel)**
  - **Justification**: Both the alert and report are required ("and"), but no explicit order is stated between them, so they are modeled as able to occur in parallel.

## 6. Open Issues / Assumptions Worth Flagging

1. **Contradiction in the source text** (delivery-phase battery at 30%): two opposite behaviors are specified for the same condition. The model follows the fully-elaborated rule (return to checkpoint + reassign + alert-on-failure); this should be confirmed/corrected with stakeholders.
2. **Inferred locations** (AT5, AT8, AT9, AT10 all use the nearest cited location as a proxy, since no new location is explicitly named for those specific sub-actions) — worth confirming during design review.
3. **No OR-decompositions** appear anywhere in this mission, since the description contains no genuine either/or choices — only joint (AND) requirements and conditional (Fallback) exceptions.
