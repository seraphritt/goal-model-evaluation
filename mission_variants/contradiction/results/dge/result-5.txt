# Mission Analysis: Goal Model for Resource Collection & Delivery

## Step-by-Step Reasoning

**1. Identifying the actors and the overall intention.**
The description centers on a single recurring mission pattern: *a robot collects resources from storage and delivers them to a requesting agent*. This is clearly a goal that requires planning and sequencing (visit storages → request → wait → deliver), and its success is defined by reaching a concrete end-state (resources delivered). That makes the root node an **Achieve Goal**, not a Perform goal (it's not a single atomic action) and not a Query goal (nothing is being merely *queried*, resources are physically moved).

**2. Splitting into phases.**
The text explicitly separates two phases with an explicit temporal trigger: *"Once retrieved, the delivery phase begins."* This is a clear, stated ordering → **sequential runtime (`;`)** between Collection and Delivery, not parallel (they cannot both start at once) and not fallback (delivery is not an alternative to collection, it's a necessary continuation).

**3. Inside the Collection phase.**
Two necessary, ordered actions appear: (a) travel to storage(s) in an order defined by waiting-time + path estimation, and (b) once at a storage, send a request and wait for retrieval. The text's own wording ("*Once the robot reaches one storage... sends a message...*") signals sequential execution.

**4. Battery-at-10%-during-collection clause.**
This is a **threshold/condition** ("if battery runs low") that triggers an *alternative* behavior (return to recharge + reassign) instead of the normal flow. Per the given definitions, an explicit condition triggering an alternative behavior **must** be modeled as FALLBACK, never as OR (OR would imply either path is equally acceptable from the start, which is not the case here — the normal path is always attempted first).

**5. Inside the Delivery phase and the battery-at-30% clause.**
Same fallback logic applies for the 30% battery threshold during delivery (return to checkpoint + reassign).

**⚠️ Detected contradiction in the description.** I must flag this explicitly: the text states **twice**, in direct contradiction:
> *"If the battery... runs low (30%)... the robot must return the resource to a checkpoint and assign the remaining task to another robot"* **vs.** *"However, when the battery reaches 30%... the robot must continue delivering the resources without returning them... or reassigning the task."*

These cannot both be true for the same trigger condition without further disambiguating information (e.g., a second threshold, a distance-to-destination condition, or a load-state condition) that the description does not provide. Since the *subsequent* clause about "failure to return the resource to a checkpoint → alert to sector manager" **only makes sense if the checkpoint-return behavior actually happens**, I treat the first statement (return-to-checkpoint + reassign, plus its failure-handling continuation) as the operative rule, and treat the second statement as an unresolved inconsistency that should be clarified with the stakeholder rather than silently modeled as a second contradictory path. This is noted as an assumption in G6's justification below.

**6. Checkpoint-return failure clause.**
"*In case of failure to return the resource to a checkpoint, an alert must be triggered...*" — another explicit condition/failure → another **nested FALLBACK**, this time inside the battery-delivery-handling goal, between "return to checkpoint" and "trigger alert + report."

**7. Parallel multi-item clause.**
"*When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks*" uses the word "can" — a **possibility, not an obligation** — which matches the definition of the parallel operator exactly. However, this clause does not introduce a *new intention* (it doesn't create a new type of action distinct from "collect" and "deliver"); it only describes how many robot instances may run the same Collection/Delivery pipeline concurrently. Modeling it as a brand-new goal node would duplicate the intention already captured by G2/G5 (violating the "avoid redundancy" rule). I therefore represent it as a **range on the Number-of-Robots attribute** of the two "main-line" tasks (AT1, AT5), with `n` bound to the number of distinct required storages/items — this is exactly the kind of variable-bound case the Number-of-Robots definition anticipates.

**8. Examples section.**
The sterile-equipment / clean-linens examples are illustrative resource types, not additional operations or goals — they introduce no new robot behavior, so per the "zero-robot / no new intention" and anti-redundancy rules, they are **not modeled** as separate nodes.

**9. Checking for OR-decompositions.**
Scanning the whole text, every branching point is either (a) a necessary joint requirement (AND) or (b) a condition-triggered alternative (FALLBACK). There is no genuine "either-is-acceptable-from-the-start" alternative anywhere in the description, so **this model contains zero OR-decompositions** — which is correct, not an omission.

## Logical Relationships

- **G1 -> G2, G5 [AND] (sequential: G2;G5)**
  - **Justification**: Collection and delivery are both mandatory, and the description explicitly states delivery begins only *after* retrieval completes — a stated order, hence sequential rather than parallel.

- **G2 -> G3, G4 [AND] FALLBACK(G3, G4)**
  - **Justification**: G3 is the normal collection behavior; G4 is the alternative triggered only by the explicit 10%-battery condition. An explicit condition triggering an alternate path is a FALLBACK by definition, and FALLBACK mandates an AND relation between its branches.

- **G3 -> AT1, AT2 [AND] (sequential: AT1;AT2)**
  - **Justification**: Both travel and request/retrieval are required, and the text states the robot must *reach* the storage before it can send the request — an explicit order.

- **G4 -> AT3, AT4 [AND] (sequential: AT3;AT4)**
  - **Justification**: "Goes back to the recharging station **and** assigns the mission" — both actions are required, listed in that order.

- **G5 -> AT5, G6 [AND] FALLBACK(AT5, G6)**
  - **Justification**: AT5 is the normal delivery behavior; G6 is the alternative triggered only by the explicit 30%-battery condition, following the same FALLBACK logic as G2.

- **G6 -> AT6, AT7, AT8 [AND] ((FALLBACK(AT6, AT7));AT8)**
  - **Justification**: AT6 (return to checkpoint) is attempted first; AT7 (alert/report) is the explicit, condition-triggered alternative only on failure — a nested FALLBACK. AT8 (reassignment) is required regardless of which of the two preceding outcomes occurred, so it follows sequentially after the fallback pair. All three are necessary components of G6's complete specification, hence AND.

### Modeling Notes
- **No OR-decompositions appear anywhere in this model.** The description contains only joint requirements (AND) and condition-triggered alternatives (FALLBACK) — no genuine "either path is fine from the outset" branching — so this is the correct outcome, not a gap.
- **The sterile-equipment/clean-linens examples** were deliberately excluded as goal/task nodes: they illustrate resource *types*, not new robot behaviors.
- **The 30%-battery contradiction** (flagged above) is the one point in the description I'd recommend clarifying with the mission owner before finalizing this model for implementation — the current model resolves it in favor of the checkpoint-return/reassignment behavior, because the alert/report clause that follows it textually depends on that behavior existing.
