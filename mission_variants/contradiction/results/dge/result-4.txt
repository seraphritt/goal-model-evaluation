# Mission Analysis & Goal‑Model Design — Collect‑and‑Deliver Multi‑Robot Mission

## Step‑by‑Step Reasoning

**1. Identify the root intention.**
The description opens with "a robot must collect the required resources... and deliver them to the requesting agent in a specified location." This is the overarching, non‑operational intention — a classic **Achieve Goal**, since it has a clear persistent target state (resources delivered) reached through planning and action. This becomes **G1**.

**2. Split into the two explicitly named phases.**
The text names two phases outright — "collection phase" and "delivery phase" — and states "*Once* retrieved, the delivery phase *begins*." The word "once" is an explicit temporal marker, so this is a **sequential** relation, not parallel or fallback. Both phases are mandatory → **AND**. This gives **G2 (Collect)** and **G7 (Deliver)** under G1.

**3. Decompose the Collection phase.**
Two distinct intentions appear inside collection:
- Deciding **which order** to visit storages ("the order... is defined by the estimation of waiting time summed up with the path to be run") — this is pure information‑gathering, no world‑changing action → **Query Goal** (G3).
- **Actually visiting and retrieving** the resources (G4).
Since the order must be known before the robot starts moving, this is **sequential** (G3 ; G4), not parallel — the text presents it as a prerequisite computation, not an optional/parallel activity.

**4. Model the battery contingency as FALLBACK, not OR.**
"If the battery... runs low (10%)... the robot goes back... and assigns the mission to another robot" is a textbook conditional exception to normal behavior (an implicit IF‑statement keyed to a threshold). Per the rules, this must be **FALLBACK**, and FALLBACK pairs are always **AND**-related (both branches are jointly necessary for the model to describe all possible executions, even though only one path is taken at runtime). This happens twice in the description — once in collection (10%) and once in delivery (30%) — and a third nested time for the checkpoint‑return failure. Each becomes its own FALLBACK node (G4, G7, G9 in my numbering).

**5. Decompose the concrete, sequential physical steps into Tasks.**
"Go to storage" → "send request message" → "wait until retrieved" are concrete, assignable, located, robot‑countable actions with an explicit temporal chain ("once... and it is time to..."). These are **Tasks**, not goals, and are **sequential** (AT3;AT4;AT5).

**6. Where no explicit order is given, use parallel (#), never fallback/sequential.**
Sentences like "goes back to the recharging station **and** assigns the mission..." or "must return the resource to a checkpoint **and** assign the remaining task..." or "the alert must be suppressed **and** the report sent" use plain conjunction ("and") with **no stated first/second order**. Per the rules, FALLBACK/sequential require an *explicit* order; absent that, I used **parallel (#)**, since both actions are jointly required but not necessarily ordered.

**7. The checkpoint‑failure handling is a second, nested exception.**
"In case of failure to return the resource to a checkpoint..." is an explicit IF‑condition nested *inside* the delivery‑battery fallback → another **FALLBACK**, nested one level deeper (G9 → FALLBACK(AT9, G10)).

**8. Handling "multiple robots in parallel."**
This sentence does not introduce a new phase or action type — it describes that the *entire* collect‑deliver pipeline can be **instantiated multiple times concurrently**, one per robot, when multiple storages/items are needed. Rather than artificially duplicating the whole subtree (which would violate the "avoid redundancy" rule — it's the same underlying intention repeated), I modeled this using the **Number of Robots** task attribute as a **range `[1, m]`**, where `m` = the number of distinct storages/items required by the current request. This is exactly what the range-with-variable mechanism is for ("a value derived from... the maximum number of robots that can perform the task"). I applied this range to all collection‑related tasks and to the main delivery‑transport task, since these are the ones that can be run by parallel robot instances; contingency/failure tasks keep `1`, since each is a single robot's own exception‑handling action.

**9. The two "examples of goods" are not modeled as separate goals.**
Sterile medical equipment and clean linens are explicitly introduced as *"examples of goods/equipment,"* not as distinct operational flows — no new robot action, location, or condition is attached to them beyond the generic collect‑deliver pipeline already modeled. Creating separate goals for them would (a) duplicate an already-represented intention, violating the anti‑redundancy rule, and (b) risk adding zero-robot "goals" since no new robot behavior is described for them specifically. I therefore treat "resource" as the generic parameterized type the whole tree already operates on.

**10. Every decomposition in this mission is AND, never OR.**
There are no genuine *alternative* options in the text (no "either/or" choice a robot makes toward fulfilling the same intention). Parallel execution, sequencing, and fallback are explicitly excluded from being modeled as OR by the given rules — so OR simply never applies here. I verified this holds for every node.

## Goal List (required format)

```
G1:  Fulfill Resource Request                         G2;G7
G2:  Collect Required Resources                        G3;G4
G3:  Determine Storage Visit Order                     AT1#AT2
G4:  Visit Storages and Retrieve Resources             FALLBACK(G5,G6)
G5:  Perform Normal Collection                         AT3;AT4;AT5
G6:  Handle Low Battery (Collection Phase)              AT6#AT7
G7:  Deliver Resources                                 FALLBACK(AT8,G8)
G8:  Handle Low Battery (Delivery Phase)                G9#AT12
G9:  Return Resource to Checkpoint                     FALLBACK(AT9,G10)
G10: Handle Return Failure                              AT10#AT11
```

*(m = number of distinct storages/items the current request needs; used in task robot-count ranges below.)*

## Logical Relationships

- **G1 -> G2, G7 [AND] (sequential)**
  - **Justification**: Both collection and delivery are mandatory to fulfill the request; "Once retrieved, the delivery phase begins" is an explicit temporal marker, so collection must finish before delivery starts.

- **G2 -> G3, G4 [AND] (sequential)**
  - **Justification**: The visiting order must be computed before any travel occurs — "the order to be followed is defined by..." presumes the order exists prior to movement.

- **G3 -> AT1, AT2 [AND] (parallel)**
  - **Justification**: Waiting time and path time are two independent estimations that are only combined by summation afterward; no order between the two computations is stated.

- **G4 -> G5, G6 [AND] (FALLBACK(G5, G6))**
  - **Justification**: "If the battery... runs low (10%)" is an explicit condition causing a switch from normal collection to the battery-contingency path — a textbook FALLBACK, which the rules require to be AND-related.

- **G5 -> AT3, AT4, AT5 [AND] (sequential)**
  - **Justification**: The text gives an explicit chain — reach the storage, then (once it is "time to request") send the message, then wait until retrieval — "once... and" signals strict order.

- **G6 -> AT6, AT7 [AND] (parallel)**
  - **Justification**: "goes back to the recharging station and assigns the mission to another robot" is a plain conjunction with no stated precedence, so both are modeled as possible-parallel, jointly required actions.

- **G7 -> AT8, G8 [AND] (FALLBACK(AT8, G8))**
  - **Justification**: "If the battery of the assigned robot runs low (30%) in the delivery phase" is another explicit condition, mirroring G4's structure — normal delivery vs. the battery-contingency alternative.

- **G8 -> G9, AT12 [AND] (parallel)**
  - **Justification**: "must return the resource to a checkpoint and assign the remaining task to another robot" — conjunction without explicit ordering; the receiving robot already "will know where the resource is positioned," so the assignment doesn't need to strictly wait for the physical return to finish.

- **G9 -> AT9, G10 [AND] (FALLBACK(AT9, G10))**
  - **Justification**: "In case of failure to return the resource to a checkpoint" is an explicit nested condition — the normal checkpoint-return attempt versus the failure-handling alternative.

- **G10 -> AT10, AT11 [AND] (parallel)**
  - **Justification**: "the alert must be suppressed and the report sent to the sector manager" is a plain conjunction with no stated order between the two actions.

---

A couple of modeling notes worth flagging explicitly: every decomposition in this tree is **AND** — the mission text contains no genuine alternative/choice structure, only sequencing, parallelism, and conditional fallback, none of which the rules permit to be expressed as OR. And the "multiple robots in parallel for multiple storages" behavior is captured structurally via the **`[1,m]`** robot-count ranges on the collection/delivery tasks rather than by duplicating the goal subtree, to avoid representing the same underlying intention twice.
