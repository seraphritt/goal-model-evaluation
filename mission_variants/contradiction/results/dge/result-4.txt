## Reasoning — how I decomposed the mission

**Step 1 — Identify the top-level intention.** The description opens with "a robot must collect the required resources in the storage and deliver them to the requesting agent." That's a single overarching intention with two necessary phases — collection and delivery — so I made this the root **Achieve** goal (G1), AND-decomposed into Collect (G2) and Deliver (G7). The text says "**once** retrieved, the delivery phase **begins**" — an explicit temporal marker, not a failure-triggered alternative — so I used **Sequential**, not Fallback, between them.

**Step 2 — Collection phase internals.** Three things happen here: (a) travelling to storage(s) in an order computed from waiting-time + path estimation — I split the *estimation* out as a separate **Query goal** (G4), since estimating is pure information-gathering with no physical action, distinct from the **Achieve goal** of actually being at the location (G3); (b) requesting and waiting for the resource (G5) — two tasks I kept sequential because waiting *for retrieval* is logically impossible before the request is sent, even though the text just says "and"; (c) a battery-triggered exception (G6) explicitly marked by "**If** the battery... runs low (10%)." The explicit if-condition plus a clearly stated alternate behavior is exactly the Fallback pattern, so G2 = `FALLBACK((G3;G5), G6)`.

**Step 3 — Battery-at-10% handoff.** "Goes back to recharging station **and** assigns the mission to another robot" has no causal dependency between the two actions (reassignment is a communication act that doesn't require the robot to have physically arrived) — so I modeled this pair as **Parallel**, not Sequential, deliberately contrasting it with the request/wait pair in Step 2.

**Step 4 — Delivery phase and an important inconsistency.** The description states the battery-30% rule twice, and the two statements directly contradict each other:

> ⚠️ **Flagged inconsistency**: "If the battery... runs low (30%)... the robot must return the resource to a checkpoint and assign the remaining task to another robot" is immediately followed by "However, when the battery reaches 30%... the robot must continue delivering the resources **without** returning them to a checkpoint or reassigning the task." These cannot both be true for the same 30% threshold. I modeled the **first, operationally detailed rule** (return-to-checkpoint + reassignment) as the authoritative fallback, since it is the one that carries concrete, actionable detail (what to return, where, and that the next robot must know the resource's position). The second sentence is noted here as a conflicting requirement that should be clarified with the mission stakeholders before implementation — it may indicate a second, different threshold or a special case (e.g., "continue if already within sight of the destination") that wasn't fully specified.

**Step 5 — Nested fallback on checkpoint failure.** "In case of failure to return the resource to a checkpoint, an alert must be triggered..." is a second, nested if-condition — a classic Fallback *inside* the battery-30% Fallback, so I introduced G9 to host `FALLBACK(AT7, AT8)`.

**Step 6 — Multi-item parallelism.** "Multiple robots can be assigned to parallel collect-deliver tasks" uses "**can**," matching the Parallel operator's definition (possibility, not obligation) exactly. Rather than duplicating the whole tree per item (which the goal model shouldn't do, since it describes a *type* of mission, not a specific instance), I captured this as a **Number of Robots** range on the collection/delivery tasks, reflecting that several robots may execute this same pattern concurrently when several items/storages are involved — this is noted explicitly in each relevant task's justification below.

**Step 7 — No OR-decompositions.** I found no point in the description where fulfilling *one of several* alternatives is sufficient on its own (that's what OR would require) — every split is either a mandatory joint requirement (AND) or a primary-attempt/exception pair (Fallback, which itself requires AND between its two branches). So every decomposition in this model is AND.

**Step 8 — No Perform goals.** Every intentional node in this mission is oriented toward reaching a verifiable world state (robot at a location, resources retrieved, resource at checkpoint, alert sent) — so I classified every Goal as **Achieve**, except G4 (pure information retrieval → **Query**). Atomic, single-step actions with no further planning component (send a message, physically place an object, trigger an alert) were pushed down to **Task** nodes rather than elevated to Perform goals, since they are directly assignable, location-bound, robot-countable operations — exactly the Task definition.

## Logical relationships

- **G1 -> G2, G7 [AND] (sequential)**
  - **Justification**: Both phases are mandatory for the mission to succeed; "once retrieved, the delivery phase begins" is an explicit temporal marker of normal flow, not a condition/exception, so Sequential (not Fallback) applies.

- **G2 -> G3, G5, G6 [AND] FALLBACK((G3;G5), G6)**
  - **Justification**: "If the battery...runs low (10%)" is an explicit conditional alternative to the normal go-then-request flow. Fallback mandates AND between its branches.

- **G3 -> G4, AT1 [AND] (sequential)**
  - **Justification**: The visiting order must be estimated before the robot can travel in that order ("the order to be followed is defined by the estimation...").

- **G5 -> AT2, AT3 [AND] (sequential)**
  - **Justification**: Waiting for retrieval is logically impossible before the request is sent, even though the text uses "and" rather than "then."

- **G6 -> AT4, AT5 [AND] (parallel)**
  - **Justification**: No causal dependency links returning to the station with reassigning the mission — reassignment is a communication act the robot can perform while still travelling, so Parallel (possibility, not obligation) fits better than Sequential.

- **G7 -> AT6, G8 [AND] FALLBACK(AT6, G8)**
  - **Justification**: "If the battery...runs low (30%)" is an explicit conditional alternative to normal delivery runs. (See the flagged inconsistency above — the detailed, actionable rule was modeled as the primary Fallback alternative.)

- **G8 -> G9, AT9 [AND] (sequential)**
  - **Justification**: The replacement robot "will know where the resource is positioned" only once the checkpoint placement has occurred, so G9 must precede AT9.

- **G9 -> AT7, AT8 [AND] FALLBACK(AT7, AT8)**
  - **Justification**: "In case of failure to return the resource to a checkpoint" is an explicit nested exception condition, triggering the alert/report as the fallback alternative.

- **G3 -> AT1 [AND]; G5 -> AT2, AT3 [AND]; G6 -> AT4, AT5 [AND]; G9 -> AT7, AT8 [AND]**
  - **Justification**: In every case, both tasks under the goal are jointly necessary to satisfy that goal's target condition — none of them is an optional alternative to the other, which rules out OR.
