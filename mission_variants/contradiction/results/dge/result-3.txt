# Goal Model — Multi-Robot Collect-and-Deliver Mission

## Step-by-Step Reasoning

**1. Finding the root intention.**
The whole paragraph answers one question: *"what must happen when a request for resources arrives?"* → the resources must end up with the requesting agent at a given location. That is a clear **Achieve** goal (a target condition: resources delivered), so it becomes **G1**, the root.

**2. Splitting into phases.**
The text itself names two phases explicitly — "In the collection phase…" and "Once retrieved, the delivery phase begins." This is an **explicitly stated order** (collection *then* delivery), so the relation between them is **sequential (`;`)**, not parallel and not fallback (there is no condition triggering delivery as an *alternative* to collection — it's a mandatory, ordered two-step process). Both phases are mandatory → **AND**. This gives **G2 (Collect)** and **G6 (Deliver)**.

**3. Inside the Collection phase.**
Three distinct intentions appear:
- *How* to order the visits ("order…defined by the estimation of waiting time summed up with the path") → this is pure information-gathering, no world-state change → **Query goal (G3)**.
- *Going and retrieving* ("go to storage… sends a message… waits until retrieved") → an explicit chain of three actions in stated order ("Once the robot reaches… and it is time… sends… and waits") → **sequential tasks** under an **Achieve goal (G4)**, since the intention is a state change (resource retrieved).
- *The 10%-battery exception* — the text first describes normal behavior, then says **"If the battery…runs low…"** This is precisely the trigger condition the instructions define as mandatory for **FALLBACK**: a normal path and a condition-triggered alternative. This becomes **G5**, and the collection goal's runtime is `FALLBACK((G3;G4), G5)`.

**4. Inside the Delivery phase.**
- "The robot will make as many runs as necessary" implies the robot must first figure out *how many runs* are needed (quantity vs. carrying capacity) — this mirrors G3 structurally and is a **Query goal (G8)**, feeding sequentially into the actual transport **task (AT6)** under a **Perform goal (G7)** — I classify this as Perform (not Achieve) because the sentence is phrased around repeatedly *executing* trips rather than monitoring one terminal condition (that terminal condition already belongs to G6).
- The **30%-battery exception** is again an explicit IF-triggered alternative → **FALLBACK** between normal delivery (G7) and the battery handler (G9).
- Inside the battery handler, a **second, nested exception** appears: "In case of failure to return the resource to a checkpoint…" — another explicit condition → a **nested FALLBACK** (`FALLBACK(G10, G11)`), exactly matching the spec's nested-fallback example.

**5. Why everything is AND, never OR.**
OR means *"doing just one child is enough."* Nothing in the text offers true alternatives of that kind — every pair of sub-goals I found is either (a) jointly necessary steps of one procedure, (b) a necessary order (`;`), or (c) a conditioned contingency (`FALLBACK`), and the spec itself dictates that `FALLBACK` children are always `AND`-related. So **no OR decomposition occurs anywhere in this mission** — I flag this explicitly rather than forcing an artificial OR.

**6. Why some pairs are `#` (parallel) and not `;` (sequential).**
Wherever the text joins two mandatory actions with "and" **but never states which happens first** (e.g., "goes back to the recharging station **and** assigns the mission to another robot"; "the alert must be suppressed **and** the report sent"), I used `#`, per the rule that `;` is reserved for *explicitly* ordered steps. Wherever an order is explicit or logically forced by a stated dependency (e.g., the new robot "will know where the resource is positioned" ⇒ the resource must already be at the checkpoint), I used `;`.

**7. Zero-robot check.**
Every leaf task I kept is performed by a robot (travel, messaging, waiting/monitoring, recharging, reassigning, reporting). The "Examples of goods/equipment" paragraph is **not modeled as a goal** — it only instantiates the *resource* variable (sterile equipment, linens) and introduces no new robot behavior, so including it would violate "avoid redundancy" / the zero-robot rule (the paragraph itself performs no action).

**8. Numbering.**
Depth-first pre-order traversal gives **G1–G11** and **AT1–AT10**, detailed below.

## Logical Relationships

- **G1 → G2, G6 [AND][(sequential) `G2;G6`]**
  - **Justification**: Both phases are mandatory to fulfill the mission (AND). The description explicitly states delivery starts only "once retrieved" — an explicit order, hence sequential rather than parallel or fallback.

- **G2 → G3, G4, G5 [AND][FALLBACK((G3;G4), G5)]**
  - **Justification**: Order-estimation, visiting/retrieving, and the battery contingency are all necessary facets of the described collection behavior (AND). The normal flow is explicitly ordered (determine order, then visit — sequential), and the 10% battery clause is an explicit IF-condition diverting from that normal flow, which the rules require to be modeled as FALLBACK.

- **G4 → AT1, AT2, AT3 [AND][(sequential) `AT1;AT2;AT3`]**
  - **Justification**: The description gives an explicit temporal chain ("goes to storage… then sends… then waits"). All three are jointly required to retrieve the resource (AND), each strictly following the previous (sequential).

- **G5 → AT4, AT5 [AND][(parallel) `AT4#AT5`]**
  - **Justification**: Both actions are required by "goes back…and assigns…" (AND), but no order between them is stated, so they are modeled as possibly concurrent rather than forced sequential.

- **G6 → G7, G9 [AND][FALLBACK(G7,G9)]**
  - **Justification**: The normal delivery mechanism and its 30%-battery contingency are both required aspects of the delivery phase (AND). The explicit "If the battery…runs low…in the delivery phase" clause is a condition-triggered alternative, hence FALLBACK.

- **G7 → G8, AT6 [AND][(sequential) `G8;AT6`]**
  - **Justification**: To "make as many runs as necessary," the robot must first determine how many runs are needed before executing them (sequential); both the determination and the execution are necessary (AND).

- **G9 → G10, G11 [AND][FALLBACK(G10,G11)]**
  - **Justification**: The description introduces a second, nested explicit condition ("In case of failure to return the resource to a checkpoint…"), which per the spec must be modeled as a nested FALLBACK inside the already-fallback branch G9; both resolution paths are part of incident-handling (AND).

- **G10 → AT7, AT8 [AND][(sequential) `AT7;AT8`]**
  - **Justification**: The new robot "will know where the resource is positioned," implying the resource must already be at the checkpoint before the hand-off communicates its location — an inferred but clear sequential dependency; both actions are required (AND).

- **G11 → AT9, AT10 [AND][(parallel) `AT9#AT10`]**
  - **Justification**: "The alert must be suppressed and the report sent" — joined by "and" with no stated order, so modeled as parallel-possible; both are required (AND).

### Notes on completeness
- **No OR decomposition appears anywhere** in this model — the mission contains no true alternative ("do either X or Y") constructs; every branching in the text is either a joint requirement, an explicit order, or a condition-triggered fallback, all of which the specification requires to be AND-related.
- The **goods/equipment examples** (sterile medical equipment, clean linens) were deliberately **not** modeled as separate goals: they only instantiate the generic "resource" variable already carried by G1–G11/AT1–AT10 and introduce no distinct robot behavior, so adding goals for them would violate both the "avoid redundancy" and "zero-robot" rules.
- Locations for **AT9/AT10** are the one place I had to infer (Checkpoint) rather than read directly off the text — flagged above for your review in case your source material defines a different location for the reporting step.
