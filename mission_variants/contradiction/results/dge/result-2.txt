# Mission Decomposition: Robot Resource Collection & Delivery

## 1. Step‑by‑Step Reasoning

**Step 1 – Identify the mission's intentional core.**
The description centers on a single top‑level intent: *"a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location."* This is naturally an **Achieve Goal** — there is a concrete target world‑state (resources physically at the requester's location) that the robot plans and acts toward. Everything else in the text (ordering logic, request protocol, battery contingencies, failure handling) is subordinate detail that decomposes this root goal.

**Step 2 – Split into phases.**
The text explicitly names two phases and orders them: *"Once retrieved, the delivery phase begins."* This is an explicit temporal dependency (collection must finish before delivery starts), so the relation between the Collection goal and the Delivery goal must be **Sequential (;)**, not parallel or fallback — there is no failure/condition triggering delivery, just a strict hand‑off.

**Step 3 – Decompose the Collection phase.**
Three elements appear in order:
- Determining *which storage to visit first* ("order... defined by the estimation of waiting time summed with the path") — this is information‑gathering, not world‑changing action → **Query Goal**, and it logically must happen **before** any travel (sequential).
- Traveling to the storage — a concrete, immediately assignable action → **Task**.
- Sending the resource request and waiting for retrieval — also concrete and immediately assignable → **Task**. The text explicitly sequences these two ("once the robot reaches... and it is time to request") → **Sequential (;)** between travel and request.

A **battery‑low (10%)** condition is explicitly introduced with "If..." — a textbook trigger for the **Fallback** operator: the normal travel/request path is attempted first, and only if battery drops to 10% does the robot switch to the recharge‑and‑reassign behavior.

**Step 4 – Decompose the Delivery phase.**
The normal behavior is "make as many runs as necessary" — one operational task (the looping/repetition is a task‑level execution detail, not a separate goal, since the description gives no sub‑steps to differentiate). A second **battery‑low (30%)** condition is introduced with "If...", again a clear **Fallback** trigger.

**Step 5 – Decompose the battery‑low‑during‑delivery contingency.**
This contingency itself contains a nested conditional: *"In case of failure to return the resource to a checkpoint, an alert must be triggered..."* — another explicit "in case of" trigger → a **nested Fallback**: attempt the checkpoint return; if that fails, alert + report. The reassignment of the remaining task is stated with a plain "and" and no explicit ordering word (no "once", "after", "then"), so per the strict reading of the operators, I modeled it as **Parallel (#)** with the return/fallback block rather than inventing a sequence the text doesn't state.

**Step 6 – No OR decomposition anywhere.**
Nothing in the text presents true *alternative, mutually‑exclusive ways to satisfy the same goal* (which is what OR requires). All branching is either a strict phase order, a non‑exclusive "and", or a condition‑triggered contingency — all of which the spec requires to be represented as AND (with Sequential/Parallel/Fallback runtime annotations layered on top). Consequently, **every decomposition in this model is AND**, and the runtime annotations carry all the nuance.

**Step 7 – The parallel multi‑robot clause.**
*"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks"* does **not** describe two sibling sub‑goals of one mission instance running in parallel — it describes multiple **instances** of this same goal tree being instantiated concurrently on different robots for different storages. I therefore did not add a goal node for it; instead, I reflect it as a modeling note affecting the *Number of Robots* attribute discussion (see justifications on AT1/AT5), since inventing a goal node for it would duplicate intentions already captured in G1 (redundancy is explicitly disallowed).

**Step 8 – The two illustrative examples (sterile equipment, clean linens) are not modeled.**
They are domain examples of "resources," not additional actions performed by a robot, so per the rule that goals/tasks not performed by a robot must be excluded, no nodes are created for them.

## ⚠️ Critical Inconsistency Found — Needs Stakeholder Clarification

The description contains two directly contradictory statements about the **same condition** (battery at 30% during delivery):

> "If the battery... runs low (30%) in the delivery phase, the robot must return the resource to a checkpoint and assign the remaining task to another robot..."

> "However, when the battery reaches 30% during the delivery phase, the robot must continue delivering the resources **without** returning them to a checkpoint or reassigning the task..."

These cannot both be true for the same trigger. For this model, I chose to **retain the first (operationally detailed) rule** — including the checkpoint‑return, reassignment, and alert/report behavior — because:
1. It mirrors the symmetric, well‑specified pattern already established for the 10% collection‑phase contingency.
2. It is the only version that gives the subsequent sentence ("In case of failure to return the resource to a checkpoint, an alert must be triggered...") something to attach to — if the "however" clause were authoritative, that failure‑handling sentence would be orphaned/unreachable.

I flag the second statement as a likely drafting error (possibly meant to apply to a different threshold) and recommend the mission owner confirm the intended behavior. The model below can be trivially re‑wired to the alternative reading if clarified.

## 5. Logical Relationships

- **G1 -> G2, G5 [AND] (sequential: G2;G5)**
  - **Justification**: Both the collection and delivery phases are required (AND) for mission success. The text explicitly states delivery starts only after retrieval completes ("Once retrieved, the delivery phase begins"), so they are sequential, not parallel.

- **G2 -> G3, AT1, AT2, G4 [AND] [G3;(FALLBACK((AT1;AT2), G4))]**
  - **Justification**: All four are necessary contributors to "resources retrieved" (AND). The order-determination (G3) must precede travel (sequential). Travel (AT1) must precede the request (AT2), since the robot must "reach" the storage before it is "time to request" (sequential). The whole normal path (AT1;AT2) is challenged by the explicit battery-10% condition, requiring the Fallback relation with G4.

- **G4 -> AT3, AT4 [AND] (parallel: AT3#AT4)**
  - **Justification**: Both returning to base and reassigning the mission are required outcomes of the low-battery event (AND). No explicit ordering word links them ("goes back... and assigns..."), so they are modeled as possible-but-not-obligatory parallel actions.

- **G5 -> AT5, G6 [AND] [FALLBACK(AT5, G6)]**
  - **Justification**: Delivery succeeds either via the normal run-based task (AT5) or, if the explicit 30%-battery condition triggers, via the contingency (G6). Both are AND-connected per the Fallback rule, even though only one path executes per mission run.

- **G6 -> AT6, G7, AT9 [AND] [(FALLBACK(AT6,G7))#AT9]**
  - **Justification**: Returning the resource (AT6), reporting on failure (G7, nested Fallback due to the explicit "in case of failure" clause), and reassigning the remaining task (AT9) are all required (AND) parts of the low-battery-in-delivery response. Reassignment is modeled in parallel with the checkpoint-return/alert block since no explicit sequencing word connects "return... and assign...".

- **G7 -> AT7, AT8 [AND] (parallel: AT7#AT8)**
  - **Justification**: Both triggering the alert and sending the report are required (AND) to fulfill the notification goal. No explicit order is given ("an alert must be triggered and the report sent"), so Parallel is used.
