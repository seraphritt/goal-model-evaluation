# Multi‑Robot Goal Model — Inpatient Meal Delivery & Dish Collection

## Step‑by‑Step Reasoning

**1. Identifying the top-level intention.**
The description contains two clearly separable service threads that the robot(s) must jointly guarantee: (a) delivering food from kitchen to room, and (b) collecting dirty dishes from the corridor. Both are necessary parts of "the system," so the root is an **AND** of these two macro-goals. I treat them as able to run in **parallel** because the text never states that dish-collection must wait for (or precede) a delivery cycle — it is triggered independently by a call ("*Someone in the room can call a robot to pick up the dishes*"), so multiple delivery and pickup instances can be in flight concurrently across different rooms/robots.

**2. Delivery branch ordering.**
Within delivery, the system must first obtain the order ("*in response to kitchen delivery requests*"), then must know **who** (if anyone) can retrieve from the tray, because this determines which delivery alternative is executable. This is a logical/informational dependency (you cannot meaningfully choose "table" vs "tray" without first knowing retrieval capability), so I modeled `G3 (request) ; G4 (capability) ; G5 (deliver)` as **sequential**, not parallel — the order is dictated by information dependency even though the text doesn't use explicit "first/then" wording for this triad; this is different from the stricter FALLBACK trigger requirement, since sequential only needs a logical/explicit order of execution, which is present here.

**3. Table vs. Tray = OR, not Fallback.**
"*The food can be delivered into a room table by the robot … or the food can be fetched from the robot's tray*" is an explicit **OR** (alternative sufficient means), not a fallback, because the text never says "try X, and if X fails, try Y" — it simply states two independent ways the goal can be satisfied, each gated by different preconditions (manipulation skill vs. cooperation availability). No order of attempt is specified, so runtime is **parallel** (meaning: not mutually temporally constrained — only one executes, but neither is forced to be attempted before the other).

**4. Who retrieves from the tray = OR.**
"*Fetching from the robot's tray requires cooperation with the inpatient, a companion, a nurse, or another robot*" is explicitly enumerated with "or" four times — a clean **OR** decomposition. The sentences about some inpatients being unable, or companions/nurses being unavailable, explain *why* this uncertainty-driven OR exists (motivating `G4`'s query goal) but do not establish a preferred order, so this is **not** a fallback.

**5. Indicate / Track / Alert.**
"*Robot can carry multiple meals… should indicate which meal… track when and where… alert if wrong meal is retrieved*" — these three are distinct capabilities, all mandatory for the tray-fetch process → **AND**. Indicating the meal logically happens around/just before the hand-off (parallel with coordinating who retrieves), while tracking and alerting are only meaningful **after** a retrieval event, so I sequenced `(coordinate # indicate) ; monitor&verify`.

**6. Dish collection location constraint.**
"*Dirty dishes must be collected in the corridor… robot must never pick them up inside the room*" is a hard operational constraint, not a decomposition — I encoded it as the fixed `Location` value for every dish-related task rather than inventing a goal for it.

**7. Dish retrieval cooperation = OR.**
"*unassisted, with the cooperation of two robots or with the cooperation of robots and a human*" — explicit enumerated alternatives → **OR**, no stated preference order → parallel.

**8. Door opening = FALLBACK.**
"*Opening the room door can involve cooperation with another robot or a human… that person can signal if they can open the door when the robot comes to it.*" This **is** an explicit IF-condition: the primary, contextually default path is the human (already present, having just called the robot) opening the door; the signal is a conditional check, and robot-robot cooperation is the alternative path invoked only when the human cannot. This matches the FALLBACK definition precisely (condition-triggered alternative), unlike the other OR cases above, so `FALLBACK(Open via Human, Open via Robot)` is used, and — per the FALLBACK rule — its two children are connected by **AND**.

**9. Call → Door → Dishes sequencing.**
The robot cannot usefully retrieve dishes at a closed threshold, and it cannot be dispatched without a call. The description's own narrative order (call → door signal → implied hand-off) plus the logical precondition chain justifies **sequential** execution: `receive call ; open door ; retrieve dishes`.

**10. Zero-robot filter.**
Every leaf task keeps at least one robot in the loop (presenting the tray, logging, alerting, requesting door-opening, collecting dishes), so no goal/task exclusively performed by humans was added to the tree — e.g., I did **not** add a standalone goal like "Inpatient eats meal," since that involves no robot.

**11. Goal typing logic.**
- *Query* goals were used wherever the purpose is purely informational (processing the order, checking retrieval capability, receiving the call, tracking retrieval time/location).
- *Perform* goals were used wherever an action is attempted but explicit text acknowledges it may not be executable/successful (cooperation attempts that may fail because the party "could be unable"/"could not be available"; indicating a meal; alerting; opening via cooperation).
- *Achieve* goals were used for the higher-level state-reaching nodes (meal delivered, door opened, dishes collected), where the system plans/acts until a target condition becomes true.

## Logical Relationships

- **G1 -> G2, G17 [AND][(parallel)]**
  - **Justification**: Both meal delivery and dish collection are mandatory system responsibilities. No explicit ordering is given between the two macro-processes, and they are triggered independently (orders vs. pickup calls), so they can proceed in parallel across the fleet.

- **G2 -> G3, G4, G5 [AND][(sequential)]**
  - **Justification**: All three are required, and order matters logically: the request must be known (G3) and the retrieval capability determined (G4) before the system can select and execute a delivery method (G5).

- **G5 -> G6, G7 [OR][(parallel)]**
  - **Justification**: "Delivered into a room table … or … fetched from the robot's tray" is an explicit alternative; no attempt order is stated, so parallel (non-ordered alternatives).

- **G7 -> G8, G13, G14 [AND][(G8 # G13) ; G14]**
  - **Justification**: Coordinating who retrieves and indicating the meal are both needed and can occur around the same time (parallel); monitoring/verifying retrieval can only happen after the hand-off occurs, hence sequential after the first pair.

- **G8 -> G9, G10, G11, G12 [OR][(parallel)]**
  - **Justification**: "Cooperation with the inpatient, a companion, a nurse, or another robot" is an explicit four-way OR with no stated preference order.

- **G14 -> G15, G16 [AND][(sequential)]**
  - **Justification**: Tracking the retrieval (G15) must occur before the system can determine and raise an alert for an incorrect retrieval (G16).

- **G17 -> G18, G19, G22 [AND][(sequential)]**
  - **Justification**: The robot must receive the call, then get the door opened, then retrieve the dishes — each step is a precondition for the next.

- **G19 -> G20, G21 [AND][FALLBACK(G20, G21)]**
  - **Justification**: The person's signal ("if they can open the door") is an explicit conditional: human-opens-door is attempted/expected by default; robot-cooperation is the alternative invoked only when that condition fails. Per the fallback rule, the two branches are AND-connected.

- **G22 -> G23, G24, G25 [OR][(parallel)]**
  - **Justification**: "Unassisted, with the cooperation of two robots, or with the cooperation of robots and a human" is an explicit three-way OR with no stated order.

- **G3 -> AT1 [AND]**
  - **Justification**: A single operational step (receiving the order) fully operationalizes this query goal.

- **G4 -> AT2 [AND]**
  - **Justification**: A single task (checking record + companion presence) operationalizes the capability query.

- **G6 -> AT3 [AND]**
  - **Justification**: Table delivery is realized by one concrete manipulation action.

- **G8 -> AT4, AT5, AT6, AT7 (via G9–G12) [OR]**
  - **Justification**: Each cooperation-type goal maps to exactly one corresponding presentation task; the OR carries down from the goal level.

- **G13 -> AT8 [AND]**, **G15 -> AT9 [AND]**, **G16 -> AT10 [AND]**
  - **Justification**: Each is a single, direct operational action matching its goal's wording in the description.

- **G18 -> AT11 [AND]**
  - **Justification**: Receiving the call is a single communicative task.

- **G19 -> AT12, AT13 (via G20, G21) [FALLBACK]**
  - **Justification**: Mirrors the goal-level fallback — human-cooperation task attempted per the signaled condition, robot-cooperation task as the alternative.

- **G22 -> AT14, AT15, AT16 (via G23–G25) [OR]**
  - **Justification**: Each dish-retrieval mode maps to one concrete task; OR carries down from the goal level.
