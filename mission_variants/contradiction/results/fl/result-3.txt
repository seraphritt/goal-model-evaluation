# Goal Model Analysis — Hospital Meal Delivery & Dish Retrieval Multi‑Robot System

## 1. Step‑by‑Step Reasoning

Before producing the model, here is the analytical path I followed, including the modeling conventions I had to establish because the description leaves some structural choices implicit.

**1.1 Identifying the two independent missions.** The description covers two robot-performed responsibilities that are triggered by different events and have no stated dependency on one another: (a) delivering food on a per-order basis, and (b) retrieving dirty dishes on a per-call basis. I modeled these as the two top-level branches of a single root mission goal, combined with a **parallel (#)** runtime, since nothing in the text forces one to precede or block the other.

**1.2 The two delivery mechanisms are a genuine OR, not a fallback.** "The food can be delivered into a room table... **or** the food can be fetched from the robot's tray" gives two alternatives but never states that one is tried first and the other only on failure. Per your rule, FALLBACK requires an *explicit* stated order/condition — absent here — so I used **OR** decomposition with a **parallel (#)** runtime (meaning: the alternatives are independent, not sequenced).

**1.3 The tray‑fetch branch is the richest part of the description and needed the most careful decomposition.** I identified five distinct intentions that are all *jointly* necessary whenever the tray‑fetch path is taken (hence AND):
   - determining **who** (if anyone) can retrieve the meal — explicitly a **query** process ("information... can be obtained," "subject to uncertainty"),
   - **indicating** which meal to retrieve (needed because the robot carries multiple meals),
   - the actual **retrieval** action (OR across inpatient/companion/nurse/another robot),
   - **tracking** when/where retrieval happened,
   - **alerting** on wrong-meal retrieval.
   
   I ordered these as sequential where the text implies a necessary temporal/causal precedence (you must know *who* before you *indicate*; you must *indicate* before someone can correctly *retrieve*), and parallel between tracking and alerting, since both are monitoring activities with no stated order between them.

**1.4 ⚠️ Explicit contradiction flagged — not silently resolved.** The description states: *"The robot should alert if a wrong meal is retrieved. However, if the wrong meal is retrieved, the robot must not generate an alert."* These two sentences are in direct logical conflict (they prescribe opposite behavior for the identical condition). I did **not** quietly pick one interpretation and hide the conflict — I modeled the goal (`G9`) using the first, affirmative statement, because it expresses the apparent primary intent, but I flag this explicitly in the table and recommend this be clarified with stakeholders before implementation (e.g., perhaps the second clause was meant to apply to a different condition, such as "if the wrong meal is retrieved **due to patient choice rather than robot error**").

**1.5 Zero-robot elements were deliberately excluded as nodes** (per your rule that goals/tasks not performed by *any* robot must not appear), but I preserved their information value in justifications rather than dropping them silently:
   - *"order-by-order basis in response to kitchen delivery requests"* → explains the triggering granularity of "Deliver Food Order," not a node itself (request creation is a kitchen-staff action).
   - *"Someone in the room can call a robot to pick up the dishes"* → the act of calling is a human action; it explains the trigger for "Retrieve Dirty Dishes," not a node itself.
   - *"that person can signal if they can open the door"* → the signaling itself is a human action; it's folded into the justification for the OR choice in "Open Room Door" rather than made a separate query node (unlike the tray-retrieval capability case, this is a single undecomposable piece of information, not two combined information sources).

**1.6 Added "Collect Meal from Kitchen."** The description explicitly says food is delivered "**from the kitchen** to an inpatient room." I added this as an explicit sequential first step (you must have the meal before you can deliver it), which is also the only task grounded at the **kitchen** location.

**1.7 Door‑opening and dish‑retrieval cooperation.** Both are explicit OR alternatives over cooperation types, each mapped to one task per alternative, with robot counts taken literally from the text ("two robots" → 2; "a human" → the other robot stays at 1; "unassisted" → 1).

**1.8 Modeling convention for single-child goals.** Three goals (*Indicate Meal to Retrieve*, *Track Meal Retrieval*, *Manage Wrong-Meal Alert*) map to exactly one concrete action in the text, with no described alternative or parallel implementation. Decomposition formally requires a minimum of two children; here I treat the single-task mapping as a **trivial/direct realization** (labeled AND by convention) and mark the runtime annotation as **"-"**, since there is no second child to establish a parallel/sequential/fallback relation against. I flag this explicitly rather than inventing an artificial second branch not supported by the text.

**1.9 Goal typing.** I classified each goal as Perform / Query / Achieve based on strict adherence to your definitions — e.g., "Determine Retrieval Capability" is a **Query** because the text literally frames it as information "obtained," while "Indicate Meal to Retrieve" is a **Perform** because it's a single communicative action with no complex target state, matching your "Enter the Car" example.

## 6. Logical Relationships

- **G1 -> G2, G10 [AND] (parallel)**
  - **Justification**: Food delivery and dish retrieval are two independent, concurrently-running responsibilities triggered by separate events (kitchen requests vs. room calls); nothing in the text requires one to precede the other.

- **G2 -> AT1, G3 [AND] (sequential)**
  - **Justification**: The meal must be collected from the kitchen before it can be delivered to the inpatient — a necessary physical precondition, not an alternative.

- **G3 -> G4, AT11 [OR] (parallel)**
  - **Justification**: "Delivered into a room table... **or**... fetched from the tray" are explicit alternatives with no stated order of attempt, so OR with no sequencing (parallel, per convention) rather than fallback.

- **G4 -> G5, G6, G7, G8, G9 [AND] (G5;(G6;(G7;(G8#G9))))**
  - **Justification**: All five aspects (capability check, indication, retrieval, tracking, alerting) are jointly required for a complete tray-fetch. Capability must be known before indicating; indicating must precede retrieval; tracking and alerting are concurrent, unordered checks following retrieval.

- **G5 -> AT2, AT3 [AND] (parallel)**
  - **Justification**: Both the inpatient record and companion presence are combined ("based on... information about the patient **and** the presence of a companion") to determine capability; neither is described as dependent on the other, so they can be gathered in parallel.

- **G6 -> AT4 [AND] (-)**
  - **Justification**: Single, direct realization of the indication action; no alternative or concurrent sub-process is described.

- **G7 -> AT5, AT6, AT7, AT8 [OR] (parallel)**
  - **Justification**: Four alternative cooperators are listed ("inpatient, a companion, a nurse, or another robot"); any one suffices, with no stated preference order.

- **G8 -> AT9 [AND] (-)**
  - **Justification**: Single direct task realizing the tracking requirement.

- **G9 -> AT10 [AND] (-)** ⚠️
  - **Justification**: Single direct task realizing the (contradicted) alerting requirement; see the flag in Section 1.4 and the Goal Table.

- **G10 -> G11, G12 [AND] (sequential)**
  - **Justification**: The door must be opened before the robot can access the room to retrieve dishes — an implied physical precondition, since door-opening is described specifically in the context of the dish-pickup process.

- **G11 -> AT12, AT13 [OR] (parallel)**
  - **Justification**: "Opening the room door can involve cooperation with another robot **or** a human" — explicit alternatives, no order stated. (The person's signal about whether they can open the door determines which alternative applies at runtime, but is not itself modeled as a node, per §1.5.)

- **G12 -> AT14, AT15, AT16 [OR] (parallel)**
  - **Justification**: "can occur unassisted, with the cooperation of two robots, or with the cooperation of robots and a human" — three explicit alternatives, no order stated.

## 7. Closing Notes

- ⚠️ **Please resolve before implementation**: the wrong-meal-alert requirement is self-contradictory in the source description (G9/AT10). I'd recommend checking with whoever authored the spec whether the second sentence was meant to describe a different condition (e.g., an exception case) rather than negate the first.
- I don't have document/web access, so nothing here was cross-checked against external goal-modeling literature — treat the i*/goal-model conventions applied (e.g., the "parallel-by-default-for-unordered-OR" convention and the "trivial AND" convention for single-child goals) as my own reasonable interpretation of your rules where the rules didn't fully disambiguate, and feel free to push back on either.
- Happy to adjust the tree (e.g., split `G1` into two separate root goals, or restructure the retrieval-capability branch) if you'd prefer a different top-level framing.
