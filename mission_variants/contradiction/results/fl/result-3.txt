# Goal Model for the Hospital Food-Delivery & Dish-Collection Multi-Robot System

## 1. Step-by-step reasoning

Before building the tables, here is how I parsed the description:

1. **Identify the two independent missions.** The text describes two responsibilities that are triggered by different events and can run concurrently for different rooms/orders: (a) delivering food (triggered by a *kitchen delivery request*) and (b) collecting dirty dishes (triggered by a *patient's call*). I modeled both as an **AND** decomposition under one root goal, with a **parallel (#)** runtime, since nothing in the text forces one to wait for the other.

2. **Exclude "zero-robot" actions.** The patient opening the door unaided, or a patient simply existing, are not robot actions and were excluded, per the "zero robot" rule. Only the *cooperative* branches of door-opening (robot+robot or robot+human) are modeled.

3. **Avoid misusing FALLBACK.** The brief explicitly restricts FALLBACK to cases where the text states an explicit order ("try X, and if X fails, do Y"). I found **no** such explicit priority order between delivery methods, between cooperation partners, or between dish-retrieval modes — they are all presented as flat alternatives ("can be X **or** Y **or** Z"). So these are all modeled as **OR** decompositions with a **parallel (#)** runtime (no obligatory order), not FALLBACK. The only true sequencing I found is **physical/logical necessity** (e.g., you cannot deliver a meal before transporting it to the room; you cannot alert on a wrong meal before detecting it) — these use the **sequential (;)** operator, since that necessity is not a "failure-triggered alternative" but a hard precedence.

4. **Split "determine who can retrieve"** into its own **Query Goal**, because the text is explicit: "the information... can be obtained... this information is subject to uncertainty." This matches the Query Goal definition precisely (retrieving knowledge, not acting).

5. **Separate "indicate the meal" from "cooperate to retrieve.**" The text ties meal-indication specifically to *person*-based retrieval ("in the case of a person retrieving the meal"), so it sits only under that branch, sequential before the cooperation step.

6. **Split "track" and "alert"** into distinct Achieve/Perform goals, since they have different semantics: tracking is an unconditional state to maintain (log exists for every meal), while alerting is a reactive, conditional action — matching the Perform-goal definition (action executed when possible, no persistent target state required).

7. **Dish collection**: Because "the robot must never pick them up inside the room," every dish-task's Location is **corridor**, never "room." Door-opening is modeled as a prerequisite (sequential) to dish retrieval, grounded in "that person can signal if they can open the door when the robot comes to it" — i.e., the door event happens at arrival, before retrieval.

8. Every Goal/Task got **at least two children** wherever an AND/OR applies, as required; where the text only describes a single composite action, I split it into its two natural orthogonal facets (e.g., "when and where" → two parallel AND children) rather than leaving a 1-child decomposition.

9. **Numbering** follows strict depth-first pre-order traversal, with separate counters for `G#` and `AT#`.

## 6. Logical relationships

- **G1 -> G2, G11 [AND][parallel (#)]**
  - **Justification**: Both food delivery and dish collection are mandatory system responsibilities (AND). They are triggered by independent events (a kitchen request vs. a patient's call) and nothing in the text forces one to wait on the other, so they can proceed concurrently (parallel).

- **G2 -> AT1, G3 [AND][sequential (;)]**
  - **Justification**: Both transporting the meal and delivering it to the patient are required (AND). The meal physically cannot be delivered before it is transported to the room — this is a necessary order, not an explicitly stated failure/alternative, so sequential (not fallback) is used.

- **G3 -> AT2, G4 [OR][parallel (#)]**
  - **Justification**: "The food can be delivered into a room table... **or** the food can be fetched from the robot's tray" — two alternative, mutually sufficient methods (OR). No priority or try-this-first order is stated between them, so parallel is used rather than fallback.

- **G4 -> G5, G6, G9, G10 [AND][G5;G6;(G9#G10)]**
  - **Justification**: All four sub-processes (determine retriever, perform retrieval, track, alert) are necessary parts of a correct tray-fetch (AND). Determining who can retrieve must happen before the retrieval attempt (sequential necessity). Once retrieval occurs, tracking (unconditional logging) and alerting (conditional check) are independent monitoring functions with no stated order between them, so parallel.

- **G5 -> AT3, AT4 [AND][parallel (#)]**
  - **Justification**: The capability decision needs both the patient record **and** companion-presence information (AND) — explicitly "based on the inpatient record... and the presence of a companion." These two checks are independent data sources, so parallel.

- **G6 -> G7, AT9 [OR][parallel (#)]**
  - **Justification**: Retrieval happens either via a person or via another robot (OR) — "cooperation with the inpatient, a companion, a nurse, **or** another robot." No stated preference order, so parallel.

- **G7 -> AT5, G8 [AND][sequential (;)]**
  - **Justification**: Both indicating the meal and the person's retrieval are required (AND). The robot must indicate which meal before the person can correctly retrieve it — an explicit causal ordering in the text, so sequential.

- **G8 -> AT6, AT7, AT8 [OR][parallel (#)]**
  - **Justification**: Any one of the three person-types (inpatient, companion, nurse) suffices to retrieve the meal (OR) — flat list in the text, no stated priority, so parallel.

- **G9 -> AT10, AT11 [AND][parallel (#)]**
  - **Justification**: Tracking requires both the time **and** the location of retrieval (AND) — "track when **and** where." Both can be recorded simultaneously as part of the same logging event, so parallel.

- **G10 -> AT12, AT13 [AND][sequential (;)]**
  - **Justification**: Both detecting and alerting are required for this goal to be meaningful (AND); detection must logically precede the alert action, so sequential.

- **G11 -> G12, G13 [AND][sequential (;)]**
  - **Justification**: Both opening the door and retrieving the dishes are required (AND). The door must be opened before dishes can be handed out to the robot in the corridor — the text ties the door signal to "when the robot comes to it," i.e., at the start of the pickup, so sequential.

- **G12 -> AT14, AT15 [OR][parallel (#)]**
  - **Justification**: The door can be opened via cooperation with either another robot or a human (OR) — flat alternative in the text, no stated priority, so parallel.

- **G13 -> AT16, AT17, AT18 [OR][parallel (#)]**
  - **Justification**: Dish retrieval can occur unassisted, with two-robot cooperation, or with robot-human cooperation (OR) — three flat alternatives explicitly listed ("can occur unassisted, with the cooperation of two robots or with the cooperation of robots and a human"), no stated priority, so parallel.
