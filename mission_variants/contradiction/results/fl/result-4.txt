# Goal Model Analysis — Hospital Food Delivery & Dish Retrieval Multi-Robot System

## Step-by-Step Reasoning

**1. Identifying the mission's two macro-processes.**
The description splits naturally into two independent responsibilities that a robot (or fleet) must carry out: (a) delivering food from the kitchen to an inpatient, and (b) retrieving dirty dishes from a room to the corridor. Nothing in the text makes one depend on the other, and both can occur simultaneously for different orders/rooms, so I modeled a root goal **G1** that AND-decomposes into these two branches with a **parallel** runtime.

**2. Food delivery branch.**
The text gives a clear temporal/causal chain: a kitchen request arrives → the system must find out *who/what* can receive the meal → the meal is delivered → the retrieval is tracked. This dependency chain (you can't choose a delivery method before knowing the order, and you can't track a retrieval before it happens) justifies a **sequential** runtime, even though the text doesn't use explicit "first/then" wording — the operational dependency makes a non-sequential reading incoherent.

**3. OR vs. Fallback discipline.**
I was strict about the Fallback rule: it only applies when the text states an explicit attempt order or an explicit IF-triggered alternative.
- "Delivered on a table **or** fetched from the tray" → plain **OR**, no stated priority.
- "Cooperation with inpatient, companion, nurse, **or** another robot" → plain **OR**. I collapsed inpatient/companion/nurse into a single "human cooperation" branch (robot count = 1) because, from the robot's operational perspective, they are indistinguishable — modeling them separately would duplicate the same intention, which the instructions ask me to avoid. "Another robot" is operationally distinct (robot count = 2), so it stays separate.
- "The robot should **alert if a wrong meal is retrieved**" → this *is* a genuine IF-triggered exception over the normal tracking behavior, so I modeled it as **FALLBACK(Log Retrieval, Alert on Incorrect Retrieval)** rather than a plain AND/parallel pair.
- Door-opening and dish-collection cooperation modes are both explicit "or" lists with no stated order → **OR/parallel**.

**4. Zero-robot filtering.**
I did not create goals/tasks for "the inpatient eats the food" or "a nurse decides to help" in isolation — these are not robot actions. Wherever a human cooperates, I kept only the robot-side task (e.g., "present tray / wait for retrieval"), since the robot is always physically involved in these interactions. Likewise, "that person can signal if they can open the door" was folded into the **query** goal about the call (G11), not modeled as a separate human-only goal, since the self-opening-by-human branch involves zero robots and was excluded.

**5. Goal typing.**
- Goals whose purpose is purely informational ("obtained based on the inpatient record," "call a robot," "signal if they can open the door") → **Query**.
- Goals describing a single concrete, skill-bound action with no further planning ("delivered into a room table... requires a special manipulation robot skill") → **Perform**.
- Everything else describing a state to be brought about (meal delivered, dishes collected, door open, retrieval logged) → **Achieve**, each with an explicit target condition.

**6. Tasks and locations.**
Only three locations are explicitly cited in the text: **kitchen**, **inpatient room**, **corridor**. I never invented a location outside these three. Robot counts were derived directly from explicit cooperation cardinalities in the text (1 for human cooperation, 2 for robot-robot cooperation), and the strict "never inside the room" rule was encoded as the Location attribute of the dish-collection tasks rather than as a separate goal.

## Logical Relationships

- **G1 -> G2, G10 [AND] (parallel: G2#G10)**
  - **Justification**: Food delivery and dish retrieval are described as two independent system duties with no stated dependency between them; both must be supported, and nothing prevents them running concurrently for different rooms/orders.

- **G2 -> G3, G4, G5, G9 [AND] (sequential: G3;G4;G5;G9)**
  - **Justification**: All four steps are mandatory to fully serve one order. Their order is operationally forced: the order must be received before a method can be chosen, the method chosen before delivery, and delivery must occur before its retrieval can be tracked.

- **G3 -> AT1 [AND]**
  - **Justification**: A single operational step (receiving/parsing the request) fully satisfies this query goal.

- **G4 -> AT2 [AND]**
  - **Justification**: A single operational step (checking the inpatient record/companion presence) fully satisfies this query goal.

- **G5 -> G6, G7 [OR] (parallel: G6#G7)**
  - **Justification**: "Delivered into a room table... **or** fetched from the robot's tray" is an explicit alternative with no stated order of attempt, so OR/parallel applies rather than Fallback.

- **G6 -> AT3 [AND]**
  - **Justification**: Table delivery is realized by the single manipulation task of placing the meal.

- **G7 -> G8, AT6 [OR] (parallel: G8#AT6)**
  - **Justification**: "Cooperation with the inpatient, a companion, a nurse, **or** another robot" lists alternative cooperators with no priority stated; grouped into human-cooperation (G8) vs. robot-cooperation (AT6) to avoid duplicating the same robot-side intention across inpatient/companion/nurse.

- **G8 -> AT4, AT5 [AND] (sequential: AT4;AT5)**
  - **Justification**: The robot must indicate which meal belongs to the inpatient before that meal can be correctly retrieved — both steps are mandatory and causally ordered.

- **G9 -> AT7, AT8 [AND] (FALLBACK(AT7, AT8))**
  - **Justification**: "The robot should alert **if** a wrong meal is retrieved" is an explicit IF-condition over the normal logging behavior — the alert (AT8) is the alternative/exception path triggered when the retrieval check (AT7) reveals a mismatch, matching the Fallback definition exactly; both remain jointly required (AND).

- **G10 -> G11, G12, G13 [AND] (sequential: G11;G12;G13)**
  - **Justification**: The process is triggered by a call, which determines whether door cooperation is needed, which in turn must happen before dishes can be handed off and collected — a forced operational order, all three mandatory.

- **G11 -> AT9 [AND]**
  - **Justification**: A single operational step (receiving the call and the door signal) fully satisfies this query goal.

- **G12 -> AT10, AT11 [OR] (parallel: AT10#AT11)**
  - **Justification**: "Opening the room door can involve cooperation with another robot **or** a human" — explicit alternative with no stated order of attempt.

- **G13 -> AT12, AT13, AT14 [OR] (parallel: AT12#AT13#AT14)**
  - **Justification**: "The dish retrieve can occur unassisted, with the cooperation of two robots, **or** with the cooperation of robots and a human" — three explicit alternatives, none given precedence.
