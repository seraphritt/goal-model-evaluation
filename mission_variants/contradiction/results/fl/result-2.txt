# Mission Analysis: Hospital Food-Delivery & Dish-Collection Multi-Robot System

## Step-by-Step Reasoning

Before building the tables, here is my full reasoning process, including the judgment calls I had to make and why.

**1. Identifying the top-level structure.**
The description bundles two distinct robot responsibilities: (a) delivering food per kitchen order, and (b) collecting dirty dishes (triggered independently, by a person calling the robot). Nothing in the text says one must happen before the other system-wide (they happen per-room, per-event, asynchronously), so I model them as **parallel (#)** siblings under a root goal, related by **AND** (both are core, non-optional responsibilities of the system).

**2. Excluding "zero-robot" nodes.**
The rule "goals/tasks not performed by any robot must not appear" forced me to reconsider two tempting nodes:
- *"Kitchen delivery request"* and *"someone calls a robot"* are external triggers, not robot-performed actions — I excluded them as nodes (they're context, not goals).
- *"That person can signal if they can open the door"* — if modeled as "person opens the door themselves," this is a zero-robot action. I reframed it as a **Query Goal**: the robot *receives/senses the signal*. This preserves the explicit conditional logic in the text while keeping the robot as the actor of the node.

**3. Identifying FALLBACK vs OR.**
The spec is explicit that FALLBACK requires an explicit normal-then-exception order (an implicit "if" condition), while unordered enumerations ("X, Y, or Z") are OR.
- *"Fetching from the tray requires cooperation with the inpatient, a companion, a nurse, or another robot"* — this is a plain enumeration with **no stated priority or failure-triggered order** → modeled as **OR**, not fallback.
- *"The robot should alert if a wrong meal is retrieved"* — this is a textbook IF-triggered exception (normal = correct retrieval; exception = wrong one is retrieved → alert) → modeled as **FALLBACK(Confirm correct meal, Alert wrong meal)**.
- *"That person can signal if they can open the door"* — again an explicit IF-condition (can open → fine; cannot → cooperative opening needed) → modeled as **FALLBACK(Check signal, Cooperative opening)**.
- *"Dish retrieve can occur unassisted, with two robots, or with a robot and a human"* — again an unordered enumeration with no stated priority → **OR**.

**4. Sequential vs parallel.**
I used sequential (`;`) only where one step is a physical/logical precondition for the next (e.g., you must query capability before selecting a retrieval partner; you must open the door before handing dishes through it; you must navigate to the corridor before picking anything up). I used parallel (`#`) for: (i) true OR-alternatives (since no ordering is implied among mutually exclusive options), and (ii) verify+track, which can reasonably happen concurrently once retrieval occurs, with no stated order between them.

**5. Avoiding duplicated intentions.**
"Opening the door" appears twice in the text (once generally, once tied to the dish-pickup call). I did **not** create two separate door-opening goals — I created **one** `Ensure Room Door is Open` goal, reused once (inside the "assisted dish pickup" branch), to avoid redundant intentions, per the no-duplication rule.

**6. Transport as a Task, not a Goal.**
"Deliver food from kitchen to inpatient room" implies physically carrying the tray. I treated this as a concrete, non-decomposable operational step (Task), not an intentional Goal, since it has no further meaningful sub-decomposition in the text (it's just "move from A to B").

**7. Goal typing.**
- **Query**: used only where the sole purpose is retrieving information (capability check, door-signal check).
- **Perform**: used for single, atomic physical actions whose success is the act itself (placing food on the table, picking up dishes already in the corridor).
- **Achieve**: used everywhere a target world-state must be reached through coordination/planning (most of the tree).

**8. Locations.**
I used only locations explicitly named in the text: **Kitchen**, **Inpatient Room**, **Corridor**. I did not invent locations (e.g., no "nurse station," no "hallway" distinct from corridor).

**9. Number of robots.**
Single-robot by default (the delivering/collecting robot). I set **2** only where the text explicitly names "another robot" or "two robots" as cooperators.

## Logical Relationships

- **G1 -> G2, G11 [AND](parallel)**
  - **Justification**: Food delivery and dish collection are both independently-triggered, concurrently-operating system duties; nothing in the text orders one before the other.

- **G2 -> AT1, G3 [AND](sequential)**
  - **Justification**: The meal must physically arrive at the room (transport) before it can be handed off — a logical precondition, hence sequential.

- **G3 -> G4, G5 [OR](parallel)**
  - **Justification**: "The food can be delivered into a room table... **or** fetched from the robot's tray" — explicit alternative.

- **G4 -> AT2 [AND]**
  - **Justification**: Single operational step fulfills this goal; trivially AND.

- **G5 -> G6, G7, G9, G10 [AND](sequential: G6;(G7;(G9#G10)))**
  - **Justification**: Capability must be known (G6) before a partner is engaged (G7); once retrieval happens, verification (G9) and tracking (G10) can proceed concurrently with no stated order between them.

- **G6 -> AT3 [AND]**
  - **Justification**: Single query action; trivially AND.

- **G7 -> AT4, G8 [AND](sequential)**
  - **Justification**: The robot must indicate the correct meal before/while the retrieval partner acts, since the robot carries multiple meals.

- **G8 -> AT5, AT6, AT7, AT8 [OR](parallel)**
  - **Justification**: "Cooperation with the inpatient, a companion, a nurse, or another robot" — unordered enumeration of sufficient alternatives.

- **G9 -> AT9, AT10 [AND] FALLBACK(AT9, AT10)**
  - **Justification**: "Alert if a wrong meal is retrieved" is an explicit IF-condition: normal correctness check first, alert only triggered on failure of that check.

- **G10 -> AT11 [AND]**
  - **Justification**: Single logging action; trivially AND.

- **G11 -> AT12, G12 [AND](sequential)**
  - **Justification**: Robot must reach the corridor before obtaining dishes there.

- **G12 -> G13, G14 [OR](parallel)**
  - **Justification**: "Can occur unassisted... or with cooperation" — explicit alternative modes.

- **G13 -> AT13 [AND]**
  - **Justification**: Single operational action; trivially AND.

- **G14 -> G15, G18 [AND](sequential)**
  - **Justification**: The door must be opened before dishes (still inside the room) can be transferred out through it.

- **G15 -> G16, G17 [AND] FALLBACK(G16, G17)**
  - **Justification**: "That person can signal if they can open the door" is an explicit IF-condition — the signal is checked first; cooperative opening is pursued only if the signal indicates the person cannot open it.

- **G16 -> AT14 [AND]**
  - **Justification**: Single query action; trivially AND.

- **G17 -> AT15, AT16 [OR](parallel)**
  - **Justification**: "Cooperation with another robot **or** a human" — explicit alternative.

- **G18 -> AT17, AT18 [OR](parallel)**
  - **Justification**: "Cooperation of two robots **or** cooperation of robots and a human" — explicit alternative.
