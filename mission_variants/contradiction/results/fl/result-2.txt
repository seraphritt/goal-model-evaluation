# Multi-Robot Mission Goal Model — Food Delivery & Dish Retrieval System

## Step-by-Step Reasoning

**1. Identifying the top-level responsibilities.**
The description contains two largely independent robot responsibilities: (a) delivering food from the kitchen to a room, order-by-order, and (b) retrieving dirty dishes from a room. Nothing in the text orders one before the other or makes one conditional on the other, so I modeled them as two AND-required, parallel children of a single root mission goal (a system that only did one of the two would not satisfy the description).

**2. Finding the OR particles.** Three explicit alternative-structures appear:
- "delivered into a room table... **or**... fetched from the robot's tray" → OR
- "cooperation with the inpatient, a companion, a nurse, **or** another robot" → OR
- "unassisted, with cooperation of two robots **or** with cooperation of robots and a human" (dishes), and "cooperation with another robot **or** a human" (door) → OR

**3. Finding the FALLBACK particle.** The instructions require FALLBACK only when the text explicitly describes a *normal path followed by a failure/exception-triggered alternative*. Only one place does this: *"Some inpatients could be unable to fetch the food... and a companion visitor or nurse could not be available."* This explicitly ties unavailability/failure to the choice of *who* retrieves the meal. The other three OR-lists (table/tray; door-opening helper; dish-collection helper) are plain enumerations of options with **no** stated failure condition or order, so I kept those as OR + parallel (`#`), not FALLBACK. This is a deliberate, text-driven distinction, not an inconsistency.

**4. Finding sequencing.** Real-world causal order gives several sequential (`;`) links even without the word "then": a request must be identified before delivery; a call must be received before a robot responds; door-opening capability must be known before the door-opening method is chosen; the door must open before dishes can be collected; availability must be known before indicating/retrieving a meal.

**5. Checking the "zero-robot" rule.** Every goal retained involves the robot either acting or needing information to act (e.g., "receiving a call" and "receiving a door-opening signal" are modeled from the *robot's* side, not the human's side, so they are not zero-robot).

**6. Locations.** The text only ever names two places: the **kitchen** (origin of delivery requests) and the **room** (where everything else happens — table, tray, door, dishes, calls, signals). I did not invent any other location.

**7. A modeling exception I'm flagging.** A handful of goals (identifying a request, determining availability, indicating a meal, tracking retrieval, receiving a call, receiving a door signal) have exactly **one** realizing task, because the description only specifies one concrete action for them. This technically falls short of the "minimum two children" rule for decomposition. I chose to keep these as honest single-child (trivial AND) nodes rather than inventing a second, unsupported task — I'd rather flag this explicitly than fabricate content not in the description. If you'd prefer, I can instead merge each of these goals directly into its task (removing the goal layer) — happy to redo it that way if you tell me which you prefer.

**8. A contradiction I found and how I resolved it.**
> "The robot should alert if a wrong meal is retrieved. **However**, if the wrong meal is retrieved, the robot must not generate an alert."

These two sentences directly contradict each other. I modeled **alerting as the intended behavior** (G10/AT11), since it's the more specific, safety-motivated requirement and reads as the "main" rule, while the second sentence reads like an editing error or an unstated exception condition that was never specified. **This needs confirmation from you or the stakeholders** — if there's a real exception case (e.g., don't alert if the inpatient is intentionally swapping meals), let me know and I'll add a proper FALLBACK/condition for it instead.

- **G1 -> G2, G11 [AND] (parallel: `G2#G11`)**
  - **Justification**: Food delivery and dish retrieval are both required system responsibilities with no stated order between them.

- **G2 -> G3, G4, G9, G10 [AND] (`G3;(G4;(G9#G10))`)**
  - **Justification**: Identifying the request must precede delivery; delivery must precede tracking/alerting; tracking and alert-monitoring are independent of each other and can proceed in parallel.

- **G3 -> AT1 [AND, single-child]**
  - **Justification**: One concrete action (querying the kitchen system) fully realizes this query goal.

- **G4 -> AT2, G5 [OR] (parallel: `AT2#G5`)**
  - **Justification**: Explicit "or" between table-delivery and tray-fetch; no precedence stated.

- **G5 -> G6, G7, G8 [AND] (`G6;(G7;G8)`)**
  - **Justification**: Availability must be determined before indicating the meal or attempting retrieval; indicating logically precedes the retrieval act.

- **G6 -> AT3 [AND, single-child]** / **G7 -> AT4 [AND, single-child]**
  - **Justification**: Each is realized by exactly one described action (record/presence lookup; signaling).

  - **Justification**: Four alternative cooperating agents; the text's explicit unavailability/failure language ("could be unable," "could not be available") is the defining cue for a fallback chain rather than unordered OR.

  - **Justification**: One logging action realizes the tracking goal.
