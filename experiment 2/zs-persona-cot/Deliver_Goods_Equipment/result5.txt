## 4. Logical Relationships  

- **G1** → **G1.0**, **G1.1**, **G1.2**  `[AND][;]`  
  *Justification*: The mission must first determine the order, then perform collection and finally delivery in a sequential manner.  

- **G1.1** → **G1.1.1**, **G1.1.2**, **G1.1.3**, **G1.1.4**, **G1.1.5**  `[AND][;]`  
  *Justification*: Each step of the collection phase must be executed in order.  

- **G1.1.5** → **G1.1.5a**, **G1.1.5b**  `[AND][FALLBACK(G1.1.5a, G1.1.5b)]`  
  *Justification*: If the battery is low, either recharge or hand off; the fallback indicates the first attempt is to recharge, otherwise hand off.  

- **G1.2** → **G1.2.1**, **G1.2.2**, **G1.2.3**  `[AND][;]`  
  *Justification*: Delivery consists of moving, handing over, and handling low‑battery contingencies.  

- **G1.2.3** → **G1.2.3a**, **G1.2.3b**, **G1.2.3c**  `[AND][FALLBACK(FALLBACK(G1.2.3a,G1.2.3b),G1.2.3c)]`  
  *Justification*: The robot first tries to return the resource to a checkpoint, then to recharge; if neither succeeds it raises an alert.  

- **G1.1.1** → **AT1**  `[AND]`  
  *Justification*: The navigation goal is realized by task AT1.  

- **G1.1.2** → **AT2**  `[AND]`  
  *Justification*: The request goal is realized by task AT2.  

- **G1.1.3** → **AT3**  `[AND]`  
  *Justification*: Waiting is a task.  

- **G1.1.4** → **AT4**  `[AND]`  
  *Justification*: The pick‑up action is a task.  

- **G1.1.5a** → **AT5**  `[AND]`  
  *Justification*: Return‑to‑charge is a task.  

- **G1.1.5b** → **AT6**  `[AND]`  
  *Justification*: Assignment message is a task.  

- **G1.2.1** → **AT7**  `[AND]`  
  *Justification*: Navigation to destination is a task.  

- **G1.2.2** → **AT8**  `[AND]`  
  *Justification*: Delivery action is a task.

### Key Design Choices

- **Perform vs. Query vs. Achieve**  
  *All high‑level mission steps (collection, delivery, battery handling) are marked **Perform** because they require the robot to *act*.  
  The only *knowledge‑acquisition* subtask is the *order determination* (G1.0), which is a **Query**.  
  No explicit **Achieve** goals are needed because the mission is defined in terms of actions rather than a desired end state beyond the delivery itself.*

- **Fallback Decompositions**  
  Battery‑related contingencies are modeled with `FALLBACK`, reflecting the mission’s requirement that the robot should try a primary action (recharge) and if that fails, try an alternative (hand‑off or alert).*

- **Parallelism**  
  The root mission is sequential, but the *fallback* structure and the separate collection/delivery phases allow simultaneous execution when multiple robots are available, satisfying the “parallel collect‑deliver” requirement implicitly.*

- **Task Attributes**  
  All tasks involve a single robot at a specific location (storage, delivery point, checkpoint, charging station, manager office). The number of robots is fixed to 1 for each concrete action because each task represents an atomic operation performed by a single robot.  

This goal‑task decomposition fully captures the mission description and provides a clear, justified hierarchical model for multi‑robot coordination.
