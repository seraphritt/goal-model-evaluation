Below is a structured goal model for the mission. I model the mission as a **hospital logistics multi-robot mission**, where one or more robots collect resources from storage locations and deliver them to a requesting agent at a specified location.

## 1. Modeling rationale

The mission has four main concerns:

1. **Understand the request**: identify required resources, requesting agent, destination, and storage sources.
2. **Plan the mission**: compute collection order using waiting time plus robot path cost, and decide whether one or multiple robots should be assigned.
3. **Execute collection and delivery**: collect resources from storages, then deliver them to the specified location.
4. **Handle contingencies**: react to low battery differently in collection and delivery phases, including reassignment, checkpoint handoff, alerting, and reporting.

The mission is mostly modeled with **AND decompositions**, because the request cannot be fulfilled unless planning, collection, delivery, and exception handling are all available. The main explicit alternative behavior is modeled with **FALLBACK**, especially for battery and checkpoint failure situations.

# 5. Logical Relationships

## Top-level mission

* **G1 -> G2, G5, G8 [AND][sequential: `G2;G5;G8`]**

  * **Justification**: The mission cannot be fulfilled unless the system first identifies the request, then plans and assigns the mission, and finally executes collection and delivery.

---

## Requirement identification

* **G2 -> G3, G4 [AND][sequential: `G3;G4`]**

  * **Justification**: The system must first know what was requested, then determine where the requested resources can be found.

* **G3 -> AT1, AT2 [AND]**

  * **Justification**: Capturing the request alone is not enough; the robot must also extract the operational parameters needed for planning.

* **G4 -> AT3, AT4 [AND]**

  * **Justification**: The robot must both query the storage catalog and confirm that the resources are actually available.

---

## Planning and allocation

* **G5 -> G6, G7 [AND][sequential: `G6;G7`]**

  * **Justification**: The collection order must be calculated before assigning robots to concrete subtasks.

* **G6 -> AT5, AT6, AT7 [AND]**

  * **Justification**: The mission states that order is based on waiting time plus path. Therefore, both values must be estimated before ranking storages.

* **G7 -> AT8, AT9 [AND]**

  * **Justification**: The system must decide the number of robots and then assign concrete collect-deliver subtasks.

---

## Execution of transport mission

* **G8 -> G9, G15, G20 [AND][parallel/sequential combined: `(G9;G15)#G20`]**

  * **Justification**: For each resource flow, collection must precede delivery. However, coordination of multiple robots can occur in parallel with execution.

---

## Collection phase

* **G9 -> G10, G11, G12 [AND][parallel/sequential combined: `(G10;G11)#G12`]**

  * **Justification**: The robot must reach storage and request/receive resources in sequence. Battery monitoring is concurrent because low battery can occur at any time during collection.

* **G10 -> AT10 [AND]**

  * **Justification**: Reaching storage is operationalized by navigating to the selected storage location.

* **G11 -> AT11, AT12, AT13 [AND]**

  * **Justification**: The robot must send the precise request, wait for retrieval, and load the resource before delivery can begin.

* **G12 -> G13, G14 [AND][FALLBACK: `FALLBACK(G13,G14)`]**

  * **Justification**: The preferred situation is that the robot continues collection with sufficient battery. If that fails because battery reaches 10%, the fallback is to return to recharge and reassign the mission.

* **G13 -> AT14, AT15 [AND]**

  * **Justification**: The robot must monitor the battery and continue collection only if the collection threshold is respected.

* **G14 -> AT16, AT17 [AND]**

  * **Justification**: When battery is low in collection, both actions are required: the robot returns to recharge and another robot receives the mission.

---

## Delivery phase

* **G15 -> G16, G17 [AND][parallel: `G16#G17`]**

  * **Justification**: Delivery runs are executed while delivery battery contingency is monitored in parallel.

* **G16 -> AT18, AT19, AT20, AT21 [AND]**

  * **Justification**: Since the robot may need several runs, it must calculate runs, transport each batch, hand over resources, and repeat until all are delivered.

* **G17 -> G18, G19 [AND][FALLBACK: `FALLBACK(G18,G19)`]**

  * **Justification**: If battery reaches 30% during delivery, the robot first attempts checkpoint handoff. If it cannot return the resource to a checkpoint, the fallback is alerting and reporting.

* **G18 -> AT22, AT23, AT24 [AND]**

  * **Justification**: Checkpoint handoff requires moving the resource, registering its position, and assigning the remaining task to another robot.

* **G19 -> AT25, AT26 [AND]**

  * **Justification**: The mission explicitly requires both an alert and a report to the sector manager.

---

## Parallel robot coordination

* **G20 -> AT27, AT28 [AND]**

  * **Justification**: When multiple robots are used, the system must monitor each robot’s subtask and confirm that the whole mission is complete, not only one robot’s part.

---
