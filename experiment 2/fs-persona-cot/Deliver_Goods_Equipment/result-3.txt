Below is a structured **goal model** for the multi-robot resource collection and delivery mission. I treat the mission as a hospital/logistics environment because the description mentions sterile medical equipment, laundry, storage rooms, checkpoints, and sector managers.

## 1. Design rationale used for the decomposition

The mission has a clear lifecycle:

**request received → request information queried → collection strategy planned → robot(s) assigned → resources collected → resources delivered → mission closed**

The main contingencies are:

1. **Collection battery threshold: 10%**
   If the assigned robot reaches low battery during collection, it must go to the charging station and transfer the mission to another robot.

2. **Delivery battery threshold: 30%**
   If the robot reaches low battery during delivery, it must place the resource at a checkpoint and transfer the remaining delivery task to another robot.

3. **Checkpoint failure**
   If the robot cannot return the resource to a checkpoint, the system must trigger an alert and send a report to the sector manager.

4. **Parallelization**
   If multiple items are required from different storages, multiple robots may be assigned to parallel collect-deliver tasks to reduce completion time.

# 5. Logical Relationships

## Root mission

**G1 → G2, G5, G10, G16, G25 [AND] [sequential: `G2;G5;G10;G16;G25`]**

* **Justification:** The mission must first understand the request, then plan, then collect, then deliver, and finally close the mission. All phases are necessary, and the order is sequential.

---

## Request characterization

**G2 → G3, G4 [AND] [sequential: `G3;G4`]**

* **Justification:** The system must know what was requested before it can identify storage locations and calculate routes. Both pieces of information are required.

**G3 → AT1, AT2 [AND] [sequential]**

* **Justification:** The request must first be received and then parsed into resource type, quantity, destination, and requester.

**G4 → AT3, AT4 [AND] [parallel]**

* **Justification:** Storage availability and route/waiting estimates are both required and can be obtained in parallel once the request details are known.

---

## Strategy preparation

**G5 → G6, G7 [AND] [sequential: `G6;G7`]**

* **Justification:** The storage order should be computed before robot assignment is finalized, because the assignment depends on storage distribution and path cost.

**G6 → AT5 [AND]**

* **Justification:** Computing the ordered route directly fulfills the goal of defining the storage visit order.

**G7 → G8, G9 [AND] [fallback: `FALLBACK(G8,G9)`]**

* **Justification:** Parallel execution is preferred when multiple items are required from different storages because it reduces mission time. If parallel execution is not applicable or feasible, the system falls back to one robot.

**G8 → AT6, AT7 [AND] [sequential]**

* **Justification:** Items must be partitioned before multiple robots can be assigned to separate collect-deliver tasks.

**G9 → AT8 [AND]**

* **Justification:** A single robot assignment is sufficient when the request does not benefit from parallelization.

---

## Collection phase

**G10 → G11, G15 [AND] [fallback: `FALLBACK(G11,G15)`]**

* **Justification:** Normal collection is attempted first. If the robot reaches 10% battery during collection, the mission switches to the low-battery recovery path.

**G11 → G12, G13, G14 [AND] [sequential: `G12;G13;G14`]**

* **Justification:** The robot must reach storage before requesting resources, and the resources must be retrieved before they can be loaded.

**G12 → AT9, AT10 [AND] [parallel]**

* **Justification:** The robot navigates to storage while continuously monitoring battery. Monitoring happens during movement, not after.

**G13 → AT11, AT12 [AND] [sequential]**

* **Justification:** The robot first sends the precise request message and then waits until storage retrieves the resources.

**G14 → AT13 [AND]**

* **Justification:** Loading or securing the resource completes the collection step.

**G15 → AT14, AT15 [AND] [sequential]**

* **Justification:** At 10% battery during collection, the robot must return to the charging station and transfer the mission to another robot.

---

## Delivery phase

**G16 → G17, G21 [AND] [fallback: `FALLBACK(G17,G21)`]**

* **Justification:** Normal delivery is attempted first. If the battery reaches 30% during delivery, the system executes checkpoint-based recovery.

**G17 → G18, G19, G20 [AND] [sequential: `G18;G19;G20`]**

* **Justification:** The robot must know how many runs are required, execute those runs, and then confirm delivery.

**G18 → AT16 [AND]**

* **Justification:** Calculating delivery runs satisfies the need to make as many runs as necessary.

**G19 → AT17, AT18, AT20 [AND] [parallel monitoring with sequential delivery]**

* **Justification:** The robot transports and unloads resources, while battery monitoring occurs continuously during delivery.

**G20 → AT19 [AND]**

* **Justification:** Delivery is only complete when receipt is confirmed.

---

## Delivery low-battery recovery

**G21 → G22, G23, G24 [AND] [fallback: `FALLBACK((G22;G23),G24)`]**

* **Justification:** The robot first tries to checkpoint the resource and transfer the task. If checkpoint return fails, alert and report escalation is required.

**G22 → AT21, AT22 [AND] [sequential]**

* **Justification:** The resource must first be placed at the checkpoint, and then its position must be registered.

**G23 → AT23, AT24 [AND] [sequential]**

* **Justification:** A replacement robot must be assigned before it can retrieve the resource from the checkpoint.

**G24 → AT25, AT26 [AND] [sequential]**

* **Justification:** In case of checkpoint failure, an alert must be triggered and the sector manager must receive a report.

---

## Mission closure

**G25 → AT27 [AND]**

* **Justification:** The final mission status must be recorded for traceability, whether the mission was completed, transferred, or escalated.
