## 1. Modeling rationale

The mission can be decomposed into four main concerns:

1. **Understand the request**: identify what resources are required, where they are stored, who requested them, and where they must be delivered.
2. **Plan the mission**: define the storage visiting order using the sum of estimated waiting time and robot path cost, then decide whether one robot or multiple robots should be assigned.
3. **Execute collection before delivery**: the description clearly separates a **collection phase** and a **delivery phase**, so these must be modeled sequentially.
4. **Handle battery-related failures with fallback**: low battery does not represent an optional alternative; it is a contingency. Therefore, it is best modeled with `FALLBACK(...)`.

I model the multi-robot case as a parallel instantiation of the same collect-deliver workflow. When multiple items are required from different storages, the mission can instantiate several collect-deliver jobs in parallel.

# 5. Logical Relationships

## Top-level mission

* **G1 -> G2, G9 [AND][sequential: `G2;G9`]**

  * **Justification:** The mission must first be planned and then executed. Execution without request details, storage information, route order, and robot assignment would be unsafe or incomplete.

---

## Mission preparation

* **G2 -> G3, G4, G5, G6 [AND][sequential: `G3;G4;G5;G6`]**

  * **Justification:** All preparation goals are required. The system must know the request, identify storage candidates, compute route order, and assign robots before execution.

* **G3 -> AT1, AT2 [AND]**

  * **Justification:** Reading the request and extracting its fields are both required to know what resources are needed and where they should be delivered.

* **G4 -> AT3, AT4 [AND]**

  * **Justification:** Storage availability and waiting time are both needed because the robot must know where resources are and how long retrieval may take.

* **G5 -> AT5, AT6 [AND]**

  * **Justification:** The order depends on both path cost and waiting time. Therefore, the robot must estimate paths and compute the combined ordering criterion.

---

## Robot allocation

* **G6 -> G8, G7 [AND/Fallback][`FALLBACK(G8,G7)`]**

  * **Justification:** When multiple items from different storages exist, the preferred strategy is to assign multiple robots in parallel to reduce mission time. If parallel assignment is not applicable or unavailable, one robot can still execute the mission.

* **G7 -> AT7 [AND]**

  * **Justification:** Single-robot allocation is fulfilled by assigning one robot to the full route.

* **G8 -> AT8, AT9 [AND]**

  * **Justification:** Parallel execution requires splitting the resources into jobs and assigning multiple robots to those jobs.

---

## Execution of collect-deliver jobs

* **G9 -> G10, G15 [AND][sequential per job: `G10;G15`; parallel across jobs: `(G10;G15)#(G10;G15)`]**

  * **Justification:** For each resource job, collection must occur before delivery. However, when there are multiple robots, several collect-deliver jobs can run in parallel.

---

## Collection phase

* **G10 -> G11, G14 [AND/Fallback][`FALLBACK(G11,G14)`]**

  * **Justification:** The robot first attempts normal collection. If battery reaches the 10% threshold during collection, the mission switches to the low-battery recovery procedure.

* **G11 -> G12, G13 [AND][sequential: `G12;G13`]**

  * **Justification:** The robot must first reach the storage location and then request/receive the resource.

* **G12 -> AT10, AT11 [AND]**

  * **Justification:** Navigation and battery monitoring are both required during collection. The robot must move to storage while ensuring it does not violate the 10% threshold.

* **G13 -> AT12, AT13, AT14, AT15 [AND]**

  * **Justification:** The robot must wait until it is time to request, send the precise specification, wait for retrieval, and secure the retrieved resource before delivery can begin.

* **G14 -> AT16, AT17 [AND]**

  * **Justification:** When collection battery is low, the robot must return to recharge and assign the mission to another robot. Both actions are explicitly required.

---

## Delivery phase

* **G15 -> G16, G19 [AND/Fallback][`FALLBACK(G16,G19)`]**

  * **Justification:** Normal delivery is attempted first. If battery reaches 30% during delivery, the robot must switch to the checkpoint recovery procedure.

* **G16 -> G17, G18 [AND][sequential: `G17;G18`]**

  * **Justification:** The resources must first be transported to the specified location and then handed over/confirmed.

* **G17 -> AT18, AT19, AT20 [AND]**

  * **Justification:** Delivery requires navigation, battery monitoring, and repeated runs when necessary.

* **G18 -> AT21, AT22 [AND]**

  * **Justification:** The resource must be handed to the requesting agent, and the delivery must be confirmed as complete.

---

## Delivery low-battery recovery

* **G19 -> G20, G21 [AND/Fallback][`FALLBACK(G20,G21)`]**

  * **Justification:** The first recovery attempt is to place the resource at a checkpoint and reassign the remaining task. If that fails, the system must escalate by alerting and reporting to the sector manager.

* **G20 -> AT23, AT24 [AND]**

  * **Justification:** The robot must place the resource at the checkpoint and inform the replacement robot where the resource is.

* **G21 -> AT25, AT26 [AND]**

  * **Justification:** The mission explicitly requires both an alert and a report to the sector manager if checkpoint return fails.
