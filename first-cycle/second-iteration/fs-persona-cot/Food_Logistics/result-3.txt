## 4.  Logical Relationships

- **G1 → G1.1, G1.2, G1.3, G1.4 [AND] [sequential]**  
  - **Justification:** All four sub‑tasks must be completed in the specified order for the overall delivery mission to succeed.

- **G1.3 → G1.3.2, G1.3.1 [FALLBACK] [sequential]**  
  - **Justification:** The robot first attempts to place the meal on a tray (`G1.3.2`). If that fails (e.g., patient cannot retrieve), it falls back to placing it on the table (`G1.3.1`). The fallback ensures that at least one delivery mode succeeds.

- **G1.3.2 → G1.3.2.1, G1.3.2.2 [AND] [sequential]**  
  - **Justification:** The robot must query the patient’s ability (`G1.3.2.1`) before physically placing the meal on the tray (`G1.3.2.2`).

- **G1.4 → G1.4.1, G1.4.2, G1.4.3 [FALLBACK] [sequential]**  
  - **Justification:** Dish retrieval is attempted first unassisted (`G1.4.1`). If that fails, it tries robot cooperation (`G1.4.2`). Finally, it falls back to human assistance (`G1.4.3`). The nested fallback ensures all possibilities are covered in order of effort.

- **G1.4.1 → AT8 [AND]**  
  - **Justification:** If unassisted retrieval is chosen, the robot executes the single task AT8.

- **G1.4.2 → AT9 [AND]**  
  - **Justification:** Robot cooperation requires the coordination task AT9.

- **G1.4.3 → AT10 [AND]**  
  - **Justification:** Human assistance requires the task AT10.

- **G1.3.1 → AT3 [AND]**  
  - **Justification:** Placing the meal on the table is a single actionable step.

- **G1.3.2.1 → AT11 [AND]**  
  - **Justification:** Querying patient information is a single action.

- **G1.3.2.2 → AT4, AT5, AT6 [AND]**  
  - **Justification:** After placing the meal on the tray, the robot must monitor retrieval (`AT5`) and possibly alert if wrong meal is taken (`AT6`).

- **G1.1 → AT1, AT2 [AND]**  
  - **Justification:** Picking up and transporting the meal are consecutive actions.

- **G1.2 → AT7 [AND]**  
  - **Justification:** Door opening is a single action.

### Key Design Decisions & Rationale

| Decision | Why it fits the mission |
|----------|--------------------------|
| **Use of fallback for tray vs. table delivery** | The mission explicitly states that tray delivery may fail due to patient inability or lack of human help. Fallback guarantees that the robot will still deliver food by placing it on the table. |
| **Query goal for patient retrieval capability** | The information is uncertain and crucial for deciding delivery mode; a query goal is the correct semantic abstraction. |
| **Parallel/Sequential runtime annotations** | The overall workflow is linear (pickup → door → delivery → dish cleanup), but within delivery and dish cleanup we use fallbacks to reflect alternative strategies. |
| **Task “Monitor meal retrieval”** | The robot must verify the correct meal is taken; this is operational and can be performed by the robot’s sensors. |
| **Task “Alert wrong meal retrieved”** | An action that must be executed if the monitoring detects a mismatch; failure to alert would compromise patient safety. |
| **Task “Retrieve dishes with robot cooperation”** | Some dishes may be heavy or numerous; the mission mentions cooperation with another robot. |
| **Task “Retrieve dishes with human assistance”** | The mission states that human help may be necessary; the robot must be prepared to involve a nurse/visitor. |

## 5.  Final Model Overview

The model captures all intentional objectives (goals) and operational actions (tasks) required to deliver meals and clean dishes in a hospital setting. The hierarchical structure, runtime annotations, and logical relationships explicitly encode the uncertainties and cooperation requirements described in the mission statement. All goals and tasks are linked through AND/OR (fallback) operators, ensuring a clear and executable plan for a multi‑robot system.
