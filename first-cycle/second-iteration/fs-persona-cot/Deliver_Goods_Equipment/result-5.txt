## 2. Task‑Model (tables)

| **Name** | **Text** | **Relation** | **Location** | **Number of Robots** | **Justification** |
|----------|----------|--------------|--------------|---------------------|--------------------|
| **AT1 – Move to Storage** | Robot physically travels from its current location to the storage that holds the requested resource. | AND (under G1.1.1) | `Storage` | `1` | Only one robot needs to reach the storage to initiate the request. |
| **AT2 – Send Request Message** | Robot sends a digital message to the storage system specifying the exact resource(s) required. | AND (under G1.1.2) | `Storage` | `1` | Direct communication is needed; no other robot is involved. |
| **AT3 – Wait for Retrieval** | Robot remains at the storage until the storage confirms that the items have been retrieved. | AND (under G1.1.3) | `Storage` | `1` | The robot must wait at the point of hand‑over; concurrency with other tasks is not allowed. |
| **AT4 – Deliver to Destination** | Robot carries the retrieved resource(s) to the destination location specified by the requester. | AND (under G1.2.1) | `Destination` | `1` | The delivery action is carried out by one robot; multiple robots would duplicate the same delivery. |
| **AT5 – Monitor Battery (Collect)** | Robot continually checks its battery level while in the collection phase. | AND (under G1.1.4) | `Current` | `1` | Battery monitoring is performed by the robot itself. |
| **AT6 – Go to Charging Station** | Robot returns to the charging dock to recharge its battery. | AND (under G1.1.5) | `Charging Station` | `1` | Only the robot with low battery needs to recharge; the rest of the fleet remains idle or takes over. |
| **AT7 – Return to Checkpoint** | Robot transports the partially‑delivered resource to a predefined checkpoint before re‑assigning the task. | AND (under G1.2.3) | `Checkpoint` | `1` | The robot must bring the resource back to a known location for the next robot. |
| **AT8 – Assign Remaining Task** | Robot communicates with a second robot, indicating the checkpoint location and remaining portion of the delivery. | AND (under G1.1.5 & G1.2.3) | `Current / Communication Channel` | `1` | The reassignment action is performed by the robot that just recharged or returned to the checkpoint. |
| **AT9 – Trigger Alert** | Robot activates an alarm signal and logs the failure to return the resource to a checkpoint. | AND (under G1.2.4) | `Current / System` | `1` | Alerts are local to the robot that failed; no other robot is needed. |
| **AT10 – Send Report** | Robot sends a detailed report to the sector manager about the failure. | AND (under G1.2.4) | `System` | `1` | Reporting is handled by the same robot that triggered the alert. |
| **AT11 – Parallel Allocation** | System assigns multiple robots to separate collection‑delivery sub‑tasks when several items are needed. | OR (under G1.3) | `System` | `[1,n]` | The mission explicitly allows parallelism; the exact number depends on the number of items and available robots. |

## 4. Logical Relationships (tree view)

- **G1 → G1.1, G1.2**  
  - **Justification:** Collection must finish before delivery; both are mandatory → **AND**.

- **G1.1 → G1.1.1, G1.1.2, G1.1.3, FALLBACK(G1.1.4, G1.1.5)**  
  - **Justification:** All steps of the collection phase are required; the fallback branch is taken only if battery‑low fails the check → **AND** for normal path, **FALLBACK** for low battery.

- **G1.2 → G1.2.1, G1.2.2, FALLBACK(G1.2.3, G1.2.4)**  
  - **Justification:** Delivery steps are mandatory; battery‑low leads to checkpoint return, and if that fails, alert/report is triggered → **AND** + **FALLBACK**.

- **G1.1.1 → AT1**  
  - **Justification:** The “navigate” goal is realized by a single task. → **AND**.

- **G1.1.2 → AT2**  
  - **Justification:** The “request” goal is realized by a single task. → **AND**.

- **G1.1.3 → AT3**  
  - **Justification:** The “wait” goal is realized by a single task. → **AND**.

- **G1.1.4 → AT5**  
  - **Justification:** Battery monitoring is a task. → **AND**.

- **G1.1.5 → AT6, AT8**  
  - **Justification:** When battery is low, the robot must recharge and hand over the remaining task → **AND**.

- **G1.2.1 → AT4**  
  - **Justification:** The “deliver” goal is realized by a single task. → **AND**.

- **G1.2.2 → AT5**  
  - **Justification:** Same battery‑monitor task used for delivery. → **AND**.

- **G1.2.3 → AT7, AT8**  
  - **Justification:** Return to checkpoint and assign remainder → **AND**.

- **G1.2.4 → AT9, AT10**  
  - **Justification:** Alert and report tasks executed together → **AND**.

- **G1.3 → AT11**  
  - **Justification:** Parallel allocation is optional; if chosen, it is performed by a single task. → **OR** (between G1.3 and the single‑robot sequential plan).

---

### Final Remarks
The goal model above reflects the mission’s structure: a top‑level **Achieve** goal that is decomposed into two mandatory **Perform** sub‑goals (collection & delivery). Each sub‑goal is further decomposed into atomic **Perform** goals that are concretely instantiated by **Task** nodes. The **FALLBACK** operator captures the battery‑dependent contingency plans, while the **OR** operator in `G1.3` allows optional parallel execution when multiple items are requested. All relationships are justified by explicit statements in the mission description.
