### 5. Key Design Decisions & Justifications  

1. **Parallel vs Sequential Execution** – The root goal G1 uses a parallel operator (`#`) because, when several items are requested from different storages, different robots can perform collection and delivery simultaneously.  
2. **Fallback Mechanism** – Collection and delivery each have a fallback sub‑goal that is only triggered when the battery falls below the specified threshold. The `FALLBACK` operator guarantees the primary sequence is attempted first, and only if it fails will the recovery path run.  
3. **Goal Types** – All high‑level objectives (G1, G2, G3) are **Achieve** goals because they express a target condition that must become true. Sub‑goals such as navigation, request, wait, and re‑charging are **Perform** goals because they require the robot to carry out an action; no state change is explicitly specified beyond the action itself.  
4. **Task Allocation** – Every task is assigned to a single robot (`[1]`) because each robot operates independently. The model can be extended to `[1,n]` if a group of robots should coordinate a single task (e.g., carrying heavy resources), but the mission description does not require this.  
5. **Locations** – Task locations are derived directly from the mission narrative: storages, charging stations, checkpoints, delivery destinations, and the control center.  
6. **Hierarchical Depth‑First Numbering** – All IDs follow a depth‑first traversal, ensuring unique identifiers that reflect the structure of the model.  

This goal‑model fully captures the operational logic of the multi‑robot mission as described, providing clear decomposition, justification, and actionable tasks.
