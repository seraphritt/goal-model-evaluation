## 1.  Mission‑level reasoning

Below is a detailed, step‑by‑step reasoning of how the natural‑language mission description has been transformed into a **goal model** suitable for a multi‑robot system.  
The goal model follows the rules that were given:

* Every goal has an ID starting with **G** followed by a number (depth‑first order).  
* Every task has an ID starting with **AT** followed by a number (depth‑first order).  
* Every goal has a runtime annotation that captures the execution structure of its children.  
* Every goal and task is linked to its parent by an explicit **AND** or **OR** decomposition.  
* The type of each goal (Perform, Query, Achieve) is chosen according to the semantics of the mission text.  
* Where a goal is a leaf node the runtime annotation is “-”.  
* Every task carries a *Location* and a *Number of Robots* that is justified by the mission requirements.

The root of the model is **G1 – “Achieve Resource Delivery Mission”**.  The mission is naturally split into two consecutive phases:

1. **Collect Resources** – robots must locate the requested items, request them from storage, and wait until they are retrieved.  
2. **Deliver Resources** – robots must transport the items to the specified destination.  

Each phase has to respect the **battery constraints** (10 % for collection, 30 % for delivery) and the **failure handling** (return to a checkpoint, trigger alert).  Those constraints are represented by dedicated sub‑goals and the *fallback* operator.

Because the mission allows parallelism when several items are needed, the model keeps the structure of the two phases **sequential** (G1 → G2 → G3) but the **collection** and **delivery** sub‑goals are themselves decomposed in an **AND** fashion, meaning that all the constituent tasks must be completed (they can, however, run in parallel on different robots – this is expressed by the *Number of Robots* property of the tasks).

## 5.  Logical relationships (decomposition graph)

```
G1 -> G2, G3  [AND][sequential]        // G1 must perform collection then delivery
   - G2 -> G3, G4  [AND][sequential]   // Collection: plan then execute
        - G3 -> AT1, AT2  [AND][parallel]   // Both planning tasks run (can be parallel)
        - G4 -> G5, G6  [AND][fallback]     // Normal execution or fallback if battery low
            - G5 -> AT3, AT4, AT5  [AND]    // Navigate, send request, wait
            - G6 -> AT6, AT7  [AND]        // Recharge, hand over task
   - G3 -> AT14, AT15 [AND][parallel]  // Delivery planning tasks

G1 -> G7, G8  [AND][sequential]        // Delivery: plan then execute
   - G7 -> G8, G9  [AND][sequential]   // Delivery planning then execution
        - G8 -> AT14, AT15  [AND][parallel]  // Delivery planning tasks
        - G9 -> G10, G11  [AND][fallback]    // Normal execution or fallback if battery low
            - G10 -> AT8, AT9 [AND]         // Navigate and deliver
            - G11 -> G12, G13 [AND][fallback] // Return to checkpoint or alert
                - G12 -> AT10, AT11 [AND]    // Return and hand over
                - G13 -> AT12, AT13 [AND]    // Trigger alert and report
```

**Justifications**

* **AND** is used when all sub‑goals/tasks must be accomplished for the parent to be satisfied (e.g., planning and execution, navigation, sending a request).  
* **OR** is not used because the mission description does not present alternative ways to satisfy a goal (except the fallback).  
* **Sequential** (`;`) expresses the natural order of phases: first collect, then deliver.  
* **Parallel** (`#`) is used only for tasks that can logically run at the same time (e.g., estimating waiting time and computing a path).  
* **Fallback** encapsulates the battery‑dependent contingency behaviour; the second branch is only attempted if the first fails.  

This goal model faithfully captures the mission’s requirements, the robot‑centric constraints, and the possible failure handling, while leaving room for multiple robots to act in parallel where the model allows.
