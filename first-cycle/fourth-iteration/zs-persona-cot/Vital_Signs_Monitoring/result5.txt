Based on the mission description, I treat the model as a **periodic hospital-room vital-sign checking mission** in which robots must visit occupied rooms, prioritize high-risk patients, perform condition-specific checks, handle failures, and escalate infeasibility. The mission text supports the recurring two-hour cycle, occupied-room visits, pre-entry checks, patient identification, vital-sign collection, failure handling, hygiene actions, extra-robot allocation, and manager escalation. ## 1. Design rationale

The mission naturally decomposes into five main concerns:

1. **Plan the mission scope and robot resources**: identify occupied rooms, high-risk patients, and whether the assigned robots can complete the mission in time.
2. **Prioritize high-risk patients**: all high-risk patients must be checked in the first 15 minutes.
3. **Execute the room-checking workflow**: for each occupied room, the robot must satisfy pre-entry conditions, identify the correct patient, interact with the patient, collect required vital signs, handle failures, and finish the room.
4. **Apply patient-condition-specific checks**: infectious disease, post-surgical condition, and diabetes history each require different measurements.
5. **Handle exceptional cases**: patient unavailable, insufficient battery, failed collection, non-response, infectious-disease sterilization, patient-contact disinfection, extra robot assignment, and manager alert.

I use **AND decompositions** when the mission says several things are jointly required, such as checking availability and battery before entering. I use **OR decompositions** only for true alternatives, such as identifying the patient by asking or scanning the barcode. I use **FALLBACK** only when the description explicitly gives a primary action and a secondary action if the first cannot proceed, such as assigning more robots if the mission cannot be completed in time, and alerting the manager if no robot combination can complete it. # 5. Logical relationships

## Top mission relationships

**G1 -> G2, G6, G7 [AND][sequential: `G2;G6;G7`]**  
**Justification:** The mission must first define scope and robot feasibility, then ensure the high-risk timing constraint, and then execute the room-checking workflow. These are not alternatives; they are all required for the mission to be considered complete.

**G2 -> G3, G4, G5 [AND][mixed: `(G3#G4);G5`]**  
**Justification:** Occupied rooms and high-risk patients can be identified in parallel because both are information-gathering steps. Robot allocation feasibility depends on knowing the mission scope, so it comes after those queries.

**G5 -> AT3, AT4, AT5 [AND][fallback: `FALLBACK(AT3,FALLBACK(AT4,AT5))`]**  
**Justification:** The assigned robot is the primary option. If that cannot complete the mission in time, additional robots may be assigned. If no combination can complete the mission, the responsible manager must be alerted.

---

## Room-checking relationships

**G7 -> G8, G13, G16, G24 [AND][sequential: `G8;G13;G16;G24`]**  
**Justification:** The robot must satisfy pre-entry conditions before entering, identify the correct patient before collecting signs, perform the patient procedure, and finally mark the patient done and handle post-room duties.

**G8 -> G9, G10, G11, G12 [AND][fallback: `FALLBACK(G9,G10);FALLBACK(G11,G12)`]**  
**Justification:** Patient availability and battery sufficiency are both required before room entry. If the patient is unavailable, the robot returns in 5 minutes. If the battery is insufficient, the robot recharges and the tasks are reassigned.

**G13 -> G14, G15 [OR][parallel/alternative: `G14#G15`]**  
**Justification:** The mission says the robot may identify the correct patient either by asking or by scanning the barcode. Since no priority order is given, this is modeled as OR rather than FALLBACK.

---

## Patient procedure relationships

**G16 -> G17, G18, G22 [AND][sequential: `G17;G18;G22`]**  
**Justification:** The robot first prepares the patient by approaching, announcing, and instructing. Then it collects vital signs. If a necessary sign fails to be collected, failure handling is triggered.

**G17 -> AT14, AT15, AT16 [AND][sequential: `AT14;AT15;AT16`]**  
**Justification:** Once inside the room, the robot must approach the patient, announce the procedure, and provide instructions. These are complementary actions, not alternatives.

**G18 -> G19, G20, G21 [AND][parallel/condition-dependent: `G19#G20#G21`]**  
**Justification:** The required measurements depend on patient conditions. If multiple conditions apply to the same patient, the corresponding measurement goals must all be satisfied.

**G19 -> AT17, AT18, AT19, AT20 [AND][parallel: `AT17#AT18#AT19#AT20`]**  
**Justification:** Infectious-disease patients require heart rate, blood pressure, body temperature, and blood oxygenation. All four signs are necessary.

**G20 -> AT21, AT22 [AND][parallel: `AT21#AT22`]**  
**Justification:** Post-surgical patients require both heart rate and blood oxygenation.

**G21 -> AT23 [AND][leaf task]**  
**Justification:** Patients with diabetes history require blood glucose checking.

---

## Failure-handling relationships

**G22 -> AT24, G23 [AND][sequential: `AT24;G23`]**  
**Justification:** If collection fails, the robot first asks assessment questions. If the patient does not respond, the robot alerts the responsible nurse or doctor.

**G23 -> AT25 [AND][leaf task]**  
**Justification:** Alerting the nurse or doctor is the concrete operational task that satisfies the non-response alert goal.

---

## Completion and hygiene relationships

**G24 -> AT26, AT27, G25, G26 [AND][sequential plus parallel: `AT26;AT27;(G25#G26)`]**  
**Justification:** The robot marks the patient as done, proceeds to the next room, and performs applicable hygiene actions. Sterilization and actuator disinfection are condition-triggered but both may be required.

**G25 -> AT28 [AND][leaf task]**  
**Justification:** If the robot leaves a room where an infectious-disease patient is treated, sterilization is mandatory.

**G26 -> AT29 [AND][leaf task]**  
**Justification:** If patient contact occurs, actuator disinfection is mandatory.

# 6. Final model interpretation

This goal model represents a **multi-robot, condition-aware, exception-handling hospital mission**. The main mission is an **Achieve goal** because it aims to reach a target state: all required patients are checked, or infeasibility is escalated. Query goals are used where the robot must obtain information, such as occupied rooms, patient availability, battery sufficiency, identity, and risk category. Perform goals are used where the mission explicitly requires concrete actions, such as approaching the patient, sending alerts, sterilizing, and disinfecting.
