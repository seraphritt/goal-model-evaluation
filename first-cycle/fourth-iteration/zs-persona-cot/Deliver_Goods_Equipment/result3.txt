## Source-based modeling rationale

The mission has a **resource logistics objective**: a robot must collect required resources from storage and deliver them to a requesting agent at a specified location. The collection phase includes visiting storage places, ordering visits by waiting-time-plus-path estimation, requesting resources, and waiting for retrieval. The delivery phase begins after retrieval and may require multiple runs. Battery exceptions create fallback behavior: 10% during collection causes return to recharging and reassignment; 30% during delivery causes checkpoint handoff and reassignment; checkpoint-return failure triggers an alert and report. Parallelism is explicitly allowed when multiple items from different storages are required. Texto colado

I model this as an **AND-dominant goal tree** because most mission elements are jointly required: preparation, collection, delivery, exception handling, and reporting when needed. I use **FALLBACK** where the description gives normal behavior followed by an exception or failure condition, as required by the provided runtime definition. Texto colado

# Logical relationships

**G1 -> G2, G7 [AND][sequential: `G2;G7`]**  
- **Justification**: The mission must first be prepared, then executed. Collection and delivery require knowing the resources, storage places, order, and assigned robot(s).

**G2 -> G3, G4, G5, G6 [AND][sequential: `G3;G4;G5;G6`]**  
- **Justification**: Request details, storage identification, visit ordering, and robot assignment are complementary requirements.

**G7 -> G8, G16 [AND][parallel: `G8#G16`]**  
- **Justification**: Multiple robots can be assigned to parallel collect-deliver tasks when multiple items are required from different storages. Texto colado

**G8 -> G9, G12 [AND][sequential: `G9;G12`]**  
- **Justification**: Delivery begins only after resources have been retrieved. Texto colado

**G9 -> G10, G11 [AND][fallback: `FALLBACK(G10,G11)`]**  
- **Justification**: Normal collection is attempted first; the 10% battery condition triggers the fallback behavior.

**G10 -> AT1, AT2, AT3 [AND][sequential: `AT1;AT2;AT3`]**  
- **Justification**: The robot goes to storage, sends the request, and waits for retrieval.

**G11 -> AT4, AT5 [AND][sequential: `AT4;AT5`]**  
- **Justification**: The robot returns to recharge and then assigns the mission to another robot.

**G12 -> G13, G14, G15 [AND][nested fallback: `FALLBACK(G13,FALLBACK(G14,G15))`]**  
- **Justification**: Normal delivery is attempted first; delivery low battery triggers checkpoint handoff; checkpoint-return failure triggers alert/report escalation.

**G13 -> AT6, AT7 [AND][sequential: `AT6;AT7`]**  
- **Justification**: The robot performs delivery runs until all resources are at the specified location.

**G14 -> AT8, AT9 [AND][sequential: `AT8;AT9`]**  
- **Justification**: Returning the resource to checkpoint and assigning the remaining task are both required.

**G15 -> AT10, AT11 [AND][sequential: `AT10;AT11`]**  
- **Justification**: The alert and report are both required when checkpoint return fails.

**G16 -> G17, G20 [AND][sequential: `G17;G20`]**

**G17 -> G18, G19 [AND][fallback: `FALLBACK(G18,G19)`]**

**G18 -> AT12, AT13, AT14 [AND][sequential: `AT12;AT13;AT14`]**  
- **Justification**: Additional robots follow the same collection protocol.

**G19 -> AT15, AT16 [AND][sequential: `AT15;AT16`]**

**G20 -> G21, G22, G23 [AND][nested fallback: `FALLBACK(G21,FALLBACK(G22,G23))`]**

**G23 -> AT21, AT22 [AND][sequential: `AT21;AT22`]**
