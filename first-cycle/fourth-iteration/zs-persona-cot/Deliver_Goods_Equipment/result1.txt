# Multi-Robot System Mission: Goal Model Decomposition

## 1. Mission Analysis

### 1.1 Mission objective

The primary objective is to ensure that requested resources are collected from their respective storage locations and delivered to a requesting agent at a specified location, using one or more robots.

The mission must account for resource availability, collection order, robot assignments, battery limitations, recovery operations, and parallel execution when multiple resources are required from different storage locations.

The analysis follows the goal-model definitions, runtime operators, node attributes, and decomposition rules provided in the source document. Texto colado

### 1.2 Mission requirements identified

| ID | Requirement | Evidence from mission | Modeling implication |
|---|---|---|---|
| R1 | Collect and deliver resources | A robot must collect requested resources and deliver them to the requesting agent. | Root mission goal with collection and delivery subgoals. |
| R2 | Visit resource storage locations | The robot must go to storage places containing the resources. | Navigation and collection goals. |
| R3 | Determine collection order | Order depends on estimated waiting time plus the path the robot must travel. | Query and planning goals. |
| R4 | Request resources | The robot sends a message containing precise resource specifications. | Resource-request task. |
| R5 | Wait for resource retrieval | The robot waits until resources have been retrieved. | Waiting task, sequentially after requesting. |
| R6 | Perform multiple delivery runs | The robot makes as many runs as necessary. | Repeated transport task. |
| R7 | Handle low battery during collection | At 10%, return to the recharging station and reassign the mission. | Collection-phase fallback. |
| R8 | Handle low battery during delivery | At 30%, return the resource to a checkpoint and reassign the remaining task. | Delivery-phase fallback. |
| R9 | Transfer resource-position information | The replacement robot must know where the resource is positioned. | Handover task. |
| R10 | Handle checkpoint return failure | Trigger an alert and send a report to the sector manager. | Checkpoint-recovery fallback. |
| R11 | Support parallel operations | Multiple robots may perform collect-deliver tasks in parallel for different storage locations. | Concurrent mission execution. |

These requirements are derived from the mission description. Texto colado

## 2. Modeling Decisions

### 2.1 AND decomposition

AND decomposition represents complementary requirements.

For example, completing a collect-deliver operation requires both obtaining the resources and delivering them.

The relationship is therefore:

**G5 → G6, G17 [AND] [G6;G17]**

Collection must precede delivery for the same resources.

### 2.2 OR decomposition

OR decomposition applies when alternative subgoals can independently satisfy the parent.

The mission does not explicitly describe interchangeable methods of achieving its main objective.

In particular, the following are **not OR decompositions**:

- Single-robot versus multi-robot execution: these describe execution configurations.
- Collection versus delivery: both are required.
- Normal execution versus battery-related recovery: the recovery is conditional.
- Successful checkpoint return versus failure reporting: these describe normal execution and exception handling.

Accordingly, the model primarily uses AND decomposition, combined with sequential, parallel, and FALLBACK runtime annotations.

### 2.3 FALLBACK execution

The description identifies three conditional recovery situations.

**Collection-phase battery interruption**

```text
FALLBACK(
    NormalCollection,
    CollectionBatteryRecovery
)
```

The normal collection operation is pursued first. Battery depletion to the specified threshold interrupts that operation and activates recovery.

**Delivery-phase battery interruption**

```text
FALLBACK(
    NormalDelivery,
    DeliveryBatteryRecovery
)
```

The normal delivery operation is pursued first. A battery level of 30% activates the recovery procedure.

**Checkpoint return failure**

```text
FALLBACK(
    CheckpointHandover,
    FailureEscalation
)
```

The robot first attempts to return the resource to a checkpoint. If this operation fails, the system triggers an alert and reports the failure.

**Important modeling distinction:** A fallback may successfully handle an exception without completing the original mission. Reporting an unrecoverable checkpoint failure must not be treated as successful resource delivery.

### 2.4 Parallel execution

The mission explicitly permits multiple robots to execute collect-deliver operations in parallel when items are required from different storage locations.

For different assigned jobs, the execution structure is:

```text
CollectDeliver_JobA # CollectDeliver_JobB
```

This is an execution-level representation of multiple instances of the same collect-deliver goal, not an OR decomposition.

Within each individual job, collection must still precede delivery.

### 2.5 Modeling assumptions and limitations

Some information required for a fully executable model is not specified in the mission.

In particular:

1. The exact number of available robots is unspecified.
2. Resource quantities and robot carrying capacities are unspecified.
3. The physical locations where scheduling, estimation, and reassignment occur are unspecified.
4. The mechanism used to communicate resource-position information is unspecified.
5. The detailed process by which a replacement robot resumes the mission is unspecified.

The model uses variables where appropriate rather than inventing these values.

For robot quantities, **N** denotes the maximum number of robots available for the operation.

The description establishes that collection recovery occurs at 10% battery and delivery recovery at 30%. These thresholds are preserved exactly.

# 3. Hierarchical Goal Model

The following model uses depth-first numbering.

The hierarchy contains:

| Element | Quantity |

| Total goals | 27 |

The goal-to-goal decomposition is AND throughout this particular model. Terminal goal-to-task connections are operational realization links; they do not invent a second alternative solely to satisfy the minimum cardinality required for an AND/OR decomposition.

# 4. Goal Definitions and Attributes

The following tables specify the attributes of every goal, including the goal type, runtime annotation, target condition or queried property, decomposition relation, and justification.

For **Achieve** goals, the target condition describes the desired resulting state. For **Query** goals, the queried property identifies the information to retrieve. **Perform** goals focus on executing the specified operation.

## 4.1 Mission preparation goals

| Name | Text | Runtime | Goal Type | Target Condition / QueriedProperty | Relation | Justification |
|---|---|---|---|---|---|---|
| **G1: Fulfill Transportation Mission** | Ensure requested resources are collected and delivered to the requesting agent at the specified location. | `G2;G5` | Achieve | `AllRequestedResourcesDelivered = true` | AND | The mission requires preparing, collecting, and delivering resources. Preparation precedes execution. |
| **G2: Prepare Mission Execution** | Obtain the information needed to plan collection and establish robot assignments. | `G3#G4` | Achieve | `MissionPreparationCompleted = true` | AND | Collection estimates and robot assignments support mission execution. Their preparation can overlap. |
| **G3: Obtain Collection Estimates** | Obtain estimated waiting times and travel-path information for resource storage locations. | `-` | Query | `EstimatedWaitingTime`, `EstimatedTravelPath` | AND* | The mission states that storage order is determined using waiting-time estimates and travel paths. |
| **G4: Establish Robot Assignments** | Establish assignments for the collect-deliver operations using available robots. | `-` | Achieve | `RobotAssignmentsEstablished = true` | AND* | The description refers to assigned robots and permits multiple robots when resources originate from different storages. |

*AND on a terminal goal denotes its operational realization by the linked task, not a decomposition into multiple children.*

### Goal-type justifications

**G1 — Achieve:** The ultimate objective is a resulting world state: the requested resources are at the specified destination. Merely attempting delivery does not satisfy the mission.

**G2 — Achieve:** Preparation should result in sufficient planning information and established robot assignments.

**G3 — Query:** Waiting-time and path estimates are information that must be obtained about the environment. Retrieving this information does not itself transport resources.

**G4 — Achieve:** The intended resulting state is that appropriate robot assignments exist. Executing an assignment procedure without establishing assignments would be insufficient.

|---|---|---|---|---|---|---|

| **G9: Perform Normal Collection** | Navigate to resource storage locations and obtain requested resources. | `G10;G11` | Achieve | `RequiredResourcesObtained = true` | AND | The robot must reach storage before requesting and receiving resources. |

### Goal-type justifications

**G5 — Achieve:** Completion requires the assigned resources to reach their destination, not simply the execution of collection and transportation actions.

**G6 — Achieve:** The intended result is successful collection of the requested resources. If another robot takes over, collection must continue until that state is reached.

**G7 — Achieve:** The target state is an established storage-visit order. The calculation itself is operational, but the goal is to establish that order.

**G8 — Perform:** This goal coordinates the execution of normal collection or its recovery procedure. Its outcome alone does not guarantee that resources have been collected.

**G9 — Achieve:** The objective is to obtain the resources through navigation, requesting, and waiting.

**G10 — Achieve:** Reaching a storage location is a measurable state of the robot.

**G11 — Achieve:** The desired state is that the resources have been retrieved. Merely sending a request is not enough.

**G12 — Perform:** The requirement explicitly specifies the action of sending a message.

**G13 — Perform:** The requirement explicitly specifies a waiting activity. The completion event is resource retrieval.

## 4.3 Collection recovery goals

| Name | Text | Runtime | Goal Type | Target Condition / QueriedProperty | Relation | Justification |
|---|---|---|---|---|---|---|
| **G14: Recover Collection From Low Battery** | Recover the collection operation when the assigned robot's battery reaches 10%. | `G15;G16` | Perform | — | AND | The description requires returning to the recharging station and assigning the mission to another robot. |
| **G15: Return Robot for Recharging** | Return the affected robot to the recharging station. | `-` | Achieve | `RobotAtRechargingStation = true` | AND* | At the collection-phase battery threshold, the robot must return to the recharging station. |
| **G16: Transfer Collection Assignment** | Reassign the interrupted collection mission to another robot. | `-` | Achieve | `CollectionAssignedToReplacementRobot = true` | AND* | The mission explicitly requires another robot to take over. |

### Goal-type justifications

**G14 — Perform:** The goal describes execution of the recovery procedure. It is triggered by the specified battery condition.

**G15 — Achieve:** The intended resulting state is that the affected robot has returned to the recharging station.

**G16 — Achieve:** Successful reassignment requires the mission to be assigned to another robot.

### Collection recovery condition

```text
IF BatteryLevel <= 10%
AND MissionPhase = Collection
THEN
    FALLBACK(
        G9,
        G14
    )
```

The mission describes a low-battery threshold of 10%, so the condition is represented using that threshold. The exact sampling and interruption mechanism is not specified.

The recovery sequence is:

```text
G14: Recover Collection From Low Battery
    |
    +-- G15: Return Robot for Recharging
    |
    +-- G16: Transfer Collection Assignment
```

Runtime:

```text
G15;G16
```

The sequence follows the description, which places the robot's return before reassignment.

After reassignment, the replacement robot must carry out the remaining collection work for G6 to become satisfied. This continuation is required by the overall mission objective, although its detailed protocol is not described.

**G20 — Achieve:** The target condition directly represents successful resource delivery.

### Delivery recovery condition

```text
IF BatteryLevel <= 30%
AND MissionPhase = Delivery
THEN
    FALLBACK(
        G18,
        G21
    )
```

The normal operation is attempted first. If delivery is interrupted at the specified battery threshold, recovery is activated.

**G22 — Achieve:** Successful checkpoint handover requires the resource to be secured and the remaining task to be transferred.

**G24 — Achieve:** The desired state is that another robot has the remaining task and knows where the resource is positioned.

**G25 — Perform:** This goal coordinates required exception-handling actions rather than completing the original delivery objective.

**G26 — Perform:** The description explicitly requires the action of triggering an alert.

**G27 — Perform:** The description explicitly requires the action of sending a report.

### Nested recovery structure

```text
G17: Accomplish Resource Delivery
│
├── G18: Perform Normal Delivery
│
└── G21: Handle Delivery Battery Interruption
    │
    ├── G22: Complete Checkpoint Handover
    │
    └── G25: Escalate Checkpoint Return Failure
```

The runtime relationships are:

```text
G17:
FALLBACK(G18,G21)
```

```text
G21:
FALLBACK(G22,G25)
```

These relationships can be combined conceptually as:

```text
FALLBACK(
    G18,
    FALLBACK(
        G22,
        G25
    )
)
```

This combined expression is a conceptual expansion of the two hierarchical fallback relationships.

It should not be interpreted as making G25 a valid alternative way to achieve successful delivery. G25 provides failure escalation.

# 5. Task Definitions and Attributes

Tasks describe concrete operations performed by robots.

The task properties follow the source definitions:

- **Location:** A location explicitly mentioned in the mission, or `Not specified` where the description does not identify the execution location.
- **Number of Robots:** A numeric value or range.
- **Relation:** The task's connection to its parent goal.
- **Justification:** The requirement supporting the task and its attributes.

The source explicitly requires task locations and robot counts, with depth-first task numbering. Texto colado

## 5.1 Mission preparation tasks

| Name | Text | Relation | Location | Number of Robots | Justification |
|---|---|---|---|---|---|
| **AT1: Obtain Collection Estimates** | Obtain waiting-time estimates and robot travel-path information for the required storage locations. | AND | Not specified | 1 | The mission uses waiting time and path estimates to determine collection order. The execution location is not given; one planning agent is assumed. |
| **AT2: Assign Robots to Resource Jobs** | Assign available robots to collect-deliver jobs associated with the requested resources. | AND | Not specified | [1,N] | One robot can execute a mission, while multiple robots may be assigned when resources are required from different storages. The assignment location is not specified. |

### Additional considerations

AT1 gathers the information supporting collection planning. It does not imply that the robot must physically visit each storage to obtain the estimates.

AT2 represents assignment of participating robots. The actual assignment operation could be performed by a coordinating agent; the mission does not identify which entity performs assignment. Thus, its robot count is an operational modeling assumption rather than a stated requirement.

# 8. Parallel Multi-Robot Mission Execution

## 8.1 Parallelism identified in the description

The mission explicitly states that, when multiple items are requested from different storages, multiple robots can be assigned to parallel collect-deliver tasks.

This means the goal model must distinguish between:

1. **Sequential execution within an individual collect-deliver operation.**
2. **Potentially parallel execution across independent collect-deliver operations.**

For one assigned collect-deliver operation:

```text
Collection;Delivery
```

For two independent collect-deliver operations:

```text
CollectDeliver_JobA # CollectDeliver_JobB
```

The second structure represents optional concurrency.

## 8.2 Multi-robot example

Consider a mission that requires resources from two storage locations.

The requesting agent needs:

- Resources from Storage A.
- Resources from Storage B.

The system may assign Robot 1 and Robot 2.

The execution structure is:

```text
                 Transportation Mission
                          |
                          v
                    Preparation
                          |
                          v
                 Resource Assignments
                          |
               +----------+----------+
               |                     |
               v                     v
           Robot 1                Robot 2
               |                     |
               v                     v
        Collect Storage A      Collect Storage B
               |                     |
               v                     v
        Deliver Resources      Deliver Resources
               |                     |
               +----------+----------+
                          |
                          v
                 Mission Completed
```

The parallel execution can be represented conceptually by:

```text
(
    Collect_A;
    Deliver_A
)
#
(
    Collect_B;
    Deliver_B
)
```

Each operation is an instance of G5.

The notation above uses job-instance labels for explanation. These labels are not additional goal IDs in the formal hierarchy.

## 8.3 Why this is parallel execution rather than OR decomposition

An OR decomposition would imply that executing only one branch is sufficient to satisfy the parent.

That would be incorrect when the mission requires resources from both storages.

Both resource requirements must be fulfilled.

Therefore:

- The relationship between required resource deliveries is **AND**.
- The execution structure between independent jobs can be **parallel (`#`)**.

This distinction preserves the completeness of the transportation mission while supporting time-saving concurrent execution.

# 10. Formal Model Summary

The primary goal decomposition can be expressed as:

```text
G1 = G2;G5
```

Mission preparation:

```text
G2 = G3#G4
```

Mission fulfillment:

```text
G5 = G6;G17
```

Collection:

```text
G6 = G7;G8

G8 = FALLBACK(G9,G14)

G9 = G10;G11

G11 = G12;G13

G14 = G15;G16
```

Delivery:

```text
G17 = FALLBACK(G18,G21)

G18 = G19;G20

G21 = FALLBACK(G22,G25)

G22 = G23;G24

G25 = G26;G27
```

All non-leaf relationships in these expressions use AND decomposition.

The fallback relationships represent conditional recovery rather than ordinary alternatives.

Parallel execution applies when different assigned robots perform independent collect-deliver jobs.

### 10.1 Mission success criterion

The mission is successfully completed only when:

```text
AllRequestedResourcesDelivered = true
```

It is not sufficient that:

```text
CollectionRecoveryExecuted = true
```

or:

```text
DeliveryRecoveryExecuted = true
```

or:

```text
FailureAlertSent = true
```

Those conditions represent recovery or reporting outcomes, not completion of the original transportation objective.

### 10.2 Final modeling observations

The proposed hierarchy captures the main operational requirements: collection-order calculation, storage navigation, resource requesting, waiting for retrieval, repeated delivery runs, battery-dependent recovery, checkpoint handover, reassignment, exception reporting, and concurrent multi-robot execution.

Three limitations should be considered when converting the conceptual model into a strict machine-readable representation.

**First, terminal goal-to-task relationships:** The instructions require AND/OR decompositions with at least two children, while also permitting leaf goals and concrete task nodes. In this model, terminal goals have runtime annotation `-` and are realized by tasks. These realization links are labeled AND for traceability, but a single task does not constitute a formal multi-child AND decomposition.

**Second, battery recovery and mission continuity:** A successful reassignment does not itself achieve successful collection or delivery. Replacement robots must resume and complete the outstanding work. The mission requires continuity but does not specify the detailed resumption algorithm.

**Third, exception handling and mission success:** Failure escalation must be separated from the condition for successful mission completion. A report to the sector manager satisfies the exception-handling requirement, but the transportation mission remains incomplete if the resources have not been delivered.

## Conclusion

The resulting goal model consists of **27 goals and 14 tasks**, organized into a hierarchical structure with AND decomposition and three conditional fallback relationships.

The model preserves the mission's essential constraints:

- Collection precedes delivery for the same resources.
- Storage visits are ordered using waiting-time and travel-path estimates.
- Collection recovery is triggered at 10% battery.
- Delivery recovery is triggered at 30% battery.
- Checkpoint-return failure triggers alerting and reporting.
- Independent collect-deliver operations can execute in parallel using multiple robots.
- Successful mission completion requires delivery of all requested resources.

This provides a traceable goal-model specification that can be refined into a formal goal-modeling notation or robot mission-execution framework while keeping the original mission requirements distinct from implementation assumptions.
