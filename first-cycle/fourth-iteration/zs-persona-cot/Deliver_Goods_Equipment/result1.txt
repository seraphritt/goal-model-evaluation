# Goal Model: Multi-Robot Resource Collection and Delivery Mission

## 1. Source basis and modeling assumptions

A goal model is treated here as a hierarchical tree decomposing goals into sub-goals and tasks, using AND when all children are required and OR when one child is sufficient. The provided definitions also distinguish sequential execution, parallel execution, and fallback execution.

The mission describes a robot that collects required resources from storage and delivers them to a requesting agent at a specified location. It also defines collection ordering by waiting-time estimation plus travel path, resource-request messaging, repeated delivery runs, battery thresholds, checkpoint recovery, alert/report escalation, and possible parallel assignment of multiple robots.

Task locations and robot counts are modeled only from locations and quantities explicitly present or reasonably inferable from the mission text: storage places, specified location, recharging station, checkpoint, requesting agent, and sector manager. The number of robots is usually `1`, but becomes `[1,n]` when multiple robots are assigned to parallel collect-deliver tasks, because the description explicitly allows parallel robots when multiple items are required from different storages.

Notation used:

* `n`: number of parallel collect-deliver work units, determined by the number of required item/storage groupings.
* `k`: number of delivery runs required to transport all resources.
* `#`: parallel execution.
* `;`: sequential execution.
* `FALLBACK(x,y)`: execute `x`; if `x` fails, execute `y`.

## 5. Logical relationships

**G1 -> G2, G7, G12 [AND][`G2;((G7;G12)#...#(G7;G12))`]**
**Justification:** The full mission requires preparation, collection, and delivery. The collect-deliver branch may be instantiated in parallel when multiple items from different storages are required.

**G2 -> G3, G4, G5, G6 [AND][`G3;G4;G5;G6`]**
**Justification:** The mission plan is complete only when the system knows the request, storage locations, visit order, and robot assignment.

**G6 -> AT1 [AND][`AT1`]**
**Justification:** Assigning robot work units operationalizes the allocation goal.

**G7 -> G8, G11 [AND][`FALLBACK(G8,G11)`]**
**Justification:** Normal collection is attempted first. If collection cannot continue because battery reaches 10%, the recovery goal is executed.

**G8 -> G9, G10 [AND][`G9;G10`]**
**Justification:** The robot must first reach the storage place and then request/retrieve the resource.

**G9 -> AT2 [AND][`AT2`]**
**Justification:** Traveling to storage is the concrete task that satisfies the goal of reaching storage.

**G10 -> AT3, AT4 [AND][`AT3;AT4`]**
**Justification:** The robot must send the precise resource request and then wait until the resources are retrieved.

**G11 -> AT5, AT6 [AND][`AT5;AT6`]**
**Justification:** Collection-phase low battery requires returning to the recharging station and assigning the mission to another robot.

**G12 -> G13, G16 [AND][`FALLBACK(G13,G16)`]**
**Justification:** Normal delivery is attempted first. If delivery cannot continue because battery reaches 30%, delivery recovery is required.

**G13 -> G14, G15 [AND][`G14;G15`]**
**Justification:** The system must determine whether more runs are needed and then perform the required delivery runs.

**G14 -> AT7 [AND][`AT7`]**
**Justification:** Checking remaining delivery runs operationalizes the requirement to make as many runs as necessary.

**G15 -> AT8 [AND][`AT8`]**
**Justification:** Transporting resources to the specified location directly achieves the delivery objective.

**G16 -> G17, G18 [AND][`FALLBACK(G17,G18)`]**
**Justification:** The first recovery attempt is checkpoint handoff. If returning the resource to checkpoint fails, the fallback is alert/report escalation.

**G17 -> AT9, AT10, AT11 [AND][`AT9;AT10;AT11`]**
**Justification:** Delivery recovery requires placing the resource at checkpoint, assigning the remaining task, and ensuring the replacement robot knows the resource position.

**G18 -> AT12, AT13 [AND][`AT12;AT13`]**
**Justification:** If checkpoint return fails, both alert triggering and reporting to the sector manager are mandatory.
