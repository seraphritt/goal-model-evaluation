Below is a goal-model decomposition grounded in the pasted mission description. I treat **collection → delivery** as the main sequential flow because the mission says the delivery phase begins only once resources are retrieved, and I treat low-battery/failure behavior as **fallback** because it is triggered by explicit conditions and exceptions. Texto colado The model uses AND/OR decompositions according to the provided definitions: AND means all children are required, while OR means one child is sufficient. Texto colado

## 1. Modeling rationale

| Decision | Rationale |
|---|---|
| Main mission is an **Achieve Goal** | The mission aims to reach a final state: required resources collected from storage and delivered to the requesting agent at the specified location. |
| Collection and delivery are **sequential** | The description says “Once retrieved, the delivery phase begins,” so delivery depends on successful resource retrieval. Texto colado |
| Storage-order planning is a **Query/Achieve combination** | The robot must know where resources can be found and must define the order using waiting-time estimation plus path length. Texto colado |
| Low-battery behavior is modeled with **FALLBACK** | The description explicitly defines alternate behavior when battery drops to 10% in collection or 30% in delivery. Texto colado |
| Multiple robots are modeled as an **OR allocation strategy with possible parallel runtime** | The description says multiple robots can be assigned when multiple items are required from different storages, to reduce mission time. Texto colado |

# 5. Logical relationships

## Root mission

**G1 → G2, G10, G15 [AND] [G2;G10;G15]**  
- **Justification:** The mission must be planned, resources must be collected, and then resources must be delivered. The semicolon is used because delivery begins only after resource retrieval.

---

## Planning decomposition

**G2 → G3, G4, G5 [AND] [G3;G4;G5]**  
- **Justification:** Planning requires request information, storage identification, and execution strategy. These are complementary, not alternatives.

**G3 → AT1 [AND]**  
- **Justification:** Retrieving request data operationalizes the query for required resources, requesting agent, and specified location.

**G4 → AT2 [AND]**  
- **Justification:** Identifying storage places operationalizes the need to know where resources can be found.

---

## Execution strategy

**G5 → G6, G7, G8 [AND/OR] [G6;(G7 OR G8)]**  
- **Justification:** Ordering storage visits is always required, while robot allocation can be single-robot or multi-robot. The OR relation applies only to the allocation alternative.

**G6 → AT3 [AND]**  
- **Justification:** Computing the visit order implements the waiting-time-plus-path rule.

**G7 → AT4 [OR]**  
- **Justification:** One robot is sufficient when parallelization is not required.

**G8 → G9, G9 [AND] [G9#G9]**  
- **Justification:** Multiple collect-deliver units may run in parallel when multiple items come from different storages. The repeated G9 represents multiple instances of the same collect-deliver unit.

**G8 → AT5 [AND]**  
- **Justification:** Assigning multiple robots is the operational task that enables parallel execution.

---

## Collection phase

**G10 → G11, G14 [AND] [FALLBACK(G11,G14)]**  
- **Justification:** Normal collection is attempted first. If collection is interrupted by 10% battery, the robot returns to recharge and reassigns the mission.

**G11 → G12, G13 [AND] [G12;G13]**  
- **Justification:** The robot must first reach storage, then request and receive resources.

**G12 → AT6 [AND]**  
- **Justification:** Navigation to storage is the concrete action for reaching storage places.

**G13 → AT7, AT8 [AND] [AT7;AT8]**  
- **Justification:** The robot sends the precise resource request and then waits for retrieval.

**G14 → G14.1, G14.2 [AND] [G14.1;G14.2]**  
- **Justification:** In the collection low-battery case, both returning to the recharging station and assigning the mission to another robot are required.

**G14.1 → AT9 [AND]**  
- **Justification:** Returning to the recharging station is the operational action.

**G14.2 → AT10 [AND]**  
- **Justification:** Assigning the mission to another robot is required after the low-battery collection interruption.

---

## Delivery phase

**G15 → G16, G18 [AND] [FALLBACK(G16,G18)]**  
- **Justification:** Normal delivery is attempted first. If battery reaches 30% during delivery, checkpoint handover is required.

**G16 → G17 [AND]**  
- **Justification:** Delivery is performed through as many runs as necessary.

**G17 → AT11 [AND]**  
- **Justification:** The concrete task is to perform delivery runs to the specified location.

---

## Delivery low-battery handling

**G18 → G19, G22 [AND] [FALLBACK(G19,G22)]**  
- **Justification:** The robot first attempts to return the resource to a checkpoint. If that fails, alert/report behavior is triggered.

**G19 → G20, G21 [AND] [G20;G21]**  
- **Justification:** The resource must be placed at a checkpoint, and the remaining delivery must be assigned to another robot that knows the resource position.

**G20 → AT12 [AND]**  
- **Justification:** Returning the resource to a checkpoint is the required concrete action.

**G21 → AT13 [AND]**  
- **Justification:** The replacement robot must know the checkpoint/resource position.

**G22 → G23, G24 [AND] [G23;G24]**  
- **Justification:** If checkpoint return fails, both alert triggering and report sending are required.

**G23 → AT14 [AND]**  
- **Justification:** Triggering the alert operationalizes the failure response.

**G24 → AT15 [AND]**  
- **Justification:** Sending the report to the sector manager completes the required failure response.
