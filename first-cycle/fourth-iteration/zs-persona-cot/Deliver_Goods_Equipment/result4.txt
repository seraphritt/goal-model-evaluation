## Source-grounded interpretation

The mission is a **resource logistics mission**: when a request exists, a robot must collect required resources from storage and deliver them to the requesting agent at a specified location Texto colado. The mission has a required **collection phase**, where the robot visits storage places, orders visits using waiting time plus path estimation, sends a precise request message, and waits for resource retrieval Texto colado. After retrieval, the **delivery phase** begins and may require multiple runs to transport all resources Texto colado. Battery thresholds introduce exception behavior: 10% in collection causes recharge return and reassignment, while 30% in delivery causes checkpoint handover; checkpoint failure triggers alert/reporting Texto colado. Multiple robots may execute parallel collect-deliver tasks when multiple items from different storages are required Texto colado.

# Logical Relationships

- **G1 -> G2, G5, G10 [AND][sequential: `G2;G5;G10`]**  
  **Justification:** The mission must first know what is requested, then plan storage collection, then execute collection and delivery.

- **G2 -> G3, G4 [AND][parallel: `G3#G4`]**  
  **Justification:** Both resource information and requester/location information are required. They may be obtained in parallel because the description does not impose an order between them.

- **G5 -> G6, G7, G8, G9 [AND][sequential/parallel: `G6;(G7#G8);G9`]**  
  **Justification:** Storage places must be identified first. Waiting time and path estimation are both needed and may be computed in parallel. The final visit order depends on both estimates.

- **G10 -> G11, G19, G30 [AND][parallel/sequential: `(G11;G19)#G30`]**  
  **Justification:** For each collect-deliver flow, collection must precede delivery. In multi-storage cases, parallel collect-deliver task allocation can occur to reduce mission time.

- **G11 -> G12, G16 [AND][fallback: `FALLBACK(G12,G16)`]**  
  **Justification:** Normal collection is pursued first. If collection is interrupted by the 10% battery condition, the fallback is to recharge and reassign the mission.

- **G12 -> G13, G14, G15 [AND][sequential: `G13;G14;G15`]**  
  **Justification:** The robot must reach storage, send the request message, and then wait until resources are retrieved.

- **G16 -> G17, G18 [AND][sequential: `G17;G18`]**  
  **Justification:** The low-battery robot first returns to the recharging station, then the mission is assigned to another robot.

- **G19 -> G20, G23 [AND][fallback: `FALLBACK(G20,G23)`]**  
  **Justification:** Normal delivery is attempted first. If battery reaches 30% during delivery, the checkpoint handover behavior is triggered.

- **G20 -> G21, G22 [AND][sequential: `G21;G22`]**  
  **Justification:** A delivery run is made, and additional runs continue until all resources have been transported.

- **G23 -> G24, G27 [AND][fallback: `FALLBACK(G24,G27)`]**  
  **Justification:** The robot first attempts checkpoint handover. If returning the resource to a checkpoint fails, the fallback is alert/report escalation.

- **G24 -> G25, G26 [AND][sequential: `G25;G26`]**  
  **Justification:** The resource must first be placed at the checkpoint, then the remaining task is assigned to another robot with the resource position known.

- **G27 -> G28, G29 [AND][sequential: `G28;G29`]**  
  **Justification:** On checkpoint-return failure, the alert must be triggered and the report must be sent to the sector manager.

- **G30 -> G31, G32 [AND][sequential: `G31;G32`]**  
  **Justification:** The system must determine whether the multi-storage condition applies before assigning multiple robots to parallel collect-deliver tasks.
