**4. Logical Relationships – Detailed View**

- **G1 → G2, G3**  
  - **Relation:** `AND`  
  - **Runtime:** `;` (sequential)  
  - **Justification:** The overall mission requires first collecting and then delivering; both sub‑goals must be achieved in order.

- **G2 → G2.1, G2.2**  
  - **Relation:** `OR` (fallback) – `FALLBACK(G2.1, G2.2)`  
  - **Justification:** Normal collection (`G2.1`) is attempted first; if the robot’s battery drops below 10 % (`G2.2`) the fallback path is triggered.

- **G2.1 → AT1, AT2, AT3**  
  - **Relation:** `AND` (parallel execution `#`)  
  - **Justification:** The robot can carry out the three actions in parallel for different storage locations (handled by multiple robots).

- **G2.2 → AT6, AT9**  
  - **Relation:** `AND` (sequential `;`)  
  - **Justification:** The robot must first recharge before informing the system to re‑assign the mission.

- **G3 → G3.1, G3.2**  
  - **Relation:** `OR` (fallback) – `FALLBACK(G3.1, G3.2)`  
  - **Justification:** Delivery is attempted normally; if the battery falls below 30 % the robot must return to a checkpoint and re‑assign the task.

- **G3.1 → AT4, AT5**  
  - **Relation:** `AND` (sequential `;`)  
  - **Justification:** The robot moves to the destination and then delivers the resource.

- **G3.2 → AT7, AT9**  
  - **Relation:** `AND` (sequential `;`)  
  - **Justification:** The robot first returns the resource to the checkpoint and then re‑assigns the remaining job.

- **G4 → AT8**  
  - **Relation:** `AND`  
  - **Justification:** Sending an alert is a single action that occurs only when a failure to return to the checkpoint occurs.

- **G5, G6** are *Query* goals used to monitor battery levels during collection and delivery respectively. They are not directly linked to tasks but influence the fallback decisions in **G2** and **G3**.  

- **AT9** is used in both recovery paths (collection and delivery) to inform the system of the remaining task so that another robot can take over.

---

**5. Justification Summary**

1. **Goal Types**  
   - *Perform* goals are chosen for all executable actions (delivery, movement, recharge, alerting, reassignment). The mission explicitly requires concrete actions.  
   - *Query* goals (`G5`, `G6`) are used to obtain the battery level, which directly determines whether a fallback must be triggered.  
   - *Achieve* goals (`G1`, `G2`, `G3`) define the desired state transitions (resources collected, delivered).  

2. **Runtime Annotations**  
   - The top‑level mission is sequential (`;`) because collection precedes delivery.  
   - Fallbacks (`FALLBACK`) capture the battery‑critical contingencies.  
   - Parallel runtime (`#`) in **G2.1** reflects the ability for multiple robots to collect from different storages simultaneously.  

3. **Relations (AND / OR)**  
   - *AND* is used when all sub‑goals or sub‑tasks must be achieved (e.g., moving, requesting, and waiting are all needed for a successful collection).  
   - *OR* (fallback) is used when one of two paths is sufficient (normal operation vs. battery‑recovery).  

4. **Tasks**  
   - Each task is linked to the appropriate location and the number of robots required (most actions are performed by a single robot, but parallel execution across multiple robots is possible in the collection phase).  

5. **Alerting**  
   - The alert goal is a leaf perform task that is only triggered when the robot fails to return to the checkpoint. It ensures the sector manager is informed of a critical failure.  

This decomposition satisfies the mission description, captures all contingencies, and yields a clear, actionable goal model suitable for a multi‑robot system.
