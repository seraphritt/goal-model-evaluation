## Modeling rationale

The mission naturally decomposes into four main phases: understand the request, plan the storage/robot strategy, collect the resources, and deliver them. The strongest temporal constraint is sequential: the robot must know what is requested before planning, must plan before collecting, and must collect before delivering. Parallelism appears when multiple resources come from different storages, allowing multiple robots to execute collect-deliver tasks in parallel. Fallback appears in the two battery-contingency cases: low battery during collection transfers the mission to another robot, and low battery during delivery uses a checkpoint handoff, with alert/report escalation if checkpoint return fails.

I use **Achieve goals** for states that must become true, such as “resources delivered.” I use **Query goals** where the robot must obtain information, such as storage locations, waiting times, paths, and checkpoint resource position. I use **Perform goals** where the important issue is executing an action, such as sending messages, assigning another robot, triggering alerts, or reporting to the sector manager.

# Logical relationships

* **G1 -> G2, G3, G9, G16 [AND][`G2;G3;((G9;G16)#...(G9;G16))`]**
  **Justification:** The mission cannot be fulfilled without knowing the request, planning, collecting, and delivering. Parallel instances are used when multiple storages/resources allow multiple robots to reduce completion time.

* **G2 -> AT1, AT2 [AND][`AT1;AT2`]**
  **Justification:** The robot must first receive a request, then extract the requested resources, requesting agent, and specified location.

* **G3 -> G4, G5, G6 [AND][`G4;G5;G6`]**
  **Justification:** Planning requires source knowledge, ordering logic, and robot assignment.

* **G4 -> AT3, AT4 [AND][`AT3;AT4`]**
  **Justification:** The robot must know which storage places contain which required resources.

* **G5 -> AT5, AT6, AT7 [AND][`(AT5#AT6);AT7`]**
  **Justification:** Waiting time and path can be estimated independently and in parallel; then they are summed/sorted to define the order.

* **G6 -> G7, G8 [AND][`FALLBACK(G7,G8)`]**
  **Justification:** Parallel assignment is preferred when multiple items from different storages exist. If not feasible or not needed, a single assigned robot performs the mission. Because this is a fallback relation, the decomposition is treated as AND according to your definition.

* **G7 -> AT8, AT9 [AND][`AT8;AT9`]**
  **Justification:** Parallel work requires partitioning the required resources and assigning multiple robots.

* **G8 -> AT10, AT11 [AND][`AT10;AT11`]**
  **Justification:** Single-robot execution requires selecting one robot and assigning the complete mission to it.

* **G9 -> G10, G13 [AND][`FALLBACK(G10,G13)`]**
  **Justification:** Normal collection is attempted first. If battery reaches 10% during collection, the robot must go recharge and reassign the mission.

* **G10 -> G11, G12 [AND][`G11;G12`]**
