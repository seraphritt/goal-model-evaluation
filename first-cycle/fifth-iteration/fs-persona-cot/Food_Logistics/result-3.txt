## Modeling assumptions used

I treated the mission as two top-level capabilities: **food delivery** and **dirty dish retrieval**. The delivery capability is triggered by **kitchen delivery requests**, while dish retrieval can be triggered by **someone in the inpatient room calling a robot**.

For runtime annotations, I used **FALLBACK** where the description contains uncertainty about human availability, patient ability, nurse availability, door opening, or whether unassisted retrieval is possible. According to your definition, whenever `FALLBACK(exp1, exp2)` is used, the related child goals are marked as **AND**, because the second option is part of the recovery structure, not a classic OR choice.

## Step-by-step decomposition rationale

| Step | Interpretation                                                                                                                                                                                                    |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | The mission objective is not only to move food, but to complete an inpatient meal-service workflow: deliver meals and retrieve dirty dishes.                                                                      |
| 2    | Food delivery must start from a kitchen request, so the system first needs to query the order, meal identity, inpatient room, and assistance feasibility.                                                         |
| 3    | Because the robot can carry multiple meals, the model must include meal identification, indication of the correct meal, tracking, and wrong-meal alerting.                                                        |
| 4    | The transfer of food has two execution alternatives: tray fetching or table placement. I model tray fetching first and table placement as fallback because table placement requires a special manipulation skill. |
| 5    | Tray fetching depends on cooperation with an inpatient, companion, nurse, or another robot. Because those agents may be unavailable or unable, this is modeled as a nested fallback chain.                        |
| 6    | Door opening is also cooperative and uncertain, so it is modeled as fallback between human cooperation and robot cooperation.                                                                                     |
| 7    | Dirty dish retrieval is decomposed similarly to delivery: get request/context, reach the room, open the door, retrieve the dishes, and confirm removal.                                                           |
| 8    | Dish retrieval can be unassisted, two-robot, or robot-human; these are modeled as fallback alternatives because the feasibility may depend on the situation in the room.                                          |
