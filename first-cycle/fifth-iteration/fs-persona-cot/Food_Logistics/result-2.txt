## Modeling assumptions used

1. The food-delivery branch is modeled **per kitchen delivery request**, because the description says delivery is “order-by-order.”
2. The system-level mission has two main service capabilities: **deliver meals** and **retrieve dirty dishes**. These can be active in parallel in a multi-robot system.
3. Natural-language “or” alternatives are modeled as **FALLBACK** when the description implies runtime failure or uncertainty, such as unavailable humans, uncertain inpatient capability, unavailable manipulation skill, or need for another robot.
4. Locations are restricted to locations explicitly present in the mission text: `kitchen`, `inpatient_room`, `room_table`, `robot_tray`, and `room_door`.
5. “Another robot” means the carrying robot plus one teammate, so the number of robots is `2`.

# 1. Stepwise modeling rationale

| Step | Reflection                                                                                                                                                    | Modeling decision                                                                     |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 1    | The mission is not only about food delivery; dirty dishes must also be retrieved.                                                                             | Root goal decomposes into food delivery and dirty-dish retrieval.                     |
| 2    | Delivery is triggered by kitchen requests and handled order-by-order.                                                                                         | A per-request delivery goal is created.                                               |
| 3    | Some facts must be known before acting: order, room, patient, meal identity, patient ability, companion presence.                                             | Query goals are used for delivery request and retrieval feasibility.                  |
| 4    | The robot may carry multiple meals, creating risk of wrong retrieval.                                                                                         | The model includes meal indication, tracking, wrong-meal detection, and alerting.     |
| 5    | Delivery can be completed by table placement or tray fetching. Table placement requires manipulation skill; tray fetching depends on human/robot cooperation. | Delivery mode is modeled with fallback.                                               |
| 6    | Door opening may require a human or another robot.                                                                                                            | Door access is modeled with fallback between human cooperation and robot cooperation. |
| 7    | Dirty dish retrieval has three modes: unassisted, two robots, or robots plus human.                                                                           | Dish pickup is modeled as fallback from least cooperative to more cooperative modes.  |

# 5. Logical relationships

* **G1 -> G2, G23 [AND][parallel: `G2#G23`]**
  **Justification:** The system must support both meal delivery and dirty-dish retrieval. In a multi-robot setting, these services can occur concurrently for different rooms or requests.

* **G2 -> G3, G4, G5, G6, G7, G10 [AND][sequential/parallel: `G3;(G4#G5);G6;G7;G10`]**
  **Justification:** A delivery requires request information first; meal preparation and feasibility assessment can happen in parallel; then the robot travels, gains room access, and completes handoff.

* **G4 -> AT1, AT2 [AND][sequential: `AT1;AT2`]**
  **Justification:** The robot must first match meals to orders, then load them onto the tray.

* **G6 -> AT3, AT4 [AND][sequential: `AT3;AT4`]**
