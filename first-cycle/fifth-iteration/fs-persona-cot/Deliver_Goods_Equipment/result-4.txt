Below is a goal-model-oriented decomposition. I provide traceable design rationale, not private hidden chain-of-thought.

## Step-by-step design rationale

1. **Main mission objective**: the mission is successful when the requested resources are collected from storage and delivered to the requesting agent at the specified location.

2. **Planning must happen before execution**: the robot needs the resource specification, storage places, waiting-time estimate, path estimate, collection order, and robot allocation before acting.

3. **Collection precedes delivery**: the description explicitly says that once the resources are retrieved, the delivery phase begins.

4. **Parallelism appears when multiple items from different storages are required**: multiple robots can be assigned to parallel collect-deliver tasks to reduce total mission time.

5. **Battery handling is fallback behavior**: in collection, a 10% battery condition causes the robot to stop normal collection, go recharge, and reassign. In delivery, a 30% battery condition causes a checkpoint handover. If checkpoint return fails, alert/report is the fallback.

6. **Locations used only from the mission**: `storage_places`, `specified_location`, `recharging_station`, and `checkpoint`. Examples that instantiate storage/destination include `sterile_facilities`, `use_destinations`, `laundry`, and `storage_rooms_close_to_use`.

`N` means the number of assigned robots/resource groups determined during allocation.

# Logical Relationships

* **G1 -> G2, G6 [AND][sequential: `G2;G6`]**
  **Justification**: The mission must first be planned and then executed. Without planning, the robot does not know what to collect, where to collect it, or where to deliver it.

* **G2 -> G3, G4, G5 [AND][sequential: `G3;G4;G5`]**
  **Justification**: Request information, collection order, and robot allocation are all jointly necessary for a valid mission plan.

* **G3 -> AT1, AT2, AT3 [AND][sequential: `AT1;AT2;AT3`]**
  **Justification**: The robot needs the required resources, requesting agent, and specified location before execution.

* **G4 -> AT4, AT5, AT6, AT7 [AND][mixed: `AT4;(AT5#AT6);AT7`]**
  **Justification**: The robot first identifies storage places, then estimates waiting time and path in parallel, and finally sorts the route using the sum of both estimates.

* **G5 -> AT8, AT9 [AND][sequential: `AT8;AT9`]**
  **Justification**: The system must first decide how many robots are needed and then assign them to branches.

* **G6 -> G7, G23 [AND][parallel: `G7#G23`]**
  **Justification**: The primary branch and additional parallel branches can execute simultaneously when multiple items from different storages are required.

* **G7 -> G8, G14 [AND][sequential: `G8;G14`]**
  **Justification**: The collection phase must finish before delivery begins.

* **G8 -> G9, G13 [AND][fallback: `FALLBACK(G9,G13)`]**
  **Justification**: Standard collection is attempted first. If the collection robot reaches the 10% battery condition, fallback is the recharge-and-reassign behavior.

* **G9 -> G10, G11, G12 [AND][sequential: `G10;G11;G12`]**
  **Justification**: The robot must reach storage, request the resource, and then wait for retrieval.

* **G10 -> AT10 [AND]**
  **Justification**: Navigating to storage operationalizes the goal of reaching storage places.

* **G11 -> AT11 [AND]**
  **Justification**: Sending the precise message operationalizes the resource request goal.

* **G12 -> AT12 [AND]**
  **Justification**: Waiting for retrieval operationalizes the goal of obtaining retrieved resources.

* **G13 -> AT13, AT14 [AND][sequential: `AT13;AT14`]**
  **Justification**: In collection low-battery handling, the robot first returns to recharge and then the mission is assigned to another robot.

* **G14 -> G15, G18 [AND][fallback: `FALLBACK(G15,G18)`]**
  **Justification**: Standard delivery is attempted first. If the delivery robot reaches the 30% battery condition, checkpoint handover is required.

* **G15 -> G16, G17 [AND][sequential: `G16;G17`]**
  **Justification**: The system must know how many runs are necessary before performing the delivery runs.

* **G16 -> AT15 [AND]**
  **Justification**: Computing delivery runs operationalizes the “as many runs as necessary” requirement.

* **G17 -> AT16, AT17 [AND][sequential: `AT16;AT17`]**
  **Justification**: The robot must transport the resources and then hand them to the requesting agent.

* **G18 -> G19, G22 [AND][fallback: `FALLBACK(G19,G22)`]**
  **Justification**: The robot first attempts checkpoint return and reassignment. If return to checkpoint fails, alert/report behavior is triggered.

* **G19 -> G20, G21 [AND][sequential: `G20;G21`]**
  **Justification**: The resource must be placed at checkpoint before another robot can use that known position to continue.

* **G20 -> AT18 [AND]**
  **Justification**: Placing the resource at checkpoint directly operationalizes checkpoint return.

* **G21 -> AT19, AT20 [AND][sequential: `AT19;AT20`]**
  **Justification**: Another robot must be assigned and must know where the resource is positioned.

* **G22 -> AT21, AT22 [AND][sequential: `AT21;AT22`]**
  **Justification**: The failure response requires both alert triggering and report sending.

* **G23 -> G24, G25 [AND][sequential: `G24;G25`]**
  **Justification**: Parallel branches must first be launched and then synchronized.

* **G24 -> AT23 [AND]**
  **Justification**: Launching multiple collect-deliver branches operationalizes parallel execution.

* **G25 -> AT24 [AND]**
  **Justification**: Completion confirmation ensures all parallel robot branches are accounted for.
