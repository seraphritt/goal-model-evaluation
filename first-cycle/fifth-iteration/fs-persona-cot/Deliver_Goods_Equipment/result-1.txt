Below is a mission-oriented goal model decomposition. I use **AND** for jointly required parts of the mission, **sequential runtime `;`** where one phase must finish before the next begins, **parallel runtime `#`** where multiple robot work units can occur at the same time, and **`FALLBACK(...)`** for battery/failure contingencies.

I do **not** model the battery cases as OR alternatives, because they are not free choices. They are contingency behaviors executed only when the normal path cannot continue.

## Modeling assumptions and monitored variables

| Variable                 | Meaning                                                                                                                             |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| `required_resources`     | Resources requested by the requesting agent.                                                                                        |
| `requesting_agent`       | Agent that requested the resources.                                                                                                 |
| `specified_location`     | Location where resources must be delivered.                                                                                         |
| `storage_places`         | Storage places where required resources can be found.                                                                               |
| `waiting_time_estimates` | Estimated waiting time at each storage.                                                                                             |
| `path_cost_estimates`    | Estimated path/cost for the robot to reach each storage.                                                                            |
| `collection_order`       | Storage visiting order computed from waiting time + path cost.                                                                      |
| `battery_level`          | Battery percentage of the assigned robot.                                                                                           |
| `checkpoint`             | Place where a resource must be returned during delivery contingency.                                                                |
| `recharging_station`     | Place where a robot goes when battery is low in collection.                                                                         |
| `sector_manager`         | Recipient of failure report.                                                                                                        |
| `n`                      | Number of assigned robot work units. For one storage/resource batch, `n = 1`; for multiple items from different storages, `n >= 2`. |

# Step-by-step mission interpretation

1. **The mission starts from a request.**
   The phrase “When required” means the robot mission is triggered by a request. Before acting, the system must know the requested resources, the requesting agent, and the specified delivery location.

2. **The robot must plan collection before moving.**
   The collection order is not arbitrary. It is defined by the sum of estimated waiting time and path to be run by the robot. Therefore, the model needs a planning goal before execution.

3. **Collection and delivery are two major sequential phases.**
   The description explicitly says that after resources are retrieved, “the delivery phase begins.” So collection must occur before delivery for each robot work unit.

4. **Multiple robots introduce parallel work units.**
   When multiple items are required from different storages, several robots may execute collect-deliver assignments in parallel to reduce mission completion time.

5. **Battery behavior depends on the mission phase.**
   A low battery at **10% during collection** causes the robot to return to the recharging station and reassign the mission. A low battery at **30% during delivery** causes the robot to return the resource to a checkpoint and assign the remaining task to another robot.

6. **Failure to secure the resource at the checkpoint is a fallback failure-handling branch.**
   If the robot fails to return the resource to a checkpoint, an alert and report to the sector manager are mandatory.

# Logical Relationships

* **G1 -> G2, G3, G4 [AND][sequential: `G2;G3;G4`]**
  **Justification:** The mission must first obtain request data, then plan where/how to collect, and finally execute the transportation work.

* **G2 -> AT1, AT2 [AND][sequential: `AT1;AT2`]**
  **Justification:** The request must be received before the system can extract the required resources, requesting agent, and specified delivery location.

* **G3 -> AT3, AT4, AT5, AT6, AT7 [AND][mixed: `(AT3#AT4#AT5);AT6;AT7`]**
  **Justification:** Storage identification, waiting-time estimation, and path estimation can be prepared independently. The collection order must be computed after these values are available, and robot assignment follows the resulting plan.

* **G4 -> G5, G10 [AND][parallel over work units: `#ᵢ₌₁..ₙ(G5ᵢ;G10ᵢ)`]**
  **Justification:** Each robot work unit must collect before delivering. If multiple items are required from different storages, these work units can be assigned to multiple robots and executed in parallel.

* **G5 -> G6, G9 [AND][fallback: `FALLBACK(G6,G9)`]**
  **Justification:** Normal collection is the intended behavior. If battery falls to 10% during collection, the collection handoff behavior is required.

* **G6 -> G7, G8 [AND][sequential: `G7;G8`]**
  **Justification:** The robot must first reach the storage before it can request and receive resources.

* **G7 -> AT8, AT9 [AND][sequential: `AT8;AT9`]**
  **Justification:** The robot follows the computed collection order by selecting the next storage and then navigating to it.

* **G8 -> AT10, AT11, AT12 [AND][sequential: `AT10;AT11;AT12`]**
  **Justification:** The description says the robot sends a precise request, waits until retrieval, and only then proceeds to delivery with the retrieved resources.

* **G9 -> AT13, AT14 [AND][sequential: `AT13;AT14`]**
  **Justification:** At 10% battery during collection, the robot first returns to the recharging station and then transfers the mission to another robot.

* **G10 -> G11, G12 [AND][fallback: `FALLBACK(G11,G12)`]**
  **Justification:** Normal delivery is attempted first. If battery falls to 30% during delivery, the checkpoint contingency becomes necessary.

* **G11 -> AT15, AT16, AT17 [AND][sequential: `AT15;(AT16;AT17)`]**
  **Justification:** The robot must determine how many runs are necessary, then repeatedly travel to the specified location and hand over resources until all are delivered.

* **G12 -> G13, G14 [AND][fallback: `FALLBACK(G13,G14)`]**
  **Justification:** The robot first attempts to return the resource to a checkpoint. If that fails, the fallback is to trigger an alert and report the issue.

* **G13 -> AT18, AT19, AT20 [AND][sequential: `AT18;AT19;AT20`]**
  **Justification:** The resource must be placed at the checkpoint, the position must be known by the replacement robot, and the remaining delivery task must be reassigned.

* **G14 -> AT21, AT22 [AND][sequential: `AT21;AT22`]**
  **Justification:** Failure to return the resource to checkpoint requires both an alert and a report to the sector manager.
