## 1. Design rationale and assumptions

The mission contains two main service capabilities: food delivery from the kitchen to an inpatient room, and dirty dish retrieval from the room. The food delivery is triggered order-by-order by kitchen requests, while dish pickup can be triggered by someone in the room. 

The delivery method is uncertain because food can either be placed on the room table by a robot with special manipulation skill, or fetched from the robot tray by an inpatient, companion, nurse, or another robot. The model therefore uses fallback structures where uncertainty or unavailability may cause one delivery strategy to fail. 

The model also explicitly represents monitoring and safety duties: the robot must indicate which meal belongs to which inpatient, track when and where each meal was retrieved, and alert if a wrong meal is retrieved. 

Runtime annotations use `#` for parallel execution, `;` for sequential execution, and `FALLBACK(exp1, exp2)` for alternatives attempted only after failure.

# 5. Logical relationships

* **G1 -> G2, G22 [AND][parallel: `G2#G22`]**
  **Justification:** The system must support both food delivery and dirty dish retrieval. These are separate mission capabilities, so they can be modeled as parallel service branches.

* **G2 -> G3, G4, G5, G8, G11 [AND][sequential: `G3;G4;G5;G8;G11`]**
  **Justification:** A delivery request must be obtained before transport; transport must occur before room delivery; room access and transfer feasibility are needed before final meal transfer.

* **G3 -> AT1 [AND]**
  **Justification:** The query goal is operationalized by receiving the kitchen request.

* **G4 -> AT2, AT3 [AND][sequential: `AT2;AT3`]**
  **Justification:** The robot must load meals before transporting them to the inpatient room.

* **G5 -> G6, G7 [AND][fallback: `FALLBACK(G6,G7)`]**
  **Justification:** Door opening may involve either a human or another robot. Human assistance is attempted first; if unavailable, another robot is used.

* **G6 -> AT4 [AND]**
  **Justification:** Human-assisted door opening requires the robot to coordinate with the human at the room door.

* **G7 -> AT5 [AND]**
  **Justification:** Robot-assisted door opening requires cooperation between the delivery robot and another robot.

* **G8 -> G9, G10 [AND][parallel: `G9#G10`]**
  **Justification:** Patient/companion information and nurse/robot availability are independent information checks and can be performed in parallel.

* **G9 -> AT6 [AND]**
  **Justification:** The inpatient record and companion presence are the stated information sources for retrieval feasibility.

* **G10 -> AT7 [AND]**
  **Justification:** Nurse or robot assistance must be checked because both are possible cooperators for tray retrieval.

* **G11 -> G12, G21 [AND][fallback: `FALLBACK(G12,G21)`]**
  **Justification:** Tray retrieval is attempted first when feasible. If it fails due to uncertainty, inability, or unavailable cooperation, direct room-table placement is attempted using manipulation skill.

* **G12 -> G13, G18, G19, G20 [AND][sequential/parallel: `G13;(G18#G19#G20)`]**
  **Justification:** A retriever must first be selected. Once retrieval is underway, meal indication, wrong-meal monitoring, and tracking are all required and can happen concurrently.

* **G13 -> G14, G15, G16, G17 [AND][fallback: `FALLBACK(FALLBACK(FALLBACK(G14,G15),G16),G17)`]**
  **Justification:** The inpatient is the most direct retriever, but if unable, the system falls back to companion, nurse, and finally another robot.

* **G14 -> AT8 [OR]**
  **Justification:** Inpatient retrieval is one possible sufficient way to satisfy cooperative tray retrieval.

* **G15 -> AT9 [OR]**
  **Justification:** Companion retrieval is an alternative sufficient way when the inpatient cannot retrieve the meal.

* **G16 -> AT10 [OR]**
  **Justification:** Nurse retrieval is another sufficient alternative when patient or companion support is unavailable.

* **G17 -> AT11 [OR]**
  **Justification:** Another robot can retrieve the meal from the tray if human retrieval is unavailable.

* **G18 -> AT12 [AND]**
  **Justification:** The robot must indicate the correct meal because it may carry multiple meals.

* **G19 -> AT13 [AND]**
  **Justification:** The robot must alert if the wrong meal is retrieved.

* **G20 -> AT14 [AND]**
  **Justification:** The robot must track when and where each meal was retrieved.

* **G21 -> AT15 [AND]**
  **Justification:** Table delivery is performed by the concrete manipulation task of placing the food on the room table.

* **G22 -> G23, G24, G27 [AND][sequential: `G23;G24;G27`]**
  **Justification:** Dish retrieval requires a pickup request, room access, and execution of the retrieval mode.

* **G23 -> AT16 [AND]**
  **Justification:** Someone in the room can call the robot and signal whether they can open the door.

* **G24 -> G25, G26 [AND][fallback: `FALLBACK(G25,G26)`]**
  **Justification:** Door opening for pickup can use human help first, then robot help if human help fails or is unavailable.

* **G25 -> AT17 [AND]**
  **Justification:** Human-assisted pickup access requires coordinating with the human at the room door.

* **G26 -> AT18 [AND]**
  **Justification:** Robot-assisted pickup access requires cooperation with another robot at the room door.

* **G27 -> G28, G29, G30 [AND][fallback: `FALLBACK(FALLBACK(G28,G29),G30)`]**
  **Justification:** Dish retrieval can occur unassisted, with two robots, or with robots and a human. Fallback reflects escalating cooperation when simpler retrieval is not possible.

* **G28 -> AT19 [OR]**

* **G29 -> AT20 [OR]**
  **Justification:** Two-robot retrieval is an alternative sufficient mode.
