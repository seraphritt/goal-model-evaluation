Abaixo está um modelo completo derivado **somente da descrição fornecida**. A missão exige coleta em storages, ordenação por espera + caminho, solicitação e espera pelo recurso, entrega em uma localização especificada, tratamento de bateria baixa em dois limiares diferentes, checkpoint/alerta em falha e possível paralelização com múltiplos robôs. 

Uso `FALLBACK` apenas onde há uma alternativa explicitamente disparada pela impossibilidade de continuar o comportamento principal. Isso também segue a regra fornecida de que filhos envolvidos em `FALLBACK` possuem decomposição AND.  Não introduzo uma decomposição OR pura, porque a descrição não apresenta duas estratégias intercambiáveis em que qualquer uma, livremente, satisfaça o mesmo objetivo; os comportamentos alternativos existentes são contingências condicionais.

For robot counts, **1 robot** means one robot executes one instantiated workstream. Parallel execution is represented by several concurrent instances/workstreams rather than assuming that two robots jointly perform every physical operation.

```text
G1 Resource Request Fulfilled
│
├── AND → G2 Mission Prepared
│   ├── AND → G3 Mission Data Queried
│   ├── AND → G4 Storage Order Defined
│   └── AND → G5 Robot Allocation Defined
│
├── AND → G6 Resources Collected
│   ├── AND → AT1 Navigate to Storage
│   ├── AND → G7 Resource Request Completed
│   │   ├── AND → AT2 Send Resource Request
│   │   └── AND → AT3 Await Resource Retrieval
│   │
│   └── AND → G8 Collection Continuity Preserved
│       ├── AND → G9 Continue Collection
│       └── AND → G10 Collection Handover Completed
│           ├── AND → AT4 Return for Recharge
│           └── AND → AT5 Reassign Collection Mission
│
├── AND → G11 Resources Delivered
│   ├── AND → G12 Delivery Runs Completed
│   │   ├── AND → AT6 Deliver Current Load
│   │   └── AND → AT7 Repeat Delivery Runs
│   │
│   └── AND → G13 Delivery Continuity Preserved
│       ├── AND → G14 Continue Delivery
│       └── AND → G15 Delivery Handover Managed
│           ├── AND → G16 Checkpoint Handover Completed
│           │   ├── AND → AT8 Return Resource to Checkpoint
│           │   └── AND → AT9 Reassign Remaining Delivery
│           │
│           └── AND → G17 Checkpoint Failure Escalated
│               ├── AND → AT10 Trigger Alert
│               └── AND → AT11 Report to Sector Manager
│
└── AND, conditional → G18 Parallel Workstreams Completed
```

The apparent AND relationships inside the fallback branches are deliberate: the supplied definition explicitly says that when `FALLBACK(exp1, exp2)` is used, `exp1` and `exp2` are connected by an AND-decomposition even though the second executes only if the first fails.

# 4. Logical Relationships

### G1 → G2, G6, G11, G18 **[AND] [Sequential + Parallel]**

**Runtime**

`G2;((G6;G11)#G18)`

**Justification:** Mission preparation occurs first. Within the principal workstream, collection must occur before delivery because the description explicitly says that delivery begins once the resources have been retrieved. When multiple items from different storages exist, additional collect-deliver workstreams may simultaneously execute using multiple robots. 

---

### G2 → G3, G4, G5 **[AND] [Sequential]**

**Runtime**

`G3;G4;G5`

**Justification:** The mission first needs its relevant data, then needs a storage-ordering decision based on those data, followed by allocation of the work to robot workstreams.

---

### G6 → AT1, G7, G8 **[AND] [Sequential + Parallel]**

**Runtime**

`(AT1;G7)#G8`

**Justification:** The robot must first travel to storage and then request/retrieve the resources. Battery continuity is a cross-cutting concern that applies while these collection activities occur.

---

### G7 → AT2, AT3 **[AND] [Sequential]**

**Runtime**

`AT2;AT3`

**Justification:** The request message must be sent before the robot waits for the storage to retrieve the requested resources.

---

### G8 → G9, G10 **[AND] [FALLBACK]**

**Runtime**

`FALLBACK(G9,G10)`

**Justification:** The assigned robot normally continues collection. If continuing becomes impossible because the collection battery reaches the stated 10% condition, G10 is executed instead.

---

### G10 → AT4, AT5 **[AND] [Sequential]**

**Runtime**

`AT4;AT5`

**Justification:** The mission description states that the low-battery collection robot goes back to the recharging station **and** assigns the mission to another robot. Both are needed to complete the handover.

---

### G11 → G12, G13 **[AND] [Parallel]**

**Runtime**

`G12#G13`

**Justification:** Delivery runs are the operational activity, while delivery battery continuity must be maintained during those runs.

---

### G12 → AT6, AT7 **[AND] [Sequential]**

**Runtime**

`AT6;AT7`

**Justification:** A resource load is delivered first; if resources remain, the robot repeats the run as many times as necessary. `AT7` therefore represents a repetition/loop whose additional executions depend on remaining load.

---

### G13 → G14, G15 **[AND] [FALLBACK]**

**Runtime**

`FALLBACK(G14,G15)`

**Justification:** Delivery normally continues with the assigned robot. If the delivery battery reaches the 30% condition, the normal behavior can no longer continue and the handover procedure becomes the fallback.

---

### G15 → G16, G17 **[AND] [FALLBACK]**

**Runtime**

`FALLBACK(G16,G17)`

**Justification:** The first required response to low delivery battery is to return the resource to a checkpoint and transfer the task. Only **if returning the resource to a checkpoint fails** must an alert and manager report be generated.

This is one of the clearest explicit fallback relationships in the mission.

---

### G16 → AT8, AT9 **[AND] [Sequential]**

**Runtime**

`AT8;AT9`

**Justification:** The carried resource must first be positioned at the checkpoint; afterward the remaining mission can be transferred to another robot, which is informed of the resource position.

---

### G17 → AT10, AT11 **[AND] [Sequential]**

**Runtime**

`AT10;AT11`

**Justification:** Following checkpoint-return failure, both an alert and a report are mandatory. Alert generation is modeled first, followed by sending the report to the sector manager.

## Key modeling decisions

**1. Collection and delivery are sequential for an individual workstream.** The text explicitly says that, once resources have been retrieved, “the delivery phase begins,” so modeling them as parallel for the same resource would contradict the mission. 

**2. Parallelism applies across different workstreams.** When resources are distributed across different storages, several robots can execute separate collect-deliver workstreams concurrently. Therefore the root runtime separates intra-workstream sequence `(G6;G11)` from inter-workstream parallelism through `#`.

**3. The 10% and 30% behaviors are not equivalent.** At 10% during **collection**, the robot goes to the recharging station and transfers the mission. At 30% during **delivery**, it must first secure the resource at a checkpoint before transferring the remaining work.

**4. Checkpoint failure is a nested fallback.** `G15 = FALLBACK(G16,G17)` is preferable to OR because escalation is not a freely selectable alternative: it must happen specifically when checkpoint return fails.

**5. No pure OR decomposition is necessary.** The mission contains mandatory sequential/parallel activities and conditional fallbacks, rather than two equivalent alternative ways of satisfying a requirement. Adding OR branches just to use OR would introduce semantics that are not supported by the source.

**6. The examples of sterile medical equipment and clean linens are treated as examples of possible resources, not separate OR branches.** The description labels them as “Examples of goods/equipments,” so making them mandatory or exhaustive mission alternatives would over-model the source. 

This structure follows the requested output conventions for goal/task tables, summary, and explicit logical relationships.
