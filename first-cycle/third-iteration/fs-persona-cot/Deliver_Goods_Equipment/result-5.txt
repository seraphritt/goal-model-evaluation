Below is a structured goal model for the resource collection and delivery mission. I treat the collect-deliver branch as a **parameterized sub-tree**: if there are multiple items from different storages, the same collect-deliver lifecycle can be instantiated for multiple robots and executed in parallel, as the mission explicitly allows multiple robots to perform parallel collect-deliver tasks. Texto colado

## Modeling basis

The mission requires a robot to collect required resources from storage and deliver them to a requesting agent at a specified location. Texto colado Collection includes going to storage places, ordering visits by waiting-time plus path estimates, requesting resources, and waiting for retrieval. Texto colado Delivery starts after retrieval and may require as many runs as needed. Texto colado Battery exceptions create fallback behavior in both collection and delivery. Texto colado

The model uses AND/OR decomposition as required by the supplied definition of a goal model. Texto colado Fallbacks are used only where the description gives a normal behavior and an exception triggered by a threshold or failure, which matches the provided fallback definition. Texto colado

# 4. Logical relationships and justifications

## G1 → G2, G6, G7, G10 **[AND] [sequential + parameterized parallel]**

**Runtime:** `G2;G6;((G7;G10)_1 # ... # (G7;G10)_n)`

**Justification:**  
The mission requires knowing what is requested, assigning robot resources, collecting the resources, and delivering them. These are jointly necessary, so the decomposition is AND. The sequence is: determine mission parameters, assign robots, then execute collection and delivery. The expression `((G7;G10)_1 # ... # (G7;G10)_n)` represents parallel collect-deliver instances when multiple robots are assigned for different storages/items. This follows the statement that multiple robots can be assigned to parallel collect-deliver tasks to reduce mission time. Texto colado

---

## G2 → G3, G4, G5 **[AND] [sequential]**

**Runtime:** `(G3;G4);G5`

**Justification:**  
The system must know the requested resources and delivery location, identify where resources can be found, and then define the collection order. These are complementary pieces of mission knowledge, so AND is appropriate. The ordering goal depends on the storage and path/waiting-time information. Texto colado

---

## G5 → AT1, AT2 **[AND] [sequential]**

**Runtime:** `AT1;AT2`

**Justification:**  
The order cannot be selected until waiting time and robot path have been estimated. Therefore, AT1 must occur before AT2. Both are required to satisfy G5.

---

## G6 → AT3, AT4 **[AND] [sequential]**

**Runtime:** `AT3;AT4`

**Justification:**  
The mission first needs a robot set, then the collect-deliver task instances must be created. The task instances may be one or many depending on whether multiple items from different storages are required. This relation is AND because assignment is incomplete without both selecting robots and instantiating their tasks. Texto colado

---

## G7 → G8, G9 **[AND] [FALLBACK]**

**Runtime:** `FALLBACK(G8,G9)`

**Justification:**  
Normal collection is attempted first. If the assigned robot reaches 10% battery during collection, it returns to the recharging station and assigns the mission to another robot. This is a fallback because the second behavior is triggered by an exception threshold. Texto colado

---

## G8 → AT5, AT6, AT7 **[AND] [sequential]**

**Runtime:** `AT5;AT6;AT7`

**Justification:**  
The robot must first go to the storage, then send the precise resource request, and then wait for retrieval. Each step is required for normal collection, so the relation is AND. Texto colado

---

## G9 → AT8, AT9 **[AND] [sequential]**

**Runtime:** `AT8;AT9`

**Justification:**  
When collection-phase battery is low, the robot must go to the recharging station and assign the mission to another robot. Both actions are required; therefore, the decomposition is AND. Texto colado

---

## G10 → G11, G12 **[AND] [FALLBACK]**

**Runtime:** `FALLBACK(G11,G12)`

**Justification:**  
Normal delivery is attempted first. If the robot reaches 30% battery during delivery, the mission changes to the checkpoint handoff behavior. Because this is an exception triggered by a threshold, it is modeled as a fallback. Texto colado

---

## G11 → AT10, AT11 **[AND] [sequential]**

**Runtime:** `AT10;AT11`

**Justification:**  
The robot must perform the needed delivery runs and then the mission must reach the state where all resources are delivered. These are both required for normal delivery. Texto colado

---

## G12 → G13, G14 **[AND] [FALLBACK]**

**Runtime:** `FALLBACK(G13,G14)`

**Justification:**  
The first recovery attempt is to return the resource to a checkpoint and transfer the remaining task. If returning the resource to a checkpoint fails, an alert and report must be produced. This is a fallback because the alert/report behavior only occurs after failure of the checkpoint return. Texto colado

---

## G13 → AT12, AT13 **[AND] [sequential]**

**Runtime:** `AT12;AT13`

**Justification:**  
The resource must be placed at a checkpoint before another robot can continue using the known resource position. Thus, the tasks are sequential and both are necessary. Texto colado

---

## G14 → AT14, AT15 **[AND] [sequential]**

**Runtime:** `AT14;AT15`

**Justification:**  
When checkpoint return fails, the mission requires two actions: trigger an alert and send a report to the sector manager. Both are required, so the decomposition is AND. Texto colado

# 5. Notes on goods and equipment examples

The examples of sterile medical equipment and clean linens are treated as **possible resource types**, not separate mandatory goals, because the description presents them as examples of goods/equipment. Texto colado Therefore, they can instantiate the variable `required_resources` but do not change the structure of the goal model.
