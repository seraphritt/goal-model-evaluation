# Goal model: hospital meal delivery and dish retrieval

## 1. Step-by-step reasoning

**Step 1: Extract the mission's activities.** The description contains:
- Order-triggered meal delivery.
- Two handover modes: place the meal on the room table (needs a manipulation skill), or leave it on the tray for someone to fetch.
- Tray retrieval by an inpatient, a companion, a nurse, or another robot.
- Uncertain information about who can retrieve the meal.
- Multi-meal trays, with an indication of which meal belongs to whom.
- Tracking of when and where each meal was retrieved.
- An alert if a wrong meal is retrieved.
- Dirty-dish retrieval, done unassisted, with two robots, or with a robot and a human.
- Door opening with another robot or a human.
- Dish pickup calls from the room, where the caller can signal whether they can open the door.

**Step 2: Find the top-level split.** There are two independent service flows, delivery and dish retrieval. They have different triggers, so the root has two children.

**Step 3: Separate alternatives from obligations.** Wherever the text says "or" (handover mode, who retrieves, who opens the door, how dishes are collected), the children are alternatives, so the decomposition is OR. Wherever the text lists things that all must happen (get the meal, reach the room, hand it over, monitor retrieval), the decomposition is AND.

**Step 4: Choose the runtime operator.**
- `;` when there is a real precedence (you can't load before reaching the kitchen).
- `#` when activities are independent or must overlap (monitoring while the handover happens).
- `FALLBACK` for OR alternatives with a preference order, because uncertain information means an attempt can fail and the next option must be tried.

**Step 5: Handle uncertainty.** Who can retrieve the tray meal is uncertain, so it is modelled as a Query goal (G5) that produces beliefs with confidence. The retrieval alternatives are nested fallbacks, so a wrong prediction (for example, the inpatient is unable to fetch it) just triggers the next alternative.

**Step 6: Make tasks operational.** Each task has one location variable and a fixed team size. Alternatives that need different team sizes (robot alone vs. robot pair) are separate tasks under an OR. That keeps team allocation unambiguous, so no range `[n1,n2]` is needed.

**Step 7: Apply the tree constraints.**
- A tree cannot share nodes, so the door-opening pattern appears twice (G7 for delivery and G23 for dish pickup).
- Leaf goals are goals realised by exactly one task, so their runtime is `-`. A goal with several children gets a real operator.
- In the Relation column, non-leaf nodes show their own decomposition. Leaf nodes show `AND (single task)`, a degenerate decomposition.

**Assumptions to flag:**
1. Nurse availability (AT6) is not explicitly said to come from the record, so I assume a staff or nurse-call system.
2. Dish pickup is triggered either by a schedule after meals or by a call from the room. The description states the need and the call, and the schedule is my inference.
3. Timeouts define the failure of a cooperative attempt and trigger the fallback.
4. The preference orders are design choices and can be reordered at runtime using G5's confidence values.
5. Robots assigned to AT11, AT15's helper, and AT25 must have the manipulation skill.

## 2. Tree overview

```
G1 Provide inpatient food service                     [#]  AND
├─ G2 Deliver meal order      [G3 ; G4 ; (G5 # G6) ; G8]   AND
│   ├─ G3 Obtain order details (Query)  ── AT1
│   ├─ G4 Collect meal at kitchen  [;]  ── AT2, AT3
│   ├─ G5 Assess retrieval capabilities (Query) [#] ── AT4, AT5, AT6
│   ├─ G6 Reach inpatient room  [;]
│   │    ├─ AT7
│   │    ├─ G7 Open room door  [FALLBACK(AT8, AT9)]  OR
│   │    └─ AT10
│   └─ G8 Hand over meal  [FALLBACK(G9, G10)]  OR
│        ├─ G9 Place meal on table ── AT11
│        └─ G10 Hand over via tray  [#]  AND
│             ├─ G11 Have meal retrieved [FALLBACK(G12, G16)]  OR
│             │    ├─ G12 Human retrieves [FALLBACK(G13, FALLBACK(G14, G15))]  OR
│             │    │    ├─ G13 Inpatient ── AT12
│             │    │    ├─ G14 Companion ── AT13
│             │    │    └─ G15 Nurse ── AT14
│             │    └─ G16 Another robot ── AT15
│             └─ G17 Monitor meal retrieval [AT16 ; (G18 # G19)]  AND
│                  ├─ AT16
│                  ├─ G18 Track retrieval ── AT17
│                  └─ G19 Alert wrong meal ── AT18
└─ G20 Retrieve dirty dishes   [G21 ; G22 ; G24 ; G28]   AND
    ├─ G21 Identify pickup request (Query) [#] OR ── AT19, AT20
    ├─ G22 Reach room for pickup [;]
    │    ├─ AT21
    │    ├─ G23 Open room door [FALLBACK(AT22, AT23)]  OR
    │    └─ AT24
    ├─ G24 Collect dirty dishes [FALLBACK(G25, FALLBACK(G26, G27))]  OR
    │    ├─ G25 Unassisted ── AT25
    │    ├─ G26 With human ── AT26
    │    └─ G27 With two robots ── AT27
    └─ G28 Return dishes to kitchen [;] ── AT28, AT29
```

## 6. Logical relationships

- **G1 -> G2, G20 [AND][(parallel) #]**
  - **Justification**: The service needs both delivery and dish retrieval to be complete (AND). They have independent triggers (kitchen requests vs. room calls or schedule), so they run in parallel.

- **G2 -> G3, G4, G5, G6, G8 [AND][G3 ; G4 ; (G5 # G6) ; G8]**
  - **Justification**: Every step is needed for one order (AND). The order details come first and the meal is then collected. Capability assessment is information-only and overlaps with the trip to the room. The handover comes last, when both the answer and the robot are ready.

- **G3 -> AT1 [AND]**
  - **Justification**: A single task realises the query. The kitchen request is the input of the order-by-order process.

- **G4 -> AT2, AT3 [AND][(sequential) ;]**
  - **Justification**: Go to the kitchen, then load. Both are required.

- **G5 -> AT4, AT5, AT6 [AND][(parallel) #]**
  - **Justification**: The record, the companion status, and the nurse status are independent lookups, and together they support ranking the retrieval options.

- **G6 -> AT7, G7, AT10 [AND][(sequential) ;]**
  - **Justification**: Reach the door, get it open, then enter. Each step depends on the previous one.

- **G7 -> AT8, AT9 [OR][FALLBACK(AT8, AT9)]**
  - **Justification**: The description gives a human or another robot as alternatives (OR). The human is asked first because it needs no second robot, and the robot helper is used if no human responds.

- **G8 -> G9, G10 [OR][FALLBACK(G9, G10)]**
  - **Justification**: The two delivery modes are alternatives (OR). Table placement is first because it is independent of uncertain human availability, and tray handover is the fallback when the skill is missing or fails.

- **G9 -> AT11 [AND]**
  - **Justification**: One manipulation task realises the table placement.

- **G10 -> G11, G17 [AND][(parallel) #]**
  - **Justification**: Retrieval and monitoring must both hold (AND). They run in parallel because the monitor must observe the retrieval as it happens.

- **G11 -> G12, G16 [OR][FALLBACK(G12, G16)]**
  - **Justification**: Human or robot retrieval are alternatives (OR). Humans are tried first, and another robot is the last resort.

- **G12 -> G13, G14, G15 [OR][FALLBACK(G13, FALLBACK(G14, G15))]**
  - **Justification**: Inpatient, companion, and nurse are alternatives (OR), ordered by increasing burden on others. The nested FALLBACK copes with uncertainty in who can actually retrieve the meal.

- **G13 -> AT12, G14 -> AT13, G15 -> AT14, G16 -> AT15 [AND]**
  - **Justification**: Each retrieval mode is realised by exactly one task that presents the tray and indicates the meal, or in G16 makes the transfer with a second robot.

- **G17 -> AT16, G18, G19 [AND][AT16 ; (G18 # G19)]**
  - **Justification**: Detection and identification must come before the other two. Tracking and alerting are then independent, and all three are required.

- **G18 -> AT17, G19 -> AT18 [AND]**
  - **Justification**: Each monitoring goal is a single task: the logging task and the alert task.

- **G20 -> G21, G22, G24, G28 [AND][G21 ; G22 ; G24 ; G28]**
  - **Justification**: Pickup is a chain (identify, enter, collect, return) where every link is needed.

- **G21 -> AT19, AT20 [OR][(parallel) #]**
  - **Justification**: The pickup can be triggered by either the schedule or a room call. Both channels are monitored at the same time and one is enough. The call also carries the door-opening signal.

- **G22 -> AT21, G23, AT24 [AND][(sequential) ;]**
  - **Justification**: Reach the door, get it open, enter. All are required, in order.

- **G23 -> AT22, AT23 [OR][FALLBACK(AT22, AT23)]**
  - **Justification**: Human or robot opens the door (OR). The caller's signal makes the human option first when they can open. Otherwise, or on timeout, a helper robot is used.

- **G24 -> G25, G26, G27 [OR][FALLBACK(G25, FALLBACK(G26, G27))]**
  - **Justification**: The description gives three collection modes (OR). The unassisted mode has no dependencies, the human-assisted mode uses no second robot, and the two-robot mode consumes the most fleet resources.

- **G25 -> AT25, G26 -> AT26, G27 -> AT27 [AND]**
  - **Justification**: Each collection mode is a single task with a fixed team size: one robot, one robot plus a human, or two robots.

- **G28 -> AT28, AT29 [AND][(sequential) ;]**
  - **Justification**: Reach the dish-return area, then unload.

## 7. Reflections and open design points

- **Preference orders are policy, not fact.** The description gives the alternatives but not their priority. I chose the orders to minimise dependence on uncertain information and to spare scarce resources (nurse, second robot). Because G5 outputs confidence values, the fallback order could be reordered at runtime, for example nurse first if the inpatient and companion are unlikely to be able to retrieve the meal.
- **Timeouts are essential.** Every cooperative attempt (AT8, AT12–AT15, AT22, AT26) needs a timeout to trigger its fallback.
- **Multi-meal trays** are supported by AT3's slot registration and by G2 being instantiated per order. Task allocation across instances (batching orders by route) is a scheduling concern outside this goal model.
- **Duplicated door pattern.** G7 and G23 are the same pattern, duplicated only because a tree cannot share nodes. Their only difference is that G23 can use the caller's door-opening signal from AT20.
- **Monitoring scope.** G17 sits inside the tray branch (G10) on purpose. If it were placed above G8, the AND relation would make table delivery fail, since nothing is ever "retrieved from the tray" in that mode.
