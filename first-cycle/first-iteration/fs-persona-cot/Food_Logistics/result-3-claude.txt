# Goal model: hospital food delivery and dish retrieval

## 1. Step-by-step reasoning

**Step 1: Identify the system objective (root).** The mission has two flows: delivering meals from the kitchen to inpatient rooms, and retrieving dirty dishes from those rooms. They start from different events (a kitchen delivery request vs. a dish pickup call or post-meal need) and don't need to wait for each other. So the root is an **AND** of two goals executed in **parallel (#)**.

**Step 2: Decompose delivery, one order at a time.** The description says delivery is "order-by-order". The natural sequence is: load the meal, find out who can help retrieve it, get into the room, hand over the meal, leave. The order is strict, since you can't enter the room before loading and can't hand over before entering, so I chose **sequential (;)** with **AND**. Because the robot can carry several meals, this goal is instantiated once per kitchen request.

**Step 3: Model the uncertain information as a Query goal.** Whether the inpatient, a companion, or a nurse can retrieve food from the tray comes from the inpatient record and room presence, and this information is uncertain. It is a pure information-gathering goal (Query). The two sources are independent, so they run in **parallel**. The result is a belief with a confidence level, not a certainty. This is why the tray-retrieval branch needs fallbacks.

**Step 4: Model door opening as a fallback between cooperation modes.** "Opening the room door can involve cooperation with another robot or a human", so there are two alternatives (**OR**). I chose FALLBACK, human first. A human is usually in or near the room and costs no fleet resources, while the robot option consumes a second robot. If the person cannot open the door (for example, the caller signals this during a dish pickup), the robot option is used directly.

**Step 5: Model handover as a fallback between table delivery and tray retrieval.** Table delivery needs a special manipulation skill but no cooperation. Tray retrieval needs cooperation from someone whose availability is uncertain. The two are alternatives (**OR**). I chose FALLBACK(table, tray) because table delivery is autonomous and not affected by the uncertainty, so it is preferred whenever the robot has the skill. Tray retrieval is the fallback for robots without it.

**Step 6: Decompose tray retrieval.** The robot moves to the bedside, indicates which meal is to be retrieved (it may carry several), and then supervises retrieval. Those steps are sequential. During retrieval, tracking (when and where) and wrong-meal alerts must be active at the same time as the retrieval, so they run in **parallel** with the retrieval goal. The possible retrievers are inpatient, companion, nurse, or another robot (**OR**, as a nested FALLBACK ordered from the recipient to the scarcest resource).

**Step 7: Decompose dish retrieval.** The flow is: identify the pickup need, access the room, pick up the dishes, return them to the kitchen. Room access is the same problem as in delivery, so the model **reuses G5** as a shared node. Dish pickup can be unassisted, with another robot, or with a human plus robots, so it is a FALLBACK from cheapest to most demanding.

**Step 8: Reflection and checks.**
- Every goal has a runtime annotation and an AND/OR decomposition. A goal with a single task child and no sub-goals is treated as a **leaf goal** and gets "-". Goals with several children get an operator.
- IDs follow depth-first order (G1…G26, AT1…AT29). G5 appears under both G2 and G20 as a shared reference, so IDs stay unique.
- Uncertainty is handled twice: by the Query goal (G4) and by the fallbacks with timeouts.
- **Assumptions:** the description doesn't mention a robot opening a door alone, so I did not model an unassisted door opening. I assume the door stays open while the robot enters and leaves.

## 5. Logical relationships

**G1 -> G2, G20 [AND][parallel]**
- **Justification**: Both flows are required, and they have independent triggers (kitchen request vs. dish call or post-meal need), so they run concurrently.

**G2 -> G3, G4, G5, G9, AT20 [AND][sequential]**
- **Justification**: Every step is needed for a delivery, and each depends on the previous one: load, assess who can help, enter, hand over, leave. G4 must precede G9 because its beliefs drive the choice of retriever.

**G3 -> AT1 [AND]**
- **Justification**: Loading is a single operation in the kitchen.

**G4 -> AT2, AT3 [AND][parallel]**
- **Justification**: Both the inpatient record and the room presence are needed for a complete belief. They are independent sources and can be read concurrently.

**G5 -> AT4, G6, AT9 [AND][sequential]**
- **Justification**: Access requires arriving at the door, getting it opened, and entering, in that order.

**G6 -> G7, G8 [OR][FALLBACK(G7, G8)]**
- **Justification**: The description says door opening involves either a human or another robot. One is enough. Human first because it costs less. Robot help is used if the timeout in AT6 expires or if the caller has signaled they cannot open the door.

**G7 -> AT5, AT6 [AND][sequential]**
- **Justification**: The robot announces itself, then waits.

**G8 -> AT7, AT8 [AND][sequential]**
- **Justification**: The assistant must be called before it can open the door.

**G9 -> G10, G11 [OR][FALLBACK(G10, G11)]**
- **Justification**: The two handover modes are alternatives from the description. Table delivery is preferred because it doesn't depend on uncertain human availability.

**G10 -> AT10 [AND]**
- **Justification**: A single manipulation action needing the special skill.

**G11 -> AT11, G12, G13 [AND][sequential]**
- **Justification**: The robot must position, indicate the meal, and then supervise retrieval, in that order.

**G12 -> AT12 [AND]**
- **Justification**: A single indication action.

**G13 -> G14, G19 [AND][parallel]**
- **Justification**: Retrieval and monitoring are both required, and monitoring must be active while retrieval takes place.

**G14 -> G15, G16, G17, G18 [OR][FALLBACK(G15, FALLBACK(G16, FALLBACK(G17, G18)))]**
- **Justification**: One retriever suffices. FALLBACK is binary, so it is nested for four options. The order goes from the recipient to the scarcest resource. The uncertainty in the information is handled by timeouts.

**G15 -> AT13, G16 -> AT14, G17 -> AT15 [AND each]**
- **Justification**: Each is a single request-and-wait action for one type of retriever.

**G18 -> AT16, AT17 [AND][sequential]**
- **Justification**: The assisting robot must be called before the transfer.

**G19 -> AT18, AT19 [AND][parallel]**
- **Justification**: Both are required and both use the same sensing while the person takes the meal.

**G20 -> G21, G5, G22, G26 [AND][sequential]**
- **Justification**: The robot must know which room to visit, get inside (reusing G5), pick up the dishes, and return them.

**G21 -> AT21, AT22 [OR][parallel]**
- **Justification**: A call or a routine check is enough to trigger the pickup, and both triggers can be monitored at the same time.

**G22 -> G23, G24, G25 [OR][FALLBACK(G23, FALLBACK(G24, G25))]**
- **Justification**: The three pickup modes from the description are alternatives. They are ordered from cheapest to most demanding.

**G23 -> AT23 [AND]**
- **Justification**: A single unassisted manipulation action.

**G24 -> AT24, AT25 [AND][sequential]**
- **Justification**: The assistant must be called before the two-robot transfer.

**G25 -> AT26, AT27 [AND][sequential]**
- **Justification**: The robot must request human help before confirming the dishes are on the tray.

**G26 -> AT28, AT29 [AND][sequential]**
- **Justification**: The robot must travel to the kitchen before unloading.
