## Modeling rationale (concise design trace)

1. **Main mission objective**: move lab samples from **patient floors** to the **laboratory** while preserving security, traceability, and timing compliance.
2. **Main phases inferred from the description**:
   - Sample is identified and registered before delivery.
   - Nurse delivery request is accepted by the robot system.
   - Sample is transported in a secure locked drawer.
   - Drawer opening is restricted to authorized actors and valid locations.
   - At the laboratory, the sample is picked either by a robotic arm or by laboratory personnel.
   - Robotic arm, if used, scans, sorts, and loads samples into analysis-machine entry modules.
   - Pickup location/time and collection-to-delivery time are securely logged/tracked.
3. **Alternative handling**: “sample can be picked by a robotic arm or laboratory personnel” is modeled as an **OR decomposition**, not as fallback, because the description gives no failure-triggered priority order.
4. **No FALLBACK relation is used**: the description does not explicitly state a normal behavior followed by an exception/failure alternative.
5. **Parallelism**: traceability and timing monitoring can run in parallel with transport and laboratory handling, because logging/tracking activities observe events while the physical mission proceeds.

## FALLBACK analysis

No `FALLBACK(...)` relationship was modeled. The only explicit alternative is **robotic arm pickup vs laboratory personnel pickup**, but the description does not say that one is tried first and the other is used only after failure. Therefore, this is modeled as an **OR decomposition**, not a fallback.
