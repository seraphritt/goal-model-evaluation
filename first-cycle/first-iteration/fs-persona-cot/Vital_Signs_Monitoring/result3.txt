Below is a **goal-model decomposition** for the mission. I treat the mission as a **periodic multi-robot hospital monitoring mission**, where robots must complete patient vital-sign checks every two hours, prioritize high-risk patients, handle clinical/safety contingencies, and escalate if the fleet cannot satisfy the deadline.

## Modeling rationale

The mission description implies four main concerns:

1. **Mission-level achievement**: all occupied rooms/patients must be checked every two hours.
2. **Planning and allocation**: robots need the list of occupied rooms, patient conditions, priorities, battery constraints, and workload feasibility.
3. **Patient-room workflow**: before entering, the robot checks availability and battery; inside, it identifies the patient, communicates the procedure, collects required vital signs, handles failures, and marks completion.
4. **Safety and escalation**: infectious-disease rooms require sterilization, patient contact requires actuator disinfection, battery failures require recharge/reassignment, and impossible missions require manager alerting.

I use **AND** where every child is necessary, and **OR/FALLBACK** where the description gives alternatives or contingency behavior.

# Logical Relationships and Justifications

## Mission-level relationships

**G1 -> G2, G39 [OR][FALLBACK(G2,G39)]**

* **Justification**: The preferred outcome is completing the mission. However, if no robot combination can complete the mission, the system must alert the responsible manager. Therefore, escalation is a fallback resolution.

**G2 -> G3, G10, G38 [AND][sequential]**

* **Justification**: The mission requires planning first, then execution, then closure and scheduling of the next two-hour cycle.

---

## Planning relationships

**G3 -> G4, G5, G6, G7 [AND][sequential]**

* **Justification**: The mission plan requires knowing occupied rooms, patient conditions, high-risk priority, and feasible robot allocation. Missing any one of these prevents safe execution.

**G4 -> AT1, AT2 [AND][sequential]**

* **Justification**: Visiting every occupied room requires the occupied room list, and identifying patients in rooms with multiple beds requires bed-patient mapping.

**G5 -> AT3, AT4 [AND][sequential]**

* **Justification**: The system must first retrieve patient condition flags and then derive the vital signs required for each patient.

**G6 -> AT5, AT6 [AND][sequential]**

* **Justification**: High-risk patients must be identified/ranked, then scheduled within the first 15 minutes.

**G7 -> G8, G9 [OR][FALLBACK(G8,G9)]**

* **Justification**: Initial robot assignment is attempted first. If it cannot satisfy the time requirement, additional robots are assigned and tasks are redistributed.

**G8 -> AT7, AT8 [AND][sequential]**

* **Justification**: Routes must be computed before tasks are assigned to robots.

**G9 -> AT9, AT10, AT11 [AND][sequential]**

* **Justification**: The system must detect infeasibility, allocate extra robots, and then reassign pending tasks.

---

## Execution relationships

**G10 -> G11, G12 [AND][parallel]**

* **Justification**: High-risk deadline enforcement must occur while patient-room workflows are being executed. Parallelism is appropriate because multiple robots can work in different rooms simultaneously.

**G11 -> AT12, AT13 [AND][parallel]**

* **Justification**: The system must monitor the 15-minute deadline while dispatching robots to high-risk rooms.

**G12 -> G13, G18, G21, G34, G37 [AND][sequential]**

* **Justification**: The patient-room workflow is ordered: check pre-entry conditions, identify the patient, perform the procedure, sanitize if required, and then mark completion/proceed.

---

## Pre-entry relationships

**G13 -> G14, G16 [AND][sequential]**

* **Justification**: Before entering the room, the robot must confirm both patient availability and battery sufficiency.

**G14 -> G15, AT16 [OR][FALLBACK(G15,AT16)]**

* **Justification**: If the patient is available, the workflow proceeds. If the patient is unavailable, the robot must return after five minutes.

**G15 -> AT14, AT15 [AND][sequential]**

* **Justification**: The robot asks/checks availability and then reads or confirms the availability result.

**G16 -> G17, G18B [OR][FALLBACK(G17,G18B)]**

* **Justification**: If the current robot has enough battery, it proceeds. If not, the robot recharges and the task is reassigned.

**G17 -> AT17 [AND]**

* **Justification**: Battery sufficiency requires estimating whether current battery can cover all in-room tasks.

**G18B -> AT18, AT19 [AND][sequential]**

* **Justification**: Insufficient battery requires both robot recharge and task reassignment.

---

**G19 -> AT20 [AND]**

**G20 -> AT21 [AND]**

* **Justification**: Barcode scanning is a concrete query action.
