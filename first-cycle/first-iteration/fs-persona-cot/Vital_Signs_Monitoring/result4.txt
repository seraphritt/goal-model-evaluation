Below is a goal-model decomposition of the mission in a Multi-Robot Systems context. I treat **goals** as intentional objectives and **tasks** as concrete executable actions assignable to one or more robots.

## Modeling rationale

The mission has five main concerns:

1. **Periodicity**: vital signs must be checked every two hours.
2. **Coverage**: every occupied room and every relevant patient must be checked.
3. **Preconditions before entry**: patient availability and robot battery must be verified before entering.
4. **Patient-specific vital signs**: the signs to collect depend on the patient condition.
5. **Exception handling**: unavailable patients, low battery, failed measurements, non-response, infection-control, and mission infeasibility must be handled.

Because the mission involves ordered steps, the root execution is mostly **sequential**. Some parts may execute in **parallel**, especially worklist preparation, robot-status checks, and the allocation of multiple robots. Some parts require **fallback**, because the mission explicitly defines alternative behavior when something fails, such as patient unavailable, insufficient battery, failed vital-sign collection, or no feasible robot combination.

# 4. Logical Relationships

## Root mission structure

**G1 -> G2, G3, G7, G11 [AND][sequential `;`]**

* **Justification**: The mission must first be triggered every two hours, then the system must know which patients and robots are involved, then robots must be assigned, and finally the patient-checking mission must be executed.

---

## Mission cycle

**G2 -> AT1 [AND]**

* **Justification**: Starting the two-hour cycle is mandatory because the mission is periodic.

---

## Worklist construction

**G3 -> G4, G5, G6 [AND][parallel `#`]**

* **Justification**: The mission needs occupied rooms, patient conditions, and robot availability. These pieces of information are all necessary but can be queried in parallel.

**G4 -> AT2 [AND]**

* **Justification**: Occupied rooms must be retrieved so the robot knows where to go.

**G5 -> AT3 [AND]**

* **Justification**: Patient identity, bed assignment, condition, and risk status are required to determine the correct patient and required signs.

**G6 -> AT4 [AND]**

* **Justification**: Robot battery, availability, and capabilities are required before assigning duties.

---

## Robot allocation and fallback

**G7 -> G8, G9, G10 [OR][FALLBACK(G8,FALLBACK(G9,G10))]**

* **Justification**: The mission first tries the assigned robot. If that is not enough, helper robots may be assigned. If no combination of robots works, the manager must be alerted.

**G8 -> AT5 [OR]**

* **Justification**: Assigning the primary robot is sufficient if it can complete the mission.

**G9 -> AT6, AT7 [AND][sequential `;`]**

* **Justification**: The system must first compute a feasible multi-robot plan and then assign helper robots.

**G10 -> AT8 [OR]**

* **Justification**: Alerting the site manager is the required fallback when the mission cannot be completed.

---

## Patient-checking execution

**G11 -> G12, G13 [AND][sequential `;`]**

* **Justification**: High-risk patients must be prioritized first, then the scheduled patient checks are executed.

**G12 -> AT9 [AND]**

* **Justification**: The schedule must place high-risk patients in the first 15 minutes.

**G13 -> G14, G21, G24, G25, G26, G30, G34, G38, G42, G46 [AND][sequential `;`]**

* **Justification**: For each patient, the robot must check entry preconditions, identify the patient, communicate the procedure, determine required signs, collect or resolve each applicable sign, and complete the visit.

---

## Room-entry preconditions

**G14 -> G15, G18 [AND][sequential `;`]**

* **Justification**: The patient must be available and the robot must have enough battery before entering the room.

**G15 -> G16, G17 [OR][FALLBACK(G16,G17)]**

**G16 -> AT11 [OR]**

* **Justification**: Checking availability is sufficient when the result is positive.

**G17 -> AT12, AT13 [AND][sequential `;`]**

* **Justification**: For an unavailable patient, the robot must schedule a five-minute revisit and then return.

**G18 -> G19, G20 [OR][FALLBACK(G19,G20)]**

* **Justification**: If battery is sufficient, the robot continues. Otherwise, recharge and reassignment are required.

**G19 -> AT14 [OR]**

* **Justification**: Battery estimation is sufficient when it confirms enough charge.

**G20 -> AT15, AT16 [AND][sequential `;`]**

* **Justification**: Low battery requires both recharging and reassignment of pending tasks.

---

## Patient identification

**G22 -> AT18 [OR]**

## Procedure preparation

# 5. Important monitored variables

| Variable                       | Purpose                                                                    |
| ------------------------------ | -------------------------------------------------------------------------- |
| `missionCycleTime`             | Checks whether two hours have passed since the last cycle.                 |
| `occupiedRooms`                | Stores the rooms that must be visited.                                     |
| `roomPatients`                 | Stores patients and beds per room.                                         |
| `patientAvailable`             | Determines whether the robot may proceed or must revisit in five minutes.  |
| `robotBatteryLevel`            | Used before entering a room.                                               |
| `estimatedRoomTaskBatteryCost` | Used to decide whether battery is sufficient.                              |
| `patientIdentityConfirmed`     | Confirms that the correct patient was found.                               |
| `patientConditionSet`          | Stores infectious, post-surgical, diabetes, and high-risk classifications. |
| `requiredVitalSigns`           | Stores the vital signs required for the current patient.                   |
| `vitalSignCollectionStatus`    | Tracks success or failure of each measurement.                             |
| `patientResponseStatus`        | Determines whether nurse/doctor alert is required.                         |
| `patientCheckedStatus`         | Indicates whether the patient has been marked as done.                     |
| `infectiousRoomExit`           | Determines whether robot sterilization is required.                        |
| `patientContactPerformed`      | Determines whether actuator disinfection is required.                      |
| `availableRobotSet`            | Stores robots available for reassignment or help.                          |
| `missionFeasibilityStatus`     | Determines whether manager escalation is needed.                           |

This model captures the mission as a **sequential, fallback-aware, multi-robot goal tree** with explicit handling of timing, patient condition, safety, hygiene, and infeasibility.
