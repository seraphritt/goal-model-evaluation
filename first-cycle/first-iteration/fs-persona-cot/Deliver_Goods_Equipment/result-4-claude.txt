# Goal Model: Multi-Robot Collect-and-Deliver Mission

## 1. Reasoning (step by step)

**Step 1: Identify the top-level intention.** The mission exists so that *the requested resources end up at the specified location*. That is an achieve goal (G1). It starts "when required", so a request has to be read and understood first (G2). Linens are moved periodically, so the trigger can be scheduled or on demand. Either way it is an input that must be read.

**Step 2: Find the mission phases.** The text names two phases in strict order: collection, then delivery ("Once retrieved, the delivery phase begins"). So they are sequential (;) children of one goal, and both are needed (AND).

**Step 3: Find parallelism.** "Multiple robots can be assigned to parallel collect-deliver tasks" gives an allocation step (G3) followed by parallel execution (G4). Each robot runs a complete collect-then-deliver flow (G5).

**Step 4: Decompose collection.**
- The visiting order comes from *waiting time + path length*. That is information retrieval, so it is a query goal (G8). The two estimates are independent (parallel) and the ranking needs both (sequential afterwards): `(G9 # G10) ; G11`.
- Retrieval per storage has a fixed order: reach the storage (G13), send the request message (G15), then wait until retrieval (G16).

**Step 5: Decompose delivery.** "As many runs as necessary" means a repeated cycle: transport, hand over, return for the remainder (G21).

**Step 6: Model the exceptions as fallbacks.** Each exception replaces the normal plan only when the normal plan can no longer proceed, which is the semantics of FALLBACK:
- Battery ≤10% in collection: FALLBACK(nominal collection, hand-over). The robot returns to recharge and reassigns.
- Battery ≤30% in delivery: FALLBACK(checkpoint transfer, escalation).
- Failure to reach the checkpoint: alert and report to the sector manager. These are independent, so they run in parallel.

**Step 7: Define tasks.** Each leaf goal gets one operational task with a location variable and a robot count. Where order between actions matters, I split them into separate leaf goals so the sequence stays formal.

**Modelling assumptions (please review):**
1. Goal IDs use plain depth-first numbers (G1…G31), as the definitions require, rather than G4.1-style IDs.
2. A goal with only tasks as children is a *leaf goal* and gets "-".
3. In the goal tables, **Relation** is the goal's decomposition over its children. In the task tables, it is the AND/OR decomposition of the parent that the task belongs to.
4. Goals under "#" (G5) are templates instantiated once per robot or storage group.
5. Capacity is limited, so unfinished resources wait at `pickup_point` between delivery runs.
6. After a successful hand-over (G17), the transferring robot's flow ends. The receiving robot instantiates G5 for the remaining mission, so the first robot does not go on to G20.

**Monitored variables:** `request_spec`, `storage_places`, `assigned_storages`, `visit_order`, `current_storage`, `pickup_point`, `delivery_location`, `recharging_station`, `checkpoint`, `sector_manager_station`, `battery_level`. G6 monitors `battery_level > 10%`. G20 monitors `battery_level > 30%`.

## 5. Logical Relationships

**Goal → Goal**

- **G1 → G2, G3, G4 [AND][sequential (;)]**
  - **Justification**: The request must be known before allocation, and allocation before execution. All three are needed for the request to be fulfilled.
- **G4 → G5 [AND][parallel (#)]**
  - **Justification**: One G5 instance runs per assigned robot or storage group, at the same time. This is the stated way to "reduce the time to finish the mission". All instances are needed.
- **G5 → G6, G20 [AND][sequential (;)]**
  - **Justification**: Collection precedes delivery ("once retrieved, the delivery phase begins"). Both phases are required.
- **G6 → G7, G17 [OR][FALLBACK(G7, G17)]**
  - **Justification**: Normal collection is preferred. Only if the battery falls to 10% does the hand-over replace it. One of the two is enough.
- **G7 → G8, G12 [AND][sequential (;)]**
  - **Justification**: The order of visits is fixed before the storages are visited.
- **G8 → G9, G10, G11 [AND][(G9 # G10) ; G11]**
  - **Justification**: Waiting time and path length are independent (parallel), and the ranking needs both, so it comes after (sequential). All three are required for the order.
- **G12 → G13, G14 [AND][sequential (;)]**
  - **Justification**: The robot must be at the storage before it can request resources. This is repeated for each storage in `visit_order`.
- **G14 → G15, G16 [AND][sequential (;)]**
  - **Justification**: Send the request first, then wait for retrieval.
- **G17 → G18, G19 [AND][sequential (;)]**
  - **Justification**: The description says the robot "goes back to the recharging station and assigns the mission", in that order.
- **G20 → G21, G25 [OR][FALLBACK(G21, G25)]**
  - **Justification**: The normal delivery is preferred. The 30% battery procedure applies only when it can no longer continue.
- **G21 → G22, G23, G24 [AND][sequential (;)]**
  - **Justification**: One delivery run is transport, then hand-over, then return. The cycle repeats while resources remain ("as many runs as necessary").
- **G25 → G26, G29 [OR][FALLBACK(G26, G29)]**
  - **Justification**: Escalation happens only if the checkpoint transfer fails.
- **G26 → G27, G28 [AND][sequential (;)]**
  - **Justification**: The resource must be secured first so that the next robot "will know where the resource is positioned".
- **G29 → G30, G31 [AND][parallel (#)]**
  - **Justification**: Alert and report are independent and both are required.

**Goal → Task**

- **G2 → AT1 [AND]**: reading the request is the one action that realises the query.
- **G3 → AT2 [AND]**: the allocation is done by this single task.
- **G9 → AT3 [AND]**: querying the storages provides the wait times.
- **G10 → AT4 [AND]**: path computation provides the lengths.
- **G11 → AT5 [AND]**: sorting provides the ordered list.
- **G13 → AT6 [AND]**: navigation makes the robot arrive at the storage.
- **G15 → AT7 [AND]**: sending the message is the activity itself.
- **G16 → AT8 [AND]**: waiting until confirmation reaches the target state.
- **G18 → AT9 [AND]**: driving to the station.
- **G19 → AT10 [AND]**: the transfer needs two robots.
- **G22 → AT11 [AND]**: carrying the load.
- **G23 → AT12 [AND]**: unloading to the requester.
- **G24 → AT13 [AND]**: returning for the remainder.
- **G27 → AT14 [AND]**: depositing at the checkpoint.
- **G28 → AT15 [AND]**: assigning with the checkpoint position.
- **G30 → AT16 [AND]**: raising the alert.
- **G31 → AT17 [AND]**: sending the report.

**Justification for all Goal → Task links:** each leaf goal has exactly one task, so AND and OR coincide. I chose AND because that task is required to reach the goal, and I split multi-step behaviour into separate goals so ordering stays formal.
