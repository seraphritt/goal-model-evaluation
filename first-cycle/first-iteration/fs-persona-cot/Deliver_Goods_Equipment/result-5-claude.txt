# Goal model: multi-robot collect-and-deliver mission

## 1. Step-by-step analysis

**Step 1: Actors, phases and triggers.**
- The actors are the robot(s), the storages, the requesting agent, the recharging station, a checkpoint and the sector manager.
- The mission has two phases, *collection* and *delivery*. Delivery starts only "once retrieved", so the phases are sequential.
- The mission starts "when required". The examples (sterile equipment on demand, linens periodically) show it can be triggered on demand or periodically.

**Step 2: Goals versus tasks.**
- Goals are intentional objectives: "resources delivered", "resources collected", "mission handed over". Tasks are concrete steps a robot can execute at a location: navigate, send a message, wait, load, unload, trigger an alert.

**Step 3: Nominal flow.**
1. Assign robots to storages.
2. Order the storages by estimated waiting time plus path length.
3. For each storage in that order: reach it, request the resources, wait for retrieval.
4. Deliver in as many runs as necessary.

**Step 4: Exceptions become FALLBACKs.**
- Battery at or below 10% in collection: the robot goes to the recharging station and reassigns the mission.
- Battery at or below 30% in delivery: the robot returns the resource to a checkpoint and reassigns the remaining task.
- If returning the resource to the checkpoint fails: alert plus report to the sector manager.
- Each of these is "try the normal way, otherwise the recovery", so I used FALLBACK. Because FALLBACK is binary, the three-way delivery alternative is nested.

**Step 5: Parallelism.**
- "Multiple robots can be assigned to parallel collect-deliver tasks" gives a parallel (#) decomposition over per-robot collect-deliver goals. G4 is a parameterised goal, instantiated once per assigned robot and its storage subset.
- The alert and the report are independent, so they are also parallel.

**Step 6: Goal types.**
- I used Achieve when a world state can be stated, Query for the information-gathering goal (visiting order), and Perform when only carrying out the activity matters.

**Step 7: Assumptions** (the description does not state these).
- n is the number of distinct storages in the request.
- Replacement robots start a new instance of G4 (or resume delivery at G17 from the checkpoint).
- Where a task location is not stated, I used a variable name.
- Ordinary AND/OR relations between a goal and a single task are equivalent, and I mark them AND.

Goal IDs follow the definition (G followed by a number, depth-first), so there are no dotted IDs.

## 5. Logical relationships

**G1 -> G2, G3 [AND][sequential ;]**
- **Justification**: Robots must be assigned before they can execute. Both are needed for the request to be fulfilled.

**G3 -> G4 [AND][parallel #]**
- **Justification**: One instance of G4 per assigned robot. They run in parallel to reduce the time to finish, and all must complete.

**G4 -> G5, G15 [AND][sequential ;]**
- **Justification**: Collection precedes delivery ("once retrieved, the delivery phase begins"). Both are required.

**G5 -> G6, G12 [OR][FALLBACK(G6, G12)]**
- **Justification**: Normal collection is tried first. At 10% battery the robot recovers via recharge and reassignment. Either outcome resolves the collection.

**G6 -> G7, G8 [AND][sequential ;]**
- **Justification**: The visiting order (waiting time plus path) must be known before storages are visited.

**G8 -> G9, G10, G11 [AND][sequential ;]**
- **Justification**: The robot reaches the storage, then requests, then waits for retrieval. Each step depends on the previous one.

**G12 -> G13, G14 [AND][sequential ;]**
- **Justification**: The description states the robot "goes back to the recharging station and assigns the mission". Both are needed.

**G15 -> G16, G21, G24 [OR][FALLBACK(G16, FALLBACK(G21, G24))]**
- **Justification**: Normal delivery is tried first. At 30% battery the checkpoint handover applies. If returning the resource fails, the alert is the last resort.

**G16 -> G17, G18, G19, G20 [AND][sequential ;]**
- **Justification**: A run is physically ordered: reach, load, transport, hand over. The sequence repeats until nothing remains.

**G21 -> G22, G23 [AND][sequential ;]**
- **Justification**: The resource must be at the checkpoint before the task is reassigned, so the new robot knows where the resource is.

**G24 -> G25, G26 [AND][parallel #]**
- **Justification**: Alert and report are independent and both required, so they run in parallel.

**Goal -> task relations** (all AND, one task per leaf goal):
- G2 -> AT1
- G7 -> AT2
- G9 -> AT3
- G10 -> AT4
- G11 -> AT5
- G13 -> AT6
- G14 -> AT7
- G17 -> AT8
- G18 -> AT9
- G19 -> AT10
- G20 -> AT11
- G22 -> AT12
- G23 -> AT13
- G25 -> AT14
- G26 -> AT15
- **Justification**: Each leaf goal is realised by exactly one concrete action, so AND and OR are equivalent. I mark AND, because the task is necessary for the goal.

**Cross-tree links** (not tree edges, but implied by the description):
- AT7 (transfer at 10%) makes G2 and G4 start again for a replacement robot.
- AT13 (transfer at 30%) makes a replacement robot start at G17 from the checkpoint's `resource_position`.
