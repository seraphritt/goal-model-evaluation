# Goal Model: Multi-Robot Collect-and-Deliver Mission

## 1. Reasoning process

**Step 1: Identify the main objective.** The mission exists to get the requested resources to the requesting agent at a specified location. That is the root goal, and it is an Achieve goal because it has a clear target state.

**Step 2: Find the phases.** The text names a *collection phase* and a *delivery phase*, and says the delivery phase begins "once retrieved". So collection and delivery are ordered, which gives a sequential operator.

**Step 3: Find the parallelism.** "Multiple robots can be assigned to parallel collect-deliver tasks" means the work is first allocated (which storages go to which robots) and then executed in parallel, one collect-deliver mission per robot.

**Step 4: Find the exception handling.** There are three, and each is a fallback:
- Battery at 10% in collection: return to the recharging station and reassign the mission.
- Battery at 30% in delivery: return the resource to a checkpoint and reassign the remaining task.
- Checkpoint return fails: trigger an alert and report to the sector manager.

**Step 5: Find the ordering constraints.**
- Storage visit order is defined by waiting time plus path, so ordering is computed before moving.
- The robot reaches the storage, waits for its turn, sends the request, and waits for retrieval.
- Delivery is a loop of runs until nothing remains.

**Step 6: Modelling conventions I adopted.**
- Goal IDs are `G<n>` and task IDs `AT<n>`, both numbered depth-first.
- "Leaf goal" (runtime `-`) means the goal has a single child, so no ordering needs to be stated. Any goal with two or more children (goals or tasks) gets an operator.
- **Relation** means the decomposition of a goal over its children. For a task, it is the relation to its parent goal.
- A `FALLBACK` goal uses OR decomposition, because the success of either branch is enough.
- G6 is a *template goal*, instantiated once per assigned robot. The parallel operator on G5 works over these instances. The task location "collections" and the robot range `[n1,n2]` express the same idea.

## 2. Goal tree

```
G1 Fulfill resource request                          [;] AND
├─ G2 Allocate collect-deliver work                  [;] AND
│  ├─ G3 Identify storages (Query)                   [-] AND → AT1
│  └─ G4 Assign storages to robots                   [-] AND → AT2
└─ G5 Execute collect-deliver missions               [#] AND
   └─ G6 Complete one robot's mission (per robot)    [;] AND
      ├─ G7 Collect required resources               FALLBACK(G8,G13) OR
      │  ├─ G8 Collect from assigned storages        [;] AND
      │  │  ├─ G9 Determine visiting order (Query)   [-] AND → AT3
      │  │  └─ G10 Retrieve from one storage         [;] AND
      │  │     ├─ G11 Reach storage                  [-] AND → AT4
      │  │     └─ G12 Obtain requested resources     [;] AND → AT5, AT6, AT7
      │  └─ G13 Hand over collection (battery 10%)   [;] AND → AT8, AT9
      └─ G14 Deliver resources                       FALLBACK(G15,G16) OR
         ├─ G15 Transport all resources              [;] AND → AT10–AT13
         └─ G16 Hand over delivery (battery 30%)     FALLBACK(G17,G18) OR
            ├─ G17 Transfer to another robot         [;] AND → AT14, AT15
            └─ G18 Escalate checkpoint failure       [;] AND → AT16, AT17
```

## 4. Task tables

The Relation column gives the relation to the parent goal.

| Name | Text | Relation | Location | Number of Robots | Justification |

| **AT5: Wait for Request Turn** | Wait at the storage until it is time to request. | AND (G12) | `Storage_Location` | 1 | "once … it is time to request the resource" implies a queue or waiting time. |
| **AT6: Send Request Message** | Send the storage a message with the precise specification of the resources. | AND (G12) | `Storage_Location` | 1 | The text states the message must carry the "precise specification". |

| **AT17: Send Report to Sector Manager** | Send a failure report to the sector manager. | AND (G18) | `Current_Position` | 1 | The report is explicitly required, and it follows the alert. |

## 6. Logical relationships

- **G1 → G2, G5 [AND][sequential ;]**
  - **Justification**: Work must be allocated before any robot can act, and both allocation and execution are needed to satisfy the request.

- **G2 → G3, G4 [AND][sequential ;]**
  - **Justification**: The assignment depends on knowing which storages hold the resources, and both are needed.

- **G3 → AT1 [AND]**
  - **Justification**: The query is answered only by performing the lookup.

- **G4 → AT2 [AND]**
  - **Justification**: The target allocation is produced only by the assignment task.

- **G5 → G6 [AND][parallel #]**
  - **Justification**: One instance of G6 runs per assigned robot. The instances are independent and run concurrently to shorten the mission, and all must finish.

- **G6 → G7, G14 [AND][sequential ;]**
  - **Justification**: "Once retrieved, the delivery phase begins." Both phases are needed.

- **G7 → G8, G13 [OR][FALLBACK(G8, G13)]**
  - **Justification**: Normal collection is the default. If the battery drops to 10%, the recovery branch replaces it, and either one satisfies G7.

- **G8 → G9, G10 [AND][sequential ;]**
  - **Justification**: The visiting order must exist before storages are visited, and both are needed. G10 is repeated for each storage in the order.

- **G9 → AT3 [AND]**
  - **Justification**: The order is produced by computing waiting time + path.

- **G10 → G11, G12 [AND][sequential ;]**
  - **Justification**: The robot must reach the storage before requesting, and both are needed.

- **G11 → AT4 [AND]**
  - **Justification**: Reaching the storage is achieved by navigating there.

- **G12 → AT5, AT6, AT7 [AND][sequential ;]**
  - **Justification**: The order is wait for turn, request, wait for retrieval, and all three are needed.

- **G13 → AT8, AT9 [AND][sequential ;]**
  - **Justification**: This follows the described order, return to the charger and then reassign, and both are required.

- **G14 → G15, G16 [OR][FALLBACK(G15, G16)]**
  - **Justification**: Normal delivery is tried first. At 30% battery the handover branch applies, and either suffices.

- **G15 → AT10, AT11, AT12, AT13 [AND][sequential ;]**
  - **Justification**: A run is load, transport, unload, return. The sequence repeats while `Remaining_Resources` is non-empty ("as many runs as necessary").

- **G16 → G17, G18 [OR][FALLBACK(G17, G18)]**
  - **Justification**: The checkpoint transfer is preferred. Only if it fails is the alert and report triggered, and either outcome resolves the low-battery event.

- **G17 → AT14, AT15 [AND][sequential ;]**
  - **Justification**: The resource must be at the checkpoint so the new robot "will know where the resource is positioned", and both are needed.

- **G18 → AT16, AT17 [AND][sequential ;]**
  - **Justification**: The description requires an alert and a report, in that order, and both are needed.

## 7. Assumptions and open points

- **Storage-to-delivery flow:** the description doesn't say whether a robot delivers from each storage separately or from all collected items together. I modelled delivery as runs starting at `Storage_Location` (a collection), which fits both readings.
- **Reassignment:** after AT9 or AT15, the receiving robot runs its own G6 instance. The description implies this, but the model doesn't draw it explicitly.
- **Thresholds:** the 30% delivery threshold (vs 10% in collection) plausibly leaves enough charge to carry a load to a checkpoint. This is my inference, not stated in the text.
- **Failure of handover after checkpoint success:** the description doesn't cover a failure of AT15, so it isn't modelled.
- **Examples in the description:** sterile medical equipment and clean linens are instances of the resources. They don't change the structure, but they would fill `Storages` and `Delivery_Location` at run time.
