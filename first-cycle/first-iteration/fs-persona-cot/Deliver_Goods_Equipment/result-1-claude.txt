# Goal Model: Multi-Robot Collect-and-Deliver Mission

## 1. Reasoning: from description to goal model

**Step 1: Key elements in the text**

| Fragment of the description | What it tells me |
|---|---|
| "collect the required resources... and deliver them" | Top-level objective with two phases, **collection then delivery** |
| "The order... is defined by the estimation of waiting time summed up with the path" | A **query** (information gathering) that precedes moving |
| "reaches one storage... sends a message... waits until retrieved" | Per-storage operational sequence: go, request, wait |
| "Once retrieved, the delivery phase begins... as many runs as necessary" | Phases are **sequential**, and delivery is **iterative** with a capacity limit |
| "battery low (10%) in collection... recharge and assign to another robot" | **Contingency** for collection |
| "battery low (30%) in delivery... return to checkpoint, assign remaining task" | **Contingency** for delivery |
| "failure to return to checkpoint → alert + report to sector manager" | **Second-level contingency** (fallback of a fallback) |
| "multiple robots... parallel collect-deliver tasks" | Parallelism across robots |

**Step 2: Design decisions**

1. **Top level.** The mission is one goal with two ordered parts: allocate work to robots, then execute it.
2. **Parallelism.** Each robot runs the same collect-then-deliver track for its own storage group. I model this as one multi-instance goal (G4), with one instance per assigned robot or storage group. The `#` operator applies across those instances.
3. **Contingencies as FALLBACK.** A battery threshold is an event that makes the nominal plan fail, so the recovery goal is a fallback to the nominal goal. Trying the nominal plan first and switching only on failure matches "if the battery runs low...". FALLBACK is binary, so the three-level delivery recovery is nested.
4. **Goal types.** I use Query where the goal only produces information (visit order, number of runs). I use Achieve where a world-state target exists. I use Perform only for G16, where success just means the actions were executed.
5. **Tasks.** Tasks are the operational leaves. Each has a location variable and a robot count, and its parent goal monitors that variable.
6. **Runtime for single-task goals.** The `-` marker is used for a goal with a single task child (G12), since there is nothing to orchestrate.

## 5. Logical relationships

**G1 -> G2, G3 [AND][sequential (;)]**
- **Justification**: Robots must be assigned before any collection starts, and the mission is not done unless both allocation and execution happen.

**G2 -> AT1, AT2 [AND][sequential (;)]**
- **Justification**: Storages must be identified before robots can be assigned to them. Both are needed for a valid allocation.

**G3 -> G4 [AND][parallel (#) across instances]**
- **Justification**: One G4 instance runs per assigned robot or storage group. The instances are independent and all must complete. This is the "parallel collect-deliver tasks" of the description.

**G4 -> G5, G10 [AND][sequential (;)]**
- **Justification**: Delivery starts only "once retrieved". Both phases are required.

**G5 -> G6, G9 [OR][FALLBACK(G6, G9)]**
- **Justification**: Normal collection is attempted first. If the battery reaches 10%, the handover replaces it. Only one branch needs to succeed.

**G6 -> G7, G8 [AND][sequential (;)]**
- **Justification**: The visiting order must exist before storages are visited, and retrieval needs both.

**G7 -> AT3, AT4, AT5 [AND][(AT3 # AT4) ; AT5]**
- **Justification**: Waiting time and path length are independent (parallel), and the ranking requires both (sequential). All three are needed for the order.

**G8 -> AT6, AT7, AT8 [AND][sequential (;)]**
- **Justification**: Go, request, wait, in that order, repeated for each storage in the list. All steps are needed to retrieve the resource.

**G9 -> AT9, AT10 [AND][parallel (#)]**
- **Justification**: Recharging and handing over the mission are both required. They are independent, and doing them concurrently minimizes the mission delay.

**G10 -> G11, G14 [OR][FALLBACK(G11, G14)]**
- **Justification**: Nominal delivery is preferred. Recovery applies only when the 30% battery threshold interrupts it.

**G11 -> G12, G13 [AND][sequential (;)]**
- **Justification**: The number of runs must be known before executing them, and both are needed.

**G12 -> AT11 [AND][-]**
- **Justification**: A single computation task yields the queried information.

**G13 -> AT12, AT13, AT14, AT15 [AND][sequential (;)]**
- **Justification**: A run is an ordered cycle of load, transport, hand over, return. It repeats while resources remain, and the final return is skipped.

**G14 -> G15, G16 [OR][FALLBACK(G15, G16)]**
- **Justification**: Escalation is triggered only if returning the resource to the checkpoint fails.

**G15 -> AT16, AT17 [AND][sequential (;)]**
- **Justification**: The resource must be at the checkpoint before the new robot is told where it is. Both actions are required.

**G16 -> AT18, AT19 [AND][parallel (#)]**
- **Justification**: Alert and report are both mandatory, independent, and urgent.

## 7. Reflections and assumptions

- **Multi-instance G4.** Modeling parallelism with one G4 per robot keeps the tree compact. If your tooling needs explicit sibling goals, replicate G4 per robot, or add a FALLBACK(parallel multi-robot, single-robot) split.
- **`pickup_point`.** The text says robots make several runs, so I assumed retrieved resources are staged at a pickup point rather than all carried at once.
- **Handover continuity.** After AT10 or AT17, the receiving robot starts a new G4 instance (or only the delivery part) for the remaining work. I did not model this, since the description does not detail it.
- **Battery thresholds.** They are treated as the failure conditions that trigger the FALLBACKs in G5 and G10. The higher delivery threshold (30% vs. 10%) is consistent with the robot carrying cargo and needing margin to reach a checkpoint.
- **Not modeled.** What the robot does after handing over via the checkpoint (for example, recharging) is not specified, so I left it out.
