# Goal Model: Multi-Robot Resource Collection and Delivery

## Assumptions

- Goal IDs (G1 to G15) and task IDs (AT1 to AT17) follow depth-first order.
- A "leaf goal" (runtime "-") is a goal with a single child task, so there is nothing to order.
- For tasks, **Relation** is the AND/OR relation with sibling tasks under the same parent goal.
- Retrieved resources stay at the storage pickup points until delivery. This is why the delivery phase needs several runs.
- G5 to G15 are instantiated once per assigned robot, and the instances run in parallel. When G10, G14 or G15 completes, that robot's instance ends and the replacement robot re-enters G5 for the remaining work.
- N_s is the number of storages involved in the request.

## Goals

| Name | Text | Runtime | Goal Type | Relation |
|---|---|---|---|---|
| **G1: Fulfill Resource Request** | Collect the required resources from storage and deliver them to the requesting agent at the specified location. | [;] G2 ; G5 | **Achieve.** Target condition: all requested resources are at `delivery_location`. Justification: the mission defines a world state to reach, not just activities to run. | AND |
| **G2: Plan Mission** | Find out where the resources are and which robots will do the collect-deliver work. | [;] G3 ; G4 | **Achieve.** Target condition: sources identified and robots assigned to every required storage. Justification: what matters is that the mission is ready to execute. | AND |
| **G3: Identify Storages** | Identify the storages holding each requested resource. | - | **Query.** Enquired information: mapping of each requested resource to its storage(s) and available quantity. Justification: the robot only needs to retrieve information; the world is not changed. | AND |
| **G4: Assign Robots** | Assign robots to the collect-deliver tasks: several in parallel when items come from different storages, otherwise one. | FALLBACK(AT2, AT3) | **Achieve.** Target condition: every required storage has an assigned robot. Justification: the description says multiple robots are assigned when items come from different storages, so the resulting assignment state is what counts. | OR |
| **G5: Execute Collect-Deliver** | Each assigned robot collects its share of resources and then delivers them. | [;] G6 ; G11 | **Achieve.** Target condition: the robot's share of resources is at `delivery_location`. Justification: collection must finish before the delivery phase begins, and the outcome is a state. | AND |
| **G6: Complete Collection Phase** | Collect resources from the storages. If battery drops to 10%, hand the mission over instead. | FALLBACK(G7, G10) | **Achieve.** Target condition: all resources in `assigned_storages` retrieved, or the mission transferred to another robot. Justification: the phase ends in a verifiable state, either normally or via handover. | OR |
| **G7: Collect From Storages** | Visit the assigned storages in the defined order and retrieve the resources. | [;] G8 ; G9 | **Achieve.** Target condition: `retrieved(s) = true` for every storage `s` in `assigned_storages`. Justification: success is defined by the resources being retrieved. | AND |
| **G8: Order Storages** | Sort the storages by estimated waiting time plus path length. | - | **Query.** Enquired information: estimated waiting time and path length to each assigned storage, giving the ordered visiting list. Justification: the description defines the order from estimates, so this is pure information retrieval. | AND |
| **G9: Retrieve At Storage** | For each storage in order: go there, send the precise request message, and wait until the resources are retrieved. | [;] AT5 ; AT6 ; AT7 | **Achieve.** Target condition: the requested resources at storage `s` are retrieved. Justification: the robot waits until retrieval is complete, so success depends on a state, not just on having sent the message. | AND |
| **G10: Hand Over Collection** | When battery reaches 10% in the collection phase, return to the recharging station and assign the mission to another robot. Reassignment runs in parallel so the mission is not delayed if the robot cannot reach the station. | [#] AT8 # AT9 | **Achieve.** Target condition: the robot is at `recharging_station` and the mission is assigned to another robot. Justification: both parts of the outcome are states that can be checked. | AND |
| **G11: Complete Delivery Phase** | Deliver the resources. If battery drops to 30%, execute the low-battery procedure. | FALLBACK(G12, G13) | **Achieve.** Target condition: all resources delivered, or safely handed over or reported. Justification: the phase ends in a verifiable state on either path. | OR |
| **G12: Deliver Resources** | Make as many runs as needed to take all resources to the specified location. | [;] AT10 ; AT11 ; AT12 ; AT13 (repeated while resources remain) | **Achieve.** Target condition: `remaining_resources = ∅` and all resources are at `delivery_location`. Justification: the description requires repeating runs until everything is delivered, so completion is state-based. | AND |
| **G13: Handle Low Battery (Delivery)** | At 30% battery, secure the resource at a checkpoint and reassign the task. If that fails, escalate. | FALLBACK(G14, G15) | **Achieve.** Target condition: resource secured at `checkpoint` with the task reassigned, or the failure reported to the sector manager. Justification: one of two safe end states must hold. | OR |
| **G14: Hand Over Via Checkpoint** | Return the resource to a checkpoint and assign the remaining task to another robot, which knows where the resource is positioned. | [;] AT14 ; AT15 | **Achieve.** Target condition: resource at `checkpoint` and remaining task assigned to another robot. Justification: the outcome is a specific world state. | AND |
| **G15: Escalate Failure** | If the resource cannot be returned to the checkpoint, trigger an alert and send the report to the sector manager. | [#] AT16 # AT17 | **Perform.** Justification: the description only requires that the alert be triggered and the report sent, so the goal succeeds once these activities are performed. | AND |

## Tasks

| Name | Text | Relation | Location | Number of Robots |
|---|---|---|---|---|
| **AT1: Query Storage Registry** | Request and read the inventory of storages to map resources to storages. | AND (G3) | `control_center` | 1 |
| **AT2: Assign Parallel Robots** | Assign one robot to each storage (or group of storages) so collect-deliver flows run in parallel. | OR (G4) | `control_center` | [2, N_s] |
| **AT3: Assign Single Robot** | Assign one robot to all storages, used when parallel assignment is not possible. | OR (G4) | `control_center` | 1 |
| **AT4: Compute Visiting Order** | Compute waiting-time estimate plus path length per storage and sort ascending. | AND (G8) | `robot_pos` | 1 |
| **AT5: Navigate To Storage** | Go to the next storage in the ordered list. | AND (G9) | `assigned_storages` | 1 |
| **AT6: Send Request Message** | On arrival, send the storage a message with the precise specification of the requested resources. | AND (G9) | `assigned_storages` | 1 |
| **AT7: Wait For Retrieval** | Wait until the storage confirms the resources have been retrieved. | AND (G9) | `assigned_storages` | 1 |
| **AT8: Return To Recharging Station** | Navigate to the recharging station when battery is at 10%. | AND (G10) | `recharging_station` | 1 |
| **AT9: Reassign Mission** | Send the mission (with remaining storages) to another available robot. | AND (G10) | `robot_pos` | 1 |
| **AT10: Load Resource Batch** | Load the next batch of resources that fits the robot's capacity. | AND (G12) | `pickup_points` | 1 |
| **AT11: Transport Batch** | Carry the batch to the specified location. | AND (G12) | `delivery_location` | 1 |
| **AT12: Unload Batch** | Unload the batch at the specified location. | AND (G12) | `delivery_location` | 1 |
| **AT13: Return For Next Run** | Return to the pickup point if resources remain; skipped on the last run. | AND (G12) | `pickup_points` | 1 |
| **AT14: Return Resource To Checkpoint** | Carry the current resource to the nearest checkpoint when battery is at 30%. | AND (G14) | `checkpoint` | 1 |
| **AT15: Assign Remaining Task** | Assign the remaining task to another robot and share the resource position. | AND (G14) | `checkpoint` | 1 |
| **AT16: Trigger Alert** | Raise an alert that the resource could not be returned to a checkpoint. | AND (G15) | `robot_pos` | 1 |
| **AT17: Send Report To Sector Manager** | Send a report with robot state, resource position and failure cause. | AND (G15) | `sector_manager` | 1 |

## Variables monitored by parent goals

| Goal | Monitored variables |
|---|---|
| G1 | `delivery_location`, `requested_resources` |
| G3 | `requested_resources`, storage inventory |
| G4 | `control_center`, available robots, `N_s` |
| G7, G8 | `assigned_storages`, `robot_pos`, waiting-time estimates |
| G9 | `assigned_storages` |
| G10 | `battery_level` (≤ 10%), `recharging_station`, `robot_pos` |
| G12 | `pickup_points`, `delivery_location`, `remaining_resources` |
| G14 | `battery_level` (≤ 30%), `checkpoint` |
| G15 | `robot_pos`, `sector_manager` |

## Logical Relationships

- **G1 -> G2, G5 [AND][(sequential) G2 ; G5]**
- **G2 -> G3, G4 [AND][(sequential) G3 ; G4]**
- **G3 -> AT1 [AND]**
- **G4 -> AT2, AT3 [OR][FALLBACK(AT2, AT3)]**
- **G5 -> G6, G11 [AND][(sequential) G6 ; G11]**
- **G6 -> G7, G10 [OR][FALLBACK(G7, G10)]**
- **G7 -> G8, G9 [AND][(sequential) G8 ; G9]**
- **G8 -> AT4 [AND]**
- **G9 -> AT5, AT6, AT7 [AND][(sequential) AT5 ; AT6 ; AT7]**
- **G10 -> AT8, AT9 [AND][(parallel) AT8 # AT9]**
- **G11 -> G12, G13 [OR][FALLBACK(G12, G13)]**
- **G12 -> AT10, AT11, AT12, AT13 [AND][(sequential) AT10 ; AT11 ; AT12 ; AT13]**
- **G13 -> G14, G15 [OR][FALLBACK(G14, G15)]**
- **G14 -> AT14, AT15 [AND][(sequential) AT14 ; AT15]**
- **G15 -> AT16, AT17 [AND][(parallel) AT16 # AT17]**

The two examples in the description (sterile medical equipment and clean linens) fit this model with different `delivery_location` and `pickup_points` values. Linens are periodic, so G1 would simply be triggered on a schedule.
