**Goal Model – Multi‑Robot Resource Delivery Mission**

| **Name** | **Text**                             | **Runtime**      | **Goal Type** | **Correct Goal Type** | **Target Condition / Enquired Info** | **Relation** |
| -------- | ------------------------------------ | ---------------- | ------------- | --------------------- | ------------------------------------ | ------------ |
| **G1**   | Execute Resource Delivery Mission    | `;` (sequential) | Perform       | Achieve. Target Condition: all resources were delivered.               | –                                    | –            |
| **G2**   | Collect Resources                    | `;` (sequential) | Perform       | Perform               | –                                    | AND with G1  |
| **G3**   | Deliver Resources                    | `;` (sequential) | Perform       | Perform               | –                                    | AND with G1  |
| **G2.4** | Handle Low Battery During Collection | `;` (sequential) | Perform       | Perform               | –                                    | AND with G2  |
| **G3.3** | Handle Low Battery During Delivery   | `;` (sequential) | Perform       | Perform               | –                                    | AND with G3  |
| **G3.4** | Handle Delivery Failure              | `-` (leaf)       | Perform       | Perform               | –                                    | AND with G3  |


> **Notes on Goal Types**  
> All goals are *Perform* goals because the mission consists of concrete actions that must be executed by the robots (navigation, request, transport, battery‑recharging, etc.). No goal simply queries information or seeks a state change that is not action‑based.

### Logical Relationships

| **Parent** | **Children** | **Relation** | **Runtime** |
|------------|--------------|--------------|-------------|
| **G1** | G2, G3 | AND | `;` (sequential – first collection, then delivery) |
| **G2** | AT1, AT2, AT3, AT4, G2.4 | AND | `;` (sequential – navigation → request → wait → battery check → low‑battery handler) |
| **G2.4** | AT8, AT9 | AND | `;` (robot recharges, then delegates task) |
| **G3** | AT5, AT6, AT7, G3.3, G3.4 | AND | `;` (navigation → transport → battery check → low‑battery handler → failure handler) |
| **G3.3** | AT10, AT9 | AND | `;` (return to checkpoint → delegate remaining work) |
| **G3.4** | AT11 | AND | `-` (leaf – send alert) |

> **Parallelism** – If multiple items are requested from different storages, the mission planner can spawn additional *Collect* goals (additional instances of G2) and link them in parallel under G1 using the `#` operator. For the current model, a single sequence is assumed.

---

### Justification of Design Choices

1. **Perform Goals**  
   Every high‑level objective in this mission (collect, deliver, handle battery, handle failure) requires explicit robot actions; thus they are classified as *Perform* goals.

2. **Sequential vs. Parallel**  
   Collection must finish before delivery can start, so the top‑level relation is sequential (`;`). Within each phase, the required sub‑steps are also strictly ordered (navigation → request → wait → battery check). The only parallelism arises when multiple items are collected concurrently—this can be modelled by spawning multiple `G2` instances under `G1` with `#` (not shown in the base model).

3. **Fallback and Recovery**  
   Low‑battery situations are handled by dedicated sub‑goals (`G2.4`, `G3.3`) which contain the recovery tasks (`AT8`/`AT10` followed by delegation `AT9`). These are placed as children of the respective phases to ensure they are triggered only when the parent phase is active.

4. **Task‑Goal Mapping**  
   Tasks are direct descendants of the phase goals, allowing clear assignment of robot agents and execution locations. Each task is linked with an `AND` relation to its parent goal, ensuring that all tasks in a phase must succeed for the phase to succeed.

5. **Alerting**  
   Failure to return a resource to a checkpoint triggers `G3.4`, which in turn executes `AT11` to notify the sector manager. This goal is a leaf (no further children) and is therefore marked with `-`.

The resulting goal model satisfies the mission description, supports parallel execution when needed, and provides a clear mapping from high‑level objectives to concrete robot actions.
