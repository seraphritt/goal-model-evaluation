Below is a goal-model decomposition grounded in the provided mission description. I use **AND** when all children are required to satisfy the parent, and **OR** only when the mission supports alternative execution modes. Leaf goals use runtime `-`, as required by the specification. The mission itself states that the robot must collect resources from storage and deliver them to the requesting agent, with collection followed by delivery. Texto colado

## Modeling assumptions

1. **One collect-deliver flow** means one assigned robot or group handles the resources associated with a storage/request segment.
2. When multiple items are required from different storages, the model allows **parallel instances** of the collect-deliver flow, because the description explicitly says multiple robots can be assigned to parallel collect-deliver tasks. Texto colado
3. Low-battery behavior is modeled as **contingency handling**. It is part of the mission model because the description explicitly defines what must happen at 10% battery in collection and 30% battery in delivery. Texto colado
4. The checkpoint failure case is modeled with **FALLBACK**, because the description explicitly says that if returning the resource to a checkpoint fails, an alert and report must be triggered. Texto colado

# Logical Relationships

- **G1 → G2, G5 [AND][sequential: `G2;G5`]**  
  - **Justification:** The mission cannot be executed before required resources, storage information, and execution strategy are known. After preparation, the collect-deliver execution begins.

- **G2 → G3, G4 [AND][sequential: `G3;G4`]**  
  - **Justification:** The robot must first obtain mission information, then use that information to plan storage order and robot assignment.

- **G3 → AT1, AT2 [AND][sequential: `AT1;AT2`]**  
  - **Justification:** The mission needs both the request details and the storage places where resources can be found.

- **G4 → AT3, AT4, AT5 [AND][sequential: `AT3;AT4;AT5`]**  
  - **Justification:** The system estimates waiting/path cost, uses that estimate to define the order, and then decides whether multiple robots should be assigned.

- **G5 → G6, G11 [OR][parallel-capable: `G6#G11`]**  
  - **Justification:** A single collect-deliver flow is enough for simple requests, but multiple parallel flows may be used when multiple items from different storages are required.

- **G6 → G7, G9 [AND][sequential: `G7;G9`]**  
  - **Justification:** The description explicitly states that delivery begins once the resources are retrieved, so collection must precede delivery.

- **G7 → G8, G10, G13 [AND][sequential/conditional: `G8;G10;G13`]**  
  - **Justification:** Collection requires reaching storage and obtaining the resource. The low-battery rule is included as a conditional safety/continuity requirement during collection.

- **G8 → AT6 [AND]**  
  - **Justification:** Reaching storage is operationalized by the robot physically going to the storage places.

- **G10 → AT7, AT8 [AND][sequential: `AT7;AT8`]**  
  - **Justification:** The robot first sends the precise request message, then waits until the resources are retrieved.

- **G9 → G12, G14 [AND][sequential/conditional: `G12;G14`]**  
  - **Justification:** Delivery requires moving resources to the destination, while the delivery low-battery contingency must be handled if the 30% threshold occurs.

- **G12 → AT9, AT10 [AND][sequential: `AT9;AT10`]**  
  - **Justification:** Transporting resources and repeating delivery runs are jointly required when all resources cannot be delivered in one run.

- **G13 → AT11, AT12 [AND][sequential: `AT11;AT12`]**  
  - **Justification:** During collection, if battery reaches 10%, the robot returns to the recharging station and assigns the mission to another robot.

- **G14 → G15, G16, G17 [AND][fallback: `FALLBACK((G15;G16),G17)`]**  
  - **Justification:** The normal delivery low-battery response is to return the resource to a checkpoint and assign the remaining task. If returning to the checkpoint fails, the fallback is to trigger an alert and send a report.

- **G15 → AT13 [AND]**  
  - **Justification:** Returning the resource to a checkpoint is the concrete task that satisfies checkpoint handoff.

- **G16 → AT14 [AND]**  
  - **Justification:** Assigning the remaining task to another robot operationalizes delivery continuation.

- **G17 → AT15 [AND]**  
  - **Justification:** The alert/report task operationalizes the failure-handling requirement when the checkpoint return fails.
