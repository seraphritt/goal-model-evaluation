## Modeling scope and assumptions

- The model is built **per requested sample**; for multiple samples, the same structure is repeated or instantiated for each sample/barcode.
- The mission is a **multi-robot / human-robot workflow** involving:
  - a mobile delivery robot or robotic drawer system for transport and access control,
  - a robotic arm in the laboratory,
  - nurses and laboratory personnel as human collaborators,
  - the track system as the information infrastructure.
- I use **OR decompositions only where the description gives alternatives**, e.g., “robotic arm or laboratory personnel,” “authorized personnel or specific robots.”
- I do **not use FALLBACK**, because the description does not define a preferred normal behavior followed by a failure-triggered alternative. The alternatives are available choices, not fallback chains.
- For OR branches, the runtime annotation uses `#` only to indicate that alternatives may be available without a required order; the **OR relation** is what defines that only one alternative is sufficient.

# 4. Logical Relationships

## Top-level mission

- **G1 -> G2, G6, G9, G13, G16, G23 [AND][`(G2;G6;G9;G13;(G16#G23))`]**
  - **Justification:** The mission is not only to move a sample. It must be requested/identified, secured, transported, opened only by authorized actors, picked/processed in the laboratory, and logged securely. These are all jointly required.
  - The sequence follows the natural mission flow:
    1. sample request and identity,
    2. secure drawer preparation,
    3. transport and time tracking,
    4. authorized opening,
    5. pickup/processing and pickup logging.
  - Pickup logging can occur in parallel with the pickup/processing event, hence `(G16#G23)`.

---

## Request and identity

- **G2 -> G3, G4, G5 [AND][`(G3;G4;G5)`]**
  - **Justification:** A valid transport mission requires barcode identity, a nurse delivery request, and sample data in the track system. The barcode is explicitly required before collection, so it appears first.

- **G3 -> AT1 [AND]**
  - **Justification:** Validating the barcode operationalizes the goal that the sample is identified before pickup/collection.

- **G4 -> AT2 [AND]**
  - **Justification:** Reading the nurse’s delivery request from the track system operationalizes obtaining the requested delivery.

- **G5 -> AT3 [AND]**
  - **Justification:** Retrieving sample metadata operationalizes the requirement that the nurse-inserted data is available to the robot/system.

---

## Secure drawer transport preparation

- **G6 -> G7, G8 [AND][`(G7;G8)`]**
  - **Justification:** The sample must both be inside the locked drawer and protected by access restrictions. A locked empty drawer is insufficient, and an unlocked drawer with a sample is insecure.

- **G7 -> AT4 [AND]**
  - **Justification:** The concrete operation is placing or receiving the sample into the secure drawer.

- **G8 -> AT5 [AND]**
  - **Justification:** The concrete operation is locking the drawer and activating the authorization/location policy.

---

## Transport and protocol time tracking

- **G9 -> G10, G11, G12 [AND][`(G10;G11;G12)`]**
  - **Justification:** To track elapsed time, the system must record the collection time, transport the sample, then record delivery time and evaluate protocol compliance. The order is temporal and required by the description.

- **G10 -> AT6 [AND]**
  - **Justification:** Recording the collection timestamp provides the start time for protocol tracking.

- **G11 -> AT7 [AND]**
  - **Justification:** Physical movement from patient floors to the laboratory is the core delivery action.

- **G12 -> AT8 [AND]**
  - **Justification:** The elapsed time can only be checked once the delivery time is known.

## Authorized drawer opening

- **G13 -> G14, G15 [OR][`(G14#G15)`]**
  - **Justification:** The description states that only authorized personnel or specific robots in specific locations should be able to open the locked drawers. Either authorized personnel or a specific robot is sufficient.
  - This is **not FALLBACK**, because the description does not say “try robot first, then personnel if robot fails,” or vice versa.

- **G14 -> AT9 [OR branch]**
  - **Justification:** This branch operationalizes drawer opening by a specific authorized robot.

- **G15 -> AT10 [OR branch]**
  - **Justification:** This branch operationalizes drawer opening by authorized personnel through controlled release.

- **G16 -> G17, G22 [OR][`(G17#G22)`]**
  - **Justification:** The description says the sample can be picked by a robotic arm or laboratory personnel. Either route satisfies laboratory pickup.
  - Again, this is not FALLBACK because no preferred/default route or failure condition is specified.

  - **Justification:** The robotic arm workflow is explicitly described as a sequence: pick up, scan barcode, sort, load into the entry-module. All actions are required for the automated laboratory-processing branch.

  - **Justification:** The robotic arm pickup action directly implements the pickup goal.

- **G19 -> AT12 [AND]**
  - **Justification:** Barcode scanning retrieves the sample identity and implements the barcode-query goal.

  - **Justification:** Robotic sorting implements the goal of placing the sample into the correct processing category.

- **G21 -> AT14 [AND]**
  - **Justification:** Loading into the entry-module implements the final automated preparation step for analysis machines.

- **G22 -> AT15 [OR branch]**
  - **Justification:** Laboratory personnel pickup is the human alternative explicitly allowed by the description.

# 5. Notes on FALLBACK

No fallback relation is used in this model.

The description contains alternatives, but not failure-ordered alternatives. For example:

- “robotic arm or laboratory personnel” means either may pick the sample;
- “authorized personnel or specific robots” means either may open the drawer if authorized.

There is no statement such as:

- “If the robotic arm fails, laboratory personnel pick the sample,” or
- “Try personnel first, then robot if personnel is unavailable.”

Therefore, these alternatives are modeled as **OR decompositions**, not FALLBACK.
