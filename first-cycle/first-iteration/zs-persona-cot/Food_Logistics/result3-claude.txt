# Goal model: hospital meal delivery and dish retrieval (multi-robot)

## Modeling conventions

- **IDs:** goals are G1..G36 and tasks are AT1..AT26, both numbered in depth-first order.
- **Table layout:** I read "a table for each goal/task" as one goals table and one tasks table, with one row per node.
- **Goal Relation:** this column is the AND/OR decomposition over the goal's children.
- **Task Relation:** this column is the relation with the parent goal. Every task is the sole child of a leaf goal, or a sequential step of an AND goal. The alternatives (OR) are expressed at the goal level, so all tasks are AND.
- **Runtime "-":** used for goals refined into a single task, since there is nothing to order.
- **Uncertainty:** the uncertain information about who can retrieve the meal is obtained by the Query goal G13 as beliefs with confidence values. The fallback chain under G15 then acts on them, with a timeout per alternative.
- **Monitored variables:** location variables used by tasks are monitored by the parent goal, as listed in the goal's Text.

### Goal type justifications

| Goal | Justification |
|---|---|
| G1 | The root is an ongoing service. Success depends on running the delivery and retrieval activities, not on one end state. |
| G2, G10, G12 | Each has a clear world state: meal delivered, handed over, or removed from the tray. |
| G3, G13, G21, G25 | These only retrieve information: the order data, who can retrieve the meal (uncertain), what was retrieved, and the pickup demand with the door signal. |
| G4, G5, G6, G7, G8, G9, G11 | Each brings about a state: meals loaded, robot inside the room or at the door, door open, meal on the table. |
| G14 | Indicating the meal is an activity. The description asks only that the robot indicate the meal, not that the person understood. |
| G15–G19 | The state is that the meal is removed from the tray by a specific agent, as the description names the four cooperating agents. |
| G20 | Monitoring is a continuous activity that runs alongside retrieval. |
| G22, G23 | The states are a stored retrieval record and an issued alert when the meal is wrong. |
| G24, G26–G36 | Each has a target state: dishes returned, robot in the room, door open, dishes on the tray. |

## Design rationale for the fallback orders

- **Door opening (G7, G28):** another robot is tried before a human, to avoid interrupting people. In pickup (G28), the caller is tried first, because they may have signaled they can open the door. If no signal was given, G29 is skipped by its context condition.
- **Hand over (G10):** table delivery is tried first because it needs no human availability, which is uncertain. Tray retrieval is the fallback when no manipulation-capable robot is available or the placement fails.
- **Tray retrieval (G15):** the order is inpatient, companion, another robot, then nurse, to spare nurse time. The confidence values from G13 decide which alternatives are attempted, and each has a timeout before the next.
- **Dish collection (G32):** the unassisted mode is tried first. Two-robot and robot-human cooperation follow, in order of increasing dependence on humans.
