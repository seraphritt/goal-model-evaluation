## 1. Visible decomposition rationale

The mission has two major service intentions:

1. **Deliver food from the kitchen to an inpatient room**, triggered order-by-order by kitchen delivery requests Texto colado.  
2. **Retrieve dirty dishes from the room**, possibly after someone in the room calls a robot and signals whether they can open the door Texto colado.

I model delivery and dirty-dish retrieval as an **AND decomposition** of the overall service because the description says the system should both deliver food and retrieve dirty dishes. I use a **sequential runtime** at the top level because dirty dishes logically become available after meal delivery in the described lifecycle.

For food delivery, the main alternatives are:

- Robot places food on the room table, requiring special manipulation skill.
- Food is fetched from the robot tray through cooperation with an inpatient, companion, nurse, or another robot Texto colado.

I model those as an **OR decomposition**, not fallback, because the description gives alternatives but does not explicitly say one must be attempted first and the other only after failure.

## 6. Note on FALLBACK

I did **not** use `FALLBACK(...)` because the mission description gives alternatives but does not explicitly define a required attempt order such as “try tray retrieval first, then table placement if it fails.” The provided definition says fallback should be used only when an explicit ordered alternative is specified by the mission description Texto colado.
