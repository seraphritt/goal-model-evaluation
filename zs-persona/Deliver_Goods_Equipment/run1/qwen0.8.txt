### Goal Model: Multi-Robot Logistics Mission

| Name | Text | Runtime | Goal Type | Relation |
| :--- | :--- | :--- | :--- | :--- |
| **G1: Execute Logistics Mission** | Manage the overall mission of collecting and delivering resources using multi-robot coordination. | `#` | Achieve | AND |
| **G2: Collect Resources** | Navigate to storage, request, and retrieve the required resources. | `-` | Perform | AND |
| **G3: Deliver Resources** | Check battery status and deliver resources to the requesting agent. | `FALLBACK(AT4, G4)` | Perform | AND |
| **AT1: Navigate to Storage** | Move the robot from current location to the storage facility. | - | - | AND |
| **AT2: Request Resource** | Send message to storage specifying the requested resources and wait. | - | - | AND |
| **AT3: Retrieve Resource** | Wait for resources to be retrieved from storage. | - | - | AND |
| **AT4: Deliver Resource** | Move resources to the specified agent location. | - | - | AND |
| **G4: Battery Check** | Verify if the assigned robot's battery is low during delivery phase. | `-` | Perform | OR |
| **G5: Recharge Station** | Robot returns to recharge station if battery is low (10%) in collection phase. | `-` | Perform | AND |
| **G6: Checkpoint Handover** | Robot returns resource to checkpoint if battery is low (30%) in delivery phase. | `-` | Perform | AND |
| **AT5: Send Alert** | Trigger alert and report to sector manager in case of failure. | - | - | OR |
| **AT6: Assign New Robot** | Assign the remaining task to another robot if current robot needs recharge/handover. | - | - | AND |

### Logical Relationships

The goal model follows a hierarchical structure where the root goal **G1** decomposes into the primary mission phases **G2** (Collection) and **G3** (Delivery) using an **AND** decomposition, as both must be fulfilled.

*   **G1 -> G2, G3 [AND;]**
    *   *Explanation:* The overall mission requires both the collection phase and the delivery phase to be completed. Parallelism (`#`) is applied at the top level to handle multiple independent requests as described in the mission ("multiple robots can be assigned... to parallel collect-deliver tasks").

*   **G2 -> AT1, AT2, AT3 [AND]**
    *   *Explanation:* The collection phase requires the robot to sequentially navigate (`AT1`), request (`AT2`), and retrieve (`AT3`) the resources. All these tasks must be completed for the collection goal to be fulfilled.

*   **G3 -> AT4, G4 [AND]**
    *   *Explanation:* The delivery phase involves delivering the resource (`AT4`) and checking the battery status (`G4`). These are sequential steps in the delivery workflow.

*   **G4 -> G5, G6 [FALLBACK(...)]**
    *   *Explanation:* The battery check goal decomposes based on the specific battery level.
    *   *Runtime:* `FALLBACK(G5, G6)` (This implies a binary choice: if battery < 10% in collection phase -> `G5` context, if battery < 30% in delivery phase -> `G6` context). Since the description distinguishes between 10% (Collection) and 30% (Delivery), we model this as a fallback to specific exception handling goals. Note: In a strict tree for a single mission instance, this is an OR/Fallback split.
    *   *Correction for Logic:* Since `G4` is a Perform goal, it must decompose. The failure modes (Low Battery) trigger specific sub-goals.
    *   *Logic:* `G4 -> G5` (Recharge), `G6` (Handover).
    *   *Runtime:* `FALLBACK(G5, G6)` is appropriate if the path depends on the condition. However, for the table structure, we will define `G4` as an OR decomposition leading to `G5` and `G6` which are handled via specific fallback logic in the text.
    *   *Refined Runtime:* `FALLBACK(AtDeliver, G5)` is not possible if `G4` is the check.
    *   *Revised Structure:* `G3` Runtime: `FALLBACK(AT4, G4)`. `G4` Runtime: `FALLBACK(G5, G6)`.
    *   *Wait, `G5` and `G6` are Goals.*
    *   *Relation:* `G4` decomposes into `G5` (Recharge) and `G6` (Handover) via `FALLBACK`.
    *   *Wait, `G5` and `G6` must be tasks or goals.* They are goals.
    *   *Actually, `G5` and `G6` are Perform Goals representing the state where the robot goes to recharge or checkpoint.*
    *   *Task `AT5` (Send Alert)* is a child of a Failure Goal (not explicitly numbered here for brevity, but included in summary).
    *   *Let's assume `G4` -> `G5`, `G6` [OR] with `FALLBACK` notation.*

*   **Task Relations:**
    *   **AT1 -> AT2 -> AT3**: Sequential tasks (AND).
    *   **AT4**: Leaf task (AND).
    *   **G5**: Leaf Goal (AND/OR for sub-actions).
    *   **AT6**: Leaf Task (AND).

### Logical Relationships Explanation

1.  **G1 -> G2, G3 [AND]**: The main mission requires both collecting and delivering resources. The `#` runtime at the top level indicates that if multiple requests are pending, these sub-missions (`G2`, `G3`) can be executed in parallel across the fleet.
2.  **G2 -> AT1, AT2, AT3 [AND]**: The collection phase is a sequence of actions. The robot must navigate (`AT1`), request (`AT2`), and then retrieve (`AT3`). All must succeed.
3.  **G3 -> AT4, G4 [AND]**: The delivery phase must attempt to deliver (`AT4`) and simultaneously check battery (`G4`). If `AT4` fails or battery is low, `G4` handles the exception.
4.  **G4 -> G5, G6 [FALLBACK(...)]**: The battery check goal triggers a fallback. If battery is critical, the robot executes `G5` (Recharge) or `G6` (Handover). The `FALLBACK` operator is used because the execution path depends on the battery condition (10% vs 30%).
5.  **AT5 -> G7 [OR]**: If the checkpoint handover fails, the system triggers `AT5` (Alert). This is an alternative path to the main delivery flow.
6.  **G5 -> AT7 [AND]**: The recharge goal requires the robot to go to the Recharging Station (`AT7`).
7.  **G6 -> AT8 [AND]**: The handover goal requires the robot to return the resource to the Checkpoint (`AT8`).
