**Key Design Choices**

* **Sequential vs. Parallel** – Collection and delivery must happen in sequence; within collection, ordering, navigation, request, wait, and pick‑up must also happen sequentially. Low‑battery handling is performed only when the battery threshold is breached; therefore, it is represented as a subgoal with a linear sequence (return, delegate).  
* **Parallel Execution** – When multiple items are required, the robot can assign parallel collect‑deliver tasks. This is modeled by a separate parallel goal (`G18` with runtime `#`), but for brevity the model shows a single run.  
* **Fallback** – Low‑battery delivery includes a fallback: attempt to return to checkpoint; if that fails, send an alert. This is captured by the sequential decomposition of `G5` (return → delegate → alert).  
* **Task Granularity** – Each concrete action (navigate, request, wait, pick‑up, charge, delegate, alert, deliver, multiple runs) is a single task. Tasks are atomic and have a single robot.  
* **Goal Types** – All goals are **Achieve** (except the low‑battery handling which is **Perform** because it only requires execution of actions, not a state change).  

The resulting goal–task hierarchy fully captures the mission requirements and provides a clear structure for multi‑robot planning and coordination.


A goal model is a modeling structure which consists in the hierarchical decompositionof goals into sub-goals and tasks, using a tree structure. There are two types of decompositions which are the (i)OR decomposition, where the fulfillment of one child is sufficient for the fulfillment of theparent, and the (ii) AND decomposition, where all childs need to be fulfilled in order forthe parent to be fulfilled.

Query Goal Syntax

Query goals use QueriedProperty.

The syntax is:

collection->select(variable:Type | condition)

or:

world_db->select(variable:Type | condition)

The instructions define the select form as:

c->select(x : xt | φ)

where c is the queried collection or world_db, x is the query variable, xt is the type, and φ is the condition. The result is assigned to the first variable in Controls. It is important to note that the condition φ can be empty, which means that no condition is required and that the first variable in the controlled variables list will be instantiated with the result of the query operation. φ must be a atribute present on the world knowledge.

Example

G2,,M1,Find Requesting Agents,Identify all agents that currently request equipment.,istar.Goal,-,AND,Query,world_db->select(a:Agent | a.requesting_equipment),,requesting_agents : Sequence(Agent),,,,True,True,54,209,,The mission starts only when agents require resources, so the system must query the world knowledge first.

Achieve Goal Syntax

Achieve goals use AchieveCondition.

There are two forms:

Normal Achieve Condition

condition

Example:

current_object.retrieved

Universal Achieve Condition

collection->forAll(variable:Type | condition)

The instructions define the universal form as:

c->forAll(x : xt | φ)

The collection c must already be available through Monitors, and the iteration variable x should be declared in Controls. Universal achieve goals can expand the goal model into multiple child instances based on world knowledge. It is important to note that the condition φ can be empty, which means that no condition is required. φ must be a atribute present on the world knowledge.

Example

G3,,M1,Process Requesting Agents,For each requesting agent collect and deliver the requested resources.,istar.Goal,G4;G5;G6;G11,AND,Achieve,,requesting_agents->forAll(current_agent:Agent | ),current_agent : Agent,requesting_agents,,,False,True,666,199,,The mission must be completed for every agent requesting equipment.

4. Relationship Table

Brief Description

The Relationship Table is necessary for parsing because it explicitly stores the tree structure.

The goal table and task table define nodes.The relationship table defines edges.

{
  "id": "link_uuid",
  "type": "istar.AndRefinementLink",
  "source": "child_uuid",
  "target": "parent_uuid"
}

Important:

source = child node
target = parent node

Relationship Syntax

AND Relationship

OR Relationship

R10,,M1,G20,G21,Goal,istar.OrRefinementLink,OR,#,parallel,1,,,,True,True,Either available storage may satisfy the resource request.

Fallback Relationship

Use when the mission has a normal path and recovery path.

R7,,M1,G6,G7,Goal,istar.AndRefinementLink,AND,FALLBACK,fallback,1,FB1,,False,True,True,The normal path is to retrieve requested objects.

Even if the JSON link type is istar.AndRefinementLink, the relationship table should still keep runtime_operator = FALLBACK, because piStar links alone do not fully preserve runtime behavior.

6. Recommended Final Output Structure

For the parser, the model output should always be organized like this:

ACTOR_TABLE
GOAL_TABLE
TASK_TABLE
RELATIONSHIP_TABLE
LOGICAL_RELATIONSHIPS
SUMMARY_TABLE

The first four tables are parser-friendly.The Logical Relationships and Summary are human-readable explanations.

7. Logical Relationship Syntax

Use this syntax after the tables:

Parent -> Child1, Child2, Child3 [AND/OR][parallel/sequential/FALLBACK(...)]
- Justification: ...

Examples:

G1 -> G2, G3 [AND][sequential]
- Justification: The mission first needs to identify the agents requesting resources, then collect and deliver the requested resources.

G3 -> G4, G5, G6, G11 [AND][sequential with partial parallelism]
- Justification: For each requesting agent, the robot system must know the requested objects, know the delivery location, retrieve the objects, and deliver them.

G6 -> G7, G10 [AND][FALLBACK(G7,G10)]
- Justification: The normal collection path is to retrieve the objects. If the battery becomes low during collection, the fallback behavior is to recharge or transfer the mission.

G9 -> AT1 [AND][sequential]
- Justification: The intentional goal “Get Object” is operationalized by the executable HDDL task GetObject.
