### Modeling rationale

The mission naturally decomposes into four major phases: mission preparation, robot assignment, collection, and delivery. Recovery behavior is modeled with `FALLBACK(...)` because the description gives explicit contingency rules for low battery and checkpoint-return failure. Parallel execution `#` is used only where the description explicitly allows multiple robots to execute collect-deliver tasks in parallel. Sequential execution `;` is used where the mission text indicates an ordered process: go to storage, request resources, wait, retrieve, then deliver.

## Logical relationships

- **G1 -> G2, G5, G6, G9, G13 [AND][sequential `;`]**  
  **Justification:** The mission requires preparation, assignment, collection, delivery, and, when applicable, time-reduction through parallelization. The phases are sequential because resources must be identified and collected before they can be delivered.

- **G2 -> G3, G4 [AND][sequential `;`]**  
  **Justification:** The robot must know both the request details and the storage visit order. These are not alternatives; both are necessary inputs for execution.

- **G3 -> AT1 [AND]**  
  **Justification:** Reading the mission request is the concrete operation that provides the queried information: resources, requesting agent, and delivery location.

- **G4 -> AT2 [AND]**  
  **Justification:** Computing storage order using waiting time plus travel path directly implements the described planning rule.

- **G5 -> AT3, AT4 [OR][FALLBACK(AT3, AT4)]**  
  **Justification:** The mission can be assigned to one robot or, when multiple items from different storages are involved, to multiple robots. Only one assignment strategy is needed for a given execution context, so the decomposition is OR.

- **G6 -> G7, G8 [OR][FALLBACK(G7, G8)]**  
  **Justification:** Normal collection is attempted first. If battery reaches 10% during collection, the low-battery recovery branch is used. This is a fallback structure because the second branch is activated only under the low-battery condition.

- **G7 -> AT5, AT6, AT7 [AND][sequential `;`]**  
  **Justification:** The robot must first navigate to storage, then send the request message, then wait until the resources are retrieved. All three steps are required and ordered.

- **G8 -> AT8, AT9 [AND][sequential `;`]**  
  **Justification:** During collection low battery, the robot first goes to the recharging station and then transfers the mission to another robot. Both actions are mandatory.

- **G9 -> G10, G11, G12 [OR][FALLBACK(G10, FALLBACK(G11, G12))]**  
  **Justification:** Normal delivery is preferred. If battery reaches 30%, checkpoint handoff is used. If checkpoint return fails, alert/report handling is activated. These branches are conditional alternatives.

- **G10 -> AT10, AT11 [AND][sequential `;`]**  
  **Justification:** Delivery requires making all necessary runs and then confirming that the resources arrived at the specified location. Completion depends on both steps.

- **G11 -> AT12, AT13 [AND][sequential `;`]**  
  **Justification:** The robot must return the resource to a checkpoint and then assign the remaining task to another robot that knows the resource position. These actions must occur in order.

- **G12 -> AT14, AT15 [AND][sequential `;`]**  
  **Justification:** In checkpoint-return failure, the mission requires both an alert and a report to the sector manager. Neither action alone fully satisfies the failure-handling requirement.

- **G13 -> AT16 [AND][parallel `#`]**  
  **Justification:** Parallel execution is explicitly justified by the statement that multiple robots can be assigned to parallel collect-deliver tasks to reduce mission completion time.
