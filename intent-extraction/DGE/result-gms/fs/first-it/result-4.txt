Below is a **goal-model-oriented decomposition** of the mission. I treat the battery rules as **exception-handling goals**, and I treat the “multiple robots can be assigned” sentence as an **OR alternative** to the single-robot strategy, preferably used when there are multiple items from different storages.

## Modeling reflections and assumptions

| Design choice | Rationale |
|---|---|
| The root mission is modeled as an **Achieve Goal** | The mission aims to bring about a final world state: required resources are delivered to the requesting agent at the specified location. |
| Request interpretation and route/order calculation are modeled as **Query Goals** | They mainly obtain or compute information: required resources, storages, destination, waiting times, and paths. |
| Collection and delivery are modeled as **Perform/Achieve Goals** | They involve concrete robot activities, but also target world states such as “resources retrieved” and “resources delivered.” |
| Battery management is modeled with **FALLBACK** | The mission gives explicit exceptional alternatives when battery thresholds are reached. |
| Multi-robot execution is modeled as an **OR alternative** to single-robot execution | The text says multiple robots “can be assigned” when multiple items are required from different storages. Therefore, it is optional/conditional, not always mandatory. |
| Parallel runtime `#` is used for multi-robot tasks and battery monitoring | Parallel robots can collect/deliver simultaneously; battery monitoring must conceptually occur while collection or delivery is being performed. |
| Sequential runtime `;` is used for request → planning → execution and for navigation → request → wait | The mission explicitly describes ordered phases and ordered actions. |

| **G3: Define Collection Plan** | Define the order in which storage locations should be visited. | `;` | Query | **Enquired information:** ordered list of storages based on waiting-time estimation plus robot path cost. | AND under G1 | The description states that the order is defined by estimated waiting time summed with the path to be run. | **G4: Estimate Storage Waiting Times** | Estimate the waiting time associated with requesting resources from each storage. | `;` | Query | **Enquired information:** expected waiting time for each storage location. | AND under G3 | Waiting time is explicitly part of the ordering criterion, so it must be obtained or estimated before ordering storages. |

| **G6: Execute Resource Transport Strategy** | Execute a strategy that collects and delivers the required resources. | `FALLBACK(G7,G10)` | Achieve | **Target condition:** resources are collected and delivered through either parallel multi-robot execution or single-robot execution. | OR under G1 | The mission may be executed by multiple robots when there are multiple items from different storages; otherwise, a single assigned robot can perform the mission. | **G9: Run Parallel Collect-Deliver Tasks** | Execute the assigned collect-deliver subtasks in parallel. | `#` | Perform | Activities performed: multiple robots execute assigned collection and delivery subtasks. | AND under G7 | The mission explicitly mentions “parallel collect-deliver tasks,” so this goal captures simultaneous execution. |
| **G10: Single-Robot Strategy** | Use one assigned robot to collect required resources and deliver them to the specified location. | `;` | Achieve | **Target condition:** one assigned robot completes collection and delivery, unless handover is required. | OR under G6 | This is the normal strategy implied by “a robot must collect … and deliver.” Collection must precede delivery, so runtime is sequential. |
| **G11: Collection Phase** | Collect the required resources from storage locations. | `#` | Achieve | **Target condition:** required resources have been retrieved from storage. | AND under G10 | The description explicitly names the collection phase. | **G12: Retrieve Resources From Storage** | Visit storage locations, request the resources, and wait until they are retrieved. | `;` | Achieve | **Target condition:** requested resources have been retrieved from storage. | AND under G11 | The text states that the robot goes to storage, sends a message, and waits until resources have been retrieved. These are ordered steps. |
| **G13: Preserve Collection Continuity** | Ensure the mission can continue if the assigned robot has low battery during collection. | `FALLBACK(G14,G15)` | Achieve | **Target condition:** collection continues either with the current robot or through reassignment. | AND under G11 | The mission gives a contingency for collection battery low at 10%. The fallback models normal continuation first, then handover when low battery occurs. |
| **G14: Continue Collection Normally** | Continue the collection phase with the currently assigned robot. | `-` | Achieve | **Target condition:** assigned robot remains able to continue collection, with battery above the low-battery threshold or no low-battery event detected. | OR under G13 | If the robot battery is not low during collection, no reassignment is needed. This is one sufficient way to preserve collection continuity. |
| **G15: Handover Collection On Low Battery** | Return the robot to the recharging station and assign the mission to another robot. | `;` | Perform | Activities performed: go to recharging station and reassign the mission. | OR under G13 | The text explicitly states that if battery reaches 10% in collection, the robot goes back to the recharging station and assigns the mission to another robot. |
| **G16: Delivery Phase** | Deliver all retrieved resources to the specified location. | `#` | Achieve | **Target condition:** all resources are delivered to the specified location or a recovery procedure is activated if battery becomes low. | AND under G10 | The delivery phase starts once resources are retrieved. Delivery activity and battery monitoring occur during this phase. |
| **G17: Deliver All Resources** | Make as many runs as necessary to take all resources to the specified location. | `;` | Achieve | **Target condition:** all required resources are at the specified location. | AND under G16 | The mission explicitly says the robot will make as many runs as necessary to take all resources to the specified location. |
| **G18: Preserve Delivery Continuity** | Ensure the delivery phase can continue or be safely transferred if battery becomes low. | `FALLBACK(G19,G20)` | Achieve | **Target condition:** delivery continues with the current robot or the remaining task is transferred safely. | AND under G16 | The mission gives a 30% battery threshold during delivery and defines a recovery behavior. |
| **G19: Continue Delivery Normally** | Continue delivery with the currently assigned robot. | `-` | Achieve | **Target condition:** assigned robot remains able to continue delivery, with battery above 30% or no low-battery event detected. | OR under G18 | If the robot battery is not low during delivery, the current robot can keep delivering. |
| **G20: Handle Delivery Low Battery** | Handle the case where the robot battery reaches 30% during delivery. | `FALLBACK(G21,G22)` | Perform | Activities performed: checkpoint recovery, or escalation if checkpoint recovery fails. | OR under G18 | The mission states that low battery in delivery requires returning the resource to a checkpoint and assigning the task to another robot; if this fails, alert/report is required. |
| **G21: Recover Through Checkpoint** | Return the resource to a checkpoint and transfer the remaining task to another robot that knows the resource position. | `;` | Achieve | **Target condition:** resource is safely positioned at a checkpoint and another robot has the remaining task and resource location. | OR under G20 | This is the primary recovery behavior described for low battery during delivery. It must happen before another robot can continue. |
| **G22: Escalate Checkpoint Return Failure** | Trigger an alert and send a report to the sector manager if the resource cannot be returned to a checkpoint. | `;` | Perform | Activities performed: alert triggered and report sent. | OR under G20 | This is the specified fallback when checkpoint return fails. It does not complete delivery, but it satisfies the required failure-handling protocol. |

# Logical Relationships

- **G1 -> G2, G3, G6 [AND][sequential `;`]**  
  **Justification:** The robot must first understand the request, then plan the collection order, then execute the transport mission. All three are necessary.

- **G2 -> AT1, AT2 [AND][sequential `;`]**  
  **Justification:** The mission request must be received before its parameters can be extracted.

- **G3 -> G4, G5, AT5 [AND][sequential `;`]**  
  **Justification:** The storage order depends on both estimated waiting time and robot path cost. Once both are known, the order can be selected.

- **G4 -> AT3 [AND][sequential `;`]**  
  **Justification:** Estimating waiting time is required because the description explicitly uses waiting time in ordering storages.

- **G5 -> AT4 [AND][sequential `;`]**  
  **Justification:** Estimating path cost is required because the description explicitly uses the robot path in ordering storages.

- **G6 -> G7, G10 [OR][FALLBACK(G7,G10)]**  
  **Justification:** The mission can be executed by multiple robots when multiple items from different storages exist, but the normal description also supports a single assigned robot. One execution strategy is sufficient. Parallel execution is preferred when applicable because the text says it reduces mission completion time.

- **G7 -> G8, G9 [AND][parallel `#`]**  
  **Justification:** Preparing parallel work and running parallel subtasks are both part of the multi-robot strategy. The runtime is parallel because several robots may operate simultaneously.

- **G8 -> AT6, AT7 [AND][sequential `;`]**  
  **Justification:** The system must first identify independent multi-storage items before building task bundles.

- **G9 -> AT8, AT9 [AND][parallel `#`]**  
  **Justification:** Multiple robots are assigned and then execute collect-deliver subtasks concurrently to reduce total mission time.

- **G10 -> G11, G16 [AND][sequential `;`]**  
  **Justification:** The description says that once resources are retrieved, the delivery phase begins. Therefore, collection precedes delivery.

- **G11 -> G12, G13 [AND][parallel `#`]**  
  **Justification:** Resource retrieval is the main collection activity, while low-battery continuity must be monitored during collection.

- **G12 -> AT10, AT11, AT12 [AND][sequential `;`]**  
  **Justification:** The robot first goes to storage, then sends the resource request message, then waits for retrieval.

- **G13 -> G14, G15 [OR][FALLBACK(G14,G15)]**  
  **Justification:** If the robot battery remains sufficient, collection continues normally. If it reaches 10%, the mission falls back to recharging and reassignment.

- **G15 -> AT13, AT14 [AND][sequential `;`]**  
  **Justification:** The robot must go to the recharging station and assign the mission to another robot. Both actions are required by the description.

- **G16 -> G17, G18 [AND][parallel `#`]**  
  **Justification:** Delivery must be performed while battery-related delivery continuity is monitored.

- **G17 -> AT15, AT16 [AND][sequential `;`]**  
  **Justification:** The robot performs as many delivery runs as necessary before the resources can be considered delivered to the requesting agent.

- **G18 -> G19, G20 [OR][FALLBACK(G19,G20)]**  
  **Justification:** If the battery remains above the delivery threshold, the robot continues normally. If battery reaches 30%, the low-battery handling procedure is triggered.

- **G20 -> G21, G22 [OR][FALLBACK(G21,G22)]**  
  **Justification:** The primary delivery recovery is to return the resource to a checkpoint and reassign the task. If that fails, the fallback is alerting and reporting.

- **G21 -> AT17, AT18, AT19 [AND][sequential `;`]**  
  **Justification:** The resource must first be placed at the checkpoint, then the remaining task assigned, and the new robot must know the resource position.

- **G22 -> AT20, AT21 [AND][sequential `;`]**  
  **Justification:** In case of checkpoint-return failure, the mission requires both an alert and a report to the sector manager.
