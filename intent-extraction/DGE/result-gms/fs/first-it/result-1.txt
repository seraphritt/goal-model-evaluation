### Modeling rationale

I treat the mission as a **resource logistics mission in a hospital-like multi-robot system**. The central desired world state is: **the requested resources are available to the requesting agent at the specified location**. The mission has three main parts: assignment/planning, collection, and delivery. Battery-related behavior is modeled as **fallback behavior**, because it is only activated when the normal execution path cannot continue safely.

## Logical relationships

- **G1 -> G2, G5, G9 [AND][sequential ;]**  
  - **Justification:** The complete mission requires assignment/preparation, then collection, then delivery. The text describes collection before delivery: “Once retrieved, the delivery phase begins.”

- **G2 -> G3, G4 [AND][sequential ;]**  
  - **Justification:** The system must first identify what resources, storages, requesting agent, and destination are involved. Only then can it assign one robot or multiple robots.

- **G4 -> AT1, AT2 [OR][FALLBACK(AT1, AT2)]**  
  - **Justification:** The mission may be executed by multiple robots when there are multiple items from different storages, but a single robot can also execute the mission. One assignment strategy is enough. Parallel assignment is modeled first because the description says it can reduce mission completion time.

- **G5 -> G6, G7, G8 [OR][FALLBACK((G6 ; G7), G8)]**  
  - **Justification:** The normal collection path requires ordering storages and retrieving resources. If the robot battery reaches 10% during collection, the fallback behavior is activated: go to recharge and assign the mission to another robot.

- **G6 -> AT3, AT4, AT5 [AND][sequential ;]**  
  - **Justification:** Storage ordering depends on both waiting time and path estimation. After both are estimated, the system computes the order.

- **G7 -> AT6, AT7, AT8 [AND][sequential ;]**  
  - **Justification:** The robot must first go to the storage, then request the resources, then wait for retrieval. These steps are all mandatory and naturally sequential.

- **G8 -> AT9, AT10 [AND][sequential ;]**  
  - **Justification:** During collection low-battery recovery, the robot must go to the recharging station and assign the mission to another robot. Both actions are required.

- **G9 -> G10, G11 [OR][FALLBACK(G10, G11)]**  
  - **Justification:** The preferred delivery behavior is to complete the necessary delivery runs. If battery reaches 30% during delivery, the checkpoint-based fallback is used.

- **G10 -> AT11 [AND][sequential ;]**  
  - **Justification:** Delivery is operationalized by making as many runs as necessary to transport all resources to the specified location.

- **G11 -> AT12, AT13, G12 [OR][FALLBACK((AT12 ; AT13), G12)]**  
  - **Justification:** The preferred low-battery delivery recovery is to return the resource to a checkpoint and assign the remaining task to another robot. If returning to the checkpoint fails, escalation through G12 is required.

- **G12 -> AT14, AT15 [AND][sequential ;]**  
  - **Justification:** In the failure case, both an alert and a report are required. The alert informs the system immediately, while the report informs the sector manager.

- **AT1 enables parallel instances of G5 and G9 [AND][parallel #]**  
  - **Justification:** When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks. Each robot may execute its own collection and delivery branch, reducing total mission time.

- **AT12 -> AT13 [AND][sequential ;]**  
  - **Justification:** The remaining task can only be reassigned effectively after the resource has been placed at a known checkpoint, because the replacement robot must know where the resource is positioned.

- **AT14 -> AT15 [AND][sequential ;]**  
  - **Justification:** After the checkpoint return failure is detected, the system first triggers an alert and then sends a report to the sector manager. Both are mandatory escalation actions.
