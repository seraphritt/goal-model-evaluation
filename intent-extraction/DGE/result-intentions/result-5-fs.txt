## Goal Model — Goals

| Name | Text | Runtime | Goal Type | Target Condition / Enquired Information | Relation | Justification |
|---|---|---:|---|---|---|---|
| **G1: Fulfill Resource Delivery Request** | The mission is fulfilled when the required resources are collected from storage and delivered to the requesting agent at the specified location. | `[;]` | Achieve | **Target:** all required resources are delivered to the requesting agent at the specified location. | AND | The request can only be fulfilled if the mission is first planned and then executed. The description says the robot must collect and deliver the requested resources, so both parts are mandatory. Sequential runtime is used because execution depends on knowing what, where, and how to collect first. |
| **G2: Plan Resource Collection** | Determine what resources are required, where they are stored, and the order in which storage places should be visited. | `[;]` | Query | **Enquired information:** requested resources, storage locations, waiting-time estimates, path estimates, visit order. | AND | This is a query goal because it gathers information needed to execute the mission. The description states that storage places must be found and the order is defined by waiting time plus robot path. All planning information is required before collection. |
| **G3: Execute Resource Logistics Strategy** | Execute the collect-deliver mission using either a standard assigned-robot strategy or a parallel multi-robot strategy. | `FALLBACK(G17,G4)` | Achieve | **Target:** the required resources are collected and delivered using an applicable execution strategy. | OR | The mission may be executed by one assigned robot or, when multiple items are required from different storages, by multiple robots in parallel. OR is used because either strategy can fulfill the logistics mission. Fallback is used because the parallel strategy is preferable when applicable for reducing completion time, but the standard flow remains valid otherwise. |
| **G4: Execute Standard Assigned-Robot Flow** | Execute the mission with an assigned robot that collects resources and then delivers them. | `[;]` | Achieve | **Target:** the assigned robot completes collection before delivery. | AND | Collection and delivery are both required. Sequential runtime is necessary because the description explicitly says the delivery phase begins once the resources are retrieved. |
| **G5: Collect Required Resources** | Collect the required resources from the storage places where they can be found. | `FALLBACK(G6,G7)` | Achieve | **Target:** all required resources are retrieved from storage. | OR | Nominal collection is attempted first. If the battery becomes low during collection, the collection battery handover branch is used. OR is appropriate because the collection goal can be satisfied either by normal collection or by transferring the mission to another robot after recovery. |
| **G6: Perform Nominal Collection** | The robot visits the ordered storage locations, requests the resources, and waits until they are retrieved. | `[;]` | Perform | — | AND | This is a perform goal because it consists of concrete activities: navigating to storage, sending a request message, and waiting. AND is used because all these steps are necessary to complete nominal collection. Sequential runtime follows the description: first go to storage, then request, then wait. |
| **G7: Handle Collection Low Battery** | Handle the case where the assigned robot battery reaches the low threshold during collection. | `[;]` | Achieve | **Target:** the low-battery robot stops collection safely, goes to recharge, and another robot receives the mission. | AND | The description states that if the battery runs low at 10% in the collection phase, the robot goes to the recharging station and assigns the mission to another robot. These actions are both required and must occur in sequence. |
| **G8: Check Collection Battery Level** | Check whether the robot battery is low during the collection phase. | `[;]` | Query | **Enquired information:** collection-phase battery percentage, especially whether it is at or below 10%. | AND | This is a query goal because it retrieves monitored information. The 10% threshold is explicitly used in the description to decide whether the collection handover must occur. |
| **G9: Transfer Collection Mission** | Transfer the unfinished collection mission to another robot after the assigned robot returns to recharge. | `[;]` | Perform | — | AND | This is a perform goal because it specifies concrete recovery actions. The robot must go to the recharging station and assign the mission to another robot. Both actions are required. |
| **G10: Deliver Retrieved Resources** | Deliver all retrieved resources to the specified location. | `FALLBACK(G11,G12)` | Achieve | **Target:** all retrieved resources are delivered to the requesting agent’s specified location. | OR | Nominal delivery is attempted first. If battery becomes low during delivery, the recovery branch is used. OR is appropriate because delivery can be completed either normally or through a checkpoint handover to another robot. |
| **G11: Perform Nominal Delivery Runs** | Transport the retrieved resources to the specified location, making as many runs as necessary. | `[;]` | Perform | — | AND | This is a perform goal because it describes concrete delivery actions. The description says the robot will make as many runs as necessary, so repeated transportation is required until all resources are delivered. |
| **G12: Handle Delivery Low Battery** | Handle the case where the assigned robot battery reaches the low threshold during the delivery phase. | `[;]` | Achieve | **Target:** the resource is safely handled and the remaining delivery task is either transferred or escalated. | AND | The robot must first detect the delivery-phase battery condition and then execute the appropriate contingency. Sequential execution is used because the contingency depends on the battery state. |
| **G13: Check Delivery Battery Level** | Check whether the robot battery is low during the delivery phase. | `[;]` | Query | **Enquired information:** delivery-phase battery percentage, especially whether it is at or below 30%. | AND | This is a query goal because it retrieves battery-status information. The description explicitly defines 30% as the delivery-phase threshold for returning the resource to a checkpoint. |
| **G14: Resolve Delivery Battery Contingency** | Resolve the delivery low-battery case either by successfully using a checkpoint or by escalating if checkpoint return fails. | `FALLBACK(G15,G16)` | Achieve | **Target:** the delivery contingency is resolved through checkpoint handover or failure escalation. | OR | The preferred recovery is to return the resource to a checkpoint and assign the remaining task to another robot. If that fails, alerting and reporting are required. OR and fallback capture this conditional alternative. |
| **G15: Perform Checkpoint Handover** | Return the resource to a checkpoint and transfer the remaining task to another robot that knows the resource position. | `[;]` | Perform | — | AND | This is a perform goal because it contains concrete recovery actions. The resource must be placed at a checkpoint, the remaining task must be assigned, and the new robot must know where the resource is positioned. |
| **G16: Escalate Checkpoint Failure** | Trigger an alert and send a report to the sector manager if the robot fails to return the resource to a checkpoint. | `[;]` | Perform | — | AND | The description states that, in case of failure to return the resource to a checkpoint, an alert must be triggered and a report sent to the sector manager. Both actions are mandatory. |
| **G17: Execute Parallel Multi-Robot Flow** | Assign multiple robots to parallel collect-deliver tasks when multiple items are required from different storages. | `[#]` | Achieve | **Target:** multiple collect-deliver subtasks are executed in parallel to reduce mission completion time. | AND | This goal exists because the description states that multiple robots can be assigned to parallel collect-deliver tasks. Parallel runtime is used because the purpose is to reduce the total time to finish the mission. |
| **G18: Analyze Parallelization Need** | Determine whether the mission involves multiple items from different storages and whether multiple robots can be assigned. | `[;]` | Query | **Enquired information:** item-to-storage mapping, number of required items, storage distribution, available robots. | AND | This is a query goal because it gathers the information needed to decide whether parallel execution is applicable. The description makes parallelization conditional on multiple items from different storages. |
| **G19: Assign Parallel Collect-Deliver Tasks** | Assign available robots to collect-deliver subtasks and execute those subtasks in parallel. | `[#]` | Perform | — | AND | This is a perform goal because it operationalizes parallel execution. The tasks are concurrent because the description explicitly says multiple robots can be assigned to parallel collect-deliver tasks. |

## Logical Relationships

- **G1 -> G2, G3 [AND][sequential `;`]**  
  - **Justification:** The robot cannot execute the mission before knowing the requested resources, storage locations, delivery location, and ordering criteria. Planning must precede execution.

- **G2 -> AT1, AT2, AT3, AT4 [AND][sequential `;`]**  
  - **Justification:** The mission plan requires all four pieces: request details, storage locations, cost estimation, and final visit order. Missing any of these would make the collection phase underspecified.

- **G3 -> G17, G4 [OR][`FALLBACK(G17,G4)`]**  
  - **Justification:** The mission can be executed using multiple robots in parallel when multiple items from different storages exist. If parallelization is not applicable or not available, the standard assigned-robot flow can still fulfill the mission.

- **G4 -> G5, G10 [AND][sequential `;`]**  
  - **Justification:** The standard mission requires both collecting and delivering. Delivery starts only once the resources have been retrieved, so the runtime is sequential.

- **G5 -> G6, G7 [OR][`FALLBACK(G6,G7)`]**  
  - **Justification:** Nominal collection is the intended path. If the assigned robot reaches the 10% battery threshold during collection, the mission switches to the low-battery handover path.

- **G6 -> AT5, AT6, AT7 [AND][sequential `;`]**  
  - **Justification:** The robot must first reach the storage, then send the precise resource request, then wait for retrieval. These actions form the explicit collection sequence.

- **G7 -> G8, G9 [AND][sequential `;`]**  
  - **Justification:** The low-battery condition must be detected before the recovery behavior is executed. The description defines 10% as the collection-phase trigger.

- **G8 -> AT8 [AND][sequential `;`]**  
  - **Justification:** Battery monitoring is the concrete task that supplies the information required by the low-battery decision.

- **G9 -> AT9, AT10 [AND][sequential `;`]**  
  - **Justification:** The robot must go to the recharging station and assign the mission to another robot. Both are explicitly required by the description.

- **G10 -> G11, G12 [OR][`FALLBACK(G11,G12)`]**  
  - **Justification:** Nominal delivery is attempted when battery is sufficient. If battery reaches the 30% delivery threshold, the delivery recovery path is required.

- **G11 -> AT11, AT12 [AND][sequential `;`]**  
  - **Justification:** The robot transports resources and repeats the delivery runs until all resources are delivered. Repetition is necessary because the description says the robot may need as many runs as necessary.

- **G12 -> G13, G14 [AND][sequential `;`]**  
  - **Justification:** The robot must first identify the delivery-phase low-battery condition, then perform the appropriate contingency action.

- **G13 -> AT13 [AND][sequential `;`]**  
  - **Justification:** Reading the delivery battery percentage supplies the monitored information needed to trigger the 30% recovery procedure.

- **G14 -> G15, G16 [OR][`FALLBACK(G15,G16)`]**  
  - **Justification:** The preferred contingency is checkpoint handover. If returning the resource to a checkpoint fails, the fallback is escalation through alert and report.

- **G15 -> AT14, AT15, AT16 [AND][sequential `;`]**  
  - **Justification:** The resource must be placed at a checkpoint, the remaining task assigned, and the checkpoint position communicated to the replacement robot.

- **G16 -> AT17, AT18 [AND][sequential `;`]**  
  - **Justification:** In case of checkpoint-return failure, both an alert and a report to the sector manager are required.

- **G17 -> G18, G19 [AND][parallel `#`]**  
  - **Justification:** Parallel execution is introduced to reduce mission completion time when multiple items are required from different storages. The analysis of applicability supports the assignment and concurrent execution of robot subtasks.

- **G18 -> AT19, AT20 [AND][sequential `;`]**  
  - **Justification:** The system must know both whether the items are distributed across storages and whether enough robots are available.

- **G19 -> AT21, AT22 [AND][parallel `#`]**  
  - **Justification:** Multiple robots are assigned to different collect-deliver tasks and then execute them concurrently, matching the description’s explicit parallelization option.
