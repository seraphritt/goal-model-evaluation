## 1. Design Rationale

The mission describes a **resource collection and delivery workflow** in a hospital/logistics environment. The mission starts when a request is issued, then the system must identify what resources are needed, where they are stored, how to order the storage visits, which robot or robots should be assigned, and how to execute collection and delivery.

The model must also represent **contingency behavior**. The description gives two explicit battery thresholds:

1. **10% battery during collection**: the robot returns to the recharging station and the mission is assigned to another robot.
2. **30% battery during delivery**: the robot returns the resource to a checkpoint and transfers the remaining delivery to another robot.
3. **Failure to return to checkpoint**: an alert is triggered and a report is sent to the sector manager.

Because the mission says that **multiple robots can be assigned in parallel** when items are required from different storages, the model includes both a **parallel allocation strategy** and a **single-robot allocation strategy**. The preferred strategy is parallel execution when applicable; otherwise, the system falls back to a single-robot mission.

# 5. Logical Relationships

## Top-Level Mission

**G1 -> G2, G3, G9 [AND][sequential (;)]**

* **Justification**: The mission cannot be executed unless the system first acquires mission information, then plans the storage order and robot assignment, and finally executes the collection-delivery jobs. All three are necessary, so the decomposition is AND. The order is sequential because planning depends on request information, and execution depends on the plan.

---

## Mission Information

**G2 -> AT1, AT2, AT3, AT4 [AND][sequential (;)]**

* **Justification**: The system must receive the request, understand the resource specification, identify storages, and know the destination. These pieces of information are all necessary before planning. Therefore, the relation is AND.

---

## Planning

**G3 -> G4, G5, G6 [AND][sequential (;)]**

* **Justification**: The system must first estimate storage visit costs, then order the storage visits, then assign robots. These steps are all required for a valid mission plan, so the decomposition is AND.

---

## Estimating Visit Costs

**G4 -> AT5, AT6 [AND][parallel (#)]**

* **Justification**: Waiting time and path cost are both required to compute the storage order. They can be estimated independently, so the runtime can be parallel.

---

## Ordering Storage Visits

**G5 -> AT7, AT8 [AND][sequential (;)]**

* **Justification**: The robot must first compute the combined priority value `waitingTime + pathCost`, then sort the storages. Both are required, and the second depends on the first.

---

## Robot Allocation

**G6 -> G7, G8 [OR][FALLBACK(G7, G8)]**

* **Justification**: Only one allocation strategy is needed to satisfy the parent goal. Parallel assignment is preferred when multiple resources from different storages allow time reduction. If parallel assignment is not applicable, the system falls back to a single robot.

---

## Parallel Robot Assignment

**G7 -> AT9, AT10 [AND][parallel (#)]**

* **Justification**: The system must split items into storage-based jobs and assign multiple robots to those jobs. The relation is AND because both steps are necessary for parallel execution.

---

## Single-Robot Assignment

**G8 -> AT11, AT12 [AND][sequential (;)]**

* **Justification**: The system must select an available robot and then assign the mission to it. Assignment depends on selection, so the runtime is sequential.

---

## Execution of Collect-Deliver Jobs

**G9 -> G10, G13 [AND][(G10 ; G13) per job, # across jobs]**

* **Justification**: For each assigned job, collection must occur before delivery. However, when multiple robots are assigned, several collect-deliver jobs can execute in parallel to reduce total mission time.

---

## Collection Phase

**G10 -> G11, G12 [OR][FALLBACK(G11, G12)]**

* **Justification**: Normal collection is attempted first. If the robot battery reaches 10% during collection, the mission follows the fallback behavior: return to recharge and reassign the mission.

---

## Normal Collection

**G11 -> AT13, AT14, AT15, AT16 [AND][sequential (;)]**

* **Justification**: The robot must navigate to storage, send the resource request, wait for retrieval, and load/receive the resources. These actions are all required and must occur in order.

---

## Collection Low-Battery Recovery

**G12 -> AT17, AT18, AT19 [AND][sequential (;)]**

* **Justification**: The robot must detect the 10% battery condition, return to the recharging station, and transfer the mission to another robot. These are all mandatory actions in the collection low-battery case.

---

## Delivery Phase

**G13 -> G14, G15 [OR][FALLBACK(G14, G15)]**

* **Justification**: Normal delivery is attempted first. If the robot battery reaches 30% during delivery, the delivery low-battery contingency must be used instead.

---

## Normal Delivery

**G14 -> AT20, AT21, AT22, AT23 [AND][sequential (;)]**

* **Justification**: The robot must determine how many delivery runs are needed, travel to the destination, deliver resources, and repeat until all resources are delivered. All actions are necessary to complete delivery.

---

## Delivery Low-Battery Management

**G15 -> G16, G17 [OR][FALLBACK(G16, G17)]**

* **Justification**: The preferred behavior is to return the resource to a checkpoint and reassign the remaining task. If that fails, the system must trigger an alert and report the failure to the sector manager. Since either recovery path resolves the contingency according to mission rules, the relation is OR.

---

## Checkpoint and Reassignment

**G16 -> AT24, AT25, AT26, AT27 [AND][sequential (;)]**

* **Justification**: The robot must detect the 30% battery condition, move the resource to a checkpoint, register the resource position, and assign the remaining delivery to another robot. These steps must happen in sequence because the replacement robot needs the checkpoint position.

---

## Failure Escalation

**G17 -> AT28, AT29, AT30 [AND][sequential (;)]**

* **Justification**: Failure escalation requires detecting the checkpoint failure, triggering an alert, and sending a report to the sector manager. All three are required by the description, so the decomposition is AND.

---
