## 1. Modeling interpretation and decomposition logic

The mission is a **collect-and-deliver logistics mission** in a multi-robot hospital-like environment. The central objective is not only “move resources,” but to **guarantee that required resources are collected from the correct storage places and delivered to a requesting agent**, while handling ordering, waiting time, battery constraints, checkpoints, replacement robots, and possible escalation to a sector manager.

The main design decisions are:

| Mission evidence                                                                                 | Modeling decision                                                                                                                                         |
| ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| “When required, a robot must collect the required resources…”                                    | The root goal is an **Achieve Goal**, because the desired future state is that the required resources are delivered or the mission is properly escalated. |
| “The order to be followed is defined by the estimation of waiting time summed up with the path…” | Planning is decomposed into **Query Goals** for waiting/path information and an **Achieve Goal** for creating the route/order.                            |
| “Once the robot reaches one storage… sends a message… waits…”                                    | Collection is modeled as a **sequential AND decomposition**: navigate → request → wait/retrieve/load.                                                     |
| “The robot will make as many runs as necessary…”                                                 | Delivery is modeled as an **iterative delivery-run goal**, operationalized by tasks that may repeat until all resources are delivered.                    |
| “If battery… low 10% in collection…”                                                             | Collection has a **FALLBACK**: normal collection first, then low-battery delegation if normal collection cannot continue.                                 |
| “If battery… low 30% in delivery…”                                                               | Delivery has a **FALLBACK**: normal delivery first, then checkpoint handoff and reassignment.                                                             |
| “In case of failure to return… checkpoint, alert…”                                               | The delivery contingency has another **FALLBACK**: checkpoint handoff first, alert/report if checkpoint return fails.                                     |
| “Multiple robots can be assigned to parallel collect-deliver tasks…”                             | The execution goal supports **parallel instances** of the same collect-deliver unit.                                                                      |

# 5. Logical relationships and justifications

## Root mission flow

**G1 -> G2, G3, G10, G33 [AND][sequential ;]**

* **Justification:** The mission must first understand the request, then plan where/how to collect, then execute the collect-deliver assignments, then close the mission record. These are all required, and the order is naturally sequential.

---

## Requirement acquisition

**G2 -> AT1, AT2 [AND][sequential ;]**

* **Justification:** The system must first receive the delivery requirement and then extract the relevant details. Both are mandatory before planning.

---

## Planning phase

**G3 -> G4, G5, G6, G7 [AND][sequential ;]**

* **Justification:** The robot must know where resources are, estimate waiting/path costs, order storage visits, and choose robot allocation. Each planning step depends on information produced by the previous one.

**G4 -> AT3 [AND][sequential ;]**

* **Justification:** Locating resources is operationalized by querying inventory or storage information.

**G5 -> AT4, AT5 [AND][parallel #]**

* **Justification:** Waiting-time estimation and path-cost computation are both necessary, but they can be performed independently and therefore in parallel.

**G6 -> AT6 [AND][sequential ;]**

* **Justification:** The storage order is created by ranking storages using the criterion described in the mission: waiting time plus path.

**G7 -> G9, G8 [OR][FALLBACK(G9,G8)]**

* **Justification:** If multiple resources from different storages exist and robots are available, the preferred strategy is parallel allocation. If that is not applicable, a single robot route is sufficient.

**G8 -> AT7 [AND][sequential ;]**

* **Justification:** A single-robot strategy requires assigning one robot to the whole route.

**G9 -> AT8, AT9 [AND][parallel #]**

* **Justification:** Parallel execution requires splitting the request into bundles and assigning multiple robots. These planning tasks support simultaneous collect-deliver missions.

---

## Execution phase

**G10 -> G11* [AND][parallel #]**

* **Justification:** All assigned collect-deliver units must be completed. When multiple robots are assigned, their units execute in parallel to reduce mission time.

**G11 -> G12, G21 [AND][sequential ;]**

* **Justification:** For each assigned unit, the robot must collect before it can deliver. Therefore, collection precedes delivery.

---

## Collection phase

**G12 -> (G13, G14), G18 [OR][FALLBACK((G13 # G14),G18)]**

* **Justification:** The normal path is to collect resources while monitoring battery. If collection cannot continue because battery reaches 10%, the fallback is to return to recharge and delegate the mission.

**G13 -> AT10 [AND][sequential ;]**

* **Justification:** Battery status must be read during collection to detect the 10% threshold.

**G14 -> G15, G16, G17 [AND][sequential ;]**

* **Justification:** Collection requires ordered navigation to storage, requesting/waiting for retrieval, and securing the retrieved resources.

**G15 -> AT11 [AND][sequential ;]**

* **Justification:** The robot must move to the storage locations in the planned order.

**G16 -> AT12, AT13 [AND][sequential ;]**

* **Justification:** The robot first sends a precise request message, then waits until the resources have been retrieved.

**G17 -> AT14 [AND][sequential ;]**

* **Justification:** Retrieved resources must be loaded or confirmed before delivery begins.

**G18 -> G19, G20 [AND][sequential ;]**

* **Justification:** In collection low-battery handling, the current robot must go to recharge and the mission must be assigned to another robot. Both are required.

**G19 -> AT15 [AND][sequential ;]**

* **Justification:** The robot physically returns to the recharging station.

**G20 -> AT16, AT17 [AND][sequential ;]**

* **Justification:** Delegation requires sending the mission handoff and having the replacement robot accept the context.

---

## Delivery phase

**G21 -> (G22, G23), G27 [OR][FALLBACK((G22 # G23),G27)]**

* **Justification:** The normal delivery path runs while battery is monitored. If battery reaches 30%, the fallback is checkpoint handoff.

**G22 -> AT18 [AND][sequential ;]**

* **Justification:** Battery status must be read during delivery to detect the 30% threshold.

**G23 -> G24, G25, G26 [AND][sequential ;]**

* **Justification:** The robot must determine required runs, transport resources, and transfer them to the requester. All three are necessary for complete delivery.

**G24 -> AT19 [AND][sequential ;]**

* **Justification:** Since the robot may need several runs, the load must be partitioned into delivery runs.

**G25 -> AT20 [AND][sequential ;]**

* **Justification:** Physical transport to the destination is the main operational delivery action.

**G26 -> AT21 [AND][sequential ;]**

* **Justification:** The resources must be unloaded or transferred at the specified delivery location.

---

## Delivery low-battery contingency

**G27 -> G28, G32 [OR][FALLBACK(G28,G32)]**

* **Justification:** The intended contingency is checkpoint handoff. If the robot fails to return the resource to a checkpoint, the fallback is alert and report.

**G28 -> G29, G30, G31 [AND][sequential ;]**

* **Justification:** Checkpoint handoff requires three mandatory actions: place the resource at checkpoint, register its position, and assign the remaining task to another robot.

**G29 -> AT22 [AND][sequential ;]**

* **Justification:** The resource must physically reach a checkpoint.

**G30 -> AT23 [AND][sequential ;]**

* **Justification:** The replacement robot must know where the resource is positioned.

**G31 -> AT24 [AND][sequential ;]**

* **Justification:** The remaining delivery must be assigned to another robot.

**G32 -> AT25, AT26 [AND][sequential ;]**

* **Justification:** If checkpoint return fails, both an alert and a report to the sector manager are required by the mission description.

---

## Mission closing

**G33 -> AT27, AT28 [AND][sequential ;]**

* **Justification:** The system should record the final mission status and notify the relevant actors. This supports traceability for normal delivery, delegation, or escalation.
