## 1. Design rationale from the mission description

The mission naturally decomposes into five major phases:

1. **Mission triggering**: the system starts either from an explicit resource request or from a periodic logistics need, such as clean linen movement.
2. **Mission specification**: the system must know what resources are required, where they are stored, and where they must be delivered.
3. **Planning and robot allocation**: the system must estimate waiting time and path cost, sort storage visits, and decide whether to use one robot or multiple robots.
4. **Execution**: each assigned robot performs a collection phase followed by a delivery phase.
5. **Exception handling**: low battery thresholds create different recovery strategies depending on the phase:

   * **10% in collection**: robot returns to recharge and another robot takes over.
   * **30% in delivery**: robot places the resource at a checkpoint and transfers the remaining task.
   * **Failure to reach checkpoint**: alert and report to the sector manager.

The most important modeling decision is that **collection and delivery are sequential inside each assigned work package**, but **different work packages may execute in parallel** when multiple items from different storages are required.

# 5. Logical Relationships

## Root mission decomposition

* **G1 → G2, G5, G8, G14, G24 [AND][sequential `;`]**

  * **Justification**: A complete logistics mission requires trigger detection, mission specification, planning/allocation, execution, and closure. These happen in sequence because later phases depend on earlier information.

---

## Mission trigger decomposition

* **G2 → G3, G4 [OR][FALLBACK(G3,G4)]**

  * **Justification**: The mission can be triggered either by an on-demand request or by a periodic logistics requirement. One valid trigger is sufficient to start the mission.

* **G3 → AT1, AT2, AT3 [AND][sequential `;`]**

  * **Justification**: To capture an on-demand request, the system must receive the request, extract resources, and identify the requester/destination.

* **G4 → AT4, AT5 [AND][sequential `;`]**

  * **Justification**: A periodic mission first requires checking the schedule and then instantiating a concrete movement request.

---

## Mission specification decomposition

* **G5 → G6, G7 [AND][sequential `;`]**

  * **Justification**: The system must know both what is required and where resources/destination are located.

* **G6 → AT6, AT7 [AND][sequential `;`]**

  * **Justification**: The exact resource requirements must be queried and validated before storage can be contacted.

* **G7 → AT8, AT9 [AND][parallel `#`]**

  * **Justification**: Storage lookup and destination lookup are independent information queries and can be performed in parallel.

---

## Planning and allocation decomposition

* **G8 → G9, G10, G11 [AND][sequential `;`]**

  * **Justification**: The system first estimates costs, then defines order, then chooses robot allocation.

* **G9 → AT10, AT11 [AND][parallel `#`]**

  * **Justification**: Waiting time and path cost are independent estimates, but both are required for ranking storages.

* **G10 → AT12, AT13 [AND][sequential `;`]**

  * **Justification**: Storages must first be ranked; then the ordered itinerary is sent to robots.

* **G11 → G12, G13 [OR][FALLBACK(G12,G13)]**

  * **Justification**: Parallel allocation is preferred when multiple resources from different storages allow time reduction. If not applicable, a single robot assignment is sufficient.

* **G12 → AT14, AT15 [AND][sequential `;`]**

  * **Justification**: Resources must be partitioned into work packages before multiple robots can be assigned.

* **G13 → AT16 [AND][sequential `;`]**

  * **Justification**: A single-robot mission only requires assigning one robot.

---

## Execution decomposition

* **G14 → G15, G19 [AND][parallel over work packages: `#((G15;G19) per assigned work package)`]**

  * **Justification**: For each work package, collection must happen before delivery. Across different work packages, several robots may operate in parallel to reduce total mission time.

---

## Collection decomposition

* **G15 → G16, G17, G18 [OR][FALLBACK(G16,(G17;G18))]**

  * **Justification**: Normal collection is preferred. If collection is interrupted by 10% battery, recovery and replacement continuation are required.

* **G16 → AT17, AT18, AT19, AT20 [AND][sequential `;`]**

  * **Justification**: The robot must navigate to storage, send the resource request, wait for retrieval, and receive/load the resources.

* **G17 → AT21, AT22, AT23, AT24 [AND][sequential `;`]**

  * **Justification**: Once the 10% threshold is detected, the robot returns to recharge, another robot is assigned, and pending context is transferred.

* **G18 → AT25, AT26 [AND][sequential `;`]**

  * **Justification**: The replacement robot must reach the pending storage and continue the resource request/retrieval process.

---

## Delivery decomposition

* **G19 → G20, G21, G22, G23 [OR][FALLBACK(G20,FALLBACK((G21;G22),G23))]**

  * **Justification**: Normal delivery is preferred. If battery reaches 30%, checkpoint handoff and replacement delivery are attempted. If checkpoint return fails, escalation is required.

* **G20 → AT27, AT28, AT29 [AND][sequential `;`]**

  * **Justification**: The robot navigates to the destination, delivers resources, and repeats runs until all resources are delivered.

* **G21 → AT30, AT31, AT32, AT33 [AND][sequential `;`]**

  * **Justification**: At 30% battery during delivery, the robot must move the resource to a checkpoint, record its position, and assign the remaining task.

* **G22 → AT34, AT35, AT36 [AND][sequential `;`]**

  * **Justification**: The replacement robot must go to the checkpoint, pick up the resource, and complete delivery.

* **G23 → AT37, AT38, AT39 [AND][sequential `;`]**

  * **Justification**: If checkpoint return fails, the system must detect failure, trigger an alert, and report to the sector manager.

---

## Mission closure decomposition

* **G24 → AT40, AT41 [AND][sequential `;`]**

  * **Justification**: The system must confirm whether the mission ended successfully or through escalation, then update the mission log for traceability.
