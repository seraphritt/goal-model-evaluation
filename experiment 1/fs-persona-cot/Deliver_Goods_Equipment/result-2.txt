## 1. Step-by-step decomposition rationale

The mission describes a **resource logistics mission** in a hospital or similar institutional environment. The main objective is not merely for a robot to move, but for the system to ensure that **requested resources are collected from storage and delivered to the requesting agent at a specified location**.

The mission naturally decomposes into four main concerns:

1. **Mission preparation**: identify what was requested, where the resources are stored, how long each storage may take, and how far the robot must travel.
2. **Robot assignment**: choose either one robot or multiple robots, depending on whether the request involves multiple items from different storages.
3. **Collection phase**: robots visit storage locations in an order based on waiting-time estimation plus travel path cost.
4. **Delivery phase and recovery**: robots deliver resources, but if battery thresholds are reached, the mission must be reassigned safely.

The runtime structure follows the mission text:

* **Sequential `;`** is used when the mission explicitly requires one phase before another, such as planning before execution, collection before delivery, and alert before report.
* **Parallel `#`** is used when multiple robots can perform collect-deliver subtasks simultaneously to reduce total mission time.
* **Fallback `FALLBACK(...)`** is used for battery and failure handling, because those branches replace the normal execution only when a monitored condition prevents continuation.

# 5. Logical relationships

## Root mission

* **G1 -> G2, G13 [AND][sequential `;`]**

  * **Justification**: The mission cannot be executed before it is prepared. The system must first identify resources, storages, route order, and robot assignment, then execute the assigned workflows.

---

## Mission preparation

* **G2 -> G3, G4, G5, G9 [AND][sequential `;`]**

  * **Justification**: The mission preparation requires all four elements: request details, storage identification, ordered collection plan, and robot assignment. These steps are naturally sequential because later decisions depend on earlier information.

* **G3 -> AT1 [AND]**

  * **Justification**: Obtaining request details is operationalized by reading the delivery request.

* **G4 -> AT2 [AND]**

  * **Justification**: Identifying storages requires querying the storage catalog or equivalent source of resource-location information.

* **G5 -> G6, G7, G8 [AND][sequential `;`]**

  * **Justification**: The order depends on two estimates: waiting time and path cost. Only after both are known can the system define the storage visit order.

* **G6 -> AT3 [AND]**

  * **Justification**: Waiting-time estimation is concretely performed by querying or computing expected waiting time for each storage.

* **G7 -> AT4 [AND]**

  * **Justification**: Path estimation requires computing the travel path from robot position to candidate storages.

* **G8 -> AT5 [AND]**

  * **Justification**: The ordered route is produced by sorting storages according to waiting time plus path cost.

---

## Robot assignment

* **G9 -> G10, G11, G12 [OR][FALLBACK(G12,G11)]**

  * **Justification**: The mission can be assigned either to multiple robots or to one robot. Multiple robots are preferred when multiple independent storage-based subtasks exist; otherwise, the system falls back to single-robot assignment.

* **G10 -> AT6 [AND]**

  * **Justification**: The system must check whether the mission has multiple items from different storages and whether enough robots are available.

* **G11 -> AT7 [OR]**

  * **Justification**: Assigning one robot satisfies the assignment goal when the mission is not parallelized.

* **G12 -> AT8 [OR]**

  * **Justification**: Assigning multiple robots satisfies the assignment goal when parallel collect-deliver tasks are beneficial.

---

## Execution of collect-deliver workflows

* **G13 -> G14 [AND][parallel `#`]**

  * **Justification**: G14 represents a workflow template. If several robots are assigned, several G14 instances execute in parallel. All assigned workflows must finish for the overall mission to be complete.

* **G14 -> G15, G23 [AND][sequential `;`]**

  * **Justification**: A robot must collect resources before it can deliver them. Therefore, collection precedes delivery.

---

## Collection phase

* **G15 -> G16, G20 [OR][FALLBACK(G16,G20)]**

  * **Justification**: The normal branch is collection with the current robot. If the battery reaches 10%, the robot cannot continue normally and the recovery branch is used.

* **G16 -> G17, G18, G19 [AND][sequential `;`]**

  * **Justification**: During collection, the robot checks battery, travels to storage, then requests and receives resources. These actions depend on one another and occur in order.

* **G17 -> AT9 [AND]**

  * **Justification**: Battery verification is operationalized by reading the robot’s current battery level.

* **G18 -> AT10 [AND]**

  * **Justification**: Traveling to storages is operationalized by navigation to the next storage in the computed order.

* **G19 -> AT11, AT12, AT13 [AND][sequential `;`]**

  * **Justification**: The robot must send the precise request, wait while storage retrieves the resources, and then receive/load the resources.

* **G20 -> G21, G22 [AND][sequential `;`]**

  * **Justification**: When battery is low during collection, the current robot first returns to recharge, and the mission is then assigned to another robot.

* **G21 -> AT14, AT15 [AND][sequential `;`]**

  * **Justification**: Returning to the charging station requires navigation and docking.

* **G22 -> AT16 [AND]**

  * **Justification**: Mission transfer requires communicating the remaining mission state to another robot.

---

## Delivery phase

* **G23 -> G24, G28 [OR][FALLBACK(G24,G28)]**

  * **Justification**: Normal delivery is attempted first. If the delivery battery threshold of 30% is reached, recovery is required.

* **G24 -> G25, G26, G27 [AND][sequential `;`]**

  * **Justification**: The robot checks delivery battery, transports resources, and repeats runs until all assigned resources are delivered.

* **G25 -> AT17 [AND]**

  * **Justification**: Delivery battery verification is operationalized by reading the robot’s battery level during delivery.

* **G26 -> AT18, AT19 [AND][sequential `;`]**

  * **Justification**: Transporting resources requires navigation to the specified location and unloading/delivering them.

* **G27 -> AT20 [AND]**

  * **Justification**: If the robot cannot deliver everything in one run, it repeats the delivery run until all resources are delivered.

---

## Delivery low-battery recovery

* **G28 -> G29, G30, G31 [OR][FALLBACK((G29;G30),G31)]**

  * **Justification**: The preferred recovery is to place the resource at a checkpoint and transfer the remaining task. If the robot cannot return the resource to a checkpoint, the failure-reporting branch is used.

* **G29 -> AT21, AT22 [AND][sequential `;`]**

  * **Justification**: Returning the resource to a checkpoint requires navigating to the checkpoint, placing the resource, and recording its position.

* **G30 -> AT23 [AND]**

  * **Justification**: The remaining delivery can only be continued if another robot is informed of the checkpoint position and remaining task.

* **G31 -> G32, G33 [AND][sequential `;`]**

  * **Justification**: In case of checkpoint-return failure, the system must trigger an alert and send a report to the sector manager.

* **G32 -> AT24 [AND]**

  * **Justification**: Triggering an alert is the concrete task required by the failure condition.

* **G33 -> AT25 [AND]**

  * **Justification**: Sending the failure report to the sector manager is explicitly required by the mission description.
