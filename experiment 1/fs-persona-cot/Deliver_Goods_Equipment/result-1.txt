## 1. Design rationale used to build the goal model

The mission has one main objective: **collect required resources from storage and deliver them to the requesting agent at a specified location**. This is naturally an **Achieve goal**, because the desired final world state is that the requested resources are at the destination.

The mission is decomposed into four major phases:

1. **Understand the request**: identify resources, requesting agent, destination, quantity, and possible storages.
2. **Plan the logistics**: find storage places, estimate waiting time plus path cost, order the visits, and decide whether one or multiple robots should be used.
3. **Execute collect-deliver jobs**: robots collect resources and then deliver them.
4. **Handle contingencies**: battery thresholds create fallback branches:

   * During **collection**, low battery at **10%** means the robot goes to recharge and transfers the mission to another robot.
   * During **delivery**, low battery at **30%** means the robot must place the resource at a checkpoint and transfer the remaining task.
   * If checkpoint return fails, the system must alert and report to the sector manager.

Parallelism appears because the description says that **multiple robots can be assigned to parallel collect-deliver tasks** when multiple items are required from different storages. Sequential execution appears because collection must happen before delivery, and requesting a resource from storage must happen after reaching the storage.

# 5. Logical relationships

## Root decomposition

**G1 -> G2, G3, G9, G18 [AND][sequential `;`]**

* **Justification:** The delivery mission requires all four major stages: obtain the request, plan the mission, execute the collect-deliver jobs, and verify the final status. The order is sequential because planning depends on request data, execution depends on the plan, and verification comes after execution.

---

## Request understanding

**G2 -> AT1, AT2 [AND][sequential `;`]**

* **Justification:** The system must first receive the request and then extract the relevant parameters. Both are required because the robot cannot collect or deliver without knowing what resources are required and where they must be delivered.

---

## Logistics planning

**G3 -> G4, G5, G6 [AND][sequential `;`]**

* **Justification:** The robot must first know which storages contain the resources, then rank those storages by waiting time plus path cost, and finally decide how many robots should be assigned.

**G4 -> AT3 [AND]**

* **Justification:** Querying the storage inventory is the concrete operation needed to identify where resources are located.

**G5 -> AT4, AT5 [AND][sequential `;`]**

* **Justification:** The route order can only be generated after estimating waiting time and path cost. Both are required because the description defines the order using the sum of those two values.

---

## Robot allocation

**G6 -> G7, G8 [OR][FALLBACK(G7,G8)]**

* **Justification:** The mission can be allocated to multiple robots or one robot. Multiple robots are preferred when multiple resources from different storages allow parallelization and time reduction. If parallel allocation is not useful or possible, single-robot allocation is sufficient.

**G7 -> AT6, AT7 [AND][sequential `;`]**

* **Justification:** The system must first split items into job bundles and then assign those bundles to multiple robots.

**G8 -> AT8 [AND]**

* **Justification:** Assigning one robot is the concrete task that operationalizes the single-robot allocation alternative.

---

## Parallel job execution

**G9 -> G10ᵢ for each assigned collect-deliver job [AND][parallel `#`]**

* **Justification:** When the request is split into multiple jobs, all jobs must complete for the mission to succeed. The runtime is parallel because the description explicitly says multiple robots can be assigned to parallel collect-deliver tasks to reduce mission time.

---

## One collect-deliver job

**G10 -> G11, G14 [AND][sequential `;`]**

* **Justification:** A robot must collect the resources before it can deliver them. Therefore, collection and delivery are both mandatory and sequential.

---

## Collection phase

**G11 -> G12, G13 [OR][FALLBACK(G12,G13)]**

* **Justification:** Normal collection is the primary path. If the robot reaches 10% battery during collection, the mission falls back to the low-battery recovery branch.

**G12 -> AT9, AT10, AT11, AT12 [AND][sequential `;`]**

* **Justification:** The description gives a clear order: go to storage, send a message with precise resource specifications, wait for retrieval, and then proceed once the resource is retrieved.

**G13 -> AT13, AT14 [AND][sequential `;`]**

* **Justification:** The low-battery collection rule requires two actions: the robot returns to the recharging station and assigns the mission to another robot.

---

## Delivery phase

**G14 -> G15, G16, G17 [OR][FALLBACK(G15,FALLBACK(G16,G17))]**

* **Justification:** Normal delivery is attempted first. If the robot battery reaches 30% during delivery, checkpoint handoff is required. If the robot fails to return the resource to a checkpoint, alert/reporting is the final fallback.

**G15 -> AT15, AT16, AT17, AT18 [AND][sequential `;`]**

* **Justification:** The robot must determine how many runs are needed, travel to the destination, deliver the resource batch, and repeat until all assigned resources are delivered.

**G16 -> AT19, AT20, AT21, AT22 [AND][sequential `;`]**

* **Justification:** The checkpoint handoff requires the robot to place the resource at a checkpoint, record the position, assign the remaining task to another robot, and allow the new robot to retrieve and continue delivery.

**G17 -> AT23, AT24 [AND][sequential `;`]**

* **Justification:** The failure rule explicitly requires both an alert and a report to the sector manager. One without the other would not satisfy the requirement.

---

## Mission verification

**G18 -> AT25 [AND][sequential `;`]**

* **Justification:** Final status checking is needed to confirm whether all resources were delivered, checkpointed for continuation, or reported as failed. This supports mission monitoring and manager accountability.
