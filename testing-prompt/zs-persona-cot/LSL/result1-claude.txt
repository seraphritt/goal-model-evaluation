# Mission Analysis: Lab Sample Transport & Processing System

## Step‑by‑Step Reasoning

**1. Identifying the actors in the description**
The mission mixes human actors (nurse, laboratory personnel, "authorized personnel") with robotic actors (robotic arm, transport mechanism for locked drawers, "specific robots"). Per the modeling rule *"Goals and tasks that are not performed by any robot (zero robot) must not be on the goal model,"* I first separated human‑only activities from robot‑relevant ones.

**Excluded (zero‑robot) elements** — not represented as nodes, but noted here for traceability:
- *"A nurse ... can request a delivery"* — human trigger, no robot involved.
- *"Each sample before collection is identified with a barcode"* — pre‑collection labeling, performed by ward staff, not a robot.
- *"The nurse inserts data about the sample in a track system"* — human data‑entry action.
- *"...picked by a robotic arm **or laboratory personnel**"* — the "laboratory personnel" branch of this OR is zero‑robot and is dropped; only the robotic‑arm branch survives, which is why this no longer appears as an OR‑decomposition (an OR needs ≥2 surviving children).
- *"Only **authorized personnel** or specific robots..."* — the "authorized personnel" branch is likewise dropped; only the robot‑authorization branch remains.

**2. Finding the robot‑relevant backbone**
What remains is a physical pipeline: a locked drawer is transported → the drawer is opened by an authorized robot at the laboratory → a robotic arm picks, scans, sorts and loads the sample into the analysis machine → two monitoring concerns run alongside this (secure pick logging, and time‑tracking for protocol compliance).

**3. Sequencing vs. parallelism**
- Transport must finish before in‑lab processing starts (explicit order: *"transported ... to the laboratory. In the laboratory, the sample can be picked..."*) → **sequential**.
- Inside processing, the verbs are explicitly chained — *"picks up ... scans ... sorts, and loads"* — → **sequential**, and drawer‑opening logically precedes picking, so it was placed first in that same chain.
- The two monitoring concerns (securely logging *where/when* picked, and tracking *elapsed time*) are independent of each other and can run alongside the main flow → **parallel**.
- No sentence states "if X fails, do Y" / no condition, exception or threshold triggering an alternative behavior is present anywhere in the text → **no FALLBACK is used** anywhere in this model.

**4. Avoiding redundancy**
"Picking up the sample" and "opening the drawer to access the sample" are kept as two distinct tasks only because the mission singles out drawer‑opening as its own authorization concern (location‑ and robot‑restricted) — they are not merging the same intention, they represent two different intentions (gaining physical access vs. retrieving the item).

## Logical Relationships

- **G1 -> AT1, G2, G3 [AND] [(sequential AT1;G2) parallel with G3: (AT1;G2)#G3]**
  - **Justification**: All three are jointly necessary for the mission to succeed (AND). Transport must complete before in‑lab processing can begin, since the text presents them in that physical order ("transported ... In the laboratory ..."), hence `AT1;G2`. Monitoring (G3) is not causally gated the same way — logging and time‑tracking accompany the flow rather than strictly follow it — so it is modeled as possible to proceed in parallel: `(AT1;G2)#G3`.

- **G2 -> AT2, AT3, AT4, AT5, AT6 [AND] (sequential): AT2;AT3;AT4;AT5;AT6**
  - **Justification**: All five steps are required to reach the processing goal's target condition (AND). The description lists the robotic arm's actions in an explicit, unambiguous order — "picks up, scans, sorts, and loads" — and drawer‑opening must precede picking since the sample cannot be retrieved from a locked drawer, so all five are chained sequentially.

- **G3 -> AT7, AT8 [AND] (parallel): AT7#AT8**
  - **Justification**: Both a secure log of the pick event and a tracked elapsed time are required by the protocol (AND — the text uses two separate "should" statements, both mandatory). They concern independent pieces of information (a location/time stamp vs. a duration calculation) and nothing in the text forces one before the other, so they are modeled as possible to execute in parallel.

## Notes on Modeling Choices Worth Flagging

- **No OR‑decomposition appears in the final tree.** The two "or" statements in the source text (robotic arm *or* personnel; authorized personnel *or* specific robots) each had one branch eliminated by the zero‑robot rule, leaving a single surviving option — which is why they surface as single tasks (AT2, AT3) rather than OR nodes.
- **No FALLBACK appears**, because the description never states an explicit first‑attempt/alternative‑on‑failure behavior (no "if the robot cannot X, then Y").
- **Robot counts are inferred, not stated.** The text never gives numeric values; every "Number of Robots = 1" reflects the singular phrasing used throughout ("a robotic arm," "the robotic arm," "a nurse... can request"). If your system intends fleets (e.g., multiple transport robots operating concurrently across floors), AT1 and AT8 are the most natural candidates to generalize into a range like `[1, n]`.
