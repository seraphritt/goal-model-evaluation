# Mission Analysis: Lab Sample Transport & Processing

## Step‑by‑Step Reasoning

**1. Identify the robotic agents implied by the text.**
The description never names robots explicitly as "Robot 1" or "Robot 2," but it does identify distinct *robot roles* through the actions attributed to them:
- A **transport robot** (implicit) — the agent that must exist to carry the "secure locked drawers" between patient floors and the laboratory, since drawers don't move themselves.
- A **robotic arm** (explicit) — "The robotic arm picks up samples, scans the barcode in each sample, sorts, and loads the samples into the entry-module of the analysis machines."
- **"specific robots in specific locations"** (explicit) — authorized to open the locked drawers.

**2. Apply the zero‑robot exclusion rule.**
Several activities in the text are performed exclusively by humans and have no robot equivalent stated or implied:
- "A nurse responsible for collecting a sample can request a delivery" → nurse action, excluded (modeled only as the triggering event, not as a goal/task).
- "Each sample before collection is identified with a barcode" → passive, no agent stated, presumably manual labeling, excluded.
- "The nurse inserts data about the sample in a track system" → nurse action, excluded.
- "the sample can be picked by a robotic arm **or** laboratory personnel" → explicit OR, but the "laboratory personnel" branch is zero‑robot. Per the rule, it is excluded rather than kept as an empty OR branch. Only the robotic‑arm branch survives, modeled as a direct task rather than as an OR node (an OR decomposition needs ≥2 surviving children, and here only one remains robot‑feasible).
- "Only authorized personnel **or** specific robots in specific locations…" → same reasoning: the "authorized personnel" branch is dropped, leaving only the robot‑opening branch as a task.

This is why the final model contains **no OR decomposition**: both textual "or" constructs collapse to a single survivable (robot) branch once the zero‑robot rule is applied.

**3. Check for FALLBACK conditions.**
FALLBACK requires an explicit primary/alternative pair triggered by failure, exception, or threshold language ("if X fails, do Y"). Nothing in the description expresses such a condition — the "or" statements are alternatives of *authorization/assignment*, not sequential retries after failure. **No FALLBACK is used.**

**4. Build the hierarchy.**
Three top‑level concerns emerge, all mandatory (AND) for the mission to be considered fulfilled:
- Physically moving the sample (transport),
- Processing it once at the lab (drawer access → pick → scan → sort → load → log), and
- Verifying the transit time against protocol (a cross‑cutting, concurrent concern).

**5. Decide ordering/concurrency (runtime annotations).**
- Transport must finish before lab processing can start → sequential.
- Within lab processing: opening the drawer must precede picking, which precedes scan/sort/load (explicit order in "picks up… scans… sorts… and loads") → sequential chain.
- Logging the pick location/time only needs the pick event's data — it does not need to wait for scanning/sorting/loading to finish → modeled in parallel with that sub‑chain.
- Time‑compliance tracking spans the whole journey (from collection to delivery) and does not gate or get gated by the operational steps → modeled in parallel with the entire transport+processing chain.

**6. Avoid redundancy.**
"Log where/when picked" (event‑level, security‑audit intent, tied to the pick action at the lab) and "track elapsed collection‑to‑delivery time" (duration/SLA intent, spans the whole trip) address different intentions, different data, and different purposes — they are kept as two distinct goals/tasks, not merged.

## Logical Relationships

- **G1 -> AT1, G2, G3 [AND] [(AT1 ; G2) # G3]**
  - **Justification**: Transport, lab processing, and time‑compliance tracking are all mandatory, complementary parts of fulfilling the mission (AND — none is an alternative to another). Transport must physically complete before lab processing can begin (sequential, `;`), while time tracking (collection → delivery) spans the whole journey and is not gated by, nor gates, the operational steps, so it runs alongside them (parallel, `#`).

- **G2 -> AT2, AT3, AT4, AT5, AT6, AT7 [AND] [AT2 ; AT3 ; ((AT4 ; AT5 ; AT6) # AT7)]**
  - **Justification**: All six steps are required (AND) to reach G2's target condition. The text gives an explicit operational order — drawer must be opened before the sample can be picked, and "picks up... scans... sorts... and loads" is an explicit sequential chain — hence `AT2;AT3;AT4;AT5;AT6`. AT7 (logging) only depends on the pick event's data (location/time of AT3), not on the subsequent scan/sort/load outcomes, so it is modeled as possible in parallel with that sub‑chain rather than forced to wait for it.

- **G3 -> AT8, AT9 [AND] [AT8 ; AT9]**
  - **Justification**: Both timestamps are required to compute the elapsed interval (AND). Collection necessarily happens before delivery in time, so the recording tasks are sequential, matching the natural temporal order implied by "the time between sample collection and laboratory delivery."

- **No OR decomposition appears anywhere in the model.** Both explicit "or" statements in the description ("robotic arm or laboratory personnel," "authorized personnel or specific robots") pair a robot‑feasible branch with a human‑only branch. Per the zero‑robot exclusion rule, the human branch cannot appear in the model, and an OR decomposition requires a minimum of two surviving children — so each collapses to a single task (AT3 and AT2, respectively) rather than a formal OR node.

- **No FALLBACK relation is used.** FALLBACK requires an explicit statement of order tied to failure/exception/threshold ("if X fails, do Y"). The description contains authorization constraints and alternative‑agent statements, but no failure‑triggered retry logic, so applying FALLBACK would violate the instruction to use it only when explicitly warranted.
