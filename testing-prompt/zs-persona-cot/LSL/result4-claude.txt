# Mission Decomposition: Lab Sample Transport & Processing

## Step-by-Step Reasoning

**Step 1 — Identify every actor and action in the text.**
Actors: nurse (human), lab personnel (human), robotic arm (robot), "specific robots" that open drawers (robot), a transport mechanism implied by "transported... from patient floors to the laboratory" (robot, inferred — this is the core mission of a multi-robot delivery system), and a "track system" (software).

**Step 2 — Apply the zero-robot exclusion rule.**
The following actions are performed exclusively by humans and therefore **must not appear** as nodes:
- Nurse requesting a delivery.
- Barcode identification of the sample (not attributed to a robot).
- Nurse inserting sample data into the track system.
- "Laboratory personnel" picking the sample (OR-alternative to the robotic arm).
- "Authorized personnel" opening drawers (OR-alternative to the designated robot).

**Step 3 — Consequence for the OR-decompositions implied by the text.**
The description contains two explicit "or" statements:
- "the sample can be picked by a robotic arm **or** laboratory personnel"
- "authorized personnel **or** specific robots... open the locked drawers"

Normally these would be OR-decompositions. However, since one branch of each ("laboratory personnel", "authorized personnel") involves zero robots, that branch is dropped entirely. This leaves a single robot-performed path in each case, so **no OR-decomposition survives** in the final model — only the robot-executed alternative is modeled directly as a task. This is an important design decision driven directly by the given exclusion rule, not an oversight.

**Step 4 — Group remaining robot-relevant intentions into non-redundant goals.**
Three distinct intentions remain:
- Physically relocating the locked drawer and making it accessible (**transport + unlock**).
- Converting an accessible sample into an analysis-ready state (**pick → scan → sort → load**, explicitly listed in that order in the text → sequential).
- Securely recording where/when the pick happened (**logging** — tied to the pick event, so nested under processing).
- Measuring the collection-to-delivery interval for protocol compliance (**time tracking** — spans collection through delivery, so parallel to transport, not to processing).

**Step 5 — Determine AND vs OR.**
Every surviving relationship is complementary (all parts are necessary for mission success), never substitutable alternatives → all decompositions are **AND**.

**Step 6 — Determine runtime annotations.**
- Transport must precede drawer-opening (physical necessity, in the order the text presents them) → sequential.
- Pick must precede scan/sort/load, which the text lists in strict operational order → sequential; logging only depends on the pick, not on the later steps, so it is treated as running in parallel with them.
- Time-tracking spans "between collection and laboratory delivery," i.e., concurrently with the transport phase, not with processing → parallel with transport, then sequential before processing begins.

**Step 7 — Assign goal types.**
All three goals describe a desired end-state to be brought about through action (drawer delivered & opened; sample processed; — these are **Achieve** goals with target conditions) except the time-tracking task, which is about obtaining a data value (elapsed time) rather than changing world state, making it a **Query**-flavored intention — modeled as a task feeding the parent Achieve goal's monitoring requirement (see justification in table).

**Step 8 — Assign Location/Number of Robots.**
Only "patient floor" and "laboratory" are named locations in the text — no location is invented. Robot counts default to 1 where the text uses singular/definite references ("a robotic arm", a single delivery request), since no multiplicity is stated.
