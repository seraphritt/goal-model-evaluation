# Mission Decomposition — Robotic Collect & Deliver Task

Below is my full reasoning process followed by the formal goal model (goal tables, task tables, summary, and logical relationships).

---

## Step-by-Step Reasoning

**1. Finding the root intention.**
The description opens with a single overarching intentional statement: *"a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location."* This is the mission's top-level, non-operational objective → **G1**. It has a clear end-state (resources at the requested location for the requesting agent), so it's an **Achieve** goal, not Perform (it's not "try an action regardless of outcome") and not Query (nothing is being retrieved as information).

**2. Finding the phase structure (sequential).**
The text explicitly separates a *"collection phase"* and a *"delivery phase"*, and states *"Once retrieved, the delivery phase begins."* This is an explicit statement of **order**, but it is *not* triggered by a failure/condition/threshold — it's the normal flow of the mission. Per the rules, FALLBACK only applies to condition-triggered alternatives; a plain stated order of normal steps is **sequential (`;`)**. So G1 decomposes AND into Collection Phase and Delivery Phase, executed `G2;G7`.

**3. Finding the fallback (exception) structures.**
Two explicit "if-threshold" clauses appear, each describing a normal path and a condition-triggered alternative — the textbook definition of FALLBACK:
- *"If the battery... runs low (10%) in the collection phase, the robot goes back to the recharging station and assigns the mission to another robot."* → FALLBACK between "normal collection" and "low-battery collection recovery."
- *"If the battery... runs low (30%) in the delivery phase, the robot must return the resource to a checkpoint and assign the remaining task to another robot."* → FALLBACK between "normal delivery" and "low-battery delivery recovery."
- Nested inside the second one: *"In case of failure to return the resource to a checkpoint, an alert must be triggered..."* → a **second, nested FALLBACK** inside the low-battery-delivery recovery goal itself (`FALLBACK(FALLBACK(...), ...)` pattern).

Per the rule, every FALLBACK forces an **AND** decomposition between its two branches (both branches must exist in the model even though only one executes at runtime).

**4. Distinguishing Achieve vs. Perform vs. Query goals.**
- Ordering storages by *"estimation of waiting time summed up with path to be run"* is pure information-gathering about the world (no action, no target world-state) → **Query**.
- Knowing how many runs remain before the robot can stop making trips is also information-gathering → **Query**.
- Visiting a storage, retrieving a resource, and delivering resources all have an explicit completion condition ("until retrieved," "reach... location") → **Achieve**.
- The two battery-recovery procedures are *reactive action sequences* with no explicit success/failure verification of their own (except the delivery one, which has an explicit failure clause) — I used this distinction: the **collection recovery** (G6) is modeled as **Perform** (just execute the two actions, no stated condition to verify), while the **delivery recovery** (G9) is modeled as **Achieve**, because the text explicitly introduces a success/failure condition on the checkpoint-return step. The pure notification response to failure (trigger alert + report) is again just "do these actions" → **Perform** (G10).

**5. Finding tasks, locations, and robot counts.**
Only four locations are explicitly cited in the text: **storage**, **recharging station**, **checkpoint**, and the **specified (delivery) location**. I did not invent any location beyond these. Every concrete, assignable, single-step robot action (navigate, send message, wait, return, reassign, transport, trigger alert, send report) became a **Task (AT#)**, since Tasks must be fully operational/atomic, unlike Goals.

**6. Handling "multiple robots in parallel."**
*"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks..."* This describes **multiple concurrent instances of the same collect/deliver subtree** (one per item/storage), not two *different* sibling sub-goals running in parallel. Since the parallel operator `#` explicitly cannot relate a goal to itself (`exp1` cannot equal `exp2`), I did not model this as a goal-level parallel annotation. Instead, I captured it where the model's own attribute structure supports it: the **Number of Robots** range `[1, n]` on the tasks that actually scale with the number of required items/storages — `AT1 (Navigate to Storage)` and `AT6 (Transport Resource to Destination)` — with `n` = number of distinct storages/items the mission currently requires. This is the only place the mission text ties multiplicity of robots to a concrete action.

**7. Handling the two examples (sterile medical equipment, clean linens).**
These are given only as illustrations of what "required resources" can be (*"Examples of goods/equipment are..."*), not as separate missions with their own actions, locations, or robot behavior beyond what's already generically described. Modeling them as additional goals would duplicate the already-captured intention "collect & deliver resource" — violating the redundancy-avoidance rule. I therefore treat `storage`/`DeliveryLocation` as the generic variables that these examples instantiate (e.g., sterile facility ≡ storage, use destination ≡ DeliveryLocation) rather than adding new nodes.

**8. On OR decomposition.**
I found **no OR decomposition** anywhere in this description. Every decomposition is either a plain AND (jointly required steps) or an AND forced by a FALLBACK (mutually exclusive-at-runtime, but structurally both required in the model). There is no point in the text where the fulfillment of *one* child alone, chosen freely among true alternatives, would satisfy a parent goal — the only "alternative" behaviors present are condition-triggered (fallback), not optional choices.

**9. Zero-robot content excluded.**
"Requesting agent" and "sector manager" are recipients/stakeholders, not robots, so no goal was created purely for their existence — they only appear as destinations/targets inside robot tasks.

## Logical Relationships

- **G1 -> G2, G7 [AND] (sequential: G2;G7)**
  - **Justification:** Collection and delivery are both mandatory for the mission to succeed, and the text explicitly states delivery begins only once collection finishes ("Once retrieved, the delivery phase begins") — a stated normal order, not a condition-triggered alternative, so sequential rather than FALLBACK.

- **G2 -> G3, G5, G6 [AND] FALLBACK((G3;G5), G6)**
  - **Justification:** G3 (visit storage) must precede G5 (request/retrieve) in normal operation. The whole normal path (G3;G5) is challenged by an explicit battery-threshold condition (10%), whose alternative is G6 — a textbook FALLBACK, which mandates AND between the branches.

- **G3 -> G4, AT1 [AND] (sequential: G4;AT1)**
  - **Justification:** The visiting order must be computed before the robot can navigate; both the computation and the travel are required, in that stated order.

- **G5 -> AT2, AT3 [AND] (sequential: AT2;AT3)**
  - **Justification:** The robot must send the request before it can wait for the resource to be retrieved — both actions required, explicit order.

- **G6 -> AT4, AT5 [AND] (sequential: AT4;AT5)**
  - **Justification:** "Goes back to the recharging station **and** assigns the mission to another robot" — both actions are required and stated in that order.

- **G7 -> G8, AT6, G9 [AND] FALLBACK((G8;AT6), G9)**
  - **Justification:** Determining remaining load (G8) precedes each transport run (AT6) in normal delivery. This normal path is challenged by the explicit 30% battery condition, whose alternative is G9 — FALLBACK, forcing AND.

- **G9 -> AT7, AT8, G10 [AND] FALLBACK((AT7;AT8), G10)**
  - **Justification:** Normally the robot returns the resource to checkpoint then hands off the remaining delivery (stated in that order: "return the resource... and assign the remaining task"). This is itself challenged by an explicit failure condition ("in case of failure to return"), whose alternative is G10 — a nested FALLBACK, forcing AND.

- **G10 -> AT9, AT10 [AND] (parallel: AT9#AT10)**
  - **Justification:** Both the alert and the report are explicitly required ("an alert must be triggered and the report sent"), but no order between them is stated, so they are modeled as possibly-parallel rather than forced sequential.

- **G3 -> G4, AT1 [AND]** *(goal-to-task-and-goal link, restated for clarity)* — see above.
- **G5 -> AT2, AT3 [AND]** — see above.
- **G6 -> AT4, AT5 [AND]** — see above.
- **G9 -> AT7, AT8 [AND]** (within the FALLBACK's first branch) — both are required together as the "success path" of the low-battery-delivery reaction.
- **G10 -> AT9, AT10 [AND]** — see above.

**Note:** No OR decomposition appears anywhere in this model — the mission description contains no true optional alternatives (only AND-required steps and condition-triggered FALLBACKs). The two application examples (sterile medical equipment, clean linens) are intentionally not modeled as separate goals, since they are domain instantiations of the already-generic `storage` / `DeliveryLocation` variables, and adding them would duplicate G1–G10.
