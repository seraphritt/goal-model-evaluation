## Step‑by‑step reasoning

Before building the tables, here is how I parsed the description into a tree:

1. **Top‑level intent**: "a robot must collect the required resources... and deliver them... to a specified location" is a single mission with a clear end‑state (resources in the requester's hands). That end‑state makes it an **Achieve** goal, not a Perform goal.
2. **Two phases are named explicitly and sequenced**: "Once retrieved, the delivery phase begins" is an explicit temporal order → **sequential (`;`)** between a Collection goal and a Delivery goal, joined by **AND** (both phases are mandatory, not alternatives — there is no "OR" particle anywhere in the text).
3. **Inside Collection**, three things must happen for the robot to actually have the resource: decide the order of storages to visit, travel, and request/retrieve. The ordering rule itself ("order... defined by the estimation of waiting time summed up with the path") is pure information‑gathering with no physical effect on the world → modeled as a **Query goal**, not a task, since it only produces a ranking, not an action.
4. **Every "if battery runs low X% → do Y instead" sentence is a textbook Fallback**: the text gives a normal course of action and an explicit condition‑triggered alternative, which is exactly the trigger condition the instructions describe for `FALLBACK(exp1, exp2)`. I found three such conditional branches:
   - 10% battery in collection → return & reassign mission
   - 30% battery in delivery → return resource to checkpoint & reassign remaining task
   - failure to reach the checkpoint → trigger alert & report to manager
   Per the rules, each `FALLBACK` pair is connected by an **AND** decomposition (exp1 "and" its alternative exp2 are both part of the same goal's realization logic), even though only one branch executes at runtime.
5. **"an alert must be triggered and the report sent"** has no stated order between the two actions, so I used **parallel (`#`)** rather than sequential — the text never says one happens before the other, and under the rules sequential can only be used when order is explicit.
6. The final sentence about "multiple robots... parallel collect‑deliver tasks" describes **re‑instantiating the whole mission goal (G1) in parallel across storages/robots**, not a new intention. Since the modeling rules forbid duplicating goals with the same underlying intention and forbid `exp1 = exp2` in a parallel expression, I did **not** create a duplicate "G1‑bis" node. Instead this is captured as a cross‑cutting property of G1 (noted in its justification and in the closing remark), which is the accurate way to represent "N concurrent instances of the same goal" in this notation.
7. **Goal types**: every node with a persistent target state (resource retrieved, robot at recharge station, resource at checkpoint, resource delivered) is **Achieve**. The one node whose purpose is purely informational (visit order) is **Query**. The one node whose purpose is just "execute these two notification actions, success = they ran" (trigger alert / send report) is **Perform** — there is no further state the agent is trying to establish beyond having performed them.
8. **Tasks** only got created for things that are concrete, location‑bound, robot‑executable operations (travel, send‑and‑wait, recharge trip, checkpoint drop‑off, alert, report, reassignments). I did **not** create tasks/goals for the two equipment examples (sterile medical equipment, clean linens) because they are illustrative examples of *resources*, not actions performed by a robot — "zero robot" content per the rules.
9. Locations used are only the ones explicitly named: **storage**, **specified (delivery) location**, **recharging station**, **checkpoint**. The two reassignment tasks (AT4, AT9) and the request task have no robot‑movement location tied to them in the text beyond where the robot already is, so I did not invent one.

### Modeling note on multi-robot parallelism

The closing sentence — "When multiple items are required from different storages, multiple robots can be assigned to parallel collect‑deliver tasks" — describes **multiple concurrent instances of G1 itself** (one per required item/storage), not a new intention. I deliberately did not add a duplicate goal node for this, since the notation's parallel operator requires two *different* expressions (`exp1 ≠ exp2`) and the modeling guidance explicitly forbids duplicating goals that share the same underlying intention. The correct reading is: **G1 is re‑instantiable**, and when the triggering condition (multiple storages/items) holds, several independent instances of the G1 subtree may execute in parallel, each with its own robot — this is a possibility ("can be assigned"), not an obligation, consistent with the parallel operator's semantics.
