# Mission Decomposition: Multi-Robot Collect-and-Deliver System

## Step-by-Step Reasoning

Before building the tables, here's how I read the description and the decisions I made:

**1. Identifying the two macro-phases.** The text explicitly separates "the collection phase" from "the delivery phase" and states "*once retrieved, the delivery phase begins*" — this is an explicit ordering, so the two phases are modeled as **sequential** (`;`), not parallel, under one root mission goal.

**2. Spotting the FALLBACK structures.** Two clauses use the "if [threshold condition], then [alternative behavior]" pattern — battery at 10% during collection, and battery at 30% during delivery. Both explicitly describe a normal path and a conditional alternative path, which is the textbook trigger for `FALLBACK(normal, alternative)`. A third, nested case appears inside the delivery-battery clause: "*in case of failure to return the resource to a checkpoint*" — this is a second-order condition on top of the first, so it becomes a **nested fallback**: `FALLBACK(FALLBACK(normal_delivery, recover_and_reassign), report_failure)`.

**3. Why no OR-decomposition appears anywhere.** OR requires genuine *alternatives* where fulfilling one child is enough. Nothing in the description offers the robot a choice between equivalent options — everything is either a conjunctive requirement (AND) or a conditional contingency (FALLBACK, which the spec forces to be AND). I did not fabricate an OR just for variety.

**4. The waiting-time + path estimation.** "*The order... is defined by the estimation of waiting time summed up with the path to be run*" literally names two independent estimations that are summed. I split this into a Query goal with two parallel (`#`) estimation tasks, since no order between computing the two estimates is stated.

**5. Handling "multiple robots in parallel."** This clause doesn't introduce a new robot action — it describes how the *same* collect-deliver goal can be instantiated concurrently by different robots when several storages/items are involved. Rather than inventing an unsupported "assignment coordinator" goal (which the text never attributes to a specific robot — risking a "zero-robot" violation), I captured this as a property of the root goal itself (explained in its justification), keeping the tree faithful to only robot-performed actions.

**6. Excluding the examples.** Sterile equipment and clean linens are explicitly "examples of goods," not actions — no robot performs "being an example," so per the zero-robot rule they are left out of the tree entirely; they only inform the `Location`/resource semantics already captured in existing tasks.

**7. Goal typing.** Most goals are **Achieve** (they describe a target world-state reached through planning/action: resources retrieved, robot recharged, resource delivered). The order-estimation goal is a **Query** (it only produces information, doesn't change the world). The failure-reporting goal is a **Perform** (success = the alert/report actions were executed, not a persisting state).

**8. Numbering.** Goals (`G#`) and Tasks (`AT#`) are each numbered by a single depth-first traversal of the full tree, left children first, matching the order children are written in each decomposition below.

## Logical Relationships

- **G1 -> G2, G7 [AND] (sequential)**
  - **Justification**: Both the collection and the delivery phase must be completed for the mission to succeed, and the text explicitly states delivery starts only once collection is done ("once retrieved, the delivery phase begins").

- **G2 -> G3, G6 [AND] FALLBACK(G3, G6)**
  - **Justification**: Normal collection (G3) is attempted first; G6 is only triggered by the explicit 10%-battery condition. FALLBACK children are mandatorily AND-related per the modeling rules.

- **G3 -> G4, G5 [AND] (sequential)**
  - **Justification**: The visiting order must be determined before the storages can be visited in that order; both sub-goals are required, not alternatives.

- **G4 -> AT1, AT2 [AND] (parallel)**
  - **Justification**: Both estimates are needed to compute the sum that defines the order; the text gives no sequencing between computing them.

- **G5 -> AT3, AT4, AT5 [AND] (sequential: AT3;AT4;AT5)**
  - **Justification**: The text gives an explicit chronology — reach the storage, then send the request, then wait for retrieval.

- **G6 -> AT6, AT7 [AND] (sequential)**
  - **Justification**: "Goes back to the recharging station **and** assigns the mission" explicitly orders returning before reassigning; both actions are required.

- **G7 -> G8, G9 [AND] FALLBACK(G8, G9)**
  - **Justification**: Normal delivery (G8) is the default path; G9 only triggers on the explicit 30%-battery condition. FALLBACK forces AND.

- **G8 -> AT8, AT9 [AND] (sequential)**
  - **Justification**: A delivery run requires transporting the current load, then returning for the next one if resources remain — matching "as many runs as necessary."

- **G9 -> G10, G11 [AND] FALLBACK(G10, G11)**
  - **Justification**: Returning the resource and reassigning the task (G10) is attempted first; reporting (G11) is only reached if that itself fails ("in case of failure to return the resource to a checkpoint") — a nested, condition-triggered alternative, which is exactly FALLBACK's purpose.

- **G10 -> AT10, AT11 [AND] (sequential)**
  - **Justification**: "Must return the resource to a checkpoint **and** assign the remaining task" explicitly orders the checkpoint return before the reassignment.

- **G11 -> AT12, AT13 [AND] (parallel)**
  - **Justification**: Both the alert and the report are mandated consequences of the failure, with no stated order between them.

---

**A modeling note worth flagging:** no OR-decomposition occurs anywhere in this tree. The description never offers the robot a genuine choice between equivalent alternatives — every branch is either a strict joint requirement (AND) or a condition-triggered contingency (FALLBACK, itself AND). I treated this as a finding rather than forcing an artificial OR into the model.
