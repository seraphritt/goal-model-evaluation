# Mission Design: Robot Resource Collection & Delivery

## Step-by-Step Reasoning

Before building the model, here is my interpretive walkthrough of the description:

1. **Two mandatory phases, strictly ordered.** The text explicitly separates "the collection phase" from "the delivery phase" and states "*Once retrieved, the delivery phase begins*." This is an explicit temporal order between two complementary (not alternative) sub-goals → **AND decomposition with sequential (`;`) runtime**, not OR and not fallback (fallback is reserved for failure/condition-triggered alternatives, not normal phase progression).

2. **Ordering of storage visits is an information-gathering step, not a physical action.** "*The order to be followed is defined by the estimation of waiting time summed up with the path*" describes a computation the robot performs to decide where to go first. This matches the **Query Goal** definition (obtaining knowledge, not changing world state), so I isolated it as its own goal rather than folding it into "visit storage," since reusing the same goal for two different intentions (compute order vs. physically retrieve) would violate the non-redundancy rule.

3. **Battery thresholds are explicit conditional triggers → FALLBACK.** Both "if battery runs low (10%) in collection" and "if battery runs low (30%) in delivery" describe a normal behavior and an alternative behavior triggered by a condition/threshold. Per the given definitions, this is the textbook case for **FALLBACK**, and since FALLBACK mandates AND-decomposition of its two branches, both are modeled as AND.

4. **Nested fallback in delivery.** "*In case of failure to return the resource to a checkpoint*" is a second, nested condition layered on top of the first fallback branch (the battery-triggered one). This required a **nested FALLBACK** structure, consistent with the `FALLBACK(FALLBACK(exp1, exp2), exp3)` pattern described in the instructions — here realized as a sub-goal (G9) whose own runtime is a FALLBACK between "return & reassign" and "alert & report."

5. **No OR decomposition appears anywhere.** The description never offers true alternatives ("either X or Y, any one suffices"); every branching is either a mandatory joint requirement (AND) or a condition-triggered contingency (FALLBACK, which is itself AND). So the whole tree uses AND relations only — this is a valid and expected outcome, not a shortcut.

6. **Sequencing within tasks.** Wherever the text gives an explicit order of actions ("sends a message... and waits until retrieved"; "goes back to the recharging station and assigns the mission"; "return the resource... and assign the remaining task"; "alert must be triggered and the report sent"), I used sequential (`;`) runtime between the corresponding tasks. Where no order is stated and two things are naturally independent inputs to a shared result (the two estimations that get summed), I used parallel (`#`).

7. **Locations used are exactly those named in the text**: *storage*, *specified location* (the requesting agent's delivery destination), *recharging station*, *checkpoint*. I deliberately did **not** invent "sterile facility," "laundry," or "use destination" as separate location nodes — the prompt frames these as **illustrative examples** of the generic "storage" and "specified location" concepts, not as additional operational sites in the generic mission logic. Making them separate variables would hardcode the model to one domain and violate reusability.

8. **The "sector manager" is a recipient role, not a location** — I kept the task location as *checkpoint* (where the failure context occurs) and described the manager only as the destination of the message, since the mission text gives no office/location for this role.

9. **Parallel multi-robot assignment** ("*multiple robots can be assigned to parallel collect-deliver tasks*") is not a new goal — it's an execution-scaling property. I reflected it in the **Number of Robots** attribute (as a `[1, n]` range) on the tasks that are repeated per storage/resource (navigation, request, retrieval, loading, transport), rather than duplicating the whole tree, since the tree represents one collect-deliver pipeline template that can be instantiated concurrently by multiple robots.

10. **Perform vs. Achieve for contingency goals.** The battery-fallback and failure-reporting goals ("goes back... and assigns," "must return... and assign," "alert must be triggered and report sent") are phrased as mandatory concrete actions rather than a state to be reached through flexible planning — this matches **Perform Goal** ("succeeds when the action is executed"), whereas the main collection/delivery goals describe a state to be brought about (resources retrieved/delivered) through context-dependent planning — matching **Achieve Goal**.

## Logical Relationships

- **G1 -> G2, G7 [AND] (sequential)**
  - **Justification**: The text states collection and delivery are both mandatory, in that fixed order: "*Once [resources are] retrieved, the delivery phase begins.*" Both phases are required (AND), and delivery can only start after collection completes (`;`).

- **G2 -> G3, G6 [AND] FALLBACK(G3, G6)**
  - **Justification**: Normal collection (G3) is attempted first; the 10%-battery condition explicitly triggers an alternative behavior (G6) only if the normal path is interrupted. This is a textbook condition-triggered alternative, so FALLBACK applies, and FALLBACK mandates AND between its branches.

- **G3 -> G4, G5 [AND] (sequential)**
  - **Justification**: The visiting order must logically be known before the robot executes the visits; the description presents the ordering rule before describing the actual storage visits, so order-determination precedes visiting (`;`), and both are necessary for normal collection to succeed (AND).

- **G4 -> AT1, AT2 [AND] (parallel)**
  - **Justification**: "*the estimation of waiting time summed up with the path*" — waiting-time and path-cost estimates are two independent inputs that are simply added together; the text gives no order between computing them, so they may proceed in parallel, while both are required to produce the sum (AND).

- **G5 -> AT3, AT4, AT5 [AND] (sequential)**
  - **Justification**: "*Once the robot reaches one storage and it is time to request the resource, the robot sends a message... and waits until the resources have been retrieved*" gives an explicit three-step order: arrive, request, wait/retrieve. All three are required (AND) and strictly ordered (`;`).

- **G6 -> AT6, AT7 [AND] (sequential)**
  - **Justification**: "*the robot goes back to the recharging station and assigns the mission to another robot*" — explicit order (return, then reassign); both actions are required for the contingency goal to be fulfilled (AND).

- **G7 -> G8, G9 [AND] FALLBACK(G8, G9)**
  - **Justification**: Mirrors G2's structure — normal delivery (G8) is attempted first, and the 30%-battery condition explicitly triggers the alternative contingency behavior (G9) only on interruption.

- **G8 -> AT8, AT9 [AND] (sequential)**
  - **Justification**: A delivery run logically requires loading the resource before transporting it; both steps are necessary per run (AND) and occur in that order (`;`), repeated "as many runs as necessary."

- **G9 -> G10, G11 [AND] FALLBACK(G10, G11)**
  - **Justification**: "*the robot must return the resource to a checkpoint and assign the remaining task... In case of failure to return the resource to a checkpoint, an alert must be triggered...*" — this is a second, nested condition: G10 (return & reassign) is attempted first; G11 (alert & report) is the fallback specifically for the case where G10 cannot be completed. This nested structure mirrors the `FALLBACK(FALLBACK(...), exp3)` pattern, with G9 itself being the inner FALLBACK node relative to G7.

- **G10 -> AT10, AT11 [AND] (sequential)**
  - **Justification**: "*return the resource to a checkpoint and assign the remaining task*" — explicit order (return, then reassign); both required (AND).

- **G11 -> AT12, AT13 [AND] (sequential)**
  - **Justification**: "*an alert must be triggered and the report sent to the sector manager*" — explicit order (alert first, then report); both required (AND) for the failure-handling goal to be fulfilled.

---

**Notes on scope decisions:**
- No OR-decomposition appears in this model because the description contains no true alternative-fulfillment statements — every branch is either a joint requirement or a condition-triggered contingency (which the given formalism treats as AND via FALLBACK).
- The two domain examples (sterile medical equipment, clean linens) were treated as illustrative instantiations of the generic *storage* → *specified location* flow already modeled, not as additional goals/tasks, to keep the model general and avoid redundant intentions, per the no-redundancy instruction.
- All tasks are robot-executed (navigation, messaging, loading, reporting, etc.), so none were excluded under the "zero-robot" rule.
