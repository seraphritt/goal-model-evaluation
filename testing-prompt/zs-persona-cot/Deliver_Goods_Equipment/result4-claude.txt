# Mission Decomposition — Robotic Collect‑and‑Deliver Logistics

## Step‑by‑Step Reasoning

Before presenting the model, here is the reasoning path I followed:

1. **Identify the top‑level intention.** The mission is triggered "when required" and consists of two explicit phases joined by "and": *collect* the resources, *deliver* them. Since the text explicitly states "once retrieved, the delivery phase begins," this is an **explicit order**, not a conditional/failure branch → **sequential**, not fallback. Both phases are mandatory → **AND**.

2. **Decompose the Collection phase.** Three distinct intentions appear: (a) deciding *which order* to visit storages (an information/estimation activity — waiting time + path), (b) physically *traveling and requesting/retrieving* resources, and (c) a **conditioned alternative** triggered by "if battery runs low (10%)" — this is a textbook **FALLBACK** trigger (explicit condition + alternative behavior), not an OR (OR would mean either path is equally acceptable from the start, which isn't the case here — the recharge path only occurs *because* the normal path failed/was interrupted).

3. **Decompose the Delivery phase.** Symmetric reasoning: normal delivery runs vs. a battery-triggered alternative (30%) → FALLBACK. Inside that alternative, a **second, nested conditional** appears: "in case of failure to return the resource to a checkpoint" → a second FALLBACK nested inside the first, matching exactly the pattern `FALLBACK(FALLBACK(exp1, exp2), exp3)` given in the instructions.

4. **Distinguish Achieve vs. Perform vs. Query.** I avoided duplicating the same intention under two Achieve goals (redundancy rule). Where the description specifies a *reachable world state* (resources retrieved, resources delivered, resource repositioned so another robot "will know where it is"), I used **Achieve**. Where the description specifies *executing an action* with no further state condition stated (traveling+retrieving as a literal act, running back to recharge, triggering an alert, sending a report), I used **Perform**. Where the description is about *obtaining information to make a decision* (estimating waiting time + path), I used **Query**.

5. **No OR decompositions exist.** Nothing in the text presents two options where fulfilling either one is equally sufficient from the outset — every branch is either a mandatory AND requirement or a failure-triggered FALLBACK. I explicitly avoided mis-using OR for this.

6. **Tasks and their properties.** Every leaf action was checked against the text for an explicit **Location** (storage, recharging station, checkpoint, specified/delivery location) — I did not invent locations; for purely communicative/administrative tasks (reassigning a robot, triggering an alert, sending a report) no physical location is stated, so I marked these **N/A** rather than fabricate one. For **Number of Robots**, the text consistently uses singular phrasing ("a robot," "the robot," "the assigned robot") for every action inside one collect‑deliver cycle, so each task = 1 robot. The *only* place multiplicity appears is the closing sentence about parallel robots across *different* items/storages — this is a mission‑orchestration‑level concurrency (multiple independent instances of the whole tree running side by side), not multiple robots cooperating on a single task, so I documented it separately rather than forcing an artificial branching factor into the tree (see the note after the tables).

7. **IDs** were assigned by depth‑first traversal, separately for the G‑namespace and the AT‑namespace, as specified.

## Logical Relationships

- **G1 -> G2, G6 [AND] (sequential: G2;G6)**
  - **Justification**: Collection and delivery are both required ("collect... and deliver"), and the text explicitly states delivery starts only once collection/retrieval is complete — an explicit, unconditional order, hence sequential rather than fallback.

- **G2 -> G3, G4, G5 [AND] [FALLBACK(G3;G4, G5)]**
  - **Justification**: Normal path is "determine order, then travel & retrieve" (G3;G4). An explicit condition ("if battery runs low (10%)") triggers an alternative recovery path (G5). This is a genuine condition-triggered alternative, which must be modeled as FALLBACK, and FALLBACK operands are always AND-related.

- **G3 -> AT1, AT2 [AND] (parallel: AT1#AT2)**
  - **Justification**: Both the waiting-time estimate and the path estimate are needed to compute the combined ranking value ("waiting time summed up with the path"), and nothing in the text orders one before the other, so they may proceed in parallel.

- **G4 -> AT3, AT4 [AND] (sequential: AT3;AT4)**
  - **Justification**: "Once the robot reaches one storage... the robot sends a message" — arrival is explicitly a precondition for the request, so travel must precede the request/retrieval.

- **G5 -> AT5, AT6 [AND] (parallel: AT5#AT6)**
  - **Justification**: The text states "goes back to the recharging station and assigns the mission to another robot" with no explicit sequencing language (no "then"/"after"); both can reasonably proceed concurrently (e.g., handoff communicated while physically returning), so no fallback or forced sequence is warranted.

- **G6 -> G7, G8, G9 [AND] [FALLBACK(G7, FALLBACK(G8, G9))]**
  - **Justification**: Normal delivery runs (G7) proceed unless battery drops to 30%, triggering recovery (G8); if the checkpoint return within that recovery itself fails, a second explicit condition triggers escalation to alert/report (G9). This matches the nested-fallback pattern `FALLBACK(FALLBACK(exp1,exp2),exp3)` directly.

- **G7 -> AT7, AT8 [AND] (sequential: AT7;AT8)**
  - **Justification**: The robot must reach the specified location before it can hand over the resource there; the text implies this physical precondition.

- **G8 -> AT9, AT10 [AND] (sequential: AT9;AT10)**
  - **Justification**: The handoff robot "will know where the resource is positioned," which requires the checkpoint placement (AT9) to be completed and known before reassignment (AT10) is meaningful.

- **G9 -> AT11, AT12 [AND] (parallel: AT11#AT12)**
  - **Justification**: "An alert must be triggered and the report sent" is a plain conjunction with no stated order, so both can occur together.

## Additional Notes

- **No OR decompositions appear anywhere in this model.** Everything in the description is either a joint (AND) requirement or a condition-triggered alternative (FALLBACK); there is no point where two children are presented as equally valid starting options, which is what OR is reserved for.

- **Mission-level parallelism (not modeled as a tree node):** the closing sentence — "When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks" — describes *multiple independent instances* of the entire G1 tree running concurrently (one robot per item/storage), not multiple robots cooperating inside a single task. Since the number of concurrent instances is variable and not fixed by the text, it is not represented as a fixed branch in the tree (which would require an arbitrary, unjustified branching factor); every task in the tables above correctly reflects "Number of Robots = 1" for a single instance, with this note documenting the system-level replication behavior.

- **Resource-type examples (sterile medical equipment, clean linens)** are illustrative instantiations of the generic variables already in the model rather than new goals: "storage" maps to *sterile facilities* / *the laundry*, and "specified location" maps to *use destinations* / *storage rooms near use points*. No additional goals or tasks were introduced for them, per the non-redundancy instruction.
