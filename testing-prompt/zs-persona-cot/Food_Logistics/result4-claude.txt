# Goal Model Design: Hospital Meal Delivery & Dish Retrieval Multi-Robot System

## Step-by-Step Reasoning

**1. Identify the two independent mission processes.**
The description names two triggers: a *kitchen delivery request* (food → room) and a *pickup call* (dirty dishes → removed from room). Nothing in the text says one must wait for the other at the system level — different orders/rooms can be in either phase simultaneously — so I treat them as two AND-required, but **parallel**, branches under one root service goal.

**2. Identify explicit alternatives ("or" statements) → OR-decompositions.**
- Delivery method: *"delivered into a room table... or ... fetched from the robot's tray"* → OR.
- Who can retrieve from the tray: *"the inpatient, a companion, a nurse, or another robot"* → OR.
- Dish retrieval mode: *"unassisted, with the cooperation of two robots or with the cooperation of robots and a human"* → OR.
- No stated priority order exists among these alternatives, so their runtime annotation is **parallel (#)**, not fallback — there is no "try X, then Y if X fails" language here, just alternative means.

**3. Identify explicit uncertainty/information needs → Query Goals.**
- *"The information about if the inpatient, a companion visitor or nurse can be able to retrieve the food... is subject to uncertainty"* → this is knowledge-gathering, not action → **Query Goal**.
- *"that person can signal if they can open the door"* → also knowledge-gathering about a capability → **Query Goal**.

**4. Identify explicit normal-vs-exception language → Fallback.**
- *"should track when and where each meal was retrieved. The robot should alert if a wrong meal is retrieved"* → normal behavior (tracking a correct retrieval) vs. an exception condition (wrong meal) triggering a different action → **FALLBACK**.
- Door opening involves two cooperation alternatives, but since door-opening capability is explicitly signaled by the occupant (a condition check), I model the chosen cooperation partner (human first, since the person is the one signaling; robot cooperation as the alternative) as **FALLBACK**, since the text frames this as "if the person *can* open it" vs. the implied alternative when they can't.
- Per the rules, FALLBACK operands must always be connected by AND, and must be goals (not raw tasks), since fallback is a goal-level runtime construct. I therefore wrap single actions that need fallback semantics (track/alert, human-open/robot-open) in minimal leaf-goals.

**5. Identify logical/physical dependencies → Sequential.**
- A door must be open before dishes can be picked up → **sequential**.
- Determining who/whether someone can act (query) must happen before the dependent action is attempted → **sequential**.
- Table-placement vs. tray-fetch don't have this dependency (no query precedes them) → stay parallel.

**6. Zero-robot filtering.**
I excluded any node whose sole actor would be a human with no robot participation (e.g., "a visitor decides to visit", "a nurse becomes available") — these are environmental conditions feeding the Query Goals, not goals/tasks themselves, consistent with the rule that zero-robot goals/tasks must not appear.

**7. Avoiding invented content.**
I did not model an explicit "transport from kitchen to room" task, since the description gives no detail about navigation/loading — adding it would be inventing content beyond the text. All locations used (Room, Room Table, Room Door) are explicitly cited.

## Logical Relationships

- **G1 -> G2, G10 [AND](parallel)**
  - **Justification**: Delivery and dish retrieval are both mandatory system responsibilities, triggered by independent events (kitchen requests vs. room calls); nothing in the text orders one before the other, so they may proceed concurrently.

- **G2 -> AT1, G3 [OR](parallel)**
  - **Justification**: "Delivered into a room table... **or** fetched from the robot's tray" — explicit alternative; no stated preference or failure-driven order, so parallel (either may be chosen independently).

- **G3 -> G4, G5, G6, G7 [AND]((G4#G5);G6;G7)**
  - **Justification**: All four steps are necessary for a correct tray handoff. G4 (capability check) and G5 (indicating the meal) have no stated order relative to each other → parallel; both must complete before G6 (actual retrieval) can be attempted → sequential; G7 (verification/tracking) can only happen after retrieval → sequential.

- **G4 -> AT2 [AND]**
  - **Justification**: A single, necessary information-gathering action; no alternatives exist for this step.

- **G5 -> AT3 [AND]**
  - **Justification**: A single necessary signaling action.

- **G6 -> AT4, AT5, AT6, AT7 [OR]**
  - **Justification**: "the inpatient, a companion, a nurse, or another robot" — explicit OR list of interchangeable retrieving agents.

- **G7 -> G8, G9 [AND]FALLBACK(G8,G9)**
  - **Justification**: Normal behavior is tracking a correct retrieval; the wrong-meal alert is the explicit exception case triggered by a failure condition — textbook FALLBACK, which per the rules is always AND-connected.

- **G8 -> AT8 [AND]**
  - **Justification**: Single necessary logging action.

  - **Justification**: Single necessary alerting action.

- **G11 -> G12, G13 [AND](sequential) G12;G13**
