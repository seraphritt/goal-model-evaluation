# Mission Decomposition: Hospital Food Delivery & Dish Collection Robot System

## Step-by-Step Reasoning

**1. Identifying the top-level scope.** The description bundles two distinct, independently-triggered service flows: (a) *food delivery*, triggered by a kitchen request, and (b) *dirty dish retrieval*, triggered by a room occupant's call. Neither depends on the other to start or finish, and nothing in the text forces one to wait for the other, so I modeled a single root goal (G1) that AND-decomposes into these two branches, executed in parallel (they can co-occur, e.g., one robot delivering while another collects dishes).

**2. Food delivery branch.** The text explicitly orders "deliver food from the kitchen to an inpatient room" before describing *how* it's made available — this gives a clear sequential dependency: the robot must first **transport** the meal (AT1) before it can be **made available** (G3). "Made available" splits into two explicitly OR-ed alternatives: table delivery (needs a manipulation skill) or tray retrieval.

**3. Tray retrieval is the richest sub-process.** It requires, in logical/textual order: (a) determining *who* is capable/available to retrieve (explicitly flagged as uncertain information derived from the patient record *and* companion presence — a **Query** goal), (b) indicating the assigned meal (relevant because the robot can carry multiple meals), (c) the actual retrieval, modeled as an OR over the four named cooperating agents, (d) tracking retrieval time/location, and (e) a correctness check. The "alert if a wrong meal is retrieved" clause is a textbook conditional/exception pattern (normal retrieval vs. the IF-triggered alternative), so I modeled it as **FALLBACK**(verify, alert) rather than OR — the alert is only pursued if verification fails, and FALLBACK children must always be AND-related per the spec.

**4. Dish retrieval branch.** The physical precondition "a robot must reach and open the door before it can collect dishes inside the room" is supported by the text's own ordering ("someone can call a robot... that person can signal if they can open the door **when the robot comes to it**"), which I treat as justifying a sequential chain: navigate → open door → collect dishes. Door-opening and dish-collection each list explicit alternative cooperation modes ("another robot or a human"; "unassisted, two robots, or robot+human"), both modeled as OR, since no order or condition is given between the alternatives (just a human signal determining which path is taken, not a stated execution order).

**5. Excluding zero-robot actions.** "Kitchen issuing a request" and "a person calling the robot" / "signaling" are human/system-initiated events, not robot actions — per the rules, I did not create nodes for them; they appear only as *triggers/justifications* for the goals they activate.

**6. Goal typing.** Achieve goals are used wherever a world-state must be reached (meal delivered, door open, dishes removed). Query goals are used only where the sole purpose is retrieving information (capability/availability lookup; meal-match verification). No goal fit "Perform" cleanly because every intentional node here has either a clear target state or a clear information need — the atomic "perform-like" actions were instead pushed down to Task level, which doesn't require a type.

**7. Location/Robots for tasks.** I only used locations explicitly named in the text (kitchen, inpatient room/table/door) — I never introduced an unstated location (e.g., a "database" for record-checking; I anchored that check to the inpatient room since the record concerns that inpatient). Robot counts follow directly from the cooperation terms used ("another robot" → 2; "unassisted" → 1; human cooperation doesn't add to the robot count).

## Logical Relationships

- **G1 -> G2, G9 [AND] (parallel)**
  - **Justification**: Food delivery and dish collection are both explicitly required, independent system responsibilities ("The system should deliver food..." / "Dirty dishes should be retrieved..."), triggered by unrelated events, with no stated order between them.

- **G2 -> AT1, G3 [AND] (sequential)**
  - **Justification**: The meal must be physically transported to the room before it can be made available to the patient; the text's description order ("deliver... to inpatient room" → "delivered to table... or fetched from tray") supports this sequence.

- **G3 -> AT2, G4 [OR] (no fixed order, "#")**
  - **Justification**: Explicit "or" between table delivery and tray retrieval — only one method needs to succeed.

- **G4 -> G5, AT5, G6, AT10, G7 [AND] (sequential + parallel: G5 ; AT5 ; G6 ; (AT10 # G7))**
  - **Justification**: All five steps are necessary to complete tray-based delivery. Determining the capable agent must precede indicating the meal and the retrieval itself (logical dependency); tracking and verification happen after/around retrieval and don't depend on each other, so they run in parallel.

- **G5 -> AT3, AT4 [AND] (parallel)**
  - **Justification**: The capability/availability determination explicitly depends on both the patient record **and** companion presence ("...according to information about the patient and the presence of a companion..."); no order is stated between the two checks.

- **G6 -> AT6, AT7, AT8, AT9 [OR] (no fixed order, "#")**
  - **Justification**: Explicit enumeration of alternative cooperating agents ("the inpatient, a companion, a nurse, or another robot").

- **G7 -> G8, AT11 [AND] FALLBACK(G8, AT11)**
  - **Justification**: The text gives an explicit normal/exception pattern ("the robot should alert **if** a wrong meal is retrieved"), matching the FALLBACK definition; per spec, FALLBACK children are always AND-related.

- **G9 -> AT12, G10, G11 [AND] (sequential)**
  - **Justification**: The robot must arrive at the room, then the door must be opened, before dishes inside can be collected — a physical necessity reinforced by "...when the robot comes to it," which implies arrival precedes the door-related interaction and subsequent collection.

- **G10 -> AT13, AT14 [OR] (no fixed order, "#")**
  - **Justification**: Explicit "or" between robot cooperation and human cooperation for opening the door.

- **G11 -> AT15, AT16, AT17 [OR] (no fixed order, "#")**
  - **Justification**: Explicit enumeration of alternative dish-collection modes ("unassisted, with the cooperation of two robots, or with the cooperation of robots and a human").
