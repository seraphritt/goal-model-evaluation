# Multi-Robot Goal Model: Hospital Meal Delivery & Dish Retrieval

## Step-by-Step Reasoning

Before presenting the model, here is the reasoning process I followed:

1. **Identify the mission's two top-level responsibilities.** The description covers two largely independent processes: (a) delivering food from kitchen to room, and (b) retrieving dirty dishes from the room. Both are explicitly described as robot responsibilities, so both become top-level AND-children of a root mission goal. I treat them as **sequential**, not because the text explicitly orders them with an "if/then", but because dishes can only become "dirty" (i.e., require pickup) after a meal has already been delivered and consumed — a logical/causal dependency, not a FALLBACK (no failure/exception is involved here).

2. **Spot explicit alternatives ("or") → OR-decomposition.** Three clear "or" structures appear in the text:
   - Table delivery **or** tray fetch.
   - Tray-fetch cooperation with inpatient, companion, nurse, **or** another robot.
   - Door-opening cooperation with another robot **or** a human.
   - Dish retrieval unassisted, with two robots, **or** with robot+human.
   None of these come with an explicit attempt-order or failure condition, so none qualify for FALLBACK — they are modeled as OR with a "#" (unordered/parallel-possible) runtime, since the choice depends on situational capability, not a stated sequence.

3. **Spot explicit exception/condition → FALLBACK.** Only one place in the text matches the FALLBACK pattern precisely: normal behavior is that the correct meal is retrieved and tracked; the explicit exception is "the robot should alert **if** a wrong meal is retrieved." This is modeled as `FALLBACK(Track retrieval, Alert wrong meal)`.

4. **Spot uncertainty/queries.** The text explicitly flags two pieces of "subject to uncertainty" information that the robot must obtain before acting: (i) who can retrieve food from the tray (inpatient record + companion presence), and (ii) whether the person in the room can open the door. Both become **Query Goals**, each preceding an **Achieve Goal** that uses that information to choose an OR-branch — I reused this same "query-then-act" pattern in both places for consistency (per the "avoid redundancy" instruction, each distinct intention still appears exactly once).

5. **Separate concrete, atomic operations into Tasks.** Any operation that is a single, immediately executable step tied to a location and a robot count (placing food, signaling, logging, opening a door, picking up dishes) becomes a Task (AT), not a Goal — these are the tree's leaves.

6. **Zero-robot filter.** I excluded anything that isn't a robot action (e.g., "the inpatient record" as a database is not a goal itself; it's the *source* queried by a robot task). Every Task retained has ≥1 robot assigned.

7. **Robot counts.** I counted only robots, never humans, per task: "another robot" cooperation → 2 robots; human/inpatient/companion/nurse cooperation → 1 robot (just the delivery robot itself).

## Logical Relationships

- **G1 -> G2, G13 [AND] (sequential)**
  - **Justification**: Food delivery and dish retrieval are both core, non-optional system responsibilities. They are modeled as sequential because dirty dishes logically can only exist to be retrieved after a meal has been delivered (and presumably consumed) — a causal, not a failure-based, ordering.

- **G2 -> G3, G4 [AND] (sequential)**
  - **Justification**: The robot must first obtain the kitchen's request (what/where) before it can execute the delivery itself; both are required, in that order.

- **G4 -> G5, G6 [OR] (parallel, "#")**
  - **Justification**: The description explicitly presents table delivery and tray fetch as alternative delivery mechanisms ("...or..."), with no stated preference order or failure condition between them, so "#" (unordered alternative) applies rather than FALLBACK.

- **G6 -> G7, G8, G9 [AND] (sequential)**
  - **Justification**: Enabling tray retrieval requires knowing who can help (G7) before coordinating the actual retrieval (G8), with tracking/verification (G9) accompanying/following that coordination. All three are explicitly described duties.

- **G8 -> AT4, AT5, AT6, AT7 [OR] (parallel, "#")**
  - **Justification**: "Cooperation with the inpatient, a companion, a nurse, or another robot" is an explicit list of alternative cooperators, with no stated order of preference.

- **G9 -> G10, G11, G12 [AND] (FALLBACK combined with sequence: G10;FALLBACK(G11,G12))**
  - **Justification**: Indicating the meal must happen first. Then, the normal expected behavior is that tracking shows a correct retrieval (G11); the text explicitly introduces an exception — "alert **if** a wrong meal is retrieved" (G12) — which is a textbook FALLBACK trigger (normal behavior + condition-triggered alternative).

- **G13 -> G14, G15, G18 [AND] (sequential)**
  - **Justification**: A pickup call must occur, then the door must be opened, then the dishes can be collected — a necessary physical/logical sequence described in the text ("can call a robot to pick up the dishes... that person can signal if they can open the door **when the robot comes to it**").

- **G15 -> G16, G17 [AND] (sequential)**
  - **Justification**: The robot must learn whether the person can open the door before/while coordinating which door-opening strategy (OR-branch in G17) to use.

- **G17 -> AT13, AT14 [OR] (parallel, "#")**
  - **Justification**: "Cooperation with another robot or a human" is an explicit alternative with no stated order.

- **G18 -> AT15, AT16, AT17 [OR] (parallel, "#")**
  - **Justification**: "Unassisted, with the cooperation of two robots, or with the cooperation of robots and a human" is an explicit three-way alternative with no stated order or failure trigger.

- **Leaf goals -> their single task** (G3→AT1, G5→AT2, G7→AT3, G10→AT8, G11→AT9, G12→AT10, G14→AT11, G16→AT12) **[AND, trivial]**
  - **Justification**: Each of these goals is realized by exactly one concrete operational step; no further decomposition is warranted by the text.
