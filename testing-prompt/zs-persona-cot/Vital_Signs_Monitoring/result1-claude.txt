# Goal Model Design – Multi-Robot Hospital Vital-Signs Checking Mission

## Step-by-Step Reasoning

**1. Finding the root intention.**
The mission text has three "levels" of concern that keep recurring:
(a) the *recurring operational cycle* ("every two hours... visit every occupied room"), (b) *contingency for timing infeasibility* ("additional robots can be assigned... if no combination of robots can complete the mission"), and (c) nothing else at the top level. Because the text explicitly gives a **normal procedure** (a single assigned robot does the round) and **two explicit, ordered fallbacks** (add robots → if still infeasible, alert the manager), this is a textbook nested **FALLBACK**: `FALLBACK(FALLBACK(G2, AT26), AT27)`. This becomes the root goal **G1**.

**2. Decomposing "visit every occupied room".**
Two distinct intentions hide inside this sentence: (i) *deciding the order* in which rooms are visited (needed because "all high-risk patients must be checked in the first 15 minutes" is an explicit scheduling/priority constraint), and (ii) *actually performing* the per-room cycle. Since computing the order logically has to happen before executing it, and the text gives an explicit temporal constraint (15 minutes), I modeled this as **sequential** (`;`), not fallback (no failure/condition is involved) and not parallel (order matters). I deliberately avoided creating a duplicate "check high-risk patient" subtree — that would duplicate the intention of "checking a patient," which already exists once in the model (redundancy rule). The 15-minute constraint is captured as the **target condition** of the ordering goal instead.

**3. The per-room cycle.**
The text gives an explicit chronological script: *travel → check availability & battery (before entering) → identify patient → approach/announce/instruct → collect vitals (with failure handling) → mark done/proceed → (conditionally) sterilize/disinfect*. This is an explicit sequence, so **sequential** execution was used throughout this backbone.

**4. Pre-entry checks (availability & battery).**
The description uses an explicit conjunction ("check if the patient is available... **and if** there is enough battery") with no stated order between the two checks → **AND + parallel**. Each check individually has an explicit **IF-triggered alternative** ("if not available → come back in 5 min"; "if not enough battery → recharge and reassign") → each becomes its own **FALLBACK**.

**5. Identifying the patient.**
"either by asking or by scanning the... barcode" is a textbook **OR particle** → **OR decomposition**. Since no order/failure condition between the two methods is stated, I used **parallel (#)** runtime (meaning: no obligation on order, not a FALLBACK) rather than FALLBACK, reserving FALLBACK strictly for explicit failure-triggered alternatives.

**6. Vital-signs collection depends on patient condition.**
Infectious, post-surgical and diabetic patients require different (possibly overlapping) measurement sets. Since a patient can have more than one condition simultaneously, satisfying *whichever applicable branch(es)* is enough to fulfill the parent — this is modeled as **OR** (OR does not forbid multiple children being true at once, it only requires at least one), with **parallel** runtime since no order is stated between condition types. Inside each condition branch, all listed vitals are mandatory and unordered → **AND + parallel**.

**7. Failure handling cascade.**
"Failure of collecting any vital sign → trigger questions" and "non-response → alert nurse/doctor" are two chained, explicit IF-triggered alternatives → nested **FALLBACK** structures at two levels (collection→questions, questions→alert).

**8. Post-room hygiene.**
Sterilization (if infectious-disease room) and actuator disinfection (if patient contact occurred) are triggered by **two independent conditions** that may or may not both apply to the same room visit → **OR** (either/both may be needed) with **parallel** runtime (no stated order).

**9. Goal types.**
- **Query** was used only for the single genuinely information-seeking goal (identify the patient).
- **Perform** was used for pure action-execution goals with no deeper world-state target (announce/instruct, mark done, send alerts, sterilize, disinfect) — success is simply "the action was executed."
- **Achieve** was used wherever the text implies a state to be reached, especially under uncertainty/fallback (availability confirmed, battery confirmed, vitals collected, mission completed in time, etc.).

**10. Pruning.** I avoided creating goals that would only ever have a single child (which would break the "minimum two subgoals" rule and risked looking like padding); where the text names only one action for a requirement (e.g., diabetes → glucose, sterilize, disinfect, assign robots, alert manager), that action is attached directly as a **task** under the nearest goal that already has a sibling to decompose into, instead of wrapping it in a redundant one-child goal.

## Logical Relationships

- **G1 -> G2, AT26, AT27 [AND] [FALLBACK(FALLBACK(G2, AT26), AT27)]**
  - **Justification**: Normal procedure (G2) is attempted first; if the mission can't be completed in time, additional robots are assigned (AT26) as a first fallback; if still infeasible, the site manager is alerted (AT27) as a second, nested fallback — explicitly stated in that order.

- **G2 -> AT1, G3 [AND] (sequential)**
  - **Justification**: A visiting order must be computed before rooms can be visited in that order (logical prerequisite, consistent with the explicit 15-minute high-risk constraint).

- **G3 -> AT2, G4, G8, G9, G17 [AND] (sequential)**
  - **Justification**: The text narrates travel, then pre-entry checks, then identification, then the in-room procedure, then (conditional) hygiene, in that explicit order.

- **G4 -> G5, G6 [AND] (parallel)**
  - **Justification**: "check if the patient is available... and if there is enough battery" — both required, no stated order.

- **G5 -> AT3, AT4 [AND] [FALLBACK(AT3, AT4)]**
  - **Justification**: "If the patient is not available, the robot should come back in 5 minutes" — explicit condition-triggered alternative.

- **G6 -> AT5, G7 [AND] [FALLBACK(AT5, G7)]**
  - **Justification**: "If there is not enough battery, the robot should recharge..." — explicit condition-triggered alternative.

- **G7 -> AT6, AT7 [AND] (parallel)**
  - **Justification**: "recharge **and** the tasks need to be reassigned" — explicit conjunction, no order stated.

- **G8 -> AT8, AT9 [OR] (parallel)**
  - **Justification**: "either by asking or by scanning" — explicit alternative identification methods, no failure condition or order stated.

- **G9 -> AT10, G10, G11, G16 [AND] (sequential)**
  - **Justification**: "approach... announce... instructions... [vitals]... mark it as done and proceed" — explicit order.

- **G10 -> AT11, AT12 [AND] (sequential)**
  - **Justification**: Announcement logically precedes instructions; both explicitly required.

- **G11 -> G12, G15 [AND] [FALLBACK(G12, G15)]**
  - **Justification**: "The failure of collecting any necessary vital signs should trigger a set of questions" — explicit failure-triggered alternative.

- **G12 -> G13, G14, AT19 [OR] (parallel)**
  - **Justification**: Condition-dependent branches (infectious, post-surgical, diabetic); a patient may require one or several — fulfilling the applicable branch(es) is sufficient; no order between condition types.

- **G13 -> AT13, AT14, AT15, AT16 [AND] (parallel)**
  - **Justification**: "must be checked for heart rate, blood pressure, body temperature, and blood oxygenation" — explicit AND list, no order.

- **G14 -> AT17, AT18 [AND] (parallel)**
  - **Justification**: "must be checked for heart rate and blood oxygenation" — explicit AND list, no order.

- **G15 -> AT20, AT21 [AND] [FALLBACK(AT20, AT21)]**
  - **Justification**: "In case of non-response, an alert should be sent" — explicit failure-triggered alternative.

- **G16 -> AT22, AT23 [AND] (sequential)**
  - **Justification**: "mark it as done and proceed to the next room" — explicit sequential pair.

- **G17 -> AT24, AT25 [OR] (parallel)**
  - **Justification**: Sterilization (infectious-disease condition) and actuator disinfection (patient-contact condition) are independently triggered and may not both apply to the same visit; no order stated.

**Modeling notes:**
- `occupied_rooms` and `N` are introduced as the only two variables used (a room collection and a fleet-size bound), both directly grounded in the text ("occupied room," "additional robots").
- No goal/task was included that lacks a robot executor (e.g., pure administrative scheduling by non-robot staff is not in the model).
- I removed several would-be single-child goals (e.g., a standalone "sterilize" goal) and attached their task directly to the nearest multi-child parent, to respect the minimum-two-children rule for AND/OR decomposition without inventing padding siblings.
