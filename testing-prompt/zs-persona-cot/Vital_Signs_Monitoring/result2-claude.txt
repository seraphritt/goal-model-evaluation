# Hospital Vital-Signs Monitoring — Goal Model for a Multi-Robot System

## 1. Step-by-step reasoning and modeling decisions

Before building the tables, here is how I read the mission and the key choices I made (and why):

**1. Finding the root intention.** "Every two hours, all patients' vital signs should be checked" is the mission trigger; "the assigned robot should visit every occupied room" is the *means*. I made the periodic check the root goal (G1) and split it into two AND-required concerns: (a) actually visiting/processing rooms (G2), and (b) guaranteeing this is *feasible* in the required time, escalating to extra robots or the manager if not (G11). These are two genuinely different intentions (execution vs. feasibility assurance), so they are not redundant.

**2. High-risk timing constraint.** "All patients in high risk must be checked in the first 15 minutes" is **not** a different action from "visit and check a room" — it is a scheduling constraint on the *same* action. Creating a separate branch for "high-risk rooms" would duplicate the entire per-room procedure (approach, collect vitals, escalate, etc.), which violates the "avoid redundancy" rule. I therefore folded this constraint into G2's target condition/justification rather than creating a parallel subtree.

**3. Pre-entry checks (availability & battery).** The text says both must be checked "before entering," joined by "and," with no stated order between the two checks themselves → **AND decomposition, parallel runtime** between the availability-branch and the battery-branch. Each branch, however, *does* have an explicitly stated order-on-failure ("if not available… if not enough battery…") → that is a textbook **FALLBACK** trigger (IF-condition), not an OR.

**4. Patient identification.** "Identify the correct patient either by asking or by scanning the barcode" is an explicit OR in the text, so it's modeled as an OR-decomposed task. I placed it under the availability check because you must know *which* patient you're asking about before you can query their availability — this is a logically necessary order, so I used a sequential runtime annotation (identify ; query).

**5. Nested fallback for vital-sign failure.** This is the cleanest case in the whole description, because it matches the prompt's own example almost literally: normal path = collect vitals; if that fails → ask assessment questions; if *that* fails (non-response) → alert staff. This is exactly `FALLBACK(FALLBACK(exp1, exp2), exp3)`.

**6. Condition-specific checklists (infectious/post-surgical/diabetic).** These are not alternatives in the sense of "pick one forever" — a patient could be both infectious *and* diabetic. But structurally, each is a self-sufficient branch triggered by a patient attribute (fulfilling one is enough to satisfy that part of the model for that condition), and the description never requires a patient to satisfy *all three* checklists. That fits the definition of OR decomposition ("fulfillment of one child is sufficient") better than AND. I used parallel runtime since no order is stated between the three.

**7. Perform vs. Achieve vs. Query split.** I deliberately layered these: "Collect vitals and escalate if necessary" is an **Achieve** goal (it has a real target condition and a fallback-driven path to reach it), while "execute the specific measurement for this condition" is a **Perform** goal underneath it (success = action executed, no deeper state to verify). The same pattern is used for "approach/announce/instruct" (Perform) and for disinfecting/sterilizing (Perform). The two identification/availability goals and the battery goal are **Achieve** (they reach a state: patient available, battery sufficient). The identify+query bundle is a **Query** goal (its only purpose is to obtain information).

**8. Hygiene steps.** Sterilization (infectious-disease rooms) and actuator disinfection (any patient-contact task) are two independent, textually explicit obligations. I treated them as AND-siblings under one "hygiene" goal: both are standing policies of the mission, even though in a single mission instance only the applicable one(s) fire.

**9. Mission feasibility cascade.** "Additional robots can be assigned… alerted if no combination of robots can complete the mission" mirrors the vital-sign escalation pattern exactly → another nested FALLBACK: baseline single robot → add robots → alert manager.

**10. Locations.** The description only ever names two location concepts: **room** (occupied hospital room) and **site** (used for the manager — "responsible manager for the site"). I did not invent a "charging station," so battery-recharge/coordination-level tasks are scoped to **Site** when they are not room-specific, and to **Room** when they occur as part of the in-room routine.

**11. Number of robots.** The description consistently says "the assigned robot" (singular) for the room-visiting routine, so all in-room tasks are 1-robot tasks. Where the text explicitly opens the door to more robots ("additional robots can be assigned," "tasks need to be reassigned"), I used a range **[1, N]**, with N denoting the (variable) maximum number of robots available at the site.

## 5. Logical Relationships

- **G1 -> G2, G11 [AND] (parallel)**
  - **Justification**: Executing the rounds (G2) and guaranteeing feasibility/escalation (G11) are both mandatory for mission success; the text gives no order between them — feasibility assurance applies continuously, not after the rounds.

- **G2 -> G3, G5, G6, AT20 [AND] ((G3 # G5) ; G6 ; AT20)**
  - **Justification**: Both pre-entry checks are required ("must check… and if…") with no stated order between each other (parallel), but the text explicitly orders checks → in-room work → next room (sequential).

- **G3 -> G4, AT5 [AND] FALLBACK(G4, AT5)**
  - **Justification**: "If the patient is not available, the robot should come back in 5 minutes" is an explicit IF-triggered alternative to the normal identify/confirm path.

- **G4 -> AT1, AT4 [AND] (sequential: AT1 ; AT4)**
  - **Justification**: You must identify the correct patient (needed because of multi-bed rooms) before you can meaningfully query *their* availability.

- **AT1 -> AT2, AT3 [OR]**
  - **Justification**: "Either by asking or by scanning the patient's barcode" is an explicit textual alternative.

- **G5 -> AT6, AT7, AT8 [AND] FALLBACK(AT6, (AT7 # AT8))**
  - **Justification**: "If there is not enough battery, the robot should recharge and the tasks need to be reassigned" is an explicit IF-triggered alternative to proceeding; recharge and reassignment are joint consequences with no stated order (parallel).

- **G6 -> G7, G8, AT17, G10 [AND] (sequential: G7 ; G8 ; AT17 ; G10)**
  - **Justification**: The description lists these steps in an explicit temporal order (approach/announce/instruct → collect vitals/escalate → mark done → exit/sterilize).

- **G7 -> AT9, AT10, AT11 [AND] (sequential: AT9 ; AT10 ; AT11)**
  - **Justification**: "approach the patient, announce the procedure… and provide instructions" is stated in that exact order, and all three are required.

- **G8 -> G9, AT15, AT16 [AND] FALLBACK(FALLBACK(G9, AT15), AT16)**
  - **Justification**: Normal collection (G9), on failure → assessment questions (AT15), on non-response → staff alert (AT16); a direct match to the nested-fallback pattern.

- **G9 -> AT12, AT13, AT14 [OR] (parallel: AT12 # AT13 # AT14)**
  - **Justification**: Each checklist is triggered by a distinct, non-exclusive patient condition; fulfilling the applicable branch is sufficient for that condition, and the text gives no order among them.

- **G10 -> AT18, AT19 [AND] (parallel: AT18 # AT19)**
  - **Justification**: Both hygiene obligations are explicitly stated as standing requirements ("must be sterilized," "should disinfect its actuators afterwards") with no stated order between them.

- **G11 -> AT21, AT22, AT23 [AND] FALLBACK(FALLBACK(AT21, AT22), AT23)**
  - **Justification**: Baseline single-robot execution, escalating to additional robots, escalating further to a manager alert — the same explicit two-step IF-triggered escalation pattern used for vital-sign failures.

---

A couple of modeling calls worth flagging explicitly: (1) I treated the "check" steps (availability, battery) as the gating condition for their own FALLBACK, since the mission text frames them exactly as IF-conditions with a stated alternative — a defensible but not the only valid reading. (2) The hygiene goal (G10) is modeled as AND at the policy level even though, for any single room, only the applicable branch(es) actually execute — this reflects that both are standing mission obligations, not mutually exclusive alternatives.
