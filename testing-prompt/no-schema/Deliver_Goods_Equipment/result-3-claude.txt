# Multi-Robot Mission Decomposition: Hospital Resource Collection & Delivery

## Step-by-Step Reasoning Process

Before building the tables, here is how I read and decomposed the description:

**1. Identify the actors involved.**
- The **assigned robot** (primary executor)
- The **requesting agent** (destination stakeholder)
- The **storage** (a reactive system that receives requests and releases resources)
- A **backup robot** (receives reassigned missions/tasks)
- The **sector manager** (human stakeholder, notified only on failure)
- An implicit **fleet/mission coordinator** (something must decide *which* robot gets *which* resource when several are needed — the text doesn't name it, but "multiple robots can be assigned" implies an assignment function)

**2. Identify the top-level mission.** The root is a classic *Achieve* goal: "collect the required resources... and deliver them to the requesting agent in a specified location." This naturally splits into two explicitly named phases: **Collection** and **Delivery** ("Once retrieved, the delivery phase begins") — a strict **sequential** dependency, not parallel, because delivery cannot start before collection ends.

**3. Isolate the "selection logic" as a Query, not an Achieve goal.** "The order to be followed is defined by the estimation of waiting time summed up with the path" is a *computation*, not a world-state change — this is a **Query** goal (it produces information: the visit order), consumed by an Achieve goal (visiting/retrieving).

**4. Treat battery-related clauses as FALLBACK branches, not as independent goals.** Both "if battery runs low in collection" and "if battery runs low in delivery" are **conditional alternative executions** of the respective phase. Per the output format's own rule, FALLBACK decompositions are forced to **AND** relation — meaning the model must contain *both* the nominal path and the contingency path as mandatory parts of a resilient goal, even though only one executes at runtime.

**5. Notice the asymmetry between the two battery thresholds (10% vs 30%) — this is a design signal, not an inconsistency.** During collection, the robot carries nothing yet, so it only needs enough energy to reach a recharge station — 10% is an acceptable safety margin. During delivery, the robot is carrying a resource and must still reach a checkpoint *and* hand off cleanly — a riskier, more demanding maneuver — justifying a larger 30% safety margin. I treat the delivery fallback as a **more complex goal** with its own nested contingency.

**6. Identify a second-level (nested) fallback.** "In case of failure to return the resource to a checkpoint, an alert must be triggered..." is a **fallback of a fallback** — it only fires if the already-exceptional checkpoint-return action itself fails. This is modeled as a child FALLBACK underneath the delivery-battery-handling goal.

**7. Treat the multi-item/multi-storage clause as a multiplicity rule, not a new branch of the tree.** "Multiple robots can be assigned to parallel collect-deliver tasks" doesn't change *what* a robot does — it changes *how many instances* of the same Collection→Delivery unit run concurrently. I model this as a **parallel multiplicity** on the "Collect-and-Deliver Execution" goal rather than duplicating the whole subtree.

**8. Assign Goal Types using KAOS-like semantics:**
   - **Achieve** → goals with a measurable target condition (deliver, retrieve, return, assign).
   - **Query** → goals that only produce a decision/estimate used downstream (ordering, run-count).
   - **Perform** → goals that are purely coordinative/procedural hand-offs with no durable state condition to verify (reassigning responsibility to another robot).

**9. Check for OR relations.** I found **none**. Everything in the text is either a mandatory sequential/parallel step or a triggered contingency (AND via FALLBACK). The mission is fully deterministic given its triggers — there are no described "pick one of several equally valid strategies" situations. This is worth flagging explicitly in the model.

**10. Flag a notation gap: repetition/looping.** "The robot will make as many runs as necessary" and "go to the storage places" (plural) describe **iteration**, which the `#`/`;`/`FALLBACK` vocabulary doesn't natively express. I annotate these as sequential blocks that **repeat N times**, and note this as a modeling limitation at the end.

└─ G3  Collect-and-Deliver Execution  (⇉ parallel instances per resource/storage pair)
    ├─ G4  Resource Collection Phase                              [Achieve]
    │   ├─ G4.1  Determine Storage Visit Order                    [Query]
    │   ├─ G4.2  Retrieve Resource from Storage                   [Achieve]

## Logical Relationships

- **G1 -> G2, G3 [AND][sequential (;)]**
  - **Justification**: Robots cannot be assigned work (G3) before the system knows what is needed and who will do it (G2). The description implicitly requires planning before action.

- **G2 -> G2.1, G2.2 [AND][sequential (;)]**
  - **Justification**: You cannot assign robots to resource-storage pairs (G2.2) before those pairs are identified (G2.1) — a strict information-dependency.

- **G2.1 -> AT1 [AND][sequential (;)]**
  - **Justification**: Single leaf task realizing the identification goal.

- **G2.2 -> AT2 [AND][sequential (;)]**
  - **Justification**: Single leaf task realizing the assignment goal.

- **G3 -> G4, G5 [AND][sequential (;)]**
  - **Justification**: Explicitly stated — "Once retrieved, the delivery phase begins" — delivery strictly follows collection for a given robot; there is no ambiguity here.

- **G3 -> G3₍a₎, G3₍b₎, ..., G3₍n₎ [AND][parallel (#)]** *(multiplicity rule, not a structural decomposition)*
  - **Justification**: "When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks to reduce the time to finish the mission." Each parallel instance is a full copy of the G3 subtree, assigned to a different robot by G2.2.

- **G4 -> FALLBACK(G4.1 ; G4.2, G4.3) [AND]**
  - **Justification**: Normal collection path is "determine order then retrieve" (sequential); if battery hits 10% at any point, execution diverts to G4.3 instead. Per the format rule, FALLBACK decompositions are AND (both the nominal and contingency branches are mandatory parts of a resilient goal).

- **G4.1 -> AT3 [AND][sequential (;)]**
  - **Justification**: Single leaf task.

- **G4.2 -> AT4, AT5, AT6 [AND][sequential (;), repeated per storage]**
  - **Justification**: "go to the storage... sends a message... waits until... retrieved" is a strict three-step order, repeated once per storage in G4.1's computed sequence.

- **G4.3 -> G4.3.1, G4.3.2 [AND][parallel (#)]**
  - **Justification**: Both returning to recharge and reassigning the mission are mandatory ("goes back... and assigns..."), but they don't causally depend on each other — the hand-off can be communicated while the robot is still en route to recharge — so they are modeled as concurrent, independent obligations.

- **G4.3.1 -> AT7 [AND][sequential (;)]** / **G4.3.2 -> AT8 [AND][sequential (;)]**
  - **Justification**: Each is realized by a single atomic task.

- **G5 -> FALLBACK(G5.1 ; G5.2, G5.3) [AND]**
  - **Justification**: Same pattern as G4 — nominal delivery path (compute runs, then transport) versus the 30%-battery contingency (G5.3), both mandatory per the FALLBACK/AND rule.

- **G5.1 -> AT9 [AND][sequential (;)]**
  - **Justification**: Single leaf task.

- **G5.2 -> AT10, AT11, AT12 [AND][sequential (;), repeated per run]**
  - **Justification**: "make as many runs as necessary" — each run is navigate → hand over → (if needed) return for the next load, repeated N times (N from G5.1).

- **G5.3 -> G5.3.1, G5.3.2 [AND][sequential (;)]**
  - **Justification**: Unlike G4.3, these are sequential rather than parallel: the reassignment (G5.3.2) must communicate *where* the resource is, which is only known/finalized once G5.3.1 has concluded (successfully or not).

- **G5.3.1 -> FALLBACK(AT13, G5.3.1.F) [AND]**
  - **Justification**: The robot's primary move is simply to place the resource at the checkpoint (AT13); "in case of failure" triggers the nested alert/report branch (G5.3.1.F) — a second-level FALLBACK, again forced to AND.

- **G5.3.1.F -> AT14, AT15 [AND][sequential (;)]**
  - **Justification**: "an alert must be triggered and the report sent" — triggering the alert is the immediate automated signal; the detailed report to the sector manager follows as the next step.

- **G5.3.2 -> AT16 [AND][sequential (;)]**
  - **Justification**: Single leaf task carrying the hand-off, including the resource's known location.

## Reflections & Modeling Notes

1. **No OR relations appear anywhere in this model.** The mission description is fully deterministic: every branch point is a *triggered contingency* (battery level, placement failure), not a *free choice* between equally valid strategies. If future requirements introduce, say, a choice between two checkpoint locations or two delivery strategies, OR nodes would become necessary — currently they are not.

2. **Asymmetric battery thresholds (10% vs. 30%) encode risk, not inconsistency.** I modeled the collection-phase fallback as *parallel* (return + reassign can happen concurrently) but the delivery-phase fallback as *sequential* (place resource, then reassign with its location) — because the delivery contingency carries a physical dependency (the hand-off message is only meaningful once the resource's position is settled) that the collection contingency does not have.

3. **Repetition/looping is not natively expressible** in the `#` / `;` / `FALLBACK` vocabulary provided. Both "go to the storage places" (plural, G4.2) and "make as many runs as necessary" (G5.2) are loops over a dynamically computed count (from G4.1 and G5.1 respectively). I annotated these as sequential blocks "repeated per storage/run" — if the target modeling tool supports a native iteration/cardinality operator, I'd recommend introducing one rather than overloading `;`.

4. **"Mission" vs. "remaining task" reassignment are intentionally different goals (G4.3.2 vs. G5.3.2).** In the collection-phase fallback the text says "assigns **the mission**" (the whole job, since nothing has been delivered yet), while in the delivery-phase fallback it says "assign **the remaining task**... which will know where the resource is positioned" (only the delivery leg continues, because collection is already done and the resource physically exists at a known point). Treating these as distinct goals avoids conflating a full mission hand-off with a partial one.

5. **Some tasks have "0" or "2" robots rather than the default "1."** AT1/AT2 (resource identification and assignment) are plausibly performed by a central/fleet-level system rather than any single robot — the text never states a robot does this planning. AT8 and AT16 (hand-offs) inherently involve two robots interacting. These are explicit assumptions since the text doesn't name the planning actor; if your architecture uses one of the robots as an ad hoc coordinator instead of a central system, AT1/AT2's "Number of Robots" would change to 1.

6. **Domain generalization**: the Location column is grounded in the hospital examples given (sterile equipment from sterile facilities; clean linens from the laundry), but the goal/task structure itself is domain-agnostic — swapping "Hospital" for "Warehouse," "Restaurant," or "Airport" would not require any structural change to the goal tree, only to the Location and possibly the destination-task semantics (AT10/AT11).
