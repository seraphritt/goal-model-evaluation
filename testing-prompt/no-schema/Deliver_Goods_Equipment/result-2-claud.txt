# Multi-Robot Mission Goal Model — Collect & Deliver Resources

## Part 1 — Step-by-Step Reasoning

Before building the tables, I worked through the description the way a mission designer would: isolating the actors, the macro-phases, the explicit exceptions, and the parts that are implied but not literally stated.

**Step 1 — Identify the actors and the trigger.**
The mission is event-triggered ("*when required*"). Actors: the assigned robot(s), the storage(s), the requesting agent, a substitute robot, a sector manager. This gives me a natural root goal: *fulfil a resource request end-to-end*.

**Step 2 — Identify the macro-phases.**
The text explicitly names two phases — "*In the collection phase…*" and "*Once retrieved, the delivery phase begins*" — and states they are strictly ordered (delivery cannot start before retrieval). This is a clean **sequential AND** decomposition.

**Step 3 — Identify the planning/ordering logic as a separate concern.**
Two different "ordering" problems appear in the text and must **not** be collapsed into one goal:
- *Inter-robot allocation*: "when multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks." This is a **mission-level allocation** decision (which robot handles which storage).
- *Intra-robot ordering*: "the order to be followed is defined by the estimation of waiting time summed up with the path…" This is a **route-ordering** decision a single robot makes among its own assigned storages.
I modeled these as two distinct Query goals (G2 and G4.1.1) to avoid conflating fleet-level planning with single-robot routing.

**Step 4 — Identify the exception-handling structure.**
Both phases carry an explicit "if battery low → do X instead" clause. This is the textbook **Fallback pattern**: a normal execution path and a contingency path that only fires under a guard condition, but both must exist in the model (hence the instruction that Fallback uses an AND relation — the model contains *both* branches, even though only one executes at runtime).
I also noticed a **nested fallback**: inside the delivery-phase contingency, "*in case of failure to return the resource to a checkpoint*" is itself a fallback-of-a-fallback. This told me the model needs at least two levels of Fallback nesting to be faithful to the text.

**Step 5 — Notice the differentiated battery thresholds (10% vs 30%) and reflect on *why*.**
This is not arbitrary. In the collection phase the robot is *unladen* — aborting only costs time. In the delivery phase the robot is *carrying a resource* and must still reach a checkpoint — a failure here strands a physical resource and triggers a manager alert, a strictly worse outcome. A higher safety margin (30%) before the more consequential phase is a deliberate design pattern, so I made sure the justification column of G5.2 calls this out explicitly rather than treating both thresholds as interchangeable.

**Step 6 — Identify implicit/inferred goals (transparency check).**
Two goals are necessary for the described behavior to be *possible*, even though the text doesn't name them as actions:
- **Battery monitoring (G7)** — the 10%/30% thresholds can only trigger a fallback if something continuously evaluates battery level. I added this as a Query goal rather than assuming it is "free."
- **Completion confirmation (G6)** — "deliver to the requesting agent" implies a checkable end-state; I added an explicit confirmation goal so the mission has a verifiable closure, which is standard practice in goal-oriented mission specs.
I flag both as *inferred* rather than *literal* in their justifications.

**Step 7 — Decide AND vs OR.**
I found no genuine alternative-means-to-an-end in the text (no "the robot may either do A or B to satisfy the same goal"). Robot *selection* during reassignment is a resource-allocation matter (handled inside the Query goals G2/handoff tasks), not a goal-decomposition OR. So every decomposition in this model is **AND**, with **Fallback** used specifically where the text describes conditional/exceptional substitution — consistent with the instruction that Fallback itself must be expressed as AND.

**Step 8 — Decide Runtime operators.**
- Sequential `[;]` where the text gives an explicit order (collection→delivery; determine order→go→request→wait; deposit→confirm).
- Parallel `[#]` where (a) the text explicitly calls for parallelism (multiple robots across storages), or (b) two mandated outcomes have no stated dependency on each other and delaying one to wait for the other would be operationally wasteful (e.g., "return to recharge" and "reassign mission" — reassigning doesn't need to wait for the physical return trip).
- `FALLBACK(...)` strictly for the two explicit battery contingencies and the nested checkpoint-failure contingency.

**Step 9 — Separate Goals (the "what/why") from Tasks (the "how/where/who").**
Every leaf goal (one with no sub-goals) is operationalized by exactly one concrete Task carrying Location and Number-of-Robots — this is where the hospital examples (sterile equipment, linens) become useful: they tell me how to instantiate generic "Location" values (storage = sterile facility/laundry; delivery destination = operating room/use point/storage room) while keeping the model domain-agnostic enough to also fit "street" or "restaurant" scenarios, as the output format itself hints.

**Step 10 — Note on "periodically."**
The linens example ("should periodically be moved") doesn't require a new goal type (no *Maintain* type is offered). I treat periodicity as an external scheduler re-triggering the root goal G1 at intervals — the goal model itself stays the same per occurrence.

## Part 2 — Goal Model Hierarchy (overview)

```
G1 Fulfill Resource Request
 ├─ G2 Plan Collect-Deliver Allocation
 ├─ G3 Execute Collect-Deliver Mission(s)
 │   ├─ G4 Perform Collection Phase        FALLBACK
 │   │   ├─ G4.1 Execute Normal Collection Sequence
 │   │   │   ├─ G4.1.1 Determine Storage Visit Order
 │   │   │   ├─ G4.1.2 Reach Storage Location
 │   │   │   └─ G4.1.3 Request and Retrieve Resource
 │   │   └─ G4.2 Handle Collection-Phase Low-Battery Contingency
 │   │       ├─ G4.2.1 Return to Recharging Station
 │   │       └─ G4.2.2 Reassign Collection Mission to Substitute Robot
 │   ├─ G5 Perform Delivery Phase          FALLBACK
 │   │   ├─ G5.1 Execute Normal Delivery Sequence
 │   │   │   ├─ G5.1.1 Transport Resource Runs to Delivery Location
 │   │   │   └─ G5.1.2 Confirm All Resources Relocated
 │   │   └─ G5.2 Handle Delivery-Phase Low-Battery Contingency
 │   │       ├─ G5.2.1 Return Resource to Checkpoint   FALLBACK
 │   │       │   ├─ G5.2.1.1 Deposit Resource at Checkpoint
 │   │       │   └─ G5.2.1.2 Trigger Alert and Report to Sector Manager
 │   │       └─ G5.2.2 Reassign Remaining Delivery Task to Substitute Robot
 │   └─ G7 Monitor Robot Battery Status (parallel, cross-cutting)
 └─ G6 Confirm Mission Completion
```

## Part 6 — Logical Relationships

**G1 -> G2, G3, G6 [AND][sequential]**
- **Justification**: The mission must be planned, then executed, then confirmed — "collect...and deliver" implies ordered macro-steps culminating in a verifiable outcome.

**G3 -> G4, G5 [AND][sequential]**
- **Justification**: "Once retrieved, the delivery phase begins" — delivery is explicitly gated on collection's completion.

**G3 -> G7 [AND][parallel]**
- **Justification**: Battery must be monitored continuously throughout both G4 and G5 for the stated thresholds (10%/30%) to ever be detected; it does not wait for either phase to finish.

**G4 -> G4.1, G4.2 [AND][FALLBACK(G4.1, G4.2)]**
- **Justification**: The text gives a normal collection procedure plus an explicit low-battery exception that substitutes for it — the canonical Fallback pattern, expressed with AND per the Fallback rule.

**G4.1 -> G4.1.1, G4.1.2, G4.1.3 [AND][sequential]**
- **Justification**: The text orders these steps explicitly: compute order → travel → request/wait.

**G4.2 -> G4.2.1, G4.2.2 [AND][parallel]**
- **Justification**: "goes back to the recharging station and assigns the mission to another robot" are two independent, simultaneously-launchable outcomes — reassignment shouldn't wait on the physical return trip.

**G5 -> G5.1, G5.2 [AND][FALLBACK(G5.1, G5.2)]**
- **Justification**: Same pattern as G4, triggered instead by the delivery-phase (30%) threshold.

**G5.1 -> G5.1.1, G5.1.2 [AND][sequential]**
- **Justification**: Transport runs must occur before completeness can be confirmed.

**G5.2 -> G5.2.1, G5.2.2 [AND][parallel]**
- **Justification**: Mirrors G4.2's reasoning — checkpoint return and task reassignment are independent mandatory outcomes of the same contingency.

**G5.2.1 -> G5.2.1.1, G5.2.1.2 [AND][FALLBACK(G5.2.1.1, G5.2.1.2)]**
- **Justification**: "In case of failure to return the resource to a checkpoint, an alert must be triggered..." is an explicit nested exception — a Fallback inside a Fallback.

**G2 -> T1 [AND]** / **G4.1.1 -> T2 [AND]** / **G4.1.2 -> T3 [AND]** / **G4.1.3 -> T4 [AND]** / **G4.2.1 -> T5 [AND]** / **G4.2.2 -> T6 [AND]** / **G5.1.1 -> T7 [AND]** / **G5.1.2 -> T8 [AND]** / **G5.2.1.1 -> T9 [AND]** / **G5.2.1.2 -> T10 [AND]** / **G5.2.2 -> T11 [AND]** / **G6 -> T12 [AND]** / **G7 -> T13 [AND]**
- **Justification**: Each of these goals is a leaf in the hierarchy with a single, mandatory concrete operationalization — no alternative means are described in the text for any of them, so every goal-to-task link is AND rather than OR.
