# Mission Analysis: Resource Collection & Delivery (Multi‑Robot System)

Before building the model, I worked through the description as a mission designer would — identifying the trigger, the actors, the phases, the decision points, and (most importantly) the exception paths, since those are usually where goal models go wrong if you rush them.

## Step‑by‑step reasoning

**1. Find the root goal and its trigger.**
The first sentence — *"When required, a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location"* — is a complete service contract: a trigger ("when required"), an actor (a robot), and an end-state (resources in the requester's hands, at a place). This is a classic **Achieve** goal with a clear **Target Condition**, so it becomes my root, **G0**.

**2. Separate "deciding who does it" from "doing it."**
The last paragraph introduces something easy to miss if you only read linearly: *"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks."* This is not a step inside the collection or delivery phase — it's a **prior decision** about how many robots to use and which storages each one covers. I gave this its own goal (**G1**) rather than folding it into collection, because (a) it must be resolved *before* any robot starts moving, and (b) it is explicitly justified by a time-minimization objective ("to reduce the time to finish the mission"), which is the same justification pattern used for the storage-visit ordering goal. That made me classify both as **Query** goals rather than Achieve goals — their output is a decision/estimate, not a physical state.

**3. Respect the explicit phase sequencing.**
*"Once retrieved, the delivery phase begins"* is an unambiguous sequential constraint. So collection (**G2.1**) and delivery (**G2.2**) are AND-decomposed **sequentially**, never in parallel, inside a single robot's mission execution goal (**G2**).

**4. Collection phase: separate "where to go" from "going."**
The order of storages is *computed* ("defined by the estimation of waiting time summed up with the path to be run"), then *executed* (go → request → wait). I modeled the computation as a Query goal (**G2.1.1**) and the physical retrieval loop as an Achieve goal (**G2.1.2**), because retrieval has a real completion condition (resource physically obtained) while ordering only produces information.

**5. Battery handling is a *fallback*, not a *sequel*.**
This was the key design decision. The battery clauses ("if battery runs low… the robot goes back…") don't happen *after* collection/delivery — they can interrupt it at any moment. A sequential model (collect, THEN check battery) would misrepresent this. I modeled it as **FALLBACK(primary, battery-goal)**: the robot pursues the primary task until/unless the threshold is crossed, at which point the fallback preempts it. This also explains why I kept the 10%‑collection case and the 30%‑delivery case as **two distinct goals** rather than merging them: different thresholds, different target conditions (recharge+reassign vs. checkpoint+reassign), different task sets, and the text clearly ties each to its own phase.

**6. Spot the *fallback of a fallback*.**
Re-reading carefully: *"...assign the remaining task to another robot, **which will know where the resource is positioned**. In case of failure to return the resource to a checkpoint, an alert must be triggered..."* The clause "which will know where the resource is positioned" is a hidden precondition: reassignment is only valid *after* the checkpoint deposit succeeds. If the deposit itself fails, the text gives a *different* outcome (alert + report to a human). This is a second, nested FALLBACK — the system escalates to human intervention only when its own automated recovery (checkpoint deposit) breaks. I modeled this as **G2.2.2.1**, nested inside the delivery battery-management goal.

**7. Why collection has a planning sub-goal but delivery doesn't.**
Collection may involve *several* storages (hence an ordering decision is needed). Delivery always targets *one* specified location, so there's nothing to "order" — only to repeat ("as many runs as necessary"). This asymmetry is intentional and mirrors the text.

**8. Where does multi-robot parallelism actually live?**
It does **not** live inside any single task (no task needs two robots acting jointly). It lives at the **instantiation level**: G1 decides *N*, and G2 (the whole collect-deliver cycle) is spawned **N times in parallel**, one per robot/storage-subset. This matches the text precisely: "parallel collect-deliver **tasks**" means parallel *missions*, not parallel *actions within one mission*.

**9. Goal-type discipline.**
I deliberately avoided forcing a "Perform" goal type anywhere above the task level: every composite node in this mission either has a real end-state (Achieve) or produces a decision/estimate (Query). Perform-type behavior (bare actions with no interesting end-state) is what the **Tasks** represent — this keeps the taxonomy honest rather than decorative.

**10. Relation discipline (AND vs OR).**
Nothing in the description offers the robot a genuine *choice* between equally valid alternatives — every branch is either a mandatory step or a conditional/preemptive exception. I therefore used **AND** everywhere (as required for FALLBACK nodes anyway) and explicitly did *not* introduce artificial OR-branches just for variety, since that would misrepresent a deterministic procedure as having optional paths it doesn't have.

**Assumptions I made explicit (since the text doesn't state them):**
- Battery level is monitored continuously, not at discrete checkpoints — this is what makes FALLBACK semantics (preemption) correct instead of plain sequencing.
- "Checkpoint" is a predefined physical waypoint, distinct from the recharging station and from the final delivery location.
- Multiple resources requested from the *same* storage are covered by a single request message (AT5), consistent with "the precise specification of the **requested resources**" being plural.
- G1 (allocation) may be executed by a central fleet coordinator or via inter-robot negotiation — the text specifies the *outcome* (parallel assignment), not the mechanism, so I left this generic.

## Goal hierarchy (overview)

```
G0  Fulfill Resource Request                                                [Achieve]
├─(seq)── G1  Allocate Robot(s) to Resource Request                        [Query]
│          └── AT1
└─(seq)── G2  Execute Collect-and-Deliver Mission  (×N in parallel if N robots) [Achieve]
           ├─(seq)── G2.1  Collection Phase                                 [Achieve]
           │         ├─(seq)── G2.1.1 Plan Storage Visiting Order           [Query]
           │         │          └── AT2 ; AT3
           │         └── FALLBACK
           │              ├─ primary:  G2.1.2 Retrieve Resources from Storages  [Achieve]
           │              │             └── AT4 ; AT5 ; AT6  (repeat per storage)
           │              └─ fallback: G2.1.3 Manage Low Battery – Collection    [Achieve]
           │                            └── AT7 # AT8
           └── FALLBACK
                ├─ primary:  G2.2.1 Transport Resources to Destination      [Achieve]
                │             └── AT9 ; AT10  (repeat per run)
                └─ fallback: G2.2.2 Manage Low Battery – Delivery           [Achieve]
                              └── FALLBACK
                                   ├─ primary:  AT11 ; AT12
                                   └─ fallback: G2.2.2.1 Handle Checkpoint Return Failure [Achieve]
                                                 └── AT13 ; AT14
```

## Logical Relationships

- **G0 -> G1, G2 [AND][(sequential)]**
  - **Justification**: Robot allocation must be resolved before execution begins; the description frames allocation as a precondition ("multiple robots *can be assigned*...") for how execution proceeds, not a concurrent activity.

- **Note (instantiation, not a decomposition)**: **G1 ⟶ {G2}×N [parallel]**
  - **Justification**: *"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks to reduce the time to finish the mission."* Each G2 instance is a self-contained, independent collect-and-deliver cycle for the subset of storages/resources assigned by G1, so instances share no state and can execute fully in parallel — this, not intra-task collaboration, is where the mission's multi-robot scalability actually lives.

- **G1 -> AT1 [AND]**
  - **Justification**: Allocation reduces to a single computation/negotiation act; nothing in the text calls for branching or parallel sub-steps here.

- **G2 -> G2.1, G2.2 [AND][(sequential)]**
  - **Justification**: *"Once retrieved, the delivery phase begins"* is an explicit sequencing constraint — delivery cannot start before the corresponding collection completes.

- **G2.1 -> G2.1.1, FALLBACK(G2.1.2, G2.1.3) [AND][(sequential) then FALLBACK]**
  - **Justification**: The visiting order (G2.1.1) must exist before any storage visit starts. Once visiting begins, normal retrieval (G2.1.2) is the default, but is preempted the instant battery hits 10% by G2.1.3 — exactly FALLBACK semantics, not a sequential follow-up.

- **G2.1.1 -> AT2, AT3 [AND][(sequential)]**
  - **Justification**: Sorting (AT3) needs the per-storage estimates (AT2) to already exist; the text's formula (wait + path) must be computed before an order can be produced.

- **G2.1.2 -> AT4, AT5, AT6 [AND][(sequential), repeated per storage]**
  - **Justification**: The text narrates these three actions in strict order — reach, request, wait — and this triplet must repeat for every storage in G2.1.1's order until all needed resources are retrieved.

- **G2.1.3 -> AT7, AT8 [AND][(parallel)]**
  - **Justification**: No resource is yet carried at this point, so reassignment (AT8) has no dependency on the physical return trip (AT7); running them concurrently minimizes mission delay, consistent with the mission's time-sensitivity (echoed later in the parallel-robots clause).

- **G2.2 -> G2.2.1, G2.2.2 [AND][FALLBACK]**
  - **Justification**: Normal multi-run transport (G2.2.1) is the default; the 30% battery condition can interrupt it mid-delivery, so battery management (G2.2.2) is its fallback — mirroring the collection phase's structure for consistency.

- **G2.2.1 -> AT9, AT10 [AND][(sequential), repeated per run]**
  - **Justification**: Each run is inherently sequential (travel, then hand-off), and the pair repeats "as many runs as necessary" until no collected resource remains undelivered.

- **G2.2.2 -> FALLBACK([AT11, AT12], G2.2.2.1) [AND][FALLBACK]**
  - **Justification**: The text ties valid reassignment (AT12) to the successor robot "knowing where the resource is positioned" — guaranteed only once AT11 succeeds. When AT11 itself fails, the text supplies a distinct outcome (G2.2.2.1) rather than permitting an uninformed hand-off, making the two branches mutually exclusive alternatives, i.e., a fallback.

- **AT11 -> AT12 [AND][(sequential)]**
  - **Justification**: The reassignment message's content (checkpoint location) is only valid after the deposit has actually occurred.

- **G2.2.2.1 -> AT13, AT14 [AND][(sequential)]**
  - **Justification**: The text's own ordering — *"an alert must be triggered **and** the report sent"* — places the immediate, lightweight alert before the more detailed follow-up report.

---

A couple of things worth flagging if you want to take this further: the two domain examples (sterile medical equipment, clean linens) suggest **G0** could be triggered either on-demand ("when required") or periodically ("should periodically be moved") — the model above supports both without changes, since the trigger is external to the goal structure itself.
