# Multi-Robot Mission Goal Model: Resource Collection & Delivery

Below is my full decomposition process, the resulting goal/task model, and the logical relationships between all elements, built directly from the mission description.

---

## 1. Step-by-Step Reasoning Process

**Step 1 — Identify the mission trigger and final target.**
The text opens with *"When required, a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location."* This is a classic **event-triggered Achieve goal**: a request arrives → a target condition (resources delivered) must eventually hold. This becomes my root goal **G0**.

**Step 2 — Identify the macro-phases.**
The description explicitly names two sequential phases: *"In the collection phase..."* and *"Once retrieved, the delivery phase begins."* This gives a clear **AND/sequential** split, but I noticed these phases are *per robot*, while the mission as a whole may involve *several robots*. So I introduced an intermediate layer:
- A **task-allocation** goal (deciding who does what) — implied by *"multiple robots can be assigned to parallel collect-deliver tasks."*
- A **fleet-execution** goal (coordinating N parallel robot instances).
- A **single-robot template goal**, instantiated once per assigned robot, which is where Collection/Delivery actually live.

This avoids conflating "the mission" (possibly multi-robot, parallel) with "one robot's job" (strictly sequential: collect, then deliver).

**Step 3 — Decompose the Collection phase.**
Reading carefully: *"the robot must go to the storage... The order... is defined by the estimation of waiting time summed up with the path... Once the robot reaches one storage and it is time to request the resource, the robot sends a message... and waits until the resources have been retrieved."*
This gives four distinct, ordered sub-goals:
1. Decide visit order → an **information/estimation goal (Query)**, not an action.
2. Travel to storage → **Perform**.
3. Send request message → **Perform**.
4. Wait for retrieval → a **state that must become true (Achieve)**.

**Step 4 — Decompose the Delivery phase.**
*"the robot will make as many runs as necessary to take all the resources to the specified location."* This implies (a) a hidden computation of *how many runs* are needed (capacity vs. quantity) — a **Query** goal — and (b) the repeated transport action itself — **Perform**, with the phase-level **Achieve** goal being "all resources at destination."

**Step 5 — Treat battery handling as conditional fallback, not as ordinary flow.**
The two battery rules (10% in collection, 30% in delivery) are *exceptions*, not part of the nominal path. The prompt's own notation — `FALLBACK(...)` with a mandatory **AND** relation — fits perfectly: the robot *always* either (a) completes the normal sequence, or (b) executes the safety/hand-off sequence; both outcomes are "covered" by the parent goal (hence AND, not OR — OR would wrongly imply a free choice between behaving safely or not).

**Step 6 — Nest a second-level fallback for the checkpoint failure.**
*"In case of failure to return the resource to a checkpoint, an alert must be triggered..."* This failure is scoped specifically to the **checkpoint-return action**, not to the whole delivery-battery handler. So I nested a second `FALLBACK` *inside* the delivery battery-handling goal, rather than placing the alert as a sibling of equal weight to "return to checkpoint."

**Step 7 — Model parallelism explicitly where stated.**
Two explicit parallel/concurrent points exist:
- Fleet level: *"multiple robots can be assigned to parallel collect-deliver tasks to reduce the time."* → `[#]` parallel.
- I also inferred a parallel relation for "return to recharge station" + "assign mission to another robot" in the 10%-battery case, because nothing in the text makes one depend on the other, and doing them concurrently best serves the mission's own stated goal of *reducing time*.

**Step 8 — Check for OR-relations.**
I deliberately searched for any genuine *alternative strategies* (OR) in the text — e.g., "either do X or Y, pick one." I found **none**. Every branch point is either (a) a mandatory step, (b) mandatory concurrent steps, or (c) a conditional safety fallback — all of which are AND-type per the task's own notation rules. This is an important reflection: **the mission as described is deterministic/procedural with safety exceptions, not a goal model with strategic choice points.**

**Step 9 — Ground the domain context.**
The two examples given (sterile medical equipment logistics; clean linens) are both **hospital logistics** scenarios. I used this to assign realistic `Location` values in the Task table (storage/sterile facility, hospital corridors, recharging station, checkpoint, sector manager's office) rather than inventing unrelated domains like "restaurant."

## 2. Key Assumptions (flagged explicitly, since the text is ambiguous here)

| # | Ambiguity | Assumption made | Rationale |
|---|---|---|---|
| A1 | Order of "return to recharge" vs. "assign to another robot" (10% case) | Parallel | No stated dependency; concurrency reduces delay, consistent with the mission's stated efficiency goal |
| A2 | Order of "return to checkpoint" vs. "reassign task" (30% case) | Sequential (checkpoint first) | The new robot must "know where the resource is positioned" — this position only exists once the resource is actually placed |
| A3 | Scope of the checkpoint-failure alert | Fallback *only* to "return to checkpoint," not to the whole delivery-battery handler | Text ties the failure explicitly to "failure to return the resource to a checkpoint" |
| A4 | Visiting multiple storages within one robot's collection phase | Modeled narratively inside G4.2–G4.4 (iterative), not as separate repeated nodes | Keeps the model generic/reusable regardless of how many storages one robot visits |
| A5 | Any OR-relations | None found/used | All branching in the text is mandatory, concurrent, or safety-fallback (AND-type) |

**Legend for Runtime column:** `[;]` sequential · `[#]` parallel · `FALLBACK(primary → alternative)` conditional hand-off (always combined with **AND** relation, per instructions).

## 6. Logical Relationships

**Goal-to-goal:**

- **G0 -> G1, G2 [AND](sequential)**
  - *Justification*: Robots must first be assigned to tasks before task execution can begin; the text separates "assignment" from "parallel collect-deliver tasks" as distinct notions.

- **G2 -> G3 (one instance per assigned robot) [AND](parallel)**
  - *Justification*: *"multiple robots can be assigned to parallel collect-deliver tasks to reduce the time to finish the mission"* — this is the model's explicit concurrency point.

- **G3 -> G4, G5 [AND](sequential)**
  - *Justification*: *"Once retrieved, the delivery phase begins"* makes the phase order explicit and strictly dependent.

- **G4 -> G4.1, G4.2, G4.3, G4.4, G4.5 [AND] FALLBACK((G4.1;G4.2;G4.3;G4.4), G4.5)**
  - *Justification*: The nominal collection sequence (order → travel → request → wait) is interruptible at any point by the 10%-battery condition, which is the designated fallback per the mission description.

- **G4.5 -> G4.5.1, G4.5.2 [AND](parallel)**
  - *Justification*: No stated dependency between "return to recharge" and "assign to another robot"; concurrency reduces downtime, aligned with the mission's own efficiency rationale (Assumption A1).

- **G5 -> G5.1, G5.2, G5.3 [AND] FALLBACK((G5.1;G5.2), G5.3)**
  - *Justification*: The nominal delivery sequence (compute runs → execute runs) is interruptible by the 30%-battery condition, the designated delivery-phase fallback.

- **G5.3 -> G5.3.1, G5.3.2, G5.3.3 [AND] FALLBACK((G5.3.1;G5.3.2), G5.3.3)**
  - *Justification*: Checkpoint return must precede reassignment (the new robot needs the resulting position — Assumption A2); failure of the checkpoint-return step specifically triggers escalation (Assumption A3).

- **G5.3.3 -> G5.3.3.1, G5.3.3.2 [AND](parallel)**
  - *Justification*: *"an alert must be triggered and the report sent"* are named together as a joint, independent escalation response — no ordering dependency stated.

**Goal-to-task** (each leaf goal maps 1:1 to a single operational task; no OR-decomposition applies here since the description specifies exactly one concrete action per step):

- **G1 -> AT1 [AND]**, **G2 -> AT2 [AND]**, **G4.1 -> AT3 [AND]**, **G4.2 -> AT4 [AND]**, **G4.3 -> AT5 [AND]**, **G4.4 -> AT6 [AND]**, **G4.5.1 -> AT7 [AND]**, **G4.5.2 -> AT8 [AND]**, **G5.1 -> AT9 [AND]**, **G5.2 -> AT10 [AND]**, **G5.3.1 -> AT11 [AND]**, **G5.3.2 -> AT12 [AND]**, **G5.3.3.1 -> AT13 [AND]**, **G5.3.3.2 -> AT14 [AND]**
  - *Justification*: Each leaf goal describes exactly one concrete, named action in the source text (e.g., "sends a message," "goes back to the recharging station"), so each resolves to a single mandatory operationalizing task rather than a choice among alternative implementations.

---

**Reflection on overall model quality**: the structure cleanly separates *strategic* concerns (allocation/parallelization, G1–G2), *procedural* concerns (collection/delivery execution, G4–G5), and *resilience* concerns (battery/failure fallbacks, G4.5/G5.3/G5.3.3) — which mirrors how multi-robot system architectures are typically layered (mission planner → task executor → safety/recovery layer). This should make the model directly usable as a basis for BDI-style agent design, behavior trees, or a formal goal-model (e.g., KAOS/i*) diagram.
