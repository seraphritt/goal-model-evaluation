# Multi-Robot Mission Goal Model: Hospital Vital Signs Monitoring

## PART 1 — Step-by-Step Reasoning & Analysis

Before building the tables, I read the description as a mission designer looking for four things: (1) **triggers and recurring conditions** (what starts the mission and how often), (2) **control-flow signals** — words like *"before,"* *"if,"* *"in case of,"* *"once,"* *"after"* — which tell me whether a decomposition is sequential, parallel, or a contingency (fallback), (3) **classification/conditional logic** — patient attributes that change *what* is done (infectious/post-surgical/diabetic, high-risk), and (4) **multi-robot/system-level concerns** — things that are not about a single robot in a single room, but about the fleet as a whole (team scaling, manager escalation).

**Step 1 — Identify the root goal and its recurrence.**
"Every two hours, all patients' vital signs should be checked" is a periodic Achieve goal. Everything else in the text is sub-ordinate to this. I made it **G1**, the mission root.

**Step 2 — Separate "what must always eventually happen" from "what keeps the mission possible."**
Re-reading, I noticed the text actually describes two concerns that run at different levels: (a) the operational loop of visiting rooms and checking patients, and (b) a *meta*-concern about whether the current robot team can finish in time ("additional robots can be assigned," "manager alerted if no combination... can complete the mission"). This second concern is not about any single room — it's a supervisory/fleet-level goal that must be monitored **throughout** the mission, not just at the end. So I split G1 into two parallel branches: **G2** (do the checking work) and **G3** (guarantee feasibility of doing it). This is a key reflection: if I had nested G3 only at the end, the model would imply robots wait until mission failure to act, but the text implies continuous monitoring and reassignment ("if there is not enough battery... tasks need to be reassigned" is itself a micro version of this same feasibility logic at the single-robot level, reinforcing that feasibility management is a standing concern, not a one-off check).

**Step 3 — Handle the high-risk/15-minute constraint.**
I initially considered making "check high-risk patients" a fully separate branch from "check all occupied rooms," but re-reading, I realized high-risk patients *are* occupied-room patients — the 15-minute rule is a **scheduling priority constraint**, not a different kind of checking. I modeled it as **G2.1 (sequential, before) G2.2**, where G2.1 handles the subset of rooms containing high-risk patients and G2.2 handles the rest. Both reuse the same underlying "visit and process a room" goal — I did not want to duplicate that entire subtree, so I made that subtree a **reusable, instantiated goal: G4**, applied once per room. This mirrors how a real goal model should avoid redundant specification for repeated entities (rooms).

**Step 4 — Distinguish genuine OR-alternatives from fallback/contingency patterns.**
This was the most important judgment call. I separated two linguistically different patterns:
- *"either by asking or by scanning the barcode"* — two **equally valid alternative means** to the same end, no stated precedence or failure-trigger. → modeled as **OR relation**.
- *"If the patient is not available... if there is not enough battery... failure of collecting vital signs... in case of non-response"* — every one of these is explicitly **conditioned on the failure of a prior attempt**. These are contingency plans, not free choices. → modeled as **FALLBACK(...)**, and per the requested convention, every FALLBACK is tagged with an **AND** relation (the branches are jointly part of one designed recovery strategy, even though only one branch executes at runtime).

**Step 5 — Decompose the condition-specific vital-sign requirements.**
The text gives three independent condition categories, each needing a different measurement set, and a patient **can belong to more than one simultaneously** (e.g., post-surgical *and* diabetic). This isn't an exclusive choice, so I used an **inclusive OR** (more than one branch may be active) rather than a FALLBACK. I flagged an **assumption**: the text never explicitly says the robot looks up *which* condition category a patient belongs to, but this is logically necessary for the OR-branches to trigger correctly — so I added an inferred task, **AT28 (Query Patient Medical Profile)**, and call this out explicitly as an inference rather than a literal requirement.

**Step 6 — Hygiene/safety rules as situational, not universal, branches.**
Sterilization applies only *if* the room held an infectious-disease patient; actuator disinfection applies only *if* physical contact occurred. Neither is guaranteed, and both could occur together — again **inclusive OR**, not FALLBACK (these aren't recoveries from failure, they're situational safety protocols).

**Step 7 — Vital sign collection failure → questions → non-response → alert, as a nested fallback.**
This is a two-level contingency: measurement fails → ask questions (level 1 fallback); questions get no response → alert staff (level 2 fallback). I modeled this as its own reusable goal, **G4.3.3**, invoked as the fallback branch of *every* condition-specific measurement goal (G4.3.2.1/2/3), since the same failure-handling procedure applies regardless of which vital sign failed.

**Step 8 — Keep Relation and Runtime conceptually distinct.**
*Relation* = is this an AND (all branches required) or OR (one or more applicable branches) decomposition? *Runtime* = **when AND is used**, how do the children execute — together (`#`), in order (`;`), or as ordered contingency attempts (`FALLBACK(...)`, always paired with AND per the instructions)? I applied this consistently throughout.

## PART 5 — Logical Relationships

**G1 -> G2, G3 [AND][(parallel)]**
- **Justification**: The checking work (G2) and the feasibility/team-scaling watchdog (G3) are independent concerns that must run concurrently — feasibility must be monitored *while* rooms are being processed, not only after the fact.

**G2 -> G2.1, G2.2 [AND][(sequential)]**
- **Justification**: The explicit 15-minute deadline for high-risk patients establishes a priority ordering over the general room sweep.

**G2.1 -> G4 (∀ high-risk room) [AND][(parallel)]**
- **Justification**: Multiple high-risk rooms may need simultaneous handling by multiple robots to meet the hard 15-minute deadline; each instantiates the same room-processing template.

**G2.2 -> G4 (∀ remaining room) [AND][(parallel)]**
- **Justification**: Remaining occupied rooms can be distributed across available robots and processed concurrently within the 2-hour window.

**G3 -> G3.1, G3.2, G3.3 [AND][FALLBACK(G3.1, G3.2, G3.3)]**
- **Justification**: "Additional robots can be assigned... manager must be alerted if no combination can complete the mission" is a staged contingency: monitor first, reinforce the team if monitoring detects risk, escalate to the manager only if reinforcement still fails. Per the fallback convention, relation is AND.

**G3.1 -> AT1, AT2, AT3 [AND][(parallel)]**
- **Justification**: The three data points (rooms left, time left, team status) are independent reads that can be gathered simultaneously to compute feasibility.

**G3.2 -> AT4, AT5 [AND][(sequential)]**
- **Justification**: You must compute how many robots are needed before you can dispatch them.

**G3.3 -> AT6 [AND][(sequential)]**
- **Justification**: Single terminal action; trivially sequential.

**G4 -> G4.1, G4.2, G4.3, G4.4 [AND][(sequential)]**
- **Justification**: The text's own narrative order — pre-entry checks, then identification, then the in-room procedure, then closing out — is an explicit temporal sequence ("Before entering...", "Once inside...", "Once the patient is checked...").

**G4.1 -> G4.1.1, G4.1.2 [AND][(parallel)]**
- **Justification**: "Check if the patient is available... and if there is enough battery" are two independent conditions that can be evaluated at the same time before entry.

**G4.1.1 -> AT7, AT8 [AND][FALLBACK(AT7, AT8)]**
- **Justification**: "If the patient is not available, the robot should come back in 5 minutes" is a direct primary-attempt/retry contingency.

**G4.1.2 -> AT9, AT10, AT11 [AND][FALLBACK(AT9, AT10;AT11)]**
- **Justification**: "If there is not enough battery, the robot should recharge **and** the tasks need to be reassigned" — two recovery actions that must happen in order within the fallback branch.

**G4.2 -> AT12, AT13 [OR][(parallel)]**
- **Justification**: "Either by asking or by scanning the patient's barcode" — stated as equal alternatives with no precedence or failure-trigger, unlike the FALLBACK cases elsewhere; hence a true OR, not a contingency.

**G4.3 -> AT28, G4.3.1, G4.3.2 [AND][(sequential)]**
- **Justification**: The robot must know the patient's condition category (AT28, inferred) and complete the social preparation (G4.3.1) as part of the same in-room procedure before/alongside collecting vitals (G4.3.2); ordering reduces risk of measuring before the patient is briefed.

**G4.3.1 -> AT14, AT15, AT16 [AND][(sequential)]**
- **Justification**: Verbatim ordered sequence: "approach... announce... provide instructions."

**G4.3.2 -> G4.3.2.1, G4.3.2.2, G4.3.2.3 [OR][(parallel)]**
- **Justification**: A patient may belong to more than one condition category simultaneously, so this is an inclusive OR; applicable branches can be executed concurrently since they involve different sensors/measurements.

**G4.3.2.1 -> AT17, AT18, AT19, AT20, G4.3.3 [AND][FALLBACK([AT17#AT18#AT19#AT20], G4.3.3)]**
- **Justification**: The four measurements can be taken in parallel; any failure routes to the shared escalation goal, per "the failure of collecting any necessary vital signs should trigger a set of questions."

**G4.3.2.2 -> AT17, AT20, G4.3.3 [AND][FALLBACK([AT17#AT20], G4.3.3)]**
- **Justification**: Same failure-handling logic applied to the smaller post-surgical measurement set.

**G4.3.2.3 -> AT21, G4.3.3 [AND][FALLBACK(AT21, G4.3.3)]**
- **Justification**: Same failure-handling logic applied to the single glucose measurement.

**G4.3.3 -> AT22, AT23 [AND][FALLBACK(AT22, AT23)]**
- **Justification**: "Trigger a set of questions... in case of non-response, an alert should be sent" is itself a nested fallback (ask, then escalate only if unanswered).

**G4.4 -> AT24, G4.4.1, AT25 [AND][(sequential)]**
- **Justification**: Verbatim order: mark done, (apply hygiene protocols while/just before leaving), then move to the next room.

**G4.4.1 -> G4.4.1.1, G4.4.1.2 [OR][(parallel)]**
- **Justification**: Sterilization and actuator disinfection are triggered by independent situational conditions (infectious-disease room vs. physical contact) and can co-occur; inclusive OR, executed in parallel since they involve different robot subsystems.

**G4.4.1.1 -> AT26 [AND][(sequential)]**

### Key Assumptions Flagged During Reasoning
1. **AT28 (Query Patient Medical Profile)** is inferred, not explicit — needed to trigger the right condition-specific branch(es).
2. **"High-risk"** was treated as an independent scheduling attribute (affects *when* a room is visited), distinct from infectious/post-surgical/diabetic status (which affects *what* is measured) — the text never states these overlap, so I kept them orthogonal.
3. **"Disinfect actuators afterwards"** was placed at room-exit time (G4.4.1.2) rather than immediately after each individual contact task, for model simplicity; a more granular model could attach it as an immediate fallback-free follow-up to any specific contact task if finer-grained hygiene timing is required.
