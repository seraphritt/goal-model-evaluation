# Multi-Robot Mission Goal Model: Hospital Vital-Signs Checking Round

Below is the full decomposition of the mission description into a goal model, following a GORE-style approach adapted for multi-robot systems (goal types *Perform/Query/Achieve*, AND/OR decomposition, and runtime operators sequence `[;]`, parallel `[#]`, and `FALLBACK(...)`).

---

## 1. Step-by-Step Reasoning (How I Decomposed the Mission)

**Step 1 — Identify the mission trigger and top-level success condition.**
The phrase "every two hours, all patients' vital signs should be checked" gives a **periodic trigger** and a **mission-level target condition** ("all patients checked"). This becomes my root goal **G1**. Because the description later says additional robots can be added, and a manager must be alerted if *no* combination of robots works, I treat G1 as having three alternative execution strategies rather than one monolithic plan — a textbook **FALLBACK** pattern: (1) try with the current team, (2) if infeasible, add robots and retry, (3) if still infeasible, escalate to a human. This is why `FALLBACK` requires an AND relation in this notation: all three branches are structurally part of *one* contingency strategy, even though only one branch executes at a time.

**Step 2 — Separate "do the rounds" from "manage feasibility".**
"Visit every occupied room" (the operational task) and "monitor whether the team can finish in time" (a supervisory concern) are logically independent and can run concurrently — one robot checking vitals doesn't block the fleet coordinator from estimating whether the 2-hour budget will be met. I modeled these as **parallel siblings** (G1.1.1 and G1.1.2) rather than nesting the monitoring inside the visiting loop, to avoid conflating "doing the work" with "watching the clock."

**Step 3 — Handle the high-risk deadline as a parallel partition, not a strict phase.**
"High-risk patients must be checked in the first 15 minutes" could be modeled as a strict two-phase sequence (finish all high-risk rooms, *then* start the rest). I rejected this because it would waste multi-robot parallelism: nothing in the text forbids other robots starting normal rounds while some robots race the 15-minute clock. I instead modeled it as **two parallel room-visit streams**, where the high-risk stream simply carries a tighter deadline as part of its target condition.

**Step 4 — Treat the per-room procedure as a reusable template.**
"Visit every occupied room" is really "apply the same procedure to N rooms." Rather than duplicating the whole subtree per room, I defined **G1.1.1.4 (Visit Room)** once and instantiate it per occupied room, executed in parallel across whatever robots are available and sequentially for any single robot's own room list.

**Step 5 — Decide what's a Goal vs. a Task.**
I kept something as a **Goal** only if it requires further decomposition, contains a decision point (AND/OR/FALLBACK), or has a condition that can succeed/fail. Pure one-shot physical/communicative actions (navigate, announce, scan, measure X) became **Tasks**. This keeps the tree from becoming artificially deep.

**Step 6 — Resolve the two pre-entry checks (availability, battery).**
"Check if patient is available... and if there is enough battery" — both are **independent preconditions**, each with its own explicit recovery action stated in the text (wait 5 min / recharge+reassign). This is a clean textbook case for two parallel **Query** goals, each wrapped in its own `FALLBACK` (query → if negative → stated recovery task).

**Step 7 — Patient identification: OR or FALLBACK?**
The text says "either by asking or by scanning the barcode" — grammatically an OR. However, a goal model meant to drive actual robot behavior needs a deterministic execution order, not an undefined non-deterministic choice. I reflected on this explicitly: scanning is faster, less intrusive, and doesn't require the patient to be responsive; asking is the natural recourse when scanning isn't possible (unreadable/missing barcode) or when extra confirmation is needed in a multi-bed room. So I modeled it as `FALLBACK(Scan Barcode, Ask Patient)` — preserving the "either/or" *intent* while making it executable. I flag this as a design decision, not a literal reading, in its justification.

**Step 8 — Condition-based vital signs: AND or OR?**
Infectious-disease, post-surgical, and diabetic requirements are each internally an **AND** ("heart rate, blood pressure, body temperature, *and* blood oxygenation"). But a single patient can belong to **more than one category at once** (e.g., post-surgical *and* diabetic). If I modeled the three categories as AND siblings, every patient would be forced through all three regardless of condition — wrong. If modeled as strict XOR, a comorbid patient would be checked only once — also wrong. The correct structure is an **inclusive OR**: each condition branch is independently guarded and activates only if applicable, and multiple branches can be active simultaneously. This is the most important modeling nuance in the whole mission.

**Step 9 — Failure handling is itself a nested contingency.**
"Failure to collect any vital sign → ask questions → non-response → alert" is a two-level fallback: first try to still get an assessment conversationally, and only alert staff if *that* also fails (non-response). I modeled this as a sequential goal whose last step is itself a `FALLBACK`.

**Step 10 — Hygiene actions are independent, both triggered by guards, not mutually exclusive.**
Sterilization is guarded by "patient had an infectious disease"; actuator disinfection is guarded by "robot touched the patient." These conditions frequently co-occur (most contact-based vital sign checks on an infectious patient trigger both), so I modeled them as **OR/parallel**, not FALLBACK — there's no preference order between them, and the goal model should hold the possibility of both firing together.

**Step 11 — Robot-team augmentation and manager alert are mission-level, not room-level, concerns.**
These only make sense as a property of the whole mission's progress (can the *fleet* finish in time?), not of any single room visit, so they sit as siblings of the main visiting goal at the top of the tree (G1.2, G1.3), fed by the monitoring goal G1.1.2.

## 2. Goal Hierarchy Overview

```
G1  Execute Periodic Vital Signs Monitoring Mission            [FALLBACK]
├─ G1.1  Perform Mission With Assigned Robot Team               [#]
│  ├─ G1.1.1  Visit All Occupied Rooms                          [; then #]
│  │  ├─ G1.1.1.1  Determine Room Visit List & Risk Classification
│  │  ├─ G1.1.1.2  Check High-Risk Patients Within First 15 Minutes   [#]→ G1.1.1.4 (per room)
│  │  └─ G1.1.1.3  Check Remaining Occupied Rooms                     [#]→ G1.1.1.4 (per room)
│  │
│  │     G1.1.1.4  Visit Room and Check Patient Vital Signs [TEMPLATE]   [;]
│  │     ├─ AT1  Navigate to Room
│  │     ├─ G1.1.1.4.1  Verify Entry Preconditions                       [#]
│  │     │  ├─ G1.1.1.4.1.1  Check Patient Availability     [FALLBACK: AT2, AT3]
│  │     │  └─ G1.1.1.4.1.2  Check Battery Sufficiency       [FALLBACK: AT4, G1.1.1.4.1.2.1]
│  │     │        └─ G1.1.1.4.1.2.1  Recharge and Reassign Tasks  [#]→ AT5, AT6
│  │     ├─ G1.1.1.4.2  Identify Correct Patient              [FALLBACK: AT7, AT8]
│  │     ├─ G1.1.1.4.3  Conduct Vital Signs Checking Procedure            [;]
│  │     │  ├─ AT9 Approach │ AT10 Announce │ AT11 Instructions
│  │     │  ├─ G1.1.1.4.3.1  Collect Required Vital Signs      [OR / #]
│  │     │  │  ├─ G1.1.1.4.3.1.1 Infectious-Disease Signs  [AND/#]→ AT12,13,14,15
│  │     │  │  ├─ G1.1.1.4.3.1.2 Post-Surgical Signs       [AND/#]→ AT12,15
│  │     │  │  └─ G1.1.1.4.3.1.3 Diabetes Sign              → AT16
│  │     │  └─ G1.1.1.4.3.2  Handle Vital Sign Collection Failures        [;]
│  │     │     ├─ AT17 Ask Assessment Questions
│  │     │     └─ G1.1.1.4.3.2.1 Handle Patient Response  [FALLBACK: AT18, AT19]
│  │     └─ G1.1.1.4.4  Finalize Room Visit                               [;]
│  │        ├─ AT20 Mark as Checked
│  │        ├─ G1.1.1.4.4.1  Apply Hygiene Protocol         [OR/#]→ AT21, AT22
│  │        └─ AT23 Proceed to Next Room
│  │
│  └─ G1.1.2  Monitor Mission Time Feasibility  → AT24
│
├─ G1.2  Augment Robot Team to Meet Time Constraints  → AT25 (then resumes G1.1.1)
└─ G1.3  Alert Site Manager of Mission Infeasibility  → AT26
```

| **G1.1 – Perform Mission With Assigned Robot Team** | The primary attempt to complete the round using whichever robots are already assigned. | [#] | Achieve | Visiting of all occupied rooms completed within budget, continuously verified against the time budget. | AND | Visiting rooms and watching the clock are independent concerns that must both hold; they don't block each other operationally. |

### 3.4 Patient Identification

| Name | Text | Runtime | Goal Type | Target Condition / QueriedProperty | Relation | Justification |
|---|---|---|---|---|---|---|
| **G1.1.1.4.2 – Identify Correct Patient** | Confirm exactly which patient (of possibly several in the room) is being checked. | FALLBACK(AT7, AT8) | Achieve | The targeted bed's patient is unambiguously identified. | AND | Text: "has to identify the correct patient either by asking or by scanning the patient's barcode." I chose `FALLBACK` over a plain OR because an executable mission needs a deterministic order: barcode scanning is faster/less intrusive and attempted first; asking is the natural recourse when scanning fails or isn't possible (e.g., damaged/missing barcode, non-visible tag). This operationalizes the "either/or" wording rather than leaving it as an undefined choice. |
