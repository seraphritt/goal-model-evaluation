# Mission Decomposition: Multi-Robot Vital Signs Checking in a Hospital Ward

## Step 1 — Reading the description as a mission designer

Before building any table, I read the text multiple times extracting **triggers, preconditions, branching logic, loops, and escalation paths**. Here is my reasoning trail:

1. **Periodicity is the mission's entry point.** "Every two hours… all patients' vital signs should be checked" tells me the whole tree sits under one **recurring root goal**, with a dedicated trigger sub-goal (G1) so the scheduling concern doesn't get buried inside the operational logic.

2. **The core is an iterative "visit every occupied room" loop.** This is naturally an **Achieve** goal (G2) since it has a target state — "every occupied room processed" — not a single action.

3. **Pre-entry checks are queries with recovery, not simple actions.** "Check if patient is available" and "check if there is enough battery" are **Query** goals (they return a boolean), but each one has an explicit recovery behavior described in the text (wait 5 minutes / recharge + reassign). I model each as a **Query goal carrying its own FALLBACK runtime** — a deliberate, explicit design choice, since strict goal-modeling purists separate "query" from "action," but the mission text fuses them, and separating them further would fragment a tightly-coupled check-then-react pattern.

4. **Patient identification is a genuine OR, not a fallback.** "Either by asking or by scanning the barcode" — the text gives no preference order or retry logic between the two, so I treat this as **OR (interchangeable means to the same end)**, distinct from FALLBACK (which implies an ordered primary/backup).

5. **Vital-sign sets are condition-gated, not mutually exclusive.** A patient could be *both* diabetic *and* post-surgical. If I modeled this as plain OR ("satisfy one branch and you're done"), a diabetic post-surgical patient would be under-checked. I instead model it as an **AND of conditionally-activated branches** — every branch whose triggering condition is true *must* run; branches whose condition is false are simply not instantiated. This is a key reasoning point I want to flag explicitly because it's easy to mis-model as a simple OR.

6. **Failure-handling belongs under vital-sign collection, not beside it.** "Failure of collecting any vital sign triggers questions" is a **recovery of a specific step**, not an independent stage every room visit performs. I nest it as a FALLBACK child of "Collect Vital Signs," not as a sibling phase of the room visit — this avoids implying every patient is always subjected to the questioning stage.

7. **Non-response is a second-level fallback inside the first.** "In case of non-response, alert nurse/doctor" is a fallback *of the fallback* (ask questions → if that also fails → escalate to a human). Two nested FALLBACK levels, both AND per the given rule.

8. **Hygiene protocols (sterilization, actuator disinfection) are conditional-AND, like the vital signs case.** They are not alternatives to anything — they are mandatory *when their triggering condition holds* (infectious-disease room / physical patient contact), and these conditions are independent of each other and of the vital-sign conditions.

9. **High-risk prioritization is a scheduling constraint, not a branch of the room-visit procedure.** It governs *order*, not *content*, of G2.2's instantiation, so I model it as a sibling sub-goal of G2 that produces/enforces a schedule, rather than embedding it inside the room-visit template.

10. **Multi-robot reallocation and manager escalation form a mission-level, two-tier FALLBACK**, separate from the per-room logic: (i) try to finish with the currently assigned robot(s); (ii) if infeasible, bring in additional robots; (iii) if *no combination* of robots works, escalate to a human (the site manager). This mirrors the text's own three-tier structure almost verbatim.

11. **Local task reassignment vs. mission-level robot reallocation are different concerns.** "If there is not enough battery… the tasks need to be reassigned" is a *local* hand-off of one robot's remaining room-list, whereas "additional robots can be assigned… impossibility of performing the mission in required time" is a *mission-level* scaling decision. I keep these as two distinct tasks/goals but cross-reference them, since a failed local reassignment (no idle robot available) is precisely what should trigger the mission-level mechanism.

**Explicit assumptions I'm making (stated for transparency):**
- Patient identification (ask/scan) happens *after* entering the room, at the bedside — barcode scanning needs physical proximity, and this keeps the pre-entry checks patient-record-based rather than requiring physical presence first.
- "High risk" is treated as an independent scheduling attribute, not a new vital-sign set (it doesn't add new measurements, only urgency).
- All activity is in a hospital; I further distinguish sub-locations (room, corridor, charging dock, nurse station, management office) for realism.
- One robot per room instance; multiple rooms can be processed concurrently once more than one robot is active.

│       ├── G2.2.1  Perform Pre-Entry Checks
│       │   ├── G2.2.1.1  Confirm Patient Availability        [FALLBACK]
│       │   └── G2.2.1.2  Confirm Sufficient Battery          [FALLBACK]

## Step 6 — Logical Relationships

**G0 → G1 [AND][sequential]**
- **Justification**: The mission must first be triggered before any room visiting can start.

**G0 → G2, G3 [AND][(parallel)]**
- **Justification**: Once triggered, room-visiting (G2) and timeliness-monitoring (G3) run concurrently — G3 must watch G2's progress in real time to decide whether reallocation is needed, not after G2 finishes.

**G2 → G2.1, G2.2 [AND][(sequential)]**
- **Justification**: The priority schedule (G2.1) must be computed/available before or as G2.2 begins executing visits in that order.

**G2.2 → G2.2.1, G2.2.2, G2.2.3, G2.2.5 [AND][(sequential)]**
- **Justification**: Strict precedence: checks must pass before identification; identification before the procedure; the procedure before closing the room.

**G2.2.1 → G2.2.1.1, G2.2.1.2 [AND][(parallel)]**
- **Justification**: Patient availability and battery level are independent conditions with no dependency on each other; both must hold before entry.

**G2.2.1.1 → "Proceed", "Wait 5 min & Retry" [AND][FALLBACK(Proceed, Wait & Retry)]**
- **Justification**: "If the patient is not available, the robot should come back in 5 minutes" is a textbook primary/fallback pair.

**G2.2.1.2 → "Proceed", AT6, AT7 [AND][FALLBACK(Proceed, (AT6 # AT7))]**
- **Justification**: Insufficient battery triggers two things together (recharge *and* reassign), so the fallback branch itself is an AND of two parallel recovery actions.

**G2.2.2 → AT8, AT9 [OR][(not concurrent — single choice)]**
- **Justification**: "Either by asking or by scanning" explicitly offers two interchangeable, non-ordered means of satisfying the same goal.

**G2.2.3 → G2.2.3.1, G2.2.3.2 [AND][(sequential)]**
- **Justification**: The patient must be informed/instructed before any measurement is attempted ("approach… announce… instructions" precedes vitals in the text).

**G2.2.3.1 → AT11, AT12, AT13 [AND][(sequential)]**
- **Justification**: Natural, textually-ordered sequence: approach, then announce, then instruct.

**G2.2.3.2 → G2.2.3.2.1, G2.2.3.2.2, G2.2.3.2.3 [AND][(parallel)]**
- **Justification**: Each condition-set is independently and conditionally activated; a patient may match more than one condition (e.g., diabetic + post-surgical), so all matching sets must run. I deliberately avoid OR here — see reasoning step 5.

**G2.2.3.2.1 → AT14, AT15, AT16, AT17 [AND][(parallel)]**
- **Justification**: "Must be checked for heart rate, blood pressure, body temperature, and blood oxygenation" is an explicit, unconditional AND-set with no stated precedence.

**G2.2.3.2.2 → AT14, AT17 [AND][(parallel)]**
- **Justification**: "Must be checked for heart rate and blood oxygenation" — same reasoning, reusing shared leaf tasks already defined for the infectious-disease set.

**G2.2.3.2.3 → AT18 [AND][(sequential, single task)]**
- **Justification**: Single required measurement for diabetic history.

**G2.2.3.2 → G2.2.4 [AND][FALLBACK(G2.2.3.2.x success, G2.2.4)]**
- **Justification**: G2.2.4 only activates when a required sign fails to be collected — a recovery path of vital-sign collection specifically, not a universal stage of every visit.

**G2.2.4 → G2.2.4.1, G2.2.4.2 [AND][FALLBACK(G2.2.4.1, G2.2.4.2)]**
- **Justification**: "Trigger a set of questions… In case of non-response, an alert should be sent" is a second fallback layer nested inside the first.

**G2.2.5 → AT21, AT22, AT23, AT24 [AND][(sequential)]**
- **Justification**: Marking done, then any applicable hygiene step(s), then moving on — AT22/AT23 are conditionally-gated but mandatory when their condition (infectious room / patient contact) holds, hence AND rather than OR, consistent with the same conditional-AND reasoning used for G2.2.3.2.

**G3 → G3.1, G3.2, G4 [AND][(sequential) then FALLBACK(G3.2, G4)]**
- **Justification**: G3.1 continuously monitors feasibility; only if it detects insufficiency does the fallback chain (add robots → if still infeasible, escalate) activate. "Additional robots can be assigned… impossibility" then "manager must be alerted if no combination… can complete" are explicitly two tiers of the same contingency.

**G3.2 → AT25 [AND]**
- **Justification**: Direct mapping of the mission-level reallocation action.

**G4 → AT26 [AND]**
- **Justification**: Direct mapping of the escalation action.

**G2.1 → AT27 [AND]**, **G3.1 → AT28 [AND]**
- **Justification**: Both are single coordination computations with no internal branching described in the text.
