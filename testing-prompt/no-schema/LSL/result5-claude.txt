# Mission Analysis: Lab Sample Transport by Multi-Robot System

## 1. Step-by-Step Reasoning Process

Before building the tables, I worked through the description in five passes. I'm showing this explicitly because the choices I made later (goal types, AND/OR, runtime) all trace back to this analysis.

**Pass 1 — Identify the actors/agents.**
The text mentions a mix of *human* actors and *robotic* agents:
- **Nurse** (human, patient floor) — requests delivery, barcodes sample, enters tracking data, likely loads the physical drawer.
- **Transport mechanism** — "samples are transported in secure locked drawers." The text never names a robot here, but given the mission is explicitly a *multi-robot system* and the drawers are described as mobile ("transported"), I infer a **Transport/Delivery Robot (AMR)** with an integrated locked compartment. I flag this as an **assumption**, not an explicit fact.
- **Robotic arm** (lab) — explicitly named, performs pick/scan/sort/load.
- **Laboratory personnel** (human, lab) — alternative to the robotic arm.
- **Tracking/Access-control system** — implicit software agent behind "track system," "logged securely," "time... tracked," and the authorization check on drawers.

This matters because a goal model for a *multi-robot system* should still represent human and software actors when they gate or trigger robot behavior — otherwise the model has gaps at the interfaces.

**Pass 2 — Find the mission trigger and the end condition.**
Trigger: nurse's request. End condition: sample inside the analysis machine's entry-module (or, in the fallback case, in the hands of lab personnel), *and* the two cross-cutting conditions (secure access, traceable timing) hold throughout. This gives me the shape of the root goal: an **Achieve** goal whose target condition combines a physical outcome with two non-functional guarantees.

**Pass 3 — Separate "pipeline" statements from "constraint" statements.**
Re-reading the paragraph, two sentences are structurally different from the rest:
- *"Only authorized personnel or specific robots in specific locations should be able to open the locked drawers."*
- *"Information about where and when a given sample was picked should be logged securely"* / *"The time between sample collection and laboratory delivery should be tracked..."*

These aren't steps in a line — they're **invariants/cross-cutting requirements** that apply *at multiple points* of the pipeline (every drawer-opening event; the whole collection-to-delivery interval). I modeled them as separate goals (G5, G6) that run in **parallel** with the main sequential flow, rather than forcing them into the sequence — this avoids artificially saying "security happens once" when really it's checked every time a drawer opens.

**Pass 4 — Decide where OR / FALLBACK applies.**
Only one place in the text offers a genuine *alternative way to satisfy the same goal*: *"the sample can be picked by a robotic arm or laboratory personnel."* I chose **FALLBACK(robotic arm, personnel)** rather than a plain OR, because in a robotic-automation-first system it's natural to assume the robot is the primary path and the human is the backup (e.g., robot unavailable, jammed, or under maintenance) — this is a reasonable mission-design inference, and the task explicitly allows FALLBACK with AND relation for this case. The "authorized personnel OR specific robot" for drawer-opening is a true OR (either is independently sufficient; there's no stated priority), so I kept that one as OR.

**Pass 5 — Assign Goal Types (Perform / Achieve / Query).**
I used this rule of thumb:
- **Achieve** → a state must become true (barcode attached, sample delivered, access-policy respected).
- **Perform** → a procedure/sequence of actions with no independently checkable end-state beyond "the actions happened" (navigating, physically picking, requesting).
- **Query** → the goal is to obtain/compute information, not to change the world. The "time tracked... to be sure it goes according to protocol" sentence is a textbook Query goal (it reads data and checks it against a threshold), so I gave it its own node instead of flattening it into a task — this was the clearest case for demonstrating the Query type.

## 2. Explicit Assumptions Made

| # | Assumption | Why needed |
|---|---|---|
| A1 | A dedicated **Transport Robot (AMR)** physically carries the locked drawer from floor to lab. | The text says drawers are "transported" but never names the carrier; given the multi-robot framing, a mobile robot is the natural reading. |
| A2 | The robotic arm must **unlock the drawer before picking** — not stated explicitly, but required by the access-control sentence and physically necessary before "picks up samples" can occur. | Keeps the model consistent with the stated security constraint. |
| A3 | Barcoding and track-system entry happen **before** the delivery request, so the robot picks up a fully-identified, logged sample. | The text doesn't give a strict chronological order; this ordering is the most operationally sound. |
| A4 | When personnel pick the sample manually (fallback path), the text gives no further detail (no scan/sort/load) — this is treated as a **deliberate scope gap** in the original mission description (it only elaborates the automated path), not an omission on my part. | Prevents inventing unstated behavior. |

│     G3 Securely Transport Sample [;]                  │  # parallel with

│           AT7 Unlock(robot) → AT8 Pick → AT9 Scan → AT10 Sort → AT11 Load

│           AT12 Unlock(personnel) → AT13 Retrieve      │
│                                                         │

│     AT15 Verify Robot Identity & Location

Legend: `;` sequential · `#` parallel · `FALLBACK(...)` ordered alternative (AND)

## 7. Logical Relationships

- **G1 -> G2, G3, G4 [AND](sequential)**
  - **Justification**: These three goals form the physical pipeline described end-to-end in the text (request/prep → secure transport → lab retrieval), and each depends on the previous one's completion (you can't transport an unregistered sample, can't retrieve a sample that hasn't arrived).

- **G1 -> G5, G6 [AND](parallel)**
  - **Justification**: Access control and traceability/timing are not steps *in* the pipeline but *constraints on it* — they must be continuously true while G2, G3, G4 execute, so they run in parallel with the whole pipeline rather than after it.

- **G2 -> AT1, AT2, AT3 [AND](sequential)**
  - **Justification**: A sample should be identified (barcode) and registered before the delivery request is made, so the robot picks up a fully-documented sample — this ordering is an explicit mission-design assumption noted in Section 2 (A3).

- **G3 -> AT4, AT5, AT6 [AND](sequential)**
  - **Justification**: Physically, the robot must reach the floor, receive/lock the sample, then travel to the lab — strict temporal order, each a precondition for the next.

- **G4 -> FALLBACK(G4.1, G4.2) [AND]**
  - **Justification**: "...picked by a robotic arm or laboratory personnel" is an explicit alternative; FALLBACK is chosen (rather than plain OR) because the robotic arm represents the automated/primary mechanism of this multi-robot system, with personnel as the backup. Per the task's own rule, FALLBACK carries an AND relation.

- **G4.1 -> AT7, AT8, AT9, AT10, AT11 [AND](sequential)**
  - **Justification**: Matches the verb order in the text exactly ("picks up... scans... sorts... loads"), with AT7 (unlock) inserted first as a necessary, if implicit, precondition.

- **G4.2 -> AT12, AT13 [AND](sequential)**
  - **Justification**: Unlocking must precede retrieval; the text gives no further detail for this branch, so no additional tasks are invented.

- **G5 -> AT14, AT15 [OR](parallel)**
  - **Justification**: "Authorized personnel **or** specific robots in specific locations" — either mechanism independently satisfies the access-control goal; both exist concurrently as available verification paths in the system.

- **G6 -> AT16, G6.1 [AND](parallel)**
  - **Justification**: Logging a pick event and checking overall elapsed time are independent monitoring concerns that can occur concurrently (logging happens at the moment of picking; timing can be checked at any point, including continuously).

- **G6.1 -> AT17 [AND]**
  - **Justification**: The Query goal is realized by a single data-retrieval/computation task; trivial single-child AND.

- **(Cross-cutting, non-decomposition) G5 constrains AT5, AT7, AT12**
  - **Justification**: This isn't a parent-child edge but a *guard* relationship — every physical drawer-opening event in the mission (loading at the floor, robotic unlock at the lab, personnel unlock at the lab) must satisfy G5 before proceeding. I call this out explicitly because a strict tree structure would otherwise hide the fact that the same security policy is enforced at three different points in the mission — an important multi-robot/system-design insight (the policy is a reusable service, not a one-off step).

### A note on reliability
This analysis is my interpretation of the text, including some explicitly-flagged assumptions (Section 2) where the description was silent (e.g., which robot carries the drawer, the order of nurse-side actions, the lack of detail in the manual-pickup fallback). If any of these assumptions don't match your intended system design, they're easy to swap out without disturbing the rest of the tree — happy to iterate (e.g., turning G5 into a literal shared sub-goal node, adding a fleet-level goal for multiple simultaneous deliveries, or splitting the Transport Robot and Robotic Arm into a formal multi-robot coordination diagram).
