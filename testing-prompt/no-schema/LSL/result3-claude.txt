# Mission Analysis: Lab Sample Transport & Processing (Multi-Robot System)

## Step 0 – Methodology

Before decomposing, I read the description three times with three different lenses:

1. **Actor/Resource pass** – who or what performs actions, and what physical/digital objects are involved.
2. **Event/Constraint pass** – what triggers the mission, what security/time constraints exist, what alternatives (OR) and contingencies (FALLBACK) are implied.
3. **Causal-order pass** – what must happen before what (sequential), what can happen concurrently (parallel), and what is a one-time condition to reach (Achieve) vs. a repeated/continuous check (Query) vs. a plain action (Perform).

Only after this triple pass did I start building the tree top-down (Mission Goal → sub-goals → leaf goals → tasks), checking at each level that the AND/OR and runtime choice is traceable to a specific sentence in the description.

## Step 2 – Reasoning on the Decomposition (key design decisions)

1. **Why Achieve for G0, G2, G3, G4, G5 but Perform for G1?** – These goals describe a *state that must hold* (sample prepared, sample transported, sample processed, drawer access restricted) → `Achieve` with a `Target Condition`. G1 is a discrete act with no persisting condition to verify afterward → `Perform`.
2. **Why is G5 (access control) not nested only under G3?** – The sentence about authorized opening is written as a *general rule* about the drawers, not tied to one location. In practice the drawer is opened at least twice: once when the nurse loads the sample (under G3) and once when the lab retrieves it (under G4). Rather than duplicating the goal in two branches, I modeled it as a **cross-cutting goal running in parallel (#)** with the whole pipeline — this is standard practice for safety/security invariants in goal models.
3. **Why FALLBACK for arm-vs-personnel, and not plain OR?** – The text presents it as "can be picked by a robotic arm **or** laboratory personnel," which is textbook OR, but in a *multi-robot mission* this is almost always a preference/contingency: the robotic arm is the primary automated path (it also scans/sorts/loads — a richer, more desirable outcome), and personnel is the manual contingency when the arm is unavailable/fails. I modeled it as `FALLBACK(G4.1.1, G4.1.2)`, which per your notation rule carries an **AND** relation (both branches belong to the same construct; only one executes).
4. **Why is logging a child of G4 and not a sibling of G0?** – The logging sentence appears immediately after the arm's actions and specifically says "where and when **a given sample was picked**" — "picked" ties it to the pick event inside G4, not to the whole mission. Time-tracking (G7), by contrast, explicitly spans "between sample collection **and** laboratory delivery" — two events in different branches (G2/G3 and G4) — so it must stay a **top-level parallel monitor**, not nested in one branch.
5. **Why split "Pick Sample" (G4.1) from "Robotic Arm Processing" (G4.1.1)?** – To keep every decomposition using a *single* runtime operator (clean FALLBACK node) rather than mixing FALLBACK and sequence in one row.
6. **Order G1→G2→G3→G4** – No explicit timestamps are given, so I followed the narrative order of the text (request → identification/tracking → secure transport → lab processing), which also matches operational logic (you must know *what* to transport and have a request before dispatching a robot).

## Logical Relationships

### Goal → Goal

- **G0 -> G1, G2, G3, G4 [AND][sequential]**
  - **Justification**: These four goals form the mission's causal backbone — you cannot transport a sample before identifying/registering it, nor process it before it arrives. The text introduces them in this operational order.

- **G0 -> G5, G7 [AND][parallel]**
  - **Justification**: Access control and time-compliance monitoring are not tied to a single stage — G5 applies at every drawer-opening event (inside G3 and G4), and G7 explicitly spans from collection (G3) to delivery (G4). Both must hold *throughout* the pipeline, so they run concurrently with it rather than occupying a fixed position in the sequence.

- **G2 -> G2.1, G2.2 [AND][sequential]**
  - **Justification**: Barcode identification happens "before collection," and the barcode is naturally part of what gets entered into the track system, so identification logically precedes data registration; both are mandatory (AND).

- **G3 -> G3.1, G3.2 [AND][sequential]**
  - **Justification**: The sample must physically be inside the drawer before the robot can move; both steps are mandatory.

- **G4 -> G4.1, G4.2 [AND][sequential]**
  - **Justification**: The sample must first be picked (by whichever agent) before the pick event can be logged — logging requires knowledge of *who/where/when* the pick happened.

- **G4.1 -> G4.1.1, G4.1.2 [AND][FALLBACK(G4.1.1, G4.1.2)]**
  - **Justification**: Text frames arm-pickup and personnel-pickup as alternative ways of resolving the same goal ("can be picked by a robotic arm or laboratory personnel"). Since the arm path is the richer, automated, preferred route and personnel is the manual contingency, FALLBACK best captures this preference-ordered alternative; per the stated rule, FALLBACK carries an AND relation.

- **G5 -> G5.1, G5.2 [AND][sequential]**
  - **Justification**: Authorization must be verified *before* the lock is actuated — acting without verification would violate "only authorized... should be able to open."

### Goal → Task

- **G1 -> AT1 [AND]**
  - **Justification**: Single, atomic operationalization of the request action.

- **G2.1 -> AT2 [AND]**; **G2.2 -> AT3 [AND]**
  - **Justification**: Each sub-goal maps to exactly one concrete, non-decomposable human action described in the text.

- **G3.1 -> AT4 [AND]**; **G3.2 -> AT5 [AND]**
  - **Justification**: Loading and navigating are each a single physical robot action.

- **G5.1 -> AT6 [AND]**; **G5.2 -> AT7 [AND]**
  - **Justification**: Verification and actuation are distinct, atomic operations performed by the same physical access-control subsystem on the transport robot/drawer.

- **G4.1.1 -> AT8, AT9, AT10, AT11 [AND][sequential]**
  - **Justification**: The description lists these four actions in an explicit, fixed order ("picks up... scans... sorts, and loads"), so they must execute sequentially and are all mandatory for this goal to be satisfied.

- **G4.1.2 -> AT12 [AND]**
  - **Justification**: Single fallback human action.

- **G4.2 -> AT13 [AND]**
  - **Justification**: Logging is a single, atomic secure-write operation.

- **G7 -> AT14 [AND]**
  - **Justification**: A single monitoring/computation task comparing two timestamps against a protocol threshold.

## Assumptions & Design Reflections

- **Order of G1 vs. G2**: The description doesn't give timestamps, so I followed narrative order (request → prepare). An equally valid alternative reading would prepare the sample first and request delivery second; if your organization's actual workflow differs, only the `[;]` ordering under G0 needs to change — the goal set itself is unaffected.
- **G5 as a cross-cutting parallel goal** rather than duplicated inside G3 and G4 avoids redundancy and better reflects that it is a *standing security policy* on the drawer, not a one-off step.
- **FALLBACK vs. plain OR for G4.1**: I chose FALLBACK because robots are the subject of this mission model and the arm path yields more functionality (scan/sort/load) than the human path (pick only) — this asymmetry suggests a preferred/contingency relationship rather than two equally-weighted options. If your intent was a neutral choice (e.g., load-balancing between arm and staff), this could instead be modeled as a plain **OR** with equal priority — worth confirming with stakeholders.
- **Human tasks (Number of Robots = 0)** were kept in the task table because a multi-robot mission model benefits from showing explicit human–robot handoff points (request, barcode, data entry, fallback pick) — these are exactly the points where robot autonomy ends and human responsibility begins, which is valuable for safety/liability analysis.
- **G7's dependency on AT4 and AT5 timestamps** is an inference (the text doesn't name the exact start/end events) — "collection" most naturally maps to the moment the sample enters the drawer (AT4) and "delivery" to the robot's arrival at the lab (AT5); this should be validated against the actual laboratory protocol definition.
