# Mission Design Analysis — Lab Sample Transport System

## Step 1: Reading the mission for actors, resources, and constraints

Before building any tree, I extract the "ingredients" of the mission, because a goal model is only as good as the actor/resource map behind it.

**Actors identified:**
- **Nurse** (human) — initiates requests, attaches identification, enters data
- **Transport Robot** (mobile robot, likely a fleet) — carries the locked drawer between floors and the lab
- **Robotic Arm** (stationary robot, lab-side) — picks, scans, sorts, loads
- **Laboratory Personnel** (human) — alternative to robotic arm
- **Track System** (software backend) — stores sample metadata, logs, timing
- **Analysis Machine** (passive receiver, not an agent with goals of its own — it's a resource/interface, so I will **not** give it a goal node, only treat its entry-module as a destination for a task)

**Key constraints/non-functional requirements I must represent as first-class goals (not just footnotes):**
1. Security of the drawer (who can open it) — appears **twice** in the text (implicitly at loading, explicitly at any opening) → this is a *cross-cutting safety/security goal*, not a one-off task.
2. Secure logging of pick events → traceability goal.
3. Time tracking against protocol → compliance goal, continuous, not a one-time check.
4. The **OR** between robotic arm and personnel for picking — I need to decide if this is a *pure OR* (either, by design, e.g. load balancing) or a **FALLBACK** (robot is primary, human is backup). Reading the text again: *"In the laboratory, the sample can be picked by a robotic arm **or** laboratory personnel."* immediately followed by a **detailed description only of the robotic arm's behavior** (scan, sort, load into entry-module). This asymmetry — one branch fully specified, the other left implicit — is a strong signal that the robotic arm is the **primary/automated path** and personnel are the **contingency path** (e.g., when the arm is down, busy, or the sample requires manual handling). I will model this as **FALLBACK**, and per your own formatting rule, FALLBACK forces an **AND** relation at that node.

## Step 2: Deciding the top-level decomposition

Two structurally different things are happening in the text:
- A **linear physical/data pipeline**: request → prepare → transport → receive/process.
- A **cross-cutting monitoring concern**: logging + time compliance, which must run **alongside** the entire pipeline, not after it (you can't "log where/when picked" only at the end — it has to capture an event *during* the pipeline, and time tracking spans from collection to delivery).

This is a classic reason to split the root goal into a **sequential process branch** running in **parallel** with a **monitoring branch**, rather than forcing everything into one sequential chain. I treat this as the single most important structural decision in the model.

## Step 3: Deciding goal types (Achieve / Perform / Query)

I used this rule of thumb while going through each clause:
- If the clause describes a **state to reach and then stop** → **Achieve** (e.g., "drawer is locked", "sample is delivered").
- If the clause describes **checking/reading a property of the environment** → **Query** (e.g., "is this entity authorized", "how much time has elapsed").
- If the clause describes an **open-ended human/robot behavior with no explicit terminal condition in the text** → **Perform** (e.g., "laboratory personnel picks it" — the text gives no completion criteria for the manual path, unlike the automated one).

This is why access-control checks and time measurement became explicit **Query** goals rather than being folded silently into Achieve goals — the text explicitly calls out verification ("should be able to," "should be tracked"), which are epistemic/monitoring statements, not state-change statements.

## Step 4: Building the tree (depth-first reflection)

I allowed up to 4 levels of depth only where the text justified it (access control appears important enough to deserve its own Query goal, not just a task), but I resisted over-decomposing branches the text doesn't elaborate on (e.g., G5.2 manual picking stays a single task — inventing sub-steps the text never gave would be fabrication, not analysis).

## Logical Relationships

- **G1 -> G2, G6 [AND][(parallel)]**
  - **Justification**: The handling pipeline (G2) and the monitoring concern (G6) are both mandatory, but monitoring spans the entire duration of the handling process rather than following it, so they must execute concurrently rather than one after the other.

- **G2 -> G3, G4, G5 [AND][(sequential)]**
  - **Justification**: The text imposes a causal order — a sample must be identified/registered (G3) before it can be collected and transported (G4), and it must be transported before it can be received at the lab (G5). All three are mandatory, hence AND.

- **G3 -> AT1, AT2, AT3 [AND][(sequential)]**
  - **Justification**: Request, barcode assignment, and data entry are each described as necessary and naturally ordered steps; omitting any one would leave the sample unidentifiable or untracked.

- **G4 -> G4.1, AT6, G4.2 [AND][(sequential)]**
  - **Justification**: A locked-drawer transport cannot skip the lock-then-move-then-unlock order; all three are required for the security property to hold end-to-end.

- **G4.1 -> G4.1.1, AT5 [AND][(sequential)]**
  - **Justification**: Authorization must be confirmed before the drawer is loaded and locked — this directly reflects "only authorized...should be able to open the locked drawers," treating "open to load" as the first access event requiring the same gate.

- **G4.1.1 -> AT4 [AND]**
  - **Justification**: A single atomic credential-check task fully realizes this Query goal; no further decomposition is warranted by the text.

- **G4.2 -> G4.2.1, AT8 [AND][(sequential)]**
  - **Justification**: Symmetrical to G4.1 — the same access-control policy must be re-verified before the drawer is opened at the laboratory.

- **G4.2.1 -> AT7 [AND]**
  - **Justification**: Same reasoning as G4.1.1, instantiated at the destination.

- **G5 -> G5.1, G5.2 [AND][FALLBACK(G5.1, G5.2)]**
  - **Justification**: The mission text presents the robotic arm as the fully specified, default automated path and personnel as an unspecified alternative — this asymmetry (one detailed, one not) is the hallmark of a primary/fallback relationship rather than a freely-chosen OR. Per the stated notation rule, FALLBACK forces the Relation field to AND (both branches belong to the same mandatory goal; only one needs to execute per mission instance, but the model must always provide the fallback as the AND-connected contingency).

- **G5.1 -> AT9, AT10, AT11, AT12 [AND][(sequential)]**
  - **Justification**: Directly mirrors the verb sequence in "picks up...scans...sorts...and loads" — each action presupposes the previous one has completed (you can't sort an unscanned sample, can't load an unsorted one).

- **G5.2 -> AT13 [AND]**
  - **Justification**: The manual path is left undecomposed by the source text; a single task captures it faithfully without inventing unstated sub-steps.

- **G6 -> G6.1, G6.2 [AND][(parallel)]**
  - **Justification**: Logging the pick event and tracking elapsed time are independent monitoring activities with no stated dependency between them — both are mandatory, so AND; both can run concurrently, so parallel.

- **G6.1 -> AT14 [AND]**
  - **Justification**: "Logged securely" is satisfied by one atomic, well-defined logging task.

- **G6.2 -> G6.2.1, G6.2.2 [AND][(sequential)]**
  - **Justification**: You cannot verify compliance before you have measured the elapsed time — measurement must precede the compliance check.

- **G6.2.1 -> AT15 [AND]**
  - **Justification**: A single measurement task fully satisfies this Query goal.

- **G6.2.2 -> AT16 [AND]**
  - **Justification**: A single comparison/alerting task fully satisfies this Achieve goal.

## Reflections, assumptions, and open questions worth validating with stakeholders

1. **FALLBACK vs. OR for G5** is my single biggest interpretive call. If, in practice, the hospital *routinely* splits picking between arm and personnel for load-balancing (not just as contingency), this should be remodeled as a plain **OR** with parallel/alternative semantics instead of FALLBACK — I'd recommend confirming this operational detail with the lab.
2. **Who physically places the sample in the drawer (AT5)** is not explicit in the text — I attributed it to the transport robot's mechanism, but it could equally be a nurse action with the robot merely holding the drawer open; this affects whether AT5's "Number of Robots" should be 0 or 1.
3. **I treated "specific robots in specific locations"** as a single location-aware authorization policy (G4.1.1/G4.2.1) rather than two unrelated policies — worth confirming that the same access-control service governs both ends, versus independent floor-level and lab-level systems.
4. **Fleet size** is left implicit everywhere I noted "1 robot" per task — the mission is clearly multi-robot at the *system* level (many transport robots and possibly multiple arms across the hospital), but each *instance* of this goal tree, per sample, only needs one of each. If you want, I can extend this model with a resource-allocation/dispatch goal layer (e.g., "Select Available Transport Robot") to make the multi-robot fleet aspect explicit rather than implicit.
