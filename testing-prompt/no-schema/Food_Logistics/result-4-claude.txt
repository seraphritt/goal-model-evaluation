# Mission Analysis: Hospital Meal‑Delivery & Dish‑Retrieval Multi‑Robot System

## 1. Step‑by‑Step Reasoning Process

Before building the tables, I walked through the description several times, each pass extracting a different layer of the goal model.

**Pass 1 — Identify the triggers (what starts a mission instance).**
Two independent triggers are named explicitly:
- *"The delivery is made on an order‑by‑order basis in response to kitchen delivery requests"* → delivery is **event‑driven** by the kitchen.
- *"Someone in the room can call a robot to pick up the dishes"* → dish collection is **event‑driven** by a person in the room.

Since both triggers are independent, happen for different rooms at different, potentially overlapping times, I concluded the **top‑level mission decomposes into two AND‑related, parallel branches**: *Deliver Meal Order* and *Retrieve Dirty Dishes*. They are not alternatives (OR) — the system must always be able to do both.

**Pass 2 — Find the explicit alternatives ("X or Y" patterns).**
I catalogued every disjunction in the text, because each is a candidate OR/FALLBACK decomposition:
1. Delivery mechanism: *table placement* **or** *tray retrieval*.
2. Tray‑retrieval cooperator: *inpatient* **or** *companion* **or** *nurse* **or** *another robot*.
3. Door opening: cooperation with *another robot* **or** *a human*.
4. Dish retrieval: *unassisted* **or** *two robots* **or** *robot + human*.
5. Door opening for pickup: additionally, *the caller opens it themselves* (a new option specific to the call scenario).

**Pass 3 — Find where uncertainty is explicitly named.**
The text is unusually explicit about uncertainty twice:
- *"Some inpatients could be unable to fetch… a companion visitor or nurse could not be available"*
- *"This information is subject to uncertainty."*

This is the most important modeling signal in the whole description. It tells me:
- The capability check (patient record + companion presence) must be a **Query goal** whose **QueriedProperty is itself uncertain/probabilistic**, not a crisp boolean precondition.
- Because the query can be *wrong*, the delivery‑mechanism choice (#1 above) cannot be a one‑shot decision — it needs a **runtime contingency**. This is exactly what **FALLBACK** is for: attempt the preferred/cooperative path, but guarantee completion through the autonomous path if the first one doesn't actually materialize. This is the clearest, most textually‑grounded use of FALLBACK in the whole model.

**Pass 4 — Decide FALLBACK vs. plain OR for each disjunction.**
Because the allowed runtime operators are only `[#]` (parallel), `[;]` (sequential) and `FALLBACK(...)`, I reasoned as follows:
- If two alternatives are **mutually exclusive and contradictory to run together** (you would never place the meal on the table *and simultaneously* have it fetched from the tray), a sequential contingency is correct → **FALLBACK, Relation = AND** (per the stated convention).
- If several alternatives **could legitimately be attempted concurrently, with only the first success mattering**, that's a genuine **OR decomposition executed in parallel** (a "race"), which is a different, equally valid pattern.

I applied this distinction to the retriever‑engagement goal (#2): food gets cold while waiting, so sequentially trying inpatient → companion → nurse → robot one at a time is realistically slow and fragile. I deliberately modeled it as **OR + `[#]` parallel** (signal all plausible candidates at once, accept the first capable responder) instead of FALLBACK, and I flag this as a conscious design trade‑off (coordination overhead vs. delivery latency/food temperature), since the text does not mandate either strategy.

For door‑opening and dish‑retrieval (#3, #4) there is no explicit urgency argument comparable to food temperature, and no stated preference order, so I used **FALLBACK (AND)** with a reasoned default priority (cheapest/least human‑disruptive option first) — explicitly flagged as an assumption, not a textual requirement.

**Pass 5 — Identify reusable sub‑capabilities.**
"Opening the room door" is discussed once but is clearly needed in *two* places: entering to deliver food, and entering to collect dishes. I modeled it as a **shared sub‑goal/tasks** (`G1.1.2.2`, tasks `AT3`/`AT4`) referenced again inside the pickup flow (`G1.2.2`), which additionally gets a new, cheaper first option — *"that person can signal if they can open the door"* — placed ahead of the shared fallback chain, since it's free information obtained earlier in the pickup call.

**Pass 6 — Map the remaining requirements (multi‑meal handling) to goals.**
*"Carry multiple meals… indicate which meal… track when and where… alert if wrong meal"* are four distinct, sequentially‑dependent obligations that only apply to the tray‑retrieval branch (they're meaningless for table delivery, where the robot itself places the known meal). I grouped them under `G1.1.4.1` (Tray‑Based Delivery): *engage retriever → indicate meal → monitor & validate (log + check + conditional alert)*.

**Pass 7 — Assign goal types (Perform / Query / Achieve).**
Using a KAOS‑style reading: goals that acquire information → **Query** (with `QueriedProperty`); goals with a clear resulting world‑state → **Achieve** (with `Target Condition`); goals that are just a procedural action with no persistent state to check → **Perform** (only "Indicate Correct Meal" fit this cleanly — everything else either fetches info or changes/maintains world state).

With this reasoning fixed, here is the resulting model.

## 6. Logical Relationships

- **G1 → G1.1, G1.2 [AND] (parallel)**
  - *Justification*: Delivery and dish‑retrieval are triggered by different events (kitchen request vs. room call) and run concurrently across rooms; neither can substitute for the other.

- **G1.1 → G1.1.1, G1.1.2, G1.1.3, G1.1.4 [AND] ([;] sequential, with G1.1.2 # G1.1.3 in parallel)**
  - *Justification*: The order must arrive first; travel and feasibility‑assessment are independent of each other and can overlap; delivery needs both finished.

- **G1.1.1 → AT1 [AND]**
  - *Justification*: Single information‑capture task implementing the order trigger.

- **G1.1.2 → AT2, G1.1.2.2 [AND] ([;] sequential)**
  - *Justification*: Must arrive before door access is relevant.

- **G1.1.2.2 → AT3, AT4 [AND] FALLBACK(AT3, AT4)**
  - *Justification*: Explicit alternative cooperators for door‑opening; robot‑robot assumed first for speed, human as fallback.

- **G1.1.3 → AT5, AT6 [AND] (parallel)**
  - *Justification*: Two independent, concurrently‑fetchable information sources feeding one uncertain feasibility estimate.

- **G1.1.4 → G1.1.4.1, G1.1.4.2 [AND] FALLBACK(G1.1.4.1, G1.1.4.2)**
  - *Justification*: Mutually exclusive delivery mechanisms where the preferred one (tray) is explicitly uncertain; table delivery is the autonomous guarantee.

- **G1.1.4.1 → G1.1.4.1.1, G1.1.4.1.2, G1.1.4.1.3 [AND] ([;] sequential)**
  - *Justification*: Must engage a retriever, tell them which meal, then monitor the act — in this causal order.

- **G1.1.4.1.1 → AT7, AT8, AT9, AT10 [OR] ([#] parallel — race)**
  - *Justification*: Any one capable cooperator suffices; offering them concurrently avoids delivery delay given explicitly stated unreliability of each individual candidate.

- **G1.1.4.1.2 → AT11 [AND]**
  - *Justification*: Single, direct procedural task.

- **G1.1.4.1.3 → AT12, AT13, AT14 [AND] ((AT12 # AT13) ; AT14)**
  - *Justification*: Logging and validating can run together on the sensed event; alerting is conditionally sequential on validation's result.

- **G1.1.4.2 → AT15 [AND]**
  - *Justification*: Single autonomous manipulation task.

- **G1.2 → G1.2.1, G1.2.2, G1.2.3 [AND] ([;] sequential)**
  - *Justification*: Call must be received before access is attempted, which must precede collection.

- **G1.2.1 → AT16 [AND]**
  - *Justification*: Single information‑capture task.

- **G1.2.2 → AT17, AT3, AT4 [AND] FALLBACK(AT17, AT3, AT4)**
  - *Justification*: The caller's self‑reported ability to open the door is a free, already‑known option, tried before re‑using the general‑purpose robot/human door‑cooperation fallback shared with delivery.

- **G1.2.3 → AT18, AT19, AT20 [AND] FALLBACK(AT18, AT19, AT20)**
  - *Justification*: Explicit alternative collection modes, ordered here from least to most coordination‑/human‑intensive (an assumption, since no priority is stated in the text).

## 7. Key Assumptions & Design Notes (for traceability)

1. **FALLBACK vs. OR+parallel** — I used FALLBACK (AND) wherever alternatives are mutually exclusive and one is a clear "safety net" for the other (tray‑vs‑table delivery; door‑opening; dish‑pickup modes). I used **true OR with parallel execution** only for *Engage Retriever*, because the explicit mention of individual‑candidate unreliability plus the time‑sensitivity of food delivery favors a concurrent "race" over a slow sequential trial‑and‑error. This is the one place I deliberately diverged from a pure sequential pattern — flagged for discussion with domain stakeholders.
2. **Ordering assumptions** without explicit textual priority (robot‑before‑human for doors; autonomy‑before‑cooperation for dish pickup) are reasonable engineering defaults, not requirements — they should be validated against actual hospital workflow/staff‑burden policies.
3. **Shared sub‑capability**: "Open Room Door" (G1.1.2.2 / AT3, AT4) is reused verbatim inside the pickup flow (G1.2.2), which simply adds a cheaper, call‑specific first option (AT17) ahead of it — reflecting that the description treats door‑opening as one general capability referenced in two contexts.
4. **Uncertainty handling** is the structural centerpiece of the model: it surfaces as (a) an explicit uncertain `QueriedProperty` in G1.1.3, and (b) a guaranteed‑completion FALLBACK in G1.1.4, so the system never fails an order even when the uncertain prediction about human/companion/nurse availability turns out to be wrong.
5. **Scope limitation**: the text only describes a *call‑initiated* trigger for dish pickup; I did not invent a proactive/scheduled pickup goal since nothing in the description supports it.
