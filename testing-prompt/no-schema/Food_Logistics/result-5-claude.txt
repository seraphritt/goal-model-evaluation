# Multi-Robot Mission Analysis: Hospital Meal Delivery & Dish Retrieval

## 1. Analysis Method — Step-by-Step Reasoning

Before building the tables, I read the description multiple times looking for five specific signal types that drive goal-model structure:

1. **Triggers / events** → become *Query* goals (the system must first detect/know something before acting).
   - "in response to kitchen delivery requests" → a request-detection goal.
   - "someone in the room can call a robot to pick up dishes" → a call-detection goal.

2. **Variability points introduced by "or"** → become **OR-decomposition**.
   - "delivered into a room table ... *or* fetched from the robot's tray"
   - "cooperation with the inpatient, a companion, a nurse, *or* another robot"
   - "unassisted, with the cooperation of two robots *or* ... robots and a human"
   - "cooperation with another robot *or* a human" (door)

3. **Variability points introduced by explicit uncertainty/unavailability** → become **FALLBACK** (an ordered AND, "try until one succeeds") rather than a plain OR, because the text explicitly describes *why* an option might not work and implies an attempt order:
   - "Some inpatients could be unable... a companion... or nurse could not be available" → ordered attempt: inpatient → companion → nurse → robot (this is literally the order the sentence lists them in, which I used as the priority).
   - "that person can signal if they can open the door" (dish-pickup call) → human-first attempt, robot-cooperation as fallback.

4. **Statements about information/state that is uncertain** → become **Query** goals with a `QueriedProperty`.
   - inpatient record + companion/nurse presence → capability assessment (explicitly "subject to uncertainty").
   - caller's door-opening ability.

5. **Pure actions with no explicit world-condition to verify** → become **Perform** goals (indicate meal, track retrieval, alert on mismatch).

6. **Mandatory, non-alternative steps** → become **AND-decomposition**, usually **sequential**, since physically a robot must detect → fetch → navigate → access room → deliver, in that order. Two independent "lines of business" (delivery vs. retrieval) are **AND/parallel** at the top because they are triggered independently and can coexist.

I also separated **Goals** (what must become true / be known / be done, abstractly) from **Tasks** (the concrete atomic robot/robot-human actions that realize leaf goals), mapping every leaf goal to one or more tasks — mirroring the `G4 -> AT1, AT2` pattern in the requested example.

**Notation convention I adopted (stated explicitly for traceability):** For OR-decomposed goals, only one branch is actually executed at runtime (selection depends on robot capability, patient condition, or availability), so there is nothing to run "in parallel or sequence" — I mark `Runtime: N/A (OR – single branch selected)`. `#`, `;`, and `FALLBACK(...)` are only meaningful for AND-decompositions.

## 5. Logical Relationships

**G0 -> G1, G2 [AND][(parallel)]**
- **Justification**: Food delivery and dish retrieval are two independently triggered services (kitchen order vs. room call) that the system must support simultaneously throughout its operation.

**G1 -> G1.1, G1.2, G1.3, G1.4, G1.5 [AND][(sequential)]**
- **Justification**: A single delivery instance can only proceed in this causal order: you must know about the order, fetch it, travel, get into the room, then deliver. No step can be skipped or reordered.

**G1.4 -> G1.4.1, G1.4.2 [OR][N/A — single alternative selected]**
- **Justification**: "Opening the room door can involve cooperation with another robot or a human" — stated as a neutral alternative with no priority or triggering-condition language.

**G1.5 -> G1.5.1, G1.5.2 [OR][N/A — single alternative selected]**
- **Justification**: "The food can be delivered into a room table ... or the food can be fetched from the robot's tray" — two mutually exclusive delivery mechanisms, selected per robot capability/patient condition rather than attempted in sequence.

**G1.5.2 -> G1.5.2.1, G1.5.2.2, G1.5.2.3, G1.5.2.4, G1.5.2.5 [AND][(sequential), with G1.5.2.4 and G1.5.2.5 executing in parallel once retrieval starts]**
- **Justification**: Capability must be assessed first, then the meal indicated, then retrieval attempted; tracking and mismatch-alerting are continuous monitoring concerns that naturally run alongside/after the retrieval act rather than strictly before it.

**G1.5.2.3 -> G1.5.2.3.1, G1.5.2.3.2, G1.5.2.3.3, G1.5.2.3.4 [AND][FALLBACK(G1.5.2.3.1, G1.5.2.3.2, G1.5.2.3.3, G1.5.2.3.4)]**
- **Justification**: The text explicitly raises the possibility that each option may fail ("could be unable," "could not be available"), which is the defining signature of a fallback (try-in-order) structure rather than a free-choice OR. The order mirrors the text's own listing order, prioritizing patient autonomy, then readily-present companion, then staff, then robot-robot cooperation as the costliest last resort.

**G2 -> G2.1, G2.2, G2.3, G2.4 [AND][(sequential)]**
- **Justification**: "As with delivery," the pickup process must detect the call, travel, access the room, then retrieve — the same causal-ordering logic as G1.

**G2.3 -> G2.3.1, G2.3.2 [AND][FALLBACK(G2.3.1, G2.3.2)]**
- **Justification**: Unlike the generic door-opening alternative in G1.4, this instance is explicitly tied to a caller who "can signal if they can open the door when the robot comes to it" — implying the human option is checked/attempted first (since the person is already engaged and present), falling back to robot-robot cooperation only if they can't or don't respond.

**G2.4 -> G2.4.1, G2.4.2, G2.4.3 [OR][N/A — single alternative selected]**
- **Justification**: "The dish retrieve can occur unassisted, with the cooperation of two robots or with the cooperation of robots and a human" — three explicit, equally-weighted alternatives with no stated priority or failure condition, unlike the meal-retrieval case.

**G1.1 -> AT1 [AND]**
- **Justification**: A single monitoring/sensing task is sufficient to realize the detection goal.

**G1.2 -> AT2, AT3 [AND][(sequential)]**
- **Justification**: The robot must arrive at the kitchen before it can load the meal(s).

**G1.3 -> AT4 [AND]** / **G1.4.1 -> AT5 [AND]** / **G1.4.2 -> AT6 [AND]** / **G1.5.1 -> AT7 [AND]**
- **Justification**: Each of these leaf goals is realized by exactly one corresponding atomic action named or directly implied by the text.

**G1.5.2.1 -> AT8, AT9 [AND][(parallel)]**
- **Justification**: The capability assessment draws on two independent information sources named separately in the text ("the inpatient record" and "the presence of a companion"), which can be queried concurrently.

**G1.5.2.2 -> AT10 [AND]**, **G1.5.2.3.1 -> AT11 [AND]**, **G1.5.2.3.2 -> AT12 [AND]**, **G1.5.2.3.3 -> AT13 [AND]**, **G1.5.2.3.4 -> AT14 [AND]**, **G1.5.2.4 -> AT15 [AND]**, **G1.5.2.5 -> AT16 [AND]**
- **Justification**: Direct one-to-one mapping between a single explicit requirement sentence and a single atomic task.

**G2.1 -> AT17 [AND]**, **G2.2 -> AT18 [AND]**, **G2.3.2 -> AT19 [AND]**
- **Justification**: Direct realization of straightforward leaf goals.

## 6. Assumptions, Reflections & Open Design Questions

Because a mission description in natural language is necessarily incomplete, I want to be transparent about the inferences I made and flag them for validation with stakeholders:

1. **FALLBACK order for meal retrieval (G1.5.2.3)** is inferred from the sentence's own enumeration order (inpatient → companion → nurse → robot). This is a *reasonable* default (favor patient autonomy, then minimize staff/robot resource use) but should be confirmed with clinical/operational staff — a hospital might instead prefer "nurse first" for safety reasons in some wards.

2. **G1.5 (table vs. tray) modeled as OR, not FALLBACK.** An equally defensible alternative reading is that this is secretly a capability-driven fallback too: *if* the robot has the manipulation skill, *always* prefer table delivery (more hygienic, no human workload), *else* fall back to tray retrieval.
