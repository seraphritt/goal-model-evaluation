# Multi-Robot Mission Goal Model: Hospital Meal Delivery & Dish Collection

## Part 1 — Step-by-Step Analysis (Mission Designer's Reasoning)

Before building the tables, I worked through the description systematically:

**Step 1 — Identify the triggers (events that spawn mission instances).**
Two independent, asynchronous triggers exist: *"kitchen delivery requests"* (one per order) and *"someone in the room can call a robot to pick up the dishes"*. This tells me the system has **two parallel, recurring sub-missions**, not one linear process — so the root of the goal model must fork into two branches that run concurrently and independently (the robot "can carry multiple meals," which confirms multiple order-instances can be in flight at once).

**Step 2 — Separate "what must always happen" (AND) from "what could happen instead" (OR/FALLBACK).**
I looked for every place the text offers alternatives:
- Delivery: *table placement* **or** *tray retrieval*.
- Tray retrieval agent: *inpatient* **or** *companion* **or** *nurse* **or** *another robot*.
- Door opening: *another robot* **or** *a human*.
- Dish retrieval: *unassisted* **or** *two robots* **or** *robot+human*.

Critically, in every one of these cases the text explicitly pairs the alternative with a reason it might **fail or be unavailable** ("some inpatients could be unable…", "a companion… could not be available…", uncertainty about the inpatient record). This is the textbook signature of a **FALLBACK pattern**, not a simple OR: the system shouldn't pick one option once and stop — it must be able to try one option and, upon failure/unavailability, automatically attempt the next. That's why I used `FALLBACK(...)` (with AND relation, as instructed) everywhere an alternative is coupled with a failure condition, and reserved plain OR for cases of mutually exclusive static choice (I found none pure enough to justify OR in this mission — every alternative here is contingency-driven).

**Step 3 — Decide Goal Type (Perform vs. Achieve vs. Query) methodically, not by guesswork.**
- **Query** goals are used exactly where the text says information must be *obtained* and is *"subject to uncertainty"* — i.e., sensing/information-gathering goals whose result feeds a decision (inpatient-record lookup + companion-presence detection; the door-opening signal).
- **Achieve** goals are used for every node that is a candidate branch inside a FALLBACK, because fallback logic needs a success/failure verdict against a target condition to decide whether to try the next branch. A "Perform" goal (pure procedure) doesn't carry that pass/fail semantics cleanly.
- **Perform** goals are used for straightforward, non-contingent procedural steps (receiving a request, navigating, loading, logging) where there's no alternative to fall back to.

**Step 4 — Scope the "indicate / track / alert" cluster correctly.**
The text places "indicate which meal," "track when/where retrieved," and "alert if wrong meal retrieved" immediately after describing *person-based* tray retrieval — not after table delivery or robot-robot transfer. I therefore nested these three goals **inside** the tray-retrieval branch rather than as siblings of the whole delivery goal, to avoid implying they apply to table delivery (where the robot itself controls placement and no "wrong pick" risk from a third party exists).

**Step 5 — Notice the asymmetry in uncertainty.**
Uncertainty is explicitly flagged for *meal-retrieval capability* but not for *dish-collection cooperation mode* or *door-opening mode*. I preserved this: a Query goal precedes the delivery-mode fallback and the door-opening fallback (door-opening signal), but **not** the dish-collection fallback, which I model as a pure runtime-success/failure fallback chain (robot discovers mid-task whether it needs help).

**Step 6 — Flag inferred elements.**
The description doesn't state what happens to dishes after collection. I added one closure goal/task for this, explicitly marked as an **assumption**, since "retrieve dirty dishes" is only meaningful if they end up somewhere (kitchen/wash station). Everything else in the model is directly traceable to a sentence in the description.

## Part 5 — Logical Relationships

- **G1 -> G2, G3 [AND] [#] (parallel)**
  - **Justification**: Delivery and dish-collection are triggered by independent events (kitchen request vs. room call) and must be supported concurrently; the mission doesn't require one to finish before the other starts.

- **G2 -> G4, G5, G6, G7, G8 [AND] [;] (sequential)**
  - **Justification**: "order-by-order" delivery implies a strict causal chain — you cannot assess retrieval context before arriving, cannot load before receiving the request, etc.

- **G7 -> AT4, AT5 [AND] [#] (parallel)**
  - **Justification**: Inpatient-record lookup and companion-presence detection are independent information sources that can be gathered concurrently to answer the same query.

- **G8 -> G9, G18 [AND] FALLBACK(G9, G18)**
  - **Justification**: "food can be delivered into a room table... or... fetched from the robot's tray" — paired explicitly with reasons tray retrieval might fail, so the system must retry via the alternate mechanism rather than commit to one choice upfront.

- **G9 -> G10, G11, G16, G17 [AND] [;] (sequential)**
  - **Justification**: The meal must be indicated before/while it's grabbed, the grab must be logged, and only after logging can a mismatch be detected and alerted — direct order of the "indicate / track / alert" passage.

- **G11 -> G12, G13, G14, G15 [AND] FALLBACK(G12, G13, G14, G15)**
  - **Justification**: "cooperation with the inpatient, a companion, a nurse, or another robot," explicitly motivated by inpatient inability and companion/nurse unavailability — a contingency chain, escalating from least to most "automated" assistance.

- **G3 -> G19, G20, G21, G26, G30 [AND] [;] (sequential)**
  - **Justification**: Mirrors G2's structure: trigger → travel → gain access → act → close out (dishes must go somewhere).

- **G21 -> G22, G23 [AND] [;] (sequential)**
  - **Justification**: The caller's door-opening signal ("can signal if they can open the door") must be known before/while the opening action executes, so it can bias which cooperation mode is tried first.

- **G23 -> G24, G25 [AND] FALLBACK(G24, G25)**
  - **Justification**: "cooperation with another robot or a human" — ordered human-first here because G22's signal, when positive, makes human assistance immediately available and avoids summoning a second robot.

- **G26 -> G27, G28, G29 [AND] FALLBACK(G27, G28, G29)**
  - **Justification**: "unassisted, with the cooperation of two robots or with the cooperation of robots and a human" — order taken directly from the text, escalating coordination cost only as needed; no preceding Query goal, since no uncertainty is stated for this decision (contrast with G8/G21).

- **G4 -> AT1 [AND]**, **G5 -> AT2 [AND]**, **G6 -> AT3 [AND]**, **G10 -> AT6 [AND]**, **G12 -> AT7 [AND]**, **G13 -> AT8 [AND]**, **G14 -> AT9 [AND]**, **G15 -> AT10 [AND]**, **G16 -> AT11 [AND]**, **G17 -> AT12 [AND]**, **G18 -> AT13 [AND]**, **G19 -> AT14 [AND]**, **G20 -> AT15 [AND]**, **G22 -> AT16 [AND]**, **G24 -> AT17 [AND]**, **G25 -> AT18 [AND]**, **G27 -> AT19 [AND]**, **G28 -> AT20 [AND]**, **G29 -> AT21 [AND]**, **G30 -> AT22 [AND]**
  - **Justification**: Each is a single-task realization of its parent leaf goal; trivial AND since there is exactly one concrete action satisfying each goal.

### Key modeling observations worth flagging back to you
1. **No pure OR-decompositions appear anywhere.** Every "either/or" in the text is paired with a reason an option can fail — so FALLBACK (AND) consistently beats OR as the faithful choice.
2. **Asymmetric uncertainty** (explicit for meal-retrieval and door-signal, silent for dish-collection mode) is preserved by placing Query goals only where the text puts them.
3. **One inferred element** (G30/AT22, dish transport destination) is not in the source text and is flagged as a designer assumption — worth confirming with stakeholders.
