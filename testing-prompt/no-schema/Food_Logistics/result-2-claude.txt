# Goal Model for the Hospital Meal‑Delivery / Dish‑Retrieval Multi‑Robot Mission

## 1. Step‑by‑Step Analysis (how I read the description)

Before building any table I went through the description several times looking for five specific things, because each one maps to a different modeling decision in this notation:

1. **Triggers / events** → these become the top‑level, independently‑launchable mission goals.
   - "in response to kitchen delivery requests" → trigger for the *delivery* mission.
   - "Someone in the room can call a robot to pick up the dishes" → trigger for the *dish‑retrieval* mission.
   - These are clearly two separate, asynchronous services (different initiators, different locations of initiation), so I modeled them as two parallel top‑level goals under one umbrella mission, not as one sequential pipeline.

2. **Explicit "or" statements** → candidates for **OR** decomposition.
   - "The food can be delivered into a room table... **or** the food can be fetched from the robot's tray" — a genuine *alternative strategy* choice, apparently driven by a **fixed robot capability** (does this robot have the manipulation skill?) rather than by something that can fail at runtime. I modeled this as **OR**, and I flag the alternative interpretation in §7.

3. **Uncertainty / "could be unable / could not be available" statements** → candidates for **FALLBACK**, not plain OR.
   - "Some inpatients could be unable to fetch the food... a companion visitor or nurse could not be available" and "This information is subject to uncertainty" — this is *not* a free choice, it's "try the best option, and if it isn't possible, try the next one." That is exactly what FALLBACK encodes (ordered contingency, AND‑joined because all branches together guarantee the goal). The same reasoning pattern (cooperation with another robot **or** a human, for the door; unassisted **or** two robots **or** robot+human, for dishes) was treated the same way for consistency, even though the "could not" wording isn't repeated verbatim there (discussed in §7).

4. **Cross‑cutting / supporting obligations** that are not steps in the main flow but *quality/safety wrappers* around a step:
   - "indicate which meal should be retrieved," "track when and where," "alert if a wrong meal is retrieved" — these only make sense in the *tray‑retrieval* branch (nobody needs to be told which meal if the robot itself places it on the table), so I nested them under that branch rather than under the whole delivery goal.
   - The information used to pick a retriever ("based on the inpatient record... and the presence of a companion") is itself a **Query goal** that must resolve *before* the FALLBACK is attempted.

5. **Shared sub‑problems** appearing in both missions:
   - "Opening the room door" is needed both to deliver and to pick up dishes, so I treat it as the *same kind* of goal in both branches, but **not identical**, because the dish‑pickup flow adds an extra piece of information not present in the delivery flow ("that person can signal if they can open the door"). That extra signal gives pickup a third, cheaper fallback option (occupant opens it themselves) that delivery does not have.

This gives a tree with: 1 root, 2 mission goals, 18 supporting goals (21 goals total), and 23 atomic tasks.

### Resulting tree (overview)

```
G1 Hospital Meal Robot Service [Perform] (AND, parallel)
├─ G2 Deliver Kitchen Order to Inpatient [Achieve] (AND, sequential)
│   ├─ G4 Acquire Meal Order from Kitchen [Achieve] → AT1, AT2
│   ├─ G5 Travel to Inpatient Room [Achieve] → AT3
│   ├─ G6 Gain Room Access for Delivery [Achieve] FALLBACK → AT4, AT5
│   └─ G7 Deliver Meal into Room [Achieve] (OR)
│       ├─ G8 Place Meal on Room Table [Achieve] → AT6
│       └─ G9 Deliver Meal via Tray Retrieval [Achieve] (AND, sequential)
│           ├─ G10 Determine Capable Meal Retriever [Query] (AND, parallel) → AT7, AT8
│           ├─ G11 Indicate Target Meal for Retrieval [Perform] → AT9
│           ├─ G12 Obtain Meal Retrieval by Capable Party [Achieve] FALLBACK → AT10, AT11, AT12, AT13
│           └─ G13 Monitor Meal Retrieval [Perform] (AND, sequential)
│               ├─ G14 Verify Retrieved Meal Identity [Query] → AT14
│               ├─ G15 Log Retrieval Time & Location [Achieve] → AT15
│               └─ G16 Alert on Meal Mismatch [Achieve] → AT16
└─ G3 Retrieve Dirty Dishes from Room [Achieve] (AND, sequential w/ one parallel pair)
    ├─ G17 Receive Dish Pickup Call [Perform] → AT17
    ├─ G18 Determine Door-Opening Capability of Caller [Query] → AT18
    ├─ G19 Travel to Room for Pickup [Achieve] → AT19
    ├─ G20 Gain Room Access for Pickup [Achieve] FALLBACK → AT20, AT4, AT5
    └─ G21 Retrieve Dirty Dishes from Room [Achieve] FALLBACK → AT21, AT22, AT23
```

## 5. Logical Relationships

**G1 -> G2, G3 [AND][(parallel)]**
- **Justification**: Delivery and dish‑retrieval are triggered by different, unrelated events (kitchen request vs. room call) and the system must support both at any time, so they are mandatory (AND) and independent (parallel) rather than ordered.

**G2 -> G4, G5, G6, G7 [AND][(sequential)]**
- **Justification**: A single order must be loaded, transported, have room access gained, and then delivered — in that physical order; all four are mandatory for the order to count as delivered.

**G7 -> G8, G9 [OR]**
- **Justification**: The description states the food "can be delivered into a room table... or... fetched from the robot's tray" as two mutually exclusive strategies for a given delivery; only one needs to succeed.

**G9 -> G10, G11, G12, G13 [AND][(sequential)]**
- **Justification**: Before tray‑retrieval can succeed the system must know who can retrieve (G10), tell them which meal (G11), get it retrieved (G12), and then verify/log/alert (G13) — each depends on the previous one's output.

**G13 -> G14, G15, G16 [AND][(sequential)]**
- **Justification**: The identity of the retrieved meal must be checked (G14) before a mismatch can be logged for traceability (G15) and alerted on (G16); all three are explicitly required quality/safety obligations in the text.

**G10 -> AT7, AT8 [AND][(parallel)]**
- **Justification**: The two information sources — "the inpatient record" and "the presence of a companion" — are independent data points that can be gathered concurrently; both are needed to resolve the query.

**G6 -> AT4, AT5 [AND][FALLBACK(AT4, AT5)]**
- **Justification**: "Opening the room door can involve cooperation with another robot or a human" gives two means with no guaranteed availability; FALLBACK tries one, then the other, guaranteeing the AND‑level goal (door open) is still met.

**G12 -> AT10, AT11, AT12, AT13 [AND][FALLBACK(AT10, AT11, AT12, AT13)]**
- **Justification**: The text explicitly warns that each of the four possible retrievers may be unable/unavailable; the ordered retry (inpatient → companion → nurse → robot) is the direct operationalization of that uncertainty, AND‑joined as required by the FALLBACK rule.

**G3 -> G17, G18, G19, G20, G21 [AND][(sequential, with G18 and G19 executable in parallel)]**
- **Justification**: The call must be received first (trigger), after which the door‑capability question (G18) can be resolved over the comms channel *while* the robot is still travelling (G19) — an efficiency the text doesn't forbid — before access (G20) and collection (G21), which do depend on arrival.

**G20 -> AT20, AT4, AT5 [AND][FALLBACK(AT20, AT4, AT5)]**
- **Justification**: Because the caller "can signal if they can open the door," that option (cheapest, no cooperation needed) is tried first; only if it is not available does the system fall back to the general robot/human cooperation options reused from G6.

**G21 -> AT21, AT22, AT23 [AND][FALLBACK(AT21, AT22, AT23)]**
- **Justification**: "Can occur unassisted, with the cooperation of two robots, or with the cooperation of robots and a human" is read as a resource‑escalation ladder — attempt the cheapest (unassisted) option, escalate only as needed — mirroring the uncertainty‑driven FALLBACK pattern used elsewhere in the model (see design note in §7 below).

**G4 -> AT1, AT2 [AND][(sequential)]**
- **Justification**: Meals must be loaded before they can be confirmed as correctly matched to the order.

**G13 -> AT14 / AT15 / AT16 via G14/G15/G16 [AND]**
- **Justification**: Each monitoring sub‑goal maps to exactly one concrete sensing/logging/alerting action; no alternative method is described in the text.

**G5 -> AT3, G19 -> AT19, G8 -> AT6, G11 -> AT9, G17 -> AT17, G18 -> AT18 [AND, single task each]**
- **Justification**: These are atomic, single‑method goals in the description (one way to travel, one way to place on table, one way to indicate, one way to receive a call/signal), so each decomposes to exactly one task under AND.

## 6. Design Notes, Assumptions & Reflections

A few places required a judgment call rather than a literal reading, which I want to flag explicitly rather than hide inside a table cell:

- **OR vs. FALLBACK for G7 (table vs. tray delivery).** I modeled this as a plain **OR** because the "special manipulation robot skill" reads as a fixed, known‑in‑advance robot capability (either this robot has it or it doesn't), not something that fails unpredictably at runtime the way availability of a companion or nurse does. An equally defensible alternative is **FALLBACK(G8, G9)** if the mission designer wants the robot to *attempt* table placement and gracefully degrade to tray delivery when, say, the table is physically unreachable (obstructed, wrong height, etc.) — a failure mode the text doesn't mention but that is realistic. I'd recommend confirming with domain experts whether manipulation failures at the table are a concern before finalizing this as OR vs. FALLBACK.

- **FALLBACK for G21 (dish‑retrieval modes) is an inference, not a direct textual mandate.** Unlike the meal‑retrieval case, the text never says the robot "could be unable" to retrieve dishes unassisted. I chose FALLBACK over plain OR to keep the model consistent with the resilience pattern used everywhere else uncertainty about human/robot availability appears, and because "unassisted → two robots → robot+human" reads naturally as an escalation of resource cost. If, in practice, the delivery mode is instead chosen *in advance* by a dispatcher (e.g., always send two robots for heavy trays), plain **OR** (context‑selected, no retry) would be the more faithful choice — this is worth validating with stakeholders.

- **Reuse of the door‑opening goal (G6/G20).** I treated delivery‑side and pickup‑side door access as two *distinct* goals rather than one shared instance, because the pickup flow has access to an extra piece of information (the occupant's self‑reported ability to open the door) that the delivery flow never gets. Modeling them identically would have silently lost that nuance; modeling them as two goals that *share two tasks* (AT4, AT5) keeps the reuse visible while preserving the asymmetry.

- **Parallelization opportunity not shown in the baseline tree.** G10 ("Determine Capable Meal Retriever") only needs database/sensor access, not physical presence in the room — in a real implementation it could run concurrently with G5/G6 (travel/door access) rather than strictly after G7 is entered. I kept it sequential inside G9 for readability, but this is a legitimate optimization a later refinement pass should consider.

- **Uncertainty is modeled structurally, not probabilistically.** The text twice stresses "subject to uncertainty." In this notation, uncertainty is handled by (a) a Query goal that fetches the best available estimate, feeding (b) a FALLBACK chain that tolerates the estimate being wrong by trying the next option. I did not introduce explicit confidence/probability attributes since the notation given has no column for them — if the underlying framework supports probabilistic annotations on Query goals, that would be a natural extension.

- **"Robot can carry multiple meals" was treated as a capability statement, not a standalone goal.** It surfaces as a *requirement* on G4 (confirm correct meal(s) loaded) and G11 (indicate which of several meals is whose) rather than as its own node, since the text never asks the robot to "achieve" carrying multiple meals — it's a precondition that shapes other goals.
