# Mission Analysis: Hospital Meal Delivery & Dish Retrieval Robot System

## Step‑by‑Step Reasoning

**1. Identify the top-level responsibilities.**
The description states two independent, mandatory system responsibilities: "the system should deliver food…" and, separately, "Dirty dishes should be retrieved from the room." Nothing suggests one is an alternative to the other — both must be supported. → **AND** at the root, and since the text gives no explicit order between the two service loops (they are triggered by different events — kitchen requests vs. room calls), I treat them as **parallel (#)**.

**2. Identify triggers.** Both sub-processes are explicitly event-triggered: delivery is "in response to kitchen delivery requests" (order-by-order), and dish pickup is triggered when "someone in the room can call a robot." I modeled both triggers as **Query goals** (the robot must obtain information from the environment — the request/call), rather than ignoring them, because the robot is the one perceiving/receiving them (zero-robot rule is satisfied).

**3. Decomposition type decisions (OR vs AND vs FALLBACK).**
I applied the strict rule that **FALLBACK is used only when the text explicitly states an attempt order** ("try X, and if it fails do Y"). I found **no such explicit ordering** anywhere in the text — including the delivery-method choice (table vs. tray) and the cooperation-mode choices (dish retrieval, door opening). Even though a "try manipulation, fallback to human help" reading is *plausible*, it is not *stated*, so per the rule I modeled these as **OR decompositions**, and gave them a **parallel (#)** runtime annotation to express "alternative, unordered, no obligatory sequencing" rather than inventing an order that isn't in the text.

Conversely, I used **sequential (;)** wherever the text implies a necessary causal/physical order (e.g., you must receive an order before transporting it; you must open a door before picking up dishes; you must determine eligibility before indicating a meal). This is not FALLBACK because there is no failure/alternative condition — it's a plain required order.

**4. Goal typing.**
- **Query**: goals whose purpose is to obtain information (requests, calls, record checks, presence detection, eligibility, door-signal).
- **Perform**: goals that are a discrete reactive action without a complex target state (e.g., raising an alert).
- **Achieve**: goals with a state to reach, usually through alternative strategies (delivery, retrieval, collection, tracking).

**5. Avoiding redundancy.** 
I noticed the text scopes "indicate which meal" **only** to the "a person retrieving" case, but scopes "track when/where" and "alert on wrong meal" **generally** (not restricted to person-only). I therefore placed "Indicate Meal" inside the *person* branch only, but placed "Track" and "Alert" at the common ancestor shared by both the person-cooperation and robot-cooperation branches, avoiding duplicating them under each OR branch. Similarly, "cooperation with inpatient, companion, nurse, or another robot" was split into **(person) OR (robot)** first, because the uncertainty/eligibility-check machinery ("some inpatients could be unable…companion/nurse not available…subject to uncertainty") applies only to the human options, not to robot cooperation — nesting the eligibility Query goal only under the person branch avoids falsely implying robots need eligibility checks too.

**6. Locations.** I used only literally cited locations: **kitchen**, **room** (inpatient room), **room table**, **room door**. I avoided inventing "hospital" or similar since it never appears in the text.

**7. Robot counts.** Derived directly from cooperation cardinality stated in text: "another robot" → 2 robots; "two robots" → 2 robots; "robot and a human" / "robot alone" / person-retrieval (human isn't a robot) → 1 robot.

### Notes on modeling choices worth flagging
- Two cases (**G3**, **G11**) have only a single child task. Since the fallback/parallel/sequential operators require two distinct expressions, I used the leaf-symbol "**-**" there rather than inventing a second branch, and marked their relation as AND by convention (a single necessary child trivially satisfies AND semantics).
- I deliberately **did not** use FALLBACK anywhere, even where a "try the robot skill, otherwise use cooperation" interpretation feels intuitive, because the mission text never states an explicit attempt order or failure-triggered alternative — per your rule, this must remain OR, not FALLBACK.
- The uncertainty mentioned for G8's information ("subject to uncertainty") has no dedicated modeling construct in the goal-model notation you specified, so I recorded it as a qualifying note on the Query goal's queried property rather than inventing a new node type.
