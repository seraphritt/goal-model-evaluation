# Goal Model – Hospital Meal Delivery & Dish Collection Robot System

Oct 17, 2026 · @Isaque

## Methodology and Step-by-Step Reasoning

1. **Identify the system's distinct responsibilities.** The description names two independent processes: delivering food (triggered by "kitchen delivery requests") and retrieving dirty dishes (triggered by someone "calling a robot"). Since both are required capabilities of the system and nothing ties their timing together, they form the two AND-children of the root goal, executed in parallel — no order is stated, and a multi-robot system naturally handles several orders/rooms concurrently.
2. **Separate "receiving a trigger" from "acting on it."** Both delivery and dish pickup react to an external trigger (a kitchen request; a call from the room), and each trigger carries information the robot needs before it can act (what/where to deliver; whether the person can open the door). Each is modeled as a leaf **Query** goal, since its entire purpose is to obtain information — matching the Query Goal definition exactly.
3. **Resolve the delivery alternatives as OR, not FALLBACK.** "The food can be delivered into a room table ... or ... fetched from the robot's tray" uses "or" with no stated order of preference. FALLBACK requires an explicit "try X, then Y" or a stated condition; since none is given, this is an **OR decomposition** with a parallel (unordered) runtime, not a fallback.
4. **Resolve "who can retrieve from the tray" as OR, not FALLBACK — despite the uncertainty language.** The text notes inpatients/companions/nurses may be unable or unavailable, and that this is "subject to uncertainty," but it never states an explicit sequence of attempts (e.g. "try the inpatient first, then the companion"). Because FALLBACK is reserved strictly for explicitly ordered normal/alternative behavior, this stays an **OR decomposition** of alternative cooperating agents. "Inpatient," "companion," and "nurse" are merged into one task (Retrieve Meal via Human Cooperation) because, from the robot's operational perspective, the action is identical regardless of which human performs it — keeping them separate would duplicate the same robot intention three times, which the no-redundancy rule forbids. "Another robot" stays a separate alternative because it requires a materially different task (a two-robot handoff).
5. **Identify the one genuine FALLBACK in the description.** "The robot should alert if a wrong meal is retrieved" is an explicit IF-condition describing an exception to the normal (correct) retrieval outcome — exactly the FALLBACK pattern: exp1 = normal behavior (retrieve the meal), exp2 = alternative behavior triggered by failure (alert). This is modeled as FALLBACK(Retrieve Meal from Tray, Alert on Wrong Meal Retrieved), AND-connected per the rule that FALLBACK's two branches are always AND-related.
6. **Order the tray-fetch sub-steps sequentially where the text implies a necessary order.** The robot must indicate the meal before it can be retrieved, and can only log the time/location after retrieval happens — a temporal necessity (not a fallback-style condition), justifying a **sequential** runtime.
7. **Model door-opening and dish collection only where the text supports them.** Door-opening cooperation is described specifically in the dirty-dish paragraph, so it is placed under "Retrieve Dirty Dishes" rather than assumed for delivery too (nothing is invented). The physical necessity of an open door before dishes can be collected justifies sequencing "Open Door" before "Pick Up Dirty Dishes."
8. **Apply the zero-robot rule.** Every leaf task keeps at least one robot in its description (presenting a tray, handing off between robots, opening a door, picking up dishes); purely human-only actions (e.g. the inpatient eating the food) were excluded as outside the robot system's scope.
9. **Choose goal types.** Query is used exactly where the text frames the goal as "obtaining information" (order details; retrieval-capability data; pickup-call/door-availability data). All other non-leaf, non-task goals are **Achieve**, since each represents a target world-state (meal delivered, door open, dishes collected, correct meal confirmed) reachable through one or more means, not a single fixed action. Atomic, concretely assignable actions (place meal on table, indicate a meal, retrieve a meal, alert, track, open a door, pick up dishes) are modeled directly as **Tasks** — the framework's fully operational layer — which is why no goal node needed the **Perform** type here.
10. **Avoid redundancy and keep the tree connected.** Each node was checked against its siblings and ancestors to confirm it expresses a distinct intention (e.g. "Deliver Food Order," "Transfer Meal to Patient," and "Fetch Meal from Robot Tray" are different grains of the same process, not duplicates), and every node connects to the tree through a justified AND/OR relation.

## Goal Model Tree Overview

- **G0** Provide Inpatient Meal Service — AND (parallel: G1 # G8)
  1. **G1** Deliver Food Order to Inpatient — AND (sequential: (G2;G3);G4)
     1. **G2** Receive Kitchen Delivery Request *(leaf, Query)*
     2. **G3** Determine Food Retrieval Capability *(leaf, Query)*
     3. **G4** Transfer Meal to Patient — OR (parallel: AT1 # G5)
        1. **AT1** Place Meal on Room Table *(task, leaf)*
        2. **G5** Fetch Meal from Robot Tray — AND (sequential: (AT2;G6);AT6)
           1. **AT2** Indicate Correct Meal to Retriever *(task, leaf)*
           2. **G6** Ensure Correct Meal Retrieved — AND, FALLBACK(G7, AT5)
              1. **G7** Retrieve Meal from Tray — OR (parallel: AT3 # AT4)
                 1. **AT3** Retrieve Meal via Human Cooperation *(task, leaf)*
                 2. **AT4** Retrieve Meal via Robot-Robot Handoff *(task, leaf)*
              2. **AT5** Alert on Wrong Meal Retrieved *(task, leaf)*
           3. **AT6** Track Meal Retrieval Time and Location *(task, leaf)*
  2. **G8** Retrieve Dirty Dishes from Room — AND (sequential: (G9;G10);G11)
     1. **G9** Receive Dish Pickup Request *(leaf, Query)*
     2. **G10** Open Inpatient Room Door — OR (parallel: AT7 # AT8)
        1. **AT7** Open Door via Robot Cooperation *(task, leaf)*
        2. **AT8** Open Door via Human Cooperation *(task, leaf)*
     3. **G11** Pick Up Dirty Dishes — OR (parallel: (AT9 # AT10) # AT11)
        1. **AT9** Retrieve Dishes Unassisted *(task, leaf)*
        2. **AT10** Retrieve Dishes via Two-Robot Cooperation *(task, leaf)*
        3. **AT11** Retrieve Dishes via Robot-Human Cooperation *(task, leaf)*

## Logical Relationships

- **G0 -> G1, G8 \[AND\] (parallel)**
  - Justification: Food delivery and dish retrieval are two independent, explicitly stated system responsibilities with no stated dependency or order between them; in a multi-robot hospital setting, both can proceed at the same time for different orders and rooms.
- **G1 -> G2, G3, G4 \[AND\] (sequential)**
  - Justification: All three are necessary parts of fulfilling a delivery order, and each logically depends on the one before it: the request must be received (G2) and the retrieval capability determined (G3) before the meal can actually be transferred (G4).
- **G4 -> AT1, G5 \[OR\] (parallel)**
  - Justification: "delivered into a room table ... or ... fetched from the robot's tray" presents alternative, mutually exclusive delivery modes with no explicit order of preference between them.
- **G5 -> AT2, G6, AT6 \[AND\] (sequential)**
  - Justification: Indicating which meal to retrieve must precede the retrieval/verification step, which must in turn precede logging the retrieval's time and location — a necessary processing order implied by the text.
- **G6 -> G7, AT5 \[AND\] (FALLBACK(G7, AT5))**
  - Justification: "The robot should alert if a wrong meal is retrieved" is an explicit condition that triggers an alternative action (alert) only when the normal retrieval outcome (the correct meal taken) fails — the defining FALLBACK pattern. FALLBACK's two branches are always AND-related per the modeling rule.
- **G7 -> AT3, AT4 \[OR\] (parallel)**
  - Justification: "cooperation with the inpatient, a companion, a nurse, or another robot" lists interchangeable alternative cooperating agents with no stated order; the three human types are merged into AT3 to avoid duplicating the same robot intention three times.
- **G8 -> G9, G10, G11 \[AND\] (sequential)**
  - Justification: The robot must receive the pickup request — and the door-opening signal it carries — before opening the door, and the door must be open before the dishes can physically be collected.
- **G10 -> AT7, AT8 \[OR\] (parallel)**
  - Justification: "Opening the room door can involve cooperation with another robot or a human" presents two alternative, unordered means of opening the door.
- **G11 -> AT9, AT10, AT11 \[OR\] (parallel)**
  - Justification: "the dish retrieve can occur unassisted, with the cooperation of two robots or with the cooperation of robots and a human" lists three unordered alternative execution modes.
