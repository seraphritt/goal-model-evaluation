# Mission Analysis: Hospital Meal-Delivery & Dish-Retrieval Multi-Robot System

## Step-by-Step Reasoning

**1. Identifying the high-level intentions.**
The description contains two macro-processes that the robot fleet must support: (a) **delivering food** from the kitchen to a patient's room, and (b) **retrieving dirty dishes** from the room afterward. Both are explicitly described, both require robot action, and the text itself orders them (food is delivered and eaten before dishes become "dirty" and need retrieval). I therefore model a single root goal that AND-decomposes into these two processes, with a **sequential** runtime (dish pickup logically cannot precede delivery).

**2. Delivery has two explicit, mutually exclusive mechanisms.**
"The food can be delivered into a room table by the robot ... **or** the food can be fetched from the robot's tray." This is an explicit OR particle → OR-decomposition. No order of preference is stated between the two, so I avoid FALLBACK (which requires an explicit stated order) and instead use the "no-ordering-constraint" parallel operator `#`.

**3. Table delivery is a simple Perform goal.**
It is a single concrete manipulation action ("requires a special manipulation robot skill") with no further conditionality — this matches the "Enter the Car" Perform-goal pattern.

**4. Tray delivery is a composite Achieve goal requiring a prior Query.**
The text explicitly separates *information gathering* ("obtained based on the inpatient record ... and the presence of a companion") from *action* (the actual retrieval). This is a textbook **Query Goal** (uncertain, world-information-oriented) feeding an **Achieve Goal** (the retrieval itself). I modeled the two information sources (record vs. companion presence) as an AND because the text uses "according to information about the patient **and** the presence of a companion."

**5. Who retrieves from the tray.**
The text lists "inpatient, a companion, a nurse, **or** another robot" as OR alternatives. To avoid goal duplication (same underlying intention: "a human helps retrieve the meal"), I collapsed inpatient/companion/nurse into **one** goal (they produce identical robot behavior: indicate + present), and kept "another robot" as a distinct alternative because it changes the **Number-of-Robots** task attribute (2 robots vs. 1 robot+human) — a materially different operational intention, so it is *not* redundant.

**6. Indicate / Track / Alert.**
These three behaviors are explicitly scoped to the tray/person-retrieval branch ("in the case of a person retrieving the meal... It should track... The robot should alert..."), motivated by the robot carrying multiple meals at once. I placed "indicate" inside the human-helper sub-goal (it must happen before presenting the tray — sequential, logically necessary) and kept "track" and "alert" as siblings at the tray-delivery level, run in parallel since both are independent monitoring behaviors with no stated order.

**7. Dish retrieval has three explicit OR modes** ("unassisted, with the cooperation of two robots, or with the cooperation of robots and a human") — a clean three-way OR, nested per the binary-operator rule.

**8. Door opening is explicitly tied to the dish-pickup call scenario** ("Someone in the room can call a robot to pick up the dishes. In that case, that person can signal if they can open the door..."). I did not extend door-opening to the delivery branch since the text never mentions it there — extending it would be an unsupported assumption. The "signal" is a Query Goal (mirrors the tray-capability pattern), feeding an OR between robot-cooperation and human-cooperation opening.

**9. Zero-robot exclusion.** Every leaf task keeps at least one delivering/assisting robot in the loop (even the "human cooperation" branches, since the robot still approaches, requests, and detects/coordinates) — no purely human-only goal was added to the tree.

## Logical Relationships

- **G1 -> G2, G12 [AND] (sequential: G2;G12)**
  - **Justification**: Delivery and dish retrieval are two distinct, explicitly required functions of the meal service; dishes only become "dirty" (retrievable) after the meal has been delivered, so delivery must precede retrieval.

- **G2 -> G3, G4 [AND] (sequential: G3;G4)**
  - **Justification**: The meal must physically reach the room (transport) before it can be handed to the inpatient (delivery mechanism); both steps are explicitly necessary for an order to be fulfilled.

- **G3 -> AT1, AT2 [AND] (sequential: AT1;AT2)**
  - **Justification**: The robot must load the meal(s) at the kitchen before it can navigate to the room; this order is physically required and the two are distinct operational steps.

- **G4 -> G5, G6 [OR] (parallel/no-order: G5#G6)**
  - **Justification**: Explicit "or" in the text: "delivered into a room table by the robot... or ... fetched from the robot's tray." No order of preference between the two mechanisms is stated, so no fallback or sequence is imposed.

- **G6 -> G7, G8, G10, G11 [AND] (G7;(G8;(G10#G11)))**
  - **Justification**: All four behaviors (determine capability, achieve retrieval, log retrieval, watch for errors) are described as jointly required for a correct tray delivery. The capability must be known before retrieval is attempted (sequential), while tracking and alerting are independent monitoring activities with no stated order (parallel).

- **G7 -> AT4, AT5 [AND] (parallel: AT4#AT5)**
  - **Justification**: The text explicitly conjoins the two information sources: "based on the inpatient record... **and** the presence of a companion"; both are needed and neither is stated to precede the other.

- **G8 -> G9, AT8 [OR] (parallel/no-order: G9#AT8)**
  - **Justification**: Explicit alternation between human help (inpatient/companion/nurse — consolidated into one goal since they share the same underlying intention) and robot-robot cooperation ("another robot"), kept separate because they differ in required robot count.

- **G9 -> AT6, AT7 [AND] (sequential: AT6;AT7)**
  - **Justification**: The robot must indicate which meal belongs to the inpatient before presenting the tray for retrieval — the text states the indication requirement first, and it is logically required (the helper must know which meal to take before taking it).

- **G10 -> AT9 [AND]**
  - **Justification**: Single, atomic logging action fully realizes this goal ("track when and where each meal was retrieved").

- **G11 -> AT10 [AND]**
  - **Justification**: Single, atomic alerting action fully realizes this goal ("alert if a wrong meal is retrieved").

- **G12 -> G13, G16 [AND] (sequential: G13;G16)**
  - **Justification**: The door must be open before dishes can be collected from the room; both are explicitly necessary components of dish retrieval.

- **G13 -> G14, G15 [AND] (sequential: G14;G15)**
  - **Justification**: The availability signal must be known before deciding how to open the door (robot cooperation vs. human cooperation), mirroring the capability-then-action pattern used for tray retrieval.

- **G15 -> AT12, AT13 [OR] (parallel/no-order: AT12#AT13)**
  - **Justification**: Explicit "or": "cooperation with another robot or a human," with no stated priority between the two.

- **G16 -> AT14, AT15, AT16 [OR] (nested parallel/no-order: AT14#(AT15#AT16))**
  - **Justification**: Explicit three-way "or": "unassisted, with the cooperation of two robots, or with the cooperation of robots and a human," none prioritized over another.
