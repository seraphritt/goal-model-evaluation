# Hospital Meal Delivery & Dish Collection — Multi-Robot Goal Model

Oct 17, 2026

## Reasoning and design decisions

The description covers two largely independent robot responsibilities — delivering meals and collecting dirty dishes — so the root (G1) splits into G2 and G14 as an AND (both are mandatory system responsibilities) with a **parallel** runtime: nothing in the text orders one before the other, and different orders/rooms are served concurrently.

1. **Two symmetric pipelines.** Both G2 and G14 follow the same shape: receive a trigger (kitchen order / room call) → travel to the room → handle an access step (handoff method / door opening) → do the physical work (handoff or collection). Each step is a precondition for the next — you cannot hand off food before arriving, cannot collect dishes before the door is open — so these chains use **sequential** runtime. No IF/exception language appears at this level, so FALLBACK was not used; FALLBACK is reserved for an explicit "try X, and if it fails do Y" which the description never states for these steps.
2. **Query goals isolate uncertain or external information.** Four pieces of information must be fetched rather than acted on: the kitchen order content (G3), the capability/availability of the inpatient, companion or nurse to retrieve from the tray (G7 — explicitly flagged in the text as "subject to uncertainty"), a dish-pickup call (G15), and the occupant's door-opening signal (G17). Each became a Query goal with its own queried property, always placed immediately before the goal that depends on its answer (sequential).
3. **Explicit "or" → OR decomposition.** Three places in the text alternate explicitly: delivery method ("table ... or ... tray"), door opening ("another robot or a human"), and dish collection ("unassisted, with ... two robots, or with ... robots and a human"). Each became an OR-decomposed Achieve goal (G4, G18, G21) over Perform-type leaf alternatives. No priority order between the alternatives is stated, so these use a parallel/no-fixed-order runtime rather than FALLBACK.
4. **Collapsing the four tray-fetch cooperators avoids redundancy and zero-robot nodes.** The text lists four possible cooperators for tray retrieval (inpatient, companion, nurse, another robot). From the robot's perspective the first three are functionally identical — the robot performs the same actions (indicate the meal, present the tray) regardless of which human receives the food. Modelling "inpatient retrieves," "companion retrieves," and "nurse retrieves" as three separate goals would duplicate one underlying intention (violating the no-redundancy rule) and would describe an action with zero robot participation on the human's side (excluded by the zero-robot rule). Only "another robot" changes what the delivery robot must actually do (coordinate a second robot), so exactly two alternatives are kept: Human-Assisted Tray Retrieval (G9) vs. Robot-Assisted Tray Retrieval (G10). The same logic applies to door opening (human vs. second robot). Dish collection keeps all three options from the text (unassisted / two robots / robot+human) because those three are already robot-count-distinct, matching the text's own three-way enumeration.
5. **Goal typing applied consistently.** Query is used only for information gathering (G3, G7, G15, G17). Achieve is used for composite goals that combine several actions or an information need into one verifiable end-state, typically sitting above an OR of alternative methods or an AND that includes a query (G1, G2, G4, G6, G8, G11, G12, G14, G16, G18, G21). Perform is used for the concrete, directly executable manipulation, coordination or signalling actions where success simply means the action was carried out (G5, G9, G10, G13, G19, G20, G22, G23, G24) — mirroring the worked examples, where "Enter the Car" (a direct action) is Perform and "Check Room Patients" (a verifiable, composite end-state) is Achieve.
6. **"Indicate which meal" and "monitor retrieval" are cross-cutting, not alternative-specific.** "The robot can carry multiple meals ... indicate which meal should be retrieved" is scoped by the text to the person-retrieval case only, so it sits inside Human-Assisted Tray Retrieval (G9), AND with "present tray," in parallel (nothing says one must precede the other). "Track when/where retrieved" and "alert if wrong meal" apply to meal retrieval in general, not to one delivery method, so they sit as a sibling AND-branch of the whole handoff (G11), after the handoff in the G2 sequence.
7. **Locations and robot counts come only from the text.** "Kitchen," "room," the room's "table," and the room "door" are the only locations named, so every task uses one or both of them. Robot counts follow explicit numbers where given ("two robots" → 2; "another robot" → 2 total) and default to 1 where the text describes a single robot acting, optionally alongside a human, who is not a robot and is not counted.
8. **Numbering.** Goals (G1–G24) and Tasks (AT1–AT17) are numbered in strict depth-first pre-order, following the order children are listed in each decomposition in the sections below.

## Logical relationships

- **G1 -> G2, G14 \[AND\] (parallel): G2#G14**
  - **Justification**: Meal delivery and dish collection are both mandatory system responsibilities named in the mission; the text gives no order between them, and different orders/rooms are served concurrently.
- **G2 -> G3, AT2, G4, G11 \[AND\] (sequential): G3;(AT2;(G4;G11))**
  - **Justification**: Knowing the order, travelling, handing off, and monitoring are all jointly required to complete a delivery; each is a physical/logical precondition of the next (know destination before travelling, arrive before handing off, hand off before monitoring retrieval).
- **G3 -> AT1 \[AND\]**
  - **Justification**: The query goal is fully operationalized by one concrete task (receiving the order).
- **G4 -> G5, G6 \[OR\] (parallel): G5#G6**
  - **Justification**: Explicit "or" in the text ("delivered into a room table...or...fetched from the robot's tray"); no priority order is stated between the two methods.
- **G5 -> AT3 \[AND\]**
  - **Justification**: The goal is fully operationalized by the one manipulation task.
- **G6 -> G7, G8 \[AND\] (sequential): G7;G8**
  - **Justification**: The robot must determine who can retrieve the meal (G7) before the retrieval can be executed by the right agent (G8); both are required and ordered.
- **G7 -> AT4 \[AND\]**
  - **Justification**: The query is operationalized by one task (checking the record and sensing companion presence).
- **G8 -> G9, G10 \[OR\] (parallel): G9#G10**
  - **Justification**: The text's four possible cooperators for tray retrieval are collapsed (to avoid redundancy and zero-robot nodes) into the only two distinctions that change the robot's behaviour: human cooperation vs. robot cooperation; no priority is stated.
- **G9 -> AT5, AT6 \[AND\] (parallel): AT5#AT6**
  - **Justification**: Indicating which meal and presenting the tray are both necessary for a correct human-assisted retrieval; the text does not state that one must strictly precede the other.
- **G10 -> AT7 \[AND\]**
  - **Justification**: The goal is fully operationalized by the one robot-to-robot coordination task.
- **G11 -> G12, G13 \[AND\] (parallel): G12#G13**
  - **Justification**: Tracking retrieval and alerting on a wrong meal are two distinct, independently triggered monitoring duties mentioned together with no stated order.
- **G12 -> AT8 \[AND\]**
  - **Justification**: The goal is fully operationalized by one logging task.
- **G13 -> AT9 \[AND\]**
  - **Justification**: The goal is fully operationalized by one alert task.
- **G14 -> G15, AT11, G16, G21 \[AND\] (sequential): G15;(AT11;(G16;G21))**
  - **Justification**: Symmetric with G2 — receiving the pickup call, navigating, opening the door, and collecting dishes are all jointly required, each a precondition of the next.
- **G15 -> AT10 \[AND\]**
  - **Justification**: The query is operationalized by one task (receiving the room's call).
- **G16 -> G17, G18 \[AND\] (sequential): G17;G18**
  - **Justification**: The occupant's door-opening signal must be known (G17) before the appropriate opening method is executed (G18) — the text ties the signal to "when the robot comes to it," i.e., on arrival, before opening.
- **G17 -> AT12 \[AND\]**
  - **Justification**: The query is operationalized by one task (checking the signal at the door).
- **G18 -> G19, G20 \[OR\] (parallel): G19#G20**
  - **Justification**: Explicit "or" ("cooperation with another robot or a human"); no priority order stated.
- **G19 -> AT13 \[AND\]**
  - **Justification**: The goal is fully operationalized by one request/wait task.
- **G20 -> AT14 \[AND\]**
