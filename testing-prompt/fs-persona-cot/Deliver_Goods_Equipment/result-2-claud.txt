# Multi-Robot Resource Collection & Delivery – Goal Model

Oct 21, 2026 · @Isaque

## Step-by-step analysis

1. **Two phases, one dependency.** The mission names exactly two operational phases — collection and delivery — and states explicitly that "once retrieved, the delivery phase begins," so delivery depends on collection finishing first. That is a sequential relation, not a parallel or alternative one, so the root goal is an AND of Collect Required Resources and Deliver Resources, in that order.
2. **Two explicit IF-conditions become FALLBACK — nothing else does.** The description gives two battery thresholds, 10% in collection and 30% in delivery, each with its own named contingency. An explicit condition with a stated primary behavior and a stated alternative behavior is exactly what the FALLBACK rule calls for. Every other juncture (determining order, requesting and waiting, making delivery runs) is a plain, unconditional step, modeled as AND with sequential or parallel runtime instead.
3. **A third IF-condition nests one level deeper.** "In case of failure to return the resource to a checkpoint" is itself a condition on the primary action inside the delivery battery contingency, so it becomes a second, nested FALLBACK: attempt the return, and only trigger the alert and report if that attempt does not succeed.
4. **Ordering follows the text's own words.** Conjunctions with no explicit first/second marker ("an alert must be triggered and the report sent") are modeled as AND with parallel runtime. Conjunctions whose word order implies a necessary before/after ("goes back ... and assigns"; "must return ... and assign the remaining task ... which will know where the resource is positioned") are modeled as AND with sequential runtime.
5. **No OR decomposition appears anywhere.** OR requires genuine interchangeable alternatives — fulfilling either one is enough. The mission never offers that; every decomposition found is either a strict joint requirement (AND) or a conditioned primary/backup pair (FALLBACK, itself AND by definition). The full tree therefore uses AND exclusively.
6. **Every leaf traces to a robot action.** Travel, send a message, wait, make a run, trigger an alert, assign a mission — each task is an explicit action attributed to "the robot" in the text, so no branch had to be dropped for performing zero robots.
7. **Parallel multi-robot scaling is a task property, not a new goal.** "Multiple robots can be assigned to parallel collect-deliver tasks" describes several concurrent copies of the same Collect-and-Deliver mission (one robot per item/storage), not a new intention. Duplicating the root goal for this would break the no-redundancy rule, so it is captured instead as a note on the collection/delivery tasks: each task instance still takes 1 robot, and parallelism comes from running several instances of the whole tree at once.
8. **The two examples are instances, not goals.** Sterile medical equipment and clean linens illustrate what "required resources" can be; they introduce no intention beyond Collect/Deliver, so they appear as illustrations in the task justifications rather than as separate nodes.
9. **Goal-type pattern.** Achieve models every goal with a concrete target state to reach through planning (the two phases and their normal-path attempts). Query models the one step that only gathers information rather than acting on the world (the visiting-order estimate). Perform models the three contingency-action goals (battery/collection handoff, battery/delivery handoff, alert-and-report): each executes a fixed, triggered set of actions rather than pursuing an open-ended state.

## Logical relationships

- **G1 -> G2, G7 \[AND\] (sequential)**
  - *Justification*: collection must finish before delivery starts — "once retrieved, the delivery phase begins" — so both are required (AND) and strictly ordered (sequential), not alternatives or parallel options.
- **G2 -> G3, G6 \[AND\] FALLBACK(G3, G6)**
  - *Justification*: normal collection (G3) is attempted first; the explicit 10% battery threshold with its own named behavior is the alternative branch (G6), only reached if G3 cannot be completed. FALLBACK always implies AND between its two branches.
- **G3 -> G4, G5 \[AND\] (sequential)**
  - *Justification*: the visiting order has to be computed (G4) before the robot can visit storages in that order (G5); both are required and strictly ordered.
- **G4 -> AT1 \[AND\]**
  - *Justification*: a single operational step (estimate and rank) fully realizes this goal; with only one child the relation is trivially AND (necessary and sufficient).
- **G5 -> AT2, AT3, AT4 \[AND\] (sequential)**
  - *Justification*: "go to the storage ... sends a message ... waits until retrieved" names three necessary actions in exactly that order.
- **G6 -> AT5, AT6 \[AND\] (sequential)**
  - *Justification*: "goes back to the recharging station and assigns the mission to another robot" — both actions are required, and the sentence's own word order gives the sequence.
- **G7 -> G8, G9 \[AND\] FALLBACK(G8, G9)**
  - *Justification*: mirrors G2/G6 — normal delivery (G8) is attempted first, and the explicit 30% battery threshold defines the alternative (G9).
- **G8 -> AT7, AT8 \[AND\] (sequential)**
  - *Justification*: the robot must arrive at the specified location before it can hand the resource to the requesting agent.
- **G9 -> G10, AT12 \[AND\] (sequential)**
  - *Justification*: "must return the resource to a checkpoint and assign the remaining task to another robot, which will know where the resource is positioned" — the reassignment only makes sense once the return (or its failure-handling) has happened, so G10 precedes AT12.
- **G10 -> AT9, G11 \[AND\] FALLBACK(AT9, G11)**
  - *Justification*: "in case of failure to return the resource to a checkpoint" is a second, nested IF-condition — the robot attempts the return (AT9) first, and only triggers the alert-and-report branch (G11) if that attempt fails.
- **G11 -> AT10, AT11 \[AND\] (parallel)**
  - *Justification*: "an alert must be triggered and the report sent" — both are required, joined by "and" with no stated order between them, so they are modeled as able to proceed in parallel rather than forced into a sequence the text never specifies.

No OR decomposition appears anywhere in the model: OR requires genuine interchangeable alternatives (fulfilling either child is enough), and the mission never offers one — every branch point is either a strict joint requirement or a conditioned primary/backup pair, both of which are AND.
