# Goal Model Design – Robot Resource Collection & Delivery Mission

## Step-by-step reasoning

**Step 1 — Identify the top-level intention.**
The description opens with a single standing intention: *"a robot must collect the required resources in the storage and deliver them to the requesting agent in a specified location."* This is the mission's root goal. It has a clear target state (resources delivered), it requires planning and multi-step action, and it is not a single atomic action nor a pure information query → **Achieve**.

**Step 2 — Split into phases.**
The text explicitly separates two phases and states their order: *"Once retrieved, the delivery phase begins."* This explicit ordering word ("once… begins") is a clear signal for a **sequential** runtime annotation (not parallel, not fallback — there is no IF/exception framing here, just a stated temporal order). Both phases are mandatory and complementary → **AND**.

**Step 3 — Decompose the Collection phase.**
Inside collection, three distinct activities appear:
- Computing *which order* to visit storages ("defined by the estimation of waiting time summed up with the path") — this is information-gathering, not world-changing → **Query** goal.
- The "normal" visiting behavior (reach storage → request → wait) — explicitly ordered ("once… reaches… and it is time to request… sends a message… and waits"), so **sequential**.
- The battery-low exception — explicitly introduced with "If the battery… runs low," which is the textbook trigger word for **FALLBACK**: normal collection is attempted, and the battery procedure is the alternative path, not a parallel/independent activity.

Per the rules, exp1/exp2 inside a FALLBACK are always AND-related, and I keep that convention consistently.

**Step 4 — Decompose the Delivery phase.**
Similarly: normal delivery (repeated runs) vs. the explicit "If the battery… runs low (30%)" exception → another **FALLBACK**. Inside that exception, two further explicit conditionals appear nested:
- Returning the resource to a checkpoint vs. "In case of failure to return the resource to a checkpoint" (alert + report) → a **nested FALLBACK**.
- Reassigning the remaining task is stated with a plain "and" (no ordering word) relative to the checkpoint action → **parallel**, not sequential, since the text gives no explicit precedence.

**Step 5 — Check minimality/redundancy rules.**
- The two examples (sterile medical equipment, clean linens) are illustrative instances of "resources," not distinct behaviors — adding separate goals for them would duplicate the same intention (collect-and-deliver) covered by G1, so I deliberately excluded them as nodes (avoiding redundancy, per the instructions).
- Every goal/task above is actually executed by a robot — no zero-robot nodes were introduced (e.g., "sector manager" never gets its own goal; it only appears as the target of a robot-performed task).
- No true alternative ("either…or") exists anywhere in the text, so **no OR-decomposition occurs** in this mission — every decomposition is AND, including the FALLBACK ones (as mandated by the definitions).

**Step 6 — The multi-robot parallel clause.**
*"When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks…"* This describes **multiple full instances of G1** running concurrently (one robot per item/storage), not a single task that needs several robots cooperating simultaneously. I therefore did **not** inflate individual task's "Number of Robots" into ranges — doing so would conflate "N parallel single-robot missions" with "a task that literally requires a team of robots," which the text never states. Instead, every task keeps **Number of Robots = 1**, and I flag this mission-level parallelism explicitly in the notes below the tables.

## Compact specification

```
G1: Collect requested resources and deliver them to the requesting agent at the specified location.      G2;G5
G2: Retrieve all required resources from the storage(s).                                                  G3;FALLBACK((AT3;AT4;AT5),G4)
G3: Determine the storage visiting order from waiting-time and path estimates.                             AT1#AT2
G4: Handle low battery (≤10%) during the collection phase.                                                 AT6#AT7
G5: Deliver all collected resources to the specified location.                                             FALLBACK(AT8,G6)
G6: Handle low battery (≤30%) during the delivery phase.                                                   FALLBACK(AT9,G7)#AT12
G7: Handle checkpoint-return failure.                                                                       AT10#AT11

AT1:  Estimate storage waiting time.                           -
AT2:  Estimate travel path time to storage.                    -
AT3:  Travel to storage.                                       -
AT4:  Request resources from storage.                          -
AT5:  Wait for resource retrieval.                              -
AT6:  Return to recharging station.                            -
AT7:  Assign collection mission to another robot.               -
AT8:  Transport resources to delivery location (repeated runs). -
AT9:  Return resource to checkpoint.                            -
AT10: Trigger alert.                                            -
AT11: Send report to sector manager.                            -
AT12: Assign remaining delivery task to another robot.          -
```

## Logical Relationships

- **G1 -> G2, G5 [AND] (sequential)**
  - **Justification**: Collection and delivery are both mandatory and non-interchangeable (AND). The text explicitly states "Once retrieved, the delivery phase begins," which fixes the order — hence sequential, not parallel or fallback.

- **G2 -> G3, AT3, AT4, AT5, G4 [AND] (`G3;FALLBACK((AT3;AT4;AT5),G4)`)**
  - **Justification**: Determining the order must happen before visiting storages (sequential, implied by "the order to be followed is defined by…"). Within the visiting block, reaching the storage, requesting, and waiting are explicitly ordered ("once… reaches… sends… waits"). The battery-low procedure is explicitly introduced as a conditional exception ("If the battery… runs low"), which is the defining case for FALLBACK. Per the rules, FALLBACK forces AND between its branches, and all elements are jointly necessary for the phase, so the whole decomposition is AND.

- **G3 -> AT1, AT2 [AND] (parallel)**
  - **Justification**: Waiting-time and path estimates are both explicitly required ("waiting time summed up with the path") — complementary, not alternative (AND). Nothing in the text orders one estimate before the other, so they are modeled as parallel.

- **G4 -> AT6, AT7 [AND] (parallel)**
  - **Justification**: "Goes back to the recharging station **and** assigns the mission to another robot" — both actions are required (AND). No explicit sequencing word ("then," "once," "after") links them, so parallel is used rather than inventing an order.

- **G5 -> AT8, G6 [AND] (`FALLBACK(AT8,G6)`)**
  - **Justification**: Normal delivery (repeated runs) is the default behavior; the battery-low condition ("If the battery… runs low (30%)…") is an explicit IF-triggered exception — the canonical FALLBACK pattern. FALLBACK mandates an AND relation between the two branches.

- **G6 -> AT9, G7, AT12 [AND] (`FALLBACK(AT9,G7)#AT12`)**
  - **Justification**: Returning the resource to the checkpoint is the default action, and "in case of failure to return the resource to a checkpoint" is an explicit conditional exception → nested FALLBACK(AT9, G7). Reassigning the remaining task is additionally required ("and assign the remaining task"), stated without an ordering word relative to the checkpoint outcome, so it runs in parallel with the fallback block. All three are jointly necessary → AND.

- **G7 -> AT10, AT11 [AND] (parallel)**
  - **Justification**: "An alert must be triggered **and** the report sent to the sector manager" — both are required (AND), with no stated order between them, hence parallel.

## Modeling notes worth flagging

1. **No OR-decomposition appears anywhere** in this mission: every branching point in the text is either a joint requirement (AND) or a condition/exception (FALLBACK, which the given definitions also treat as AND-based), never a genuine "either/or" alternative. This is a property of this specific description, not a shortcut on my part.
2. **The two resource examples (sterile medical equipment, clean linens) were intentionally left out of the model.** They are illustrative instances of "resources," not separate behaviors — representing them as extra goals would duplicate the intention already captured by G1–G7 (avoiding redundancy, per the instructions).
3. **Mission-level parallelism vs. task-level robot count.** The clause "multiple robots can be assigned to parallel collect-deliver tasks" describes several independent instances of the whole G1 tree running concurrently (one robot per required item/storage), not a single task needing a team of robots. I therefore kept every task's "Number of Robots" at 1 rather than encoding this as a `[1,n]` range on individual tasks, which would have implied robots cooperating on one task instance — something the text never states. If you'd prefer the model to explicitly show this multiplicity (e.g., an outer "Mission Coordinator" goal that fans out multiple G1 instances, one per storage/item), I can add that layer — just let me know.
