# Goal Model Analysis — Multi-Robot Collect & Deliver Mission

## Step-by-step reasoning

Before building the tables, here is how I decomposed the description:

**1. Identify the top-level intention.**
The mission is triggered "when required": a robot collects resources from storage and delivers them to a requesting agent at a specified location. This is a single, non-duplicated intention → root goal **G1**. It is an *Achieve* goal because the description cares about a final world-state (resources actually delivered), not merely that some action was attempted.

**2. Identify the two macro-phases.**
The text explicitly separates "the collection phase" and "the delivery phase," and states "*Once retrieved, the delivery phase begins*" — an explicit ordering cue. This is a **sequential** runtime relation (not fallback, since there is no failure/condition triggering the switch — it's the normal, unconditional flow), and an **AND** decomposition (both phases are mandatory).

**3. Detect FALLBACK patterns.**
Two "if battery is low → alternative behavior" statements are textbook fallback triggers (explicit condition + alternative path):
- Collection: normal collection vs. (battery ≤10%) return‑and‑reassign.
- Delivery: normal delivery vs. (battery ≤30%) return‑to‑checkpoint‑and‑reassign.
A third, nested fallback appears inside the delivery contingency: "*In case of failure to return the resource to a checkpoint*" → alert/report. Per the rules, every FALLBACK pair is connected by **AND** (not OR), since both branches are part of one jointly-required contingency logic.

**4. Detect parallel vs. sequential micro-steps.**
- "Sends a message… **and** waits until… retrieved" after "goes to the storage" → the description gives an explicit order (go → request → wait), so these are **sequential**.
- "Goes back to the recharging station **and** assigns the mission to another robot" and "an alert must be triggered **and** the report sent" → no explicit ordering word is used (no "then", no "once X, Y"), so per the rule ("fallback/strict order only when explicit") I treated these as **parallel** (possible, not obligatory, simultaneity) rather than inventing an order.
- "Return the resource to a checkpoint **and** assign the remaining task" → here the second action logically and textually depends on the first having happened (the new robot must know where the resource *is*, i.e., already positioned), so this one I treated as **sequential**, not parallel.

**5. Query goal detection.**
"The order to be followed is defined by the estimation of waiting time summed up with the path to be run" describes retrieving/computing information to make a decision, not performing a world-changing action — a textbook **Query** goal.

**6. Avoiding redundancy / the "multiple robots in parallel" clause.**
"*When multiple items are required from different storages, multiple robots can be assigned to parallel collect-deliver tasks*" does **not** describe a new intention — it describes multiplicity of execution of the *same* collect-deliver goal. Duplicating the whole subtree per storage would violate the "no duplicated intention" rule. Instead, I captured this by giving the core tasks (navigate, request, wait, transport) a **Number of Robots = [1, n]**, where *n* is a variable bound by how many storages/items are concurrently required — this is exactly what the task-attribute specification is designed for.

**7. Zero-robot check.**
Every leaf task above is explicitly tied to the robot performing it (the assigned robot or its successor). I did not create any node for "the system" or "the requesting agent" in isolation, since those aren't robots and would violate the zero-robot exclusion rule.

**8. Location discipline.**
I only used locations explicitly named in the text: *storage*, *specified location*, *recharging station*, *checkpoint*. For the alert/report tasks, no distinct "failure location" is named, so I anchored them to *checkpoint* as the nearest cited contextual location (the failure is defined relative to reaching the checkpoint), and flagged this inference explicitly in the justification rather than inventing a new location.

## Logical Relationships

- **G1 -> G2, G6 [AND] (sequential)**
  - **Justification**: Both the collection phase and the delivery phase are mandatory to fulfill the mission (AND). The description states delivery starts "once retrieved," an explicit sequential cue — collection must finish before delivery starts.

- **G2 -> G3, G5 [AND] FALLBACK(G3, G5)**
  - **Justification**: Normal collection (G3) is attempted first; the low-battery procedure (G5) is only triggered by the explicit condition "if the battery…runs low (10%)." This is a textbook fallback, and fallback relations are mandated to be AND.

- **G3 -> G4, AT1, AT2, AT3 [AND] (sequential)**
  - **Justification**: All four steps are required (AND). The text lays out an explicit chronological chain: determine order → travel → request → wait, hence sequential (same operator throughout, no parentheses needed).

- **G5 -> AT4, AT5 [AND] (parallel)**
  - **Justification**: Both actions ("goes back to the recharging station **and** assigns the mission to another robot") are required (AND), but joined only by "and" with no explicit sequencing language, so they are modeled as possible-parallel rather than forced sequential.

- **G6 -> AT6, G7 [AND] FALLBACK(AT6, G7)**
  - **Justification**: Normal delivery (AT6, "the robot will make as many runs as necessary") is the default path; the checkpoint contingency (G7) is triggered only by the explicit condition "if the battery…runs low (30%)" — an explicit fallback, hence AND.

- **G7 -> G8, G9 [AND] FALLBACK(G8, G9)**
  - **Justification**: Returning the resource and reassigning (G8) is attempted first; the alert/report escalation (G9) is explicitly conditioned on failure ("in case of failure to return the resource to a checkpoint"). This is a nested fallback, mandated AND.

- **G8 -> AT7, AT8 [AND] (sequential)**
  - **Justification**: Both actions are required (AND). Reassignment textually depends on the resource already being positioned ("another robot, which will know where the resource is positioned"), so returning the resource must precede reassigning the task — sequential.

- **G9 -> AT9, AT10 [AND] (parallel)**
  - **Justification**: Both the alert and the report are required (AND) ("an alert must be triggered and the report sent"), joined only by "and" with no explicit order, so modeled as possible-parallel.
