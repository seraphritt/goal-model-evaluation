# Mission Decomposition — Hospital Vital-Signs Check (Multi-Robot System)

## 1. Step-by-step reasoning

Before building the tree, I extracted the mission's **operational primitives** (what a robot actually does), its **decision points** (checks that branch the flow), its **failure-recovery patterns** (explicit fallbacks), and its **conditional/parallel work** (vitals that depend on patient condition, independent checks).

**a) Top-level structure.** The mission has two concerns that run concurrently: (1) the functional loop of visiting rooms and checking patients, and (2) the non-functional guarantee that the mission stays feasible in time (adding robots, escalating to the manager). Since feasibility management ("additional robots... if impossible... alert the manager") is monitored *throughout* the visiting process rather than happening strictly after it, I modeled these as **parallel (`#`) AND-siblings** of the root.

**b) Why FALLBACK appears where it does.** The brief is explicit about "if this condition occurs, do this other thing instead" in exactly four places: (i) patient unavailable → come back in 5 min, (ii) insufficient battery → recharge & reassign, (iii) failed vital collection → ask questions → (iv) no response to questions → alert nurse/doctor. These are textbook FALLBACK cases (normal attempt, then an alternative triggered by failure), including one **nested** fallback (collect → ask → alert) that mirrors the worked example in the instructions almost exactly. I did **not** use FALLBACK for things that are just conditional follow-ups without a "try X, else Y" structure (e.g., sterilizing after leaving an infectious room, disinfecting actuators after contact) — these are mandatory sequential steps conditioned on a patient attribute, not alternatives to a failed attempt, so I modeled them as sequential AND-steps instead, per the instructions' restriction that fallback requires an explicit order between a primary attempt and a failure-triggered alternative.

**c) Sequential vs. parallel decisions.** Wherever the text gives an explicit order via narrative or connecting words ("approach... announce... provide instructions", "mark it as done and proceed", "recharge... and reassign" when one logically must follow intake of failure), I used sequential (`;`). Wherever the text lists requirements with a plain "and" and gives no ordering cue (the two pre-entry checks; the four infectious-disease vitals; the two post-surgical vitals), I used parallel (`#`), since the definition states parallel only expresses a *possibility*, not an obligation, of concurrent execution.

**d) OR usage.** OR decomposition was reserved for genuine alternatives: identifying the patient ("either by asking or by scanning") and the condition-dependent vital-sign set (a patient may qualify for one, several, or all of infectious/post-surgical/diabetic checklists, so fulfilling the relevant subset is sufficient).

**e) Avoiding redundancy.** "Measure heart rate" and "measure blood oxygenation" are required under both the infectious-disease and post-surgical profiles. Rather than creating two separate condition-specific goals that would each contain a duplicate "Measure Heart Rate" task (same intention, same action), I factored all five distinct measurements (heart rate, blood pressure, body temperature, blood oxygenation, glucose) into a single OR-decomposed goal, and documented in the justification which subset applies to which condition. This keeps each distinct intention as exactly one node, as required.

**f) Goal typing.**
- **Query** goals are used only where the sole purpose is retrieving information with no world-changing action: fetching occupied rooms/risk levels, and identifying which patient is present.
- **Achieve** goals are used everywhere a target state must be brought about through planning/action (patient available, battery sufficient, vitals collected, room finalized, mission feasible).
- **No Perform goals were needed.** Every atomic, state-less action in the mission (enter room, approach patient, measure a vital, alert someone) is operational and bears a Location/Number-of-Robots — i.e., it fits the **Task** definition, not an intentional non-operational goal. All intentional nodes above the task layer have a clear target condition or queried property, so they classify as Achieve/Query rather than Perform.

**g) Zero-robot exclusion.** The two-hour recurrence itself and the fact that "rooms may have one or more beds" are *context/triggers*, not robot-executed actions, so they are **not** modeled as nodes — they appear only as justification/target-condition text.

## 2. Goal tree overview

```
G1 Ensure All Patients' Vital Signs Are Checked [AND, G2 # G15]
├─ G2 Visit All Occupied Rooms [AND, G3 ; G4]
│  ├─ G3 Determine Room Visit Order [AND, AT1 # AT2] (Query)
│  │  ├─ AT1 Fetch Occupied Rooms
│  │  └─ AT2 Identify High-Risk Patients
│  └─ G4 Check Room Patients [AND, G5 ; G9 ; AT10 ; G10 ; G14]
│     ├─ G5 Perform Pre-Entry Checks [AND, G6 # G7]
│     │  ├─ G6 Ensure Patient Availability [AND, FALLBACK(AT3, AT4)]
│     │  │  ├─ AT3 Check Patient Availability
│     │  │  └─ AT4 Reschedule Visit (Wait 5 Minutes)
│     │  └─ G7 Ensure Sufficient Battery [AND, FALLBACK(AT5, G8)]
│     │     ├─ AT5 Check Battery Level
│     │     └─ G8 Handle Low Battery [AND, AT6 # AT7]
│     │        ├─ AT6 Recharge Robot
│     │        └─ AT7 Reassign Pending Tasks
│     ├─ G9 Identify Correct Patient [OR, AT8 # AT9] (Query)
│     │  ├─ AT8 Ask Patient Identity
│     │  └─ AT9 Scan Patient Barcode
│     ├─ AT10 Enter Room
│     ├─ G10 Conduct Patient Interaction & Vital Collection [AND, AT11 ; AT12 ; AT13 ; G11]
│     │  ├─ AT11 Approach Patient
│     │  ├─ AT12 Announce Procedure
│     │  ├─ AT13 Provide Instructions
│     │  └─ G11 Collect Required Vital Signs [AND, G12 ; AT21]
│     │     ├─ G12 Perform Vital Signs Assessment [AND, FALLBACK(FALLBACK(G13, AT19), AT20)]
│     │     │  ├─ G13 Measure Vital Signs by Condition [OR, AT14 # AT15 # AT16 # AT17 # AT18]
│     │     │  │  ├─ AT14 Measure Heart Rate
│     │     │  │  ├─ AT15 Measure Blood Pressure
│     │     │  │  ├─ AT16 Measure Body Temperature
│     │     │  │  ├─ AT17 Measure Blood Oxygenation
│     │     │  │  └─ AT18 Measure Blood Glucose Level
│     │     │  ├─ AT19 Ask Patient Assessment Questions
│     │     │  └─ AT20 Alert Responsible Nurse/Doctor
│     │     └─ AT21 Disinfect Actuators
│     └─ G14 Finalize Room Visit [AND, AT22 ; AT23 ; AT24]
│        ├─ AT22 Mark Patient as Checked
│        ├─ AT23 Sterilize Robot
│        └─ AT24 Proceed to Next Room
└─ G15 Ensure Mission Feasibility [AND, FALLBACK(AT25, AT26)]
   ├─ AT25 Assign Additional Robots
   └─ AT26 Alert Site Manager
```

## 6. Logical Relationships

- **G1 -> G2, G15 [AND] (parallel)**
  - *Justification*: Both visiting rooms and guaranteeing feasibility are required for mission success, and feasibility management (adding robots, escalating) is monitored concurrently with the visiting process, not strictly after it.

- **G2 -> G3, G4 [AND] (sequential)**
  - *Justification*: The robot must know which rooms are occupied and which patients are high-risk before it can determine the visiting order required by "high-risk patients checked in the first 15 minutes."

- **G3 -> AT1, AT2 [AND] (parallel)**
  - *Justification*: Fetching room occupancy and identifying high-risk patients are independent queries with no stated dependency between them.

- **G4 -> G5, G9, AT10, G10, G14 [AND] (sequential)**
  - *Justification*: The mission description lays out this exact chronology for a room visit — pre-entry checks, patient identification, entry, interaction/vitals, then closing the visit.

- **G5 -> G6, G7 [AND] (parallel)**
  - *Justification*: "check if the patient is available... and if there is enough battery" — a plain conjunction with no ordering cue.

- **G6 -> AT3, AT4 [AND] FALLBACK(AT3, AT4)**
  - *Justification*: Availability check is attempted first; rescheduling is the explicit alternative only on failure ("If the patient is not available...").

- **G7 -> AT5, G8 [AND] FALLBACK(AT5, G8)**
  - *Justification*: Battery check is attempted first; recharge/reassignment is the explicit alternative only on failure ("If there is not enough battery...").

- **G8 -> AT6, AT7 [AND] (parallel)**
  - *Justification*: Recharging the robot and reassigning its tasks to others can proceed independently/concurrently; the text gives no order.

- **G9 -> AT8, AT9 [OR] (parallel)**
  - *Justification*: "either by asking or by scanning" is an explicit alternative; both methods could, in principle, be attempted concurrently, but only one success is required.

- **G10 -> AT11, AT12, AT13, G11 [AND] (sequential)**
  - *Justification*: "approach the patient, announce the procedure..., and provide instructions" is an explicit order, followed by vital-sign collection.

- **G11 -> G12, AT21 [AND] (sequential)**
  - *Justification*: Actuator disinfection is required "afterwards," i.e., only once the contact-involving measurement activity (G12) has taken place.

- **G12 -> G13, AT19, AT20 [AND] FALLBACK(FALLBACK(G13, AT19), AT20)**
  - *Justification*: This is the mission's explicit nested contingency: attempt measurement; on failure, ask questions; on no response to the questions, alert the nurse/doctor.

- **G13 -> AT14, AT15, AT16, AT17, AT18 [OR] (parallel)**
  - *Justification*: Which measurements apply depends on the patient's condition(s) — infectious disease (HR, BP, Temp, SpO2), post-surgical (HR, SpO2), diabetes (glucose) — and a patient may require more than one subset simultaneously, with no required order among the measurements themselves.

- **G14 -> AT22, AT23, AT24 [AND] (sequential)**
  - *Justification*: "mark it as done and proceed to the next room," with sterilization occurring "when a robot comes out of" an infectious-disease room — i.e., between marking done and moving on.

- **G15 -> AT25, AT26 [AND] FALLBACK(AT25, AT26)**
  - *Justification*: Additional robots are assigned first to resolve infeasibility; the manager is alerted only as the last resort, "if no combination of robots can complete the mission."
