# Step-by-Step Reasoning

Before building the tables, here is my decomposition logic, including the harder calls and why I made them.

**1. Finding the root objective.** The mission is ultimately about *time-bounded coverage*: every occupied room must be checked, high-risk patients within 15 minutes, and the whole thing must still succeed even if the default robot team can't keep up (extra robots, then manager alert). Because "additional robots" and "alert the manager" are both explicitly conditioned on failure ("in case of impossibility...", "if no combination of robots can complete the mission"), I treated this as a **nested FALLBACK** at the very top of the tree — this mirrors the worked example `FALLBACK(FALLBACK(exp1,exp2),exp3)` in your spec exactly.

**2. High-risk priority.** "All patients in high risk must be checked in the first 15 minutes" gives an explicit temporal precedence over the rest of the rooms, so I modeled it as **sequential** (high-risk group, then the rest) rather than parallel — the ordering is stated, even though it's a group-level rather than task-level order.

**3. The "before entering the room" block.** Availability-check, battery-check, and patient-identification (for multi-bed rooms) are all described as pre-entry activities joined by "and," with no stated order among them — so these are **parallel** by default (per your rule: parallel is the default when no order is stated; sequential/fallback require an explicit order or an explicit IF).

**4. Two genuine IF-statements before entry.** "If the patient is not available..." and "If there is not enough battery..." are textbook FALLBACK triggers (explicit IF-condition driving an alternate behavior), so each became its own `FALLBACK(check, alternative)` goal, each AND-related per your fallback rule.

**5. Patient identification.** "Either by asking or by scanning the barcode" is a literal "either...or" → **OR**.

**6. Inside the room.** "Approach… announce… provide instructions" is a literal ordered list → **sequential**.

**7. Vital-sign requirements per condition.** Infectious disease (4 signs), post-surgical (2 signs), diabetes history (1 sign) are three independent, possibly co-occurring triggers — not true exclusive alternatives, but also not jointly mandatory for every patient. I used **OR** (fulfilling one branch is sufficient; multiple can apply) rather than AND, since not every patient needs all three branches. Within a branch, the specific signs are joined by "and" → **AND**, **parallel** (no order given).

**8. Reuse, not duplication.** Heart rate and blood-oxygenation measurement are physically the same action whether triggered by "infectious disease" or "post-surgical" rules, so I reused the same two tasks under both condition-branches instead of creating duplicates — this follows your redundancy-avoidance rule extended down to tasks. Similarly, "Check Patient In Room" is a single goal reused by both the high-risk visiting branch and the remaining-rooms branch, rather than being modeled twice.

**9. Vital-sign collection failure.** "Failure of collecting any vital sign → ask questions" then "non-response → alert nurse/doctor" is a second clean nested-FALLBACK pattern, structurally identical to the robot-assignment one at the top.

**10. Conditional hygiene rules.** Sterilization (infectious rooms only) and actuator disinfection (any patient contact) are both conditional, not universal, so sterilization is modeled as an **OR** alternative to a plain exit, while actuator disinfection — since in this mission *all* contact happens during vital-sign measurement — is modeled as an unconditional sequential step after measurement (I flag this assumption explicitly below).

**11. Zero-robot check.** Every leaf task in the model is something a robot (or the fleet-coordination logic, treated as part of the MRS) physically does — scanning, measuring, moving, alerting, sterilizing, recharging. The purely temporal rule ("every two hours") and the purely descriptive fact ("rooms may have one or more beds") are *not* modeled as goals/tasks themselves — they only shape target conditions and the need for patient identification — consistent with the no-zero-robot-nodes rule.

**12. Single-child exceptions.** Two goals (G9 for the diabetic branch, replaced by a direct task, and G20 "Assign Additional Robots") end up with only one child after I removed artificial padding. I flagged these explicitly rather than inventing unstated sub-steps.

A compact view of the tree (IDs assigned in depth-first order, task numbering reset/continued the same way):

```
G1 Ensure All Occupied Rooms Checked In Time
 ├─ G2 Visit Rooms With Current Robot(s)
 │   ├─ G3 Visit High-Risk Rooms First
 │   │   ├─ AT1 Travel to high-risk room
 │   │   └─ G4 Check Patient In Room
 │   │       ├─ G5 Identify Correct Patient (OR: AT2 Ask | AT3 Scan)
 │   │       ├─ G6 Satisfy Entry Preconditions
 │   │       │   ├─ G7 Ensure Availability  FALLBACK(AT4 Check avail., AT5 Return in 5 min)
 │   │       │   └─ G8 Ensure Battery       FALLBACK(AT6 Check battery, G9 Recharge&Reassign[AT7,AT8])
 │   │       ├─ G10 Room Entry Interaction: AT9 Approach ; AT10 Announce ; AT11 Instruct
 │   │       ├─ G11 Collect Required Vital Signs
 │   │       │   ├─ AT12 Query patient condition
 │   │       │   ├─ G12 Obtain Vitals w/ Escalation  FALLBACK(FALLBACK(G13, AT18 Ask questions), AT19 Alert staff)
 │   │       │   │    └─ G13 Measure Automatically (OR: G14 Infectious[AT13,14,15,16] | G15 Post-surgical[AT13,16] | AT17 Glucose)
 │   │       │   └─ AT20 Disinfect actuators
 │   │       └─ G16 Finalize Room: AT21 Mark done ; G17 Exit Room(OR: AT22 Exit | G18 Sterilize&Exit[AT22,AT23]) ; AT24 Proceed next
 │   └─ G19 Visit Remaining Rooms: AT25 Travel ; G4 (reused)
 ├─ G20 Assign Additional Robots → AT26
 └─ AT27 Alert responsible manager
```

# Logical Relationships

- **G1 → G2, G20, AT27 [AND][FALLBACK(FALLBACK(G2,G20),AT27)]**
  - *Justification*: The mission first tries the current robot team (G2); only "in case of impossibility of performing the mission in the required time" does it try additional robots (G20); only if "no combination of robots can complete the mission" is the manager alerted (AT27) — a textbook nested fallback.

- **G2 → G3, G19 [AND](sequential)**
  - *Justification*: Both room groups must be visited; high-risk rooms are given an explicit 15-minute priority window, so they come first.

- **G3 → AT1, G4 [AND](sequential)**
  - *Justification*: A robot must travel to a room before it can check the patient inside it.

- **G4 → G5, G6, G10, G11, G16 [AND][(G5#G6);G10;G11;G16]**
  - *Justification*: Phase order is explicit in the text (pre-entry checks → entry interaction → vital-sign collection → close-out); identification (G5) and precondition-checking (G6) are both "before entering" with no relative order, hence parallel.

- **G5 → AT2, AT3 [OR](parallel)**
  - *Justification*: "either by asking or by scanning" — explicit alternative.

- **G6 → G7, G8 [AND](parallel)**
  - *Justification*: Availability and battery are checked together ("and"), with no stated order.

- **G7 → AT4, AT5 [AND][FALLBACK(AT4,AT5)]**
  - *Justification*: Explicit IF-condition ("If the patient is not available…") triggers the alternative action.

- **G8 → AT6, G9 [AND][FALLBACK(AT6,G9)]**
  - *Justification*: Explicit IF-condition ("If there is not enough battery…") triggers recharge+reassignment.

- **G9 → AT7, AT8 [AND](parallel)**
  - *Justification*: "recharge and the tasks need to be reassigned" — jointly required, no stated order.

- **G10 → AT9, AT10, AT11 [AND](sequential)**
  - *Justification*: "approach…announce…provide instructions" is an explicit ordered list.

- **G11 → AT12, G12, AT20 [AND](sequential)**

- **G12 → G13, AT18, AT19 [AND][FALLBACK(FALLBACK(G13,AT18),AT19)]**

  - *Justification*: "comes out of a room…must be sterilized" — exit then sterilize.

- **G19 → AT25, G4 [AND](sequential)**
