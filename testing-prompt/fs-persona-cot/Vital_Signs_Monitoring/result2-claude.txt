# Goal Model Analysis – Hospital Multi-Robot Vital Signs Checking Mission

## Step‑by‑Step Reasoning

Before building the tables, here is the analytical path I followed and the key decisions/reflections that shaped the tree.

**1. Finding the root.** The mission's overarching intention is "every two hours, all patients' vital signs should be checked." This is a state to be reached (not a single action), so **G1 is an Achieve goal**.

**2. Finding the top-level contingency.** Two sentences at the end of the text ("Additional robots can be assigned to help…", "The responsible manager…must be alerted if no combination of robots can complete the mission") describe an explicit escalation order: *try with the mission as planned → if infeasible, alert the manager*. This is a textbook **FALLBACK**: G1 = FALLBACK(G2, AT‑AlertManager).

**3. Reflection on "additional robots".** My first instinct was to model "use additional robots" as its own fallback branch (mirroring the nested FALLBACK example given in the prompt). On reflection, this would **violate the no-redundancy rule**: adding robots doesn't change *what* is done (visit rooms, check patients) — it only changes *how many agents* do it. So instead of duplicating the "visit rooms" goal, I encoded this as a **Number‑of‑Robots range `[1,N]`** on the room-prioritization task. The genuine nested-FALLBACK pattern was reserved for a case where it's truly justified (see point 6).

**4. OR is rare here.** The description contains only **one** explicit alternative marked with "either…or": identifying the patient "either by asking or by scanning the patient's barcode." This is the only OR-decomposition in the model; everything else is conjunctive (AND), consistent with the instruction to use OR only for genuine stated alternatives.

**5. Two more FALLBACKs from explicit conditionals.** "If the patient is not available → come back in 5 minutes" and "If there is not enough battery → recharge and reassign" are both normal-behavior/exception patterns → **FALLBACK**.

**6. The nested FALLBACK.** "The failure of collecting any necessary vital signs should trigger a set of questions… In case of non-response, an alert should be sent…" is a two-stage escalation on top of normal measurement — this is a direct match for `FALLBACK(FALLBACK(exp1, exp2), exp3)`.

**7. Avoiding redundancy across patient conditions.** Infectious-disease, post-surgical, and diabetic patients share overlapping vital-sign requirements (e.g., heart rate and blood oxygenation appear for both infectious and post-surgical patients). Rather than creating separate "check infectious patient" / "check post-surgical patient" goals (duplicate intentions), I created **one task per vital sign** (heart rate, blood pressure, temperature, oxygenation, glucose) and noted the *conditions that trigger each* in its justification. This keeps each distinct intention (measuring a given vital sign) represented exactly once.

**8. Sequencing vs. parallelism.** I used **sequential (;)** only where the text gives an explicit temporal order (e.g., "before entering… once inside… comes out of the room…"; approach → announce → instruct). I used **parallel (#)** where actions are conjunctive but unordered (e.g., checking availability "and" battery; the five vital-sign measurements, which have no stated order).

**9. Zero-robot check.** I verified every leaf task is physically/communicatively executed by a robot (including alerts, which are "sent" by the robot) — nothing purely administrative/human-only was included, per the exclusion rule.

**10. High-risk timing constraint.** "All high-risk patients must be checked in the first 15 minutes" doesn't introduce a new *intention* (it's still "visit and check a room") — duplicating the whole per-room subtree for "high-risk" vs. "normal" rooms would be redundant. Instead, I modeled it as a scheduling **task** (`AT2: Prioritize High-Risk Patient Rooms`) that orders the room queue, keeping the per-room procedure defined once and reused for every room regardless of risk class.

## Logical Relationships

- **G1 -> G2, AT26 [AND] FALLBACK(G2, AT26)**
  - **Justification**: The mission is attempted as G2; only if that cannot be completed (even after scaling robots, see AT2) is the manager alerted. FALLBACK requires its two branches to be AND-related.

- **G2 -> G3, AT2, G4 [AND] (sequential: G3 ; AT2 ; G4)**
  - **Justification**: Rooms must be identified, then ordered by priority, then processed — a logical and explicit sequence; all three are jointly necessary (AND).

- **G3 -> AT1 [AND]**
  - **Justification**: A single task fully operationalizes this query goal; no alternative method is described.

- **G4 -> G5, G6(in-room check), G7(exit) [AND] (sequential: G5 ; G6 ; G7)** — *(note: here "G6" refers to the in-room-check goal, listed as G11 in the tables; "G7" refers to G13, the exit goal — relabeled below using the final IDs)*
  - **G4 -> G5, G11, G13 [AND] (sequential: G5 ; G11 ; G13)**
  - **Justification**: "Before entering…", "Once inside…", "comes out of a room…" explicitly separate the mission into pre-entry, in-room, and post-exit phases, each required (AND) and ordered (sequential).

- **G5 -> G6, G7, AT10 [AND] (sequential: G6 ; G7 ; AT10)**
  - **Justification**: The patient must be identified and readiness verified before the robot physically enters; all three steps are mandatory.

- **G6 -> AT3, AT4 [OR] (unordered: AT3 # AT4)**
  - **Justification**: "either…or" explicitly marks these as alternatives; only one need succeed.

- **G7 -> G8, G9 [AND] (parallel: G8 # G9)**
  - **Justification**: Both checks are required ("and") with no stated order, so they may be performed concurrently.

- **G8 -> AT5, AT6 [AND] FALLBACK(AT5, AT6)**
  - **Justification**: Checking availability is the primary action; returning later is only attempted if that check indicates unavailability.

- **G9 -> AT7, G10 [AND] FALLBACK(AT7, G10)**
  - **Justification**: Checking battery is primary; recharging/reassigning is only triggered if the check indicates insufficiency.

- **G10 -> AT8, AT9 [AND] (parallel: AT8 # AT9)**
  - **Justification**: Both are consequences of the same trigger (low battery) with no stated dependency between them.

- **G11 -> AT11, AT12, AT13, G12 [AND] (sequential: AT11 ; AT12 ; AT13 ; G12)**
  - **Justification**: The text lists approach, announcement, and instructions in that order, naturally preceding the actual measurement phase.

- **G12 -> AT14, AT15, AT16, AT17, AT18, AT19, AT20 [AND] FALLBACK(FALLBACK((AT14#AT15#AT16#AT17#AT18), AT19), AT20)**
  - **Justification**: The five measurements have no stated order (parallel). If any fails, assessment questions are triggered (first fallback); if the patient doesn't respond, an alert follows (second, nested fallback) — directly matching the description's two-stage escalation.

- **G13 -> AT21, AT22, AT23, AT24, AT25 [AND] (sequential: AT21 ; AT22 ; AT23 ; AT24 ; AT25)**
  - **Justification**: "afterwards" (disinfection after contact), "mark it as done" before proceeding, and "comes out of a room…sterilized" (after exiting) together establish this explicit order; all steps are conditionally mandatory when applicable.

### Key modeling assumptions worth flagging
- "Additional robots" is treated as a resourcing attribute (`[1,N]` on AT2) rather than a duplicate goal branch, to satisfy the no-redundancy rule — happy to revisit this if you'd prefer an explicit fallback branch instead.
- Patient identification (AT3/AT4) is assumed possible before physically entering the room (e.g., via a door-mounted scanner or intercom); if identification actually requires being inside, G6 would move after AT10.
- "Patient contact" (triggering AT21) is assumed to occur during the vital-sign measurements (cuff, probe, fingerstick), since no other contact-based action is described.
