# Multi-Robot Goal Model — Hospital Vital-Signs Monitoring Mission

Before building the tables, here is my step-by-step reasoning, since the structure of the tree depends entirely on these interpretive choices.

## 1. Reasoning and Decomposition Strategy

**Step 1 — Find the root and its contingency chain.**
The mission is triggered periodically ("every two hours"), so I made this an **Achieve** goal (G1): the target condition is a *state of the world* (all patients checked, mission completed in time), not a single action. The text then gives an explicit **conditional alternative chain**: normal execution → *if* impossible in time → assign additional robots → *if still* impossible → alert the manager. Because the order and the triggering condition ("in case of impossibility", "if no combination … can complete") are explicit, this is a textbook case for **FALLBACK**, nested because FALLBACK is binary: `FALLBACK(G2, FALLBACK(AT27, AT28))`.

**Step 2 — Separate "knowing what to visit" from "visiting".**
"Visit every occupied room" presupposes knowing which rooms are occupied — an implicit but necessary **query** step. Likewise, "high-risk patients must be checked in the first 15 minutes" presupposes knowing *who* is high-risk. I modeled both as lightweight tasks (not full goals, since the text gives them no further structure) occurring **sequentially before** the room-processing goal, since you logically cannot prioritize or visit what you haven't identified yet.

**Step 3 — The per-room pipeline.**
Inside a room visit, the text gives three clearly separated phases, performed in this explicit order: *before entering* (checks) → *once inside* (procedure) → *once checked* (mark done, decontaminate, move on). This is a textbook **sequential (;)** relation at the G4 level.

**Step 4 — Parallel vs. Sequential vs. Fallback, applied consistently.**
- "Check if the patient is available **and** if there is enough battery" — two independent conditions joined by "and", no order stated → **parallel (#)**.
- "If the patient is not available, come back in 5 minutes" / "If there is not enough battery, recharge and reassign" — explicit condition triggering an alternative path → **FALLBACK**.
- "Recharge … and … reassign" — no explicit order between these two remedial actions → **parallel (#)**.
- "Approach … announce … provide instructions" — three actions listed in an explicit order with no conditionality → **sequential (;)**, and because none of them has a persisting target state (they just need to be *executed*), I classified the parent as a **Perform** goal.
- "Identify the correct patient **either** by asking **or** by scanning the barcode" — a genuine interchangeable alternative, not a failure-triggered alternative → this is the **only OR decomposition** in the model (runtime `#`, since neither method is obligatory relative to the other).
- "Failure of collecting any vital sign triggers a set of questions… in case of non-response, an alert is sent" — two chained, explicitly failure-triggered alternatives → **nested FALLBACK**.
- The four/two/one vital-sign requirements per condition (infectious disease, post-surgical, diabetes) are **not mutually exclusive** (a patient could be both post-surgical and diabetic), so determining them is modeled as three independent **parallel (#)**, **AND**-related checks, not OR.
- Sterilization (condition: infectious room) and actuator disinfection (condition: patient contact) are independent triggers that can co-occur → **parallel (#)**, **AND**.

**Step 5 — Goal typing.**
Most nodes are **Achieve** goals because the description is about reaching and maintaining states (patient available, battery sufficient, vitals collected, room decontaminated). Two nodes are pure information-retrieval and got the **Query** type (identifying the patient; determining which vitals are required). One node (approach/announce/instruct) is a **Perform** goal because its success is defined purely by execution of the actions, not by a persisting world-state.

**Step 6 — Avoiding redundancy.**
I did **not** duplicate the entire "visit and check a room" subtree for high-risk vs. normal rooms. The "first 15 minutes" requirement is captured as a scheduling precondition (identify high-risk patients first, G3/AT2) that governs the **order in which the single, generic room-processing goal (G4) is instantiated**, rather than creating two parallel copies of the same intention — this follows the rule that a single intention must only be represented once.

**Step 7 — Zero-robot check.**
Every leaf task in the model is executed by a robot (even "alert the manager" and "alert the nurse/doctor" are actions *performed by* the robot — sending the alert — even though the recipients are humans). No purely human-only activity was added as a node.

## 5. Logical Relationships

- **G1 -> G2, AT27, AT28 [AND] FALLBACK(G2, FALLBACK(AT27, AT28))**
  - **Justification**: Normal execution (G2) is attempted first; additional robots (AT27) are the first fallback if the mission cannot be completed in time; alerting the manager (AT28) is the final fallback if even reinforcement fails. Both fallback legs are AND-connected per the FALLBACK rule.

- **G2 -> AT1, G3 [AND] (sequential: AT1 ; G3)**
  - **Justification**: The robot must know which rooms are occupied before it can process them in priority order.

- **G3 -> AT2, G4 [AND] (sequential: AT2 ; G4)**
  - **Justification**: High-risk patients must be identified before room visits can be scheduled to respect the 15-minute constraint.

- **G4 -> G5, G9, G17 [AND] (sequential: G5 ; G9 ; G17)**
  - **Justification**: The description explicitly separates "before entering," "once inside," and "once checked" as three successive phases of a single room visit.

- **G5 -> G6, G7 [AND] (parallel: G6 # G7)**
  - **Justification**: "Check if the patient is available **and** if there is enough battery" — a conjunction with no stated order.

- **G6 -> AT3, AT4 [AND] FALLBACK(AT3, AT4)**
  - **Justification**: "If the patient is not available, the robot should come back in 5 minutes" is a condition-triggered alternative.

- **G7 -> AT5, G8 [AND] FALLBACK(AT5, G8)**
  - **Justification**: "If there is not enough battery, the robot should recharge…" is a condition-triggered alternative.

- **G8 -> AT6, AT7 [AND] (parallel: AT6 # AT7)**
  - **Justification**: "Recharge **and** the tasks need to be reassigned" — no explicit order between the two remedial actions.

- **G9 -> G10, G11, G12 [AND] (sequential: G10 ; G11 ; G12)**
  - **Justification**: Identification, then preparation ("approach, announce, instruct"), then vital-signs collection, are described in that explicit order.

- **G10 -> AT8, AT9 [OR] (no forced order: AT8 # AT9)**
  - **Justification**: "Either by asking or by scanning the patient's barcode" is the only genuine interchangeable alternative in the text, not a failure-triggered one — hence OR, not FALLBACK. The "#" denotes that neither method is obligatory relative to the other.

- **G11 -> AT10, AT11, AT12 [AND] (sequential: AT10 ; AT11 ; AT12)**
  - **Justification**: "Approach the patient, announce the procedure… and provide instructions" is an explicit ordered list.

- **G12 -> G13, G14 [AND] (sequential: G13 ; G14)**
  - **Justification**: The required vitals must be determined before they can be collected.

- **G13 -> AT13, AT14, AT15 [AND] (parallel: AT13 # AT14 # AT15)**
  - **Justification**: The three condition checks are independent and non-mutually-exclusive (a patient can be post-surgical and diabetic at once), so all are required (AND), with no stated order (parallel).

- **G14 -> G15, G16 [AND] FALLBACK(G15, G16)**
  - **Justification**: "The failure of collecting any necessary vital sign should trigger a set of questions" is an explicit failure-triggered alternative.

- **G15 -> AT16, AT17, AT18, AT19, AT20 [AND] (parallel: AT16 # AT17 # AT18 # AT19 # AT20)**
  - **Justification**: Whichever vitals are required for a given patient must all be collected jointly (never just one), and no measurement order is stated.

- **G16 -> AT21, AT22 [AND] FALLBACK(AT21, AT22)**
  - **Justification**: "In case of non-response, an alert should be sent" is an explicit failure-triggered alternative.

- **G17 -> AT23, G18, AT26 [AND] (sequential: AT23 ; G18 ; AT26)**
  - **Justification**: "Once the patient is checked, mark it as done and proceed to the next room," with decontamination occurring upon exit — an explicit order.

- **G18 -> AT24, AT25 [AND] (parallel: AT24 # AT25)**
  - **Justification**: Sterilization (infectious-room condition) and actuator disinfection (contact condition) are independent and can co-occur, with no stated order.

### Notes and Assumptions
- AT1, AT2, AT13, AT14, and AT15 are not literal sentences from the text but are **necessary operational prerequisites** for explicitly stated requirements ("visit every occupied room," "high risk… first 15 minutes," and the condition-specific vital-sign lists); I flagged each clearly in its justification.
- The "first 15 minutes" constraint was deliberately **not** modeled as a duplicated subtree (high-risk room visit vs. normal room visit) to respect the anti-redundancy rule — it is instead captured as a scheduling precondition (AT2) that governs the order in which the single, generic G4 procedure is invoked.
- All leaf tasks are robot-executed, so no zero-robot nodes appear in the model.
