# Goal Model Decomposition — Lab Sample Transport Mission

## Step 1: Identifying Actors and Filtering Zero-Robot Activities

Before building the tree, I went through the description sentence by sentence to separate **robot-executable** activities from **human-only** activities, since the instructions require that goals/tasks performed by zero robots be excluded from the model.

| Mission statement | Actor(s) | Decision |
|---|---|---|
| "A nurse... can request a delivery" | Nurse (human) | **Excluded** — zero robots, pure trigger event |
| "Each sample... is identified with a barcode" | Nurse/lab staff (implicit) | **Excluded** — zero robots |
| "The nurse inserts data... in a track system" | Nurse (human) | **Excluded** — zero robots |
| "Samples are transported in secure locked drawers" | Transport robot (implicit) | **Included** — physical transport is the core robotic function |
| "Only authorized personnel **or specific robots** in specific locations... open the locked drawers" | Personnel (human) OR Robot | **Partially included** — only the robot branch is modeled; the personnel branch is dropped per the zero-robot rule |
| "the sample can be picked by a robotic arm **or** laboratory personnel" | Robotic arm OR Personnel | **Partially included** — only robotic arm branch modeled |
| "The robotic arm picks up... scans... sorts... loads..." | Robotic arm | **Included** — explicit robot sequence |
| "Information about where/when... picked should be logged securely" | Logging tied to the pick event (robotic arm) | **Included** — tied to robot action |
| "Time between collection and delivery should be tracked" | Tracking tied to the transport robot's transit | **Included** — tied to robot action |

**Reflection:** Two places in the description present an explicit OR between a human option and a robot option (drawer opening; sample picking). Because an OR decomposition requires at least two valid children, and the human branch must be dropped, I collapsed these into the **single surviving robot branch** rather than forcing an artificial one-child OR node. I note this explicitly in each relevant justification below so the exclusion is traceable to the rule, not an oversight.

## Step 2: Identifying the High-Level Process Phases

The robot-relevant content naturally clusters into three parallelizable/sequential concerns:
1. **Transport** the sample (floor → lab) inside the locked drawer.
2. **Process** the sample once at the lab (pick, scan, sort, load).
3. **Monitor** the handling (secure logging of pick location/time; tracking elapsed collection-to-delivery time).

Transport must finish before processing can start (you cannot scan/sort a sample that hasn't physically arrived) → **sequential**. Monitoring, however, spans the whole timeline (time-tracking starts at collection and continues through delivery; logging happens at the pick event) → it runs **in parallel** with the other two. This gives the mixed-operator runtime `(G2;G3)#G4` at the root, which is why parentheses are required.

## Step 3: Drawer-Access Logic

The locked-drawer constraint ("only authorized personnel or specific robots in **specific locations**") applies at two physical/temporal points: loading at the patient floor and unloading at the laboratory. Rather than creating a separate intermediate "access control" goal (which would need a second child to satisfy the minimum-two rule), I folded both opening events directly as sibling tasks under the Transport goal, alongside the physical movement task — this keeps the "specific locations" constraint visible via each task's `Location` attribute, and avoids inventing a redundant goal layer.

## Step 4: Sequencing Within Sub-Processes

- Drawer tasks (open → move → open) follow physical/logical necessity (you can't transport before loading, can't unload before arriving) → **sequential**, even though not phrased as an explicit numbered list — this is inferred from real-world physical constraints, which the instructions say to be attentive to.
- The robotic-arm tasks (pick up → scan → sort → load) are **explicitly** ordered in the text ("picks up samples, scans the barcode..., sorts, and loads...") → **sequential**, strongly supported textually.
- No FALLBACK relations are used anywhere: the text never describes a failure condition with an explicit alternate behavior (e.g., "if the barcode can't be scanned, then..."). The OR statements present are alternatives of *agent* (human vs. robot), not failure-triggered alternatives, so FALLBACK does not apply here.

## Step 5: Goal Type Classification

- **G1, G2, G3** are **Achieve** goals: each requires planning/acting across multiple steps toward a target world-state (sample delivered; drawer relocated; sample scanned/sorted/loaded), not a single atomic action (ruling out Perform) and not mere information retrieval (ruling out Query).
- **G4 / G5** (logging) are **Achieve**: the goal is to cause a persisted state to exist (a secure log record), which is a world-state change, not a query.
- **G6** (time tracking) is a **Query** goal: its essence is obtaining/monitoring a piece of information (elapsed duration) to check protocol compliance, without itself changing the sample's physical state — this matches the Query definition ("Fetch Occupied Rooms" pattern) more closely than Achieve.

## Logical Relationships

- **G1 -> G2, G3, G4 [AND][(G2;G3)#G4]**
  - **Justification**: All three sub-goals are mandatory for a complete, compliant delivery (AND). Transport must complete before processing can begin (sequential G2;G3), while monitoring (G4) spans and overlaps the entire timeline rather than waiting for either to finish, hence running in parallel with the sequential pair.

- **G2 -> AT1, AT2, AT3 [AND](sequential: AT1;AT2;AT3)**
  - **Justification**: All three physical steps are required to achieve secure transport (AND). The drawer must be opened to load the sample before it can be moved, and it can only be opened again once it has arrived — a physical necessity that forces sequential execution, even though the text does not spell out the order in one explicit sentence.

- **G3 -> AT4, AT5, AT6, AT7 [AND](sequential: AT4;AT5;AT6;AT7)**
  - **Justification**: All four actions are explicitly and jointly required ("picks up... scans... sorts... loads") — AND. The mission text lists them in this exact order, which is an explicit textual sequence, directly supporting the sequential annotation.

- **G4 -> G5, G6 [AND](parallel: G5#G6)**
  - **Justification**: Both logging the pick event and tracking elapsed time are independently required monitoring obligations (AND) stated in separate sentences with no dependency between them, so they may proceed concurrently (parallel).

- **G5 -> AT8 [AND]**
  - **Justification**: The logging goal is realized through exactly one concrete recording action; the task is the sole necessary condition for the goal's fulfillment.

- **G6 -> AT9 [AND]**
  - **Justification**: The tracking goal is realized through exactly one concrete monitoring action; the task is the sole necessary condition for the goal's fulfillment.

### Notes on assumptions made
- The nurse-performed and personnel-performed branches (request, barcode attachment, data entry, manual drawer opening, manual picking) were **deliberately excluded** per the zero-robot rule, even where the text frames them as valid OR alternatives — I called this out at each relevant node rather than silently omitting it.
- "Number of Robots" values are inferred as 1 throughout, since the description consistently uses singular phrasing ("**a** nurse," "**the** robotic arm") and gives no fleet-size or concurrency figures; a real deployment could parameterize this as a range if multiple drawers/arms operate simultaneously across the hospital.
- "Delivery" (for time-tracking purposes) was interpreted as arrival at the laboratory (end of G2), since the text doesn't explicitly define delivery as post-processing.
