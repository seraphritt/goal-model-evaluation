# Goal Model Analysis: Lab Sample Transport & Processing Mission

## Step-by-Step Reasoning

**Step 1 — Identify the mission's atomic activities.**
Reading the description sentence by sentence, I separated every activity into either (a) something a human performs alone, or (b) something a robot performs or could perform. This matters because the rules state that *zero-robot* goals/tasks must not appear in the model.

**Step 2 — Apply the zero-robot filter.**
The following activities are explicitly human-only and are therefore **excluded** from the model (kept here only as justification, not as nodes):
| Excluded activity | Why excluded |
|---|---|
| "A nurse ... can request a delivery" | Administrative trigger, no robot involved |
| "Each sample ... is identified with a barcode" (before collection) | Performed by hospital/lab staff before any robot acts |
| "The nurse inserts data ... in a track system" | Manual data entry, no robot |
| "...picked by a robotic arm **or laboratory personnel**" | The personnel-branch is zero-robot; only the robotic-arm branch is modeled. Since the human alternative is dropped, no OR node is created (an OR needs ≥2 modeled children) — the robotic arm path is simply the direct, necessary path. |
| "Only **authorized personnel** or specific robots..." (drawer opening) | The personnel-branch is zero-robot; only "specific robots in specific locations" is retained, folded into the pick task's justification rather than invented as a separate unstated step. |

**Step 3 — Identify the robot-relevant backbone.**
What remains, and who/what performs it:
- A sample must physically move from the patient floor to the laboratory, secured in a locked drawer → **transport robot**.
- Compliance requires the collection→delivery interval to be tracked → the same transport robot is the only agent with first‑hand knowledge of both timestamps, so logging is attributed to it.
- At the laboratory, a robotic arm picks, scans, sorts, and loads the sample → explicit, ordered list of actions in the text ("picks up ... scans ... sorts, and loads") → clear **sequential** execution.
- The pick's location/time must be logged securely → tied to the arm's pick action, but not stated to block the rest of the sequence → modeled as **parallel**.

**Step 4 — Decide AND vs. OR.**
No surviving branch in the robot-only view has a genuine alternative (one-child-suffices) structure — every remaining activity is a *necessary* contributor to the mission. Hence every decomposition in this model is **AND**. (The text's two "or" statements were alternatives between a robot and a human, not between two robot options, so they don't survive as OR nodes once the human branch is removed.)

**Step 5 — Decide runtime annotations.**
- Transport happens, and only afterward does "in the laboratory" processing happen → text gives explicit before/after ordering → **sequential**, not fallback (there is no failure/exception/condition language anywhere in the description, so FALLBACK is never used in this model).
- Pick→scan→sort→load is an explicit ordered list → **sequential**.
- Time-tracking spans the whole transport rather than blocking it → **parallel**.
- Secure pick-logging can proceed alongside the rest of the arm's sequence → **parallel**.

**Step 6 — Classify goal types** using the Perform/Query/Achieve definitions (detailed per-goal below).

**Step 7 — Build tasks** with Location restricted strictly to locations named in the text (*patient floor*, *laboratory*) and Number of Robots inferred from singular references ("a nurse", "a robotic arm") absent any stated fleet size.

## Logical Relationships

- **G0 -> G1, G2 [AND] (sequential)**
  - **Justification**: Both transport and laboratory processing are required for the mission to succeed (AND). The description narrates transport first and lab-handling afterward ("...transported... In the laboratory, the sample can be picked...") — an explicit normal-flow ordering, not a conditional/failure case, so sequential (not fallback) is used.

- **G1 -> AT1, AT2 [AND] (parallel)**
  - **Justification**: Moving the sample and tracking its collection-to-delivery time are both mandated requirements of the transport goal (AND). Tracking spans the entire move rather than occurring strictly before or after it, and no explicit order is stated, so the two proceed in parallel.

- **G2 -> G3, AT7 [AND] (parallel)**
  - **Justification**: Completing the robotic-arm sequence and securely logging the pick event are both explicitly required (AND). Logging can begin as soon as the pick occurs, concurrently with the subsequent scan/sort/load steps, with no stated order between them — hence parallel.

- **G3 -> AT3, AT4, AT5, AT6 [AND] (sequential)**
  - **Justification**: All four actions are required to get the sample correctly loaded (AND). The text lists them in one explicit order — "picks up samples, scans the barcode ..., sorts, and loads the samples ..." — which is a mandatory left-to-right sequence, not merely a possibility, so sequential is used.

## Notes on Design Choices

- **No FALLBACK anywhere**: the description never contains conditional/exception/failure language ("if X fails, do Y"), so the fallback operator was never applicable.
- **No OR anywhere**: every "or" in the source text (robotic arm *or* personnel; authorized personnel *or* specific robots) was a robot-vs-human alternative. After applying the zero-robot exclusion rule, only one branch of each alternative survives, so no OR node (which requires ≥2 surviving children) could be legitimately formed — this is noted explicitly rather than silently fabricating a second branch.
- **Locations** used (Patient Floor, Laboratory) are exactly the two locations named in the text; no location was invented.
- **Robot counts** default to 1 throughout because the text only ever refers to singular agents ("a nurse", "a robotic arm") and never states fleet sizes or concurrency requirements — this is flagged as an assumption rather than a hard fact from the text.
